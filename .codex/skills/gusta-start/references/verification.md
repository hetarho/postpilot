# 조정자 소유 최종 검증

이 절차가 프레임워크 기본이다. 적용되는 프로젝트 지침·활성 문서가 다른 주체·시점·발행을 요구하면 [프로젝트 규칙 대조](../../gusta-update/references/project-rules.md)대로 원문·범위·변경안·영향을 제시하고 기본 절차로 맞춰도 괜찮은지 묻는다. 이미 구체적으로 승인한 변경은 재질문하지 않는다. 오래된 ARCH라는 이유만으로 정책을 바꾸지 않으며, 맡김에서는 미승인 차이를 parked로 남긴다. 다음 절차는 승인된 별도 예외가 없는 범위에 적용한다.

- **구현 세션·워커**: 바뀐 범위의 태스크 단계 검사(영향 단위 테스트·ARCH task 명령)만 커밋 직전 `vibe check --tier task`로 한 번 실행한다(편집마다 반복하지 않는다). 통합/e2e 테스트 코드는 함께 수정하되 실행할 명령·대상 spec은 result limits로 넘긴다. 세션 종료·태스크 done을 전체 작업 완료로 해석하지 않는다.
- **리뷰 세션**: 코드·acceptance·기존 검증 기록을 검토한다. 필요한 빠른 재현만 하고 브라우저·통합/e2e·전체 스위트를 다시 띄우지 않는다.
- **조정자**: 작업을 시작한 gusta-start 대화 하나가 최종 검증·push와 사용자 목표를 소유한다. CLI/loop 호스트가 실제 검사를 돕고 결과를 돌려준다. 실행기가 고장 나면 조정자가 기존 검사 범위를 유지해 직접 도구로 검증하고 결과를 기록한다. 다른 세션은 이미 실행 중인 최종 관문에 합류하고 새 e2e를 시작하지 않는다.

## 시간 예산

시간은 구현에 쓰고 전체 검증은 마지막 관문에 모은다. 시간 한도가 있는 맡김은 끝 구간을 예약한다. `vibe loop`는 이 구간에 새 일반 단위를 시작하지 않고 최종 관문·수정·push·CI를 실행한다(`reason:final-window`). 구간 = 실측 전체 검증 시간×2 + 최근 단위 시간 + (push 브랜치가 있으면) CI 대기. 측정은 batch/group 검사·`work finish`·`vibe design verify`가 runtime `timings.json`에 남기며(명령마다 최근 3회 중 최대), 측정 전 첫 실행만 max-hours의 20%를 쓴다. `--final-reserve-hours`가 있으면 그 값이다. 관문 검사의 제한 시간은 단위 timeout이 아니라 예약 구간 기준이다. 태스크 단계 명령 시간도 같은 파일에 남는다: 평균 60초가 넘는 명령(2회 이상)은 `vibe status`의 `taskChecks.slow`와 loop 보고서에 나오고, loop가 끝날 때 batch 이동을 inbox `suggest`로 한 번 제안한다 — 옮길지는 사람이 정한다(조정자·맡김은 ARCH를 고치지 않는다).

관문 실패는 실패한 것만 고친다: 결과 `next`대로 고친 부분을 `vibe check --tier task --diff-base <관문 커밋>`으로 먼저 확인하고 전체 관문은 한 번 더 돌린다. 실패 재현용 빌드·e2e는 `--heavy`로 한 번에 하나씩, 다른 검사와 동시에 돌리지 않는다. 관문 중·관문 실패 수정 중 새로 발견한 범위 밖 문제는 고치지 않고 보고서 limits와 inbox(`suggest` 또는 다음 태스크)로 넘긴다. 실패한 관문은 세션(`--tag`, 없으면 브랜치)마다 누적 3회가 상한이고 성공해도 초기화하지 않는다. CLI가 loop 밖에서도 세어 상한이면 명령을 돌리지 않고 거절한다(`refused:gate-cap`) — 남은 실패를 보고서와 `vibe inbox add --kind parked`로 남기고 멈춘다. loop는 같은 기록에 남기되 자기 상한(`--max-gate-attempts`, 기본 3, 2~5)으로 판정한다. 두 번째 실패 뒤 loop의 추가 수정은 같은 명령 계획의 실패 명령 집합이 엄격히 줄었을 때만이다(로그의 실패 개수·새 실패·불명확한 결과·timeout은 기회가 아니다). 실제 마감·남은 검증/CI 시간·단위 한도도 지킨다. 종료 결과는 전체 관문 시도·누적 실패/상한·남은 수정 태스크·실제 push 여부를 남기고 실패 후보를 게시하지 않는다.

loop의 자동 회복 상한은 보조 실행기의 경계다. 시작 대화는 결과를 읽고 사용자에게 남은 전체 시간·예산 안에서 실패 원인을 다시 판단해 필요한 수정만 새 하위 단위/일반 스킬로 끝내고 같은 `--tag`로 다시 검증한다(loop의 실패도 그 상한에 든다). 같은 loop를 새 예산으로 무작정 재시작하지 않고 이전 시도·변경·실패 집합을 잇는다. 사용자가 정한 전체 시도/시간 한도·실제 권한/안전 중단은 그대로 지킨다. 마지막 보고는 검증된 반영·원격 WIP 보존·미완료 작업을 구분한다.

## 작업 묶음과 기존 프로젝트

기본 매핑은 ARCH task → `--task-verify`, 빠른 통합 검사 → `--verify`, 통합/e2e·전체 스위트 → `--group-verify`다. 단위 결과는 로컬 작업 브랜치에 모으고 기본으로 `--push`를 붙이지 않는다. 기존 활성 묶음도 확정한 정책·검증 범위에 맞춰 `work configure`한다(진행 중 관문은 끝난 뒤 변경). 일반 `npm test`·`verify` 안에 브라우저가 포함됐는지도 실제 스크립트·테스트 의존성으로 확인한다. 이름만 보고 분류하거나 검사를 없애지 않는다.

기존 규칙과 충돌하면 gusta-create-architecture/gusta-update-ssot가 검증 범위·조건을 보존한 기본 단계 정리를 제안하고 승인 뒤 관련 활성 문서를 함께 맞춘다. 맡김의 기획 조각도 미승인 정책 차이를 추천안+inbox decided로 자동 변경하지 않는다. 구현 워커가 SSOT를 고치지 않는다. 별도 실행을 승인받은 경우는 그 범위만 예외로 두고, 비용·최종 검증 필요 여부와 CLI 지원 한계를 기록한다.

## 최종 관문과 push

1. 단위들을 통합하고 대상 브랜치의 최신 변경을 합친다. 조정 중에는 같은 checkout의 코드 쓰기를 멈추고 깨끗한 최종 후보를 확정한다. 기본은 모든 단위를 모은 뒤 한 번이며, 다른 세션 감지나 보고서 경계만으로 단위별 e2e/push를 켜지 않는다.
2. 조정자 CLI 한 곳에서 최종 검증한다: 묶음이면 저장된 `work finish` 관문, 단독이면 `vibe check --tier batch --tag <tag> --diff-base <묶음 시작 SHA> -- <command>`. batch/group은 clone 공용 heavy 락을 자동 획득하고 락 안에서 성공 기록을 재확인한다. 같은 트리·명령·범위의 성공은 재사용한다. `work finish`의 현재 검증 결과가 있으면 같은 e2e를 별도로 반복하지 않는다.
3. 실패하거나 실행 중 코드/HEAD가 바뀌면 push하지 않는다. 조정자가 수정 작업을 배정하고 변경 후 최종 후보를 다시 검증한다. 실행하지 않은 검사는 통과로 기록하지 않는다.
4. 성공한 검증 커밋을 `vibe push --verified-commit <검증 SHA>`로 전달한다(SETTINGS land·push대로 — 할 일이 없으면 CLI가 none으로 끝낸다). sync/retry로 코드·설정·SSOT가 달라지면 CLI가 push를 거절한다. 현재 후보를 다시 검증한 뒤 새 SHA로 재시도한다. STATE·태스크·보고서·work 실행 기록만의 변경은 재검증을 요구하지 않는다. CI는 실제 코드 push 후 한 번 기다린다(아래 CI 대기).

위임된 단위 세션에서는 호스트가 선점([세션 절차](session.md))을 맡는다.

단위별 push를 사용자가 명시하면 loop는 `--push-each-unit`, 묶음은 `--push <branch>`를 사용한다. 이 경우도 실제 push 전 관문은 조정자/호스트가 실행한다. 워커·리뷰어의 batch/group 실행은 기본 거절되며, 사용자에게 별도 실행을 명시적으로 요청받았을 때만 `--allow-final`로 예외를 표시한다. 락·실행 기록은 같은 clone의 worktree들이 공유하며 다른 clone의 직접 셸 실행까지 제어하지는 않는다.

## CI 대기

CI는 실제 push당 `vibe ci wait --commit <sha> --diff-base <묶음 시작 SHA> --json` 한 번 또는 push --wait-ci. Claude는 셸 백그라운드+하네스 완료 알림, Codex는 긴 timeout의 단일 블로킹 호출. sleep→조회→보고 모델 루프 금지. 긴 e2e·벤치마크도 완료까지 모델을 깨우지 않는다. CI를 읽을 수단이 없으면(gh·토큰 없음, 비공개 저장소, GitHub 원격 아님) CLI가 유예 뒤 `unchecked`(ok)로 돌려준다 — 멈추거나 수정 태스크를 만들지 않고 보고서 next에 `check CI later: <sha> <checkUrl>`로 남긴다. 맡김에서 실패는 근거를 담은 수정 태스크를 만들어 **다음 단위로 우선 실행**한다. 수정 태스크 생성만 하고 종료하지 않는다. 기획 판단은 SKILL.md 3절대로 해소하고, 실제 권한·외부 작업에 막히면 해당 건만 parked 후 다른 태스크로 간다. 시간·단위 한도와 반복 무진행·실행 실패 제한은 유지한다. run 없는 push는 CLI가 skipped로 마친다.
