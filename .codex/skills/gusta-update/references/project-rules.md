# 프로젝트 규칙 대조

업데이트는 설치 성공과 lint 통과만으로 끝나지 않는다. 패키지가 바꾸는 동작과 프로젝트가 현재 요구하는 절차를 대조하고, 차이가 있으면 현재 프레임워크 기본 절차에 맞추는 안을 권유한 뒤 괜찮은지 묻는다. SETTINGS는 CLI 실행값의 정본이며, 프로젝트 정책 변경 승인까지 뜻하지 않는다. 승인 전에는 적용되는 사용자·범위별 지침을 지킨다.

업데이트는 아래 전체 조사를 수행한다. 설정 변경·초기화·ARCH 개정에서 이 절차를 참조할 때는 해당 작업에 적용되는 지침과 바꾸려는 주제의 활성 규칙·실행 근거·연결 문서만 조사한다. 범위가 불명확하면 inventory로 넓힌다. 설정 보기만으로는 조사나 정책 변경을 시작하지 않는다.

## 1. 조사 범위와 완결성

- 먼저 `gusta upgrade-context --limit 1`로 snapshot·total을 확인하고, 같은 `--snapshot <snapshot> --limit <total>` 결과 전체를 대상 프로젝트 밖의 세션 임시 JSON 파일에 한 번 저장한다(total이 0이면 최소 limit 1). 저장한 목록을 네이티브 도구로 나눠 읽고 처분을 기록한다. CLI 페이지마다 트리 전체를 다시 해시하므로 큰 목록을 수백 번 재조회하지 않는다. snapshot 불일치는 새 목록으로 조사하고, 설치·이관 뒤 변경 대조와 실제 반영 전에는 원문·해시를 다시 확인한다.
- `complete`는 목록의 마지막 페이지라는 뜻이다. `coverage.inventoryComplete`도 true여야 목록 조사가 끝났으며, `coverage.policyReviewed:false`는 정책 판단을 하지 않았다는 뜻이다. `errors`·읽기 실패·경계·참조 미확인을 숨기거나 검토 완료로 세지 않는다.
- 모든 entry에 조사 처분과 이유를 남긴다: 활성 규칙·설명/참조·구현/CI 근거·생성물/외부 소유·역사 기록·미확인. CLI의 kind·scope·disposition은 발견 단서이며 의미 판정이나 지침 우선순위가 아니다. 낯선 파일명·확장자 없음·숨김/ignored 경로도 목록에 있으면 검토한다.
- 루트와 중첩 경로의 AGENT.md·AGENTS.md·CLAUDE.md, README·CONTRIBUTING·spec·임의 위치의 운영 문서를 포함한다. 이 이름들만 찾는 허용 목록으로 범위를 줄이지 않는다. 실제 적용 지침, 문서의 목적·목차·본문과 인용/링크/include를 확인하고 참조가 이어지는 곳까지 조사한다. 파일명이나 알려진 키워드가 없다는 이유만으로 무관·충돌 없음으로 판정하지 않는다.
- 네이티브 검색·읽기 도구로 문서의 범위와 규칙 블록 전체(조건·예외·의무·시점·주체 포함)를 읽는다. 링크한 로컬 문서·CI/스크립트·설정·생성 원본도 확인한다. 저장소 밖 참조가 필요하지만 읽을 수 없으면 그 한계와 영향받는 동작을 남긴다. 목록의 snapshot은 이후 본문 읽기를 고정하지 않으므로 편집 전 원문·해시가 달라졌으면 해당 근거를 다시 읽는다.
- 제3자·생성물·완료 태스크/보고서 등 역사 기록은 이유를 확인해 제외하고 고치지 않는다. 활성 문서가 이를 현재 규칙으로 인용하면 필요한 파일만 읽어 정본과 유효성을 확인한다. 생성 문서의 규칙은 원본을 찾으며, 명시된 경계가 프로젝트 소유 문서를 가렸다면 그 범위를 별도로 조사하거나 미확인으로 남긴다.
- 중첩 checkout 경계는 별도 조사 범위이지 그 안의 정책이 없다는 뜻이 아니다. 조사는 읽기 전용으로 할 수 있지만, 반영 전에는 현재 checkout과 연결된 worktree의 활성 세션·문서 소유권·미커밋 작업을 확인한다. 루트가 깨끗하거나 todo로 보인다는 이유로 다른 세션의 문서·ref를 바꾸거나 plan-sync/plan-push하지 않는다. PID가 다른 프로세스/컨테이너에서 보이지 않는다는 이유만으로 종료를 추론하지 않는다. 권한·소유자가 명확하면 맡은 범위에서 진행하고, 불명확하면 사용자/소유자와 조정하며 기존 변경을 보존한다.

검토표에는 경로·근거 줄/블록·소유/적용 범위·현재성·참조 대상·대조 결과·미확인 이유를 남긴다. 파일 목록을 끝까지 받은 것과 규칙/구현 대조를 끝낸 것을 구분한다.

## 2. 규칙·설정·실제 동작 대조

- 같은 주제이며 적용 경로·작업·시점이 겹치는 규칙만 서로 대조한다. 루트 지침과 하위 경로의 정당한 예외, 설명과 의무 규칙, 과거 기록과 현재 정책을 한 규칙으로 합치지 않는다. 실제 지침 적용 범위는 그 지침과 호스트의 규칙을 따른다.
- `settings`의 유효값·source·default·legacy 출처와 버전 변경 내용을 본다. 누락된 키의 새 기본값도 동작이며, 이미 승인된 프로젝트 선택으로 해석하지 않는다. 이전 동작을 확인할 수 없으면 추측하지 말고 미확인으로 표시한다.
- 문서끼리만 비교하지 않는다. 실제 설정 소비 코드, package 스크립트·CI/workflow·호출 플래그 등 실행 근거와도 맞춘다. 문서와 코드가 다르다는 사실만으로 문서를 코드에 맞추지 않는다. 코드가 틀렸거나 패키지가 그 절차를 지원하지 못할 수 있다.
- 활성 태스크의 acceptance도 현재 계약으로 대조한다. 참조한 테스트·스크립트가 실제로 수행하는 범위와 의존성을 읽고, 이름만으로 단위/통합 검사를 분류하지 않는다. 전체 검사를 done 조건으로 요구하면 태스크의 변경 영향 빠른 검사+명령/범위 인계, 최종 관문의 같은 전체 범위 실행·실제 증거를 추천하되 완료 시점/주체 변경은 승인받고 활성 계약도 함께 고친다. 미실행 검사를 통과로 표시하거나 필요한 범위를 없애지 않는다.
- 브랜치/기획 발행·검증/리뷰·배포·권한/MCP·정리/보존·자동화/위임을 시작점으로 보되 이 목록을 조사 한계로 삼지 않는다. 각 문서의 실제 규칙에서 추가 주제를 찾는다. 예를 들어 PR 정책이 코드뿐 아니라 spec 발행에도 적용되는지, 필수 검사의 실행 시점·주체도 계약인지 확인한다.
- 결과를 동일·상호보완·범위가 다른 예외·직접 충돌·패키지 미지원·판단 불가로 나눈다. 설정값 하나가 같아도 더 넓은 프로젝트 제약이 남아 있으면 해결로 세지 않는다.

## 3. 판단·반영·재검토

- 자동 적용은 동작이 같은 것으로 근거가 확인된 사실/표기 정리와 구조 이관뿐이다. 조건·예외·수치·부정·의무 수준·실행 주체/시점이 바뀌면 정책 선택이다. 문서가 오래됐거나 FORMAT diff에 extra로 나왔다는 것만으로 의도적인 정책을 삭제하지 않는다.
- 정책 선택이 필요하면 겹치는 범위, 양쪽의 실제 원문, 유효 설정과 실제 실행, 바뀔 파일·값·주체/시점과 영향·지원 한계를 모은다. **현재 프레임워크 기본 절차에 맞추는 안을 추천하고 "이렇게 맞춰도 괜찮을까요?"라고 묻는다.** 기존 규칙을 유지할 때의 지원 한계도 함께 알린다. 사용자가 이미 구체적인 변경을 승인했으면 다시 묻지 않고 그 범위에서 반영한다. 판단이 불가능하거나 답할 사람이 없으면 영향받는 작업과 필요한 결정을 parked로 남긴다. 맡김의 추천안 자동 채택 규칙으로 이 승인을 대신하지 않으며, 맡김에서 업데이트하지 않는 시작 조건도 유지한다.
- 승인된 선택만 SETTINGS와 모든 영향받는 활성 문서·범위별 지침에 일관되게 반영한다. SSOT 정책 변경은 gusta-update-ssot의 rev·chg·STATE 영향 절차를 따른다. 의미 보존 편집과 정책 변경을 구분하고, 변경한 문서가 다시 인용하는 규칙·진행 중 작업도 재확인한다. 역사 기록은 새 정책에 맞춰 다시 쓰지 않는다.
- 설정·문서만으로 구현할 수 없는 선택은 지원되는 것처럼 보고하지 않는다. 필요한 CLI/CI 변경을 따로 제안하고, 해결되지 않은 절차를 자동 발행·배포·삭제·권한 변경으로 우회하지 않는다.
- 새 inventory와 변경 diff로 반영 범위·근거·링크·제외·미확인을 재검토한다. lint는 구조 검사이지 정책 일치 증거가 아니다. 최종 보고에 검토한 범위와 남은 충돌/미확인·다음 결정을 명시하며, 미확인이 있는데 프로젝트 전체가 충돌 없다고 단정하지 않는다.
