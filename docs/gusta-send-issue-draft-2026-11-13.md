# [send-issue] 프로젝트 검증 지침의 사전 정합화와 성공 검사 재사용 실패 (+4)

## findings

### 1. 프로젝트 검증 지침을 실행·재사용 계획으로 정합화하지 못함
- where: gusta-init | gusta-update/references/project-rules.md | gusta-start 사전 점검
- kind: missing · severity: P2
- observed: 프로젝트 지침에는 전체 검증과 성공 결과 재사용이 함께 명시되어 있었다. CLI의 검증 해석은 declared:false, partial:true였고, 조정자가 별도 스크립트로 부족한 범위를 연결했다. 이후 전체 검증을 반복했다.
- expected: init/update에서 지침과 실제 명령을 대조하고, start가 그대로 실행할 수 있는 검증 계획과 재사용 조건까지 연결해야 한다.
- cause: 규칙 대조 절차는 있지만, 대조 결과가 실행 가능한 계획으로 연결되고 중복 실행을 방지한다는 보장이 부족했다. 이 세션에서 이전 init/update의 대조가 완료됐는지는 확인하지 못했다.
- suggestion: init/update 결과에 검사별 실행 주체·시점·입력·중복·재사용 조건을 포함하고, start 사전 점검에서 부분 해석과 미연결 명령을 확인한다. 필요한 정책 조정은 승인받아 관련 활성 지침에 함께 반영한다. 로컬 지침을 이유로 문제를 사용자에게 돌리지 않는다.

### 2. 성공한 하위 검사를 재사용하지 않고 전체 검증을 반복함
- where: gusta-start/references/verification.md | CLI `vibe check --tier batch`
- kind: time · severity: P2
- observed: 전체 검증 3회의 명령 실행시간은 약 11분 05초, 21분 00초, 39분 08초였다. FE 전체 검사만 3회, 합계 약 23분 17초 실행했다.
- expected: 수정으로 무효화된 검사와 미실행 검사만 선별하고, 유효한 성공 결과는 재사용해야 한다.
- cause: 지시 준수 실패다. 조정자가 만든 외부 스크립트가 매번 새 결과 목록으로 처음부터 실행했다. 기존 재사용 지시가 실제 실행 방식에 반영되지 않았다.
- suggestion: CLI가 구조화된 검사 계획을 받아 검사별 성공 결과와 입력 식별자를 보존하고 재개하도록 지원한다. 스킬에서는 이 방식을 정본으로 참조하고, 전체 스크립트 재실행을 기본 회복 경로로 삼지 않는다.

### 3. 단일 외부 명령 때문에 실패 변화와 회복 진행을 구분하지 못함
- where: gusta-start/references/verification.md | CLI `vibe loop`
- kind: missing · severity: P2
- observed: 첫 검증은 FE 테스트 2건, 다음 검증은 BE 계약 검사에서 실패했다. 외부 명령은 동일한 검증 스크립트 하나여서 실행기는 failure-set-not-improving으로 회복을 종료했다.
- expected: 전체 예산과 회복 상한을 유지하면서 실제 하위 검사 결과를 근거로 회복 가능성을 판단해야 한다.
- cause: 조정자가 전체 계획을 단일 명령으로 전달해 실패 비교 단위를 지나치게 크게 만들었다. CLI는 외부 명령 수준의 정보만으로 보수적으로 종료했다.
- suggestion: 하위 검사 ID·결과·실패 집합의 완전성을 전달하는 구조화된 인터페이스를 제공한다. 회복 상한을 완화하기보다 판단 근거의 해상도를 높인다.

### 4. 로컬에서 마감 가능한 단위가 미커밋 blocked로 반환됨
- where: gusta-start 단위 실행 | gusta-implement-task 마감
- kind: human · severity: P2
- observed: 한 단위는 약 55분 실행 후 시간 한도를 이유로 미커밋 종료했다. 다음 단위는 약 32분 실행하고 검사 통과를 보고했지만, 결과 문구 수정과 커밋을 남긴 채 blocked로 종료했다. 시작 대화가 두 작업을 다시 인수했다.
- expected: 단위 시간 한도 도달은 이어받을 실행 상태로 구분하고, 외부 판단 없이 마감 가능한 작업은 남은 전체 예산 안에서 이어 처리해야 한다.
- cause: 모델이 마감 가능한 잔여 작업을 blocked로 분류했고, 실행기는 그 출력을 받아 종료했다. 두 실행시간 전체를 낭비로 볼 수는 없지만 인수·진단 비용이 추가됐다.
- suggestion: blocked 반환에 외부 의존 사유와 다음 실행 가능 동작을 구분한다. 단위 시간 소진·문서 마감·커밋 잔여는 전체 목표의 중단과 분리해 회복 경로로 연결한다.

### 5. 최신 사용자 지시를 따르지 않고 검사를 재개했으며 하위 실행도 남음
- where: gusta-start 실행 중 제어 | 사용자 지시 반영
- kind: human · severity: P2
- observed: 사용자가 먼저 push하고 지연 원인을 보고하라고 했지만 조정자는 남은 검사 4개를 재개했다. 사용자가 다시 항의한 뒤 push했고, 재개한 검사는 배경에서 약 3분 더 실행됐다.
- expected: 최신 지시를 실행 순서에 즉시 반영하고, 검증 예외와 미완료 상태를 정확히 보고해야 한다. 중단 시 이미 실행한 하위 작업도 추적해야 한다.
- cause: 지시 준수 실패다. 조정자가 기본 검증 절차를 최신 지시보다 우선했고, 대화 중단 뒤 남은 하위 실행까지 정리하지 못했다.
- suggestion: 사용자 개입 시 기존 실행 계획을 재평가하는 절차를 제어 정본에 통합한다. CLI는 실행 소유권과 하위 프로세스 상태를 추적해 중단 요청의 적용 결과를 반환한다.
