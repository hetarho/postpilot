# Product model-request inventory

This inventory describes the current application request composers after T630, T626–T628, T631, T633–T637 and T649. It is a developer map of code and synthetic fixtures. It grants no access to customer requests and makes no claim about a historical provider call. The owning composer remains the authority for prompt text, ordering, optional material, output grammar and precedence.

From the repository root, enumerate the registered descriptors without starting the API, reading configuration or opening account storage:

```sh
cd backend
go run ./cmd/api prompt-inventory
```

The JSON declares `kind: "code"`, `material: "synthetic"` and `source_root: "backend"`. Every entry identifies its stage/mode, composer, repository-relative source files, activation, prompt/schema versions, parser, consumer and output contract. The aggregate lives in [cmd/api/prompt_inventory.go](../../backend/cmd/api/prompt_inventory.go); each context exports `RequestCompositions()` using the descriptor that also seeds its real request assembler. Dynamic fragments belong to those assemblers, rather than a second global prompt registry. Generation entries include synthetic assembled fragments, and `RequestCompositionFixtures()` exposes those same requests for all ten post modes.

## Inspection and execution

[llm.RequestComposition](../../backend/internal/llm/inspection.go) is an additive product descriptor on the actual `llm.Request`. It is not a prompt DSL. Fragments carry stable IDs, ordered safe text/source identifiers, message role, authorship, material role, owning files and activation. Omissions explain absent material. Selected stock-rule IDs retain the frozen order. Native speech fields describe description/text/settings without inventing System or User messages.

| View                       | What it establishes                                                 | How it is obtained                                                                                              |
| -------------------------- | ------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| Current code/configuration | The current composer and declared options                           | Code inventory; no account or execution claim                                                                   |
| Prepared request           | A locally assembled request that has not been issued                | `llm.PreparedRequestInspection(request)`; `Registry.Prepare(ctx, ref, request)` also resolves effective options |
| Captured request           | The effective application request at an observed adapter invocation | `Registry.Complete`; `Response.Inspection` or `llm.RequestInspectionFromError(err)`                             |
| Unavailable history        | No retained dispatch witness is available                           | `llm.UnavailableRequestInspection(stage, mode)`; no rebuilding from current settings                            |

Preparation and dispatch share the registry's effective-option resolver. Ordinary calls resolve the explicit admitted model, capability checks, stage override, reasoning omission/disable policy and default or requested budget. Frozen `Execution` calls retain their admitted model/budget/effort/schema policy instead of accepting a later override. Prepared inspection performs no provider call, free qualification, hold, fallback or canonical mutation.

Capture means the adapter was invoked; it does not assert network acceptance. Refused entitlement/capability checks, cancellation before dispatch and unsupported models cannot produce an issued witness. Adapter errors preserve their error chain and return a captured witness only when invocation occurred. A missing or malformed optional manifest leaves paid execution behavior intact with unavailable inspection, rather than inventing historical evidence.

The registry returns evidence to the caller. There is no LLM account-data store, general prompt log or new inspection RPC here. Durable owner result storage and customer read projections are later work (T640/T641). Captured text inherits the owning result's authentication, blind-comparison boundary, cache partition, deletion and purge policy. A crash or persistence failure may lose the witness; recovery never reconstructs it or repeats an uncertain paid call to restore inspection.

## Roles, authorship and measures

`Role` describes the application wire position. `Authorship` distinguishes code-supplied content from account-supplied configuration/material; it does not prove who originally composed every word. `MaterialRole` records the explicit semantic boundary. Thus an owner guideline may have the System role, a code-selected fictional scene may have the User role, and a reviewed AI plan remains a plan rather than becoming owner event evidence.

- Accepted voice projections and excerpts are style material. Fictional scenes, generated style samples and template form are not facts about this post.
- Literal template text retains its authoring basis, while a typed `write` topic is an instruction and a scoped `fact` is data from its specific answer field. Legacy plain template bytes retain unknown role; they are not reparsed into new roles at dispatch.
- Memo, explicitly supplied edit facts and selected memories are source material. Observation results remain identifiable visual interpretation, not owner taste or experience. Existing canonical prose does not reconstruct missing historical evidence.
- Frozen owner guidelines stay in order and retain their full lines. Stock filtering uses declared stage/output applicability, never keyword classification of owner prose.

Character counts are Unicode scalar counts; UTF-8 byte counts are separate. Reference-token estimates are labeled estimates when the owner has one, otherwise unknown. Provider prompt/completion/reasoning counts are actual reported usage when available, otherwise unknown. Native speech billing units are not fictional token counts. Inspection has no fields for credentials, endpoints/base URLs, provider SDK/network shapes, media bytes, signed links, supplier handles or supplier prices. Media fragments retain only safe product identifiers and their order.

## Verification and limits

Generation regression tests verify exact prompt-text reconstruction from ordered fragments, adversarial owner material equal to headings/delimiters, typed literal/topic/fact separation, NoVoice omission, ordered media redaction, real source-file references and frozen queued settings after live edits with no extra writer call. Registry tests verify effective ordinary overrides/defaults/disable, strict frozen execution, free admission, cancellation/refusal and captured/error evidence. Domain composer tests cover the existing authoring/style/memory/video/speech paths. The aggregate command has no account arguments and is exercised before platform boot.

This task exposes metadata and caller-returned dispatch evidence. It does not persist request history, create customer inspection RPCs, add provider calls, reconstruct old actual requests, add origin response fields or activate future sensory permissions. T636–T642 build those separately on the retained contracts.
