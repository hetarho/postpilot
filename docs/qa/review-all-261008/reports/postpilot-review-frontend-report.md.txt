### FE-A (P1) Memory directory refresh destroys active unsaved input

- Location: `frontend/src/pages/memories/ui/MemoriesPage.tsx:49` (`MemoriesPage` renders all MemoryRow/CreateMemorySheet content only under !isError); `MemoryEditForm.tsx:46` owns text/kind/tags exclusively in mounted local state; `entities/memory/api/useMemories.ts:25` uses staleTime0; memory CRUD invalidations are in `memory-mutations.ts:20,48,72` and `memory-cache.ts`.
- Trigger: open an existing memory's edit form, type changed text/tags, then a background ListMemories read fails (reconnect, sibling create/delete/update invalidation, or explicit client refetch). A previous successful list remains in Query cache, but isError hides its rows and unmounts the active form. Retry and reopen the same item: original persisted values return, with the unsaved edit gone and no discard choice.
- Concrete proof: actual MemoriesPage, real useMemories + mutation hooks, fake Auth/Memory RPC through createRouterTransport. Start with ORIGINAL MEMORY, type UNSAVED MEMORY, fail/refetch list, assert form disappears, restore list/retry/open, assert field ORIGINAL MEMORY. Probe passes. App globally disables refetch-on-window-focus, so focus alone is NOT the claimed trigger.
- User impact: transient directory read failure discards unrelated unsaved authored facts. This also unmounts an open CreateMemorySheet, since its host is under the same gate.
- Policy: ARCH20 shared controls/lifetimes; THEME9 unreliable cellular network, THEME34 input preservation; MEM30 failed saves preserve the form, analogous preservation is needed for a read of other rows. A transient read should retain last-known rows and mounted input while exposing retry; distinguish first-load error from background error.
- Scope confidence: formal candidate, outside pending T631/T633–T646 origin/prompt functionality. Do not yet claim all directories affected; GuidelineDirectory and VoiceScreen have comparable conditional mounts, but their durable actors need separate falsification.

### FE-B (P1) Resetting URL mutation while it is running permits stale publication writes

- Location: `features/record-published-url/ui/PublishedUrlField.tsx:101,105–108` keeps field editable and calls saving.reset on every input change; `:57,125` rely on saving.pending for admission; `entities/post/api/useSavePublishedUrl.ts:17–23` blindly replaces cached post on every response; `PublishedUrlField.tsx:28` keys/remounts the form by each response URL.
- Trigger: submit Naver URL /1 on a slow connection. While pending, correct the text to /2. Mutation.reset sets observer pending false even though /1 is still in flight, enabling Save and Clear. Submit /2. If /2 reaches the server before the older /1, /1 later overwrites the user's newer correction; each response also reseeds the form.
- Concrete proof: actual PublishedUrlField + useSavePublishedUrl + query cache; an isolated PostService delays the first write while accepting the second. Save begins disabled, typing enables it, both calls are accepted, /2 is displayed, release old call, persisted post/cache/form return to /1. Probe passes.
- Consequence: corrected publication URL can revert, and an older URL can republish a post after a newer clear intended to unlock editing. Even without a second submit, a response-keyed remount loses any correction typed while the save was pending.
- Policy: POST75 replacing/clearing published URL is explicit owner intent; POST84 refuses invalid address without altering previous saved state; THEME28 pending prevents repeated action and THEME34 input preservation. Keep in-flight admission independent of error-message reset; disable pending edits or serialize/coalesce newest intent and fence response-driven draft replacement.
- Scope confidence: this is an existing publication form outside T642's BlockEditor changes; root should check T646's qualification overlap before final classification.
