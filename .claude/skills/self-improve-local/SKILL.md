# self-improve-local — 제안 승인과 로컬 통합

**역할: 실행한 세션이 오케스트레이터.** 탐색 세션이 근거 있는 제안을 보내고, 이 세션이 범위·비용·위험을 판단해 승인한 뒤 구현 세션을 배정한다. 구현자가 아닌 별도 세션의 리뷰와 검증을 통과한 단위를 호출한 checkout의 브랜치에 통합한다. PR은 만들지 않는다. 오케스트레이터는 배정·기획·승인·검증·통합·보고를 맡고 워커의 코드를 대신 작성하거나 자기 구현을 승인하지 않는다.

## 공통 규칙 (모든 spec 스킬)
1. 먼저 `vibe status --json` 또는 실행기 brief로 필요한 STATE 요약만 본다. 없으면 create-architecture 실행을 안내한다.
2. **문서 먼저**: 쓰기 전 실행기 배정 또는 `work status --json`으로 확인한다(CLI가 없으면 checkout·사용자 배정 확인). 단독/기획은 STATE에 시작·상태 변화를 기록한다. 워커는 STATE·SSOT 대신 runtime과 자기 acceptance 체크·result만 쓴다. 리뷰는 읽기 전용이며 리뷰 runtime만 쓴다. 브랜치명은 소유권이 아니다. `vibe status`에 `design`이 있으면(이 checkout이 디자인 중) 커밋·push 전에 사용자에게 디자인이 끝났는지 묻고, 끝났으면 start-design 마감부터 한다 — 맡김은 디자인 변경을 건드리지 않고 주차한다.
3. 산출 문서는 spec/FORMAT.md 표기를 따른다. `vibe format --section task|state|ssot|report` 중 필요한 발췌만 보고 FORMAT 전체를 읽지 않는다. 규칙에 없는 표기는 만들지 않는다.
4. 질문·확인·보고는 cfg.lang 언어로, 상세도는 cfg.level대로. 산출 문서는 영어로 쓴다(FORMAT 언어 규칙). 선택지형 질문 도구(AskUserQuestion 등)가 있으면 사용. 맡김 모드(start-vibe)에서는 묻지 않는다 — 추천안으로 진행하고 STATE inbox와 보고서에 남긴다(되돌리기 어렵거나 프로젝트 밖에 영향을 주는 일은 주차). 권한 확인 창도 질문이다 — 창이 뜰 만한 명령은 실행하지 않고 주차한다(start-vibe 3절). 모드가 정해지지 않았으면 함께 모드다.
5. **읽기**: brief·status 요약을 먼저 쓰고 부족한 ID·섹션만 읽는다. 결정은 `vibe brief <T###|ID-n|ID@rev>`로 원문 블록째 받는다 — 끝의 `end` 줄이 없거나 complete:no면 빠진 부분부터 다시 읽고, unfollowed·related는 필요한 것만 연다. 직접 읽은 결정은 다음 결정 줄·제목까지 본 블록만 근거로 쓴다. STATE·FORMAT·ARCH·큰 코드 전체를 반복 읽지 않는다. tasks/done/은 특정 회귀·검증 근거만 선택 조회한다. 출력은 요약·tail, 전체 로그는 파일로 남긴다.

## 1. 호출과 실행 준비

이 스킬 호출은 이번 실행 범위 안의 동작 보존 개선을 오케스트레이터가 채택하고 로컬에 통합하라는 위임이다. 후보마다 사람에게 채택을 묻지 않는다. 지속 정책이 있으면 범위·예산을 이어받고, 없으면 이번 실행의 범위·예산·호출 권한을 review notes와 보고서에 기록한다. 호출만으로 상시 스케줄을 켜거나 큰 변화·원격 발행 권한을 추가하지 않는다.

- 호출한 checkout의 실제 경로·브랜치·HEAD·미커밋 변경·배정을 기록한다. 현재 브랜치가 통합 대상이다. main으로 임의 전환하지 않는다. 디자인·다른 작업자 소유 공간·미커밋 사용자 변경을 보존하며 충돌 가능한 쓰기는 주차한다.
- 독립적인 탐색·구현·리뷰 세션을 실제로 실행할 도구와 권한을 확인한다. 기본은 탐색 최대 2개, 구현 최대 2개, 독립 리뷰 1개이며 사용 가능한 슬롯·소유권·부하에 맞춘다. 특정 제품이나 모델을 필수로 요구하지 않는다. 실행 수단이 없으면 제안용 패킷까지 만들고 부족한 연결을 보고한다. 같은 대화에서 역할만 바꿔 하위 세션이나 독립 검토를 가장하지 않는다.
- 기본은 실행 60분·하루 누적 120분·단일 명령 15분과 문제 하나다. 긴 명령·재시도·리뷰 비용까지 예약한다. 이 직접 호출은 지금 한 사이클을 시작하며 일일 발견 주기를 기다리지 않는다. 세션 밖 자동 실행은 별도 설정이다.
- [배정과 통합 절차](references/workflow.md)를 읽는다. hostManaged 단위/묶음 워커/리뷰어로 배정된 세션은 오케스트레이터를 새로 만들지 않고 해당 배정을 마친다. 맡김에서 권한 창이 필요한 도구를 우회하지 않는다.

## 2. 하위 탐색 세션이 제안

실행 기록·느린 검사·재작업·변경 이력의 비용 상위 영역을 겹치지 않게 나누고 [탐색 프롬프트](assets/scout-prompt.md)로 배정한다. 탐색은 소스·기획·Git을 쓰지 않는다. 기존 로그와 제한된 읽기로 위치·증상·원인 가설·실제 근거·수정 범위·측정/검증·예상 비용·위험·되돌림을 제안한다. 승인 전에 코딩·장기 측정·설정 변경을 시작하지 않는다.

탐색 결과는 실행기 artifact로 받고 오케스트레이터만 기존 `spec/review/<slug>.md`의 finding과 notes로 정리한다. 관련 기존 태스크·PR·기각/실패 기록을 대조해 중복과 진행 중 소유 영역을 제외한다. 원시 근거를 직접 확인하며 요약이나 추측만으로 채택하지 않는다.

## 3. 오케스트레이터가 실행 승인

제안은 처음 [?]다. 오케스트레이터가 아래 기준으로 채택 [o] / 기각 [x] / 보류 [?]를 기록한다. 승인에는 제안 artifact·기준 HEAD·허용 touches·동작 보존 조건·측정 목표·검증 명령/단계·시간 상한을 연결한다. STATE inbox decided와 보고서에는 이번 위임 또는 기존 정책 근거와 선택 이유를 남긴다. 일반 review-code의 사람 채택 규칙은 바꾸지 않는다.

- **채택**: 관측된 문제이고 기존 계약을 보존하며 비용·영향·되돌림이 제한된다. 다른 제안과 겹치면 병합/직렬화한다. 근거가 부족하면 구현 대신 제한된 계측/탐색을 승인할 수 있다.
- **기각/보류**: 효과가 불명확하거나 중복·소유 충돌·예산 부족인 제안. 내용과 이유를 남기고 구현 세션을 배정하지 않는다.
- **사람 판단**: 결과 의미·정밀도·공개 계약·저장 형식·필수 검증 범위 변경, 광범위/영향 불명 변경과 되돌리기 어려운 일. 설계·근거·대안·권장 판단을 준비해 parked로 보고하고 다른 허용 작업을 계속한다. 오케스트레이터가 이 경계를 스스로 승인하지 않는다.

채택한 finding만 create-task로 만들고 승인된 태스크 ID를 작업 묶음의 `--tasks`에 명시한다. 제안 승인과 제출 코드 리뷰 승인은 별개다. 승인 뒤 범위·행동 계약·기준이 달라지면 구현 세션이 확대하지 않고 오케스트레이터에게 재제안한다.

## 4. 구현·독립 리뷰

[구현 배정 프롬프트](assets/worker-prompt.md)에 승인 근거·정확한 태스크·배정 workspace·검증·금지 사항을 포함해 implement-task로 보낸다. 탐색만 했다는 이유로 구현 권한이 자동 생기지는 않는다. 워커는 승인된 작업과 자신의 acceptance/result만 쓰고, STATE·SSOT·런타임 정책·다른 워커 영역은 바꾸지 않는다.

측정은 [측정 절차](../self-improve/references/measurement.md), 반복 실험은 [실험 루프와 도구](../self-improve/references/experiments.md)를 재사용한다. 측정·기록은 공유하되 통합/발행·완료 조건은 이 로컬 스킬을 따른다. 불확실한 explore와 그 후속은 기존 규칙대로 메인 세션에서 소유하고 작업 묶음에 넣지 않는다. 단위 테스트와 빠른 검사는 구현 단계, 무거운 전체 관문은 조정자 소유다.

제출 커밋은 작성자와 다른 세션이 review-task로 검토한다. 모든 개선은 리뷰하며 묶음은 `--review all`이다. P1/P2가 있으면 수정 후 재제출·재리뷰한다. 오케스트레이터의 사전 승인을 제출물 승인으로 복사하지 않는다. 검토자가 없으면 현재 브랜치에 코드 통합을 시작하지 않는다.

## 5. 현재 브랜치에 통합하고 마감

단위 검사와 독립 리뷰를 통과한 제출물은 오케스트레이터가 관리하는 CLI로 호출한 checkout/브랜치에 통합한다. 최종 후보에서 필수 통합/전체 검사를 한 번 수행하고 실제 통합 SHA·검증 SHA·배정 이력을 보고한다. 후행 관문이 실패하면 완료·push하지 않고 수정 또는 되돌림을 조정한다. 구현 worktree나 별도 작업 브랜치에만 결과를 남기고 로컬 통합이 끝났다고 보고하지 않는다.

기본은 현재 브랜치의 로컬 커밋까지다. PR·GitHub CLI는 필요하지 않다. 원격 코드 push는 사용자가 이미 지정한 cfg push/명시적 요청이 있을 때만, 조정자의 최종 검증 뒤 한 번 수행한다. 원격 권한이 없으면 로컬 결과와 미발행 상태를 분리한다. 기획 문서의 plan-sync/plan-push는 기존 cfg plan 정책을 따르며 이를 몰래 변경하지 않는다.

기존 reports 골격으로 done=승인 제안·태스크·통합 커밋, decided=오케스트레이터의 선택/기각 이유, parked=사람 판단·권한·미통합, checks=실측/검증/미실행/예산, next=다음 관찰·재개 지점을 남긴다. expert는 범위·수치·SHA·판정, mid는 개선 효과·비용·한계, novice는 달라질 작업 경험과 사람 판단부터 보고한다. 스케줄러가 연결되지 않았다면 자동 재실행을 약속하지 않는다.
