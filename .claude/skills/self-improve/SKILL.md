# self-improve — 지속 개선 조정자

**역할: 개선 조정자.** 사용자가 문제를 지정하지 않아도 실행 기록·코드·작업 흐름에서 개선 후보를 찾는다. 문제 발견 → 한 지표의 반복 실험 → 확인된 최선의 후보 → 독립 검토 → PR → 결과 관찰을 운영한다. 태스크·구현·기획은 기존 스킬에 맡긴다. 최적화할 대상과 검증 기준을 함께 바꿔 성과를 만들지 않는다.

호출한 세션이 하위 제안을 승인하고 PR 없이 현재 브랜치에 반영하는 요청이면 self-improve-local로 전환한다. 측정/실험 절차는 공유하지만 로컬 통합과 PR 발행을 혼동하지 않는다.

## 공통 규칙 (모든 spec 스킬)
1. 먼저 `vibe status --json` 또는 실행기 brief로 필요한 STATE 요약만 본다. 없으면 create-architecture 실행을 안내한다.
2. **문서 먼저**: 쓰기 전 실행기 배정 또는 `work status --json`으로 확인한다(CLI가 없으면 checkout·사용자 배정 확인). 단독/기획은 STATE에 시작·상태 변화를 기록한다. 워커는 STATE·SSOT 대신 runtime과 자기 acceptance 체크·result만 쓴다. 리뷰는 읽기 전용이며 리뷰 runtime만 쓴다. 브랜치명은 소유권이 아니다. `vibe status`에 `design`이 있으면(이 checkout이 디자인 중) 커밋·push 전에 사용자에게 디자인이 끝났는지 묻고, 끝났으면 start-design 마감부터 한다 — 맡김은 디자인 변경을 건드리지 않고 주차한다.
3. 산출 문서는 spec/FORMAT.md 표기를 따른다. `vibe format --section task|state|ssot|report` 중 필요한 발췌만 보고 FORMAT 전체를 읽지 않는다. 규칙에 없는 표기는 만들지 않는다.
4. 질문·확인·보고는 cfg.lang 언어로, 상세도는 cfg.level대로. 산출 문서는 영어로 쓴다(FORMAT 언어 규칙). 선택지형 질문 도구(AskUserQuestion 등)가 있으면 사용. 맡김 모드(start-vibe)에서는 묻지 않는다 — 추천안으로 진행하고 STATE inbox와 보고서에 남긴다(되돌리기 어렵거나 프로젝트 밖에 영향을 주는 일은 주차). 권한 확인 창도 질문이다 — 창이 뜰 만한 명령은 실행하지 않고 주차한다(start-vibe 3절). 모드가 정해지지 않았으면 함께 모드다.
5. **읽기**: brief·status 요약을 먼저 쓰고 부족한 ID·섹션만 읽는다. 결정은 `vibe brief <T###|ID-n|ID@rev>`로 원문 블록째 받는다 — 끝의 `end` 줄이 없거나 complete:no면 빠진 부분부터 다시 읽고, unfollowed·related는 필요한 것만 연다. 직접 읽은 결정은 다음 결정 줄·제목까지 본 블록만 근거로 쓴다. STATE·FORMAT·ARCH·큰 코드 전체를 반복 읽지 않는다. tasks/done/은 특정 회귀·검증 근거만 선택 조회한다. 출력은 요약·tail, 전체 로그는 파일로 남긴다.

## 1. 활성화·재개

처음 설정하거나 실행기를 연결할 때 [운영 정책](references/operation.md)을 읽는다. 한 번의 명시적인 지속 개선 위임을 ARCH의 결정 블록으로 보존하고, 이미 위임된 범위에서는 후보마다 승인을 다시 묻지 않는다. 스킬 설치만으로 지속 개선이 켜지지는 않는다. 정책이 없으면 이번 요청 범위의 진단·검토 가능한 초안까지 진행하고, 근거 없는 무기한 실행은 만들지 않는다.

- 시작은 정책·최근 개선 보고서·열린 개선 PR·진행 중 작업의 소유권 확인이다. 명시적인 사용자 작업, 실패한 필수 CI, 진행 중 디자인을 우선한다. 중복 실행이면 기존 사이클에 합류하거나 종료한다.
- 기본은 24시간 간격으로 문제 하나를 고르고, 그 문제의 고정 지표를 예산 안에서 여러 가설로 개선한다. 한 시도에는 변경 하나만 넣는다. 새 세션도 최초 기준선·최선 후보·시도 기록·사용 예산·실패 횟수·열린 PR을 이어받는다. 새 문제를 무한히 만들거나 정해진 횟수를 채우려고 장기 실험을 반복하지 않는다.
- 세션 중에는 사용자 작업 종료 후 또는 유휴 시작 시 정책이 허용한 주기로 진입한다. 세션 밖 실행은 실제 스케줄러/CI/에이전트 실행기가 필요하다. `vibe loop`는 기존 작업 소진 시 끝나며 개선 스케줄러가 아니다. 자동 실행을 연결하지 않았다면 그 사실과 다음 실행 방법을 보고한다.

## 2. 지시 없이 문제 발견

매번 전체 저장소를 감사하지 않는다. 지난 관찰 이후의 변경과 비용 상위 지점부터 읽고, 근거가 없는 영역은 순환해서 다음 사이클로 넘긴다.

- **실행 비용**: 기존 CI·테스트·벤치마크 기록의 실제 시간, 실행 횟수, 대기·CPU·메모리, 느린 상위 구간. 실행 시간이 없으면 계측부터 한다.
- **테스트**: 중복된 전체 실행, 비싼 fixture·초기화, 격리 가능한 I/O, flaky 재시도, 영향 범위보다 넓은 실행. 테스트 개수 자체는 개선 목표가 아니다.
- **엔진·코드**: 반복 계산·할당·I/O, 변경 시 자주 깨지는 경계, 기존 결함·프로파일의 병목. 긴 시뮬레이션은 먼저 기존 로그와 짧은 대표 입력으로 조사한다.
- **업무 흐름**: 같은 검증·읽기·기획의 반복, 재작업·인계 누락, 선점 충돌, 피드백 지연. 정확성·검증 공백이 있으면 속도보다 먼저 다룬다.

`spec/review/<slug>.md`의 기존 골격을 사용한다. finding은 위치·문제·영향을 갖추고, notes에 관측 출처·기준 commit·측정 시각·가설·기대 이익·비용·반증 조건을 적는다. 원인·경로·불변식이 같은 기존 finding/태스크/PR을 먼저 찾아 이어간다. 기각·실패한 후보는 새 근거가 있을 때만 다시 연다. 가치 있는 후보가 없으면 관찰 범위와 다음 시점을 기록하고 종료한다.

## 3. 채택과 사람 판단 경계

범위 안의 동작 보존 개선은 사전 위임을 근거로 [o]로 채택하고 notes·inbox decided에 정책 결정 참조와 이유를 남긴다. 이는 일반 review-code의 사용자 채택 절차를 바꾸지 않는다. 불확실한 후보는 [?]로 남긴다.

| 구분 | 판단 기준 | 진행 |
|---|---|---|
| 위임 범위의 작은 개선 | 결과·계약·검증 범위를 보존하며 영향과 되돌림이 국소적 | create-task → implement-task → 독립 검토 → PR |
| 큰 변화·근거 부족 | 알고리즘 의미·확률 분포·정밀도·공개 API·저장 포맷 변경, 검증 범위 축소, 광범위 구조/의존성 변경, 영향 불명 | [?] 유지, 설계·측정·호환성·되돌림을 갖춘 제안/격리된 초안까지만; 사람 판단 전 적용·통합하지 않음 |
| 위임 밖 작업 | 예산 초과, 과금·데이터 삭제·개인정보·보안 정책, 배포·외부 시스템 변경 | 해당 작업만 parked, 다른 허용 후보 또는 마감 |

파일·줄 수는 보조 신호다. 한 줄이어도 결과 의미를 바꾸면 큰 변화다. 큰 변화를 작은 PR 여러 개로 나눠 사람 판단을 피하지 않는다. 사람에게는 막연한 허가 대신 [PR 본문 템플릿](assets/pr-body.md)에 따라 실제 후보·증거·대안·권장 판단을 보고한다. 맡김에서는 답을 기다리지 않는다.

## 4. 측정과 구현

반복 실험을 시작할 때 [실험 루프](references/experiments.md), 비용을 측정할 때 [측정 절차](references/measurement.md)를 읽는다. 대표 작업·고정 지표·목표·회귀 검사·실행 상한을 먼저 확정하고, 측정기가 증상을 구분하며 실제 일을 세는지 확인한다. 기존 필수 검사를 없애거나 임계값·샘플·정확도를 낮춰 빨라졌다고 하지 않는다.

- create-task는 채택 finding을 기존 리뷰 태스크로 만든다. 불확실한 프로파일·시뮬레이션 탐색은 wall-clock 제한과 exit가 있는 explore 태스크로 분리하고 메인 세션에서 실행한다. 후속 구현은 실험 결과로 범위가 정해진 뒤 만든다.
- 실험은 확인된 최선 후보에서 한 가설씩 수행하고 측정·빠른 회귀 검사 뒤 유지/폐기/미확정을 기록한다. 효과가 없는 변경은 후보에 누적하지 않는다. 같은 전제의 실패가 두 번 반복되면 다음 수정 전에 그 전제를 직접 검증한다. 목표와 필수 검증 완료, 예산 종료, 실제 막힘을 구분해 마감한다.
- 코드/테스트/워크플로 수정은 개선용 브랜치나 배정된 worktree에서 implement-task로 수행한다. 사용자 진행 영역을 덮어쓰지 않는다. 기획 공간의 plan-sync → spec-only commit → plan-push와 전역 채번 절차를 지킨다. 코드 발행 권한과 기획 문서 발행 절차를 혼동하지 않는다.
- 워커는 영향 단위 테스트와 빠른 검사만, 조정자는 최종 후보에서 필수 전체 검증을 한 번 한다. 필요한 테스트는 위험·계약에 근거해 작성하며 개수·커버리지 수치를 맞추려고 복제하지 않는다. 캐시 재사용은 검증용이고 성능 비교의 새 표본이 아니다.
- 예산 부족·무진행·기준 미달이면 측정과 진행분을 보존하고 끝낸다. 미완료 검증을 pass로 기록하거나 자동 채택하지 않는다.

## 5. 독립 검토·PR

구현 전에 검토자 확보와 발행 가능 경로를 확인하고, 제출할 때 [검토·발행 절차](references/review.md)를 읽는다. **모든 자율 개선은 작성자와 다른 새 세션의 검토가 필요하다.** 다른 LLM은 선택할 수 있고, 같은 LLM의 별도 세션도 가능하다. 작성자가 역할 이름만 바꿔 자기 PR을 승인하지 않는다.

독립 검토자는 고정된 base/head commit·전체 diff·현재 계약·원시 측정·실제 검증 기록을 읽고 정확성, 측정 공정성, 검증 범위, 사람 판단 대상 여부를 판정한다. 제출 리뷰에서는 조정자 소유의 후행 통합/전체 검사를 명시적으로 인계할 수 있으며, 코드 리뷰 승인을 전체 검증 완료로 취급하지 않는다. 최종 관문 뒤 실제 PR 후보와 증거를 독립 검토자가 마감 확인한다. 실패는 제한 횟수 안에서 수정 후 새 head를 재검토한다. 검토자/권한이 없으면 검토 패킷을 남기고 review pending으로 종료한다.

허용된 개선 브랜치 push·PR 작성은 사전 위임 범위에서 진행하며 매번 허가를 다시 묻지 않는다. 일반 cfg push나 plan 브랜치를 PR 대상 코드의 직행 경로로 쓰지 않는다. 기본은 독립 검토와 필수 관문이 통과한 PR 작성까지다. 큰 변화·미검증·검토 대기는 허용된 draft PR 또는 로컬 초안으로 표시한다. merge는 별도의 명시적 사전 위임과 프로젝트 보호 규칙을 모두 만족할 때만 가능하며, 작성자 계정으로 플랫폼의 독립 승인 제한을 우회하지 않는다.

## 6. 피드백·종료

보고서는 기존 reports 골격만 쓴다: done에 finding/태스크·commit·PR, decided에 위임 내 채택 이유, parked에 사람 판단/검토/권한 부족, checks에 전후 수치·원시 근거·검증/미실행·소모 예산, next에 다음 관찰 시각·재개 지점을 남긴다. 새 cfg 키·STATE 섹션·별도 태스크 체계를 만들지 않는다.

merge된 개선은 다음 사이클에서 실제 CI/실행 기록으로 효과와 회귀를 확인한다. merge 전의 제안·국소 벤치마크를 운영 성과로 집계하지 않는다. 회귀 시 신규 최적화보다 중단·원인 기록·되돌림 제안을 우선한다. 자동 되돌림도 사전 허용 범위 안에서만 한다. 폐기·실패 실험과 비용도 남겨 같은 시도를 반복하지 않는다.

반복되는 교정은 원인이 확인되면 작은 검사·메타데이터·실행 규칙으로 옮긴다. 판단이 필요한 교훈만 스킬 문장으로 남긴다. 개선 기록은 행동을 설명하는 검토 가능한 근거이며 모델의 내부 사고를 수집하지 않는다.

최종 보고는 cfg.level에 맞춘다: expert는 수치·근거·commit·PR·판정, mid는 변화와 비용/한계, novice는 달라질 작업 경험과 사람이 결정할 사항을 먼저 설명한다. 어느 경우든 실행기 연결 여부와 다음 실행 조건을 숨기지 않는다.
