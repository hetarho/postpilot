# 10. Independent Voice Profiles and Post Assignment

> Give one account multiple fully isolated writing voices, require every post to choose one, and preserve deleted
> voices as historical tombstones instead of inventing a topic/project hierarchy | Scope: FS | Status: done (job 18)

## Purpose

One person does not necessarily write every post in one register. A personal diary, a product review, and an
informational article may need different endings, vocabulary, structure, examples, and learned correction rules.
The shipped account-wide profile forces those signals into one average voice: learning a polite review can alter the
next casual post, and there is no explicit choice at post creation to prevent that contamination.

The product needs a durable parent between account and post:

```
account 1 ──▶ many voices 1 ──▶ many posts
                     └───────▶ one independent profile/evidence history per voice
```

The user-facing noun is **말투** (`Voice` in contracts and code), not topic or project. Every post explicitly chooses
one voice from a dropdown, initially set to the account's default voice. Each voice learns, validates, and supplies
examples independently. This keeps PRD goal 2 (a draft in the author's voice) while recognizing that one author may
deliberately use several voices.

## Scope / Non-goals

### In scope

- A `Voice` aggregate per account with create, rename, set-default, soft-delete, and restore lifecycles.
- Exactly one active default voice per account and a required active `voice_id` on every post.
- A required voice dropdown on new-post creation, initialized to the default voice, plus post reassignment to another
  active voice from the editor.
- Complete profile isolation: legacy guidance, pasted samples, structured versions, manual overrides, finalized
  sources, rules/evidence, feedback, comparisons, validations, active jobs, and prompt excerpts are partitioned by
  `voice_id` as well as by the authenticated account.
- Generation, AI revision, rule saving, finalization learning, analyze experiments, and profile validation operating
  against the post's or explicitly selected voice only.
- Soft-deleted voice tombstones on existing posts, with read/manual-edit/export continuity and server-enforced AI
  restrictions until the voice is restored or the post is reassigned.
- A lossless migration that creates `기본 말투` for every existing account and assigns its current profile data and
  every current post to that voice.
- Authenticated voice list/detail management and voice-aware post list/editor/profile screens.

### Non-goals

- A topic, project, category, folder, or post-grouping hierarchy. Title, memo, and tags may remain retrieval text but
  are not promoted to a persisted `Topic` entity.
- A shared account-level base profile, inheritance, fallbacks, copying, merging, linking, or automatic synchronization
  between voices. A voice with no evidence is genuinely empty even when another voice is well trained.
- Selecting an in-app post from another voice as imported evidence. The existing optional external-text paste remains
  available inside the target voice; it creates evidence only there.
- Moving old samples, profile versions, rules, learning events, or authored sources when a post is reassigned. Only
  later work belongs to the new voice.
- Automatic voice selection from a post's title, tags, content, platform, or model output. The server never guesses a
  missing voice, and a deleted voice never silently falls back to the default.
- Hard-deleting a voice through the product, or hard-deleting posts/profile history when a voice is soft-deleted.
  Account deletion retains its existing full cascade.
- A fixed limit on voices, a new provider/SDK, a new job queue, scheduled learning, or changes to the explicit model
  selection and no-background-provider-call guarantees.
- Changes to block-array canonical content, browser-only image processing, the existing copy-only export, or plan
  12's explicit local-capability publishing boundary ([I1], [I2], [I6]).

## Design

### Domain rules and terminology

`Voice` is an account-owned aggregate with its own lifecycle. A voice owns exactly one possibly-empty profile and all
evidence that can change that profile. `Post` remains a separate aggregate and references one voice by immutable id;
the relationship may be reassigned explicitly, but profile data is never co-owned or moved implicitly.

The invariants are:

1. every account has at least one active voice and exactly one active default voice;
2. every post has exactly one voice belonging to the same account;
3. every profile/evidence mutation identifies one active voice, either explicitly or through an owned post/rule/event;
4. a prompt uses data from exactly that voice and never falls back to another voice;
5. a soft-deleted voice and its profile remain addressable for historical display but cannot initiate or receive an
   AI/profile mutation; and
6. no RPC accepts a user id—the authenticated account remains authoritative.

Existing “topic-aware” excerpt ranking stays an implementation detail inside one voice: post title/memo and tags may
rank that voice's own excerpts. Published behavior is renamed around `retrieval_text`, not a new `Topic` domain noun.

### Voice lifecycle

- Migration `0009_independent_voice_profiles.sql` and account bootstrap create one active voice named `기본 말투`,
  mark it default, and create an empty profile when the account has no prior profile. `adduser` runs the voice
  context's idempotent `EnsureDefaultVoice` right after creating the account (and again on a duplicate-account rerun,
  as a repair) and exits nonzero when the invariant cannot be established; reads do not silently create domain rows.
- `CreateVoice` trims and validates a name, creates an empty isolated profile, and never copies the default profile.
  Active names are unique within one account. There is no fixed voice-count cap. It also accepts an OPTIONAL free-text
  `description` of the wanted register with the account's analyze-stage `ModelRef` (change 14): the voice is created
  the same way, and one durable `seed_voice` job then writes its first profile version from that description. The
  description is an instruction, never evidence, so it becomes no sample, no source count, and no measurement, and
  the seed publishes only while the profile is still empty and unversioned. Every reason to refuse a described
  creation, the analyze-model requirement included, is checked before the row is inserted. Omitting the description
  is the original behavior exactly: no model is required, no job is enqueued, and the returned `job_id` is empty.
- `RenameVoice` updates only the display name. It may rename an active or deleted owned voice, does not rewrite post
  rows or immutable profile snapshots, and rejects an active-name collision.
- `SetDefaultVoice` accepts only an active owned voice and atomically clears the previous default and sets the new
  one. It performs no profile or provider work.
- `DeleteVoice` is a soft delete (`deleted_at`), refuses the active default and the last active voice, and refuses a
  voice with a queued/running voice-owned job, an undecided comparison/validation, or a publishable analyze
  experiment. It leaves posts, samples, profile versions, rules, sources, and completed history intact. The voice
  disappears from selectable dropdown options immediately. Deleting an already deleted voice is a no-op.
- `RestoreVoice` clears `deleted_at` without enqueueing work. Restore fails if its name conflicts with an active name;
  the user can rename the tombstone and retry. A restored voice is not made default automatically.
- The current default must first be replaced before deletion, so the last active voice cannot be deleted. There is no
  public hard-delete RPC.

### Post assignment, reassignment, and baseline safety

`SavePostDraft` creation requires an explicit active owned `voice_id`. The new-post dropdown is initialized to the
server-returned default but the request always carries the concrete id; an empty, foreign, unknown, or deleted id is
rejected. The backend does not substitute the default for an invalid request.

An existing post may be reassigned to another active owned voice. The reassignment:

- preserves slug, title, memo, photos, canonical `PostContent`, content revision, status/finalized revision, and
  exportability;
- is refused while generation/revision or a post-backed undecided model experiment could still apply output;
- atomically changes `posts.voice_id`, clears the latest machine baseline and its voice association, and makes
  finalization learning ineligible until generation or AI revision under the new voice establishes a new baseline;
- does not move, delete, or recount any learning event/source/rule already published under the previous voice; and
- causes every later generation, revision, saved rule, feedback item, and finalization-learning event to use the new
  voice.

A machine-written baseline stores `machine_baseline_voice_id`. Finalization learning verifies that it equals the
post's current `voice_id`; this check is authoritative even if a stale client presents an older eligible state. A
finalize-only action from change 03 may still finalize preserved content because finalization is a content boundary,
not a profile mutation.

A post whose voice is deleted keeps a `VoiceRef` with the original id/name and `deleted=true`. It remains readable,
manually editable, copyable, and exportable. Generation, AI revision, save-as-rule, voice feedback, and finalization
learning fail with `FailedPrecondition` before enqueue/provider work. Restoring the voice or explicitly reassigning
the post to an active voice re-enables the appropriate actions.

### Independent profile, learning, and experiment behavior

- All profile reads/edits, pasted samples, imports, version restore, manual overrides, rules, confirmations,
  comparisons, and validations are keyed by `(user_id, voice_id)`. A foreign voice id is inaccessible; an id from
  another voice in the same account is not treated as interchangeable evidence.
- Each voice has its own empty state, `corpus_version`, `current_version`, active analysis guard, source count, and
  validation eligibility. Two voices may enqueue independent work; the existing worker concurrency policy still
  decides execution order.
- Optional historical-text paste occurs from a voice detail screen and writes one sample for that voice. There is no
  picker or RPC to copy/select a post or sample from another voice.
- `FinalizeAndLearn(post_slug, model)` derives and freezes the post's current `voice_id`; the caller cannot nominate a
  different voice. Retries use the event's frozen voice even if the post is later reassigned. A later baseline created
  under the new voice may create a distinct event there.
- Generation and revision resolve the post, freeze its active voice id and exact profile version/projection with the
  input, and inject only that voice's descriptors, active constraints, 0–3 excerpts, and manual rules. `save_as_rule`
  appends only to the frozen/current post voice according to the existing revision transaction contract.
- Rule status changes and comparisons derive the voice from the owned rule; feedback derives it from the post and
  matching finalization source. Profile validation starts with an explicit active `voice_id` and counts only that
  voice's authored sources.
- Analyze-stage model experiments start with an explicit active `voice_id`, freeze only its corpus, and apply a
  winning styleguide only to that same still-active voice. Model Elo and active model selections remain account- and
  stage-scoped; profile content does not.
- Soft delete/restore, list/detail reads, post reassignment, page mount, polling, copy, and export make no provider
  call and enqueue no personalization work ([I5]).

### Proto / Connect contract

`proto/postpilot/v1/voice.proto` gains the aggregate and directory operations:

```proto
message Voice {
  string id = 1;
  string name = 2;
  bool is_default = 3;
  bool deleted = 4;
  string created_at = 5;
  string updated_at = 6;
  string deleted_at = 7;
}

service VoiceService {
  rpc ListVoices(ListVoicesRequest) returns (ListVoicesResponse);
  rpc CreateVoice(CreateVoiceRequest) returns (CreateVoiceResponse);
  rpc RenameVoice(RenameVoiceRequest) returns (RenameVoiceResponse);
  rpc SetDefaultVoice(SetDefaultVoiceRequest) returns (SetDefaultVoiceResponse);
  rpc DeleteVoice(DeleteVoiceRequest) returns (DeleteVoiceResponse);
  rpc RestoreVoice(RestoreVoiceRequest) returns (RestoreVoiceResponse);
  // Existing profile/sample/version/override procedures remain and take voice_id.
}

message GetVoiceProfileRequest { string voice_id = 1; }
message AddVoiceSampleRequest { string voice_id = 1; string label = 2; string body = 3; ModelRef model = 4; }
```

Every existing profile-scoped request (`UpdateVoiceProfile`, `DeleteVoiceSample`, version list/restore, and override)
adds or derives one `voice_id`; sample/rule/event ids are also checked against that voice when both appear.
`VoiceProfile.voice` carries the owning `Voice` summary so cache entries and deleted-state UI cannot become detached;
`SetDefaultVoice` answers with the whole directory because the previous default changed too.

`post.proto` defines a transport-only `VoiceRef {id, name, deleted}` and extends `Post` and `PostSummary` with
`voice`; `Post` also exposes `machine_baseline_voice_id`. `SavePostDraftRequest` adds presence-aware
`optional string voice_id`: it is required for create, omitted means preserve on ordinary edits, a present value equal
to the current voice also preserves, and a different present value requests reassignment. This preserves autosave
patch semantics while making an accidental empty value invalid.

`voice_learning.proto` keeps `FinalizeAndLearn` post-derived; returned events expose `voice_id` for routing and cache
invalidation. Voice-wide list operations such as confirmations add `voice_id`, while event/rule-specific operations
derive and verify it from their owned aggregate. `voice_validation.proto` adds `voice_id` to start/list projections;
comparison detail carries its frozen voice id. `model_experiment.proto` adds `voice_id` to analyze experiment start and
projection. Generated clients are regenerated through `pnpm gen:proto`; generated files are never hand-edited.

### SQLite model and migration

The implementation adds the `voices` aggregate and rebuilds the account-keyed voice tables transactionally:

```sql
voices (
  id TEXT PRIMARY KEY,
  user_id TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  name TEXT NOT NULL,
  is_default INTEGER NOT NULL CHECK (is_default IN (0,1)),
  deleted_at TEXT,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  UNIQUE (id, user_id)
)

-- one active default and no duplicate active display name per account
UNIQUE INDEX voices_one_default ON voices(user_id) WHERE is_default = 1 AND deleted_at IS NULL;
UNIQUE INDEX voices_active_name ON voices(user_id, name) WHERE deleted_at IS NULL;

posts.voice_id TEXT NOT NULL
posts.machine_baseline_voice_id TEXT NULL
FOREIGN KEY (voice_id, user_id) REFERENCES voices(id, user_id)
```

The service transaction enforces “at least one active voice”; the partial index enforces “at most one default.”
There is no voice hard-delete path, so soft deletion never invokes an FK cascade.

Every existing account gets one generated voice id. That mapping backfills all posts and every row in
`voice_profiles`, `voice_samples`, `voice_profile_versions`, `voice_manual_overrides`, `voice_learning_events`,
`voice_authored_sources`, `voice_contrast_rules`, `voice_rule_evidence`, `voice_rule_confirmations`,
`voice_sentence_feedback`, `voice_rule_comparisons`, `voice_rule_comparison_candidates`,
`voice_profile_validations`, and `voice_profile_validation_items` without changing bodies, snapshots, revisions,
timestamps, statuses, or legacy styleguide/rules bytes. Tables and indexes whose uniqueness is currently per user are
rebuilt per voice—for example `(voice_id, version)`, `(voice_id, canonical_key)`, and one active validation per voice.
Composite `(voice_id, user_id)` constraints retain defense-in-depth account isolation.

`generation_jobs` and analyze `model_experiments` gain a nullable/frozen `voice_id` for voice-owned work. Post-backed
write jobs also snapshot the post voice so a result cannot establish a baseline for another voice. Account-scoped
model selections and Elo rows are not repartitioned.

The embedded migration runs after job 16 and job 17's migration (expected next number under that build order),
uses SQLite table rebuilds rather than lossy column shortcuts, runs under the single writer, and fails boot on any
ownership/default/backfill inconsistency ([I7]). SQL code is regenerated with `pnpm gen:sql`.

### Job and state transitions

No new job kind is introduced. Existing `analyze_voice`, `learn_voice`, `compare_voice_rule`, and
`validate_voice_profile` payloads/rows freeze `voice_id`; active guards change from account+kind to voice+kind where
the aggregate is voice-owned. Boot sweep, explicit retry, progress, and provider error behavior remain unchanged.

```
active voice ──delete──▶ deleted tombstone ──restore──▶ active voice
      │                         │
      │ AI/profile work        └─ read/history/export only; no enqueue/provider call
      ▼
voice-scoped durable job (frozen voice_id)

post voice A ──reassign to B──▶ same post/content + cleared machine baseline
     │                                      └─ next machine result establishes baseline for B
     └─ completed A evidence remains owned by A
```

Deleting a voice is rejected while a voice-owned job or undecided analyze experiment could still publish to it.
Once frozen, a job never follows a later post reassignment. Queue records, errors, retries, and UI polling always
route by their frozen voice id.

### Frontend behavior and placement

- `/voices` lists active voices first (the default badged, each a link into its profile) and a separate deleted
  section. Rename is in place through the shared `Editable` pencil; `기본으로 설정` and `삭제` appear on non-default
  voices only; deletion is confirmed through the sheet, which says what stays; the `새 말투` form is the page's one
  CTA. Server refusals (duplicate name, busy voice, restore conflict) are shown under the control in the user's words.
- `/voices/$voiceId` is the existing voice-profile experience scoped to one voice — the tabs `프로필`, `버전 기록`,
  `기존 글 가져오기`, `대조 규칙`, `프로필 검증` — with the layout naming the voice, badging default/deleted, and
  offering `복원` on a tombstone; the import form is blocked for a deleted voice. The detail screens moved with it to
  `/voices/$voiceId/rules/$id/compare` and `/voices/$voiceId/validations/$id`. `/voice` and `/voice/<tab>` redirect to
  the same tab of the current default voice for old links (or to `/voices` when there is none); they create nothing.
- `/posts/new` loads the voice directory before the editor mounts and renders a required dropdown initialized to the
  default voice; the first save always carries that concrete id, and choosing a voice alone creates no post. The
  dropdown is never replaced by heuristic selection. On an existing post the same dropdown reassigns after a
  confirmation sheet that says existing content stays while prior learning remains with the old voice and a fresh
  machine result is required before learning in the new voice; it is disabled with a reason while a job runs or an A/B
  result waits, and a refusal is reported under the field with the old voice kept.
- Post list/editor projections show the active name. A tombstone renders `삭제된 말투 · {name}` on the list row, in the
  picker, and in the editor's warning, which offers `복원` beside the picker's reassignment; generate, A/B, revise,
  sentence feedback and learning are disabled with one shared reason while manual block editing and export remain
  available.
- Query keys are `(account_id, voice_id, resource)`; post cache entries carry the voice projection. Account switches,
  rename/default/delete/restore, and reassignment invalidate or patch only the relevant directory/profile/post keys.
  The per-post draft queue carries the voice assignment (`assignVoice`): a create always sends the id, an ordinary
  edit never does, a reassignment is sent at once and reported on its own promise, text typed meanwhile cannot revert
  it, and a refused reassignment is taken back so later autosaves carry text only.
- The model lab's analyze tab carries a required voice picker initialized to the default; experiment history and
  detail name the frozen voice.

## Acceptance Criteria

1. Migrating an existing database creates exactly one active `기본 말투` per account, marks it default, assigns every
   existing post and all existing voice/profile/evidence rows to it, and preserves legacy text, snapshots, revisions,
   job/history status, timestamps, and prompt output byte-for-byte apart from the new ids/projections.
2. Creating a new account establishes one active default voice before post creation. An account can create two more
   voices with empty independent profiles; no sample, rule, descriptor, example, or version appears in either merely
   because another voice has data.
3. Active voice names are trimmed, non-empty, bounded by the owned character limit, and unique within the account.
   Rename affects list/post display without rewriting post content or immutable profile history.
4. Setting an active owned voice as default atomically replaces the previous default. New-post UI initializes its
   required dropdown to that exact voice, and the create request always carries the id; missing, foreign, unknown, or
   deleted ids are rejected without silently choosing a fallback.
5. Deleting a non-default inactive voice sets a tombstone and preserves all posts/profile history. It disappears from
   selectable options and existing posts show `삭제된 말투 · {name}` after reload. The default/last active voice and a
   voice with publishable active work cannot be deleted.
6. Restoring a deleted voice preserves its profile/history and re-enables selection and AI work without starting a
   job. A conflicting active name blocks restore until the tombstone is renamed; restore does not change the default.
7. A deleted-voice post remains readable, manually editable, copyable, and exportable. Generation, revision,
   save-as-rule, feedback, and finalization learning are rejected before enqueue/provider calls, with a visible action
   to restore or reassign the voice.
8. Reassigning an idle post to another active owned voice preserves its slug, inputs, photos, canonical content,
   content revision, finalization state, and export. It clears the old machine baseline/eligibility and does not move
   prior evidence; active post work or an undecided write result blocks reassignment.
9. After reassignment, a machine generation/revision freezes only the new voice profile and establishes a baseline
   carrying that voice id. Finalization learning rejects an old/mismatched baseline and succeeds only against a
   matching baseline, publishing its source/evidence exclusively to the new voice.
10. Two voices can hold contradictory endings, manual rules, samples, and active contrast rules. Generation and five
    repeated AI revisions of posts assigned to each voice consistently receive only their selected voice projection;
    no profile fallback or cross-voice excerpt appears in prompt snapshots.
11. Pasting a historical text sample analyzes only the selected active voice's full corpus. There is no in-app
    cross-voice post/sample picker or copy RPC, and deleting/reanalyzing a sample changes no other voice's corpus
    version or profile head.
12. Finalize/learn events, retries, feedback, rules, confirmations, rule comparisons, validation eligibility/results,
    and profile restore are all voice-scoped and account-scoped. Reassigning a source post does not retarget a frozen
    event or completed source.
13. Analyze-model experiments require an explicit active voice, compare one frozen corpus, and apply a winner only to
    that same voice. Experiment completion cannot overwrite another or a deleted voice; model Elo/selections retain
    their existing account-stage semantics.
14. Voice-owned active-job guards are per voice, durable rows expose/freeze `voice_id`, and page load, directory CRUD,
    reassignment, delete/restore, polling, copy, and export initiate no provider call. Restart and explicit retry retain
    the existing personalization safety behavior.
15. Every RPC remains authenticated with no request user id. Crafted foreign account/voice/post/sample/rule/event ids
    cannot read or mutate another account, and a same-account id from voice A cannot mutate voice B's aggregate.
16. Voice directory/detail, legacy redirect, post list, new-post dropdown, editor reassignment, deleted-state warnings,
    mobile layout, keyboard interaction, focus restoration, pending/error states, and account-switch cache isolation
    are covered by frontend interaction tests using the design-system primitives and semantic tokens. Since change 14
    the directory is a list of one-target rows carrying `기본으로 설정`/`삭제`, tombstones sit in a collapsed
    disclosure, renaming lives on the voice's own screen, and creation is a docked action opening a bottom sheet that
    also takes the optional description.
17. Migration/store/domain/RPC/prompt/job tests cover default uniqueness, lifecycle races, table partition keys,
    reassign-versus-job races, baseline voice mismatch, deletion guards, soft-delete retention, restoration, and
    byte-preserving backfill. Proto/sql generation checks, backend vet/build/tests, frontend tests/lint/FSD/style/build,
    and spec lint all pass without weakening current assertions.
