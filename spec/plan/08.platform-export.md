# 08. Platform Export

> Four copy-ready formats derived in the browser from the block array — Naver plain text with photo markers, a Tistory
> HTML fragment, a standalone fixed-template HTML page, and Markdown with front matter — one tab each, one copy button
> | Scope: FE | Status: done

## Purpose

postpilot never publishes ([I1], PRD §3.1): the last thirty seconds are paste-into-the-editor, and that is what makes
the frontend a static SPA deployable anywhere. This plan is that last step done well for the four targets the PRD
names (PRD F-7, §1 목표 4).

The Naver case dictates the architecture: SmartEditor ONE has no HTML input mode and discards pasted markup, so the
Naver format is plain text with `[사진 …]` markers where photos go, and the user drags the photos in. That only works
because the canonical post is a block array ([I2]) from which every format is a pure function — computed on the
client, instantly, with no server round-trip.

## Scope / Non-goals

**In scope**

- Four pure converters `(PostContent, images) → string`: `naver`, `tistory`, `site`, `markdown`, each with snapshot
  tests over a fixture that covers every block type.
- The export panel: four tabs, the output preview, the per-format guidance line (PRD F-7 table), a copy button.
- Clipboard write with fallback: when the Clipboard API is unavailable or refused, auto-select the text for manual
  copy (PRD §7).
- The fixed HTML template for the `site` format (code-owned CSS; identical across posts).
- Front-matter shape for the `markdown` format (Hugo / Jekyll / Obsidian compatible).
- Image references by **filename** in every format.

**Non-goals**

- Publishing, browser automation, platform credentials of any kind ([I1]).
- Server-side conversion or storage of derived formats (they are recomputed on demand).
- Theming or per-post styling of the `site` format (PRD F-7: 디자인은 고정 템플릿 — the model never writes CSS).
- Embedding image bytes (data URIs) or long-lived image URLs in the output — presigned URLs expire and would rot in a
  pasted page.
- Bulk photo download. The PRD does not define one; formats reference photos by filename and the guidance tells the
  user to upload/place them. Flagged as a PRD gap (see Design → Images).
- Editing the derived text in place (edit the draft via plan 07, then re-copy).

## Design

### Input

`PostContent { title, summary, tags, blocks }` from `GetPost` (plan 06), plus the post's `images` and `created_at`
(mapped to the frontend post entity for the dated formats). Converters are total functions: an IMAGE block whose file
is unknown is rendered as-is by filename (the server already filtered fabricated names; the converters do not
re-filter).

### Images

Every format refers to a photo by its **filename** (`IMG_1.jpg`) — the name the user sees in the contact sheet and
that the platform will show after upload. Presigned URLs are never emitted. The `site` and `markdown` outputs
therefore expect the photo files to be placed next to the page (Hugo/Jekyll page bundles and Obsidian attachments
work this way); their relative path segments are URL-encoded so accepted names containing spaces, parentheses,
`?`, or `#` still resolve correctly. Tistory keeps the exact name in `data-file` and neutralizes comment-closing
sequences inside its adjacent instruction comment. The guidance line explains placement. Getting the files to the
user's machine is not covered by the PRD (flagged non-goal above).

### Block → format mapping

| Block | Naver (plain text) | Tistory (HTML fragment) | Site (standalone HTML) | Markdown |
|---|---|---|---|---|
| TEXT | paragraph, blank line between paragraphs | `<p>…</p>` | `<p>…</p>` | paragraph, blank line |
| HEADING level 2 / 3 | the heading text on its own line, blank line after | `<h2>` / `<h3>` | `<h2>` / `<h3>` | `## ` / `### ` |
| IMAGE | `[사진 <file> — <caption>]` on its own line; `[사진 <file>]` when no caption | `<figure><img src="" alt="<alt>" data-file="<file>"><!-- <file> 업로드 후 src 교체 --><figcaption><caption></figcaption></figure>` | `<figure><img src="<file>" alt="<alt>"><figcaption>…</figcaption></figure>` | `![<alt>](<file>)` then `*<caption>*` on the next line when present |
| QUOTE | the line wrapped in curly double quotes (“…”) | `<blockquote><p>…</p></blockquote>` | same | `> …` |
| LIST | one `- item` per line | `<ul><li>…</li></ul>` | same | `- item` lines |
| title / summary / tags | not in the body — shown in a separate copy field for the title (Naver has its own title box); summary and tags omitted | title omitted (Tistory title box); summary as a leading `<p class="summary">`; tags omitted (Tistory has a tag field) | `<h1>` title, summary paragraph, tags list, date | front matter `title`, `date`, `summary`, `tags`; body starts after |

- Text is HTML-escaped in the three HTML/Markdown-adjacent formats where it must be; Naver output is raw text.
- Naver output ends each block with `\n\n`; consecutive blank lines are collapsed to one.
- The `site` format is a complete document: `<!doctype html>`, `<html lang="ko">`, `<meta charset>`, viewport,
  `<title>`, an inline `<style>` from the fixed template constant, then the article. The template never varies with
  content; it is a string constant in code (PRD F-7: 모델이 매번 CSS를 만들면 글마다 디자인이 달라진다).
- Markdown front matter:

  ```yaml
  ---
  title: "<title>"
  date: <post.created_at as YYYY-MM-DD>
  summary: "<summary>"
  tags: [tag1, tag2]
  ---
  ```

### Panel and clipboard

- `widgets/export-panel`: tabs `네이버 블로그 · 티스토리 · 자체 사이트 · 마크다운`; the selected format's output in a
  read-only, monospace, scrollable area; the guidance line (PRD F-7): Naver "붙여넣고 표시된 자리에 사진을 드래그하세요",
  Tistory "HTML 모드에 붙여넣고 사진 업로드 후 src를 교체하세요", Site "그대로 .html로 저장하고 사진 파일을 옆에 두세요",
  Markdown "Hugo · Jekyll · Obsidian — 사진 파일을 같은 폴더에 두세요"; a `복사` button. For Naver, a second small
  field with the title and its own copy button.
- Copy: `navigator.clipboard.writeText(text)`. On rejection or when the API is absent (non-secure context, iOS
  quirks), the output area is focused and fully selected and a hint reads "자동 복사가 막혀 있어요 — 선택된 텍스트를
  길게 눌러 복사하세요" (PRD §7). Success shows a transient "복사됨".
- Clipboard operations are serialized. A tab/content change or later copy invalidates an older operation's feedback
  and fallback selection, so a delayed permission result cannot select or label the wrong output.
- Tab switching is synchronous: converters are memoized per `(content, format)`; no network activity.
- The panel is shown whenever canonical content exists in `review` or `finalized` state.

The four converters are one function each, as PRD F-7 prescribes (`features/export-*`), and know nothing about the
DOM; the widget owns all UI.

## Acceptance Criteria

1. All four tabs render output derived from the same `PostContent`; switching tabs triggers no network request and is
   visually instant.
2. Naver output is plain text (no `<` `>` markup) and every IMAGE block appears at its position exactly as
   `[사진 <file> — <caption>]` (or `[사진 <file>]` without a caption).
3. Tistory output is a valid HTML fragment (parses without error when wrapped in a `<div>`), every `<img>` has an
   adjacent replacement comment naming the file, and it contains no `<html>`/`<body>` wrapper.
4. Site output is a single standalone HTML document; two different posts produce byte-identical `<style>` content
   (the template is fixed, not generated).
5. Markdown output starts with valid YAML front matter containing `title`, `date`, `summary`, `tags`; headings,
   quotes, lists and images use the mapping above.
6. The copy button places the exact rendered string on the clipboard; in an environment where the Clipboard API
   is unavailable, the output area is auto-selected and the manual-copy hint appears.
7. Each converter has a snapshot test over a fixture that includes every `BlockType`, an image without caption, a
   heading of level 3, and Korean text with characters that need HTML escaping.
8. Each tab shows its PRD guidance line; the Naver tab additionally offers the title for separate copying.
9. No converter emits a presigned URL or any `api.postpilot.*` / R2 host string.
10. The export panel is absent while a post has no generated content.

## Policy / Config Impact

**Implemented rules** (canonicalized in `spec/policy/export.md`):

- Naver photo marker format is `[사진 <file> — <caption>]` / `[사진 <file>]` — a contract the guidance and users
  rely on; changing it is a policy change.
- Tistory `<img>` tags carry an adjacent `<!-- <file> 업로드 후 src 교체 -->` comment and an empty `src`.
- The site template is fixed and content-independent; image references are relative filenames in every format.
- Conversion happens only in the browser; no derived format is stored or served by the API.
- Clipboard failure falls back to auto-select, never to a silent no-op.

**Config**

| Value | Owner | Supplied as | Default |
|---|---|---|---|
| site HTML template (CSS + shell) | FE `features/export-site/config` | code constant | fixed design |
| guidance strings per format | FE `widgets/export-panel/config` | code constants (Korean copy) | as above |
| `COPY_FEEDBACK_MS` | FE `shared/config` | typed constant | `1500` |

No env vars; no backend impact.

## As-built extension — job 16

All four converters continue to derive output from the current canonical `PostContent`, including direct block
edits. Export and clipboard actions are read-only: they do not finalize a post, enqueue learning, mutate a baseline,
or call a model. Finalization remains a separate explicitly confirmed editor action.

## As-built extension — job 17 / change 03

The export panel is available for both `review` and `finalized` content. Its output always follows the current
canonical blocks, so exporting neither changes lifecycle state nor publishes, learns, enqueues work, or calls a
provider.
