# 08. Platform Export

> Four copy-ready formats derived in the browser from the block array — Naver plain text with photo markers, a Tistory
> HTML fragment, a standalone fixed-template HTML page, and Markdown with front matter — one tab each, one copy button
> | Scope: FE | Status: done

## Purpose

This export surface never publishes: it derives copy-ready values entirely in the browser, which keeps the frontend
a static SPA deployable anywhere. This plan is that manual path done well for the four targets the PRD names (PRD
F-7, §1 goal 4). Plan 12 later adds an explicit, separate Naver publishing action through a paired Mac; it does not
turn an export conversion or copy into a side effect.

The Naver case dictates the architecture: SmartEditor ONE has no HTML input mode and discards pasted markup, so the
Naver format is plain text with `[사진 …]` markers where photos go, and the user drags the photos in. That only works
because the canonical post is a block array ([I2]) from which every format is a pure function — computed on the
client, instantly, with no server round-trip.

## Scope / Non-goals

**In scope**

- Four pure converters `(PostContent, images) → string`: `naver`, `tistory`, `site`, `markdown`, each with snapshot
  tests over a fixture that covers every block type.
- The export panel: four tabs, the output preview, the per-format guidance line (PRD F-7 table), a copy button.
- Clipboard write with fallback: when the Clipboard API is unavailable or refused, auto-select the text for manual
  copy (PRD §7).
- The fixed HTML template for the `site` format (code-owned CSS; identical across posts).
- Front-matter shape for the `markdown` format (Hugo / Jekyll / Obsidian compatible).
- Image references by **filename** in every format.

**Non-goals**

- Publishing, browser automation, or platform credentials **inside this export surface**. Plan 12 owns those separate
  capabilities and keeps the manual export path as the universal fallback ([I1]).
- Server-side conversion or storage of derived formats (they are recomputed on demand).
- Theming or per-post styling of the `site` format (PRD F-7: 디자인은 고정 템플릿 — the model never writes CSS).
- Embedding image bytes (data URIs) or long-lived image URLs in the output — presigned URLs expire and would rot in a
  pasted page.
- Bulk photo download. The PRD does not define one; formats reference photos by filename and the guidance tells the
  user to upload/place them. Flagged as a PRD gap (see Design → Images).
- Editing the derived text in place (edit the draft via plan 07, then re-copy).

## Design

### Input

`PostContent { title, summary, tags, blocks }` from `GetPost` (plan 06), plus the post's `images` and `created_at`
(mapped to the frontend post entity for the dated formats). Converters are total functions: an IMAGE block whose file
is unknown is rendered as-is by filename (the server already filtered fabricated names; the converters do not
re-filter).

### Images

Every format refers to a photo by its **filename** (`IMG_1.jpg`) — the name the user sees in the contact sheet and
that the platform will show after upload. Presigned URLs are never emitted. The `site` and `markdown` outputs
therefore expect the photo files to be placed next to the page (Hugo/Jekyll page bundles and Obsidian attachments
work this way); their relative path segments are URL-encoded so accepted names containing spaces, parentheses,
`?`, or `#` still resolve correctly. Tistory keeps the exact name in `data-file` and neutralizes comment-closing
sequences inside its adjacent instruction comment. The guidance line explains placement. Getting the files to the
user's machine is not covered by the PRD (flagged non-goal above).

### Block → format mapping

| Block | Naver (plain text) | Tistory (HTML fragment) | Site (standalone HTML) | Markdown |
|---|---|---|---|---|
| TEXT | paragraph, blank line between paragraphs | `<p>…</p>` | `<p>…</p>` | paragraph, blank line |
| HEADING level 2 / 3 | the heading text on its own line, blank line after | `<h2>` / `<h3>` | `<h2>` / `<h3>` | `## ` / `### ` |
| IMAGE | `[사진 <file> — <caption>]` on its own line; `[사진 <file>]` when no caption | `<figure><img src="" alt="<alt>" data-file="<file>"><!-- <file> 업로드 후 src 교체 --><figcaption><caption></figcaption></figure>` | `<figure><img src="<file>" alt="<alt>"><figcaption>…</figcaption></figure>` | `![<alt>](<file>)` then `*<caption>*` on the next line when present |
| QUOTE | the line wrapped in curly double quotes (“…”) | `<blockquote><p>…</p></blockquote>` | same | `> …` |
| LIST | one `- item` per line | `<ul><li>…</li></ul>` | same | `- item` lines |
| title / summary / tags | not in the body — shown in a separate copy field for the title (Naver has its own title box); summary and tags omitted | title omitted (Tistory title box); summary as a leading `<p class="summary">`; tags omitted (Tistory has a tag field) | `<h1>` title, summary paragraph, tags list, date | front matter `title`, `date`, `summary`, `tags`; body starts after |

- Text is HTML-escaped in the three HTML/Markdown-adjacent formats where it must be; Naver output is raw text.
- Naver output ends each block with `\n\n`; consecutive blank lines are collapsed to one.
- The `site` format is a complete document: `<!doctype html>`, `<html lang="ko">`, `<meta charset>`, viewport,
  `<title>`, an inline `<style>` from the fixed template constant, then the article. The template never varies with
  content; it is a string constant in code (PRD F-7: 모델이 매번 CSS를 만들면 글마다 디자인이 달라진다).
- Markdown front matter:

  ```yaml
  ---
  title: "<title>"
  date: <post.created_at as YYYY-MM-DD>
  summary: "<summary>"
  tags: [tag1, tag2]
  ---
  ```

### Panel and clipboard

- `widgets/export-panel`: tabs `네이버 블로그 · 티스토리 · 자체 사이트 · 마크다운`; the selected format's output —
  a read-only text field for Tistory/site/Markdown, the rendered post preview for Naver (job 45); the guidance line
  (PRD F-7): Naver "본문을 붙여넣은 뒤, 미리보기의 사진을 복사해 [사진 …] 자리에 붙여넣으세요"
  (job 45; "본문을 그대로 붙여넣으세요" for a post with no photos),
  Tistory "HTML 모드에 붙여넣고 사진 업로드 후 src를 교체하세요", Site "그대로 .html로 저장하고 사진 파일을 옆에 두세요",
  Markdown "Hugo · Jekyll · Obsidian — 사진 파일을 같은 폴더에 두세요"; a `복사` button. For Naver, a second small
  field with the title and its own copy button.
- Copy: `navigator.clipboard.writeText(text)`. On rejection or when the API is absent (non-secure context, iOS
  quirks), the output area is focused and fully selected and a hint reads "자동 복사가 막혀 있어요 — 선택된 텍스트를
  길게 눌러 복사하세요" (PRD §7); on the Naver tab, where the raw text is not the default view, the raw field is
  first revealed for exactly this fallback (job 45). Success shows a transient "복사됨".
- Clipboard operations are serialized. A tab/content change or later copy invalidates an older operation's feedback
  and fallback selection, so a delayed permission result cannot select or label the wrong output.
- Tab switching is synchronous: converters are memoized per `(content, format)`; no network activity.
- The panel is shown whenever canonical content exists in `review` or `finalized` state.
- For Naver only, the output is presented as the **rendered post** (job 45 / change 18): the block array as the
  reading view renders it, photos inline in marker order, each with its own single-flavor `image/png` clipboard copy
  overlaid at the photo's top-right. The `[사진 …]` markers exist only in the copied text. See the as-built
  extensions below.

## Acceptance Criteria

1. All four tabs render output derived from the same `PostContent`; switching tabs triggers no network request and is
   visually instant.
2. Naver output is plain text (no `<` `>` markup) and every IMAGE block appears at its position exactly as
   `[사진 <file> — <caption>]` (or `[사진 <file>]` without a caption).
3. Tistory output is a valid HTML fragment (parses without error when wrapped in a `<div>`), every `<img>` has an
   adjacent replacement comment naming the file, and it contains no `<html>`/`<body>` wrapper.
4. Site output is a single standalone HTML document; two different posts produce byte-identical `<style>` content
   (the template is fixed, not generated).
5. Markdown output starts with valid YAML front matter containing `title`, `date`, `summary`, `tags`; headings,
   quotes, lists and images use the mapping above.
6. The copy button places the exact rendered string on the clipboard; in an environment where the Clipboard API
   is unavailable, the output area is auto-selected and the manual-copy hint appears.
7. Each converter has a snapshot test over a fixture that includes every `BlockType`, an image without caption, a
   heading of level 3, and Korean text with characters that need HTML escaping.
8. Each tab shows its PRD guidance line; the Naver tab additionally offers the title for separate copying.
9. No converter emits a presigned URL or any `api.postpilot.*` / R2 host string.
10. The export panel is absent while a post has no generated content.

## Policy / Config Impact

**Implemented rules** (canonicalized in `spec/policy/export.md`):

- Naver photo marker format is `[사진 <file> — <caption>]` / `[사진 <file>]` — a contract the guidance and users
  rely on; changing it is a policy change.
- Tistory `<img>` tags carry an adjacent `<!-- <file> 업로드 후 src 교체 -->` comment and an empty `src`.
- The site template is fixed and content-independent; image references are relative filenames in every format.
- Conversion happens only in the browser; no derived format is stored or served by the API.
- Clipboard failure falls back to auto-select, never to a silent no-op.

**Config**

No env vars; no backend impact.

## As-built extension — job 44 / change 17

The Naver format copies its photos, one at a time ([policy/export.md](../policy/export.md) *Clipboard and UI*).
Job 44 shipped this as a photo strip beneath the text; job 45 moved the presentation inline (next section). The
clipboard contract is unchanged by that move:

- **One `ClipboardItem`, `image/png` only.** The payload is measured, not chosen (owner, 2026-08-31, SmartEditor ONE
  on macOS Chrome): a `text/html` flavor makes the editor render a broken image, a second item is ignored, and a page
  cannot put files on the clipboard. `shared/lib/clipboard/copyImage` owns it and there is deliberately no text
  fallback — the text output beside it is the fallback plan 08 already promises ([I1]).
- **The write is issued before the bytes arrive.** The PNG is passed to `ClipboardItem` as a promise, because
  awaiting the encode first spends the user activation WebKit requires and would make every iOS copy fail as a refusal
  the user could never retry past. (Job 44 awaited a `fetch` here; the copy reads the rendered element now — see the
  last section.)
- **PNG encoding reuses the upload pipeline's canvas machinery.** `shared/lib/image`'s `encodePng` sits beside
  `resizeToJpeg` and shares its `createCanvas`; it does not resize (the stored photo is already inside
  `IMAGE_MAX_LONG_EDGE_PX`, [I6]) and does not flatten onto white (PNG keeps its alpha). Nothing encoded here is
  uploaded — [I6] governs the upload pipeline and is untouched.
- **Per-photo state on the panel's existing discipline.** The same `copyGeneration` guard against a stale async
  result, the same `copyQueue` serialization, the same `COPY_FEEDBACK_MS` dwell and the same always-mounted live
  region as the two text copies. Failures are named per kind on the photo that failed — unsupported · refused ·
  blocked · unreadable · no matching photo (the blocked/unreadable split is job 51, next section) — and a photo whose
  view URL is a local `blob:` preview or fails to load offers no copy control at all.
- **Bulk photo download is still not built.** The owner chose per-photo copy only; multi-photo paste through Finder
  stays the unfilled PRD gap this plan records. The measurements behind that choice — a page cannot put files on the
  system clipboard, and only Finder can — live in
  [changes/archive/17](../changes/archive/17.copy-each-naver-photo-from-the-export-pa.md).

Config: **none added.** `COPY_FEEDBACK_MS` and `IMAGE_MAX_LONG_EDGE_PX` are reused from
`frontend/src/shared/config`.

## As-built extension — job 45 / change 18

The Naver tab's preview **is the post, not the wire text**
([changes/archive/18](../changes/archive/18.render-the-naver-export-preview-as-the-p.md)). The owner's verdict on
the job-44 strip was that it did not read as the post: markers where photos belong, and tiles to match against them
by filename.

- **Rendered preview.** The Naver tab renders the block array through `entities/post`'s `BlockList` — the same
  reading view the editor uses — body only (the copy does not paste the title/summary/tags header; the title has its
  own field). No `[사진 …]` marker text is visible; the markers exist only in the copied string, which stays
  byte-identical (`toNaver` and its snapshots untouched). The other three formats keep the raw read-only field:
  their output is source to be read, not a post to be seen.
- **Inline photo copy.** Each photo renders at its marker position, full column width, with an icon copy control
  overlaid at its top-right on the `media-scrim` plane (job 44's beside-the-tile reasoning was about a 44px control
  covering a quarter of a 128px tile; over a column-wide photo it covers a corner). The control's accessible name
  carries the marker filename; per-photo copied/failure status renders under that photo with the job-44 kinds. A
  marker whose photo is missing keeps its inline position as a filename placeholder, so later photos cannot shift
  against their markers; a `blob:`-preview photo keeps its pixels but offers no copy.
- **The manual fallback is revealed, not resident.** The raw marker text mounts only when the body copy is refused:
  it is then focused and fully selected with the existing hint, and a later copy, tab switch, or content change
  returns the tab to the preview. Feedback and fallback store the value (and content identity) they described, so a
  stale async result or a re-materialized output string cannot resurrect or mislabel them; dismissal that unmounts
  the focused field hands focus back to the copy button.
- **Seams, not copies.** `BlockList` gained three consumer seams for this: `label` (a second article on the editor
  page names itself apart from the reading view), `className`, and `renderMissingImage` (the reading and editing
  views keep rendering nothing for a missing image). `widgets/export-panel → entities/post` is a legal FSD
  dependency; `imageByFile` is reused rather than re-derived.

Config: **none added.**

## As-built extension — job 51 / change 23

A photo copy that cannot read the bytes now says WHICH of the two read failures it was, because they need opposite
advice and the wrong one is a loop with no exit
([changes/archive/23](../changes/archive/23.tell-a-blocked-photo-copy-apart-from-an-.md)).

- **`blocked` vs `unreadable`, told apart by the URL — not by the response.** A view URL that has run out of
  lifetime is reloaded away; bytes the bucket will not serve to this origin are not, and the text output beside the
  photo is the fallback ([I1]). They cannot be separated by the response: R2 answers an expired read with a 403 that
  carries **no CORS headers**, so the browser withholds it and `fetch` rejects exactly as it does when the bucket
  allows this origin no `GET` at all (Cloudflare, *R2 → CORS → Use CORS with a presigned URL*). `copyImage`
  therefore reads the lifetime SigV4 states in the URL's own query (`X-Amz-Date` + `X-Amz-Expires`): a rejected
  fetch on a URL that had already expired is `unreadable`, on a live one it is `blocked`. A readable non-2xx, and a
  decode or encode failure, stay `unreadable`. A wrong client clock costs a less useful message and nothing else.
- **The bucket rule is a repo artifact with a deploy gate.** `deploy/r2-cors.json` holds the rule (in the shape
  `wrangler r2 bucket cors set --file` accepts, which is not the dashboard's array form), DEPLOY.md §5 applies it by
  command, and the backend deploy asserts a `GET` preflight from `WEB_ORIGIN` against the host the presigned URLs
  are actually signed against (`R2_PUBLIC_ENDPOINT` when set, else `R2_ENDPOINT`). This is the failure nothing else
  reported. Like the API CORS gate it is separate from the rollout and does not roll the image back, because a
  bucket rule is not a bad image. *(The symptom this section describes — uploads succeed and photos render, only the
  copy breaks — is no longer what a missing `GET` allow looks like on the export panel; see the last section.)*
- **Not built, deliberately.** Refetching `GetPost` to remint a URL and retrying the copy automatically: it would
  thread a refetch from the editor page into the panel and re-open the user-activation question, for a case the
  now-accurate message resolves with a reload. The presign TTL is unchanged — a leaked URL is a leaked object.
  *(Reversed by the last section: the copy no longer touches a URL, and the refetch it did need turned out to have
  nothing to do with the clipboard.)*

Config: **none added.** The two messages are i18n catalog keys; the deploy check reads the endpoint and bucket from
the stack `.env` and the origin from the existing `WEB_ORIGIN` repo variable, so it adds no GitHub secret or variable.

## As-built extension — photo copy reads the rendered pixels

The copy was re-downloading the photo through its presigned view URL, and that is what made it fail intermittently
in production: `presignGetTTL` is 10 minutes, `GetPost` is refetched on editor mount and never again while the screen
sits open (window-focus refetching is off, and a draft save patches the cached image list in place rather than
invalidating it), so a panel opened late — or left open — copied through a URL that had already run out. The photo
stayed on screen the whole time, because its pixels were fetched while the URL was alive, and right-clicking it
copied fine. The clipboard payload contract above is unchanged.

- **`copyImage` takes the `<img>`, not the URL.** `createImageBitmap(element)` → the same `encodePng`. No request is
  made, so after a photo has painted the copy no longer depends on the URL, the network, or the clock. The
  user-activation discipline survives unchanged — the encode is still handed over as a promise.
- **The preview photo is CORS-loaded and eager.** `crossOrigin="anonymous"` keeps the canvas origin-clean; without
  it the browser refuses the bytes for a photo plainly on screen. `loading="lazy"` is gone: a photo has to have
  PAINTED to be copyable, and deferring the load defers it past the URL's lifetime on exactly the panel that is left
  open. This moves the bucket rule's symptom — a missing `GET` allow now stops the export panel's photos from
  DISPLAYING, while every other screen's plain `<img>` keeps working (DEPLOY.md §5 says so).
- **`blocked` vs `unreadable` survives, re-anchored.** The copy now reads them off the browser's own `SecurityError`
  (origin-unclean bitmap or tainted canvas) rather than off a rejected fetch. The URL-lifetime reading moved to the
  LOAD failure, where the same ambiguity reappeared: `shared/lib/presign`'s `presignExpired` — the job 51 parser,
  moved out of the clipboard module unchanged — decides whether a photo that never painted is reloaded away or
  placed by hand.
- **The refetch job 51 declined is built, on the load path.** `entities/post`'s `useRefreshPostImages` invalidates
  the post query; the panel calls it when a photo fails to load, at most once per photo per mount (every refresh
  mints a new URL, so an unbounded guard would let a refusing bucket drive a fail-remint-fail loop). It is not a
  poll: a painted photo is never re-requested, so a timer would re-download the panel to fix URLs nothing will use.
  It is on the LOAD path, not the copy path, so the user-activation question job 51 worried about never arises.
- **The photo IS the copy control.** The overlaid corner button is gone: a 44px target in the corner of a photo that
  fills the column was a quarter of the reach it needed, and the corner is where the thumb rests while scrolling.
  The `<img>` sits INSIDE the `<button>` rather than under an invisible overlay, so the browser's own 이미지 복사
  stays on the right-click menu — the workaround that carried this while the copy was broken.
- **The presign TTL is unchanged.** Raising it was the obvious fix and the wrong one: a leaked URL is a leaked
  object, and the copy no longer cares how long one lives.

Config: **none added.** No interval, no TTL, no new catalog key — the four failure messages are the ones job 51
wrote.

## As-built extension — job 50 / change 22

The generated tags now have a field on the export panel, because plan 08's per-format decision was
right about the body and incomplete about the screen
([changes/archive/22](../changes/archive/22.expose-the-generated-tags-as-a-copy-fiel.md)).

- **A read-only field with its own copy button, on all four tabs.** Built exactly like the Naver
  title field it sits above — `FieldLabel` + read-only `TextField` + adjacent secondary `Button` +
  an always-mounted `role="status"` line — so field order reads title → tags → output. It is
  deliberately outside the `naver` branch: the site HTML embeds an HTML list and the Markdown front
  matter a YAML sequence, and neither is what a platform's tag box wants.
- **`toHashtags` is the whole derivation** (`widgets/export-panel/lib/hashtags.ts`, the slice's
  second non-`ui` segment): trim, drop what is empty once trimmed, strip any leading `#` run the
  model emitted and put exactly one back, join with a single space. An empty result is what keeps
  the field off the screen — an empty tag list gets no field and no label, not a blank one.
- **A third text copy target, on the panel's existing discipline.** `'tags'` joins `'output'` and
  `'title'` in `CopyTarget`, `copy()`'s target and `manualCopy.target`, with its own `tagsRef`.
  `isCurrent`'s two-way `output ? outputRef : titleRef` ternary became a per-target lookup of
  getters: with three targets a ternary would have compared a tags copy against the TITLE field's
  element, and the tags field is conditionally mounted, so the ref has to be read at check time
  rather than snapshotted when the copy started. The generation counter, the `copyQueue`, the
  `COPY_FEEDBACK_MS` dwell and `invalidateCopyFeedback` are untouched — a tab switch clears tag
  feedback the same way it clears the title's.
- **The status line is derived, not stored.** The confirmation compares the copied value against
  the current hashtag string, and the fallback hint additionally compares content identity, so a
  confirmation for one tag list cannot survive a change to a different one and a dismissed
  fallback cannot resurrect when an edit is undone. A tags fallback does NOT reveal the Naver raw
  field: that reveal is gated on `manualCopy.target === 'output'`.
- **Unchanged, deliberately:** all four converters and their snapshots — the Naver body still omits
  summary and tags, the Tistory body still omits tags, the site HTML keeps its tags list, the
  Markdown front matter keeps its `tags` key; the Naver title field, the suppressed preview header,
  the `[사진 …]` markers and the per-photo copy; the `BlockList` header's tag rendering in the
  reading view; tag editing, which is plan 07's business.

Config: **none added.** `COPY_FEEDBACK_MS` in `frontend/src/shared/config` stays the owner of the
feedback dwell, and no timing or format literal lands inline.
