# 00. Overview — plan index, progress board, constitution

The entry point for the spec workflow. Every plan registers here so a second agent can see what exists, what is
claimed, and what is done without reading every doc.

- Product SSOT: [PRD.md](../../PRD.md) — what postpilot is, and why.
- Structural SSOT: [ARCHITECTURE.md](../ARCHITECTURE.md) — where code goes, which way dependencies point.
- Deploy/ops SSOT: [DEPLOY.md](../../DEPLOY.md).

## 1. The workflow

```
new feature      /create-plan  NN → /create-plan-job  NN → /implement-job MM
change to built  /create-change NN → /create-change-job NN → /implement-job MM
audit → refactor /create-code-review → /create-refactor-job NN → /implement-job MM
```

- `spec/plan/NN.*.md` — the **as-built** WHAT. Updated when a job lands; no checkboxes.
- `spec/changes/NN.*.md` — a WHAT **delta** against a shipped plan. Archived when its job lands.
- `spec/jobs/MM.*.md` — the buildable work doc (Acceptance Criteria + Implementation Checklist). Archived when done.
- `spec/code-review/NN.*.md` — a read-only audit; findings only, never code changes.
- `spec/policy/**` — canonical product rules that are **currently true**.
- `spec/tech/**` — a doc per non-obvious technical decision the PRD doesn't already own
  ([draft-autosave](../tech/draft-autosave.md)).

Plan numbers and job numbers are independent sequences, monotonic across `archive/` — never reused, never renumbered.

Plans 01–09 cover PRD F-1…F-9 and the original design decisions in PRD §3, §5, §6. Plan 10 extends the profile/post
model after the explicit [I4] amendment so one account may keep several isolated voices. Plan 11 adds a reusable
_purpose_ brief beside the voice so a post can say what kind of text it is (genre/structure) without touching the
voice profile (register). Plan 12 records the explicitly approved [I1] amendment after real use showed that manually
uploading/placing every Naver photo remained the dominant last-mile work: the VPS owns a durable publish request, but
platform credentials and browser execution stay on an account-paired Mac. PRD §9 items 2 (mobile app),
3 (rules auto-cleanup) and 4 (backup) remain open and are deliberately **not** planned; §9.5 (orphan cadence) is
carried as config in plan 02.

Plan 13 adds the Korean/English product-language foundation without changing routes: browser locale controls app
copy, each post independently controls the language of its next full generation, and each voice keeps one immutable
source language for safe learning. Plan 14 adds browser-owned system/light/dark preference over the existing day and
night tokens. Plan 15 composes those foundations into a public `/about` page while preserving `/` as the authenticated
product home and `/login` as the sole entry CTA; since plan 17 exists, the page also presents the shipped
`free/basic/max` plan ladder (values mirroring plan 17's limits table) without any purchase or signup affordance.

Plan 16 adds the third orthogonal prompt axis beside the voice (how sentences sound, plans 03/10) and the purpose
(what kind of text, plan 11): account-owned **writing guidelines** — reusable rules about what every post must avoid
or watch out for (clichéd filler, invented facts). A guideline applies globally by default or is scoped to specific
purposes, can be captured from the AI-revision flow as an explicit save, and is frozen at enqueue like the purpose
brief; the fixed write/revise prompts also gain a universal grounding constraint (no facts absent from the memo and
photo observations), complementing change 10's stylistic naturalness baseline. Nothing about a guideline is learned —
[I4] stays entirely with voice.

Plan 17 introduces the first authorization tier above "has a session": every account carries a plan
(`free < basic < max < master`) that bounds daily LLM-job starts (10/30/100/∞), daily and monthly spend
(free $0.10/$2 · basic $0.50/$12 · max $1/$25 · master ∞, enforced at job admission against a persisted per-call
usage ledger, calendar windows in Asia/Seoul), and model access (a `min_plan` floor per model in
`config/providers.yaml`). The human publishing surface and the new user-administration RPCs become master-only.
The ladder is deliberately shaped like a future subscription (PRD §9), but no billing is built.

Why this order:

- **17 before 19 and 20.** Job 17 rewrites the editor's actions and establishes the `draft`/`review`/`finalized`

- **19 before 20.** Job 19 creates the `Editable` primitive in `shared/ui`; job 20 consumes it. Reversing them makes
  job 20 hand-roll the shape and job 19 the duplicate — the design-system bug §1.1 names.
- **18 last.** It partitions the voice profile, the finalization aggregate, and these same screens by voice. Running
  it before 19/20 would force both to rebase onto a changed structure; running it after lets it partition one
  settled arrangement.
- **24 may run alongside 18.** It is a backend production fix with no product or contract dependency on multi-voice
  behavior. Job 24 shares the generation package with job 18, but that is an integration concern rather than a
  prerequisite; reconcile the combined tests and doc reflection before merging. Job 23 is already archived.
- **25 may also run alongside 18 and 22.** Publishing consumes the stable finalized-post behavior and does not depend
  on multi-voice or purpose semantics. Concurrent proto/post/editor/config edits are merged deliberately, and every
  in-flight migration reserves a unique number or is renumbered before integration.
- **22 alone waits for 18.** Its purpose selector is explicitly composed beside job 18's required voice selector,
  extends the post contract/migration that job 18 creates, and therefore retains `requires: 18`.
- **26–31 (review 01) have no dependencies on each other or on any plan job**, so every one carries

## 3. The constitution

The invariants below are derived from the PRD's core design decisions (§3) and confirmed stack decisions (§6). They
are the rules a plan, change, or job may **not** break silently. If a request requires breaking one, stop and resolve
it with the user first — reversing one of these reverses a stack decision with it.

- **[I1] Publishing is explicit and local-capability-bound.** Copy-ready output remains the universal fallback.
  Automatic publication may start only from a separate user confirmation over an exact finalized snapshot, and it is
  a durable server-side job. The VPS/frontend never hold platform credentials or a browser profile: an account-paired
  local agent claims the job outbound and drives its own browser. No finalization, learning, schedule, reconnect or
  retry may imply a publish, and an ambiguous external commit is never auto-retried. (PRD §3.1, plan 12.)
- **[I2] The canonical generated post is a block array, not HTML.** Per-platform output (Naver plain text + photo
  markers, Tistory HTML fragment, …) is _derived_ from it. Making HTML canonical makes Naver unsupportable. (PRD §3.2)
- **[I3] Generation separates observe from write and keeps every model choice explicit.** The observation stage looks
  only at photos and produces structured output; writing consumes observations + notes + the style profile. Ordinary
  generation observes at most once and calls one active writer; only the explicit A/B action may fan out to two
  writing candidates over the same snapshot. The app may ship a versioned recommended pairing, but never applies it
  automatically; the user explicitly applies/changes every active model and A/B pair. (PRD §3.3)
- **[I4] One or more mutually isolated style profiles per account, exactly one per voice.** Every post selects one
  voice. Profiles, samples, authored sources, rules, evidence, comparisons, validations, and prompt excerpts are never
  shared or inherited across accounts **or voices**—a merged profile cannot be separated later. Korean style analysis
  treats the sentence-ending form (종결어미) as the primary signal. (PRD §3.4, plan 10)
- **[I5] Long work is a server-side job record, not a blocking RPC.** `StartGeneration` returns a `job_id`; the client
  polls `GetGeneration`; a worker goroutine in the API process consumes the queue; `running` jobs are swept to
  `failed` on restart. Edits ride the same queue. (PRD §3.5)
- **[I6] Image work happens in the browser, before upload.** HEIC decode + 1024px downscale + JPEG encode client-side;
  originals never reach the API. This is what keeps the Go image CGO-free and distroless. (PRD §6.2)
- **[I7] Schema migrations are embedded in the binary and run at boot.** A migration failure kills the process so the
  deploy's `/health` gate rolls back. No separate migration container, no manual step. (PRD §6.3, DEPLOY.md §2)

The provider abstraction is a boundary, not a preference: nothing above `internal/llm` learns which provider answered
(PRD §6.4, ARCHITECTURE.md §2.1).
