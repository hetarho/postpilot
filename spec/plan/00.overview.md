# 00. Overview — plan index, progress board, constitution

The entry point for the spec workflow. Every plan registers here so a second agent can see what exists, what is
claimed, and what is done without reading every doc.

- Product SSOT: [PRD.md](../../PRD.md) — what postpilot is, and why.
- Structural SSOT: [ARCHITECTURE.md](../ARCHITECTURE.md) — where code goes, which way dependencies point.
- Deploy/ops SSOT: [DEPLOY.md](../../DEPLOY.md).

## 1. The workflow

```
new feature      /create-plan  NN → /create-plan-job  NN → /implement-job MM
change to built  /create-change NN → /create-change-job NN → /implement-job MM
audit → refactor /create-code-review → /create-refactor-job NN → /implement-job MM
```

- `spec/plan/NN.*.md` — the **as-built** WHAT. Updated when a job lands; no checkboxes.
- `spec/changes/NN.*.md` — a WHAT **delta** against a shipped plan. Archived when its job lands.
- `spec/jobs/MM.*.md` — the buildable work doc (Acceptance Criteria + Implementation Checklist). Archived when done.
- `spec/code-review/NN.*.md` — a read-only audit; findings only, never code changes.
- `spec/policy/**` — canonical product rules that are **currently true**.
- `spec/tech/**` — a doc per non-obvious technical decision the PRD doesn't already own
  ([draft-autosave](../tech/draft-autosave.md)).

Plan numbers and job numbers are independent sequences, monotonic across `archive/` — never reused, never renumbered.

## 3. The constitution

The invariants below are derived from the PRD's core design decisions (§3) and confirmed stack decisions (§6). They
are the rules a plan, change, or job may **not** break silently. If a request requires breaking one, stop and resolve
it with the user first — reversing one of these reverses a stack decision with it.

- **[I1] postpilot never publishes.** The deliverable is copy-ready output; the app holds no platform write
  credentials and drives no browser automation. (PRD §3.1 — this is what keeps the frontend a purely static SPA.)
- **[I2] The canonical generated post is a block array, not HTML.** Per-platform output (Naver plain text + photo
  markers, Tistory HTML fragment, …) is *derived* from it. Making HTML canonical makes Naver unsupportable. (PRD §3.2)
- **[I3] Generation separates observe from write and keeps every model choice explicit.** The observation stage looks
  only at photos and produces structured output; writing consumes observations + notes + the style profile. Normal
  generation observes once and may fan out to two writing candidates over the same snapshot. The app may ship a
  versioned recommended pairing, but never applies it automatically; the user explicitly applies/changes every active
  model and A/B pair. (PRD §3.3)
- **[I4] One style profile per account.** Never shared between accounts — a merged profile cannot be separated later.
  Korean style analysis treats the sentence-ending form (종결어미) as the primary signal. (PRD §3.4)
- **[I5] Long work is a server-side job record, not a blocking RPC.** `StartGeneration` returns a `job_id`; the client
  polls `GetGeneration`; a worker goroutine in the API process consumes the queue; `running` jobs are swept to
  `failed` on restart. Edits ride the same queue. (PRD §3.5)
- **[I6] Image work happens in the browser, before upload.** HEIC decode + 1024px downscale + JPEG encode client-side;
  originals never reach the API. This is what keeps the Go image CGO-free and distroless. (PRD §6.2)
- **[I7] Schema migrations are embedded in the binary and run at boot.** A migration failure kills the process so the
  deploy's `/health` gate rolls back. No separate migration container, no manual step. (PRD §6.3, DEPLOY.md §2)

The provider abstraction is a boundary, not a preference: nothing above `internal/llm` learns which provider answered
(PRD §6.4, ARCHITECTURE.md §2.1).
