# 13. Multilingual Interface and Target-Language Generation

> Serve the complete interface in Korean or English, let every post choose the language of its next full generation,
> and keep voice learning language-safe | Scope: FS | Status: done (job 32)

## Purpose

Postpilot currently assumes Korean in interface copy, document metadata, errors, generation prompts, and voice
analysis. That prevents an English-speaking visitor from understanding the product and prevents an operator from
deliberately writing an English post without fighting Korean-only prompt rules.

This plan separates four values that must not silently follow one another:

- **UI locale** — the language of Postpilot's own chrome (`ko` or `en`), selected per browser.
- **Post target language** — the language requested for the next ordinary generation or write A/B comparison.
- **Post content language** — the declared language provenance of the current machine-established canonical content.
- **Voice source language** — the one language from which a voice may learn language-specific style.

A new post starts with the current UI locale as its target, but the user can change it. Changing either the UI locale
or a post's target language never translates or discards existing content. Full generation and write A/B use the
post's frozen target; AI revision preserves the current content language. A voice used across languages contributes
only portable structure and tendency traits outside its source language.

This is also the localization foundation for the public Postpilot explanation page: that page can keep one stable URL
and mount the same locale control in its header.

## Scope / Non-goals

### In scope

- Exactly two supported languages: Korean and English, represented at persistence/browser boundaries by canonical
  BCP 47 primary tags `ko` and `en`.
- Korean and English for all app-owned visible copy: authenticated routes, login, navigation, dialogs, validation and
  failure summaries, empty/loading states, accessibility names, document title/description, dates, numbers, and
  status labels.
- URL-neutral locale selection with browser preference detection, an explicit persistent override, and an accessible
  selector available before and after login.
- A typed `i18next` + `react-i18next` runtime for the static Vite SPA, with bundled resources and no translation fetch
  at runtime.
- A persisted per-post target language, initialized by the frontend from the current UI locale on `/posts/new`, and a
  separate content-language provenance field.
- A persisted immutable source language per voice; existing and account-bootstrap voices migrate as Korean.
- Language-aware writing, revision, voice analysis, rule comparison, and profile validation.
- Full same-language voice projection and a deliberately restricted portable cross-language projection.
- Excluding a post from voice-learning mutations when its content language differs from its voice's source language.
- Stable structured application failures (`reason + params`) localized by the frontend instead of displaying
  backend-authored Korean prose.
- A lossless migration of current accounts, voices, posts, jobs, experiments, profiles, and history.

### Non-goals

- More languages, regional translations, locale-prefixed routes, locale query parameters, or language redirects.
- Persisting UI locale to an account or synchronizing it across devices. It must work while signed out, so the browser
  owns it.
- Machine translation of existing posts, memos, purposes, voice names, profile values, samples, or user-authored text.
- Automatic language detection of authored/generated content. Language fields are explicit product provenance.
- Translating model/provider names or arbitrary provider/Mac diagnostics. Postpilot supplies a localized summary;
  external detail may remain verbatim in an optional technical disclosure.
- Changing a voice's source language after creation, sharing evidence between voices, or translating one voice into
  another. The user creates another isolated voice instead ([I4]).
- Making AI revision a translation operation. To change the body language, change the target and run ordinary
  generation or write A/B.
- Making photo observation depend on the target language. Observations remain target-language-independent semantic
  facts and are not translated merely because the writing language changes.
- New locales from environment config, a translation-management service, SSR, or backend-rendered copy.
- Any change to block-array canon, explicit model selection, publication boundaries, browser image processing, or job
  durability ([I1]–[I7]).

## Design

### Language vocabulary and invariants

The public proto contract uses a finite enum because the supported set is closed and required at transport edges:

```proto
enum ContentLanguage {
  CONTENT_LANGUAGE_UNSPECIFIED = 0;
  CONTENT_LANGUAGE_KOREAN = 1;  // persisted/browser tag: ko
  CONTENT_LANGUAGE_ENGLISH = 2; // persisted/browser tag: en
}
```

The Go domain uses a validated value (`ko | en`), SQLite stores the canonical tags, and the frontend maps the enum to
the same `ContentLanguage = 'ko' | 'en'` union inside `shared/api`. `UNSPECIFIED` is never persisted and is invalid on
every create/start boundary that requires a language.

The invariants are:

1. UI locale changes presentation only.
2. A new post snapshots the current UI locale as its initial target; the request carries a concrete value.
3. Changing target language preserves content, observations, content revision, machine baseline, status, and
   finalization.
4. Ordinary generation and write A/B freeze the stored target language at enqueue/snapshot time.
5. Successful generation or application of a write candidate sets `content_language` to that frozen target.
6. Manual content edits and target changes preserve `content_language`.
7. Revision freezes and preserves `content_language`, regardless of the current target.
8. A voice learns from a post only when `post.content_language == voice.source_language`.
9. Cross-language generation receives only the portable projection defined below; it never receives excerpts or
   language-specific rules from the source language.
10. Locale switches, language selects, reads, page mounts, export, and finalization alone make no provider call.

### UI locale resolution and lifecycle

Before React mounts, the app resolves locale synchronously:

```text
valid localStorage["postpilot.locale"]
  > first supported primary tag in navigator.languages
  > ko
```

Matching is case-insensitive by primary subtag (`en-US → en`, `ko-KR → ko`); unsupported or malformed values are
ignored. An explicit selection writes the canonical tag and wins on later visits. The URL, pathname, search, hash,
router cache, and session are untouched.

Initialization sets, before the first React paint:

- i18next's active language;
- `<html lang="ko|en">`;
- localized document title and description; and
- locale-aware `Intl.DateTimeFormat`, `Intl.RelativeTimeFormat`, and `Intl.NumberFormat` helpers.

The selector uses autonyms (`한국어`, `English`), exposes a real accessible label, and changes language without
navigation. It appears on login and in authenticated shell controls; the public page later mounts the same feature in
its header. It is not a sixth bottom-navigation destination.

Resources are bundled, typed namespaces under `frontend/src/app/providers/i18n/resources` (`common`, `auth`, `nav`,
`posts`, `voices`, `purposes`, `models`, `publishing`, `errors`, and downstream `marketing`). Components use stable
semantic keys with interpolation/pluralization; Korean source sentences are not keys. Catalog-topology tests require
the Korean and English namespaces to carry the same keys. Production has a Korean fallback only as a defensive
boundary.

The implementation job invokes `/library-setup`, reads the current official React/Vite documentation, installs the
then-current latest `i18next` and `react-i18next`, and verifies the lockfile. No language-detector or HTTP-backend
plugin is needed because resolution and resources are local.

### Post target language and content provenance

`Post.target_language` is the desired language of the **next full machine write**. `Post.content_language` is absent
until a machine result establishes canonical content, then records that result's language provenance.

`/posts/new` shows `글 언어 / Post language` with Korean and English, initialized from the current UI locale. The
first `SavePostDraft` carries it explicitly; the server never infers a browser locale. Existing posts expose the same
select with the post inputs.

The target is presence-aware in `SavePostDraftRequest`: required on create, absent preserves on ordinary title/memo
autosave, and a present valid value updates only the target. It travels through the existing newest-wins draft queue
so a delayed text save cannot revert a newer language selection. Selecting a language alone on an unsaved page does
not create a post.

Changing target language:

- persists immediately for an existing post;
- preserves all current text and lifecycle fields;
- affects only a later ordinary generation or write A/B snapshot; and
- shows a localized hint when target and content differ: current content remains in its recorded language until a
  full generation/result application succeeds.

It may change while another run is frozen; that run retains its old language and a later run takes the new one. Target
length remains Unicode-character based in both languages. Purpose text and memo are injected verbatim; the explicit
target-language instruction outranks a conflicting language instruction inside purpose or voice text.

### Voice source language and projection

Every `Voice` has one immutable `source_language`.

- Migration and `adduser` bootstrap assign Korean to all existing/default voices.
- `CreateVoice` requires an explicit source language; the create form defaults it to the current UI locale but lets
  the user choose before submission.
- Directory, profile, post `VoiceRef`, tombstone, and experiment projections expose the source language.
- Rename/default/delete/restore do not change it. There is no update-language RPC.
- Pasted samples are accepted as evidence declared for that voice's source language; the form clearly names the
  expected language. The server does not guess the pasted text's language.

Prompt projection is exact:

| Relation           | Included                                                                                                                         |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------- |
| `target == source` | complete structured profile, legacy/manual guidance, active rules, user rules, and ranked imported/authored excerpts             |
| `target != source` | structured `structure` and `axes` only: paragraph range, intro/closing pattern, heading/list/emoji habits, and six tendency axes |

The cross-language projection excludes lexical preferences/bans, endings/register, language-specific syntax and
connectives, free-form styleguide/manual rules, lexical/endings/syntax contrast rules, samples, and authored excerpts.
It includes no translated substitute. The prompt labels the projection as portable and states that the target language
wins. This is deterministic backend behavior in the voice context's published projection, not frontend filtering.

### Generation, observation, revision, and experiments

At ordinary `StartGeneration`, the service reads the owned post and freezes its target language into the durable
payload beside target length and purpose. The worker never rereads language from the post. The write prompt:

- explicitly names the target language;
- chooses the full or portable voice projection using frozen target vs immutable source;
- includes the fixed `[한국어 자연 문체 기준선]` from plan 06 only when the frozen target is Korean and omits it
  entirely for every non-Korean target;
- keeps the existing voice → purpose → per-post precedence;
- requests title, summary, tags, prose, image alt, and caption in the target language; and
- retains block/schema/attachment rules unchanged.

Observation is deliberately independent. Its prompt, semantic schema, batching, persistence, and filename matching do
not receive target language. The same photo facts can feed either writer, and changing target alone does not translate,
invalidate, or reinterpret persisted observations. Contact-sheet observation text remains model-produced diagnostic
data rather than localized UI chrome.

A write A/B snapshot freezes target language once. Both candidates receive byte-identical language/profile/purpose
input; target participates in the snapshot hash. Retry retains it. Applying the winner writes content,
`content_language`, and the machine baseline through one post-context operation. Experiment detail exposes the frozen
target.

Revision ignores a later target change and freezes the current `content_language`. Its prompt requires that language
and treats translation as outside revision semantics. Success preserves the same content language and creates the new
baseline as today. A contentless post cannot revise; a legacy content row receives Korean provenance in migration
rather than being guessed at runtime.

### Language-safe learning and analysis

Finalization itself is language-neutral and remains available. The following post-derived profile mutations require
`content_language == voice.source_language` before event/job/provider work:

- finalize-and-learn and retry;
- sentence feedback that can become evidence;
- save-revision-instruction-as-rule; and
- any post-backed rule-comparison or validation input.

A mismatch returns `VOICE_CONTENT_LANGUAGE_MISMATCH` and localized UI copy explaining that the post can still be
finalized/exported but cannot teach this voice. No event, source, rule, evidence, corpus version, or job is created.

Voice analysis is selected by source language:

- Korean retains deterministic `다 / 해요 / 습니다 / 기타` ending measurement and the PRD-required ending priority.
- English measures sentence length in words as well as characters and analyzes register, contraction use, connective
  style, sentence-final punctuation/cadence, structure, lexical habits, and the same six axes. It does not force
  English prose into Korean ending categories.
- Both variants reject unsupported guesses, preserve structured-output validation, and publish analysis/profile values
  in the source language.
- Profile validation, analyze-model experiments, rule extraction, and comparison use the voice source language and
  only that voice's eligible corpus.

### Localizable failure contract

Backend prose is not a translation API. `proto/postpilot/v1/error.proto` defines stable details:

```proto
message AppErrorDetail {
  string reason = 1;             // stable UPPER_SNAKE_CASE product reason
  map<string, string> params = 2;
}

message Failure {
  string reason = 1;
  map<string, string> params = 2;
  string technical_detail = 3;   // optional provider/agent detail; never the only explanation
}
```

Connect handlers attach `AppErrorDetail` while retaining normal Connect status codes. `shared/api` is the only
generated-proto seam and exposes a parser; UI surfaces translate `errors.<reason>` with validated parameters.
Unknown/malformed reasons render localized `errors.UNKNOWN_FAILURE`, never raw backend text.

Durable jobs, experiment candidates, validation/comparison failures, and publish failures expose `Failure`.
App-owned failure states persist reason+params. External provider/Mac detail may be shown beneath the localized summary
in a clearly marked technical disclosure and is never interpolated as HTML. Existing substring-based raw-message
mappers are removed rather than expanded.

### Proto / Connect contract

`proto/postpilot/v1/language.proto` owns `ContentLanguage`; `error.proto` owns the two failure messages. Generated
clients are regenerated through `pnpm gen:proto` and never hand-edited.

Key additions:

```proto
message Voice {
  // existing fields...
  ContentLanguage source_language = 8;
}
message CreateVoiceRequest {
  string name = 1;
  optional ContentLanguage source_language = 2; // presence is required by the service
}

message VoiceRef {
  // existing fields...
  ContentLanguage source_language = 4;
}

message Post {
  // existing fields...
  ContentLanguage target_language = 21;
  ContentLanguage content_language = 22; // UNSPECIFIED before machine content
}
message PostSummary {
  // existing fields...
  ContentLanguage target_language = 9;
  ContentLanguage content_language = 10;
}

message SavePostDraftRequest {
  // existing fields...
  optional ContentLanguage target_language = 6; // required on create; absent preserves
}

message GenerationJob {
  // existing fields...
  ContentLanguage target_language = 13;
  Failure failure = 14;
}

message ModelExperiment {
  // existing fields...
  ContentLanguage target_language = 20; // write only; otherwise UNSPECIFIED
}
```

`StartGeneration`, `StartRevision`, and `StartWriteExperiment` do not trust a caller-supplied language: their services
resolve and freeze the owned post's persisted fields. Learning snapshots carry content/source language so retry cannot
follow a later post or voice change. Existing raw `error` fields may remain deprecated for one compatibility migration,
but new frontend code renders structured failure data.

### SQLite model and migration

The next available embedded migration adds canonical tags at rest:

```sql
voices.source_language TEXT NOT NULL CHECK (source_language IN ('ko','en'));

posts.target_language  TEXT NOT NULL CHECK (target_language IN ('ko','en'));
posts.content_language TEXT CHECK (content_language IS NULL OR content_language IN ('ko','en'));

model_experiments.target_language TEXT
  CHECK (target_language IS NULL OR target_language IN ('ko','en'));
```

It also adds structured `error_reason` / `error_params` / `technical_detail` storage beside each durable user-visible
failure owned by generation jobs, experiment candidates/application/adoption, voice validation/comparison/learning,
and publishing. `error_params` is a JSON object validated at mapping boundaries; private/logging causes stay separate.

Backfill rules:

- every existing voice → `source_language='ko'`;
- every existing post → `target_language='ko'`;
- existing posts with canonical/machine content → `content_language='ko'`; contentless drafts → `NULL`;
- frozen legacy queued generation/write snapshots without language → Korean;
- legacy failed rows → a stable generic reason plus retained technical detail.

The migration preserves ids, content JSON, observations, baselines, revisions, purpose/voice assignments, status,
timestamps, jobs, experiments, and evidence. Any required `posts` rebuild follows the established foreign-key-off,
explicit-transaction, `foreign_key_check` discipline and remains boot-embedded ([I7]). No provider call occurs.

### Job and state transitions

```text
UI locale ko ⇄ en
  └─ presentation only; URL/session/domain rows unchanged

post target ko ──select en──▶ target en + existing content/content_language unchanged
                                     │
                                     ├─ full generation / write A/B freezes en
                                     │     └─ success/apply → content_language=en
                                     └─ revision → preserves existing content_language

voice source == content language ──explicit learn──▶ normal voice job
voice source != content language ──explicit learn──▶ refused before event/job/provider
```

No job kind is introduced. Boot sweep, polling, retry, explicit model choice, and the no-transaction-across-provider
rule remain unchanged.

## Acceptance Criteria

1. With no stored override, `navigator.languages=['en-US','ko-KR']` yields English; `['ja-JP']` yields Korean.
   Selecting Korean/English persists `postpilot.locale`, survives reload, and changes no URL, session, or domain row.
2. Locale resolves before React paint; `<html lang>`, document title/description, dates, relative times, numbers,
   visible labels, and accessibility names all match it.
3. Every current route is operable in Korean and English at 360px and desktop widths. Catalog topology tests catch
   missing keys; app-owned prose does not remain scattered through components or backend messages.
4. An English UI opens `/posts/new` with target English; Korean opens it with Korean. The first create request always
   carries a concrete non-`UNSPECIFIED` value, and missing/unsupported values are rejected without server fallback.
5. Changing a post target from Korean to English preserves content bytes, observations, revisions, baseline, status,
   and finalization. Reload shows English target, Korean content provenance, and the explanatory mismatch hint.
6. Ordinary generation freezes the stored target. Changing target after enqueue cannot alter that job; success writes
   content and content-language provenance in the frozen language. Korean prompt snapshots contain the plan-06
   naturalness baseline, while otherwise-equivalent non-Korean snapshots omit the complete section.
7. Otherwise-equal Korean- and English-target jobs build byte-identical observation requests with no target-language
   instruction, and changing only the stored target does not translate, clear, or invalidate existing observations.
8. Write A/B gives both candidates the same frozen target and appropriate voice projection, includes target in the
   input hash/detail, and applying a winner atomically establishes matching content-language provenance.
9. Revision after changing target preserves the existing content language through five revisions; its prompt never
   reads the newer target as output language.
10. Existing voices/posts migrate as Korean without changing current Korean content/profile/history. Contentless
    drafts have no content provenance; existing machine content has Korean provenance.
11. Creating an English-source voice requires explicit English; source language appears after reload and cannot be
    changed through any RPC. It receives only its own English evidence.
12. Same-language generation receives the complete voice projection. Cross-language prompt snapshots prove that only
    structure/axes remain and there are no excerpts, lexical/endings/syntax rules, or free-form guidance.
13. A finalized English-content post assigned to a Korean-source voice can be finalized, edited, exported, copied,
    and published, but learn/save-as-rule/feedback is rejected before event/job/provider creation with a localized
    explanation. The inverse behaves identically.
14. Korean analysis retains deterministic ending behavior. English analysis uses its language-specific prompt and
    word-length/register/contraction/cadence measurements; neither corpus includes a different-language post.
15. Connect validation/conflict failures and durable job/experiment failures render from stable reason+params in both
    locales. Unknown reasons show a localized generic fallback; arbitrary raw backend text is never the sole message.
16. Locale selection, language-option saves, voice/list/profile reads, page mount, copy, export, and finalization make
    no provider call and enqueue no language-related job.
17. Proto/sql generation, migration integrity/backfill tests, prompt/payload/snapshot tests, backend vet/build/tests,
    frontend tests/lint/FSD/style/build, and spec lint pass without weakening existing Korean assertions.
