# 09. Stage Model Experiments and Leaderboards

> Opt-in recommended model pairs, blind A/B comparisons for observe/analyze/write, winner application, and a
> per-account stage leaderboard | Scope: FS | Status: done — job 15 plus the generation/finalization split in job 17

## Purpose

The model registry lets each account choose a model, but it cannot answer the product question that matters: which
model produces the better result for this person's photos, Korean voice and posts? Public benchmarks do not measure
that. Model names and prices also change faster than the rest of the application.

Postpilot learns from the two users' explicit comparison decisions without taxing every draft. Ordinary `생성` uses
the active observe/write selections and one writer, while `A/B 비교 생성` produces two writing candidates from one
shared observation/input snapshot. The post list makes completed comparisons visible after the browser has been
closed, and a blind review turns the chosen candidate into the canonical post. Observation and voice-analysis models
are evaluated in an explicit model lab. Every valid pairwise verdict feeds a private, stage-specific leaderboard.

The app may ship a versioned **recommended set**, but it never silently applies one. A user must press
"추천 조합 적용". This is the deliberate amendment to [I3] agreed in the plan interview: no automatic default, while
an opt-in recommendation is allowed.

## Scope / Non-goals

**In scope**

- A versioned recommended set in the provider registry: one active model and one A/B pair for each of `observe`,
  `analyze` and `write`.
- Selection slots (`active`, `candidate_a`, `candidate_b`) persisted per user and stage, with atomic pair/preset RPCs.
- The shipped August 2026 balanced set: Gemini vs Qwen for observation, GPT vs DeepSeek for voice analysis, and
  Claude vs Grok for writing.
- Ordinary generation as one queued job: observe at most once, call one explicit active writer, and persist validated
  canonical content directly. Explicit write A/B as a separate queued experiment over one immutable snapshot.
- Explicit observe-model experiments against the same saved post/photos and explicit analyze-model experiments
  against the same saved voice corpus.
- Server-enforced blind review, random left/right assignment, retry of only a failed candidate, skip/dismiss, and
  stage-specific winner application.
- `AI 생성 중` and `AI 결과 확인` states on the post list, plus resumable review after navigation or reload.
- A private leaderboard per account and stage with Elo, matches, wins, losses, win rate, average latency, token usage
  and actual/estimated cost.
- Usage accounting through the vendor-neutral LLM response (`prompt_tokens`, `completion_tokens`, `cost_usd` when
  reported), with a price-snapshot fallback.
- Content retention and deletion rules for sensitive photos, writing samples, prompts and candidate outputs.

**Non-goals**

- Automatically splitting production traffic, silently choosing a winner, or changing a model without an explicit
  user action.
- Comparing more than two candidates in one experiment. Multi-arm tests obscure the simple left/right decision and
  increase spend combinatorially.
- Varying more than one stage in the same verdict. A write comparison shares observation and profile inputs; an
  observe comparison does not write posts; an analyze comparison does not also generate posts.
- A global leaderboard across accounts. Writing preference and voice are personal; neither raw content nor verdicts
  are shared between the two accounts.
- Automated statistical significance claims, public benchmark ingestion, model auto-routing, automatic fallbacks,
  prompt optimization, or an operator/admin UI for editing `providers.yaml`.
- Keeping an experiment payload forever. Durable aggregate metadata is enough for the leaderboard.
- Replacing the existing provider boundary or adding a second queue/worker system.

## Design

### One isolated variable per experiment

```
ordinary post generation
  saved post + photos
        │
        ▼
  observe once with active observe model
        │ immutable write snapshot: observations + memo + profile + filenames
        └──────────────▶ active write model ─▶ canonical PostContent

explicit write A/B
  same frozen inputs/options ─▶ candidate A / candidate B ─▶ blind verdict ─▶ canonical PostContent

model lab
  observe tab: same photo snapshot ─▶ model A / model B ─▶ choose better observation set
  analyze tab: same corpus snapshot ─▶ model A / model B ─▶ choose better style guide
```

Only the explicit A/B action fans out writing. If observation also fanned out, a fair write comparison would require
four drafts or a mid-job human pause. The model lab instead measures observation and analysis independently and lets
a winner become the active model for later jobs.

An experiment always captures its inputs before enqueueing and records an input hash. Both candidates receive the
same prompt/schema and snapshot; only `ModelRef` differs. Temperature, max tokens, prompt version and validation path
are identical. Candidate calls run concurrently (limit two) after the snapshot/common observation is ready. No DB
transaction is held across either provider call.

### Recommended registry set

`backend/config/providers.yaml` gains price/context display metadata and versioned recommendation sets. Prices below
are USD per one million tokens as checked on 2026-08-30 against the OpenRouter Models API; promotions and
routed endpoints can change them.

| Stage | Slot | OpenRouter model id | Context | Input / output | Reason for the initial pair |
|---|---|---|---:|---:|---|
| observe | A / active | `google/gemini-3.7-flash` | 1,048,576 | $0.75 / $3.75 | fast multimodal primary |
| observe | B | `qwen/qwen3.8-flash` | 1,000,000 | $0.15 / $0.47 | low-cost Chinese multimodal challenger |
| analyze | A / active | `openai/gpt-5.6-luna` | 1,050,000 | $0.20 / $1.20 | inexpensive long-context analysis primary |
| analyze | B | `deepseek/deepseek-v4-flash-0731` | 1,310,720 | $0.045 / $0.09 | very low-cost Chinese analysis challenger |
| write | A / active | `anthropic/claude-sonnet-5` | 1,000,000 | $2.00 / $10.00 | high-quality prose primary |
| write | B | `x-ai/grok-4.6` | 500,000 | $2.00 / $6.00 | frontier alternative with cheaper output |

The set id is `balanced-2026-08`; model ids are pinned rather than `latest` aliases so an experiment never changes
identity halfway through its history. The YAML declares `context_tokens`, `input_usd_per_million`,
`output_usd_per_million`, `pricing_checked_at`, and the normal capability flags. This metadata is informational and
must never be used as the charged amount when `usage.cost` is present.

`ListRecommendationSets` exposes only refs, labels and version. `ApplyRecommendationSet` first resolves every ref and
refuses the whole operation if any model is missing, disabled or unsuitable. A successful apply atomically stores all
nine rows (active + A/B for three stages). A fresh account still has no selections. The frontend never invokes apply
on mount or first login.

Users may replace either candidate with any registered, enabled model suitable for that stage. The pair RPC refuses
the same ref twice. Observe candidates both require `vision`; write candidates must both pass the plan-06 output path;
analyze candidates are text-capable models.

### Selection memory

Plan 04's provider-owned `model_selections` becomes:

```sql
model_selections (user_id TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
                  stage TEXT NOT NULL,       -- observe | write | analyze
                  slot  TEXT NOT NULL,       -- active | candidate_a | candidate_b
                  provider_id TEXT NOT NULL,
                  model_id TEXT NOT NULL,
                  updated_at TEXT NOT NULL,

```

The migration rebuilds the shipped table and copies every existing row into `slot = 'active'`. Existing
`GetSelections`/`SaveSelection` retain active-slot behavior for compatibility; pair and preset writes use explicit
batch RPCs. Start RPCs still receive explicit model refs from the frontend and never infer a model from this table.

### Experiment aggregate and lifecycle

`internal/experiment` owns two tables. A model label is snapshotted with the ref so history remains legible after a
model disappears.

```sql
model_experiments (
  id TEXT PRIMARY KEY,
  user_id TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  post_slug TEXT REFERENCES posts(slug) ON DELETE SET NULL,
  stage TEXT NOT NULL,                 -- observe | analyze | write
  status TEXT NOT NULL,                -- queued | running | review | partial | decided | dismissed | failed
  job_id TEXT,
  input_snapshot TEXT,                 -- stage-specific JSON; NULL after content purge
  input_hash TEXT NOT NULL,
  prompt_version TEXT NOT NULL,
  winner_candidate_id TEXT,
  outcome TEXT,                        -- winner | skipped | unpaired
  apply_error TEXT,
  applied_at TEXT,                     -- durable idempotency marker for target mutation
  adoption_requested INTEGER NOT NULL, -- 0 | 1, fixed with the verdict
  adoption_error TEXT,
  adopted_at TEXT,
  created_at TEXT NOT NULL,
  finished_at TEXT,
  decided_at TEXT,
  content_expires_at TEXT)

model_experiment_candidates (
  id TEXT PRIMARY KEY,
  experiment_id TEXT NOT NULL REFERENCES model_experiments(id) ON DELETE CASCADE,
  model_provider_id TEXT NOT NULL,
  model_id TEXT NOT NULL,
  model_label TEXT NOT NULL,
  display_side TEXT NOT NULL,           -- left | right, randomized once by the server
  status TEXT NOT NULL,                 -- pending | running | succeeded | failed
  output TEXT,                          -- stage-specific protojson or style-guide text
  error TEXT,
  prompt_tokens INTEGER,
  completion_tokens INTEGER,
  cost_microusd INTEGER,
  cost_source TEXT,                     -- reported | estimated | unavailable
  latency_ms INTEGER,
  started_at TEXT,
  finished_at TEXT,
  UNIQUE (experiment_id, display_side))
```

The experiment is a separate aggregate because it has its own lifecycle, retries, verdict and retention. It refers to
a post by slug but never owns or updates the `posts` table directly. Candidate output is validated by the owning stage
before the experiment stores it.

Lifecycle:

```
queued → running ─┬─ two succeeded ─▶ review ─┬─ winner ─▶ decided
                  │                           └─ skip ───▶ dismissed
                  ├─ one succeeded ─▶ partial ── retry failed candidate ─▶ queued
                  │                           └─ use single ─▶ decided (outcome=unpaired)
                  └─ zero succeeded ─▶ failed ── retry candidates ───────▶ queued
```

Only `outcome=winner` changes Elo/win-loss counts. `skipped`, `unpaired`, failures and retries are visible usage but not
quality verdicts. One undecided write experiment is allowed per post. The plan-05 active-job guard prevents a second
running post job; the experiment guard also prevents starting another after the job has finished but before its result
is decided/dismissed, and keeps a decided write blocked until its winner has actually been applied and any requested
active-model adoption has completed.

### Queue execution and resumability

All three experiment kinds ride plan 05's `generation_jobs`; no second worker exists. The job payload carries the
experiment id and stage. Post-backed observe/write jobs use `post_slug`; analyze experiments use the acting user as
their target. `Start*` creates the experiment/candidates and enqueues before returning `{job_id, experiment_id}`; no
provider call happens in the RPC.

The experiment job handler depends on consumer-owned stage-runner ports:

- generation publishes snapshot, observe-candidate, write-candidate, and apply-winner behavior. It reuses plan 06's
  prompts, schemas, parser, validator and attachment filter; it does not persist candidate output as canonical.
- voice publishes corpus snapshot, analyze-candidate and apply-styleguide behavior. It reuses plan 03's nine-section
  prompt/validation and never touches user-owned `rules`.
- experiment owns orchestration, candidate persistence, random display assignment, verdicts, retention and ranking.

The composition root injects these behaviors; experiment never imports a provider adapter or reads another context's
tables. Progress stages are `observe`, `compare_write`, `compare_observe`, and `compare_analyze`. Candidate progress is
persisted as each call completes. A partial result is a successfully completed job with experiment status `partial`;
both failures make the job and experiment `failed`.

Retry creates a new queue job for only failed candidates and uses the original snapshot. If a referenced photo/object
was deleted or the snapshot can no longer be reconstructed, retry is refused with "입력이 변경되어 같은 조건으로
재시도할 수 없어요. 새 비교를 시작해 주세요." Successful paid output is never discarded by a sibling failure.

At boot, the normal job sweep runs first. Experiment recovery then converts interrupted running candidates to
retryable failures and checks queued experiment ids through the job context's published runnable-job behavior. It
preserves queued work that still has a job and fails only an orphan created in the narrow pre-enqueue/link crash
window.

### Stage-specific review and application

**Write (explicit A/B comparison)**

- `A/B 비교 생성` sends one explicit observe ref when needed, two explicit write refs, and optional target presence.
- Observation runs once and is persisted for the contact sheet. Both writers consume the same resulting observation,
  title, memo, exact filenames and voice-profile snapshot.
- On completion, `posts.content` and `posts.status` are unchanged; the post projection exposes
  `pending_experiment_id`, so the list shows `AI 결과 확인`.
- After a blind candidate is selected, `결과 적용` and `결과 적용하고 활성 모델로 변경` each record the verdict
  and idempotently apply canonical content. Only the latter requests adoption of the winning write model. Durable
  application/adoption markers preserve that intent across partial failure and retry without duplicate Elo/content.
- The A/B pair remains unchanged so the same rivalry can accumulate evidence until the user edits the pair. Neither
  result action finalizes the post or starts voice learning.

**Observe (model lab)**

- The user chooses an existing post with at least one photo. Both vision models see the same ordered photo set and
  filename list; neither result is written to `posts.observations` during the comparison.
- The review shows each photo once and aligns `scene`, `mood`, `visible_text`, `objects`, and `people_present` for the
  two candidates. One verdict covers the whole photo set, so a post with eight photos is one match, not eight votes.
- After reveal, separate explicit actions may apply the winner's observations to that post and/or adopt its model as
  the active observe selection.

**Analyze (model lab)**

- Both models receive the same immutable concatenation of all current voice samples and the same nine-section prompt.
- The review aligns the generated style-guide sections; the existing profile and `rules` remain unchanged during the
  experiment.
- After reveal, applying the output requires overwrite confirmation and replaces `styleguide` only. `rules` are never
  changed. A separate explicit action adopts the winning analyze model.

Before a verdict, the API omits all candidate `ModelRef`s and model labels; hiding text only in React is not blind.
Opaque candidate ids and randomized `display_side` are returned. After a verdict/dismissal, the same response reveals
both model snapshots, usage, latency and cost.

### Contract — `proto/postpilot/v1/model_experiment.proto`

The concrete proto uses enums and a typed output `oneof`; this sketch names the required surface:

```proto
service ModelExperimentService {
  rpc StartObserveExperiment(StartObserveExperimentRequest) returns (StartExperimentResponse);
  rpc StartAnalyzeExperiment(StartAnalyzeExperimentRequest) returns (StartExperimentResponse);
  rpc StartWriteExperiment(StartWriteExperimentRequest) returns (StartExperimentResponse);
  rpc GetExperiment(GetExperimentRequest) returns (GetExperimentResponse);
  rpc RetryCandidate(RetryCandidateRequest) returns (RetryCandidateResponse);
  rpc ChooseWinner(ChooseWinnerRequest) returns (ChooseWinnerResponse);
  rpc UseSingleCandidate(UseSingleCandidateRequest) returns (ChooseWinnerResponse);
  rpc DismissExperiment(DismissExperimentRequest) returns (DismissExperimentResponse);
  rpc ApplyWinnerOutput(ApplyWinnerOutputRequest) returns (ApplyWinnerOutputResponse);
  rpc DecideWriteExperiment(DecideWriteExperimentRequest) returns (ChooseWinnerResponse);
  rpc ListExperiments(ListExperimentsRequest) returns (ListExperimentsResponse);
  rpc GetLeaderboard(GetLeaderboardRequest) returns (GetLeaderboardResponse);
}

message StartObserveExperimentRequest { string post_slug = 1; ModelRef model_a = 2; ModelRef model_b = 3; }
message StartAnalyzeExperimentRequest { ModelRef model_a = 1; ModelRef model_b = 2; }
message StartExperimentResponse { string experiment_id = 1; string job_id = 2; }

message ExperimentCandidate {
  string id = 1;
  DisplaySide display_side = 2;
  CandidateStatus status = 3;
  oneof output { PostContent post = 4; ObservationSet observations = 5; string styleguide = 6; }
  string error = 7;
  // ref/label/usage/latency/cost are populated only after reveal.
  ModelRef model = 8;
  string model_label = 9;
  Usage usage = 10;
}
```

Plan 06's `StartGeneration` contract remains the ordinary one-writer path and returns only `job_id`.
`StartWriteExperiment` carries the required distinct pair and returns both ids. `Post`/`PostSummary` expose
`pending_experiment_id` through the experiment context's published query rather than a cross-context SQL join.

ProviderService gains `ListRecommendationSets`, `ApplyRecommendationSet`, `GetComparisonPairs` and
`SaveComparisonPair`. API keys, base URLs and provider routing details still never cross the proto boundary.

### Usage and cost accounting

`llm.Usage` gains reported cost without exposing an OpenRouter type:

```go
type Usage struct {
    PromptTokens, CompletionTokens int
    CostMicrousd int64
    CostReported bool
}
```

The OpenAI-compatible adapter reads `usage.cost` from the final JSON/SSE usage object. When absent, the experiment
calculates an estimate from the catalog price snapshot and marks `cost_source=estimated`; when either tokens or price
is unavailable it marks `unavailable`. The UI labels estimates with `≈` and never adds a reported and estimated value
as if they had the same authority.

Actual cost includes provider routing, cache and reasoning adjustments and therefore wins over the displayed catalog
rate. Token and cost values are stored per candidate even for a failed/partial comparison when the provider returned
usage. Leaderboard usage totals include every successful candidate call; match quality uses winner verdicts only.

### Leaderboard methodology

Each account has three independent ladders. A model starts at Elo 1500 with K=32. A decided pair is replayed in
`decided_at` order to derive ratings; the small two-user data set does not justify a materialized table. This projection
can always be rebuilt from verdicts. Entries with fewer than `LEADERBOARD_MIN_MATCHES` (3) are shown as "데이터 수집
중" below ranked entries.

Every entry shows:

- rating and rank, matches, wins, losses, raw win rate;
- successful calls, average latency, prompt/completion tokens, and total/average cost;
- `reported`, `mixed`, or `estimated` cost quality;
- active/recommended/disappeared badges based on the current catalog, while historical labels remain intact.

Ties are not forced. "둘 다 사용하지 않기" dismisses the comparison and affects neither rating nor win rate.
Left/right assignment is randomized once per experiment and stored, preventing a reload from swapping candidates.

### Frontend UX and placement

Routes:

- `/ai-models` — recommendation set, current active/A-B settings, stage tabs, recent experiments and leaderboards.
- `/ai-models/experiments/$id` — resumable blind comparison/retry/reveal.
- `/posts` — `AI 생성 중`, `AI 결과 확인`, or `AI 결과 오류` badge/action derived from active job/experiment.

The editor exposes primary `생성`, secondary `A/B 비교 생성`, and a collapsed optional-length popover. Ordinary
generation reads active observe/write selections; A/B reads the configured write pair. Each passes refs explicitly
and reports only its own blockers. The model lab tabs retain explicit `비교 시작`; there is no scheduled/background
experiment.

`CandidateComparison` is two columns at `md` and above. On a phone, 50%-width Korean prose is unreadable, so it uses a
sticky `A | B` switch with independent preserved scroll positions and a persistent bottom choice bar. Candidate A/B
remain the same left/right identities across breakpoints. Observe review pins the photo/field label while switching;
analyze review aligns the mandated sections. The model reveal and usage panel appears only after the choice.

FSD placement:

| Piece | Placement |
|---|---|
| catalog price/recommendation/selection-slot types and hooks | `entities/model-catalog/{model,api}` |
| experiment model, API mappers, polling/history queries | `entities/model-experiment/{model,api}` |
| apply preset/pair, start/retry, choose/apply/dismiss actions | `features/apply-model-recommendation`, `configure-model-pair`, `start-model-experiment`, `review-model-experiment` |
| reusable responsive candidate review | `widgets/candidate-comparison` |
| stage leaderboard table/summary | `widgets/model-leaderboard` |
| settings/lab and review routes | `pages/ai-models`, `pages/model-experiment` |
| list/editor composition and badges | existing `pages/posts`, `pages/editor`; domain state remains in entities/features |
| polling/retention/display constants | `shared/config` only when genuinely client-owned |

Pages compose same-layer features/widgets; features do not import features. Generated proto code remains behind
`shared/api`. Any generic segmented control/dialog added for the phone comparison is a demand-driven `shared/ui`
primitive and uses the design-language semantic tokens; candidate output is a real preview card, while ordinary page
sections remain borderless planes.

### Retention, ownership and deletion

- Every RPC is scoped to the acting user. An experiment id from another account is `PermissionDenied`; leaderboard
  queries have no user-id input.
- Pending review/partial output remains until the user decides or dismisses it, so paid results do not vanish.
- After decide/dismiss, `input_snapshot` and both candidate outputs are purged after 30 days. Winner/loser refs,
  verdict, aggregate usage/cost/latency and timestamps remain until account deletion for leaderboard replay.
- Deleting the source post immediately clears its experiment payloads and sets `post_slug` null; metadata can remain.
  Deleting an account cascades every selection, experiment, candidate and verdict.
- Raw prompts, image bytes, sample bodies and candidate outputs are never logged. Logs may contain experiment id,
  stage, model ref, usage, latency, cost and error class.
- The content sweeper is idempotent and runs in the API process. It never deletes canonical post/profile output.

## Acceptance Criteria

1. A fresh account has no active or A/B selections and generation is blocked; nothing applies the recommendation
   automatically. Pressing `추천 조합 적용` stores the complete versioned set atomically, and reload shows it.
2. The shipped set contains the six pinned model ids in the table above. Apply is rejected without partial writes when
   any ref is missing, disabled, duplicated in a pair, or unsuitable for its stage.
3. Starting explicit write A/B returns `job_id` and `experiment_id` before any provider call. With photos, exactly one
   observe pipeline runs and both write calls receive byte-identical prompt/schema snapshots except for model ref.
4. While an A/B job is active the post list shows `AI 생성 중`; after two candidates finish it shows `AI 결과 확인`.
   Closing/reopening the browser at either point resumes polling/review from server state.
5. Before a verdict, `GetExperiment` contains opaque candidate ids/sides and outputs but no model refs or labels.
   Left/right assignment is server-randomized, stable across reloads, and revealed only after decision/dismissal.
6. Either write-result action records one verdict, applies exactly that validated `PostContent`, and moves the post
   to `review`. Apply-only changes no active model; apply-and-adopt changes only the active write model. Repeats are
   idempotent across ranking, content, and selection writes.
7. A write candidate is never persisted as canonical merely because the job finished. If winner application fails,
   the verdict remains with a visible retry and the previous post content/status is preserved.
8. An observe experiment sends the same ordered photo snapshot to two vision models, writes neither result during the
   run, and renders aligned per-photo fields. Its winner may be explicitly applied to the source post and/or adopted
   as active observe model.
9. An analyze experiment sends the same complete corpus snapshot to both models and changes neither profile nor
   rules during the run. Applying its winner requires confirmation, replaces `styleguide`, and never changes `rules`.
10. If one candidate fails, the successful result remains, the list/review shows a partial state, and retry invokes
    only the failed model with the original snapshot. `Use single` may apply the survivor but creates no win/loss.
11. Starting another write experiment for a post with an active, undecided, unapplied, or adoption-incomplete
    experiment is refused with the existing id. A snapshot that cannot be fairly retried produces the fixed
    "새 비교" reason.
12. Choosing "둘 다 사용하지 않기" dismisses the experiment and does not change either model's match count/rating.
13. Leaderboards are isolated by account and stage. A decided winner changes exactly two entries; ratings replay in
    decision order from 1500/K=32, and entries under three matches are marked provisional.
14. Candidate usage stores prompt/completion tokens, latency and reported `usage.cost` when present. When absent, a
    catalog-price estimate is marked with `≈`; unavailable data is not silently treated as zero.
15. A removed model remains legible in history/leaderboard from its snapshotted label but cannot start/retry/apply as
    an active selection. Provider capability checks still happen before network calls.
16. Another user cannot read, decide, retry, apply or list an experiment; raw model identities are not discoverable in
    a pre-verdict network response.
17. On desktop candidates render side by side; on phone the A/B switch preserves each candidate's scroll position and
    the choice controls remain at least 44px. All three stage output shapes are readable without horizontal prose.
18. Thirty days after a terminal verdict/dismissal the payload/output is purged while leaderboard counts, usage and
    model labels remain. Post deletion purges related payload immediately; account deletion removes everything.
19. Ordinary `생성` uses one active writer and creates no experiment. Target length is optional: absence has no hidden
    1,200-character prompt constraint, while a configured positive value is frozen for ordinary/A/B/revision work.
20. Post finalization is an exact-revision post transition separate from experiments and learning. `확정` makes no
    provider call; explicit combined/later learning failures never roll the post back from `finalized`.
