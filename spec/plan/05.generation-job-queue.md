# 05. Generation Job Queue

> Long model work is a server-side job record with real progress: start returns a `job_id`, the phone polls, a
> worker goroutine inside the API does the work, and a restart sweeps `running` → `failed` | Scope: FS | Status: done

## Purpose

Generation takes 30 s – 2 min (PRD §6.6). The primary scenario is a phone in the evening: the screen locks, the
network flips between cellular and Wi-Fi, the tab gets killed. If generation were one blocking RPC, every such moment
would throw away two minutes of work and the tokens paid for it (PRD §3.5).

So generation is **a job, not a request** ([I5]). The record lives in SQLite, the worker runs inside the API process
(two users need no separate service), the client polls every 2 s, and progress is real — "사진 3/8 관찰됨", "작성 중" —
because the pipeline reports it while it works. Reconnecting simply resumes polling; opening the post from the list
shows the in-flight state. Revision (plan 07) and voice analysis (plan 03) ride the same queue for the same reason.

## Scope / Non-goals

**In scope**

- `generation_jobs` table (PRD §5) and the job lifecycle `queued → running → done | failed`.
- Job kinds `generate | revise | analyze_voice` with handlers registered by their owning contexts.
- The worker goroutine: DB-backed queue, one job at a time, wake-up on enqueue plus a fallback poll.
- Boot sweep: `running` → `failed` with a "server restarted" reason (PRD §3.5, §7).
- `GetGeneration(job_id)` and the polling contract (2 s, stop on terminal state).
- Surfacing the active job on a post (`Post.active_job`) and on the profile, so reopening shows the in-flight state.
- Progress semantics (`stage`, `progress_done`, `progress_total`) and error surfacing (provider message verbatim).
- One-active-job-per-target guard.
- Recording which models a job ran with (`observe_model`, `write_model`).
- FE: a shared polling hook and the job-status UI primitives the editor and voice screens use.

**Non-goals**

- A separate worker process, external queue, or multi-node coordination (2-user scale; PRD §3.5).
- Automatic retries — a failed job is surfaced with its reason and the user retries by starting a new job.
- Job cancellation. The PRD does not define it; flagged as a gap rather than invented (the guard means a user waits
  for the current job to finish or fail).
- Job history / listing past jobs. Only the latest job per target matters to the product; the table keeps rows for
  debugging but no RPC lists them.
- Streaming partial text to the client (PRD §6.6: the stream stays inside the server).
- The `StartGeneration` / `StartRevision` / `AddVoiceSample` RPCs themselves — they are domain RPCs and live in plans
  06, 07, 03. This plan owns the record, the worker, and `GetGeneration`.

## Design

### Data model (PRD §5, one column relaxed)

```sql
generation_jobs (id TEXT PRIMARY KEY,
                 post_slug TEXT REFERENCES posts(slug) ON DELETE CASCADE,   -- NULL for analyze_voice
                 user_id   TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
                 kind      TEXT NOT NULL,    -- generate | revise | analyze_voice
                 status    TEXT NOT NULL,    -- queued | running | done | failed
                 stage     TEXT,             -- observe | write | analyze  (NULL until running)
                 progress_done  INTEGER NOT NULL DEFAULT 0,
                 progress_total INTEGER NOT NULL DEFAULT 0,
                 error     TEXT,             -- user-facing reason when failed
                 observe_model TEXT, write_model TEXT,   -- "provider_id/model_id" as chosen for this run
                 payload   TEXT,             -- kind-specific input (e.g. revise instruction) as JSON
                 created_at TEXT NOT NULL, updated_at TEXT NOT NULL,
                 started_at TEXT, finished_at TEXT)
unique partial index generation_jobs(post_slug) WHERE status is active,
unique partial index generation_jobs(user_id, kind) WHERE post_slug is NULL and status is active,
index generation_jobs(status, created_at)
```

`payload` is an addition to PRD §5 so a `revise` job can carry its instruction (and `save_as_rule`) without a second
table. Model columns store the `ModelRef` from plan 04 as `provider_id/model_id`.

### Lifecycle

```
enqueue (domain RPC) ──▶ queued ──worker picks──▶ running ──handler ok──▶ done
                                                    │
                                                    ├──handler error / timeout──▶ failed (error = reason)
                                                    └──process restart──▶ failed (error = "server restarted…", boot sweep)
```

- `queued → running` sets `started_at` and `stage` to the handler's first stage.
- The handler calls `progress(stage, done, total)` as it works; each call is a small write in its own transaction,
  never inside a transaction that spans a provider call (ARCHITECTURE §2.4).
- `done` and `failed` are terminal; rows are never reopened. Retrying means a new job.
- Errors: the handler returns an error; the worker stores a user-facing message. For provider errors (plan 04's
  normalized set) the provider's own message is kept verbatim so a free-tier quota failure reads as such and the UI
  can suggest choosing another model (PRD §7).

### Enqueue API (Go, consumed by plans 03/06/07)

```go
type Job struct { ID, Kind, UserID string; PostSlug *string; ObserveModel, WriteModel string; Payload []byte }
type Handler func(ctx context.Context, job Job, progress func(stage string, done, total int)) error

queue.Register(kind string, h Handler)                               // at composition root wiring
queue.Enqueue(ctx, NewJob{...}) (jobID string, err error)            // inserts queued, wakes the worker
queue.ActiveForPost(ctx, slug) (*JobSummary, error)                  // post target → non-terminal job
queue.ActiveForUserKind(ctx, userID, kind) (*JobSummary, error)      // account target → non-terminal job
queue.Get(ctx, jobID, userID string) (*JobSummary, error)            // ownership-checked
```

- **Guard:** `Enqueue` fails with `AlreadyInProgress` when a non-terminal job exists for the same target: same
  `post_slug` for `generate`/`revise` (one active job per post, any kind), same `(user_id, analyze_voice)` for
  analysis. Callers surface this as `FailedPrecondition` with the active job's id so the UI can attach to it.
- Post-targeted rows also carry a composite foreign key to `(posts.slug, posts.user_id)`, and their guard lookup is
  scoped by both values. A malformed future caller cannot attach one user's job to another user's post.
- `Enqueue` and the handler run under the acting user; `Get` refuses foreign jobs with `PermissionDenied` (403).

### The worker

- One goroutine started by `cmd/api` after migrations and the boot sweep. `WORKER_CONCURRENCY = 1`: the single
  SQLite writer and provider rate limits make parallelism pointless at this scale; it also keeps job ordering obvious.
- Wake-up: an in-process channel notified by `Enqueue`, plus a fallback tick every `WORKER_POLL_INTERVAL` (1 s) so a
  missed signal never strands a job.
- Pick: oldest `queued` row; mark `running` in one write; run the handler with a context that carries the stage
  timeout (`LLM_STAGE_TIMEOUT`, plan 04) applied per provider call by the handler; write the terminal state.
- Graceful shutdown: on SIGTERM the worker stops picking. A handler that returns cancellation leaves its row
  `running` for the next boot sweep. A handler that has already returned success or an ordinary failure gets one
  bounded terminal write, so a shutdown racing that write cannot relabel completed work as interrupted.
- Boot sweep, before the worker starts:
  `UPDATE generation_jobs SET status='failed', error='서버가 재시작되어 작업이 중단됐어요. 다시 시도해 주세요.', finished_at=now WHERE status='running'`.

### Contract — `proto/postpilot/v1/post.proto` (this plan's part)

```
service GenerationService {
  rpc GetGeneration (GetGenerationRequest) returns (GetGenerationResponse);   // Start* RPCs are added by plans 06/07
}
message GenerationJob { string id = 1; string kind = 2; string status = 3; string stage = 4;
                        int32 progress_done = 5; int32 progress_total = 6; string error = 7;
                        string post_slug = 8; ModelRef observe_model = 9; ModelRef write_model = 10;
                        string created_at = 11; string updated_at = 12; }
```

`Post` (plan 02) gains `GenerationJob active_job = …` — set when a non-terminal job exists for the post, so
`GetPost` on reopen and `ListPosts` (a `generating` badge) show the in-flight state without a second request. The
post context obtains it through the job context's `ActiveFor`, never by reading the table (ARCHITECTURE §2.2).
`VoiceProfile.active_job_id` (plan 03) is filled the same way.

### Polling contract (FE)

- `useJob(jobId)` — TanStack Query with `refetchInterval: POLL_INTERVAL_MS` (2000) while `status ∈ {queued, running}`;
  `refetchInterval: false` once terminal. On `done` it invalidates the post (or profile) query so the finished content
  loads; on `failed` it exposes `error` for the UI.
- Polling survives navigation and reload because the job id is recoverable from `Post.active_job` /
  `VoiceProfile.active_job_id`, not from component state.
- The editor renders a progress line from `stage` + `progress_done/total`: `observe` → "사진 {done}/{total} 관찰됨",
  `write` → "작성 중", `analyze` → "문체 분석 중"; `failed` → the error with a "다시 시도" affordance.

## Acceptance Criteria

1. A domain `Start*` RPC returns a `job_id` before any provider call is made (RPC latency is DB-bound, well under a
   second).
2. `GetGeneration` reflects live progress: during observation `stage=observe` with `progress_done/total` advancing;
   during writing `stage=write`.
3. Closing the browser mid-job and reopening the post shows the in-flight state via `Post.active_job`, polling resumes,
   and when the job finishes the post's content appears without a manual refresh.
4. Killing the API process while a job is `running` and restarting it leaves the job `failed` with the restart
   reason; the UI shows the reason and a retry affordance.
5. The client polls at 2 s intervals while the job is non-terminal and issues no further `GetGeneration` calls after
   `done`/`failed` (network-tab evidence).
6. `GetGeneration` for another user's job → 403; unknown id → 404.
7. Starting a second job for a post that already has a non-terminal job is refused with `FailedPrecondition` carrying
   the active job id.
8. A handler error becomes `failed` with a non-empty user-facing `error`; a provider quota error preserves the
   provider's message (a stubbed provider returning 429 yields a job error that contains that message).
9. Progress writes never occur inside a transaction that spans a provider call (asserted by the handler test harness).
10. `ListPosts` marks posts with an active job as generating (badge), derived from the job context's published
    behavior, not from a cross-context table read.

## Policy / Config Impact

Canonical shipped rules are recorded in [policy/jobs.md](../policy/jobs.md):

- Every model call longer than a round-trip runs as a `generation_jobs` record; no RPC blocks on a provider.
- One active job per post (any kind) and one active analysis per user.
- `running` jobs are swept to `failed` at boot; jobs are never retried automatically.
- Provider error messages are surfaced to the user verbatim in `error`.
- Polling is 2 s and stops on terminal state.

## As-built extension — job 15

`model_experiment` now rides the same worker with the experiment id in its payload and compare-stage progress. The
queue lifecycle/concurrency remain unchanged. After the ordinary running-job boot sweep, experiment-owned recovery
reconciles running and orphaned queued aggregates through the job context's published runnable-job query. Current
rules live in [policy/jobs](../policy/jobs.md).

## As-built extension — job 16

The queue now supports `learn_voice`, `compare_voice_rule`, and `validate_voice_profile` with durable payloads and
progress labels. These kinds are deliberately different at restart: boot marks even queued personalization work
failed before starting the worker, so application boot can never become the action that initiates AI. Explicit retry
creates another job. An owner-scoped queued-job compensation closes the aggregate-create/job-link window without
stopping work a worker already owns.
