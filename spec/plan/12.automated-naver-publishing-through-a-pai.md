# 12. Automated Naver Publishing Through a Paired Mac Agent

> Explicitly publish a finalized post all the way to Naver Blog from the phone by handing an immutable text-and-JPEG
> manifest to an account-paired Mac, where a constrained Hermes profile drives an isolated logged-in Chromium
> profile | Scope: FS + Mac companion | Status: implementation verification in progress; pairing flow verified live

## Purpose

The copy-ready export in plan 08 removes most of the writing work, but real use exposed that its last step is not a
thirty-second formality: every photo still has to be found, uploaded and placed by hand in SmartEditor ONE. The user
wants to finish a post from a phone — including while away from the Mac or lying in bed — and have the already-on Mac
perform the repetitive browser work through the user's existing Korean network and Naver login session.

Naver exposes no public blog-writing API in its current developer API list. Running the same automation from the VPS
would move the login session onto an overseas server and make the browser identity both less familiar to Naver and
harder for the owner to recover interactively. This plan therefore adds a **paired local publishing agent**: the VPS
owns the durable request and status, but a Mac-owned browser session performs the publish. The user explicitly starts
publishing from postpilot; this is never an implicit consequence of finalizing a post.

The shipped copy/export workflow remains valuable and remains available. The new `발행하기` section appears below
`내보내기` in 글 완성, so manual export is always the fallback when the Mac is offline, Naver changes its editor, or
the user does not want automation for a particular post.

## Scope / Non-goals

### In scope

- Naver Blog only: title, canonical body text, every attached 1024 px JPEG in canonical block order, image captions,
  canonical tags, category, visibility, the final Naver publish action, and capture of the resulting post URL.
- A separate `발행하기` section immediately below the existing export panel in 글 완성. Only an exactly finalized
  current content revision can start a publish; the action is a separate explicit `네이버에 발행` confirmation.
- Durable server-side publishing jobs with a frozen post revision and immutable staged JPEG set, progress/status,
  safe retry before commit, a hard ambiguity fence around the final click, and one successful Naver publication per
  post.
- An account-scoped pairing flow and device revocation. The first version supports multiple paired account
  connections on one Mac, each mapped to its own browser identity; this is how the two postpilot users publish through
  different Naver sessions.
- A minimal macOS companion: a background CLI daemon installed as a user LaunchAgent plus a loopback-only setup page
  for API URL, pairing, Hermes health, browser-binary selection, isolated profile login/test, category sync, defaults,
  connection status and logs.
- A dedicated Hermes profile plus a postpilot publisher plugin/skill. The local companion invokes Hermes as a
  programmatic one-shot against a local manifest and receives progress/completion through a structured local tool,
  not by scraping prose from the model's final answer.
- Chrome, Brave, Chromium and Edge binaries supported by Hermes's local Chromium/CDP path. Each connection gets an
  agent-owned `user-data-dir`; the user signs into Naver once in that visible profile.
- Category and public/private selection. A connection has defaults discovered/configured during local setup and the
  publish panel may override them for one job. Tags come from the canonical `PostContent.tags`.
- In-app mobile status while the page is open: agent unavailable, queued, claimed, preparing, opening editor,
  filling content, uploading photos, committing, verifying, published, failed, needs attention, or outcome unknown.

### Non-goals

- Instagram Reels, Naver Clip, or any other blog/social platform. A later plan may reuse the publishing-job and
  paired-agent boundaries after this Naver path works in practice.
- Video generation, transcoding, speech recognition, subtitles, music, covers or short-form metadata generation.
- Web Push, email, Telegram or any other completion notification. The first version reports only inside postpilot.
- Scheduled publication. The user may submit while the Mac is offline and the durable job will wait for it, but the
  user cannot choose a future publish time.
- Publishing as a side effect of `FinalizePost`, finalizing-and-learning, autosave, generation, opening the panel, or
  reconnecting an agent. Every publication has its own explicit user confirmation.
- Safari, iOS browser control, a native menu-bar application, App Store packaging, automatic Mac wake, multiple
  simultaneous Hermes runs, or a general-purpose remote desktop/control channel.
- Bypassing CAPTCHA, two-factor authentication, suspicious-login challenges, Naver policy checks, or bot detection.
  Those states stop the job and ask the user to repair the dedicated browser session locally.
- Automatic semantic reconciliation after an ambiguous final click. An unknown outcome is never auto-retried.
- Reformatting canonical content into a new rich-text model. The Naver automation preserves plan 08's plain-text
  mapping while replacing each image marker with the real JPEG at the corresponding block position.

## Design

### Product contract

The existing `내보내기` widget stays byte-for-byte copy-oriented. The editor page composes a new `발행하기` panel
immediately after it when canonical content exists. The panel has four states:

1. **No paired agent:** explain that Naver login stays on the Mac and link to the agent-management page.
2. **Agent unavailable:** show the selected connection and last seen time. `네이버에 발행` remains available; a
   confirmed request queues until the agent returns.
3. **Ready:** category and visibility use the connection defaults but may be changed for this job. The confirmation
   names the Naver blog, states that final publication will occur without another click, and freezes the exact current
   revision.
4. **Job/history:** show the server-owned stage and error. A published job links to its Naver URL. `needs_attention`
   explains that the owner must repair login/CAPTCHA on the Mac; `outcome_unknown` explains that the final click may
   have succeeded and must not be retried blindly.

Start is accepted only when all of these are true:

- the post belongs to the authenticated account;
- `status == finalized`, `finalized_revision == content_revision`, and valid canonical content exists;
- an active, non-revoked agent connection belongs to the same account and has a tested Naver browser profile;
- the requested category belongs to the last category set synced by that connection; and
- no nonterminal job or successful Naver publication exists for that post.

The request takes an `expected_content_revision`. A stale phone/tab is rejected rather than publishing content the
confirmation did not show. After immutable JPEG staging, the publishing store reserves the serialized SQLite writer,
re-reads the post through post behavior and the agent through publishing behavior, and inserts only if revision,
finalization, image set, active profile, blog identity, and category are still the confirmed values. The publishing
store never reads the post table. Finalization remains independent: it does not start or imply publishing.

### Pairing and local identity

The Mac companion never receives the user's password and never copies the SPA's HttpOnly session cookie. Pairing is
a short device-code flow:

1. The local setup page opens postpilot's authenticated agent-management page in the user's browser.
2. The logged-in user creates a single-use, short-lived code and names the connection.
3. The user pastes that code into the loopback page. `EnrollPublishingAgent` consumes it once and returns a random
   raw agent token exactly once.
4. The server stores only the token hash. The Mac stores the raw token in macOS Keychain and only a keychain reference
   in its config file.
5. The user selects an installed Chromium-family binary. The companion creates a dedicated profile directory, opens
   it visibly, and asks the user to sign into Naver. The companion opens Naver's generic writer URL with no
   user-supplied blog id; Naver resolves the signed-in blog, and a deterministic local CDP probe accepts only the
   versioned editor root, observed `blogId`, conflict-free categories, and the same single page target before and
   after navigation. The first observed category becomes the initial default and may be changed in Postpilot.

Pairing is account-scoped. Repeating it while logged into the second postpilot account creates a second connection
with a second token and isolated browser/Hermes profile. A connection cannot read, claim or report another account's
job. Revocation immediately invalidates its token without deleting publication history.

The server stores safe connection metadata only: postpilot account id, user label, Naver blog label/identifier,
browser label (not the local profile path), synced category ids/names, defaults, last-seen time and revocation time.
Naver cookies, passwords, CDP endpoints, filesystem paths, Hermes credentials and model-provider keys never leave
the Mac.

### Immutable manifest and JPEG staging

`StartPublish` asks the post context for an ownership-checked exact finalized snapshot through published behavior;
the publishing context never reads post tables. The snapshot contains `PostContent`, revision and ordered image
references. Publishing stores canonical protojson plus the chosen agent/category/visibility/tags as the job manifest.

The R2 photo objects are already stripped-metadata, ≤1024 px JPEGs from plan 02. To make a queued job independent of
later post edits/deletes, the publishing context copies the referenced objects server-side to immutable
`publishing/{job_id}/{ordinal}.jpg` keys before marking the job queued. Bytes never pass through the API process and
no image is decoded or re-encoded, so [I6] is unchanged. A failed partial staging attempt removes its copies and does
not expose a runnable job.

Each claim receives short-lived presigned GET URLs, expected byte counts, a unique ordinal filename plus canonical
source filename for every IMAGE occurrence, and canonical block order. Reusing one attached JPEG in multiple IMAGE
blocks therefore yields multiple isolated local files without changing the canonical content snapshot.
The Mac downloads them to a random per-job directory, refuses redirects outside the signed storage target, verifies
that every expected download completed, and exposes only those paths to the Hermes publisher plugin. Terminal jobs
purge manifest content and staged objects; metadata, error classification, selected settings and the published URL
remain for history. An orphan sweep removes unreferenced staged objects left by crashes.

### Durable job and delivery semantics

The server is the source of truth. SSE/WebSocket is not required in the first version: the daemon performs an
authenticated unary poll, claims work with a lease, and heartbeats while it runs. It reloads the owner-only connection
file every two seconds so a newly armed account begins polling without restart. Reconnection therefore loses no request
and the Mac exposes no inbound internet port.

Authentication stamps `last_seen_at`, but at most once per `PUBLISH_AGENT_HEARTBEAT_INTERVAL` per agent: the poll runs
several times per freshness window, so an unthrottled stamp would spend the single serialized writer on a display hint.
The refresh is non-fatal — a storage fault degrades the liveness display instead of refusing a valid token — except for
a revocation the write itself discovers, which is still a refusal.

```text
queued
  └─claim─> claimed -> preparing -> opening_editor -> filling_content -> uploading_photos
                                                          |
                                                          └─safe failure─> failed / needs_attention

uploading_photos -> committing -> verifying -> published
                          |             |
                          └─lost/exit────┴─> outcome_unknown
```

- A lease that expires before `committing` returns the job to `queued`; a safe retry cannot have published anything.
- The publisher plugin must report `committing` **immediately before** activating Naver's final publish control.
  From that persisted boundary onward, a timeout, agent crash, browser disappearance or malformed result becomes
  `outcome_unknown`, never an automatic retry.
- `published` requires navigation to/readback of the created post and a captured Naver URL belonging to the expected
  blog. Seeing only a button acknowledgement is not sufficient.
- Login expiry, CAPTCHA, 2FA and suspicious-login challenges are `needs_attention`, not failures to brute-force.
- User cancellation is allowed only while queued or before the local run reaches `committing`.
- A successful `(post_slug, NAVER_BLOG)` publication is unique. Republishing an already published post is outside
  this plan and requires a later explicit product rule.

The job has no LLM/provider work on the VPS and does not reuse `generation_jobs`. It is its own aggregate because its
lease, external side effect, ambiguity and retention rules are different, while still satisfying [I5]'s durable-job
principle.

### Hermes execution contract

The companion owns process supervision and invokes a dedicated named Hermes profile in programmatic one-shot mode.
It passes a constant instruction containing only the local job handle; title/body/captions are read as inert data
through the publisher plugin and are never concatenated into the agent prompt or shell command. The run preloads one
versioned postpilot Naver-publisher skill and only the browser plus publisher-plugin toolsets. It has no postpilot
server token, general file tree, messaging, delegation or web-search tool.

The shipped Hermes plugin provides a narrow structured surface:

- read the validated manifest, match each IMAGE block to the same-ordinal asset by `source_filename`, and resolve its
  unique staged `filename` path;
- report an allowed progress transition;
- report `needs_attention` with a normalized reason;
- enter the irreversible `committing` boundary; and
- complete with a verified Naver URL or fail before commit.

A plugin `pre_tool_call` guard rejects browser navigation outside the enumerated Naver editor/login hosts and rejects
asset paths outside the current staging directory. The versioned skill tells Hermes how to map each canonical block:
TEXT/HEADING as paragraphs, QUOTE with the same curly-quote representation as plan 08, LIST as `- item` lines, and
IMAGE by uploading the exact manifest JPEG at that position followed by its caption. Unknown controls, a changed
editor structure, missing blocks/assets or an unexpected blog identity fail closed before `committing`.

The implementation must consult the then-current official Hermes installation, CLI, profile, plugin and CDP docs,
install the latest compatible release, and run `hermes doctor` plus a publisher compatibility probe. No remembered
Hermes command or version is a permanent product contract; the companion checks capability and refuses publishing
with an actionable setup error when the installed surface is incompatible.

### Contracts

A new `proto/postpilot/v1/publishing.proto` defines two unary services. Names below express behavior; the job may
refine message factoring but not weaken the boundaries.

```proto
service PublishingService {                 // ordinary HttpOnly user session
  rpc CreateAgentPairing(CreateAgentPairingRequest) returns (CreateAgentPairingResponse);
  rpc ListPublishingAgents(ListPublishingAgentsRequest) returns (ListPublishingAgentsResponse);
  rpc UpdatePublishingAgent(UpdatePublishingAgentRequest) returns (UpdatePublishingAgentResponse);
  rpc RevokePublishingAgent(RevokePublishingAgentRequest) returns (RevokePublishingAgentResponse);
  rpc StartPublish(StartPublishRequest) returns (StartPublishResponse);
  rpc GetPublishJob(GetPublishJobRequest) returns (GetPublishJobResponse);
  rpc CancelPublish(CancelPublishRequest) returns (CancelPublishResponse);
}

service PublishingAgentService {            // publishing-agent bearer token, never browser cookie
  rpc EnrollPublishingAgent(EnrollPublishingAgentRequest) returns (EnrollPublishingAgentResponse);
  rpc SyncAgentProfile(SyncAgentProfileRequest) returns (SyncAgentProfileResponse);
  rpc ClaimPublishJob(ClaimPublishJobRequest) returns (ClaimPublishJobResponse);
  rpc RenewPublishLease(RenewPublishLeaseRequest) returns (RenewPublishLeaseResponse);
  rpc ReportPublishProgress(ReportPublishProgressRequest) returns (ReportPublishProgressResponse);
  rpc CompletePublish(CompletePublishRequest) returns (CompletePublishResponse);
  rpc FailPublish(FailPublishRequest) returns (FailPublishResponse);
}
```

`StartPublishRequest` carries `post_slug`, `expected_content_revision`, `agent_id`, category id and visibility. It
does not carry content, image URLs, user id or platform credentials. Agent authentication travels in an Authorization
header and its raw token appears in no stored proto payload or log. Every agent mutation carries job id, lease token
and monotonic progress sequence so stale/delayed reports cannot move a newer attempt backward.

### Data model

Migration `000x` (the next number at implementation) is embedded per [I7] and adds publishing-owned tables:

```text
publishing_pairings
  code_hash PK, user_id FK, label, expires_at, consumed_at, created_at

publishing_agents
  id PK, user_id FK, token_hash UNIQUE, label, platform,
  platform_account_id, platform_account_label, browser_label,
  categories_json, default_category_id, default_visibility,
  last_seen_at, revoked_at, created_at, updated_at

publish_jobs
  id PK, user_id FK, post_slug snapshot, post_created_at incarnation, (agent_id,user_id) composite FK, platform,
  status, stage, progress_seq, content_revision,
  manifest_json, settings_json, lease_token_hash, lease_expires_at,
  error_code, error_message, platform_post_url,
  created_at, claimed_at, committed_at, published_at, updated_at

publish_assets
  job_id FK, ordinal, filename, source_filename, staged_key, bytes,
  PRIMARY KEY(job_id, ordinal), UNIQUE(job_id, filename)
```

The publishing context owns all four tables. `manifest_json` is canonical protojson, not a second HTML truth. A
terminal transition clears `manifest_json`, lease data and asset rows after object cleanup. The source-post slug is a
detached snapshot rather than a foreign key so deleting a post cannot erase publication history. It carries the post
creation timestamp as its incarnation, so a newly created post that reuses the slug cannot inherit old history.
Per-occurrence ordinal filenames allow the same canonical image to appear in multiple blocks. User/account metadata
cascades; explicit remaining-object purge during a future account-deletion choreography remains an open acceptance
item because this codebase does not yet expose account deletion.

### As-built verification status (through 2026-08-31)

Job 25 has built the migration/contracts, publishing context and separate auth boundaries, immutable R2 staging,
recovery/cleanup sweepers, editor and Mac-management UI, standalone macOS Go companion, Keychain/launchd adapters,
verified loopback Chromium CDP handoff through `BROWSER_CDP_URL`, and the constrained Hermes plugin/skill. Automated
tests cover state/lease fences, stale credentials, storage copy/pagination/TTL, immutable snapshots, browser/profile
isolation seams, path/redirect guards, inert manifest strings, explicit UI confirmation, and unchanged export tests.
The as-built safety pass also flushes edits before confirmation, reuses frozen attention-job values, strips signed
URLs before Hermes, verifies active hosts after every browser action, enforces the acknowledged commit boundary,
serializes daemon/Hermes execution, hot-loads newly armed connections, binds bearer credentials to the configured API
origin, persists setup as unarmed before sync, and keeps raw failure detail off the VPS. Publication identity includes
the source post incarnation, repeated image references get unique local names, pairing capacity is atomically enforced,
and retryable R2 cleanup cannot block database lease recovery or API startup. Start's final state check and insertion
share one serialized-writer transaction, setup rejects a heartbeat-incompatible lease before ready sync/activation,
and only the authenticated loopback finish callback—not model stdout—can supply the terminal publication result.
Frozen attention-job retries remain available after source-post deletion through an account-scoped recovery list,
so the deleted post route is not required. A reused DevTools port must match the
connection's recorded browser id. Unknown final buttons/dialog acceptance fail closed. Every JPEG needs a successful
one-file upload in exact manifest order plus an exact-one-image full-snapshot editor delta; the commit fence also
requires the full frozen content and settings in a current full editor snapshot. Category ID is grounded by an exact
DOM selector and the category/visibility controls must expose selected or checked state. A published URL must still be open in the active paired
browser with a post-fence readback matching the frozen title, block/image/caption order, tags, and category.
Every URL, full snapshot, selector query, ref, final activation, and readback is now bound to the same single CDP
page target. Paired-blog identity is machine-checked before the
fence, exact semantic matching rejects inserted content/images, and the acknowledged fence grants one consumable
activation to the exact final-control ref. Transient heartbeat failure leaves classification to server lease recovery
instead of racing it with a terminal report. Existing armed connections can reopen their same isolated browser
profile from loopback setup for `needs_attention` repair without a new pairing code.

The final offline safety reviews replaced keyword-based commit authorization with an exact versioned accessible-name
allowlist and require exactly one matching final button on the verified target; scheduled, generic, or duplicate
publish-like controls fail closed. Frozen tags are compared as one exact ordered collection, so extras, duplicates,
or reordering fail both editor and readback verification. Naver identity is derived from the generic writer URL chosen
by the signed-in session rather than copied from user input, requires editor-specific DOM evidence, and rechecks the
single CDP target after navigation. A revoked connection is a failed-precondition business state for a still-valid
human session, while the revoked agent bearer remains unauthenticated. Retained deleted-post jobs expose both retry
and confirmed cancel outside the post route, including after revocation or identity/category drift.

Canonical tag comparison rejects empty or duplicate values after whitespace/hash normalization at the post hand-off
and again inside the local publisher. The hand-off revalidates already-finalized legacy rows before staging, not only
new saves. Editor/readback verification recognizes category, visibility, and tag boundaries by their accessibility
roles rather than label text alone, so a legitimate paragraph equal to `일상`, `비공개`, or a tag remains body content.
Terminal cleanup attempts every asset and every eligible job before returning an aggregated error; rows are removed
only for jobs whose complete object set was deleted, leaving failed work retryable without starving unrelated jobs.

The setup server uses a per-run cryptographic nonce plus exact loopback Host/Origin checks and request-size limits.
Identity/category discovery is a deterministic local CDP read and never trusts Hermes/model stdout. Revocation is
rechecked atomically in every leased SQL mutation, and each random job prefix is durably reserved before any R2 copy;
random-source failure or a collision therefore cannot overwrite or delete an existing job's assets.
Terminal database transitions remain the authoritative RPC result even when immediate object deletion fails; the
terminal cleanup sweeper retries idempotently. S3 `CopySource` escapes each bucket/key segment while preserving the
documented slash separators.

The source spec remains not done until a designated Naver test account is paired and the authorized live fixture with
every block type and eight JPEGs verifies SmartEditor content/order/settings, challenge handling, and commit-boundary
fault behavior. In particular, acceptance criteria 6, 8, 9, 10, and 14 are not claimed from fake/offline evidence.

## Acceptance Criteria

1. A user can pair two different postpilot accounts on one Mac; each stores a distinct token in Keychain, owns a
   distinct Hermes/browser profile, sees only its account's jobs, and publishes through the Naver identity verified
   for that connection. Revoking one leaves the other usable and the revoked token immediately fails.
2. The Mac exposes no public listener: its setup UI binds loopback only and work arrives through outbound authenticated
   polling. Turning the Mac off leaves a confirmed job durably queued; starting its LaunchAgent later claims it and
   proceeds without another phone action.
3. In 글 완성, `내보내기` is unchanged and a separate `발행하기` section follows it. No other lifecycle step renders
   the panel. Opening/rendering it performs no publication; only the explicitly confirmed `네이버에 발행` action does.
4. `StartPublish` rejects an unfinalized post, stale `expected_content_revision`, foreign/revoked agent, stale/foreign
   category, second nonterminal job, and a post already successfully published to Naver. Finalization and voice
   learning behavior are unchanged.
5. A successful request freezes the exact finalized protojson, category, visibility, tags and ordered image set. A
   later post edit/delete cannot alter the job, and every staged object is the existing converted JPEG copied inside
   R2 without entering or being decoded by the API process.
6. Given a finalized fixture containing every block type and eight photos, the paired Mac publishes one Naver post
   whose title, plain-text block order, eight JPEG positions, captions, tags, category and visibility match the frozen
   manifest, then stores and renders the verified Naver URL.
7. Agent/job progress survives phone reloads and Mac/VPS reconnects. A lease lost before `committing` safely requeues;
   stale lease/progress tokens cannot update a newer attempt or regress its stage.
8. Immediately before Hermes activates the final Naver publish control, the server has durably recorded
   `committing`. Any crash/timeout/disconnect from that point until verified URL capture becomes `outcome_unknown`
   and is never automatically retried. Reproducing this fault never creates a second post through the system.
9. Expired Naver login, CAPTCHA, 2FA or account mismatch becomes `needs_attention`; the agent neither bypasses the
   challenge nor sends Naver credentials/cookies/CDP/profile data to the VPS. After local repair, an explicit safe
   retry before commit can finish the same job.
10. The Hermes run receives only a local job handle in its prompt, treats manifest strings as data, can resolve only
    current staged assets, and is blocked from navigating outside the allowed Naver editor/login hosts. Missing
    controls/assets or a changed editor fail closed before commit.
11. On terminal completion/cancel, staged R2 objects and sensitive manifest content are purged while job metadata,
    normalized error, selected settings and published URL remain. The orphan sweep removes partial copies left by a
    killed staging operation and never deletes a live job asset.
12. The first version has no schedule control and sends no Web Push/email/chat notification. The in-app panel alone
    shows live status and actionable failure text.
13. Existing Naver/Tistory/site/Markdown conversion snapshots and clipboard behavior remain unchanged; disabling or
    never pairing the Mac agent leaves postpilot fully usable as the copy-only product it is today.
14. Setup installs or verifies the implementation-time latest compatible official Hermes release, runs `hermes
    doctor` and the plugin/CDP compatibility probe, and refuses to arm the connection when the required capabilities
    are absent. No stale hardcoded installer/version is treated as authoritative.

### Mac-local config

| Value | Storage | Default / rule |
|---|---|---|
| postpilot API URL | agent config file | required, HTTPS except loopback development |
| agent token | macOS Keychain | generated by pairing; never config/env/plaintext file |
| poll interval | agent typed config | `5s` with jitter/backoff |
| lease heartbeat interval | agent typed config | `10s`, strictly below server lease TTL |
| job timeout | agent typed config | `15m`; after commit this yields unknown, not retry |
| maximum Hermes turns | agent typed config | `60` |
| local setup bind | agent typed config | loopback only, OS-selected port |
| browser binary / profile directory / Hermes profile | agent config file | one isolated set per paired connection; paths never sync |
| work directory | agent config file | app-owned directory with owner-only permissions; per-job subdirectories are removed |

The implementation adds all server env values to both env examples and validates positive server TTLs at API boot.
The agent validates its heartbeat interval against the lease TTL advertised by every claim before running work. No
Naver credential, cookie, CDP URL or Hermes provider key enters server or frontend config.
