# 03. Voice Profile Learning

> One style profile per account: paste your own writing, get an editable Korean style guide back, accumulate rules,
> and hand generation a stable "how I write" prefix | Scope: FS | Status: done

## Purpose

A draft nobody has to rewrite is only possible if it comes out in **the author's** voice, not a generic AI voice
(PRD §1 목표 2). Two people share this tool and must each get their own — a shared profile converges to a third
voice that belongs to neither and can never be pulled apart again ([I4], PRD §3.4).

Korean style is decided mostly by sentence endings (~다 / ~해요 / ~습니다), so the analysis treats 종결어미 as the
primary signal. The single most enforceable rule is "this author never says X", so the analysis must produce that
list explicitly (PRD F-3).

S2 is optional: an author who already has a post may import it, but an account with no writing history generates its
first post immediately and learns progressively only when the author explicitly finalizes that post. Both paths work
from **one** source; neither requires or recommends a historical-post minimum.

## Scope / Non-goals

**In scope**

- `voice_profiles` (1:1 with user) and `voice_samples` tables.
- `GetVoiceProfile`, `UpdateVoiceProfile` (styleguide + rules editable), `AddVoiceSample` (triggers analysis),
  `DeleteVoiceSample`.
- Minimum sample length (200 chars); analysis of the **full accumulated corpus** every time it changes.
- The `analyze_voice` job kind riding the shared queue (plan [05](05.generation-job-queue.md)).
- The mandated analysis dimensions and the styleguide's shape.
- The **profile injection contract** consumed by generation (06) and revision (07): styleguide → sample excerpts →
  rules, rules last.
- Empty-profile warning surfaced on the writing screen.
- FE: the `말투` screen (`/voice`) — paste + learn, sample list with delete, styleguide and rules editors, analysis
  progress, model picker for the analysis.

**Non-goals**

- Sharing, copying, or merging profiles between accounts; more than one profile per account ([I4]).
- Scheduled or automatic de-duplication / merging of rules. Evidence lifecycle work is evaluated only during an
  explicit eligible request; there is no periodic process.
- Appending rules from the AI-revision checkbox — that write belongs to plan [07](07.ai-revision.md); this plan only
  defines the field and makes it editable.
- Importing samples from a blog URL, or analysing someone else's text as a "target" voice.
- Style analysis of images or of anything but the pasted Korean prose.

## Design

### Contract — `proto/postpilot/v1/voice.proto`

```
service VoiceService {
  rpc GetVoiceProfile    (GetVoiceProfileRequest)    returns (GetVoiceProfileResponse);
  rpc UpdateVoiceProfile (UpdateVoiceProfileRequest) returns (UpdateVoiceProfileResponse); // optional styleguide/rules patch
  rpc AddVoiceSample     (AddVoiceSampleRequest)     returns (AddVoiceSampleResponse);     // enqueues analyze_voice
  rpc DeleteVoiceSample  (DeleteVoiceSampleRequest)  returns (DeleteVoiceSampleResponse);  // re-enqueues if samples remain
}
message VoiceProfile { string styleguide = 1; string rules = 2; string updated_at = 3;
                       repeated VoiceSample samples = 4; string active_job_id = 5; }
message VoiceSample  { string id = 1; string label = 2; int32 chars = 3; string created_at = 4; }  // body not returned
message AddVoiceSampleRequest  { string label = 1; string body = 2; ModelRef model = 3; }          // ModelRef from plan 04
message AddVoiceSampleResponse { VoiceSample sample = 1; string job_id = 2; }
message UpdateVoiceProfileRequest { optional string styleguide = 1; optional string rules = 2; }
```

There is no RPC that takes a user id: the profile is always the acting user's, so a foreign profile is unreachable by
construction (F-3 완료조건 2). Profile query caches are additionally keyed by the authenticated account id so a
fresh cache entry from one login is never rendered after another account signs in on the same browser.

### Data model (PRD §5)

```sql
voice_profiles (user_id TEXT PRIMARY KEY REFERENCES users(id) ON DELETE CASCADE,
                styleguide TEXT NOT NULL DEFAULT '',   -- machine-generated, user-editable
                rules      TEXT NOT NULL DEFAULT '',   -- user-authored lines; appended by plan 07
                corpus_version INTEGER NOT NULL DEFAULT 0,
                updated_at TEXT NOT NULL)
voice_samples  (id TEXT PRIMARY KEY, user_id TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
                label TEXT NOT NULL, body TEXT NOT NULL, created_at TEXT NOT NULL)
```

A profile row is created lazily on first write. "Empty profile" = `styleguide = ''` **and** no samples.

### Samples

- `body` must be ≥ 200 characters after trimming (PRD F-3); shorter → `InvalidArgument` with the count. The FE
  mirrors the check for immediate feedback; the BE check is authoritative.
- `label` optional; empty → first 20 characters of the body.
- Adding a sample enqueues one `analyze_voice` job over **all** of the user's samples (PRD F-3: 누적된 전체 샘플을
  다시 분석 — cross-sample habits like paragraph breaking are invisible in a single new text). Deleting a sample
  re-enqueues the same full analysis when at least one sample remains; when none remain, the styleguide is left as
  is (the user may have hand-edited it) and the UI says so.
- If an `analyze_voice` job is already active for the user, `AddVoiceSample` still stores the sample but returns the
  existing job's id instead of enqueueing a second analysis (the guard is plan 05's). Sample insertion/deletion and
  `corpus_version` advance in one transaction. The handler conditionally stores against the version it analyzed; if
  the corpus changed during the provider call, the same durable job repeats over the latest full snapshot. A stale
  analysis result therefore never overwrites the profile.

### The analysis job (`kind = analyze_voice`)

- Model: the user's `analyze`-stage selection (plan 04). Text-only; vision not required; structured output not
  required (the result is prose). No model selected → `FailedPrecondition` before enqueueing.
- Input: all samples concatenated with separators and labels. Output: a Korean style guide in plain Markdown-ish
  text that **must** cover, in this order:

  1. 종결어미 distribution (~다 / ~해요 / ~습니다 and mixes) — primary signal, first section
  2. average sentence length
  3. sentences per paragraph
  4. frequently used connectives and adverbs
  5. verbal tics / signature phrases
  6. emoji, interjections, ellipses — whether used and how often
  7. metaphors and numerals — whether used and how
  8. **common expressions this author never uses** (PRD: 가장 지키기 쉬운 규칙)
  9. first-person expression (나 / 저 / 우리 / none)

  The prompt enumerates these dimensions; the handler rejects a result missing the 종결어미 section and fails the job
  with a reason.
- On success the handler conditionally **replaces** `voice_profiles.styleguide` wholesale for the analyzed
  `corpus_version`. Any existing styleguide is therefore at risk of being overwritten; the FE asks for confirmation
  before adding a sample whenever `styleguide` is non-empty. `rules` is never touched by the analysis.
- Progress: a single stage (`analyze`, `1/1`) — the job exists for resumability and duration, not granularity.

### Profile injection contract (consumed by plans 06 and 07)

The voice context publishes `ProfileForPrompt(userID) → (styleguide, excerpts[], rules, empty bool)`; callers place
the three parts into the prompt **in this order and nowhere else** (PRD §5):

```
1. styleguide                     the rules
2. sample excerpts, 2–3           the evidence — most recent samples, each cut to PROFILE_EXCERPT_CHARS
3. rules                          what the author typed after seeing real failures — LAST
```

Rules go last because they carry the highest weight and the tail of a prompt is followed most closely. Parts 1–2 are
stable across posts and form a cacheable prefix; the per-post material (observations, memo, instruction) always
follows them (PRD §5 덤 — prompt caching). Callers never reorder or interleave.

### Empty-profile warning

The editor reads `VoiceProfile` independently on load; when `empty` it explains that no voice has been learned yet
and that the first post can still be generated immediately. Generation is never blocked by history count.

The authenticated `/voice` route composes the analyze-stage model selector, sample form/list, durable-job progress,
and the two profile editors. `active_job_id` seeds `useJob` after a reload; a successful terminal job invalidates the
profile query so the new styleguide appears without a manual refresh. The client mirrors the 200-character boundary
for immediate feedback while displaying the backend's raw validation message if the RPC still rejects the sample.
Each editor sends only its owned optional field; the store updates that column atomically, and the client patches only
that field into its cache. A delayed save therefore cannot overwrite an analysis-produced styleguide or discard newer
input typed while the request was pending.

## Acceptance Criteria

1. With an empty profile (no styleguide, no samples) the writing screen shows the warning; after one successful
   analysis it disappears.
2. Two accounts hold different styleguides and rules; no RPC can return one account's profile to the other (no
   request carries a user id; queries are interceptor-scoped).
3. Pasting a single sample of ≥ 200 characters yields a styleguide whose first section is the 종결어미 distribution
   and which contains a "never uses" section — the handler fails the job if the 종결어미 section is absent.
4. A sample under 200 characters is refused with `InvalidArgument` and the character count.
5. Adding a second sample runs the analysis over both samples (the job's input contains both bodies — asserted by a
   unit test on corpus assembly).
6. Editing the styleguide or rules and saving persists; reloading shows the edited text.
7. Deleting a sample removes it from the list and, when samples remain, re-runs the analysis.
8. The analysis is a job: `AddVoiceSample` returns immediately with a `job_id`, progress is visible, and reloading the
   page mid-analysis resumes polling to completion.
9. `ProfileForPrompt` returns styleguide, ≤ 3 excerpts, rules, in that order; a unit test on the consumer's prompt
   assembly (plan 06) shows rules after excerpts after styleguide.

## Policy / Config Impact

The rules now in force are recorded in [policy/voice.md](../policy/voice.md).

- Exactly one voice profile per account; never readable across accounts.
- A sample is at least 200 characters; every corpus change re-analyzes the whole corpus.
- The analysis must cover the nine dimensions above with 종결어미 first and a "never uses" list.
- The analysis overwrites `styleguide` and never writes `rules`; `rules` is user-owned (and appended by plan 07).
- Adding a sample while any styleguide exists requires explicit overwrite confirmation in the UI.
- Prompt injection order is styleguide → excerpts → rules, rules last; consumers may not reorder.

| Value | Owner | Supplied as | Default |
|---|---|---|---|

| `PROFILE_EXCERPT_CHARS` | BE `internal/voice` config | typed constant | `1500` |
| `VOICE_LABEL_FALLBACK_CHARS` | BE `internal/voice` config | typed constant | `20` |

Analysis prompt text is code, not config (ARCHITECTURE §4).

## As-built extension — job 16 / change 02

The current system keeps pasted samples as an optional import surface and adds progressive learning from explicitly
finalized first-party posts:

- `PostContent` is directly editable with revision-checked block autosave. Machine generation/revision stores an
  immutable baseline. **Finalize** first binds the current content revision without requiring a model; the separate
  **Finalize and learn** or later **Learn voice** action enqueues `learn_voice` only after an explicit analyze-model
  choice. Learning input hashes and event/source/evidence uniqueness make repeats idempotent.
- The account profile is a typed whole-version snapshot: lexical, endings, syntax, structure, six bounded axes,
  explicit unknown/provenance, active/candidate/retired rules, sources, and feedback. Manual field overrides and
  restores publish new heads while retaining all old versions. Existing styleguide/rules survive as legacy manual
  guidance.
- Deterministic Unicode measurements own ending distribution and sentence length. LCS-aligned final edits create at
  most three style-only contrast rules when a pattern has two cited edits. Independent evidence activates at three;
  contradictions wait for owner resolution; stale active rules retire only during a later explicit generation or
  revision request.
- `ProfileForPromptForTopic` returns the typed/legacy guidance, evidence-ranked active constraints, and 0–3 unique
  authored/import excerpts with topical matches first and stable recent fallback. A single unrelated finalized post
  is therefore still available to the next generation, while zero history remains valid.
- Rule A/B and three-post profile validation are separate on-demand jobs. Starts carry explicit model refs; judge is
  opt-in. Neither changes model Elo. A decision is accepted only after two successful blind rule candidates.
- `learn_voice`, `compare_voice_rule`, and `validate_voice_profile` are failed before boot worker drain and retried
  only by another explicit action. No timer, page read, copy/export, age check, boot, scheduler, or cron initiates a
  personalization provider call.

The detailed algorithm, retention, idempotency, and configuration contract is
[voice-personalization-learning](../tech/voice-personalization-learning.md). Migration 0007 owns the post baseline and
versioned voice aggregates; `voice_learning.proto` and `voice_validation.proto` own the explicit learning, feedback,
lifecycle, comparison, and validation RPCs.

## As-built extension — job 17 / change 03

Voice learning consumes only an ownership-checked, still-finalized post snapshot. A learning setup, queue, worker, or
provider failure never rolls the post back from `finalized`; it remains visible as a separate, reload-safe learning
failure that retries learning only. Finalize-only is a complete outcome and never mutates the profile. Target length
is optional learning metadata rather than a hidden requirement.
