# 14. Theme Preferences

> Let every visitor choose System, Light, or Dark, apply the effective theme before first paint, and keep every
> public, login, and authenticated surface plus browser chrome in sync | Scope: FE | Status: planning

## Purpose

Postpilot already ships complete `night` and `day` semantic token maps, but only `night` is reachable. A phone-first
product is used under changing ambient light and should respect the device setting by default while still allowing an
explicit override.

Theme is an interface preference, not account data. It must work before login, survive navigation and reloads on the
same browser, and never require the API. This plan adds `System / Light / Dark`, with System as the first-visit
default, and exposes the choice on every public, login, and signed-in surface. It follows plan 13's browser-local
locale precedent and composes with its translated preference controls.

## Scope / Non-goals

### In scope

- Three preferences: `system`, `light`, and `dark`; first visit and missing, unreadable, or invalid storage resolve to
  `system`.
- `system` follows `prefers-color-scheme` initially and while the page remains open.
- Explicit Light or Dark ignores later OS changes until the user returns to System.
- Browser-local persistence across reloads, logout/login, public/authenticated routes, and tabs on the same origin.
- Theme application before React renders so stored Light does not first paint as Dark, or vice versa.
- Synchronizing `<html data-theme>`, CSS/native `color-scheme`, `<meta name="theme-color">`, and browser controls
  with the effective theme.
- A translated selector on `/login` and the authenticated shell, plus the reusable public-surface contract consumed
  by plan 15's `/about` header.
- Phone-safe composition with plan 13's locale selector; the two preferences may share one compact preferences
  popover on narrow screens rather than overflowing the header.

### Non-goals

- Account/server synchronization, a preference RPC, SQLite storage, or cross-device synchronization.
- Additional palettes, user-authored colours, accent selection, scheduled sunrise/sunset themes, or per-route themes.
- Changing the fixed app-icon artwork or redesigning existing screens.
- Theme-dependent business behavior, provider/model calls, jobs, analytics, or telemetry.
- A new styling library or runtime dependency.

## Design

### Preference and effective-theme contract

```ts
type ThemePreference = "system" | "light" | "dark";
type EffectiveTheme = "day" | "night";
```

| Preference          | Effective theme |
| ------------------- | --------------- |
| `system` + light OS | `day`           |
| `system` + dark OS  | `night`         |
| `light`             | `day`           |
| `dark`              | `night`         |

The storage key contains only explicit `light` or `dark`; choosing System removes it. Missing, unreadable, or unknown
values therefore have one meaning: System. Storage access failures are non-fatal and leave a working in-memory System
preference.

The effective theme is applied as `data-theme="day|night"` on `<html>`. The existing semantic tokens remain the only
component-facing colour contract; components never branch on theme or name palette steps.

### Bootstrap and lifecycle

A synchronous bootstrap owned by `app/providers/theme` runs before the main React entry:

1. safely read the stored preference;
2. resolve System through `matchMedia('(prefers-color-scheme: dark)')`;
3. set `<html data-theme>` before the first application paint; and
4. align browser chrome metadata with the same effective theme.

The mounted runtime reuses the same resolver and:

- listens to media-query changes only for a System preference;
- applies a user selection immediately and persists or removes the override;
- listens to `storage` events so another same-origin tab updates without reload;
- cleans every listener under React Strict Mode; and
- keeps the active `theme-color` equal to the themed header plane and native `color-scheme` equal to the effective
  theme.

Theme changes are immediate; no full-page colour transition is introduced. Logging out clears session-owned state but
does not clear this browser preference.

### UI and placement

The selector uses plan 13's active locale:

| Locale | Label   | Options                    |
| ------ | ------- | -------------------------- |
| `ko`   | `테마`  | `시스템`, `밝게`, `어둡게` |
| `en`   | `Theme` | `System`, `Light`, `Dark`  |

It uses existing `shared/ui` controls, exposes its label and selected value to assistive technology, preserves the
44 px target floor, and is keyboard-operable. Colour is never the only indication of selection. Locale and theme
remain independent: changing one neither changes the other nor changes the URL.

FSD placement:

- `frontend/src/shared/lib/theme/**`: pure resolution and safe browser-adapter helpers shared by bootstrap and UI.
- `frontend/src/shared/config`: the stable storage key and default preference.
- `frontend/src/app/providers/theme/**`: pre-React/runtime installation and document metadata side effects.
- `frontend/src/features/change-theme/{model,ui}/**`: the user-facing mutation and translated selector.
- `frontend/src/widgets/interface-preferences/**`: only when needed to compose locale and theme into one reusable
  narrow-screen control without feature-to-feature imports.
- `frontend/src/pages/login/ui/LoginPage.tsx` and `frontend/src/app/routes/AuthenticatedLayout.tsx`: compose the
  control; plan 15 composes the same public contract in `/about`.
- `frontend/src/app/styles/index.css`: retain the semantic maps and replace the statement that Night is the only
  reachable theme.

There is no proto, Connect RPC, backend package, migration, data row, or job/state transition.

## Acceptance Criteria

1. With no valid stored override, the first rendered application frame matches the current OS colour scheme and the
   selector reports System.
2. Selecting Light or Dark applies `day` or `night` immediately and survives navigation, reload, logout, and later
   login on that browser.
3. Selecting System removes the explicit override and immediately follows the current OS setting.
4. An OS colour-scheme change updates an open System-mode tab but does not alter an explicit Light or Dark tab.
5. A preference change in another same-origin tab updates the current tab through the storage event.
6. Disabled, unavailable, malformed, or throwing storage never prevents the application from rendering; it falls
   back to System for that session.
7. `<html data-theme>`, CSS/native `color-scheme`, and browser `theme-color` always describe the same effective theme.
8. Theme bootstrap completes before the React app renders; automated bootstrap tests detect no initial wrong-theme
   frame.
9. `/login` and every authenticated route can reach the selector through their shared shells; the public contract is
   reused by `/about` when plan 15 lands rather than creating a second theme state.
10. Korean and English labels come from plan 13's typed resources, and changing theme never changes locale or URL.
11. Locale/theme/session-control composition has no horizontal overflow at 320 px, preserves 44 px targets, and is
    fully usable by keyboard and screen reader.
12. Existing screens use only semantic/functional tokens and meet WCAG AA in both themes.
13. Rendering or changing theme performs no RPC, provider call, job enqueue, or account mutation.
14. Theme resolver, bootstrap, media/storage listeners, selector behavior, metadata synchronization, both-theme
    visual states, frontend tests, lint, FSD/style checks, and build pass.
