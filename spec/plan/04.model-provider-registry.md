# 04. Model Provider Registry

> A vendor-neutral LLM port, providers registered in `config/providers.yaml`, capability-aware per-stage model
> dropdowns, and per-account memory of the last choice | Scope: FS | Status: planning

## Purpose

Generation is two calls with different needs (cheap vision for observation, a good writer for the draft — [I3]),
free models vanish without notice, and the two users may want different price/quality trade-offs. The app therefore
does **not** pick models: it exposes what is registered, marks what each model can do, greys out what cannot run
(no API key, model gone), and remembers each person's last choice per stage (PRD §3.3, §6.4, §6.5, F-4).

The Go side needs a hard boundary so that nothing above `internal/llm` ever learns which vendor answered
(ARCHITECTURE §2.1). Adding a provider must be a config edit, not a code change.

## Scope / Non-goals

**In scope**

- The `internal/llm` port (`Provider`, `Request`, `Response`) exactly as the PRD frames it, plus the registry that
  loads `config/providers.yaml`, resolves API keys from env, and exposes model capabilities.
- Adapters: `openai_compatible` first (covers OpenRouter, Together, Groq, Fireworks, DeepInfra, OpenAI, Ollama, vLLM,
  LM Studio, Google's compatible endpoint); `anthropic` via the official Go SDK **when a registered provider needs
  it**. The PRD deliberately does not fix how many adapters ship in 1.0.
- `ListModels` with per-model `vision` / `structured_output` flags and `disabled` + reason.
- Per-user, per-stage (`observe`, `write`, `analyze`) last-selection persistence and RPCs.
- Stage timeout (5 min per provider call) and adapter-internal streaming to survive long outputs.
- FE: per-stage dropdowns (observe shows vision-only), disabled/greyed rendering with reasons, vanished-model handling.

**Non-goals**

- Any app-chosen default model or default pairing (PRD §3.3: 앱이 기본값을 정해 주지 않는다).
- In-app routing/fallback between models (use router models such as `openrouter/free` in the yaml instead).
- Cost or token accounting, budgets, usage dashboards.
- Streaming tokens to the client — streams stay inside the server; the client sees job progress (PRD §6.6).
- Storing API keys anywhere but process env; exposing keys or provider SDK types to the frontend.
- Prompt text, JSON schemas, and structured-output *fallback parsing* — those belong to the callers (plans 03, 06,
  07); this plan only signals whether a model supports structured output and passes a schema through.

## Design

### The port — `backend/internal/llm`

```go
type Provider interface {
    Name() string
    Complete(ctx context.Context, req Request) (Response, error)
}
type Request struct {
    Model      string
    System     string
    Messages   []Message   // Text and Image parts (image = bytes + mime); roles user/assistant
    JSONSchema []byte      // non-nil → the adapter requests structured output; error if unsupported
    MaxTokens  int
}
type Response struct {
    Text   string          // raw text, or the JSON document when JSONSchema was set
    Usage  Usage           // prompt/completion tokens when the provider reports them
}
```

- Callers pass the **model** explicitly (per stage); the port reads no global default.
- Errors are normalized into a small set the callers can act on: `ErrModelUnavailable` (unknown/vanished model),
  `ErrProviderDisabled` (no key), `ErrRateLimited` (quota — the free-tier daily limit case), `ErrUnsupported`
  (image or schema on a model that lacks it), `ErrBadOutput`, plus a generic wrapped error carrying the provider's
  message. The job layer surfaces the message verbatim to the user (PRD §7: 오류 메시지에 원인 노출).
- Each call runs under a `LLM_STAGE_TIMEOUT` (5 min) context. Adapters **may** consume the provider's streaming
  response internally to avoid idle HTTP timeouts on long outputs; the stream never leaves the process (PRD §6.6).

### Registry — `config/providers.yaml`

```yaml
providers:
  - id: openrouter
    adapter: openai_compatible          # base_url differs, protocol is the same
    base_url: https://openrouter.ai/api/v1
    api_key_env: OPENROUTER_API_KEY
    models:
      - id: openrouter/free             # auto-routing entry: survives individual free models disappearing (PRD §6.5)
        label: OpenRouter free (auto)
        vision: true
        structured_output: false
      - id: anthropic/claude-sonnet-4.5
        vision: true
        structured_output: true
  - id: anthropic
    adapter: anthropic                  # one of the few genuinely different schemas → official Go SDK
    api_key_env: ANTHROPIC_API_KEY
    models: [...]
```

- Loaded and validated at boot (unknown adapter, duplicate id, missing `base_url` for `openai_compatible` → the
  process exits, same posture as a bad migration: a broken config must be loud). Path from `PROVIDERS_CONFIG`.
- `api_key_env` names an env var; the key is read from the process environment at boot. Missing → every model of
  that provider is `disabled` with reason `API key not configured` (PRD §6.4, §7). The registry never stores the
  key in yaml.
- `vision` and `structured_output` are declared per model in the yaml (the registry cannot probe them reliably).
- Adding a model or provider = edit yaml + restart. No code change (PRD §6.4).

### Adapters — `backend/internal/llm/<adapter>`

- `openai_compatible`: `POST {base_url}/chat/completions`; images as `image_url` data URLs (base64 JPEG);
  `response_format: {type: json_schema, json_schema: …}` when `JSONSchema` is set and the model declares
  `structured_output`; streaming (`stream: true`) consumed server-side; provider error bodies mapped to the
  normalized errors above (HTTP 429 → `ErrRateLimited`, 404/400 "model not found" → `ErrModelUnavailable`).
- `anthropic`: added when a provider entry needs it, via `github.com/anthropics/anthropic-sdk-go` — never hand-rolled
  HTTP (PRD §6.4). Structured output through the SDK's tool/JSON mechanism; images as base64 blocks.
- No adapter type, SDK type, or provider error type crosses above `internal/llm` (ARCHITECTURE §2.1).

### Contract — `proto/postpilot/v1/provider.proto`

```
service ProviderService {
  rpc ListModels    (ListModelsRequest)    returns (ListModelsResponse);    // registry snapshot + per-model flags
  rpc GetSelections (GetSelectionsRequest) returns (GetSelectionsResponse); // acting user's per-stage choices
  rpc SaveSelection (SaveSelectionRequest) returns (SaveSelectionResponse);
}
message ModelRef  { string provider_id = 1; string model_id = 2; }          // reused by Start* RPCs in plans 03, 06, 07
message ModelInfo { ModelRef ref = 1; string label = 2; bool vision = 3; bool structured_output = 4;
                    bool disabled = 5; string disabled_reason = 6; }
enum Stage { STAGE_UNSPECIFIED = 0; OBSERVE = 1; WRITE = 2; ANALYZE = 3; }
message Selection { Stage stage = 1; ModelRef ref = 2; bool missing = 3; }  // missing: saved ref no longer registered
message SaveSelectionRequest { Stage stage = 1; ModelRef ref = 2; }
```

### Selection memory (PRD F-4, addition to §5)

```sql
model_selections (user_id TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
                  stage TEXT NOT NULL,             -- observe | write | analyze
                  provider_id TEXT NOT NULL, model_id TEXT NOT NULL,
                  updated_at TEXT NOT NULL, PRIMARY KEY (user_id, stage))
```

- The FE calls `SaveSelection` whenever a dropdown changes. `Start*` RPCs (plans 03/06/07) receive the `ModelRef`s
  explicitly in their requests and record them on the job row; they do not read this table — the table exists only
  to refill the dropdowns.
- `GetSelections` marks a selection `missing` when its ref is no longer in the registry. The FE then renders the old
  entry greyed with the reason "등록된 모델 목록에서 사라졌어요" and **clears** the saved selection (PRD §7: 마지막
  선택 초기화) so the user must pick again.

### Dropdown rules (FE)

- `observe` stage: only `vision: true` models are listed (PRD §6.4). `write` and `analyze`: all models.
- `disabled` models render greyed, unselectable, with `disabled_reason` as a tooltip/inline note.
- Each model shows badges: 👁 vision, `{}` structured output.
- No pre-selection: until the user picks, the stage is empty and `Start*` is blocked with an inline message
  (acceptance criterion 7 — the "no default pairing" invariant is visible here).
- Free-model advice (PRD §6.5) is expressed in yaml content (router entries), not in UI logic.

## Acceptance Criteria

1. Adding a provider or model by editing `config/providers.yaml` and restarting makes it appear in the dropdowns with
   no code change; an invalid yaml stops the api from starting with a clear error.
2. A provider whose `api_key_env` is unset shows all its models greyed with reason "API key not configured"; they
   cannot be selected.
3. The `observe` dropdown lists only `vision: true` models; `write` and `analyze` list all.
4. A selection made on one device is restored on another device for the same account and stage.
5. When a saved model is removed from the yaml, the dropdown shows it greyed with the "vanished" reason and the saved
   selection is cleared; the user must choose again.
6. The frontend never receives an API key or a provider SDK payload — only ids, labels, and flags (asserted by the
   proto shape; keys exist only in server env).
7. A fresh account has no selection in any stage; the generation and analysis actions are blocked with an inline
   message until both required stages are chosen — the app ships no default pairing ([I3]).
8. A provider 429 surfaces as `ErrRateLimited` with the provider's message intact, so the job error the user sees
   names the cause (PRD §7: 무료 모델 한도 초과).
9. Requesting an image part or a JSON schema on a model that lacks the capability fails fast with `ErrUnsupported`
   before any network call.
10. No package above `internal/llm` imports an adapter or SDK package (enforced by a build-tag/lint check in the job).

## Policy / Config Impact

**Rules that will be true once implemented** (→ `spec/policy/providers.md`):

- Providers and models are declared only in `config/providers.yaml`; keys only in env; the app ships no default model.
- Observation may run only on vision-capable models; structured output is requested whenever the model supports it.
- Missing key ⇒ disabled model with reason; vanished model ⇒ greyed with reason and the saved selection is reset.
- Nothing above `internal/llm` learns which provider answered.

**Config**

| Value | Owner | Supplied as | Default |
|---|---|---|---|
| `PROVIDERS_CONFIG` | BE `platform/config` | env | `config/providers.yaml` |
| `<api_key_env>` per provider (e.g. `OPENROUTER_API_KEY`, `ANTHROPIC_API_KEY`) | BE process env, named by yaml | env | — (stack `.env`; listed in `.env.example`) |
| `LLM_STAGE_TIMEOUT` | BE `platform/config` | typed constant | `5m` (PRD §6.6) |
| `LLM_MAX_TOKENS_DEFAULT` | BE `internal/llm` config | typed constant | adapter default; callers may override per request |
| `config/providers.yaml` | repo + deploy mount | file | model ids, labels, capability flags |

The yaml is config; the model ids inside it are data, never literals in Go or TS.
