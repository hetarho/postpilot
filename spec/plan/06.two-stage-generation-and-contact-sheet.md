# 06. Two-Stage Generation and Contact Sheet

> Observe the photos, then write the post in the author's voice; the result is a validated block array (the canonical
> post), and the contact sheet shows what the model saw under each photo | Scope: FS | Status: done — backend
> pipeline and contract (job 10), contact sheet, reading view, and generate action (job 11)

## Purpose

This is the product's core action: photos + memo → a publish-ready draft in **my** voice within ~3 minutes (PRD §1).
Three PRD decisions shape it:

- **Two calls, not one** ([I3], PRD §3.3). Eight photos plus a memo in one call makes the model smear the later
  photos together. Observation looks only at photos and emits structured facts; writing consumes those facts, the
  memo, and the voice profile. Each stage has its own model.
- **Blocks are the canonical post** ([I2], PRD §3.2). Naver's editor discards pasted HTML, so the output has to be a
  structured block array from which each platform's format is derived (plan 08).
- **The contact sheet is a debugging screen, not decoration** (PRD F-5). When a draft is wrong, nine times out of
  ten the observation stage misread a photo. The user must be able to see exactly what the model saw, per photo,
  before suspecting anything else.

## Scope / Non-goals

**In scope**

- The `Block` / `BlockType` proto (flat message, no `oneof`) and the `GenerationResult` shape
  (`title, summary, tags, blocks`); `posts.content` as protojson; `posts.observations` as JSON.
- The single post-deserialization **validation function** (field combination per type; invalid block dropped +
  logged) and the **attachment filter** (image blocks referencing non-attached filenames removed).
- Observation stage: vision model, batches of `OBSERVE_BATCH_SIZE` photos per call, per-photo structured output,
  filename-based matching, incremental persistence and progress.
- Writing stage: profile injection in the fixed order (plan 03 contract), structured output when supported,
  fence-stripping fallback parser otherwise, "one paragraph per text block" prompt rule, Korean output.
- `StartGeneration` RPC with explicit per-stage `ModelRef`s; the `generate` job handler.
- 0-photo generation (observation skipped).
- Status transition `draft → review` on success; whole-content replacement (no versions).
- Contact sheet widget: horizontal thumbnail strip with the observation text under each photo, filling in as
  batches complete; the rendered draft (block reading view); the generating indicator in the editor and list.

**Non-goals**

- Natural-language revision — plan [07](07.ai-revision.md). Platform formats and copying — plan
  [08](08.platform-export.md).
- A manual block editor. The PRD's editing model is AI revision (F-6) and copy-out; there is no hand-editing of
  blocks in 1.0 (S1: 읽어보고 "더 짧게" 한 번).
- Streaming tokens to the browser; version history / undo (PRD §8); multilingual output (PRD §8); SEO/keyword work
  (PRD §1).
- Choosing models for the user ([I3]) or fabricating images (PRD §8).
- Face blurring — must happen before upload if ever (PRD §8); nothing in this pipeline sends originals anywhere
  (it only reads the ≤1024px JPEGs already in R2).

## Design

### Canonical content — `proto/postpilot/v1/post.proto`

```
enum BlockType { BLOCK_TYPE_UNSPECIFIED = 0; TEXT = 1; HEADING = 2; IMAGE = 3; QUOTE = 4; LIST = 5; }

message BlockSlot {              // a position a template reserved (change 25); see tech/post-template-grammar
  string kind  = 1;              // photo | place | link
  string label = 2;              // the template author's words, shown to whoever fills it
}

message Block {                  // flat on purpose: protojson of this matches what models emit; no oneof (PRD §3.2)
  BlockType type = 1;
  string content = 2;            // TEXT · HEADING · QUOTE
  int32  level   = 3;            // HEADING (2 or 3)
  string file    = 4;            // IMAGE — must equal an attached Image.filename
  string alt     = 5;            // IMAGE
  string caption = 6;            // IMAGE
  repeated string items = 7;     // LIST
  BlockSlot slot = 8;            // set ONLY on an unfilled template slot; rides on TEXT rather
}                                //   than adding a sixth BlockType, so every switch stays correct
message PostContent { string title = 1; string summary = 2; repeated string tags = 3; repeated Block blocks = 4; }
```

- `posts.content` stores `protojson(PostContent)` (PRD §5 shape). `posts.title` remains the user's 가제; the
  generated title lives in `content.title`. The list shows `posts.title`, falling back to `content.title`.
- The FE consumes the generated TS types through `shared/api`; the schema lives in proto only (PRD §3.2).
- **Validation function** (one, in `internal/generation`, run immediately after unmarshalling any model output and
  before any persist — PRD §3.2, §7):

  | type | required | allowed | else |
  |---|---|---|---|
  | TEXT | `content` non-empty | schema-required `level` is ignored and normalized to `0` | drop |
  | HEADING | `content` non-empty, `level ∈ {2,3}` (other → clamp to 2) | — | drop |
  | IMAGE | `file` non-empty | `alt`, `caption`; schema-required `level` is ignored and normalized to `0` | drop |
  | QUOTE | `content` non-empty | schema-required `level` is ignored and normalized to `0` | drop |
  | LIST | `items` ≥ 1 non-empty | schema-required `level` is ignored and normalized to `0` | drop |
  | UNSPECIFIED / unknown | — | — | drop |

  Any populated field outside the type's set (e.g. `TEXT` with `items`) → the block is dropped and a log line names
  the type and offending field. The uniform structured-output schema requires `level` on every block, so non-heading
  values are the one exception: they are silently normalized to `0`. Validation never repairs across blocks.
- **Attachment filter:** after validation, IMAGE blocks whose `file` is not among the post's attached filenames are
  removed (PRD F-4, §7). Filenames are compared exactly (case-sensitive) — the prompt lists the exact names.

### `StartGeneration`

```
service GenerationService {
  rpc StartGeneration (StartGenerationRequest) returns (StartGenerationResponse);   // + GetGeneration from plan 05
}
message StartGenerationRequest  { string post_slug = 1; ModelRef observe_model = 2; ModelRef write_model = 3; }
message StartGenerationResponse { string job_id = 1; }
```

Preconditions (all `FailedPrecondition` / `InvalidArgument` before enqueue): the post is the caller's; `write_model` is
set and enabled; `observe_model` is set, enabled and `vision: true` **unless the post has no images** (then it may be
empty and is ignored); no active job on the post (plan 05 guard). The models are recorded on the job row.

### The `generate` handler

```
observe (skipped when 0 images)
  for each batch of OBSERVE_BATCH_SIZE images (order = images.created_at):
    fetch JPEG bytes from R2 via the storage port (server-side read; this is not the upload path)
    Complete(observe_model, system=OBSERVE_PROMPT, user=[image parts…, "files: IMG_1.jpg, IMG_2.jpg, …"], schema=OBSERVATIONS_SCHEMA)
    match results to images by filename; results naming unknown files are discarded; unmatched images get an empty observation
    persist posts.observations (merged so far) ; progress("observe", done += len(batch), total = len(images))
write
  profile := voice.ProfileForPrompt(user)                          // plan 03 contract: styleguide → excerpts → rules
  system  := WRITE_PROMPT + profile (in that order; rules last)     // stable prefix first (PRD §5 caching note)
  user    := observations (as JSON) + memo + title hint + attached filenames + output constraints
  Complete(write_model, schema=POST_CONTENT_SCHEMA when structured_output else nil)
  parse → validate → attachment filter → persist posts.content, posts.status='review' ; progress("write", 1, 1)
```

- **Observation schema** (per photo): `{ file, scene, mood, visible_text, objects[], people_present: bool }` — facts
  only, no prose about the post (PRD §3.3: 글은 쓰지 않는다). Batching exists because free tiers meter per call
  (PRD §6.5); batch size is config.
- **Count mismatch** (PRD §7): matching is by filename, extras are dropped, missing ones are empty — the count of
  photos never changes.
- **Writing constraints in the prompt:** output Korean; one paragraph per `TEXT` block (PRD §3.2 — the model must not
  pile a long passage into one block); use only the listed filenames and never invent images; place IMAGE blocks
  where the photo belongs in the narrative; produce `title`, `summary` (one line), 3–6 `tags`.
- **Structured output** is requested whenever the write model declares it (PRD §6.4). Otherwise the fallback parser:
  strip ```` ``` ```` fences (with or without a `json` tag), take the first `{…}` object, unmarshal. Failure → the
  job fails with `error = "모델이 JSON 대신 다른 답을 돌려줬어요: " + first 200 chars of the raw text` (PRD §7).
- 0 photos: `observe` is skipped entirely; `progress_total` for observe is 0; the write prompt says there are no photos.
- Persistence is the post context's published behavior (`post.SetObservations`, `post.SetGeneratedContent`) — the
  generation context never touches `posts` rows directly (ARCHITECTURE §2.2). Each persist is its own short write
  transaction, after the provider call returns (§2.4).
- Timeouts: every `Complete` runs under `LLM_STAGE_TIMEOUT` (plan 04). A timeout fails the job with a clear reason.

### Contact sheet (F-5) and the reading view

- `widgets/contact-sheet`: a horizontal, scrollable strip of the post's images (presigned GET `view_url` from
  `GetPost`, plan 02). Under each thumbnail: the observation for that filename — `scene`, `mood`, `visible_text`,
  `objects` — rendered plainly. While a job is in `observe`, already-observed photos show their text and the rest show
  a "관찰 대기" placeholder; the strip refreshes on each poll because observations are persisted per batch.
- Copy in the widget states its purpose ("모델이 각 사진에서 본 것 — 글이 이상하면 여기부터 확인하세요").
- Reading view: `entities/post/ui/BlockList` renders `PostContent` (title, summary, tags, blocks); IMAGE blocks show the
  thumbnail by filename with caption. This is a read-only rendering — editing is plan 07.
- Generating indicator: `pages/editor` shows the plan-05 progress line; `pages/posts` shows a `생성 중` badge from
  `active_job` (the deferral noted in plan 02).
- `features/generate-post`: the "생성" button, the two stage dropdowns (plan 04's `features/select-model`), inline
  blockers (no write model; no vision model while photos exist; empty profile warning from plan 03 is shown but does
  not block), and the `StartGeneration` call that hands the job id to `useJob`.

## Acceptance Criteria

1. Generating a post with 0 photos succeeds: no observation call is made, the write stage runs from the memo alone,
   and a `PostContent` with blocks is persisted.
2. The persisted content contains no IMAGE block whose `file` is not an attached filename — a model output that
   references `IMG_999.jpg` is filtered and logged (unit test with a crafted payload).
3. Observation precedes writing; `posts.observations` holds one entry per attached photo keyed by filename after the
   job, and the contact sheet shows each entry under its thumbnail.
4. With N photos and `OBSERVE_BATCH_SIZE = 4`, the handler makes `ceil(N/4)` observation calls and progress advances
   by batch (stubbed provider test).
5. A model output with a bad field combination (`TEXT` with `items`) or unknown type drops exactly that block, logs
   it, and persists the rest. A schema-required non-zero `level` on `TEXT`, `IMAGE`, `QUOTE`, or `LIST` instead keeps
   the block, normalizes `level` to `0`, and emits no warning (unit tests).
6. The write prompt order is task/format rules → fixed Korean naturalness baseline → styleguide → active contrast
   rules → excerpts → user rules → ending constraint → optional template → optional guidelines → per-post material (snapshot test on prompt
   assembly). User rules remain after all excerpts.
7. The write prompt includes the one-paragraph-per-TEXT-block rule, the exact attached filenames, and the
   no-invented-images rule (prompt snapshot).
8. When the write model declares `structured_output`, the request carries the `PostContent` JSON schema; when it
   does not, a fenced ```` ```json ```` response is parsed successfully and an unparseable response fails the job with
   an error that begins with the fixed Korean prefix and includes the raw head.
9. Closing and reopening the browser mid-generation shows the in-flight progress and, on completion, the rendered
   draft and `status = review` (plan 05 mechanics, this plan's content).
10. Thumbnails load via presigned GET URLs; the R2 object is not readable without one.
11. Observation results naming files that are not attached are discarded and photos without a result get an empty
    observation — the observation count always equals the photo count.
12. `StartGeneration` without a write model, or with photos attached and a non-vision observe model, is refused
    before any job is created.

## Policy / Config Impact

**Rules implemented by jobs 10, 11, 24, and 36** (recorded in [policy/generation.md](../policy/generation.md)):

- The canonical post is `PostContent` (block array) stored as protojson; HTML and every platform format are derived.
- Every model output passes the single validation function and the attachment filter before persistence.
- Generation is observe → write with per-stage, user-chosen models; observation never writes prose; structured output
  is requested whenever the model supports it.
- Prompt assembly is fixed task/format rules → Korean naturalness baseline → styleguide → active contrast rules →
  excerpts → user rules → ending constraint → optional template → optional guidelines → per-post material. Voice and user rules override
  the baseline on conflict.
- A successful generation replaces the whole content and sets `status = review`.
- The contact sheet always shows the persisted observation per photo.

## As-built extensions — jobs 15 and 17

Job 15 introduced fair blind write comparisons. Job 17 made them an explicit `A/B comparison generation` action
instead of the ordinary path. Ordinary `StartGeneration` observes at most once and calls exactly one explicitly
active writer; it creates no experiment and writes validated canonical content as `review`. Explicit A/B freezes one
shared prepared snapshot, calls two explicitly configured writers, and leaves canonical content unchanged until the
owner applies a blind result. Both paths remain resumable and share the same validation and attachment filtering.
Current rules live in [policy/generation](../policy/generation.md) and
[policy/model-experiments](../policy/model-experiments.md).

## As-built extension — job 16

The frozen write snapshot now includes the per-post target-length option when enabled and a topic-aware voice projection:
structured descriptors, bans, active evidence-ranked rules, legacy manual guidance, and 0–3 unique authored/import
excerpts. Zero history remains valid. Candidate/retired rules are excluded; the prompt follows measured ending
distribution, forbids a third identical ending, and tells the model not to copy source facts or phrasing. Applying a
write winner atomically establishes the post's new machine baseline.

Job 17 removed the mandatory 1,200-character fallback. The collapsed option round-trips as absent when disabled;
ordinary generation, both A/B candidates, and later revision freeze the exact value only when it is present.

## As-built extension — job 36

Every Korean write now receives one fixed `[한국어 자연 문체 기준선]` immediately after the static task/format and
tag rules and before `[스타일가이드]`. It caps stock antithesis, formulaic paragraph closers, obligation endings,
connective-ending commas, uniform rhythm, generic verbs, stacked invented metaphors, abstract-noun chains, and
unprompted rhetoric in newly written or explicitly revised `TEXT` prose only. Titles, summaries, structured
`HEADING`/`LIST` content, and untouched revision text are outside the floor. It deliberately does not ban the
corpus-rejected folk markers recorded by archived change 10.
The closing precedence sentence makes the voice profile, active contrast rules, and user rules authoritative on a
conflict, so the floor never erases a measured personal habit.

`BuildWritePrompt` and `BuildRevisePrompt` share the exact constant. Empty voices, ordinary generation, and both A/B
write candidates therefore receive the same floor; observation does not. The stable system prefix changed once when
the section landed and remains byte-identical for equal voice/template/length state. Plan 13 must include this
Korean-only section for Korean targets and omit it for every non-Korean target.

## As-built extension — job 49 / change 21

A run no longer re-observes photos it already understands. Starting generation on a post that has photos AND at
least one reusable stored observation opens a **re-observation picker** first, and the run observes only the photos
that picker names ([changes/archive/21](../changes/archive/21.reuse-finished-observations-and-pick-whi.md)).

- **Provenance is per entry, not per snapshot.** `Observation` carries the model ref that produced it (`model` on
  the wire, on `post.Observation` and on `generation.Observation`, in the observations JSON column — **no
  migration**: an entry written before the field decodes empty, which reads as unknown). Per entry because
  re-observing a subset is exactly what makes one snapshot hold two models' work. The stamp is applied where a batch
  runs, including on the empty entry a missing filename produces, so "this model looked and said nothing" stays
  distinguishable from "nothing has ever looked at this photo".
- **The picker is one surface on one mount.** `Dialog` — that is, `Sheet` — already renders as a bottom sheet on a
  phone and a centred dialog from `md:` up, in CSS. It lists every attached photo in post order with its thumbnail,
  its stored observation and a checkbox meaning *observe this photo again*, plus select-all / clear-all, the model
  that produced the stored observations, and a notice naming both models when the selected observation model differs
  from a KNOWN stored one. Every checkbox starts CLEAR: confirming untouched reuses everything.
- **A photo with nothing to reuse is not optional.** No stored entry, or one with no scene, mood, visible text,
  objects or people, renders checked and disabled with its reason stated — and the SERVER forces it into the
  selection regardless of what the client asked for. A run must not write from a photo it has never looked at.
- **The decision is frozen at enqueue, in one read, in two halves.** `StartGeneration`/`StartWriteExperiment` carry
  a `ReobserveSelection` message — a MESSAGE because presence is the contract and proto3 gives a repeated field
  none: absent means "no picker was involved, observe everything" (what a client predating this sends), and present
  with an empty `files` means "observe nothing". `Start` intersects that set with the attached photos, forces the
  photos with nothing to reuse, and freezes the resolved filenames plus the whole reusable snapshot into the durable
  payload (`observe_files` as a presence-carrying pointer, `observations`). The A/B write snapshot freezes the same
  two things. Attaching a photo, deleting one, or switching the observation model afterwards cannot reach queued work.
- **The handler observes only the frozen set, and the snapshot never shrinks.** Every persist writes the seed —
  what was known at the freeze — with this run's fresh entries laid over it, so a partial re-observation is complete
  from the FIRST persist and a photo awaiting its batch keeps the entry it had. A photo neither half covers is left
  out rather than given an empty entry, which is what keeps an unseeded full run's persist sequence byte-identical
  to the pre-change one. An empty frozen set makes no provider call and no `SetObservations` call at all, reports
  `observe 0/0`, and goes straight to writing. Observation progress totals the frozen set, not the attached count.
- **The write stage sees only what the run has eyesight for.** `post.Images` is read live at dequeue, so the handler
  narrows it to the photos covered by the merged snapshot before writing: a photo confirmed between the enqueue and
  the dequeue is outside the frozen decision and must not reach the write prompt as a bare filename either. It
  belongs to the next run.
- **A deleted photo's observation goes with it.** Entries pair to photos by filename alone and a filename is free to
  be taken again once its photo is gone, so `DeletePost`'s sibling `DeleteImage` drops that photo's entry — otherwise
  a different photo uploaded under a freed name would inherit reusable eyesight that was never of it.
- **The credit hold prices the frozen set.** `ObserveCalls` is computed over the frozen selection, and the job's
  stated call count is now honored EXACTLY, zero included (`internal/job`), so a reuse-everything run is held for no
  observation call. A model serving both stages states the total, because the count is per model across the job.
- **Unchanged, deliberately:** the observation prompt, schema, `OBSERVE_BATCH_SIZE` as the owner of batching,
  filename matching, the validation function and the attachment filter; the observation-model precondition for a
  post with photos, even when the frozen set is empty; terminal failure (a failed job stays failed — no resume, no
  requeue); the zero-photo path; the observe-stage A/B, which compares observation models and so must never reuse
  one; `WriteExperimentPromptVersion`, since the prompt did not change and observations were already part of the
  snapshot's identity. The write stage's completion budget is a separate change against plan 04.

Known and out of scope: the write A/B's admission prices the observe model once regardless of how many batches it
runs. That imprecision predates this change and is not worsened by it in magnitude; pricing it properly means
threading a call count through the experiment enqueue seam.

Config: **none added.** `OBSERVE_BATCH_SIZE` in `backend/internal/platform/config` stays the sole owner of batching
and the picker introduces no tunable of its own.
