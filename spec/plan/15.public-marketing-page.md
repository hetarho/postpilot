# 15. Public Marketing Page

> Explain Postpilot to external visitors on a localized, themed public `/about` route reached from "What is
> Postpilot?", with Login as its only CTA | Scope: FE | Status: planning

## Purpose

The current public surface is a credential form. An external visitor can see the Postpilot name but cannot learn what
the product does, why its workflow differs from a generic AI writer, or why there is no signup.

Postpilot needs a concise public explanation page. The login page links to it through
`Postpilot이란? / What is Postpilot?`; `/about` explains the real product workflow and gives existing users one way
forward: Login. It must not imply open registration, pricing, or generally available access that the two-user product
does not provide.

The page reuses plan 13's URL-stable Korean/English locale and plan 14's System/Light/Dark preference, remains a pure
client-rendered SPA route, and makes no API call merely to explain the product.

## Scope / Non-goals

### In scope

- Public `/about`, outside the authenticated route guard and directly refreshable through the existing Cloudflare SPA
  fallback.
- A localized secondary link from `/login`: `Postpilot이란?` in Korean and `What is Postpilot?` in English.
- A public header with the wordmark, plan 13 locale control, plan 14 theme control, and one Login CTA.
- Complete Korean and English page copy with the same meaning and section structure while the URL remains `/about`.
- A phone-first, semantic long-form page using typography, existing icons, semantic planes, and existing brand assets.
- Client-side route metadata: localized title, description, Open Graph text/locale, and canonical `/about`.
- A truthful neutral static fallback title/description in `index.html` for clients that do not execute JavaScript.
- Accurate explanation of the shipped workflow, supported outputs, explicit user control, and privacy boundaries.

### Non-goals

- Signup, invitation requests, waitlists, contact/sales forms, pricing, checkout, newsletters, comments, or a CMS.
- Testimonials, fabricated usage metrics, case studies, screenshots, generated hero art, video, or remote marketing
  assets.
- Analytics, tag managers, tracking pixels, cookie banners, A/B marketing experiments, or advertising.
- SSR, SSG, prerendering, a separate marketing deployment, or a server-rendered metadata worker.
- A blog, docs portal, changelog, legal/privacy-policy authoring, sitemap project, or broad SEO tooling.
- Backend/proto/database changes, a public marketing API, or provider/model calls.
- Locale-prefixed URLs, automatic locale redirects, or changing the URL when language changes.

## Design

### Route and authentication behavior

`/about` is a direct child of the root route, beside `/login`, and is not a child of the authenticated pathless
layout. It has no `beforeLoad` session probe and mounting it makes no `GetMe` request.

The login page places the localized About link below the credential action without changing the form's generic-error
or redirect behavior. The About header's sole product CTA links to `/login`. If a signed-in visitor follows it, the
existing login guard may redirect them to the signed-in home; `/about` itself never probes or branches on session
state.

Locale changes reuse plan 13's browser preference and keep `/about` unchanged. Theme changes reuse plan 14's single
browser preference store.

### Information architecture and copy contract

All visible, accessible, and metadata copy lives in plan 13's typed `marketing` namespace for both `ko` and `en`; the
page component composes keys rather than embedding one language.

1. **Header** — Postpilot wordmark; locale/theme preferences; `로그인 / Log in`.
2. **Hero** — one H1 communicating that photos and rough notes become a publish-ready blog draft in the user's chosen
   voice. Supporting copy states that access is private/operator-provisioned; there is no signup.
3. **How it works** — one ordered flow:
   1. choose a voice, purpose, and target content language;
   2. add browser-converted photos and rough notes;
   3. Postpilot observes the photos first, then writes with explicit model choices and the selected voice; and
   4. revise/finalize, then copy a platform format or explicitly hand an eligible Naver publication to a paired Mac.
4. **Why it is different** — mutually isolated voice profiles; observation separated from writing; structured
   canonical blocks; user-selected models and explicit A/B/revision actions.
5. **Where the result goes** — Naver, Tistory, standalone-site HTML, and Markdown are derived from the same canonical
   post. Automatic Naver publication is described only when its shipped policy supports the claim and always as a
   separate, explicit, finalized-post action performed by a paired Mac.
6. **Control and privacy facts** — original images are converted in the browser before upload; account/voice evidence
   is isolated; opening pages does not trigger background AI work; Naver credentials and browser state stay on the
   paired Mac.
7. **Footer** — concise product identity only; no second CTA, signup implication, contact collection, or legal claim.

Copy must avoid guarantees not owned by policy: no "perfectly matches your voice", "never stores data", "fully
automatic publishing", or unsupported performance/security superlatives. If plan 12 has not completed its required
live verification when this page is implemented, the paired-Mac path is presented as optional/in verification or
omitted; it is never marketed as generally verified merely because this plan names it.

### Layout and accessibility

The public header is phone-first, safe-area aware, and sticky so its single Login CTA remains available without
duplication. At narrow widths, locale and theme may use plan 14's combined preferences popover. The page uses one H1,
ordered steps, descriptive H2 sections, semantic links/buttons, visible focus, and no colour-only meaning.

Section separation uses spacing and semantic surface steps rather than bordered card stacks. Existing `Logo`,
button/link, popover/select, and icon primitives are reused. There is no screenshot placeholder or decorative image
download. The layout has no horizontal page scroll at 320 px and is reviewed at 360/390/430 px, 200% zoom, keyboard
navigation, and both themes.

### Client-rendered metadata

On `/about`, and whenever locale changes, the page sets:

- localized `<title>`;
- localized `<meta name="description">`;
- `og:type=website`;
- localized `og:title`, `og:description`, and `og:locale`; and
- canonical and `og:url` equal to the current origin plus `/about`.

No `og:image` is invented. Leaving `/about` restores the next route's metadata instead of leaking marketing metadata
into login or the app. `index.html` retains a truthful neutral fallback title/description for non-JavaScript clients.
Because this remains CSR, the plan does not claim localized social previews for crawlers that refuse JavaScript.

### Frontend placement

- `frontend/src/pages/about/{ui,model}/**`: route composition and route-scoped metadata lifecycle; no domain logic.
- `frontend/src/app/providers/i18n/resources/{ko,en}/marketing.*`: typed Korean/English marketing and metadata copy,
  per plan 13.
- `frontend/src/app/routes/router.tsx`: public `/about` registration outside the authenticated layout.
- `frontend/src/pages/login/ui/LoginPage.tsx`: localized About link.
- Reuse `features/change-locale`, `features/change-theme`, and `widgets/interface-preferences` when present.
- Reusable document-metadata mechanics may live in `shared/lib`; About-specific strings and section decisions do not.
- About-only sections stay in the page slice rather than speculative shared components or widgets.

There is no Connect contract, server package, SQLite model, migration, or job/state transition.

## Acceptance Criteria

1. An unauthenticated direct visit or refresh at `/about` renders successfully through the static SPA fallback.
2. Mounting `/about` performs no session/API/provider request and does not enqueue or mutate anything.
3. `/about` is structurally outside the authenticated route guard; protected application routes remain protected.
4. `/login` exposes the localized `Postpilot이란? / What is Postpilot?` link without changing login submission,
   generic failures, or safe redirect behavior.
5. The About header contains locale and theme controls plus Login as the page's only product CTA; there is no signup,
   contact, waitlist, or purchase action.
6. Locale initially follows plan 13, changes immediately between complete Korean and English copy, persists by its
   existing rules, and never changes `/about`.
7. Theme initially follows and persists by plan 14, and the page remains correct and AA-compliant in Day and Night.
8. Both locales accurately cover the defined hero, workflow, differentiators, output formats, access limitation, and
   control/privacy facts.
9. Marketing copy makes no unsupported capability, privacy, availability, or performance claim and does not present
   planning or unverified behavior as shipped.
10. Localized title, description, Open Graph text/locale, canonical URL, and `og:url` update on route/locale changes
    and do not leak after navigation away.
11. The page contains no screenshot, generated marketing image, analytics/tracking code, form submission, remote
    font, embedded media, or new third-party request.
12. The page has one H1, logical heading order, semantic ordered steps, labelled controls, visible focus, keyboard
    support, and no colour-only state.
13. At 320 px there is no horizontal page scroll; 360/390/430 px, safe areas, 200% zoom, both themes, and
    Korean/English header widths remain usable.
14. A signed-in visitor may follow Login and be redirected by the existing login guard; About itself does not
    special-case session state.
15. Existing authentication, authenticated navigation, locale, theme, export, and publishing tests remain unchanged
    in meaning.
16. Route, locale, metadata, zero-network, accessibility/responsive, frontend test, lint, FSD/style, and build checks
    pass.

## Policy / Config Impact

Rules that become true when the job lands, to be reflected then rather than pre-written as shipped behavior:

- New `spec/policy/public-marketing.md`: `/about` is public and read-only; allowed capability claims derive from
  shipped SSOT; private/operator-created access and Login-only CTA; no data collection or tracking; localized parity;
  no background API/provider work.
- Update `spec/policy/auth.md`: `/about` is a public SPA route, not a new public Connect procedure. The server's
  public-procedure allowlist remains unchanged.
- Update plan 13's `spec/policy/languages.md`: marketing copy, metadata, and public header are complete in both
  supported locales without locale URLs.
- Update plan 14's `spec/policy/themes.md`: the public header consumes the same browser-local theme preference.
- Update `spec/tech/design-language.md` only if the implemented long-form public-header/section pattern adds a
  genuinely reusable visual rule; no separate marketing tech document is required.

No environment variable or tuning value is introduced. Marketing text, translation keys, section order, metadata
strings, and canonical `/about` are code/content contracts, not deployment config. Canonical origin is derived from
the current document origin.
