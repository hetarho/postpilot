# 11. Post Purpose Presets

> Save reusable *purposes* — what a post is for and how such a post must be written — and let a post pick one so the
> writer produces the right kind of text (an informational sponsored-meal review, not a diary) in the chosen voice |
> Scope: FS | Status: planning

## Purpose

Everything the product learns and injects today is **style**: endings, vocabulary, sentence rhythm, banned phrases,
user rules. Nothing tells the writer what *kind* of text the post is. The result is a recurring failure the owner sees
in practice: a post that is supposed to be a plain informational review — a restaurant visit written in exchange for a
meal, where each photo needs a factual description — comes out as a first-person diary about the day, because the
memo is a diary-shaped list of what happened and the voice profile only governs how sentences sound.

Today the only place to say "this is a review, describe every photo, no diary narrative" is the memo, retyped per
post, or a voice rule, which is the wrong aggregate: the same author uses the same voice for a diary and for a
review, and plan 10 deliberately keeps voices about *how it sounds*, not *what it is for*.

A **purpose** (용도) is a saved, account-owned brief: a name, what the post is for, and the instructions for writing
that kind of post. A post optionally selects one. Generation and AI revision inject the selected purpose's
instructions as the task brief — after the voice profile and before the per-post material — so voice keeps deciding
the register and the purpose decides the genre, structure and required content. This serves PRD goal 1 (a
publish-ready draft in ~3 minutes: no per-post re-explaining) and goal 2 (in *my* voice: the voice profile is untouched)
and directly addresses S1 (읽어보고 한 번 고치기 — the current "it reads like a diary" correction disappears).

## Scope / Non-goals

### In scope

- A `Purpose` aggregate per account: `name`, `description` (what posts of this kind are for), `instructions` (how to
  write them), with create, update, delete lifecycles and an authenticated list/detail.
- An optional `purpose_id` on every post. A post may have no purpose; the server never picks one.
- A purpose selector in the editor's 글 생성 step (next to the voice selector, default 없음) with a link to manage
  purposes; a management screen `/purposes`.
- Prompt injection: the frozen purpose brief enters the write prompt and the revise prompt at one fixed position —
  after the complete voice profile (styleguide → active rules → excerpts → user rules → ending constraint) and before
  the per-post material — with a fixed precedence sentence: the purpose governs content and structure, the voice
  governs how sentences sound.
- Freezing: ordinary generation, both A/B write candidates, and every revision freeze the purpose text at enqueue in
  the job payload / experiment snapshot exactly as target length is frozen today, so a later edit of the purpose never
  changes an in-flight or resumable job.
- Deleting a purpose detaches it from posts (`NULL`) after a confirmation that names how many posts reference it;
  frozen job/experiment snapshots keep the text.
- A migration adding `purposes` and `posts.purpose_id`; existing posts have no purpose.

### Non-goals

- **Learning a purpose.** Finalization learning, rules, evidence, feedback, comparisons and validations remain voice
  learning ([I4]); nothing about a purpose is learned, inferred, or written by a model. A purpose is authored text only.
- **Guessing.** No selection from title, memo, tags, photos, or content. No default purpose; 없음 is the default.
- **Seeded or shipped presets.** No built-in library of purposes; the empty state shows one worked example as copy,
  not as a row. (Shipping a versioned library is the same shape as the recommended model pairing in plan 09 and can be
  a later plan.)
- **Verbatim required text / disclosure footers as a structured field.** A sponsored-review disclosure line belongs in
  `instructions` for now; a first-class "must appear verbatim, post-validated" field is a follow-up once the plain
  brief has proven insufficient.
- **Per-voice purposes, purpose↔voice links, or a purpose inheriting voice data.** Purposes are account-scoped and
  orthogonal to voices; a post combines exactly one voice and at most one purpose.
- **Templates of blocks / fixed outlines**, per-purpose model selection, per-purpose target length or tags, purpose
  version history, soft-delete/restore, import/export of purposes.
- **Changing the memo's role.** The memo stays per-post experience notes; the purpose is the reusable part that used
  to be retyped into it.
- Anything in PRD §8; canonical blocks, browser image work, copy-only export, and no-publish are unchanged
  ([I1], [I2], [I6]).

## Design

### Domain rules and terminology

The user-facing noun is **용도** (`Purpose` in contracts and code). A purpose is an account-owned aggregate with three
authored text fields. `Post` references at most one purpose by id; the reference is a plain nullable pointer, not
ownership — deleting the purpose detaches posts, it never deletes them.

Invariants:

1. every purpose belongs to exactly one account; every RPC derives the account from the session and none accepts a
   user id (as posts and voices);
2. a post has zero or one purpose, and it must belong to the post's account;
3. a prompt uses the purpose frozen at enqueue, never the live row;
4. the voice profile's content, order and injection are byte-identical whether or not a purpose is present — the
   purpose is appended after it;
5. no purpose read, write, selection, or deletion enqueues work or makes a provider call ([I5]).

**Field rules** (validated server-side, mirrored client-side; limits are config, see *Policy / Config Impact*):

| Field | Rule |
|---|---|
| `name` | trimmed, non-empty, ≤ `PurposeNameMaxChars` Unicode chars, unique among the account's purposes (exact match after trim) |
| `description` | trimmed, may be empty, ≤ `PurposeDescriptionMaxChars`; shown in the selector as help text and injected as "이 글의 용도" |
| `instructions` | trimmed, non-empty, ≤ `PurposeInstructionsMaxChars`; the multi-line brief injected verbatim |

### Prompt injection — the one contract this plan adds

`BuildWritePrompt` and `BuildRevisePrompt` gain an optional `*PurposeBrief{Name, Description, Instructions}`. When
present, the **system** prompt (the stable part) is:

```
WritePrompt / RevisePrompt fixed text
[스타일가이드] … [활성 대조 규칙] … [글 예시 발췌] … [사용자 규칙] … [종결어미 제약] …      ← unchanged voice prefix (plan 03/06 order)
[글의 용도: {name}]
이 글의 용도: {description}                                                             ← omitted line when description is empty
작성 지침:
{instructions}
용도는 글의 내용·구성·포함할 정보를 정하고, 문체·종결어미·어휘는 위의 말투 프로필을 따릅니다. 지침이 문체와 충돌하면 말투 프로필을 우선하세요.
```

followed by the unchanged per-post user material (`[이번 글]` 가제 · 메모 · 사진 관찰 / filenames; for revision the
current content, filenames and instruction). Rationale:

- **Order.** PRD §5 requires user rules last *within the profile* and the profile before per-post material. The
  purpose is neither: it is a task brief. Placing it after the whole profile keeps the profile prefix byte-stable
  across posts (the caching note in §5), and placing it before the per-post material keeps it in the stable half —
  every revision of the same post re-injects the identical block.
- **Precedence sentence.** Without it a brief like "정보성 리뷰, 담담하게" quietly overrides a casual voice's endings.
  Voice owns register; purpose owns genre. The sentence is fixed prompt text (code, not config).
- **No purpose → no section.** The prompt for a post without a purpose is byte-identical to today's (snapshot tests
  guard this).

The observe stage is untouched: observation stays facts-only about photos ([I3]); the purpose only reaches the writer.

### Freezing

The purpose is frozen the same way target length is:

- `StartGeneration` and `StartRevision` resolve the post's current `purpose_id` server-side (the request does not
  carry one), load the row, and write `{name, description, instructions}` into the job payload
  (`generation_jobs.payload`, next to `target_length`). A purpose deleted between save and enqueue is simply absent.
- `StartWriteExperiment` puts the same brief into the shared prepared snapshot so both candidates receive
  byte-identical system prompts except for model ref (policy/generation "A/B" rule preserved). The snapshot input
  hash therefore changes with the purpose, which is correct: a different brief is a different experiment.
- Resumed/retried jobs use the payload; they never reload the purpose row.

### Proto / Connect contract

New `proto/postpilot/v1/purpose.proto`:

```proto
service PurposeService {
  rpc ListPurposes(ListPurposesRequest) returns (ListPurposesResponse);
  rpc CreatePurpose(CreatePurposeRequest) returns (CreatePurposeResponse);
  rpc UpdatePurpose(UpdatePurposeRequest) returns (UpdatePurposeResponse);
  rpc DeletePurpose(DeletePurposeRequest) returns (DeletePurposeResponse);
}

message Purpose {
  string id = 1;
  string name = 2;
  string description = 3;
  string instructions = 4;
  int32  post_count = 5;      // posts currently referencing it; shown before delete
  string created_at = 6;
  string updated_at = 7;
}
message CreatePurposeRequest { string name = 1; string description = 2; string instructions = 3; }
message UpdatePurposeRequest { string id = 1; optional string name = 2; optional string description = 3; optional string instructions = 4; }
message DeletePurposeRequest { string id = 1; }
message DeletePurposeResponse { int32 detached_posts = 1; }
```

`UpdatePurpose` uses field presence like `UpdateVoiceProfile`: only supplied fields change, so two fields edited from
two tabs cannot overwrite each other.

`post.proto`:

- `Post` and `PostSummary` gain `PurposeRef purpose` (transport-only `{ id, name }`, unset when none). The list shows
  the purpose name as a secondary badge next to the voice name.
- `SavePostDraftRequest` gains `optional string purpose_id`: omitted = preserve (ordinary autosave patch), present
  empty string = clear, present non-empty = assign. An unknown or foreign id is `InvalidArgument` / `NotFound` — the
  server never substitutes 없음 for a bad id. Unlike `voice_id` it is never required.
- `GenerationJob`'s existing payload projection (if any is exposed) and the write-experiment snapshot projection show
  `purpose_name` so the model lab's comparison detail can say which brief the experiment used.

Generated code is regenerated with `pnpm gen:proto`; generated files are never hand-edited.

### SQLite model and migration

```sql
purposes (
  id           TEXT PRIMARY KEY,
  user_id      TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  name         TEXT NOT NULL,
  description  TEXT NOT NULL DEFAULT '',
  instructions TEXT NOT NULL,
  created_at   TEXT NOT NULL,
  updated_at   TEXT NOT NULL,
  UNIQUE (id, user_id),
  UNIQUE (user_id, name)
)

posts.purpose_id TEXT NULL
FOREIGN KEY (posts.purpose_id, posts.user_id) REFERENCES purposes(id, user_id) ON DELETE SET NULL
```

- The composite FK keeps a post from pointing at another account's purpose even if a service check is bypassed.
- `ON DELETE SET NULL` is the detach; the RPC additionally counts the affected posts inside the same transaction to
  return `detached_posts`. Account deletion keeps its existing full cascade.
- Existing posts get `NULL`; there is no backfill. Job payloads gain an optional `purpose` object; old payloads
  without it decode as "no purpose".
- One embedded goose migration, numbered after plan 10's (expected `0010` if job 18 lands `0009`), SQL regenerated
  with `pnpm gen:sql`, boot-fatal on failure ([I7]). Timestamps follow the fixed-width UTC RFC3339 rule.

### Job and state transitions

No new job kind, stage, status, or queue behavior. The only new state is `posts.purpose_id`, changed by
`SavePostDraft` (assign/clear) and by `DeletePurpose` (detach). Changing a post's purpose:

- is allowed at any status, including `finalized` (it only affects the *next* machine run);
- does not touch content, revision, machine baseline, finalization, or `can_finalize_and_learn` — unlike a voice
  reassignment, because the purpose is not learned from;
- does not affect a running job (its payload is frozen); the editor says so when a job is active.

```
post.purpose_id: NULL ──assign──▶ purpose P ──clear / delete P──▶ NULL
job payload:      frozen {name, description, instructions} at enqueue; never re-read
```

### Frontend behavior and placement

- **`/purposes`** (top-level destination 용도, after 말투 in the nav): list of the account's purposes as cards — name,
  description, `post_count`; create form (name · description · instructions, with live remaining-character counts
  from `shared/config` limits); edit in place using the shared `Editable` primitive per field, read-first as the voice
  screen does; delete with a confirmation that states `n개의 글에서 용도가 해제됩니다`. Empty state shows one worked
  example in copy (e.g. "정보성 식당 리뷰 — 사진마다 무엇인지 설명, 일기체 금지, 방문 정보 표기") and the create
  form; no row is created for the user.
- **Editor step ① (글 생성)**: `features/select-post-purpose` renders a select `용도` next to the voice select:
  options 없음 + the account's purposes; the selected purpose's description under it; a `용도 관리` link to
  `/purposes`. Selecting writes through the existing per-post draft queue as a presence-aware `purpose_id` patch
  (same mechanism plan 10 uses for `voice_id`), so a delayed title save cannot revert a newer selection. While a job is
  active the select stays enabled and the help text says the running job keeps its original purpose. `/posts/new`
  shows the same select; the create request carries `purpose_id` only when one is chosen.
- **Post list**: a small purpose badge beside the voice badge when set.
- **Model lab / experiment detail**: shows `용도: {name}` from the snapshot projection when present.
- **Caches**: query key `(account_id, 'purposes')`; post cache entries carry `purpose`. Create/update/delete
  invalidate the list and patch/invalidate affected post keys; account switches partition as today.

## Acceptance Criteria

1. An authenticated user can create, list, update, and delete purposes. `name` is trimmed, non-empty, bounded, and
   unique within the account (a duplicate is `AlreadyExists` with a Korean message); `instructions` is trimmed,
   non-empty, and bounded; `description` may be empty. No RPC accepts a user id; a foreign purpose id is
   indistinguishable from an unknown one.
2. `UpdatePurpose` changes only the fields present in the request; an update carrying only `instructions` leaves a
   concurrently saved `name` intact (store test).
3. A post can be saved with a purpose, with the purpose cleared, or with the field omitted; omitted preserves the
   current assignment under autosave. An unknown or foreign `purpose_id` is rejected and nothing else in the request is
   applied. Assignment is allowed in every status and changes no content, revision, baseline, or finalization field.
4. Generating a post **without** a purpose produces a write prompt byte-identical to the current one (snapshot test
   unchanged). Generating **with** a purpose appends exactly one `[글의 용도: …]` section after the `[종결어미 제약]`
   section and before `[이번 글]`, containing the description line only when non-empty, the instructions verbatim,
   and the fixed precedence sentence (prompt snapshot).
5. The voice profile portion of the prompt is byte-identical with and without a purpose for the same voice and post
   (test compares the prefix up to the purpose section).
6. Revision of a post with a purpose injects the same section at the same relative position in the revise prompt;
   revision of a post without one is unchanged (snapshots).
7. The purpose is frozen at enqueue: editing or deleting the purpose after `StartGeneration` / `StartRevision` returns
   does not change the prompt the worker builds, including after a restart-resume or explicit retry (test edits the
   row between enqueue and drain).
8. An A/B write experiment started on a post with a purpose gives both candidates byte-identical system prompts that
   include the brief; the experiment detail shows the purpose name; changing the purpose changes the input hash.
9. Deleting a purpose referenced by N posts returns `detached_posts = N`, sets those posts' `purpose_id` to NULL in the
   same transaction, deletes no post or content, and leaves frozen payloads/snapshots intact. Deleting an unreferenced
   purpose returns 0.
10. The migration adds `purposes` and nullable `posts.purpose_id` with the composite account FK; existing posts have
    no purpose and every existing prompt/job/experiment output is unchanged.
11. `/purposes` supports create, read-first per-field edit, and delete with the post-count confirmation, using
    design-system primitives and semantic tokens; the empty state shows the example as copy only and creates no row.
12. The editor's 글 생성 step and `/posts/new` show a `용도` select defaulting to 없음 with the purposes as options and
    a link to `/purposes`; changing it saves through the draft queue and survives a delayed title save; the list shows
    a purpose badge for assigned posts. During an active job the select remains usable and explains that the running
    job keeps its original purpose.
13. Purpose list/detail, selection, page mount, polling, copy, and export make no provider call and enqueue no job.
14. Domain/store/RPC/prompt/payload tests cover validation limits, uniqueness, presence semantics, foreign-id
    rejection, freeze-after-edit, detach counting, and snapshot equality; proto/sql generation checks, backend
    vet/build/tests, frontend tests/lint/FSD/style/build, and spec lint pass without weakening existing assertions.

## Policy / Config Impact

**Rules that become true when the job lands** (to be written into policy then, not before):

- New `spec/policy/purposes.md`: account ownership and no request user id; field rules and limits; presence-based
  update; delete = detach with count; no learning, no guessing, no seeds; no provider call from any purpose surface.
- `spec/policy/generation.md`: the write prompt appends the frozen purpose brief after the complete voice profile and
  before per-post material with the fixed precedence sentence; absence yields an unchanged prompt; ordinary jobs,
  both A/B candidates, and retries use the frozen brief; the A/B snapshot includes it and it participates in the input
  hash.
- `spec/policy/revision.md`: revision re-injects the post's frozen purpose brief at the same position; no purpose
  state is learned or saved as a rule by revision.
- `spec/policy/posts.md`: optional `purpose_id`, presence-aware assign/clear/preserve semantics, assignment allowed in
  every status with no content/baseline effect, detach on purpose deletion, list projection.
- `spec/policy/voice.md`: one clarifying sentence — voice profiles are never modified by, and never contain, purpose
  text; the purpose is not part of `ProfileForPrompt`.
- `spec/tech/`: no new document. The injection position and precedence are recorded in this plan and, once shipped, in
  policy/generation; a separate tech doc would only restate them.
