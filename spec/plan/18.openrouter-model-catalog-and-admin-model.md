# 18. OpenRouter Model Catalog and Admin Model Management

> The supported-model list lives in the database, curated by a master-plan operator on the 모델 관리 tab of
> `/admin`: the live OpenRouter catalog is browsed (featured providers first, search + filters, virtualized) on
> **five purpose tabs** (사진 해석 · 문체 분석 · 글 작성 · 이미지 생성 · 비디오 생성; change 20), and a model checked
> on a tab is selectable for exactly that purpose. `providers.yaml` keeps the provider connection and the
> recommendation sets. | Scope: FS | Status: done (jobs 46, 48)

## Purpose

The twelve usable models used to be hardcoded data in `backend/config/providers.yaml`: adding, retiring, or
re-pricing a model was a repo edit plus an image rebuild and restart. OpenRouter publishes its full catalog
(~420 models, with capabilities and pricing) through a public API, so the file was a hand-maintained shadow of data
the source already serves. Meanwhile the operator had no in-product surface for the decision that file encoded —
*which models are worth exposing at all*.

This plan makes model curation a product feature: the catalog of *candidate* models comes live from OpenRouter, the
catalog of *usable* models is database rows an operator checks on a management screen, and the change takes effect
without a deploy. It also settles the registry's shape: **OpenRouter is the single provider** — every LLM call goes
through the one `openai_compatible` OpenRouter entry, and the yaml keeps only connection config (base URL, key env,
reasoning dialect) plus plan 09's recommendation sets. The vendor-neutral `internal/llm` port and its boundary are
unchanged (PRD §6.4, ARCHITECTURE §2.1).

## Scope / Non-goals

**In scope**

- A `catalog_models` table owning the usable-model list: id, provider slug, label, capability flags, context/pricing
  snapshot, the source's **reasoning capability** (change 27), optional `reasoning_effort` override, and
  source-availability bookkeeping — with per-purpose registrations in `catalog_model_purposes` (change 20; the
  original `enabled` flag shipped here and was retired by migration `0020`).
- A server-side OpenRouter catalog client (`GET {base_url}/models`, unauthenticated, plain HTTP) with an in-memory
  TTL cache and explicit operator-triggered refresh. The user-facing path never calls it.
- `ModelCatalogService` (master-only, same interceptor list as `AdminService`): browse the merged
  live-catalog + DB state, register/deregister a model per purpose (change 20), edit its reasoning override, force
  a refresh.
- `/admin` restructured into routed tabs — 계정 관리 (the existing user-plan table) and 모델 관리 (new). The header
  entry the master already sees keeps pointing at `/admin`.
- Catalog browsing UX: featured providers (OpenAI · Anthropic · Google · DeepSeek · Z.AI · MiniMax · Meta …) sorted
  to the top in a config-owned order, case-insensitive search over model id/name, filters by provider, capability
  (vision / structured output), and registered-only — all client-side over one response, over a **virtualized**
  list, on each of the five purpose tabs.
- `internal/llm` resolves models through an injected dynamic source backed by those DB rows, so an operator change
  applies to dropdowns, `SaveSelection`, and `Complete` capability checks without a restart. Boot neither contacts
  OpenRouter nor fails on an empty model list.
- Migration seeding the twelve then-shipped yaml models (labels, flags, metadata, `reasoning_effort`) so existing
  saved selections and behavior survive the cutover unchanged.
- `providers.yaml` schema change: provider entries lose their `models:` list (strict parse makes a leftover loud);
  recommendation sets stay in the file, their refs now validated at **apply time** against the DB registry.

**Non-goals**

- No second provider entry, direct-vendor adapter (`anthropic` SDK path), or BYOK — OpenRouter 단일화 is the decision
  this plan records, enforced at boot. A future non-OpenRouter provider reopens the yaml design, not sneaks past it.
- No automatic model curation: new OpenRouter models are never auto-enabled, vanished ones are never auto-disabled,
  and nothing is auto-selected for users ([I3]).
- No scheduled/background sync loop; source availability is only re-judged when an operator loads or refreshes the tab.
- No persistence of the full OpenRouter catalog — only operator-touched models get rows.
- No per-user or per-plan *catalog*: the registered set is global, and what one account may **afford** is a
  separate question owned by [plan 17](17.plan-based-authorization-and-usage-quota.md).
- No change to selection-memory semantics, A/B slots, the usage ledger, or billing.
- Pricing stays display/estimate metadata; reported provider cost still wins (plan 09 rule).

## Design

### The catalog has two layers

1. **Candidates** — the live OpenRouter list, fetched server-side from
   `GET {base_url}/models?output_modalities=text,image,video` (the same `base_url` the provider entry already
   declares; the endpoint is public, no key needed). The query is required, not optional: the endpoint serves
   text-output models only by default, so without it no video model and only half the image models are visible at
   all ([tech/openrouter-catalog](../tech/openrouter-catalog.md)). Cached in process memory for
   `OPENROUTER_CATALOG_TTL`; an operator's 새로고침 bypasses the cache. This layer is *never* stored and *never*
   serves a user-facing request.
2. **Usable models** — `catalog_models` rows with their `catalog_model_purposes` registrations. A row exists once
   an operator has registered a model anywhere (rows are kept on full deregistration so the reasoning override
   survives re-registering). Only this layer feeds `ListModels`, `SaveSelection`, and `Registry.Complete`, and only
   through the stage its purpose projects onto.

Field mapping from an OpenRouter model object (contract details in
[tech/openrouter-catalog](../tech/openrouter-catalog.md)): `id` → `model_id` (keeps the
`provider-slug/model-slug` shape; `ModelRef` stays `{provider_id: "openrouter", model_id}` so `model_selections`
rows and job records are untouched) · `name` → `label` · `"image" ∈ architecture.input_modalities` → `vision` ·
`"image"|"video" ∈ architecture.output_modalities` → `image_output`|`video_output` (change 20) ·
`"structured_outputs" ∈ supported_parameters` → `structured_output` · `context_length` → `context_tokens` ·
`pricing.prompt|completion` (USD per token, decimal strings) × 10⁶ → `input|output_usd_per_million`, with
`pricing_checked_at` set to the fetch time · the id's segment before the first `/` → `provider_slug` (grouping and
filter key only, not a `ModelRef` field).

### Data model — migration `0018_catalog_models.sql`

```sql
catalog_models (
  model_id          TEXT PRIMARY KEY,            -- OpenRouter id, e.g. "openai/gpt-5.6-sol"
  provider_slug     TEXT NOT NULL,               -- "openai"; derived at write, kept for filtering
  label             TEXT NOT NULL,
  vision            INTEGER NOT NULL,
  structured_output INTEGER NOT NULL,
  context_tokens    INTEGER,                     -- nullable metadata, refreshed on operator refresh
  input_usd_per_million  TEXT,                   -- decimal strings, same display-only status as plan 09
  output_usd_per_million TEXT,
  pricing_checked_at TEXT,
  reasoning_effort  TEXT CHECK (reasoning_effort IN ('unset','none','minimal','low','medium','high','xhigh','max')),
  image_output      INTEGER NOT NULL DEFAULT 0,  -- added by 0020: architecture.output_modalities snapshot
  video_output      INTEGER NOT NULL DEFAULT 0,
  listed            INTEGER NOT NULL DEFAULT 1,  -- still present in the source catalog at the last successful refresh
  last_seen_at      TEXT,
  created_at        TEXT NOT NULL, updated_at    TEXT NOT NULL
)

catalog_model_purposes (                         -- added by 0020 (change 20): the registrations
  model_id   TEXT NOT NULL REFERENCES catalog_models(model_id) ON DELETE CASCADE,
  purpose    TEXT NOT NULL CHECK (purpose IN
               ('photo-analysis','style-analysis','writing','image-generation','video-generation')),
  created_at TEXT NOT NULL,
  PRIMARY KEY (model_id, purpose)
)
```

- The migration **seeds the twelve then-shipped yaml models** verbatim (label, flags, metadata, and
  `anthropic/claude-sonnet-5`'s `reasoning_effort: unset`), so the cutover changed nothing a user could see and no
  saved selection was cleared by it.
- `reasoning_effort` keeps yaml's strict override semantics (moved onto the registration by job 52, see below):
  `NULL` → stage policy decides; `unset` → the wire key is
  omitted; anything else is sent. The CHECK mirrors the boot validation the yaml used to give.
- `listed`/`last_seen_at` are bookkeeping written only by a successful refresh — a failed or stale fetch changes no
  row, so user-facing availability never depends on OpenRouter being reachable at read time.
- Migration `0018` also created a `min_plan` column, which [change 19](../changes/archive/19.credit-metering-and-open-model-access.md)
  dropped in `0019` when the per-model plan floor was retired; `0018`'s `enabled` column was likewise replaced by
  `catalog_model_purposes` in `0020` (change 20). A migration is a historical record and is never rewritten; the
  current column set is the list above.

### Registry — `internal/llm` gets a dynamic model source

- `llm.Load` parses `providers.yaml` for **connection config** (provider id, adapter, `base_url`, `api_key_env`,
  `reasoning_format`) and `recommendation_sets`; the per-provider `models:` list left the schema, and strict parsing
  turns a leftover key into a boot failure (a stack that mounts an old override file must hear about it). Exactly
  one provider may be declared — the curated catalog has no provider dimension.
- The registry's model list comes through an injected port, `llm.ModelSource` (`Models() []SourceModel` ·
  `Lookup(modelID) (SourceModel, bool)`), replacing the parsed yaml slice. `cmd/api` injects the implementation, so
  the dependency arrow points *into* `llm` and the boundary test's "nothing above llm learns the vendor" stands.
  The registry attaches its own provider id to every ref it publishes.
- The implementation is the new context's `Service`, which holds the registered rows in memory (a row with zero
  purpose registrations is excluded) and invalidates on every curation write — one process, one SQLite writer, so a
  registration change is visible to the very next RPC without a restart. `SourceModel`/`ModelInfo` carry `Stages`,
  the purposes projected onto the user-facing stages (photo-analysis → observe · style-analysis → analyze ·
  writing → write; the generation purposes project onto none), as opaque strings the llm boundary passes through.
  `Resolve`/`Complete` answer from the row: a missing, unregistered row is `ErrModelUnavailable`; a provider with no
  key disables every model with `DisabledReasonNoKey`; a delisted row disables with `DisabledReasonDelisted` (the
  no-key reason wins, being the wider problem).
- Boot no longer knows the model list: an empty `catalog_models` is a *valid* state (fresh install) — pickers show
  an empty catalog and the operator must enable models; the process does not exit over it. Boot still never contacts
  OpenRouter. `llm.Load` therefore runs after `db.Open`/`db.Migrate`, still before the listener exists, so the
  deploy's `/health` gate keeps its rollback.
- Recommendation sets ([plan 09](09.stage-model-experiments-and-leaderboards.md)) can no longer be existence-checked
  at boot (the referent is now mutable data), so `ApplyRecommendationSet` validates all nine refs against the DB
  registry **at apply time** — unknown, disabled and stage-unsuitable refs are collected into one `SetRefusal`
  naming every offender, grouped by cause. Boot keeps shape validation. A `cmd/api` test asserts every shipped
  recommendation ref names a model the seed migration inserts, replacing what boot used to catch.

### Contract — `proto/postpilot/v1/model_catalog.proto`

```
service ModelCatalogService {                       // every procedure master-only via the interceptor list
  rpc ListCatalog (ListCatalogRequest) returns (ListCatalogResponse);  // merged candidates + DB state
  rpc SetModelPurpose (SetModelPurposeRequest) returns (SetModelPurposeResponse);  // change 20
  rpc UpdateModel (UpdateModelRequest) returns (UpdateModelResponse);  // partial: reasoning_effort
}
message ListCatalogRequest  { bool refresh = 1; }   // true bypasses the server cache (새로고침)
message CatalogEntry { string model_id = 1; string provider_slug = 2; string label = 3; string description = 4;
                       bool vision = 5; bool structured_output = 6; int64 context_tokens = 7;
                       string input_usd_per_million = 8; string output_usd_per_million = 9;
                       bool curated = 10; reserved 11;  // enabled (change 20)
                       reserved 12;                     // min_plan (change 19)
                       bool listed = 13; string reasoning_effort = 14; int64 source_created_at = 15;
                       repeated string purposes = 16;   // registration slugs (change 20)
                       bool image_output = 17; bool video_output = 18; }
message SetModelPurposeRequest  { string model_id = 1; string purpose = 2; bool registered = 3; }
message ListCatalogResponse { repeated CatalogEntry entries = 1; string fetched_at = 2; bool from_cache = 3;
                              string fetch_error = 4; }  // fetch_error set ⇒ entries carry DB rows only
message UpdateModelRequest  { string model_id = 1; reserved 2, 3;  // enabled (change 20) · min_plan (change 19)
                              optional string reasoning_effort = 4; }          // "" clears the override
```

- `ListCatalog` merges: every live candidate (annotated with its DB state if a row exists) **plus** every DB row no
  longer in the live list, which comes back `listed = false` — that is the 제공 종료 badge. When the live fetch
  fails, `fetch_error` is set and the answer degrades to DB rows only; the operator screen says so instead of
  showing an empty catalog. A successful **non-cached** read also writes the availability bookkeeping; a cached one
  writes nothing, having bought no new evidence.
- `SetModelPurpose` registers or deregisters one (model, purpose) pair. It validates the model exists in the
  current live catalog **or** already has a row (re-registration works offline), refuses otherwise (`NotFound`),
  refuses an unknown purpose (`InvalidArgument`) and a model failing the purpose's capability gate
  (`FailedPrecondition`, `MODEL_PURPOSE_INELIGIBLE`) — photo-analysis needs `vision`, the generation purposes need
  the matching output modality. Registering snapshots label/flags/metadata from the live entry; deregistering keeps
  the row, so the reasoning override survives.
- `UpdateModel` refuses an unknown row (`NotFound`) and an invalid `reasoning_effort` (`InvalidArgument`). Absent
  fields are not edits, so two operators changing different properties of one model do not overwrite each other.
- The user-facing `ProviderService.ListModels` serves the rows registered to at least one **stage** purpose (a
  generation-only registration never crosses the user wire), each `ModelInfo` carrying `repeated Stage stages` so
  every picker filters by membership instead of re-deriving fitness from capability flags. A row with
  `listed = false` is served **disabled** with the 제공 종료 reason, which drops it into the existing
  greyed-with-reason rendering, `SaveSelection` refusal, and saved-selection clearing machinery with no new FE
  logic.
- Nothing new crosses to the browser beyond ids, labels, flags, and display metadata — still no key and no base URL.

### Operator surface — `/admin` is routed tabs

- `/admin` (the user-plan table, now the 계정 관리 tab) and `/admin/models` (모델 관리), both under the existing
  master-only `beforeLoad` guard; the tab bar follows the routed-tab pattern `/voice` established. The
  `widgets/account-menu` entry keeps pointing at `/admin`; its copy became 운영 관리, the frame over both tabs.
- 모델 관리 tab behavior:
  - **Five purpose tabs** (사진 해석 · 문체 분석 · 글 작성 · 이미지 생성 · 비디오 생성, a `SegmentedControl`
    tablist in the `MODEL_PURPOSES` order; change 20). Each tab registers models for its purpose only, and
    **force-filters** its candidates to the purpose's capability gate before every operator filter — 사진 해석
    lists vision-input models, 이미지/비디오 생성 list matching output-modality models, the text tabs list all. An
    empty gate renders an explanatory empty state rather than an error.
  - Full merged catalog in one response, rendered with **featured providers first** in the
    `FEATURED_MODEL_PROVIDERS` config order, remaining providers alphabetically, models within a provider by
    `source_created_at` descending (newest first).
  - Search (substring over id + label, case-insensitive), provider filter, capability filters (vision / structured
    output), and an "enabled only" filter — all client-side over the one response.
  - **The list is virtualized** (`@tanstack/react-virtual`, `useWindowVirtualizer`): the unfiltered catalog is
    several hundred rows, and mounting them all made every keystroke re-render hundreds of subtrees. It virtualizes
    the **window** rather than a scroll container of its own, because a nested `overflow-y-auto` would steal every
    vertical swipe that lands in it (design-language §4.4); the page stays the one scroller and the list reserves
    its height. `scrollMargin` carries the list's own offset, and row heights are measured — an enabled row is much
    taller than a plain one — with a zero measurement falling back to the estimate rather than collapsing the list.
  - Each row: label + id, capability badges (vision/structured/image/video output), context tokens, $/1M in·out, a
    list of the purposes the model is registered to elsewhere, and — per the no-native-select rule — an app-drawn
    checkbox for **the active tab's purpose**. A row registered anywhere exposes the shared reasoning-override
    Listbox (단계 기본값 · unset · none … max).
  - A row that is `listed = false` shows the 제공 종료 badge and a per-tab warning banner counting such rows,
    prompting the operator to disable them; nothing is disabled automatically.
  - 새로고침 calls `ListCatalog(refresh: true)`; the response's `fetched_at`/`from_cache`/`fetch_error` render as a
    status line. A standing line above the tabs states that deregistering a model clears it from the selections of
    everyone who had chosen it for that purpose — once, before anything is pressed, rather than on every row.
  - All copy lands in the ko/en i18n resources (plan 13).

## Acceptance Criteria

1. A master-plan user reaches 계정 관리 and 모델 관리 as tabs of `/admin`; a non-master is redirected by the route
   guard, and every `ModelCatalogService` procedure is refused server-side with `MASTER_ONLY` regardless of client.
2. The 모델 관리 tab shows the live OpenRouter catalog merged with DB state on five purpose tabs, each
   capability-force-filtered (사진 해석 → vision input · 이미지/비디오 생성 → matching output modality): featured
   providers first in the configured order, then the rest alphabetically, newest models first within a provider;
   search and the provider/capability/registered filters narrow the list client-side.
3. Registering a model to a purpose makes it appear in exactly that purpose's stage dropdown — the generation
   purposes feed no user-facing surface yet — **without a process restart**; deregistering removes it and the
   existing vanished machinery greys the stranded selection once and clears it per current policy. The server
   enforces the purpose capability gate and per-stage membership (`SaveSelection`, pairs, `Registry.Complete`).
4. The user-facing catalog (`ListModels`, `SaveSelection`, `Registry.Complete`) is served entirely from
   `catalog_models`; no user-path request contacts OpenRouter, and an OpenRouter outage changes nothing for users.
5. However long the catalog is, the operator list mounts only the rows near the viewport, and the page keeps its own
   single scroller; search and the filters still reach every model, including ones never mounted.
6. An operator refresh re-snapshots label/context/pricing (`pricing_checked_at` updated) for enabled rows and marks
   rows absent from the live list `listed = false`: they badge as 제공 종료 in admin, serve as disabled-with-reason
   to users, and are never auto-disabled.
7. When the OpenRouter fetch fails, `ListCatalog` degrades to DB rows plus a visible fetch error, and no
   `listed`/metadata bookkeeping is written; a cached snapshot writes none either.
8. The migration seeded the twelve then-shipped models with their labels, flags, metadata and the
   `claude-sonnet-5` `unset` override; existing accounts' saved selections survived the cutover with no clearing and
   identical generation behavior.
9. `providers.yaml` carries only provider connection config and recommendation sets; a `models:` key or a second
   provider fails boot; an empty `catalog_models` boots fine and renders an empty user catalog; boot never calls
   OpenRouter.
10. `ApplyRecommendationSet` validates all nine refs against their stage's purpose registrations at apply time and
    refuses with every offending ref named (unknown / disabled / not registered to the stage's purpose), grouped by
    cause, in one answer.
11. The per-model reasoning override round-trips through an operator edit: `NULL` defers to stage policy, `unset`
    omits the wire key, an explicit value is sent — verified at the adapter seam.
12. Boundary intact: no package above `internal/llm` imports an adapter/SDK; the OpenRouter catalog client is plain
    HTTP inside `internal/modelcatalog`; no API key or base URL reaches the frontend.

## Policy / Config Impact

**Policy — landed in [`spec/policy/providers.md`](../policy/providers.md):**

- "The registry is a file" became **"the connection is a file, the models are rows."** The one provider entry and
  the recommendation sets stay in `backend/config/providers.yaml`; the usable-model list, capability flags, catalog
  metadata and reasoning overrides live in `catalog_models`, curated only through the master-only
  `ModelCatalogService`.
- Candidate models come from OpenRouter's public models endpoint, fetched server-side and cached; users are never
  served from the live fetch, and availability bookkeeping is written only by a successful operator-driven read.
- Enabling never selects ([I3]); disabling flows into the existing vanished-selection clearing; a source-delisted
  model is flagged, disabled-with-reason for users, and cleaned up by an operator — never automatically.
- Recommendation-set refs are validated at apply time against the DB registry, and a refusal names every offender
  grouped by cause; boot keeps shape validation only.

## As-built note — the catalog read is modality-scoped

Job 48 first shipped the purpose tabs while still reading the catalog with a bare `GET {base_url}/models`, on the
mistaken belief that OpenRouter published almost no video models. It publishes **28**; the endpoint simply
**defaults to text-output models only**, so the video tab could never have a candidate and the image tab saw only
the 11 models that also answer in text. The read now carries `?output_modalities=text,image,video`, and the
pricing mapping became modality-aware: a video model's `"0"` token prices are recorded as *unknown* rather than
free, and an image-only model is priced from `image_token`/`image_output`. The contract, the measured counts and
the `image_output` unit discrepancy are in [tech/openrouter-catalog](../tech/openrouter-catalog.md).

## As-built extension — job 52 / change 24

The operator's `reasoning_effort` moved off `catalog_models` and onto the **registration**
([changes/archive/24](../changes/archive/24.bound-the-write-completion-budget-and-ma.md)). Everything this plan says
about the column's semantics still holds; what changed is where it lives and how many of them there are.

- **One effort per (model, purpose)**, on `catalog_model_purposes` (whose PK was already `(model_id, purpose)`),
  with the same value CHECK. `catalog_models.reasoning_effort` is dropped, and migration 0021 deliberately copies
  nothing forward — including this plan's seeded `anthropic/claude-sonnet-5: unset` — so every curated model returns
  to the code-owned stage policy. Carrying the values forward would have propagated one blanket setting into five
  purposes each.
- **`ListCatalog` is read per purpose.** The request names the tab; each entry reports the effort for THAT purpose
  and carries that purpose's stage spend signal. `UpdateModel` names the purpose it applies to and is refused
  server-side for one the model is not registered to — previously a UI rule (the control only appeared once
  registered), now a server rule. The row's Listbox appears on a tab only when the model serves it.
- **A spend signal sits beside the control.** `ListCatalog` attaches the recent reasoning-vs-completion split per
  model for the listed purpose's stage, read from the usage ledger through a consumer-declared port wired in the
  composition root — this context still never reads `usage_events`. The adapter translates the key, because the
  ledger records the registry ref (`openrouter/z-ai/glm-5.3-flash`) and a catalog row is the provider-local id. A
  model with no recorded call for that stage carries nothing rather than a zero.
- **`Model.Reasoning` became a map** keyed by purpose, and `stageReasoningOf` projects only REGISTERED purposes onto
  the llm boundary's stage names — an effort on a purpose the model no longer serves cannot reach a stage, and the
  two generation purposes still map to none.

## As-built extension — job 55 / change 27

The catalog now records what the source **publishes about each model's reasoning**, and the operator's effort
override is bounded by it ([changes/archive/27](../changes/archive/27.persist-catalog-reasoning-capabilities-a.md)).
Nothing about where the override lives changes — that is job 52's extension above — only what values it may hold.

- **Six snapshot columns on `catalog_models`** (migration `0024`): `reasons`, `reasoning_efforts` (a JSON array in
  the source's descending order, because that order is the order a selector offers), `reasoning_default_effort`,
  `reasoning_mandatory`, `reasoning_native_effort` and `reasoning_max_tokens`. They are written by the same
  successful fetch that already writes the label, the flags and the pricing; a failed fetch writes nothing. Nothing
  is backfilled and no boot-time fetch is added.
- **A falsy value is UNKNOWN, never "supports nothing"** — the rule the pricing columns already follow. A model
  whose accepted values the source does not publish (273 of 427, measured 2026-09-05) keeps being offered all eight.
- **The override is validated against the model.** `SetModelReasoning` refuses an effort outside a published list,
  refuses `none` when reasoning is mandatory or when a published list omits it, and refuses any effort on a model
  the source *confirms* does not reason. The control's option filtering is an affordance; this is the contract.
  `deepseek/deepseek-v4-pro-0813` accepts `max·high·low` and not `medium`, and is disable-able yet lists no `none` —
  which is the shape that let the app's own "turn it off" value be one that model does not take.
- **`unset` is labelled with the model's own default**, because `unset` omits the wire key and therefore means the
  model's default (`high` on deepseek, `medium` on gemini-3.8-flash) rather than "off".
- **Drift is a warning, never a correction.** An override the source would refuse today is kept and still sent, with
  a warning on the admin row — the same posture `listed = false` carries. Drift is derived at read time as "this
  value would be refused if it were written now", so it cannot fall out of step with the acceptance rule.
- **A seventh, unstored wire field: `reasoning_known`.** The six cannot say whether anything read them — `reasons =
  0` with no list is both "publishes no reasoning object" and "nothing has asked yet", which is what migration 0024
  leaves every existing row saying, and what every row says while the fetch is failing. A live candidate is known by
  construction; a stored row is known only if it says something. An unknown capability behaves exactly as the
  catalog did before this change, so a provider outage never removes a control whose stored value is still sent.
- **No generation path changes.** `internal/llm` is untouched, `llm.SourceModel` carries none of this, and the
  provider request body is byte-identical. `reasoning_native_effort` is stored for
  [change 29](../changes/29.give-the-write-budget-reasoning-headroom.md), which is what will consume it.

Config: no new value. The eight-value list in `frontend/src/entities/model-catalog/model/types.ts` stays where it is
and becomes the **fallback** for a model with no published list, rather than the whole truth.
