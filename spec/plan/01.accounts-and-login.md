# 01. Accounts and Login

> Operator-created accounts, id + password login, 30-day HttpOnly cookie sessions, and the SQLite persistence
> foundation they stand on | Scope: FS | Status: built (jobs 01 · 02)

## Purpose

postpilot is exposed on the public internet but serves exactly two people (PRD §1). Every other feature — posts,
photos, the voice profile, generation jobs — is scoped to an account, so identity is the first thing that has to be
true (PRD §10: steps 1–2 must land before anything else has a place to attach).

The product problem is narrow but real: a month-long session that lives on a phone (S1, "저녁에 폰으로") must not be
stealable through XSS, and the login form must not reveal which ids exist. There is deliberately no signup: a
two-person tool gains nothing from an open registration surface (PRD F-1).

This plan also lands the persistence foundation (SQLite + embedded goose migrations + sqlc) because `users` and
`sessions` are the first tables — the mechanism is the substance of invariant [I7].

## Scope / Non-goals

**In scope**

- `Login` / `Logout` / `GetMe` RPCs; session issue, validation, revocation.
- Session transport as an HttpOnly cookie; the auth interceptor that turns a missing/invalid session into 401.
- CORS with credentials against exactly one origin.
- Timing-equalized login (dummy argon2id verification when the id does not exist).
- Operator account provisioning — the only way to create an account.
- Persistence foundation: `internal/platform/db` (modernc SQLite, WAL, single serialized writer), `//go:embed`-ed
  goose migrations run at boot, sqlc query generation, and migration `0001` (`users`, `sessions`).
- FE: login page, credentialed Connect transport, 401 → redirect, route guard.

**Non-goals**

- Signup UI or RPC (PRD F-1: 가입 화면 없음 — by design, not by omission).
- Password change / reset flows. The PRD does not define one; the operator recreates the account with server-side
  tools. Flagged as a PRD gap, not silently filled.
- Roles, permission tiers, organizations, 3+ users (PRD §1 비목표).
- OAuth / social login, MFA, IP-based rate limiting (2-user scale; timing equalization is the required defense).
- Sliding session renewal — the PRD fixes 30 days; sessions expire 30 days after login.

## Design

### Contract — `proto/postpilot/v1/auth.proto`

```
service AuthService {
  rpc Login  (LoginRequest)  returns (LoginResponse);   // sets the session cookie via the HTTP response header
  rpc Logout (LogoutRequest) returns (LogoutResponse);  // revokes the session row, clears the cookie
  rpc GetMe  (GetMeRequest)  returns (GetMeResponse);   // session probe for app boot; 401 when no session
}
message LoginRequest  { string login_id = 1; string password = 2; }
message LoginResponse { User user = 1; }
message GetMeResponse { User user = 1; }
message User          { string id = 1; }
```

The session token travels **only** in the cookie. It never appears in a response body, log line, or URL. The
`Login` handler sets the `Set-Cookie` header on the HTTP response (Connect handlers may set response headers);
`Logout` sets the same cookie with `Max-Age=0`.

### Sessions

- Token: 32 bytes from `crypto/rand`, base64url in the cookie. The DB stores `hex(sha256(raw_token))` as
  `sessions.token` (PK) — a leaked DB does not yield usable cookies (PRD §5). A plain sha256 rather than a KDF: the
  input is already 256 bits of uniform randomness, so there is nothing to brute force and no reason to pay argon2
  on every request.
- `expires_at = login_time + 30d`, fixed. Lookup on every RPC compares against `now`. Timestamps are stored as
  **fixed-width** RFC3339 in UTC (`2006-01-02T15:04:05.000000000Z07:00`): `expires_at < ?` is a plain string
  comparison in SQL, and `time.RFC3339Nano`'s trimmed fraction would sort `…08.5Z` after `…08.513110616Z`.
- `Logout` deletes the row. Expired rows are deleted on the failed lookup that finds them and swept once at boot.
- Cookie, exactly (PRD F-1):

  ```
  Set-Cookie: pp_session=<token>; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=2592000
  ```

  No `Domain` attribute (host-only) — a `Domain` would leak the cookie to sibling projects on the same registered
  domain. `SameSite=Lax` is sufficient because `postpilot.<domain>` and `api.postpilot.<domain>` are same-site.

### Login and timing equalization

1. Look up `users` by `login_id`.
2. If absent, run `argon2id.Verify(password, DUMMY_HASH)` against a valid argon2id hash whose password nobody
   knows, so the "unknown id" path costs the same as the "wrong password" path. Then fail. `DUMMY_HASH` is
   **derived at boot**, not hardcoded and not built lazily: a literal would freeze today's cost parameters (and
   drift cheaper the day they are raised), and deriving it on first use would make that first unknown-id probe pay
   two derivations instead of one — a timing signal in exactly the direction the dummy exists to erase.
3. If present, verify against `password_hash`. On mismatch, fail.
4. Both failures return the same generic message (`invalid credentials`) with the same Connect code
   (`Unauthenticated`). A stored hash that will not parse takes the same path (logged, then answered as a wrong
   password) — including out-of-range cost parameters, which `argon2.IDKey` answers with a panic rather than an
   error, so they are rejected during decode.
5. An infrastructure failure (store unavailable) is **not** collapsed into `invalid credentials`; it is
   `CodeInternal`, so an outage never masquerades as a typo.

Password hashing: `golang.org/x/crypto/argon2` `IDKey` with `time=3`, `memory=64 MiB`, `parallelism=2`, 16-byte
salt, 32-byte key, stored in PHC string form (`$argon2id$v=19$m=...,t=...,p=...$<salt>$<hash>`) so parameters can be
raised later without a schema change. Plaintext or unsalted hashes are forbidden (PRD F-1).

### Interceptor and CORS

- The Connect interceptor lives in **`internal/auth/rpc`**, not `platform/rpcserver`: deciding who the acting user
  is has business meaning, and `platform/` is for code that has none (ARCHITECTURE §2.1). `rpcserver.New` takes
  `Options{Interceptors, Handlers}` instead, so each context registers its own service and its own interceptors and
  `rpcserver` never imports a context.
- It reads `pp_session`, hashes it, loads the session, checks expiry, and injects the user id into
  `context.Context`. Any failure → `connect.CodeUnauthenticated` (HTTP 401). Downstream contexts read the user id
  from the context and never re-derive it. It is a full `connect.Interceptor` (not `UnaryInterceptorFunc`, whose
  `WrapStreamingHandler` is a pass-through) so the first streaming procedure added later cannot ship unauthenticated.
- Exactly three procedures are public, listed in one map (`publicProcedures`): `AuthService/Login`,
  `AuthService/Logout`, and `HealthService/Ping`. **Logout is public** because the cookie is HttpOnly — answering
  401 to an already-expired session would leave that cookie stranded in the browser for its full 30 days with
  nothing able to remove it, and revoking a dead session is a no-op anyway. The plain `/health` endpoint is mounted
  outside the Connect stack and is likewise open.
- CORS middleware: `AllowedOrigins = [CORS_ORIGIN]` (exactly one), `AllowCredentials = true`, Connect's required
  headers allowed and exposed. Config validation rejects **any** `*` in the origin, not just a bare wildcard:
  `rs/cors` reads an embedded `*` as a pattern (`https://*.example.com`) and would reflect any matching subdomain
  with credentials — the same sibling-domain leak the cookie avoids by carrying no `Domain`.
- FE transport (`shared/api`): connect-web has **no `credentials` option**, so the opt-in rides on a fetch wrapper —
  `createConnectTransport({ baseUrl, fetch: (input, init) => fetch(input, { ...init, credentials: 'include' }) })`.
  The same transport carries an interceptor that turns a 401 on any procedure except `Login` into an app-wide
  "session lost" event (`shared/api/auth-events`), which `app/providers/auth-redirect` turns into a navigation.

### `adduser`

- `adduser <login_id>` reads the password from stdin (twice, must match), hashes it with the same argon2id
  parameters, inserts the `users` row. A duplicate id exits non-zero with a clear message. On a TTY the password is
  read with echo off; piped input is read **line by line** (not whitespace-tokenized), so a passphrase with spaces
  survives `docker compose run -T`.
- It ships as a **subcommand of the api binary**, not a second binary in the image: `cmd/api` dispatches
  `os.Args[1] == "adduser"` into `internal/auth/provision`, so `docker compose run --rm api adduser <id>` works
  against the deployed image with its `ENTRYPOINT ["/api"]` unchanged. `cmd/adduser` is a thin wrapper over the
  same package for host-side `go run ./cmd/adduser <id>` during development. Details of the image layout belong to
  `DEPLOY.md`.
- It opens the same SQLite file as the api (same `DB_PATH`) and runs pending migrations first, so it works on a
  fresh volume.

### Persistence foundation (lands with this plan)

- `internal/platform/db`: opens `modernc.org/sqlite` (pure Go — [I6]/[I7] depend on staying CGO-free) with
  `journal_mode=WAL`, `foreign_keys=ON`, `busy_timeout`. Exposes one **serialized write connection** and a read pool
  (ARCHITECTURE §2.4). Contexts get the handle injected from `cmd/api`; they never open their own.
- Migrations: SQL files under `internal/platform/db/migrations/`, `//go:embed`-ed, applied by goose in `cmd/api`
  **before** the server listens. A failure logs and exits non-zero; the container never reports healthy; the deploy
  gate rolls back to the previous image ([I7], `DEPLOY.md` §2). No migration container, no manual step.
- sqlc: per-context `queries/*.sql` compiled into per-context store packages, configured in `backend/sqlc.yaml` and
  run as a Docker step (`pnpm gen:sql`). Its **schema input is the migrations directory**, so the generated types
  cannot drift from the schema that actually runs at boot. Generated code is committed, never hand-edited
  (ARCHITECTURE §1).
- Migration `0001` (PRD §5):

  ```sql
  users     (id TEXT PRIMARY KEY, password_hash TEXT NOT NULL, created_at TEXT NOT NULL)
  sessions  (token TEXT PRIMARY KEY,                       -- sha256 hex of the raw token
             user_id TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
             expires_at TEXT NOT NULL, created_at TEXT NOT NULL)
  index sessions(user_id), sessions(expires_at)
  ```

  Later plans add their own tables in their own migrations; each context owns its tables (ARCHITECTURE §2.2).

### Frontend — session state and the guard

- **One cache entry is the session.** `entities/session` owns the `GetMe` query; `useLogin` seeds it from the login
  response and `useLogout` removes it on success. connect-query keys a query by the transport **object identity**, so
  the key helper takes the transport and the router carries it in its context — a guard built against a different
  transport would silently read a different entry and bounce a user who had just logged in.
- **`loadSession` answers, it does not throw for "signed out."** It returns `{status:'active'|'signed-out'}` and
  throws only for failures that are *not* an answer. That distinction is the whole design: an outage reported as a
  logout would strand the user on a login form that cannot work, having lost the page they were on. A 200 carrying no
  user is `signed-out`, not a session.
- **The guard is a pathless layout route** (`id: 'authenticated'`, no `path`). Every protected screen is a child, so
  "protected by default" is structural rather than something each route must remember. `/login` carries the reverse
  guard, and — unlike the protected one — it swallows an outage so the login form always renders.
- **Session freshness is bounded, not infinite** (`SESSION_STALE_MS`, 30 s). Caching the session forever would let a
  session revoked elsewhere keep rendering signed-in screens until a full reload; re-checking on every navigation
  would cost a round trip per click.
- **The `redirect` search param is validated by resolving it**, not by a pattern: anything that resolves to another
  origin is refused. `//evil.com` and `/\evil.com` both leave the origin (the URL parser folds a backslash into a
  slash), and the router does not check `to` against the known routes.
- **Logout navigates only on success.** A failed `Logout` leaves the cookie valid, so clearing local state would be a
  lie the next navigation exposes — and it would offer safety the still-live HttpOnly cookie does not.

## Acceptance Criteria

1. Any RPC other than `Login`/`Logout`/health called without a session returns `Unauthenticated` (HTTP 401); the
   same call with a valid cookie succeeds.
2. Altering a single character of the `pp_session` value yields 401 (the hashed lookup misses).
3. Login failure for an unknown id and for a known id with the wrong password return byte-identical error messages
   and codes, and the unknown-id path performs a real argon2id verification (asserted by a unit test on the dummy
   path).
4. In browser devtools, `document.cookie` never contains `pp_session`, and no response body contains the token.
5. There is no signup RPC or screen; an account created with `adduser` can log in; a duplicate id is refused.
6. After `Logout`, replaying the previous cookie yields 401 (server-side revocation, not just cookie clearing).
7. A session expires 30 days after login on both ends: cookie `Max-Age=2592000` and `sessions.expires_at`.
8. A deliberately failing migration makes the api process exit non-zero before it serves; `/health` never turns
   green ([I7]).
9. FE: an unauthenticated visit to any route redirects to `/login?redirect=<path>`; after login the originally
   requested route loads. A `redirect` that resolves off-site is ignored in favour of `/`.
10. The Set-Cookie header carries exactly `HttpOnly; Secure; SameSite=Lax; Path=/` and no `Domain`.
11. `Logout` without a valid session still answers 200 with the clearing cookie — the cookie is HttpOnly, so a 401
    would strand it in the browser with nothing able to remove it.

## Policy / Config Impact

**The rules now live in [`spec/policy/auth.md`](../policy/auth.md)** (landed by job 01). In summary:

- Passwords are stored as argon2id (PHC string) only; session tokens are stored hashed; the raw token exists only in
  the cookie.
- The session cookie is host-only, `HttpOnly; Secure; SameSite=Lax`, 30 days, fixed expiry.
- Unknown-id logins run a dummy argon2id verification so id existence never leaks by timing or message.
- Accounts are provisioned only by the operator via `api adduser` / `cmd/adduser`; the api exposes no registration
  path.
- Every authenticated RPC takes the acting user from the interceptor's context, never from request payloads.
