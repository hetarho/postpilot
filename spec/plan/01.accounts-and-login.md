# 01. Accounts and Login

> Operator-created accounts, id + password login, 30-day HttpOnly cookie sessions, and the SQLite persistence
> foundation they stand on | Scope: FS | Status: planning

## Purpose

postpilot is exposed on the public internet but serves exactly two people (PRD §1). Every other feature — posts,
photos, the voice profile, generation jobs — is scoped to an account, so identity is the first thing that has to be
true (PRD §10: steps 1–2 must land before anything else has a place to attach).

The product problem is narrow but real: a month-long session that lives on a phone (S1, "저녁에 폰으로") must not be
stealable through XSS, and the login form must not reveal which ids exist. There is deliberately no signup: a
two-person tool gains nothing from an open registration surface (PRD F-1).

This plan also lands the persistence foundation (SQLite + embedded goose migrations + sqlc) because `users` and
`sessions` are the first tables — the mechanism is the substance of invariant [I7].

## Scope / Non-goals

**In scope**

- `Login` / `Logout` / `GetMe` RPCs; session issue, validation, revocation.
- Session transport as an HttpOnly cookie; the auth interceptor that turns a missing/invalid session into 401.
- CORS with credentials against exactly one origin.
- Timing-equalized login (dummy argon2id verification when the id does not exist).
- `backend/cmd/adduser` — the operator's only way to create an account.
- Persistence foundation: `internal/platform/db` (modernc SQLite, WAL, single serialized writer), `//go:embed`-ed
  goose migrations run at boot, sqlc query generation, and migration `0001` (`users`, `sessions`).
- FE: login page, credentialed Connect transport, 401 → redirect, route guard.

**Non-goals**

- Signup UI or RPC (PRD F-1: 가입 화면 없음 — by design, not by omission).
- Password change / reset flows. The PRD does not define one; the operator recreates the account with server-side
  tools. Flagged as a PRD gap, not silently filled.
- Roles, permission tiers, organizations, 3+ users (PRD §1 비목표).
- OAuth / social login, MFA, IP-based rate limiting (2-user scale; timing equalization is the required defense).
- Sliding session renewal — the PRD fixes 30 days; sessions expire 30 days after login.

## Design

### Contract — `proto/postpilot/v1/auth.proto`

```
service AuthService {
  rpc Login  (LoginRequest)  returns (LoginResponse);   // sets the session cookie via the HTTP response header
  rpc Logout (LogoutRequest) returns (LogoutResponse);  // revokes the session row, clears the cookie
  rpc GetMe  (GetMeRequest)  returns (GetMeResponse);   // session probe for app boot; 401 when no session
}
message LoginRequest  { string login_id = 1; string password = 2; }
message LoginResponse { User user = 1; }
message GetMeResponse { User user = 1; }
message User          { string id = 1; }
```

The session token travels **only** in the cookie. It never appears in a response body, log line, or URL. The
`Login` handler sets the `Set-Cookie` header on the HTTP response (Connect handlers may set response headers);
`Logout` sets the same cookie with `Max-Age=0`.

### Sessions

- Token: 32 bytes from `crypto/rand`, base64url in the cookie. The DB stores `hex(sha256(raw_token))` as
  `sessions.token` (PK) — a leaked DB does not yield usable cookies (PRD §5).
- `expires_at = login_time + 30d`, fixed. Lookup on every RPC compares against `now`.
- `Logout` deletes the row. Expired rows are deleted on the failed lookup that finds them and swept once at boot.
- Cookie, exactly (PRD F-1):

  ```
  Set-Cookie: pp_session=<token>; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=2592000
  ```

  No `Domain` attribute (host-only) — a `Domain` would leak the cookie to sibling projects on the same registered
  domain. `SameSite=Lax` is sufficient because `postpilot.<domain>` and `api.postpilot.<domain>` are same-site.

### Login and timing equalization

1. Look up `users` by `login_id`.
2. If absent, run `argon2id.Verify(password, DUMMY_HASH)` against a fixed, valid argon2id hash so the "unknown id"
   path costs the same as the "wrong password" path. Then fail.
3. If present, verify against `password_hash`. On mismatch, fail.
4. Both failures return the same generic message (`invalid credentials`) with the same Connect code
   (`Unauthenticated`).

Password hashing: `golang.org/x/crypto/argon2` `IDKey` with `time=3`, `memory=64 MiB`, `parallelism=2`, 16-byte
salt, 32-byte key, stored in PHC string form (`$argon2id$v=19$m=...,t=...,p=...$<salt>$<hash>`) so parameters can be
raised later without a schema change. Plaintext or unsalted hashes are forbidden (PRD F-1).

### Interceptor and CORS

- A Connect interceptor in `internal/platform/rpcserver` runs for every procedure except `AuthService.Login` and the
  health endpoint. It reads `pp_session`, hashes it, loads the session, checks expiry, and injects the user id into
  `context.Context`. Any failure → `connect.CodeUnauthenticated` (HTTP 401). Downstream contexts read the user id
  from the context and never re-derive it.
- CORS middleware: `AllowedOrigins = [CORS_ORIGIN]` (exactly one), `AllowCredentials = true`, Connect's required
  headers allowed and exposed. A wildcard origin is rejected at config validation because it cannot be combined with
  credentials.
- FE transport (`shared/api`): `createConnectTransport({ baseUrl, credentials: 'include' })`.

### `cmd/adduser`

- `adduser <login_id>` reads the password from stdin (twice, must match), hashes it with the same argon2id
  parameters, inserts the `users` row. A duplicate id exits non-zero with a clear message.
- The binary ships inside the api image alongside `api`; the operator runs
  `docker compose run --rm api adduser <id>` on the VPS (the compose service's command is overridden; the image
  entrypoint resolves `adduser`). Details of the image layout belong to `DEPLOY.md`.
- It opens the same SQLite file as the api (same `DB_PATH`) and runs pending migrations first, so it works on a
  fresh volume.

### Persistence foundation (lands with this plan)

- `internal/platform/db`: opens `modernc.org/sqlite` (pure Go — [I6]/[I7] depend on staying CGO-free) with
  `journal_mode=WAL`, `foreign_keys=ON`, `busy_timeout`. Exposes one **serialized write connection** and a read pool
  (ARCHITECTURE §2.4). Contexts get the handle injected from `cmd/api`; they never open their own.
- Migrations: SQL files under `internal/platform/db/migrations/`, `//go:embed`-ed, applied by goose in `cmd/api`
  **before** the server listens. A failure logs and exits non-zero; the container never reports healthy; the deploy
  gate rolls back to the previous image ([I7], `DEPLOY.md` §2). No migration container, no manual step.
- sqlc: per-context `queries/*.sql` compiled into per-context store packages. Generated code is committed, never
  hand-edited (ARCHITECTURE §1).
- Migration `0001` (PRD §5):

  ```sql
  users     (id TEXT PRIMARY KEY, password_hash TEXT NOT NULL, created_at TEXT NOT NULL)
  sessions  (token TEXT PRIMARY KEY,                       -- sha256 hex of the raw token
             user_id TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
             expires_at TEXT NOT NULL, created_at TEXT NOT NULL)
  index sessions(user_id), sessions(expires_at)
  ```

  Later plans add their own tables in their own migrations; each context owns its tables (ARCHITECTURE §2.2).

## Acceptance Criteria

1. Any RPC other than `Login`/health called without a session returns `Unauthenticated` (HTTP 401); the same call
   with a valid cookie succeeds.
2. Altering a single character of the `pp_session` value yields 401 (the hashed lookup misses).
3. Login failure for an unknown id and for a known id with the wrong password return byte-identical error messages
   and codes, and the unknown-id path performs a real argon2id verification (asserted by a unit test on the dummy
   path).
4. In browser devtools, `document.cookie` never contains `pp_session`, and no response body contains the token.
5. There is no signup RPC or screen; an account created with `cmd/adduser` can log in; a duplicate id is refused.
6. After `Logout`, replaying the previous cookie yields 401 (server-side revocation, not just cookie clearing).
7. A session expires 30 days after login on both ends: cookie `Max-Age=2592000` and `sessions.expires_at`.
8. A deliberately failing migration makes the api process exit non-zero before it serves; `/health` never turns
   green ([I7]).
9. FE: an unauthenticated visit to any route redirects to `/login`; after login the originally requested route loads.
10. The Set-Cookie header carries exactly `HttpOnly; Secure; SameSite=Lax; Path=/` and no `Domain`.

## Policy / Config Impact

**Rules that will be true once implemented** (to land in `spec/policy/auth.md` when the job completes):

- Passwords are stored as argon2id (PHC string) only; session tokens are stored hashed; the raw token exists only in
  the cookie.
- The session cookie is host-only, `HttpOnly; Secure; SameSite=Lax`, 30 days, fixed expiry.
- Unknown-id logins run a dummy argon2id verification so id existence never leaks by timing or message.
- Accounts are provisioned only by the operator via `cmd/adduser`; the api exposes no registration path.
- Every authenticated RPC takes the acting user from the interceptor's context, never from request payloads.
