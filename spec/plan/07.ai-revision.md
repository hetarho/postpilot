# 07. AI Revision

> Fix the draft with a sentence ("더 짧게", "존댓말로"), change only what was asked, keep the author's voice on every
> pass, and optionally save the request as a permanent rule | Scope: FS | Status: done

## Purpose

The primary scenario ends with one round of "더 짧게" before copying (S1). Revision is how the author steers a
draft without hand-editing blocks — and how the profile gets better: S3 shows the loop where "반말로 써줘" with
"규칙으로 저장" checked means never having to say it again (PRD F-6).

Two failure modes drive the design. Models drift back to their default voice after three or four edits unless the
profile is re-injected every time; and a model asked to "shorten" will happily rewrite everything, so the contract is
**minimal change**: touch what was asked, keep every other sentence.

## Scope / Non-goals

**In scope**

- `StartRevision(post_slug, instruction, save_as_rule)` as a `revise` job on the shared queue (plan 05).
- The revision prompt: full profile re-injection (plan 03 order), current `PostContent`, the instruction, the
  minimal-change and image constraints.
- Image constraints: IMAGE `file`s are immutable and must stay within the attached set; reordering allowed; no new
  files.
- Same validation function + attachment filter as generation (plan 06); whole-content replacement.
- `save_as_rule`: append the instruction to `voice_profiles.rules` through the voice context's published behavior.
- Repeatability: any number of sequential revisions.
- FE: the revision box with the checkbox, progress via `useJob`, error/retry.

**Non-goals**

- Manual block editing, partial-range selection ("이 문단만"), or diff/accept UI.
- Version history and undo (PRD §8) — a revision replaces the content; the previous version is gone.
- Regenerating from scratch (that is `StartGeneration` again, plan 06) or re-running observation.
- Automatic cleanup/merging of accumulated rules (PRD §9.3).
- Applying a saved rule retroactively to the current draft beyond the revision that carried it.

## Design

### Contract — `proto/postpilot/v1/post.proto` (this plan's part)

```
service GenerationService {
  rpc StartRevision (StartRevisionRequest) returns (StartRevisionResponse);   // alongside StartGeneration / GetGeneration
}
message StartRevisionRequest  { string post_slug = 1; string instruction = 2; bool save_as_rule = 3; ModelRef write_model = 4; }
message StartRevisionResponse { string job_id = 1; }
```

Preconditions: the post is the caller's and has `content` (status `review`); `instruction` non-empty after trim and
≤ `REVISION_INSTRUCTION_MAX_CHARS`; `write_model` set and enabled (the user's `write` selection; observation is not
involved); no active job on the post (plan 05 guard). The job row records `write_model`; `payload` carries
`{instruction, save_as_rule}`.

### Saving the rule

When `save_as_rule` is true, `StartRevision` appends the instruction as a new line to the acting user's
`voice_profiles.rules` **at request time**, before enqueueing, via `voice.AppendRule(userID, line)`. The user's
stated preference stands regardless of whether this particular revision succeeds; the rule is also part of this
revision's prompt (as the instruction) and of every later generation/revision (as a rule, injected last). Duplicate
lines (exact match after trim) are not appended twice.

### The `revise` handler

```
profile := voice.ProfileForPrompt(user)                 // re-injected on EVERY revision — styleguide → active rules → excerpts → user rules → ending constraint
system  := REVISE_PROMPT + Korean naturalness baseline + profile  // stable prefix first; cache-friendly (PRD §5)
user    := current PostContent as JSON + attached filenames + instruction + constraints
Complete(write_model, schema=POST_CONTENT_SCHEMA when structured_output else nil)   // under LLM_STAGE_TIMEOUT
parse (fallback parser from plan 06) → validate → attachment filter → image-set check → persist whole content
progress("write", 1, 1)
```

Constraints stated in the prompt (and checked where checkable):

- **Minimal change:** apply the instruction and leave every other sentence exactly as it is; do not reflow or
  "improve" untouched blocks; keep `title`/`summary`/`tags` unless the instruction concerns them.
- **Images:** IMAGE blocks may be reordered or (if the instruction asks) removed, but `file` values must be a subset of
  the attached filenames and no `file` may be renamed or invented. The handler enforces the subset rule via the
  attachment filter against a fresh attachment snapshot after the provider call; a concurrently deleted photo or a
  result that renames a file simply loses that block. A result that drops all images when not asked is still accepted
  (the model's judgment, the user can revise again).
- **Voice:** the profile applies to the whole output, including rewritten sentences.
- **Korean naturalness floor:** sentences that revision actually changes follow the same fixed baseline as a fresh
  write, unless the voice profile, active contrast rules, or user rules conflict. Minimal-change rules remain
  authoritative, so the baseline never licenses rewriting an untouched sentence.
- Output is the full `PostContent` document, not a diff (structured output when supported; otherwise fenced JSON is
  tolerated).

Persistence goes through `post.SetGeneratedContent` (plan 06); `status` stays `review`.

### FE

`features/edit-with-ai`: a text field ("어떻게 고칠까요? 예: 더 짧게 · 존댓말로 · 카페 얘기 늘려줘"), a checkbox
"이 요청을 규칙으로 저장", a submit that calls `StartRevision` with the current `write` selection and hands the job id
to `useJob`; disabled while a job is active on the post. On `done` the reading view (plan 06) re-renders the new content.
On `failed` the error appears; a request started in the current editor session can be retried with its retained input,
while a resumed request asks for a new instruction rather than exposing a no-op retry. Saved rules are visible on
`/voice` (plan 03).

## Acceptance Criteria

1. Saving "존댓말로" as a rule and then generating a **new** post yields a write prompt whose rules section contains
   that line, placed after the excerpts (prompt assembly test), and the generated draft uses 존댓말 (manual QA).
2. Five consecutive revisions each re-inject the complete profile (styleguide, excerpts, rules) — asserted on the
   prompt for each of the five jobs; the draft's voice is unchanged after the fifth (manual QA).
3. A revision result never introduces an IMAGE `file` outside the attached set (crafted-output unit test); reordering
   IMAGE blocks is preserved.
4. With `save_as_rule = false`, `voice_profiles.rules` is unchanged after the revision; with `true`, the instruction
   appears as a new line in the profile immediately after `StartRevision` returns and is shown on `/voice`.
5. `StartRevision` returns a `job_id` immediately; progress is visible; closing and reopening the editor mid-revision
   resumes polling (plan 05 mechanics).
6. An empty instruction, a post without content, or another user's post is refused before a job is created.
7. Submitting the same rule twice does not duplicate the line in `rules`.
8. Revision output passes the same validation function and attachment filter as generation (shared code path,
   asserted by test).

## Policy / Config Impact

**Implemented rules** (canonicalized in `spec/policy/revision.md`, cross-referencing `generation.md`, `voice.md`):

- Every revision re-injects the full voice profile in the canonical order; the instruction follows the per-post
  material.
- Every Korean revision injects the shared naturalness baseline before the profile; profile and user rules win on
  conflict, and untouched text remains verbatim.
- Revision output is a full `PostContent` that replaces the previous content; image filenames are immutable and
  bounded by the attached set.
- A checked "규칙으로 저장" appends the instruction to the acting user's `rules` at request time, de-duplicated.
- Revision rides the job queue under the one-active-job-per-post guard.

**Config**

| Value | Owner | Supplied as | Default |
|---|---|---|---|
| `REVISION_INSTRUCTION_MAX_CHARS` | BE `internal/generation` config | typed constant | `500` |
| `LLM_STAGE_TIMEOUT` | BE `platform/config` (plan 04) | typed constant | `5m` |

Revision prompt text is code, not config.

## As-built extension — job 16

Before enqueue, the revision form flushes direct block edits so the job reads the newest canonical value. Each
revision reloads the same structured/topic-aware voice projection used by generation and retains target length when
that post option is enabled; an absent option adds no numeric length instruction.
Successful output is validated against attachments and atomically becomes both canonical content and the next
machine learning baseline. The legacy “save as rule” text remains manual guidance; evidence-derived contrast rules
have their own lifecycle and are never activated by a thumbs-only feedback event.

Every successful revision establishes `review`, including when it replaces a finalized revision. It never finalizes
or starts learning; those remain separate explicit actions at the bottom of the editor.

## As-built extension — job 36

The revise builder now injects the same fixed `[한국어 자연 문체 기준선]` bytes as the write builder, between
`RevisePrompt` and `[스타일가이드]`. The shared section itself limits the floor to requested changes in `TEXT`
prose and excludes titles, summaries, `HEADING`/`LIST` content, and untouched text; the existing minimal-change
sentences in `RevisePrompt` are also unchanged. An empty voice still receives the floor, while the voice profile,
active contrast rules, and user rules override it on conflict.
