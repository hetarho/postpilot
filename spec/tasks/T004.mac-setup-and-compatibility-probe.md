## goal
Finish the loopback setup so a connection can only become server-ready after a versioned, non-publishing compatibility probe has verified the exact dedicated profile, the sole CDP target, the Naver-selected identity, categories, the editor signature, semantic locators and the readback surface (legacy job 25 T017, first half of T002).

## acceptance
- [v] the loopback-only setup screens and actions cover API URL, device-code enroll, connection naming, supported Chromium-family binary selection, the per-connection agent-owned user-data directory, visible Naver login and test, exact blog-identity verification, category sync and defaults, driver/Chromium status, and redacted logs
- [v] the versioned probe verifies the sole bound target, required CDP/accessibility capabilities, the signed-in identity Naver selected (never user input, page prose or a claimed identifier), category discovery, the editor root and signature, semantic locators and the readback surface, and refuses to arm the connection on any mismatch; a profile lock or a failing probe leaves the connection unarmed and actionable
- [v] the probe follows only the signed-in Naver UI to the account's own blog and opens its writer without typing, uploading or publishing; it rechecks that the same page remains the sole CDP target
- [v] profile sync sends only safe driver name/version/signature/readiness metadata; the server provides no executable driver configuration, and legacy executor-specific metadata is deprecated without changing job or lease RPC semantics
- [v] two Postpilot accounts on one Mac use separate Keychain entries, browser directories, queues and work directories
- [v] after migration 0015, an existing locally armed connection reuses its agent id, token and profile, reruns the replacement probe and syncs the deterministic version before it can become server-ready again; the repair flow performs and tests that re-probe instead of requiring a new device code
- [v] the companion launches the chosen binary with `--remote-debugging-address=127.0.0.1`, an ephemeral port and the connection-owned `--user-data-dir`, verifies `/json/version` against `DevToolsActivePort` (browser id and port) and refuses a stale file; a live setup browser is reused and never killed
- [v] the setup server enforces a per-run cryptographic nonce, exact loopback Host and same-origin POST, bounded form size and actions; public HTTP API URLs are refused except loopback development
- [v] the compatibility manifest records supported Chromium/CDP versions and capabilities and is asserted by a test; signed agent releases carry reviewed driver/signature updates
- [v] agent tests cover probe success and every refusal class, identity mismatch, target switch, profile lock, and the post-0015 re-probe; ARCH-27 passes

## impl notes
- read the current official Chromium DevTools Protocol and the chosen CDP client library documentation first (ARCH-33); record the supported versions and capabilities in an agent-owned compatibility manifest with a test, and decide how a signed release carries driver updates
- placement: `agent/internal/setup` (screens, nonce, enroll, resume), `agent/internal/browser` (launch, `DevToolsActivePort` verification, the narrow port), a new probe package under `agent/internal/naver` (versioned editor signature and locator set, shared with T005), `agent/internal/postpilot` (profile sync fields), `agent/internal/config` (connection schema from T003)
- the probe is the same code path T005's publisher will use to resolve locators, so version the signature, locator set and manifest schema together from the start
- the server side (`SyncAgentProfile`, readiness) already exists; only the metadata it accepts may narrow — do not add executable configuration to the contract
- run everything on macOS; gates per ARCH-27

## result

- Added a signed-release-owned Naver compatibility manifest and a fixed, read-only CDP probe. It pins Chromium 136–152, protocol 1.3, required domains/accessibility roles, the SmartEditor signature, semantic control surface and readback capability; no server-supplied selectors or executable configuration are accepted.
- Pairing now opens the exact draft-owned profile and arms it only after the sole Naver target, Naver-selected blog identity, categories and compatibility signature pass. Only safe account/category/browser/driver readiness metadata is synchronized, while tokens remain in the per-agent Keychain entry.
- Existing armed connections can open their persistent login profile and re-probe without enrollment or a new device code. The flow reuses the agent id and token, preserves profile/work paths, rejects a changed Naver identity before sync, and records the reviewed browser/signature status locally.
- Browser startup now refuses an unavailable CDP endpoint when Chromium still holds `SingletonLock`; verified live setup browsers remain reused and unowned processes are not killed. Tests cover success, CDP/AX/editor refusal classes, target changes, profile locking, identity mismatch, safe pairing and the post-0015 replacement-probe path.
- The implementation follows the official Chromium DevTools Protocol and `coder/websocket` context-first connection model. The complete ARCH-27 gate (`gofmt`, `go vet`, `go build`, all agent tests and packaging shell syntax) passes.
