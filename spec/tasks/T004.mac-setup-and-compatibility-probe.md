# T004 Mac pairing, profile setup and the non-publishing compatibility probe
> st:todo | ssot:PUBLISH-7 PUBLISH-8 PUBLISH-18 PUBLISH-24 PUBLISH-6 PUBLISH-29 | base:PUBLISH@2 ARCH@1 | dep:T003

## goal
Finish the loopback setup so a connection can only become server-ready after a versioned, non-publishing compatibility probe has verified the exact dedicated profile, the sole CDP target, the Naver-selected identity, categories, the editor signature, semantic locators and the readback surface (legacy job 25 T017, first half of T002).

## acceptance
- [ ] the loopback-only setup screens and actions cover API URL, device-code enroll, connection naming, supported Chromium-family binary selection, the per-connection agent-owned user-data directory, visible Naver login and test, exact blog-identity verification, category sync and defaults, driver/Chromium status, and redacted logs
- [ ] the versioned probe verifies the sole bound target, required CDP/accessibility capabilities, the signed-in identity Naver selected (never user input, page prose or a claimed identifier), category discovery, the editor root and signature, semantic locators and the readback surface, and refuses to arm the connection on any mismatch; a profile lock or a failing probe leaves the connection unarmed and actionable
- [ ] the probe follows only the signed-in Naver UI to the account's own blog and opens its writer without typing, uploading or publishing; it rechecks that the same page remains the sole CDP target
- [ ] profile sync sends only safe driver name/version/signature/readiness metadata; the server provides no executable driver configuration, and legacy executor-specific metadata is deprecated without changing job or lease RPC semantics
- [ ] two Postpilot accounts on one Mac use separate Keychain entries, browser directories, queues and work directories
- [ ] after migration 0015, an existing locally armed connection reuses its agent id, token and profile, reruns the replacement probe and syncs the deterministic version before it can become server-ready again; the repair flow performs and tests that re-probe instead of requiring a new device code
- [ ] the companion launches the chosen binary with `--remote-debugging-address=127.0.0.1`, an ephemeral port and the connection-owned `--user-data-dir`, verifies `/json/version` against `DevToolsActivePort` (browser id and port) and refuses a stale file; a live setup browser is reused and never killed
- [ ] the setup server enforces a per-run cryptographic nonce, exact loopback Host and same-origin POST, bounded form size and actions; public HTTP API URLs are refused except loopback development
- [ ] the compatibility manifest records supported Chromium/CDP versions and capabilities and is asserted by a test; signed agent releases carry reviewed driver/signature updates
- [ ] agent tests cover probe success and every refusal class, identity mismatch, target switch, profile lock, and the post-0015 re-probe; ARCH-27 passes

## impl notes
- read the current official Chromium DevTools Protocol and the chosen CDP client library documentation first (ARCH-33); record the supported versions and capabilities in an agent-owned compatibility manifest with a test, and decide how a signed release carries driver updates
- placement: `agent/internal/setup` (screens, nonce, enroll, resume), `agent/internal/browser` (launch, `DevToolsActivePort` verification, the narrow port), a new probe package under `agent/internal/naver` (versioned editor signature and locator set, shared with T005), `agent/internal/postpilot` (profile sync fields), `agent/internal/config` (connection schema from T003)
- the probe is the same code path T005's publisher will use to resolve locators, so version the signature, locator set and manifest schema together from the start
- the server side (`SyncAgentProfile`, readiness) already exists; only the metadata it accepts may narrow — do not add executable configuration to the contract
- run everything on macOS; gates per ARCH-27
