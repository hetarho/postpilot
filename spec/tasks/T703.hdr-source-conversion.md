## goal
An HLG or PQ source (as T702 decided) is prepared, sampled, previewed and rendered through one versioned conversion. Browser and native give the same picture.

## acceptance
- [ ] `nativeSourceColorSpace` accepts the colour tags T702's pick covers. It returns the conversion and a new colour version (`native-source-color-v2`), and every other non-SDR tag stays refused.
- [ ] The same conversion runs in all of these:
  - the range video reader used by ①'s and ②'s previews and the browser render
  - analysis-copy preparation
  - background sampling, which checks `colorVersion` against the new constant
  - the native analysis, sampling and render ffmpeg chains, which get the same matrix and, for candidate B, `lut3d` with the versioned LUT asset (the filter is added to `media-tools.sh`)
- [ ] An SDR source's output is unchanged by the new code. The tests assert that SDR frames are byte-identical before and after the change.
- [ ] Tests:
  - Synthesized HLG and PQ fixtures generated by a checked-in script, never owner footage.
  - Frontend `shared/lib/media`: `accepts HLG with the v2 colour version`, `refuses an uncovered transfer by name`, `SDR path unchanged`.
  - Backend `clip/media`: `TestNativeHDRConversionMatchesBrowserReference`, within T702's parity tolerance, and `TestSDRChainUnchanged`.
  - The Docker media smoke that exercises a source runs once with the HLG fixture (memory: a media change must RUN the Docker-only smokes).
- [ ] The ARCH-24 checks, relevant vitest, go test `-count=1` and the media image build pass. ARCH-31's full pre-push gate runs before push.

## impl notes

- If T702 chose A, PQ stays refused here, and CLIP-219 must first be narrowed by update-ssot, as T702 records.
- Treat the colour version as part of source identity wherever `NATIVE_SOURCE_COLOR_VERSION` is compared today, so a project prepared under v1 is re-prepared rather than mixed with v2.
