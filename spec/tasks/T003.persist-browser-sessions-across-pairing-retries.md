# T003 Persist the dedicated browser session across pairing retries
> st:todo | ssot:PUBLISH-32 PUBLISH-33 PUBLISH-34 PUBLISH-35 PUBLISH-6 PUBLISH-18 | base:PUBLISH@2 ARCH@1 | dep:-

## goal
Give the Mac companion a durable local connection draft id independent of the server's single-use device code, so an unfinished connection keeps its isolated Chromium profile across code replacement, browser relaunch and companion restart (legacy change 09).

## acceptance
- [ ] starting a local connection once, signing into Naver, closing its visible Chromium window, and reopening the same draft uses the byte-identical `user-data-dir`; absent Naver-side expiry the writer resolves as the same signed-in blog without asking for credentials again (local smoke test)
- [ ] replacing or regenerating the device code for an unfinished connection changes neither its local draft id nor its Chromium profile path and creates no additional browser profile
- [ ] stopping and restarting the setup companion before enrollment presents the unfinished draft as resumable and opens the same paths; no server token is required to preserve or reopen that browser state
- [ ] successful enrollment and activation bind the returned server identity and Keychain reference to the existing draft; login repair and a later publishing run both use the same browser path used before enrollment
- [ ] explicitly starting a second connection creates a distinct local draft and `user-data-dir`; two accounts on one Mac stay isolated and reopening either never opens the other's jar
- [ ] a missing, invalid, duplicated or conflicting draft reference fails closed with an actionable local error; the companion never chooses a profile by label, device-code hash, browser type, directory age or currently logged-in Naver account
- [ ] every setup, repair and publishing launch uses the connection-owned persistent `user-data-dir`, never incognito, guest or a temporary profile, and does not clear cookies or storage on normal launch or exit
- [ ] existing armed connections retain their configured profile paths after upgrade; legacy unowned code-derived directories are left untouched and never automatically attached, merged, copied or deleted
- [ ] Naver logout, expiry, CAPTCHA, 2FA, suspicious-login checks and blog-identity mismatch still stop locally for repair or become `needs_attention`; no authentication material or profile detail reaches the VPS
- [ ] revoking or repairing one connection leaves its on-disk profile and every other connection usable; profile deletion requires a separate explicit local confirmation
- [ ] automated coverage for stable path selection, code rotation, restart/resume, activation, isolation and fail-closed handling; ARCH-27 passes

## impl notes
- current evidence: `agent/internal/setup/server.go` derives the pre-enrollment local id from `DeviceCode`, prepares the profile before enrollment, and persists a pending connection only after enrollment; repair already reuses `Connection.ProfileDir` once armed
- the Mac-owned local config schema represents resumable connection drafts separately from armed connections (draft id, browser choice, profile dir, work dir, created_at); enrollment moves a draft to a connection by binding agent id and Keychain reference without touching paths
- generate the draft id from `crypto/rand` at "start a new connection"; the setup UI lists drafts as resumable and offers "새 연결" as the only way to create another
- no new env, shared-config or platform-config value, dependency, server contract or migration; server pairing TTLs, bearer rules, jobs, manifests, the commit fence and the frontend are untouched (regression boundary)
- follow ARCH-33 if any dependency is touched; run the agent gates on macOS
