# T050 The billing screen's refundability read
> st:todo | ssot:ARCH-10 ARCH-7 | base:ARCH@2 | dep:-

## goal
Answer "is this purchase still refundable" for every purchase in one read-pool query instead of one writer query each.

## acceptance
- [ ] `GetMyBilling` resolves refundability for all in-window purchases in a single query, with no per-purchase round trip
- [ ] that query runs on the read pool, not on the writer
- [ ] the answer is unchanged per purchase: refundable only while the purchase is unrefunded, inside the 7-day window, and its purchased lot is untouched (`remaining = granted`)
- [ ] an account with no in-window purchase issues no refundability query at all
- [ ] the writer-bound `LotUntouched` keeps working for any caller whose answer is about to decide a write
- [ ] tests cover several purchases with mixed refundability in one call, an empty purchase list, and a refunded purchase being excluded
- [ ] ARCH-26 passes

## impl notes
- from review/diff-260908 F4
- the defect: `GetMyBilling` loops `s.credits.LotUntouched` per purchase and `usage/store.LotUntouched` deliberately reads on `s.write`, which `db.Open` caps at one connection (ARCH-10). A read-only screen therefore serializes N statements ahead of every concurrent generation hold and every billing transaction
- the writer is right for the balance reads whose comment explains them ("the balance they produce is about to decide a write") and wrong here: this answer only decides whether a button renders, so a read-pool query is the correct choice rather than a shortcut
- shape: one `SELECT id FROM credit_lots WHERE id IN (sqlc.slice('ids')) AND kind = 'purchased' AND granted > 0 AND remaining = granted` on the read pool, returning the untouched subset; the service turns that into the per-purchase flag. sqlc's slice helper is what keeps the variable IN list a prepared statement
- the port method belongs beside the existing one on `billing.Credits` as a plural read, so billing still learns nothing about `credit_lots` (ARCH-7)
