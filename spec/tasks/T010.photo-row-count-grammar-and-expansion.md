# T010 Photo row count in the grammar and ordered photo expansion
> st:todo | ssot:TEMPLATE-18 TEMPLATE-20 TEMPLATE-21 TEMPLATE-22 TEMPLATE-37 TEMPLATE-38 TEMPLATE-40 | base:TEMPLATE@2 ARCH@1 | dep:-

## goal
Teach the Go grammar a bounded `count` on photo positions, expand photos once in attachment order (n per position, grouped per repeat iteration), freeze the row specs, keep `place`/`link` bodies readable, and land every new rule in the shared fixture first.

## acceptance
- [ ] `<slot kind="photo" count="n"/>` parses for integer n in 1 … `TEMPLATE_PHOTO_ROW_MAX`; an absent `count` means 1; any other value (0, negative, non-integer, above the ceiling, empty) is `TEMPLATE_PARSE_FAILED` with reason `invalid_count` and the 1-based line
- [ ] `count` on a non-photo slot is `malformed_tag`; `place` and `link` slots (with or without `label`) still parse and serialize byte-exactly, and `unknown_slot_kind` still fires for every other kind
- [ ] expansion binds attached photos once, in attachment order, across every photo position in body order: a bare position with count n takes the next n unbound photos; a `<repeat each="photo">` runs ⌈photos ÷ n⌉ iterations where n is the total count of the photo positions inside it (n = 0 → one iteration, no photos consumed), each iteration binding the next group and a short last group binding what is left; a position with no photo left renders nothing; zero photos drops every repeat block whole
- [ ] the expansion bound counts iterations (not photos) against `TEMPLATE_MAX_REPEAT_EXPANSION`; a bare photo position no longer repeats the first photo (pinned by a test with two bare positions and two photos rendering two different tokens)
- [ ] a position with count n renders its n `{{photo:<file>}}` tokens adjacent (joined by a single newline) and the frozen `Rendered` carries ordered row specs `{count, filenames}` for every position that bound at least one photo; `place`/`link` slots keep rendering `{{slot:n}}` and keep appearing in `Slots` (legacy bodies only)
- [ ] the generation payload freezes the row specs beside the template body and slots; a payload written before r2 decodes with no rows; `ApplyTemplateSlots` is unchanged and still resolves legacy slot tokens
- [ ] the prompt legend no longer explains `{{slot:번호}}` when the frozen brief has no slots, still does when it has (legacy), and explains that adjacent photo tokens are photos shown side by side in one row; the section position and the voice-profile prefix bytes are unchanged (existing prompt snapshot tests updated, not loosened)
- [ ] `TEMPLATE_PHOTO_ROW_MAX` (default 4) is read into the config struct, validated positive at boot, wired into `template.Limits`, and added to `.env.example` and `.env.production.example`
- [ ] `backend/internal/template/testdata/grammar/cases.json` gains cases for: count 1 · count 4 · count absent · count 0 · count 5 (against a fixture ceiling of 4 declared in the file's `_comment` and honoured by both parsers) · count on a place slot · count with surrounding whitespace · legacy place slot with label still ok; the differential corpus is regenerated with `count="2"` and `count="9"` pieces added to the alphabet and every changed verdict reviewed
- [ ] `cd backend && test -z "$(gofmt -l .)" && go vet ./... && go build ./... && go test ./...` passes

## impl notes
- grammar (`backend/internal/template/grammar.go`): add `Count int` to `Node` (0 when not a photo slot); in the `NodeSlot` branch read `attrs["count"]` after `kind`; parse with `strconv.Atoi` on the trimmed decoded value; the ceiling is passed into the parser (`Parse(body string, opts ParseOptions)` or a `Grammar{PhotoRowMax int}` value — pick one and give the fixture test the ceiling 4 explicitly so the fixture does not depend on env); export `ReasonInvalidCount = "invalid_count"` and add it to the handler's allowlisted reasons and to the FE `ParseReason` union in T011
- keep `SlotPlace` and `SlotLink` constants and parsing: TEMPLATE-37 keeps stored bodies readable; only the builder (T011) stops authoring them
- types (`types.go`): `Limits.PhotoRowMax int` (validated > 0 in `valid()`); `Rendered.Rows []PhotoRow` with `PhotoRow{Count int; Filenames []string}` in body order; keep `Rendered.Slots`
- expansion (`expand.go`): rewrite `renderNodes` around a cursor over `filenames`; `take(n)` returns the next min(n, remaining) filenames and advances; `groupSize(children)` sums photo counts inside a repeat; iterations = ceil(photos / groupSize) when groupSize > 0, else 1 when photos > 0; `checkExpansion` uses the same iteration count; render a position as its tokens joined by `\n`, one `PhotoRow` per position that bound ≥ 1 photo
- config (`platform/config/config.go`): `positiveInt("TEMPLATE_PHOTO_ROW_MAX", "4")` next to the other template limits; add to the config test's env list; document the var in `.env.example` under the template block (it is mirrored by the FE in T011 as `VITE_TEMPLATE_PHOTO_ROW_MAX`)
- wiring (`cmd/api`): pass the new limit into `template.Limits` where the others are set
- generation (`generation/types.go`, `generation_payload.go`, `generate_handler.go`): `TemplateBrief.Rows []TemplatePhotoRow` (count, filenames) copied from `template.Rendered.Rows`; JSON `rows,omitempty`; the deep copy in `generate_handler.go` copies rows the way it copies slots; the A/B snapshot path freezes the same brief (no new code if it reuses `encodeTemplate`)
- prompt (`generation/prompts.go`): split `templateLegend` into the always-present lines and the `{{slot:번호}}` line appended only when `len(brief.Slots) > 0`; add one line after the photo line: `연속된 {{photo:…}} 토큰은 한 줄에 나란히 놓이는 사진들입니다. 각각 IMAGE 블록으로, 그 순서대로 이어서 출력하세요.` — TEMPLATE-40 interim, so the model emits consecutive single IMAGE blocks; nothing downstream (export, publisher) changes in this task
- fixture (`testdata/grammar/cases.json`): extend the `_comment` with the node shape `slot{kind,label,count}` and the fixture ceiling `photoRowMax: 4` as a top-level key both test harnesses read; every ok case with a photo slot gets an explicit `count` in its expected node (1 when absent); the TS harness change is T011's, so add cases now and expect T011 to make them pass on the other side
- corpus (`corpus_test.go`): add `count="2"`, `count="9"`, `count="x"` to `pieces`; regenerate with `TEMPLATE_CORPUS_REGEN=1 go test ./internal/template -run TestCorpusMatchesTheCommittedFile`; the seed stays `20260904`; commit the diff after reading every changed verdict
- tests: `expand_test.go` covers bare count 3 with 5 photos (rows: [a b c]), repeat of one count-2 position with 5 photos (iterations 3, last row [e]), repeat of a count-1 and a count-2 position with 4 photos (iterations 2, rows [a] [b c] [d] [ ]→ the second position of the last iteration renders nothing), zero photos, bound refusal by iterations, two bare positions bind two different photos; `grammar_test.go` runs the fixture with ceiling 4
- touch nothing under `frontend/` in this task — the FE parser reads the same fixture in T011; until then the FE fixture test fails on the new cases, so T010 and T011 ship together (both are todo in one delta)
