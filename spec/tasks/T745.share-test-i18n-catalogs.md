# T745 Stop re-evaluating the i18n catalogs in every DOM test file
> st:todo | ssot:ARCH-24 ARCH-25 | base:ARCH@21 | dep:- | touches:frontend/src/test frontend/vite.config.ts frontend/build frontend/src/app/providers/i18n | lane:- | explore:-

## goal
Cut the measured per-file i18n setup cost of the jsdom test project without changing any translation, any test's outcome or the production i18n behavior.

## acceptance
- [v] Every jsdom test file gets an i18n instance with resources deep-equal to the current catalogs (same namespaces, keys and values), the same default language, fallback, formatters and init options; prove the equality with a check that fails if a catalog key is added or changed without being reflected.
- [v] Production i18n behavior is unchanged: the app still initializes from the same catalogs with the same options; any refactor in `app/providers/i18n` is structure-only and its existing tests pass unchanged.
- [v] Test discovery and outcomes are unchanged: the same files and cases are collected before and after, the node project keeps no browser setup, and no assertion, timeout, retry, isolation or worker policy changes.
- [v] Measured effect with the F3 method: the same 40 trivial jsdom files at `--maxWorkers=4`, ABBA order, before and after, report per-file setup and Duration; plus the same 20 real files once before and after with all passing.
- [v] Affected consumers (i18n provider tests, locale/metadata tests, a sample of page and widget tests) pass, plus `tsc -b`, ESLint on changed files, format check and FSD lint. The coordinator runs the full FE suite on the candidate.

## impl notes
- from review/perf-quality-sil5-261110 F3
- Evidence: ABBA on 40 trivial jsdom files, Node 24.18.0, 4 workers: setup 1.66/1.63 s per file with `initializeI18n` versus 0.225/0.217 s without (A−B 1.43 s, spread 0.03 s); transform about 7.9 s per run is shared across files, so the per-file cost is evaluating about 124 catalog modules in each isolated module graph. 20 real files: setup 1.79 s per file.
- One acceptable direction: evaluate the catalogs once per run (for example in a vitest globalSetup that `provide`s the serializable resources, read with `inject` in the setup file) and initialize i18next from that data in each file without importing the catalog modules. Verify the catalogs are pure serializable data before relying on it; formatters stay registered as today. Other designs are fine if they meet the acceptance.
- Keep the change out of product behavior. If a production module must be split (for example separating the init from the resources import), keep exports and runtime behavior identical.
- The coordinator runs a full CI gate concurrently until about 20:00 KST: use `--maxWorkers=2` for runs before then and take the timing measurement after the gate if possible; report the load during measurements.
- Toolchain: Node 24.18.0 and pnpm 10.30.3 via `export PATH=/home/hrlee/.npm/_npx/4aa47c519def57bc/node_modules/.bin:$PATH`. Never run the full FE suite; the coordinator owns it.
