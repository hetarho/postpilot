## goal
A voice analysis reserves the larger of 30 000 prompt tokens and one token per Unicode character of the prompt it will send, so a large corpus is paid by the account up front instead of overrunning a fixed hold (QUOTA-14 r34).

## acceptance
- [v] starting an analysis freezes the snapshot it will read — the ids of the voice's 학습 글 at enqueue — in the job payload, and the run reads exactly those that still exist (VOICE-22: one snapshot, published even when a 학습 글 changed meanwhile)
- [v] the start assembles the prompt exactly as the run will (system prompt + `analysisInput` over the frozen snapshot) and plans its one call with `PromptTokens = max(30 000, rune count)`
- [v] `job.PlannedCall` and `usage.PlannedCall` gain `PromptTokens` (0 means the 30 000 default); `worstCaseMicrousd` prices `max(holdInputTokens, PromptTokens)`; every other caller is unchanged
- [v] an account whose balance cannot cover the larger hold is refused at start with the existing insufficient-credit failure, before any provider call
- [v] tests: a 50 000-character corpus holds 50 000+ prompt tokens and a small one holds 30 000; the run analyses the frozen ids only (a 학습 글 added after enqueue is not read; one deleted after enqueue is skipped); insufficient balance refuses the start
- [v] behaviour unchanged otherwise: ARCH-26 green
