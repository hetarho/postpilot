# T358 A photo's row goes before its object, and "finalized at the current revision" is one rule
> st:done@260925 | ssot:ARCH-6 ARCH-7 | base:ARCH@11 | dep:T357

## goal
A photo or video delete removes the guarded row before its storage object, so a publish that lands in between leaves the attachment whole. "The current revision is the finalized one" is written once, as a domain method, and the store only maps rows.

## impl notes
- from review/published-quality-260924 F9 F13
- Builds on T357's `writablePost`. DeleteImage / DeleteVideo already open with it there.
- The new DeleteImage order (service.go:1435-1473):
  1. GetImage.
  2. `found, err := s.writablePost(ctx, userID, image.PostSlug)`.
  3. `deleted, err := s.images.DeleteImage(ctx, imageID)`, the guarded row.
  4. If `!deleted`: `if err := s.lockedOrGone(ctx, userID, image.PostSlug, nil); err != nil { return err }`. Otherwise it is the idempotent already-gone case: skip the object, because the delete that removed the row owns it.
  5. If `deleted`: `if err := s.blobs.Delete(ctx, image.Key); err != nil { slog.WarnContext(ctx, "could not delete a removed photo's object; the stray-object sweep reclaims it", "key", image.Key, "err", err) }`, then carry on.
  6. `dropObservation` as today.
- DeleteVideo (:1477-1509) is the same shape with `videos` / `video.Key`.
- Why a failed object delete answers nil rather than an error: the row is already gone, so a retry would answer `ErrNotFound` from `GetImage`. The object is unreferenced, which is exactly what `sweepStrayObjects` (sweep.go:116-150) deletes once it is older than `minAge`. The precedent is `replacePendingUpload` (:1245-1254): "Row first, then object … Not fatal".
- The sweep covers this case. Its own type doc (sweep.go:17-18) names "a row deleted while the object delete failed". `AllReferencedKeys` reads images, videos and uploads, the keys sit under `posts/` (types.go:523-532), and serve.go:63 runs it with `cfg.OrphanMinAge`. No sweep change.
- Doc comments to rewrite:
  - DeleteImage :1430-1434: row first, then the object. The row DELETE is the lock's guard (POST-74), so a publish that lands first refuses the delete before storage is touched, and a failed object delete leaves an unreferenced object for the stray-object sweep.
  - DeleteVideo :1475-1476: says the same order.
  - The old "the user can retry" reason is gone.
- `fakeBlobs` (fake_test.go:741) gains `beforeDelete func(key string)`, called at the top of `Delete` before `f.mu.Lock()`, so a test can read `store` under its own lock. Keep `failDelete` as is.
- F13 rule in types.go, beside `Post`:
  - `func finalizedAt(status string, finalizedRevision, contentRevision int64) bool { return (status == StatusFinalized || status == StatusPublished) && finalizedRevision == contentRevision }`
  - doc: "a published post is a finalized one with an address (POST-21, POST-73)"
  - `func (p Post) FinalizedAtCurrentRevision() bool`
  - `func (s LearningSnapshot) FinalizedAtCurrentRevision() bool`
  - Both methods call `finalizedAt` ← the snapshot is the second read, and the rule must judge the row actually learned from.
- `LearningSnapshot` (types.go:342) gains `Status string` and `FinalizedRevision int64`. The voice adapter (cmd/api/adapters_voice.go:127) ignores them.
- service.go LearningSnapshot:
  - `if !found.FinalizedAtCurrentRevision() { return ErrPostNotFinalized }` stays first ← it keeps today's precedence: a draft with no content answers `ErrPostNotFinalized`, not the store's `ErrNoMachineBaseline`.
  - After the store read, add `if !snapshot.FinalizedAtCurrentRevision() { return LearningSnapshot{}, ErrPostNotFinalized }` with a comment: a save landing between the two reads demotes the post, and learning never takes a revision nobody finalized.
- Why the store check could not simply be deleted: GetLearningSnapshot is a plain SELECT, so no SQL predicate guards it. The check at store.go:338-341 was the only guard on the second read, and the service now does that job on the fresh row.
- store.go LearningSnapshot (:315-357):
  - Delete the `finalized := …` block (:338-341).
  - Map `Status: row.Status` and `FinalizedRevision: row.FinalizedRevision.Int64`.
  - Parse `finalized_at` only when `row.FinalizedAt.Valid`, leaving the zero time otherwise. FinalizePost writes it in the same statement as `finalized_revision`, so a row that passes the rule always has it.
  - Keep the `current == nil || baseline == nil → ErrNoMachineBaseline` check and the no-rows → `ErrNotFound` mapping unchanged.
- SavePublishedURL: `case address != "" && !found.FinalizedAtCurrentRevision(): return Post{}, ErrPostNotFinalized`. This is equivalent to today's `found.Status != StatusPublished && (…)` because a published post always holds its finalized revision: PublishPost requires it, and every content write carries the lock predicate.
- Finalize: replace `found.Status == StatusFinalized && found.FinalizedRevision == expectedRevision` with `found.FinalizedAtCurrentRevision()`. It is equivalent at that line: published is refused above and `ContentRevision == expectedRevision` is checked above.
- Keep PublishPost's SQL predicate (posts.sql `(status = 'finalized' AND finalized_revision = content_revision) OR status = 'published'`) as the concurrency guard.
- Fake copies (fake_test.go):
  - LearningSnapshot (:303-326) mirrors the store: no finalization check. It returns `Status` and `FinalizedRevision`, sets `FinalizedAt` only when non-nil, and keeps the ownership and `ErrNoMachineBaseline` checks. It runs the new `beforeSnapshotRead func(slug string)` hook first, outside `f.mu`, in the shape of `guarded`.
  - PublishPost (:337-339) becomes `if !existing.FinalizedAtCurrentRevision() && existing.Status != StatusPublished { return false, nil }`, which is the SQL predicate exactly.
- Out of scope, do not touch:

## result
- F9:
  - `DeleteImage` and `DeleteVideo` remove the guarded row first and reach storage only if it went. A publish that wins the race now leaves the row and the object whole.
  - A failed object delete after the row is gone logs a warning and answers success, leaving the object to the stray-object sweep.
  - The doc comments say so, and `fakeBlobs.beforeDelete` lets a test read the store when storage is reached.
- F13:
  - `finalizedAt` in types.go is the one rule, and `Post.FinalizedAtCurrentRevision` and `LearningSnapshot.FinalizedAtCurrentRevision` call it. Finalize, SavePublishedURL and LearningSnapshot use it, so neither service.go nor store.go compares `StatusFinalized` any more.
  - `LearningSnapshot` carries `Status` and `FinalizedRevision`. The store maps them and parses `finalized_at` only when set. The service judges the row it read, and the fake mirrors the store and gains `beforeSnapshotRead`.
- Tests:
  - Race subtests "a photo delete" and "a video delete".
  - `TestDeleteImage` and the renamed `TestDeleteVideoDropsTheRowThenTheObjectAndItsObservation` check that the row is gone when storage is reached.
  - `TestDeleteImageLeavesAFailedObjectDeleteToTheSweep` replaces `TestDeleteImageKeepsTheRowWhenStorageFails`.
  - New `TestLearningSnapshotRefusesARevisionDemotedBetweenItsReads`. It fails without the second check.
  - The store's unfinalized-snapshot step now reads status "review".
  - All five F9 cases failed against HEAD's order.
- One further edit: `TestLearningSnapshotReadsAPublishedPost` compares against the pre-publish snapshot, so it now sets `want.Status = published`. The row's status is new in the snapshot, and the learner does not read it.
