## goal
Pressing a saved photo or clip tile in ①'s photo strip opens it large over the page with previous/next through the strip, using the same large view the storyline space uses.

## acceptance
- [v] the large view lives once, in `entities/post` (`AttachmentViewer`), and both the storyline space and ①'s strip use it; `StorylineAttachmentViewer` no longer exists
- [v] a saved photo tile in the strip carries a full-tile press target named `{filename} 크게 보기`; its 회전 and delete buttons stay separate presses above it and still work
- [v] a saved clip tile opens the clip playing with its own controls in the view; the tile itself no longer shows native controls
- [v] the walk is the strip's order (photos, then videos); 이전/다음 and ←/→ move through it; the position reads `n / total`
- [v] uploading, converting or failed tiles open nothing
- [v] a published (read-only) post's strip still opens the view; nothing in the view saves
- [v] the storyline space's large view behaves exactly as before (existing storyline viewer tests pass unchanged except imports/keys)
- [v] tests: PhotoStrip — the view target calls `onView` with the filename, is absent on in-flight tiles, present when `readOnly`; editor — pressing a ① photo opens the dialog showing that photo, 다음 reaches the next attachment, close returns
- [v] lint:fsd passes (no feature imports another feature)

## impl notes
- move `features/edit-storyline/ui/StorylineAttachmentViewer.tsx` to `entities/post/ui/AttachmentViewer.tsx`, export `AttachmentViewer` and a `ViewableAttachment` type (`filename`, `kind: 'photo' | 'video'`, `viewUrl?`, `width?`, `height?`, `rotation?`, `durationMs?`, `contentType?` — the current `StorylineAttachment` shape) from `entities/post`; `StorylineAttachment` becomes an alias of it so storyline code keeps compiling
- i18n: move `storylineEdit.view`, `viewerPosition`, `viewerPrevious`, `viewerNext` from `features/edit-storyline/config/i18n.ts` to `entities/post/config/i18n.ts` as `attachmentViewer.view`, `.position`, `.previous`, `.next` (ko/en, same strings); `StorylineTile` uses `attachmentViewer.view`
- `widgets/storyline-space/ui/StorylineSpace.tsx` imports `AttachmentViewer` from `@/entities/post`; behavior unchanged
- `PhotoStrip` gets `onView?: (filename: string) => void`; when set, each saved photo/video tile renders, as the FIRST child inside `Thumbnail`/`VideoTile`, `<button type="button" aria-label={t('attachmentViewer.view', { file })} className="absolute inset-0 cursor-zoom-in rounded-lg focus-visible:-outline-offset-2" />` — the StorylineTile pattern; the corner buttons come later in the DOM so they paint above it; `VideoTile` gets `controls={!onView}`; in-flight tiles never get it
- `EditorPhotos` owns `viewing: string | null`, builds the walk `[...images, ...videos].filter(viewUrl)` keyed by filename into a `Map<string, ViewableAttachment>`, passes `onView={setViewing}` to `PhotoStrip` and renders `<AttachmentViewer files attachments viewing onView={setViewing} onClose={() => setViewing(null)} />`; a viewed attachment that leaves the post closes the view (the viewer already closes when `viewing` is not in `files`)
- the drop zone must not swallow the press: the view button is a plain button inside the strip, outside any drag handler
