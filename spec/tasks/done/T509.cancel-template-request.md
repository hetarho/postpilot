# T509 Cancel a running template request
> st:done@261001 | ssot:TMPL-63 QUOTA-49 QUOTA-67 | base:TMPL@18 QUOTA@30 | dep:T508 | touches:backend/internal/job backend/internal/usage backend/internal/template backend/cmd/api backend/internal/platform/db/migrations proto/postpilot/v1/template.proto

## goal
An owner can cancel their own queued or running template request: no further call is dispatched, the job ends `cancelled`, and only confirmed usage is charged.

## acceptance
- [v] `TemplateService.CancelTemplateRequest({job_id})`: for the caller's queued or running `template_request` it requests cancellation; a queued one ends `cancelled` with no call; a running one has its context cancelled and dispatches no further correction. Repeating it on a cancelled job is a no-op. On a `done` or `failed` job it returns OK and changes nothing (the client discards the result). A foreign or unknown id, or another kind, is `TEMPLATE_NOT_FOUND`.
- [v] A migration (the next free number when implemented; 0124 at planning, and another session is adding migrations) rebuilds `generation_jobs` in the 0105 style (`NO TRANSACTION`, `PRAGMA foreign_keys=OFF`, every trigger and index recreated, a `foreign_key_check` guard), widening both cancellation CHECKs so `template_request` may carry `cancel_requested_at` with `cancellation_policy_version = 1` and may end `cancelled`. A migration test shows existing rows survive and the new kind is accepted.
- [v] Job layer: the cancellation rule installed with `AllowCancellation` admits `template_request` beside the clip kinds (`cmd/api/job_subjects.go`); `Kinds.Cancellable` includes it; `Queue.Cancel` accepts an account-owned job of a kind the rule declares account-owned, verified by user id instead of a subject; `RequestCancellation` gains an id-and-user variant without a project filter; template requests are enqueued with `CancellationPolicyVersion: 1`.
- [v] Settlement: `usage.SettleCause` accepts `OutcomeCancelled` for a template request's admission (no `ApprovedMaxCredits`), charges confirmed usage only and refunds the rest to the original lots (QUOTA-49); clip settlement is unchanged.
- [v] The handler checks for a requested cancellation before each correction and stops without another call. A cancel racing the final save leaves the job `cancelled`, and `GetTemplateRequestResult` refuses a cancelled job (`TEMPLATE_REQUEST_NOT_READY`).
- [v] Boot recovery: `RecoverCancellations` ends a template request that had a cancellation requested as `cancelled`.
- [v] Tests: cancel while queued (no call, zero charge), cancel while running between calls (no further call, charge equals the confirmed calls), cancel after done (no-op), a foreign id, the settlement refund, the migration test; every existing clip cancellation and settlement test still passes. ARCH-25 verification runs green.

## impl notes
- The four layers that block non-clip cancellation today: the rule in `cmd/api/job_subjects.go` (`clipCancellation`, `Kinds.Cancellable`), the subject check in `internal/job/cancellation.go` `Queue.Cancel` (`!subject.valid() || j.Subject(...) != subject.ID` → `ErrNotFound`), the SQL `RequestCancellation` filtering `clip_project_id` (`internal/job/store/queries/jobs.sql`), and `usage.SettleCause` refusing `OutcomeCancelled` without `ApprovedMaxCredits` and policy version 1 (`internal/usage/service.go`). Generalise each by kind; keep the clip path's behaviour byte-for-byte.
- The rebuild template is `0105_clip_browser_render_sampling.sql`; copy its trigger list from the latest schema, not from 0105, in case a later migration changed one.
- Running jobs already get a cancellable context from the queue (`cancellation.go` registration, `worker.go`), and `FinishJob` writes `cancelled` when `cancel_requested_at` is set; a cancelled in-flight provider call fails and its confirmed usage, if reported, is still recorded by the metered registry. No `AuthorizeDispatch` per call is needed: the check before each correction plus the context is enough for at most four calls.
