# T045 The commit fence: arming, one activation, and readback through the post-view URL

## goal
Arm exactly one final control against a still-current observation, send exactly one activation that can never repeat, and verify the published post by reading it through the account's own post-view URL.

## acceptance
- [v] `ArmFinal` observes the same bound target, requires the arming token to still equal a current observation, and returns exactly one control whose accessible name is in the versioned allowlist; it matches on `data-testid="seOnePublishBtn"` rather than on the hashed class, and a scheduled (`nowTimeRadioBtn` / `preTimeRadioBtn`), generic, renamed or duplicate publish-like control returns a count that refuses to arm
- [v] `ActivateFinal` sends exactly one low-level activation with automatic retry disabled; the port sets an `activated` latch BEFORE the call is issued, so a second `ActivateFinal`, or any `Apply` or `ArmFinal` after it, returns a `PortError` from the port itself and not only from the publisher
- [v] `Readback` navigates the same bound target to `https://blog.naver.com/PostView.naver?blogId=<paired blog>&logNo=<numeric id>`, where the numeric id is taken from the permalink the editor itself reached after activation, and reads the post from that document: title at `.se-module-text.se-title-text`, the block sequence from `.se-component.se-*` in order, images including those grouped into a `se-imageStrip`, captions at `.se-module-text.se-caption`, tags at `.__se-hash-tag` inside `.wrap_tag`, and the category at `.category_title`
- [v] `Readback` returns the CANONICAL permalink `https://blog.naver.com/<blog-id>/<numeric-id>` as the verified URL even though it observed the post-view URL, and `validateReadback` accepts that pair while still rejecting a post for another account, a non-numeric post id, a foreign host, a different bound target, or a body that drifted from the frozen snapshot
- [v] visibility is carried from the verified pre-fence snapshot rather than re-observed, since the published post does not render it (PUB-15)
- [v] a process death simulated before the fence requeues the job, and one simulated after the activation yields `outcome_unknown` with no second activation and no automatic retry (PUB-15)
- [v] the reporter records `filling_settings` before `committing` and the stage sequence is monotonic through `committing → verifying → published` (PUB-13)
- [v] against a fake CDP editor and a fake post-view document, table-driven tests cover: an arming token that no longer matches; a duplicate and a renamed final control; a scheduled control offered beside the immediate one; a second activation attempt; an `Apply` after activation; a readback for another account, a non-numeric id, a foreign host and a different target; a readback whose title, block order, image count, caption, tag order or category drifted; an image count that matches only when strip-grouped images are counted; and the two process-death simulations
- [v] ARCH-27 passes

## impl notes
- T019's `## survey` item 3 is the whole basis for the readback design: the permalink `blog.naver.com/<id>/<logNo>` is a frameset whose iframe is built by JavaScript, so nothing static matches there, while `PostView.naver?blogId=&logNo=` serves the same post in the bound page's OWN top-level document in the editor's own `.se-component` vocabulary. That is why PUB-20 r4 states the observation URL and the reported URL differ, and why no frame-scoped method joins the driver surface
- a real published post on the owner's blog was observed with one `se-documentTitle`, nine `se-text`, eight `se-image`, one `se-imageStrip` and one `se-placesMap`; `se-imageStrip` is a grouped image row the editor vocabulary does not have, so the readback's image count must count images inside strips too or an eight-photo post will read back short
- `observe()` requires the URL to start with `PostWriteForm.naver`, so readback needs its own observation path with its own URL predicate; do not relax `observe()`
- `ActivateFinal` is one `Input` activation on the armed control: no loop, no fallback, no coordinate path and no retry wrapper anywhere in its call chain. An ambiguous outcome after it is the designed result
- the latch must be set before the call is issued, not after it returns, because a crash inside the call is exactly the case PUB-15 turns into `outcome_unknown`
- the owner's queued job `0182794e…` (`20260905-test`) is a live queued fixture, not a test target. No live publication happens in this task; that is T008's explicitly authorized smoke

### the fence
- `ArmFinal` OBSERVES. It re-proves the bound target through a full `Observe`, requires the
  arming token to still equal that observation — so PUB-22's "any subsequent pre-fence
  interaction invalidates the verification" is a property of the arming call rather than a
  convention — and requires the layer to be open with no unversioned publish-like control in
  it. It clicks nothing.
- the final control is matched on the stable `data-testid="seOnePublishBtn"` and must be the
  SAME element as the one `confirm_btn__` in the layer and the one control carrying an
  allowlisted accessible name; the scheduled choice (`nowTimeRadioBtn` / `preTimeRadioBtn`)
  that shares the layer is counted so a layer offering only it refuses instead of guessing
- the armed handle carries no geometry. Its opaque id is derived from the control's
  accessible name and the very observation that armed it, so `ActivateFinal` re-resolves the
  control at action time (PUB-36) and refuses a handle this port did not produce
- `ActivateFinal` sets the latch BEFORE issuing the call, because a crash inside it is
  exactly what PUB-15 turns into `outcome_unknown`. Afterwards the PORT itself refuses a
  second activation, a re-arm, and every `Apply` — the publisher's own refusal is no longer
  the only thing standing between an ambiguous outcome and a duplicate post
- `Readback` waits for the bound page to reach the account's own permalink, takes the numeric
  id from it, navigates to `PostView.naver?blogId=…&logNo=…` and reads the post there. It
  reports the CANONICAL `blog.naver.com/<blog>/<id>` — the observed and reported URLs differ
  by design (PUB-20 r4). `observe()` was NOT relaxed: the readback has its own URL predicate
  (`postViewAccount`) and its own script
- the readback projects the body exactly as the editor script does, because the fence
  compares the two for equality, and it walks an `se-imageStrip`'s member images so an
  eight-photo post cannot read back short. A strip carries one caption for its row, so a
  member with no caption of its own inherits it
- visibility and the category's ID are carried from the verified pre-fence snapshot, since a
  published post renders neither (PUB-15); the category NAME at `.category_title` is what the
  readback actually proves

### the filling_settings stage, end to end
- proto: `PUBLISH_STAGE_FILLING_SETTINGS = 10`, APPENDED rather than numbered into place —
  renumbering `COMMITTING`/`VERIFYING`/`PUBLISHED` would be a breaking wire change for every
  stored and in-flight job
- that appended number is a trap, and it bit twice before the tests caught it: the agent's
  reporter checked monotonicity with `next != stage+1`, and the executor classified
  pre/post-fence failures with `stage >= COMMITTING`. Both read order off the enum's numbers,
  where `FILLING_SETTINGS` now sorts AFTER the fence. Both go through an explicit
  `publisherStageRank` now, matching the server's own `stageRank`, and a test pins the trap
  so nobody reintroduces it
- migration 0037 rebuilds `publish_jobs` to widen the stage CHECK. SQLite cannot alter a
  CHECK, and this table is an FK parent whose `publish_assets` children cascade on delete, so
  it follows 0019's precedent: `NO TRANSACTION` plus an explicit `PRAGMA foreign_keys=OFF`,
  one explicit transaction, every index from 0010 recreated, every column 0012 added
  reproduced with its constraints, and `foreign_key_check` proving the graph before COMMIT.
  Its Down narrows the CHECK again and moves any job parked in `filling_settings` back to
  `uploading_photos` — the stage it legally came from — rather than leaving it unrepresentable
- `migration_0037_test.go` proves the new stage is storable, a misspelled one is not, the
  asset rows survive the rebuild WITH their cascade, all seven indexes came back, and 0012's
  columns kept their constraints
- backend `StageFillingSettings` + `stageRank` + both mapping directions; agent
  `StageFillingSettings` + `publisherStages`; `Prepare` announces it when the settings layer
  opens, and announces `uploading_photos` first for a post with no photo so the server's
  single-step rule still sees a contiguous sequence
- frontend: the stage label, ko and en
