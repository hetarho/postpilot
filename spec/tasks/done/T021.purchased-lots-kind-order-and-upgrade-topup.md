# T021 The purchased lot kind, consumption by kind, and the upgrade top-up
> st:done@260907 | ssot:QUOTA-12 QUOTA-34 QUOTA-35 QUOTA-3 QUOTA-11 | base:QUOTA@4 ARCH@2 | dep:T020

## goal
Add the `purchased` lot kind, make consumption walk lots by kind (monthly → bonus → purchased) before expiry, and make a tier upgrade raise the current cycle's monthly lot by the credit difference on both paths that change a plan.

## acceptance
- [v] migration `0027_purchased_credit_lots.sql` rebuilds `credit_lots` with `CHECK (kind IN ('monthly','bonus','purchased'))`, copies every existing row, keeps the remaining/granted CHECKs, and replaces `idx_credit_lots_user_expiry` with an index that serves the new order (`user_id`, kind rank, `expires_at`, `created_at`); the Down half restores the two-kind CHECK and the old index; a store test opens a fresh database, inserts one lot of each kind and asserts a fourth kind is refused by SQLite
- [v] `usage.LotPurchased` joins `LotMonthly` and `LotBonus`, and any exhaustive mapping over kinds (store row ↔ domain, the plan handler, the FE mapper's `toLot`) carries it
- [v] `LotsInConsumptionOrder` orders by `CASE kind WHEN 'monthly' THEN 0 WHEN 'bonus' THEN 1 ELSE 2 END`, then `expires_at IS NULL`, `expires_at`, `created_at`, `id`; its comment states that kind now orders consumption and is no longer a display distinction, and `pnpm gen:sql` is run with the regenerated code committed (ARCH-28 passes with no diff)
- [v] a service test spends across four lots — a monthly lot expiring soonest, a never-expiring bonus, a never-expiring purchased lot created BEFORE that bonus, and a second monthly lot — and asserts both monthly lots drain first, then the bonus, then the purchased lot ← the purchased lot being the older non-expiring row is exactly the case expiry order alone got wrong
- [v] `usage.Service.TopUpMonthlyLot(ctx, userID, credits)` raises the active monthly lot's `granted` and `remaining` by `credits` inside one write, is a no-op when no unexpired monthly lot exists, refuses a non-positive amount, and is covered by tests for all three cases plus one asserting the `remaining <= granted` CHECK still holds on a lot already partly spent
- [v] `auth.Service.SetUserPlan` computes `plan.MonthlyCredits(target) - plan.MonthlyCredits(current)` before writing, changes the plan, and then tops up by the difference when it is positive and neither tier is unlimited; a downgrade tops up nothing, a same-tier call tops up nothing, and moving to or from `master` tops up nothing; tests cover each
- [v] both paths that change a tier get the top-up: the `AdminService.SetUserPlan` RPC and `api setplan`; a test per path asserts the credit side ran
- [v] `cd backend && test -z "$(gofmt -l .)" && go vet ./... && go build ./... && go test ./...` passes, and `pnpm --filter ./frontend test` · `pnpm lint` pass
- [v] no purchase RPC, no par-rate constant and no payment path in this task — buying credits is BILLING's; the kind exists so the order QUOTA-12 decides is real and testable

## impl notes
- SQLite cannot alter a CHECK, so the migration is the standard rebuild: `CREATE TABLE credit_lots_new (…)` with the three-kind CHECK → `INSERT INTO credit_lots_new SELECT … FROM credit_lots` → `DROP TABLE credit_lots` → `ALTER TABLE credit_lots_new RENAME TO credit_lots` → recreate the index; `credit_hold_lots.lot_id REFERENCES credit_lots(id)` means the rebuild must run with `PRAGMA foreign_keys` off inside the migration or after the goose statement that disables it — check how 0019 and any later rebuild handled it and follow the same shape
- the kind rank is spelled in SQL rather than passed in from Go ← the order is a product rule the query is the only reader of, and a rank passed as a parameter would let two callers disagree
- the top-up seam follows the `provision.CreditGrant` precedent exactly: declare `type MonthlyTopUp func(ctx context.Context, userID string, credits int) error` in `backend/internal/auth/ports.go`, take it as the third argument of `auth.NewService`, and let `cmd/api/main.go` supply `usageSvc.TopUpMonthlyLot`; `provision.SetPlan` gains the same injected func from `cmd/api` (like `GrantCredits`' `grantCreditsTo`) and adapts it before building its own auth service ← credits belong to the usage context and the auth context must not learn about `credit_lots`
- a nil `MonthlyTopUp` makes `SetUserPlan` return an error when an upgrade actually needs a top-up, rather than silently skipping the grant ← losing a paid-for grant quietly is worse than a loud boot-wiring failure; tests that only exercise sessions may pass nil safely because they never upgrade
- the plan write and the credit top-up are two statements, not one transaction: a failure between them leaves the tier moved and the credits ungranted, and the error names that so the operator can finish with `api grantcredits`. BILLING's charge path must revisit this seam when money is involved — record it in the task result rather than papering over it here
- `frontend/src/entities/plan`: `CreditLot['kind']` gains `'purchased'`, `toLot` maps the literal and keeps its unknown → bonus fallback; the account popover's lot list needs a `plans.balance.lotPurchased` label in ko and en (LANG-7 parity) — the popover renders `lot.kind === 'monthly' ? lotMonthly : lotBonus` today and must become a three-way lookup

## result
- migration `0027_purchased_credit_lots.sql`: the three-kind CHECK by table rebuild (NO TRANSACTION + explicit PRAGMA, 0019's shape, because `credit_hold_lots` cascades off this table), `idx_credit_lots_consumption` on `(user_id, kind, expires_at, created_at)`, and a Down that turns a purchased lot into a bonus rather than dropping paid credits
- `usage`: `LotPurchased`, `Store.RaiseLot` behind the new `RaiseLot` query, and `Service.TopUpMonthlyLot` (raises the running cycle's lot, no-op with none, refuses a non-positive amount)
- `LotsInConsumptionOrder` now orders `CASE kind` monthly→bonus→purchased before expiry
- `auth`: the `MonthlyTopUp` port, `Service.SetMonthlyTopUp`, and `SetUserPlan` owing the grant difference on an upgrade only; wired from `cmd/api/main.go` for the RPC path and injected into `provision.SetPlan` (new `CreditTopUp`) for `api setplan`
- `frontend`: `CreditLot['kind']` gains `'purchased'`, `toLot` maps it, and the account popover labels lots through a three-way lookup with the new `plans.balance.lotPurchased` key in ko and en
- tests: kind CHECK and its rollback (`migration_0027_test.go`), the four-lot order with the purchased lot deliberately OLDER than the bonus, `TopUpMonthlyLot` (raise on a partly spent lot, no-op, refusal), the RPC path's top-up and a downgrade owing nothing, the CLI path's top-up and its refusal when none is wired
- deviation from the impl notes, deliberately: the top-up is a `SetMonthlyTopUp` setter rather than a third `auth.NewService` argument. `cmd/api` builds the auth service BEFORE the ledger that implements it (the session sweep needs it first), so a constructor argument would have meant reordering the composition root; the setter is the shape `catalogSvc.SetReasoningSpend` already uses for exactly this. A nil top-up still fails an upgrade loudly, as the notes required
- known non-atomic seam, as the notes anticipated: the tier write and the credit top-up are two transactions. A failure between them returns an error naming both halves so `api grantcredits` can finish it. BILLING's charge path must close this
- trap found and pinned in the query file: sqlc slices the emitted SQL by BYTE offset, so one multi-byte character in a comment shifts every query in `usage.sql` into unparseable text. The first regeneration produced exactly that; the comments are ASCII now and say why
