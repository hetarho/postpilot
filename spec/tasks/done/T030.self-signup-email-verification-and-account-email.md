# T030 Self-signup, email verification before the first session, and the account's email surface
> st:done@260908 | ssot:AUTH-1 AUTH-2 AUTH-3 AUTH-8 AUTH-17 AUTH-30 AUTH-33 AUTH-34 AUTH-35 AUTH-40 QUOTA-9 ARCH-23 | base:AUTH@2 QUOTA@5 ARCH@2 | dep:T029 T034

## goal
Let a stranger open an account with their email, verify the address before they can ever hold a session, and give an existing emailless account the one place it registers an email — with every public answer enumeration-proof.

## acceptance
- [v] `auth.proto`: `Signup{email, password}` → `SignupResponse{}`, `ResendVerification{email}` → `{}`, `VerifyEmail{token}` → `{}`, authenticated `RegisterEmail{email}` → `{}`; `User` gains `string email = 2` and `bool email_verified = 3`; the file comment stops saying there is no Signup RPC; `pnpm gen:proto` run and committed (ARCH-28 no diff)
- [v] `publicProcedures` gains Signup, ResendVerification and VerifyEmail; `TestInterceptorGuardsEveryProcedure` (or a sibling) asserts each is reachable with no cookie and that `RegisterEmail` is 401 without one
- [v] `auth.Service.Signup(ctx, email, password)`: normalizes the email (T029), requires 8–128 characters of password (`auth.PasswordMinLen`/`MaxLen` constants), and answers `nil` identically whether or not the address is taken: an existing account (by id or by email) receives `existingAccountMail` and nothing is written; a new one is created with `ID = email`, `Email = email`, `EmailVerifiedAt = nil`, `Plan = free`, the argon2id hash, then the account bootstraps run, then `verificationMail` goes out with a 24 h `verify_email` link; a test proves both branches return the same value and the taken branch inserted no row
- [v] account bootstraps are a consumer-declared `type AccountBootstrap func(ctx context.Context, userID string) error` list set through `auth.Service.SetBootstraps(...)`; `cmd/api` supplies the default-voice bootstrap and the monthly-lot bootstrap it already gives `adduser` (`EnsureMonthlyLot` — no bonus, AUTH-3 / QUOTA-9); the bootstraps run again inside `VerifyEmail` so a crash between the user insert and a bootstrap is repaired the moment the owner verifies; a test creates a user with a failing bootstrap, then verifies with working ones and asserts the lot and voice exist exactly once
- [v] `auth.Service.VerifyEmail(ctx, rawToken)`: consumes the `verify_email` link (single use, unexpired), sets `email_verified_at`, runs the bootstraps, issues NO session; an unknown, replayed or expired token is `auth.ErrLinkInvalid` → `failed_precondition` reason `VERIFICATION_LINK_INVALID`; tests: verify once ok, replay refused, expired refused
- [v] `auth.Service.ResendVerification(ctx, email)` answers `nil` identically for an unknown address, a verified account and an unverified one, and mails a fresh link (invalidating the older ones) only in the last case; a per-address floor of one mail per 60 s (`auth.ResendFloor`, in-memory map keyed by normalized email, swept as it is read) makes a burst send one mail; tests cover all three answers and the floor

## impl notes
- `users.id = email` for self-signed accounts ← AUTH-33 wants ONE field; the id is already the FK everywhere and what the account menu shows, so the email simply becomes the visible identifier; the `email` column is filled too so one query finds any account by address. Changing a verified email later is not decided by the SSOT and is not built — `RegisterEmail` serves AUTH-40's emailless accounts only
- password length is code-owned (8–128): there is no SSOT rule beyond argon2id; do not add complexity rules ← NIST 800-63B; the FE mirrors the minimum for the field hint and the server stays authoritative with reason `PASSWORD_TOO_SHORT`
- "in the same transaction" (AUTH-3): the writer pool is one connection and the two stores each open their own `BEGIN IMMEDIATE`, so a literal shared transaction would deadlock or need the stores to share a `*sql.Tx` across contexts (ARCH-7); instead the lot is opened right after the user insert with the deterministic id T034 introduces (`monthly:<user>:<cycle start>`) and both the bootstrap re-run in `VerifyEmail` and renew-on-access heal a crash in between — no window exists in which a verified account lacks its lot. Record this reading in the result
- the taken-address branch must cost about what the new-account branch costs on the wire: hash the password anyway before answering (the argon2id work is the same either way), and send the mail from the request goroutine so neither branch returns faster
- `ResendFloor` is in-memory and per process; a restart forgets it — acceptable, T032's per-IP throttle is the abuse control
- FE routes: `/signup` and `/verify-email` are children of the root route beside `/login` and `/about` (structurally public, AUTH-24); `/account` goes under the authenticated layout; the reverse guard for `/signup` reuses the `/login` route's `beforeLoad` body — extract it into `app/routes/publicGuard.ts` rather than copying
- a Korean visitor may type an upper-case address on iOS; normalization on the server is what makes login by email work, so do not `type="email"` the field (legacy ids fail its validation)
- account menu: keep the popover's existing order (id → plan material → links → logout); the new link is a `Link` styled like the `/plans` one

## result
- Added enumeration-safe self-signup, verification/resend, email login and authenticated email registration across the auth domain, Connect contract, handler and public-procedure interceptor; account bootstraps now provision the default voice and anchor-window monthly lot and repair partial signup on verification.
- Added `/signup`, `/verify-email` and authenticated `/account` screens with feature-owned mutations, shared public reverse guarding, bilingual copy, session email fields, login/signup navigation and account-menu entry.
- AUTH-3 consistency reading: signup inserts the user first, then invokes deterministic idempotent bootstraps; verification reruns them. The existing single-writer, independently transacted stores cannot share one SQL transaction without deadlock, so this preserves the task's documented crash-healing interpretation rather than introducing a cross-context transaction.
