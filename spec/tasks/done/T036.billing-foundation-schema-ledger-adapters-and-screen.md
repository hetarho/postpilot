## impl notes
- Toss Payments is the provider ← it offers exactly BILLING-16's four things for a Korean card in KRW (billing-key recurring charges, a hosted card-entry window, a cancel/refund call, webhooks), test keys work without a business registration so every task before go-live is buildable, and the API is plain HTTPS + JSON. PortOne was rejected as an extra intermediary layer over the same PGs; Stripe does not do KRW recurring card billing for a Korean merchant
- the Korea Eximbank daily rate is the rate source ← it is a published base rate (`매매기준율`) whose value for a given day is reproducible afterwards (BILLING constraints), free with an API key, and returns no row on a non-business day, which is exactly the "previous business day" walk-back
- "VAT included" (BILLING-2) is read as: the USD price IS the all-in price and the won charged is `usd × rate` — showing $5 beside a won figure worth $5.50 would contradict the published $5 (MARKETING-5); no 10 % is added on top. Record the reading in the result so update-ssot BILLING can confirm or reverse it (`KRWFor` is the one place to change)
- rates are stored as an integer ×10 000 (`krw_per_usd_e4`) so no float enters the money path, the same posture as micro-USD in the ledger; `KRWFor` rounds half up to a whole won
- `billing_events` is append-only by construction: the store exposes no UPDATE/DELETE for it and a store test proves the sqlc package has none
- the webhook re-read rule (trust the provider's server, not the browser or an unsigned POST) is what satisfies BILLING-16's "the provider's notification … is what makes a charge real" for redirect flows; server-initiated billing-key charges are confirmed by their synchronous response and the webhook only reconciles
- `Routes` on `rpcserver.Options` keeps `rpcserver` free of business meaning: it mounts what it is given, the webhook handler lives in `billing/rpc`
- `Credits`/`Plans`/`Accounts` adapters in `cmd/api` are the only place billing meets usage and auth (ARCH-7); billing never imports either
- master accounts see `/billing` like anyone else but the rung actions never target them (QUOTA-28); nothing in this task needs a master check
- the `billing` namespace is a new entry in LANG-7's list — record in the result that update-ssot LANG should append it
- FE `/billing` is not a primary destination (the nav stays at five/six); it is reached from the account popover, the credit badge popover and `/plans`
