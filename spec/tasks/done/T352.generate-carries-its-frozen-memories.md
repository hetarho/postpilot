# T352 A durable generate carries its frozen memories into the write prompt
> st:done@260924 | ssot:MEM-19 MEM-20 MEM-21 MEM-22 GEN-15 ARCH-24 | base:MEM@1 GEN@10 ARCH@9 | dep:-

## goal
- The memories StartGeneration froze into the payload reach the durable write prompt's `[기억]` section, as MEM-19/20 decide; today `Generate` drops them, so a post with `기억 사용` on is written as if it were off.

## acceptance
- [v] A durable generate whose `GenerateJob.Memories` holds texts builds a write prompt whose per-post half carries one `[기억]` section with exactly those texts in payload order, closed by `memoryPrecedence`; the system half is byte-identical to the same run without memories (MEM-20).
- [v] The drain uses the payload, never a live read: memories changed or deleted between the enqueue and the drain do not change that run's prompt, and the memory port is not called by `Generate`.
- [v] A job with no memories (option off, or a payload written before memories existed) builds a prompt byte-identical to `write_prompt_no_template.golden`'s path today.
- [v] A revision still carries no memories (MEM-22): `Revise` is untouched.
- [v] Tests: `internal/generation/memory_test.go` new `TestADurableGenerateCarriesItsFrozenMemories` (Start with the option on and a recording memory port, replace the port's answer, then `svc.Generate` with the frozen `GenerateJob.Memories`; the write request's `Messages[0].Parts[0].Text` contains `[기억]` and both frozen texts, not the replaced ones; the port recorded one call, from Start) and `TestADurableGenerateWithoutMemoriesIsUnchanged` (a `GenerateJob` without memories carries no `[기억]` bytes).
- [v] Verify: `cd backend && test -z "$(gofmt -l .)" && go vet ./... && go build ./... && go test -timeout 30m ./...`

## impl notes
- Found while writing T344. At HEAD 1a05c1cf the frozen memories travel intact through the payload: `service.go:276` sets `request.Memories`, `generation_payload.go:105`/`:142` encode and decode them, and `cmd/api/jobs.go:81` copies `options.Memories` into `GenerateJob.Memories`.
- The drop is in `internal/generation/generate_handler.go` `Generate`. It copies `job.Template` (line 38) and `job.Guidelines` (line 40) onto the `PostInput` from `s.posts.AttachedImages`, but never `job.Memories`. `write.go:27` then builds the prompt from `post.Memories`, which is always empty on this path.
- Fix: beside the guideline copy, add `post.Memories = cloneTexts(job.Memories)` with the same comment shape ("Same rule for 기억: the frozen texts, never a fresh retrieval (MEM-19)").
- Nothing else changes: the payload shape, `TestGenerationPayloadWireShapeIsPinned`, the goldens and the revise path stay as they are.
- The existing memory suite missed this because `TestMemoriesAreFrozenIntoThePayload` stops at the encode, and `TestMemoriesRenderInThePerPostHalfOnly` calls the prompt builder directly. The new test goes through `Generate`, in the shape of `guideline_test.go`'s drain test (`svc.Generate(ctx, GenerateJob{…, Guidelines: frozen}, …)` and `models.calls[0].request`).
- T344 adds two more frozen members to the same function and names this omission as a trap to avoid. If T344 lands first, keep its copies and add this one beside them.
- Out of scope: retrieval, the `[기억]` wording and the opt-in (T290's, unchanged).
