## goal
Admit and execute every selected lab candidate concurrently against one frozen input, with correct reservation, retry and blind output.

## acceptance
- [v] Observe, post-write and voice-reflection lab starts accept two to five distinct eligible refs; editor starts accept exactly two. Every ref is checked before creating a job, and count/duplicate/ineligible/unsupported requests create no experiment, reservation or provider call.
- [v] All candidates share the same frozen snapshot, hash, prompt version, schema and validation path, differing only by model ref. The service cryptographically shuffles persisted A–E display positions, never exposes ref/label/usage/provider details before ranking completion, and keeps existing LEFT/RIGHT records readable.
- [v] Every candidate call begins concurrently within a five-call bound and contributes to one monotonic comparison progress counter. The enqueue reservation includes every candidate plus shared observation calls; the ledger records each actual call once, including reported usage on failure. Provider work spans no SQLite transaction.
- [v] Partial/failed retry invokes only failed candidates against the original snapshot; enqueue refusal restores their prior failure state. Boot recovery and owner-scoped reads work for five candidates and historical two-candidate rows.
- [v] Existing clients sending only `model_a`/`model_b` still start two-candidate legacy-review comparisons. A request containing both the legacy pair and the new full list is rejected. Legacy winner/dismissal RPCs refuse every new ranking-format record, even one with two candidates.
- [v] Go service, SQL store, RPC and job/admission tests cover two/five candidates, shuffled stable positions, identical inputs, mixed outcomes, retry, eligibility, credits and old-client compatibility; regenerate proto/sqlc and pass ARCH-26/28 checks.

## impl notes
- Add `repeated ModelRef candidates` at free field numbers 4/8/5 in observe/write/voice start requests respectively; this is the full list when present. Preserve existing `model_a` and `model_b` tags and the unspecified-write-origin = editor rule. An empty new list takes the legacy pair; both forms at once are invalid. Persist an explicit `review_mode` discriminator: existing rows default to `pairwise`, legacy-field starts use `pairwise`, and full-list starts use `candidate_ranking`.
- Extend `DisplaySide` with C/D/E enum members while retaining LEFT=1 and RIGHT=2 as the first two display positions; use a domain ordering table, never lexical SQL ordering. A new forward migration after T499 expands the candidate-side CHECK, preserving all columns, indexes, rows and foreign keys in the current schema; regenerate sqlc.
- Replace two-field domain start inputs with a slice constructed at the RPC edge; retain a two-ref adapter for legacy callers if needed. Validate count by origin and stage before `Snapshot`, then resolve every ref. Shuffle slot assignments with `crypto/rand`, persist once and use the saved positions on reads/retry.
- Carry every model ref in `JobRequest.Models` and every planned call in the job's admission pricing. An observe/write preparation call is counted once; duplicate refs are refused rather than collapsed. Keep the current one-job-per-post guard and account access boundary.
- New multi-candidate rows need no pairwise decision during this task; T501 introduces the completion contract before a client offers the new start action.
