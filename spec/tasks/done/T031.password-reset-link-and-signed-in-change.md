# T031 Password reset by a 1-hour emailed link, and the signed-in password change
> st:done@260908 | ssot:AUTH-4 AUTH-17 AUTH-30 AUTH-35 AUTH-40 AUTH-8 | base:AUTH@2 ARCH@2 | dep:T030

## goal
Let a locked-out owner reset a forgotten password through a single-use emailed link that ends every live session, and let a signed-in owner change it through the same store path with the current password as the proof.

## acceptance
- [v] `auth.proto`: `RequestPasswordReset{email}` → `{}`, `ResetPassword{token, new_password}` → `{}`, authenticated `ChangePassword{current_password, new_password}` → `{}`; `pnpm gen:proto` committed (ARCH-28 no diff); `publicProcedures` gains the first two and a test asserts `ChangePassword` is 401 without a cookie
- [v] `auth.Service.RequestPasswordReset(ctx, email)` answers `nil` identically for an unknown address, an unverified account and a verified one, and only the verified one is mailed: `InvalidateLinks(user, reset_password)` then `CreateLink` with a 1 h expiry, then `passwordResetMail`; tests cover the three identical answers, that an older link is dead once a newer one is issued, and the same 60 s per-address floor T030 introduced applies
- [v] `auth.Service.ResetPassword(ctx, rawToken, newPassword)`: consumes the `reset_password` link (single use, unexpired), validates the new password (T030's length rule), writes the argon2id hash and runs `DeleteSessionsForUser` in that order; an invalid, replayed or expired token is `ErrLinkInvalid` → `failed_precondition` reason `RESET_LINK_INVALID`; an rpc test logs in, requests a reset, resets, and proves the pre-reset cookie is 401 on `GetMe`
- [v] `ResetPassword` does NOT clear `failed_logins` or `locked_until` — the lock releases itself (AUTH-37) and no mailed link may unlock an account (AUTH-38); a test pins it
- [v] `auth.Service.ChangePassword(ctx, userID, current, next)`: an account whose `password_hash` is empty (Google-only) is refused with `PASSWORD_NOT_SET` (failed_precondition) and told to use the reset flow; otherwise the current password is verified with the real argon2id work, a wrong one is `CURRENT_PASSWORD_WRONG` (failed_precondition — never `CodeUnauthenticated`, which the client reads as a lost session), and a correct one takes the same store path as the reset: new hash, then every session of the account deleted, the current one included
- [v] FE `pages/forgot-password` at `/forgot-password` (public, reverse-guarded like `/login`): one email field and one CTA; after submit the page states that a mail was sent if an account exists, identically for every address; the login page gains `비밀번호 찾기 / Forgot password` beside `회원가입` — below the CTA, outside the form (AUTH-30)
- [v] FE `pages/reset-password` at `/reset-password` (public, no guard): reads `token`, shows a new-password field with the length hint and one CTA; success renders `로그인 / Log in`; `RESET_LINK_INVALID` renders the localized failure with a link to `/forgot-password`
- [v] FE `pages/account` gains a `features/change-password` section (current, new; one action); on success the app drops the session cache, navigates to `/login` and the login page shows a one-time status `비밀번호를 바꿨어요. 다시 로그인해 주세요. / Password changed. Please log in again.` carried through router state (not a search param); the account page hides the section and shows a hint to use the reset flow when `GetMe` says the account has no password (add `bool has_password = 4` to `User`)
- [v] `errors` namespace gains `RESET_LINK_INVALID`, `PASSWORD_NOT_SET`, `CURRENT_PASSWORD_WRONG`, `PASSWORD_TOO_SHORT` in ko and en; the reason ↔ catalog test (LANG-24) passes
- [v] gates: ARCH-25 · ARCH-26 · ARCH-28; FE tests for both public pages and the change-password section (wrong current → inline failure; success → login with the status line)

## impl notes
- one store path for both (AUTH-4): `auth.Service.setPassword(ctx, tx-free, userID, newHash)` = `UpdatePasswordHash` then `DeleteSessionsForUser`; the reset and the change call it after their own proof (link vs current password). Ending the current session on a change is the literal reading of "the same store path" — the FE handles it as a normal logout with a status line rather than special-casing the mutation
- an unverified account is deliberately not mailed a reset: the address has not been proven and a reset link would turn into a second verification path; the owner resends the verification instead (T030). Note it in the result if it surprises the owner
- `RequestPasswordReset` and `Signup` share the taken/unknown timing concern: build the link and the mail regardless of the branch so both return in about the same time; the argon2 work does not apply here, so keep the branches symmetrical in I/O
- `has_password` on `User` exists only so the account page can pick the right section without a probe; it reveals nothing to a stranger (`GetMe` is authenticated)
- router state for the one-time status: TanStack Router `navigate({ to: '/login', state: { notice: 'password-changed' } })` typed through `Register`'s `HistoryState`; the login page reads `useRouterState().location.state` once and renders a `Notice` (tone info) above the form

## result
- Added enumeration-safe reset requests, one-hour single-use reset links and signed-in password changes across the auth service, Connect contract and SQL store. Reset and change share `setPassword`: the new argon2id hash is durable before every account session is revoked, while lockout columns remain untouched.
- Added `/forgot-password`, `/reset-password` and the account password section with feature-owned mutations, bilingual failures and hints, `has_password` session mapping, and a one-time post-change login notice carried only in router history state. Unverified accounts deliberately receive no reset mail because the address has not been proven; they continue through verification resend.
