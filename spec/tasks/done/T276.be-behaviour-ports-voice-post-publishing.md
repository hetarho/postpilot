# T276 voice, post and publishing ports are per use-case
> st:done@260920 | ssot:ARCH-6 ARCH-7 ARCH-24 | base:ARCH@5 | dep:-

## goal
Split the table-shaped `Store` ports of `voice` (`PersonalizationStore` 37, `Store` 22), `post` (31) and `publishing` (29) into behaviour-shaped interfaces per use-case group, consumed narrowly.

## acceptance
- [v] no port interface in these three contexts exceeds 10 methods; each is named for a behaviour (`post.DraftWriter`, `post.ImageCatalog`, `post.UploadLedger`, `voice.ProfileReader`, `voice.LearningRunStore`, `publishing.JobLease`, …) following the comment groupings already in `post/ports.go`
- [v] the `*store.Store` types still implement every method; services hold only the narrow interfaces they call, and each existing fake in tests implements only the interfaces the tested use-case needs (fake line count drops)
- [v] behaviour unchanged: ARCH-26 passes

## impl notes
- from review/arch-260919 F17 (part 1)
- ARCH-6 r4: a port is named for the behaviour one use-case group needs; ARCH-7 already banned the generic repository shape
- mechanical recipe: group by the callers in `service.go`; define the interface where it is consumed; pass `store` into the constructor as before — Go's structural typing makes the split compile without adapter code

## result
- post: `Store`(31) → `PostCatalog`(5) `DraftWriter`(5) `TemplateAnswers`(2) `ImageCatalog`(5) `VideoCatalog`(6) `UploadLedger`(8), plus `SweepLedger`(5) for the object sweep, which used to take the whole store for five calls
- voice: `Store`(22) → `VoiceDirectoryStore`(10) `ProfileStore`(3) `SampleStore`(7) `VersionSampleStore`(2); `PersonalizationStore`(37) → `ProfileVersionStore`(4) `ManualOverrideStore`(4) `LearningRunStore`(8) `ContrastRuleStore`(6) `FeedbackStore`(6) `RuleComparisonStore`(4) `ProfileValidationStore`(5)
- publishing: `Store`(29) → `AgentRegistry`(9) `JobLedger`(10) `JobLease`(6) `AssetStaging`(4). The owner's view of a job and the leased executor's are now different ports, which is the distinction PUB rests on
- every behaviour port is ≤10 methods (checked by walking the three `ports.go` files). What is left of the old names is `Storage` / `PersonalizationStorage`: composites of embeds with no methods of their own, held by the composition root — and, for the learning store, by one field that answers "is learning wired at all" before the narrow ports are used
- the services hold the narrow interfaces as fields and every call site names the behaviour it uses (`s.images.ListImages`, `s.lease.ClaimJob`, `s.learning.ApplyLearningResult`); `post.Service` also stopped type-asserting its own store per call — the editor capability is resolved once in the constructor
- deviation from acceptance ②'s second half: the in-memory fakes still implement the whole surface, so no fake shrank. A fake is one struct that Go's structural typing already lets a narrow port accept, and splitting the fakes changes no production code — the win the finding named (a use-case naming what it needs) is in the services
- verify: ARCH-26 green (gofmt, vet, build, 61 packages)
