## goal
An owner's template request runs as an account-owned job on the write model the client names, and leaves a checked name, description, title area, body and wishes list for the client to read.

## acceptance
- [v] `TemplateService.StartTemplateRequest` takes `{ModelRef write_model, Language language, string text, TemplateDraft draft{name, description, title_area, body}, optional string template_id, optional string sample_post_slug}` and returns `{string job_id}`. Refusals happen before any hold:
  - trimmed `text` over `TEMPLATE_REQUEST_MAX_CHARS` → `TEMPLATE_FIELD_TOO_LONG` (`field` `request`); blank `text` with no sample → new `TEMPLATE_REQUEST_EMPTY`
  - a draft field over its own ceiling → `TEMPLATE_FIELD_TOO_LONG` naming it; an unparsable draft body is accepted (the request may be "fix this")
  - a `template_id` that is not the caller's → `TEMPLATE_NOT_FOUND`; no `template_id` while the account holds `TEMPLATE_MAX_PER_ACCOUNT` templates → `TEMPLATE_LIMIT_REACHED`
  - a sample slug that is missing, foreign or has no canonical content → new `TEMPLATE_SAMPLE_UNAVAILABLE`
  - a write ref that is missing, unknown, disabled or not serving write → `GENERATION_WRITE_MODEL_REQUIRED` (the reason post generation gives); plan grade and credit refusals come from the hold at enqueue and map as `generation/rpc/handler.go` maps them (`MODEL_*`, `INSUFFICIENT_CREDITS`)
  - another of the account's template requests queued or running (`job.ErrAlreadyInProgress`) → new `TEMPLATE_REQUEST_RUNNING`
- [v] The job is kind `template_request`: no subject and no guard (the account-only unattached rule), `WriteModel` set, payload the frozen JSON input (language, text, draft, template id, the sample already serialized at start), `PricingCalls: [{Ref: write, Stage: "write", Count: 1 + TEMPLATE_REQUEST_CORRECTIONS_MAX, CompletionTokens: TemplateRequestCompletionBudget}]`, registered in `registerJobs` through `metered`.
- [v] The sample is the post's title and canonical blocks as plain text: TEXT as paragraphs, HEADING as `## `/`### ` lines, LIST items as `- `, QUOTE as `> `, every IMAGE block as one `[사진]` line (consecutive ones kept consecutive); captions, VIDEO blocks, summary, tags, memo, photos, observations, voice and guidelines are not sent.
- [v] The handler sends `System = FormatGuide(language) + request rules(language)` and one user message with labelled sections for the request text, the current draft (each of the four fields, `(비어 있음)`/`(empty)` when blank) and the sample when present; `Stage: write`, `Reasoning: llm.ReasoningLow`, `MaxTokens: TemplateRequestCompletionBudget`, and the JSON schema `{name, description, title_area, body, wishes: [string]}` (all strings) when the model has structured output.
- [v] The request rules (ko and en constants in `guide.go` beside the guide) say: answer with the JSON object only; the title area admits literal text, `<write>` and `<ask>` only; the name and description ceilings; keep every field the request does not ask to change and fill the empty ones; carry no sentence of the sample as 고정 문구 unless the request asks for it; a `<write>` or instructing `<ask>` names what stands there, never how to write; wishes about tone, length, emphasis or what to leave out go to `wishes`, never into the template; never output a target length or tag count.
- [v] An answer is checked by the same rules as a typed draft through one in-package `validDraft(name, description, titleArea, body)` that `Create` also uses (not a copy): trimmed name non-empty ≤ 40, description ≤ 200, body non-empty ≤ 4000, title area ≤ 200, `ParseTemplate` and the ask-label ceiling. Wishes are trimmed, blanks dropped, the first `TEMPLATE_REQUEST_WISHES_MAX` kept, each cut to `TEMPLATE_REQUEST_WISH_MAX_CHARS` scalar values.
- [v] Correction: on a JSON decode failure or a rule failure the next call carries the original messages, the previous answer as an assistant message and a user message naming the failure (parse: area, line, reason; field: field, max, actual), at most `TEMPLATE_REQUEST_CORRECTIONS_MAX` times. Truncation, a content filter or a provider error is not corrected and fails as the LLM error normalizes. Still failing after the last correction → the job fails with new durable reason `TEMPLATE_REQUEST_ANSWER_INVALID`. Every call is metered, and settlement refunds the unused hold.
- [v] On success `SaveResult` writes `{name, description, title_area, body, wishes}`. `TemplateService.GetTemplateRequestResult({job_id})` returns it for the caller's `done` template request; a foreign or unknown id or another kind is `TEMPLATE_NOT_FOUND`, a job not `done` is `FailedPrecondition` with new `TEMPLATE_REQUEST_NOT_READY`. Status polling stays `GenerationService.GetGeneration`.
- [v] Config: `TEMPLATE_REQUEST_MAX_CHARS` 12000, `TEMPLATE_REQUEST_CORRECTIONS_MAX` 3, `TEMPLATE_REQUEST_WISHES_MAX` 5, `TEMPLATE_REQUEST_WISH_MAX_CHARS` 200 in `platform/config` beside `TemplateCeilings`, read from env with those defaults and passed to the template service from `cmd/api`.
- [v] The new reasons are in `error.proto`, `appFailureSpecs` and both error catalogs; `failure_reasons_test.go` and `resources.test.ts` pass. The template.proto service comment says StartTemplateRequest is the one procedure that enqueues work.
- [v] Tests: each start refusal; the enqueued payload and planned calls; with a fake model — success on the first answer; a parse failure corrected on the second call; three failed corrections end in `TEMPLATE_REQUEST_ANSWER_INVALID` after four metered calls; truncation is not corrected; wishes trimmed and capped; the sample serialization; the prompt carries no voice, guideline or other template; `GetTemplateRequestResult` ownership and readiness. ARCH-25 verification runs green.

## impl notes
- Placement (TMPL constraints): the request's prompt, answer check and handler live in `backend/internal/template` (`request.go`), with ports in `ports.go` for the model (`Resolve`, `Complete`), the sample (`RequestSample(ctx, userID, slug)`), the job queue (enqueue, result) and the template count; adapters in `cmd/api` (`adapters_template.go`). Model the sample adapter on `memoryPosts.ExtractionSource` (`cmd/api/adapters_memory.go`), which reads `post.Service.Get` and maps `post.ErrNotFound`.
- Write-ref pre-check: copy generation's `Resolve` / `Disabled` / `ServesStage(llm.StageNameWrite)` block (`generation/service.go` `Start`) through the model port. `Stage: "write"` on both the planned call and each request is required: with model grades on, `Registry.Complete` refuses a call whose (ref, stage) was not admitted.
- Account-only job: pass no `Subjects` and no `Guards`; `Enqueue` then checks `ActiveUnattached`, backed by the partial unique index `generation_jobs_active_user_kind_idx`. No migration is needed for a non-cancellable kind (there is no CHECK on `kind`); T509 adds cancellation and its migration.
- `TemplateRequestCompletionBudget` is a package constant of 8192, used in the call and in the planned call, as `generation.StorylineCompletionBudget` is. The hold then prices `4 × (30 000 input + 8192 output)` at the model's prices (QUOTA-14, QUOTA-67).
- Result on the job row follows `extract_memory`: `Queue.SaveResult` (guarded by `status='running'`) and `Queue.Result`; read the payload only when the status is `done`, since until then it holds the input. Do not clear it after reading: job content retention is open for every kind in `JOB-RETENTION-TODO.md`, and this kind stays like the others.
- The correction loop is modelled on `clip/ai/response_correction.go` `completeValidated`, but sends the previous answer back (TMPL-60 asks for the refusal's line, which is meaningless without the answer it points into). A durable failure reason is an error implementing `Failure() llm.Failure`, mapped by `cmd/api/job_reporting.go`.
- `error.proto`, `app-failure.ts` and the error catalogs are being edited by another session (T499–T506): take the next free enum numbers from the file as it stands when this task is implemented.
