# T180 Author a character maximum in the template editor
> st:done@260916 | ssot:CLIP-116 CLIP-113 CLIP-71 CLIP-58 | base:CLIP@25 ARCH@2 | dep:T179

## goal
Give the composition editor a 최대 글자 수 control bounded by what each position allows, and describe `chars` in 원문 errors and the copied 형식 안내.

## acceptance
- [v] the builder shows a 최대 글자 수 control on an information-field row and on a text or slot row, bounded by that position's derived cap with the cap stated beside it, and clearing it means 자동
- [v] a region slot row shows its preset's cap (아웃트로 E의 display 6자) so the author sees the ceiling before typing a number
- [v] a pasted 원문 whose `chars` exceeds its position shows `invalid_max` at its 1-based line in plain words with 저장 disabled, like every other authoring error (→CLIP-71 →CLIP-113)
- [v] 형식 안내 복사 documents the attribute and the per-position caps, so an outside AI writes a number the parser accepts
- [v] ko and en copy for the control, its cap hint and the new reason
- [v] tests: the control clamps to the cap and round-trips through the body, the guide text carries the attribute, and the new reason renders at its line
- [v] verify FE (ARCH-25) passes

## impl notes
- surfaces: `entities/clip-template/ui/CompositionBuilder.tsx` for the row, `CompositionTextControls.tsx` for the element fields, `model/composition-guide.ts` for the copied format guide, and the reason copy beside the existing ones in `app/providers/i18n/resources/{ko,en}/clips.ts`
- the number input is a `shared/ui` primitive with tokens only (ARCH-20); no hand-rolled control and no arbitrary values
- the control writes the attribute through the same node edit path the other attributes use, so the draft stays lossless between the builder and 원문 (→CLIP-71)
- the cap shown is the one T179 computes; the editor must not derive its own number

## result
- the control is the editor's own `CompositionInput` in `numeric` mode, the way group min already reads, with a new `hint` line under it carrying the cap. A Stepper was the other candidate and is wrong here: a field's bound is the 500-character answer ceiling, which no one steps to
- three positions carry it — a region slot row, an information row and an element's own text — plus the information field row in the builder. The cap each shows comes from `compositionPositionChars`, exported from the parse lib for this, so the editor never derives a number of its own
- `boundedChars` clamps what the control accepts, so the editor cannot author the `invalid_max` the parser refuses; that reason stays for a body that arrives already written, and its copy is in ko and en beside the other reasons
- 자동 is the attribute's ABSENCE, not a zero: emptying the control deletes it, keeping the draft the body the author would have typed (CLIP-71)
- one defect found and fixed on the way: both row editors replaced the row's whole attribute map when changing kind or role (`attributes: { kind }`), which silently dropped any sibling attribute. They now spread
- the copied 형식 안내 documents `chars` on field, text and row, that it may only be smaller, and every per-position number including info rows and the uncapped badge and caption
- tests: the clamp against outro E's 6-character display, a body round-trip that keeps `chars` through serialize/parse, the pasted-body refusal naming the element and its 1-based line, and two guide assertions. ko/en parity is covered by the existing resources test
