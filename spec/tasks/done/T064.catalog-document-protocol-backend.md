# T064 The catalog document: parser, whole-document sync and the three RPCs
> st:done@260909 | ssot:MODEL-51 MODEL-52 MODEL-53 MODEL-54 MODEL-55 MODEL-56 MODEL-13 MODEL-15 | base:MODEL@7 ARCH@2 | dep:-

## goal
Parse, validate, preview, apply and render the `# postpilot models v1` document so one paste syncs each named purpose's registrations whole.

## acceptance
- [v] `backend/internal/modelcatalog/protocol.go` holds pure `ParseDocument(text) (Document, []LineError)` and `RenderDocument(map[Purpose][]string) string`: first non-blank line must be `# postpilot models v1`, `[<purpose>]` headers, one model id per line, further `#` comments · blank lines · surrounding whitespace ignored
- [v] parse rejects with a 1-based line number and a cause each: unrecognized version line, unknown purpose header, a line that is neither header nor id, an id before any header, a duplicate id inside one section
- [v] validation against the live snapshot rejects, grouped by cause: an id no candidate holds, an unlisted model, a provider-disabled model, a model failing the purpose's capability gate (`Purpose.EligibleFor`)
- [v] any rejection refuses the whole document — no registration, deregistration or row write happens
- [v] `Service.PreviewDocument(ctx, text)` returns per purpose the ids it would register, deregister and leave unchanged, plus every rejected line, and writes nothing
- [v] `Service.ApplyDocument(ctx, text)` parses and validates the text again from scratch (it accepts no preview token) and applies every named purpose in ONE store transaction; a purpose with no section keeps its registrations
- [v] an id with no `catalog_models` row is created from the live snapshot as part of the apply, the same write `RegisterPurpose` makes
- [v] a deregistration behaves exactly like `SetModelPurpose(registered=false)` on that row, effort override included
- [v] a failed live read refuses both preview and apply, reporting the fetch error, and writes nothing
- [v] `Service.ExportDocument(ctx)` renders all five purposes with registered ids sorted deterministically; a purpose with no registration is an empty section; no comment lines beyond the version line
- [v] `proto/postpilot/v1/model_catalog.proto` gains `PreviewCatalogDocument` `ApplyCatalogDocument` `ExportCatalogDocument` on `ModelCatalogService`, master-only like its siblings, with no key or base URL field; generated code regenerated and committed
- [v] `store.SyncPurposes` applies the whole per-purpose delta in one transaction and is covered in `store_test.go`, including a mid-apply failure leaving nothing written
- [v] `protocol_test.go` covers every parse and validation rejection above, and a round trip: `ExportDocument` → `ParseDocument` → `PreviewDocument` reports no change
- [v] `service_test.go` covers preview-writes-nothing, apply creating a row for an uncurated id, omitted-id deregistration, untouched purpose, and refusal on fetch error
- [v] `cd backend && test -z "$(gofmt -l .)" && go vet ./... && go build ./... && go test ./...` (ARCH-26)
- [v] `pnpm gen:proto && git diff --exit-code -- backend/internal/gen frontend/src/shared/api/gen agent/internal/gen` (ARCH-28)

## impl notes
- placement: pure parse/render in `modelcatalog/protocol.go`, the three use-cases as `Service` methods in `service.go`, the transaction as one new `Store` method in `ports.go` implemented in `store/store.go` — the context already owns registration writes, so nothing new crosses ARCH-7's inward rule
- the live read is mandatory for preview and apply (`Upstream.Fetch`), because a recommended id that was never curated has no `catalog_models` row and only the snapshot can create one; a fetch failure is therefore a refusal, not a degradation — `ListCatalog` still degrades to curated rows as before, this path does not
- no migration: MODEL-52 writes only `catalog_model_purposes` rows the existing schema already holds, and reads no column the document could carry
- the export is byte-stable so MODEL-55's "pasted back is a no-op" is a real test: fixed purpose order (`modelcatalog.Purposes`), ids sorted within a section, `\n` endings, one trailing newline
- rejected lines cross the wire as `{line, cause, text}` with an enum-like cause string, not as a normalized failure reason — `MODEL_PURPOSE_INELIGIBLE` and `MODEL_PURPOSE_NOT_REGISTERED` already have no entry in the FE reason catalog (MODEL constraints, LANG owns it), and this surface is master-only admin copy anyway
- `SetModelPurposeRequest`'s comment still says deregistering keeps the reasoning override, which MODEL-20 r5 and `Store.RefreshAvailability` contradict; confirm the live behavior and fix the stale comment in the same change rather than copying it into the new RPCs
- `model_selections` is never touched: a deregistration strands a saved selection and `GetSelections` reports it `missing` on the next read exactly as an operator's uncheck does (MODEL-24)

## result
- files: `backend/internal/modelcatalog/protocol.go` (new: parse + render) · `document_test.go` `protocol_test.go` (new) · `service.go` (+`PreviewDocument` `ApplyDocument` `ExportDocument` `planDocument` `rowFromCandidate`; `SetPurpose` now shares the overlay) · `types.go` (+`PurposeWrite`) · `ports.go` (+`SyncPurposes`) · `store/store.go` (+`SyncPurposes`) · `store/store_test.go` `service_test.go` (+cases, fake made faithful) · `rpc/handler.go` (+3 procedures) · `auth/rpc/interceptor.go` (master set) · `proto/postpilot/v1/model_catalog.proto` + regenerated Go/TS
- the parser is strict about shape and forgiving about whitespace: a table row, a bullet, a backticked or quoted id is `malformed_line` rather than a guess. Two sections for one purpose is `duplicate_section` — under MODEL-52 each is supposed to be the whole membership, so the pair has no meaning
- an id the successful live read does not carry splits into two causes: `unknown_model` when nothing is curated under it, `unlisted_model` when a row exists. The operator's next move differs
- a refused document is an answer, not a transport error: apply returns the same plan shape as preview with `applied = false`, so a rejection the catalog moved into renders exactly like one caught at preview
- `INSERT OR IGNORE` on the registration means the schema's purpose CHECK cannot refuse an unknown purpose — it would be skipped in silence. `SyncPurposes` now parses the purpose per write, inside the transaction, so a bad one rolls back what the document already wrote; that is what the atomicity test drives
- two stale comments fixed, both predating migration 0021: `Store.DeregisterPurpose`'s doc and `SetModelPurposeRequest`'s in the proto both claimed the reasoning override survives a deregistration. It does not — the effort is a column on the registration row the DELETE removes. The test fake shared the same wrong belief and now drops it too
- differs from SSOT: MODEL-53 lists a "provider-disabled model" as a reject cause, but this context has no per-model notion of one. There is a single provider and it is disabled exactly when its key is unset (MODEL-11), which is installation-wide and explicitly not a bar to curating — `SetModelPurpose` has no such check either. The cause is not implemented; update-ssot should drop the clause from MODEL-53 or move it to where the key is known
- also differs: MODEL-53 says "an id no catalog row holds" is refused, which reads against MODEL-52 and against the live-read decision this task was built on — a recommended id that was never curated has no row, and registering it is the point. Implemented as "an id the merged catalog does not offer"; the wording wants the same update-ssot pass
