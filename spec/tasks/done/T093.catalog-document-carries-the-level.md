# T093 The catalog document carries the level: `<id> [level]` lines, relevel preview, level-aware sync and export
> st:done@260911 | ssot:MODEL-59 MODEL-52 MODEL-53 MODEL-54 MODEL-55 MODEL-57 | base:MODEL@9 ARCH@2 | dep:T092

## goal
Extend the `# postpilot models v1` document so each id line may name the registration's level, the preview reports level changes, the apply writes them in the same transaction, and the export emits them.

## acceptance
- [v] `ParseDocument` accepts an id line as `<id>` or `<id><whitespace><level>`: the first token must still pass `looksLikeModelID`, a second token must be one of the four `Level` values, a third token is `malformed_line`; the version line stays `# postpilot models v1` and every document valid before this task still parses to the same registrations with every level unset
- [v] a second token outside the four values is rejected as a new cause `unknown_level` with its line number and text, and like every other issue refuses the whole document (MODEL-53)
- [v] `DocumentSection` holds `Entries []DocumentEntry{ModelID, Level, Line}` (replacing the parallel `ModelIDs`/`Lines`), and a duplicate id inside one section stays `duplicate_id` whatever the levels say
- [v] `PurposeWrite` gains `Level`; `planDocument` emits one write per listed id with the document's level (`""` when the line carried none) and `Store.SyncPurposes` sets the registration's `level` for EVERY listed id after its `INSERT OR IGNORE` — a line without a level clears an existing one (MODEL-59), all inside the one transaction; a deregistration still deletes the row and its level
- [v] `DocumentPurposePlan` gains `Relevel []LevelChange{ModelID, From, To}`: the ids that already hold the purpose and whose level the document would change (including to or from unset); a newly registered id is listed under `Register` only, an id whose level is unchanged stays under `Unchanged`
- [v] proto `CatalogDocumentPurposePlan` gains `message CatalogDocumentLevelChange { string model_id = 1; string from = 2; string to = 3; }` as `repeated CatalogDocumentLevelChange relevel = 5`; the handler maps it
- [v] `RenderDocument` takes the level per id and writes `<id> <level>` with one space when set and `<id>` otherwise, ids still sorted within a section, output still byte-stable; `ExportDocument` feeds it the current levels
- [v] `protocol_test.go` covers: id-only, id+level, three tokens, unknown level, tab-separated tokens, a mix within one section, and render of set/unset lines
- [v] `service_test.go` / `document_test.go` cover: preview reporting `Relevel` and writing nothing, apply clearing a level via an id-only line, apply setting a level on an already-registered id, the round trip `ExportDocument` → `ParseDocument` → `PreviewDocument` reporting no register, deregister or relevel, and a mid-apply failure leaving levels untouched (`store_test.go`)

## impl notes
- MODEL-59 keeps the version at `v1` because the grammar only widens: every old document is a valid new document with the same meaning. A document written with levels and pasted into an older build is refused line by line (`malformed_line`, since the old `looksLikeModelID` rejects whitespace) rather than misapplied — the failure mode is loud, which is what the version line is for
- the level is written by the sync for every listed id, not only for changed ones: MODEL-52 says a section is the purpose's whole state, and the write is idempotent. This is also why an exported document pasted back is a no-op — the export writes every set level, so the sync sets each to what it already is and `Relevel` is empty
- `Relevel` is separate from `Unchanged` so the panel can make level changes visible without inflating the deregistration list (MODEL-54); the FE side lands in T094
- the level write in `SyncPurposes` is the same `UpdateCatalogModelPurposeLevel` statement T092 added for the single-row edit, run inside the sync's transaction after `AddCatalogModelPurpose` — one statement, two callers, as `AddCatalogModelPurpose` already is
- the test fake `Store` in `service_test.go` must model the level per registration so the round-trip test drives the real contract rather than a stub that ignores the second token

- `DocumentSection`'s parallel `ModelIDs`/`Lines` became `Entries []DocumentEntry`; the three existing tests reading them were rewritten, and the round-trip test now carries one graded and one ungraded registration so it proves both halves of MODEL-59
- **tightened `looksLikeModelID` to require a `vendor/model` slash.** Splitting a line on whitespace made a markdown bullet (`- openai/gpt-x`) parse as the id `-` with the level `openai/gpt-x`, reported as `unknown_level` — it used to be `malformed_line`, and pointing the operator at the wrong half of the line is worse than the old answer. Requiring the slash restores it exactly. No id the source publishes lacks one (MODEL-18 takes the segment before it as the grouping key) and no existing test used a slashless id; a genuinely slashless id now reads `malformed_line` rather than reaching validation as `unknown_model`. Pinned by the `bullet kept` case
- an already-registered id whose grade moves is `Relevel`, not `Unchanged`; a NEW registration is `Register` only, since its grade is part of arriving rather than a change to something that was there
- every listed id gets a level write, not only the moved ones — the write is idempotent and it is what makes the section the purpose's whole state. That is also why an exported document pastes back as no change
