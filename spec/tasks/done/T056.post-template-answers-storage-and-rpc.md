# T056 The post's template answers: table, autosave field, and the way to generation
> st:done@260909 | ssot:POST-62 POST-13 POST-4 TMPL-43 | base:POST@3 TMPL@4 ARCH@2 | dep:-

## goal
Give a post a durable, per-label set of template answers that autosave through SavePostDraft and reach the enqueue as part of the post's input.

## acceptance
- [v] migration `0033_post_template_answers.sql` (embedded, boot-run): `post_template_answers(post_slug TEXT NOT NULL REFERENCES posts(slug) ON DELETE CASCADE, label TEXT NOT NULL, answer TEXT NOT NULL DEFAULT '', enabled INTEGER NOT NULL DEFAULT 1, updated_at TEXT NOT NULL, PRIMARY KEY(post_slug, label))` — the column is `answer`, not `text` (see result)
- [v] `post.TemplateAnswer{Label, Text, Enabled}` in the post context's domain; the store upserts one row per present answer in one transaction of its own, ahead of the draft update in the same request, and lists a post's answers ordered by label
- [v] proto: `TemplateAnswer{label, text, enabled}`; `SavePostDraftRequest.repeated TemplateAnswer template_answers = 8` documented as upsert-per-entry (an entry sets that label, an absent label is preserved, an empty list changes nothing, and no entry ever deletes); `Post.repeated TemplateAnswer template_answers` so a reload seeds the fields
- [v] the handler refuses `InvalidArgument` for a blank label, a label over `TEMPLATE_ASK_LABEL_MAX_CHARS`, a text over `TEMPLATE_ASK_VALUE_MAX_CHARS` (`POST_TEMPLATE_ANSWER_TOO_LONG` with `field` `max` `actual`) and two entries naming one label, validated before anything else in the request applies

## impl notes
- a child table rather than a JSON column on `posts` (owner's call): one row per label makes a single-field autosave one upsert instead of a read-modify-write of the whole set, which is what keeps POST-62's per-field presence honest when two tabs answer two fields; it also inherits the `images`/`videos` cascade pattern this schema already uses
- the table belongs to the POST context — the answers are part of the post aggregate, keyed by a label the template happens to have authored, and no foreign key points at a template. That is deliberate: TMPL-43's labels are text, not ids, and POST-62 keeps an answer whose label the current template no longer carries
- upsert only, never delete: clearing an answer is `text: ""`, which the freeze already treats exactly like the switch being off (→TMPL-45). No RPC deletes a row, so a label typed under an earlier template survives a swap back
- `enabled` defaults to 1 and an answer with NO row is treated as on with empty text: the field exists because the template says that data is required, so it must be presented switched on, and a blank answer is dropped at the freeze anyway — an off-by-default field would silently mean "never ask"
- validation order matters: the label/text checks run with the `template_id` validation POST-26 already does before the request applies anything, so a bad answer mints no post and changes no title
- the answers are NOT in the generation payload: the freeze bakes them into the rendered body (T057), so nothing here touches `generation_payload.go`. `PostInput` carries them only so `freezeTemplate` can pass them to the template context
- proto field 8 on `SavePostDraftRequest` — 7 is unused but check the file before claiming a number

## result
- files: migration `0033_post_template_answers.sql` · `proto/postpilot/v1/post.proto` (+ regenerated Go/TS/agent) · `internal/post/store/queries/post_template_answers.sql` (+ generated sqlc) · `internal/post/{types,ports,service}.go` · `internal/post/store/store.go` · `internal/post/rpc/handler.go` · `internal/generation/types.go` · `cmd/api/main.go` · `internal/platform/rpcserver/failure_reasons_test.go` · `shared/api/app-failure.ts` · i18n ko/en `errors.ts` · new tests in `internal/post/{template_answer_test.go,fake_test.go}`, `internal/post/store/template_answer_store_test.go`, `internal/post/rpc/handler_test.go`, `cmd/api/bootstrap_test.go`
- the column is `answer`, not the planned `text`: `text` is a SQLite type keyword, and the generated Go field reads better as `Answer` beside `Label` than a column that shadows a type name. The domain field stays `Text`, which is what POST-62 calls it
- the answers are written in their OWN transaction, ahead of the draft update, rather than atomically with the title and memo: `UpdateDraft` is a separate store method, and making the two one write would mean a new combined store method for no guarantee anyone needs — the client sends the whole current draft on every debounce, so a half-applied save is corrected by the retry that follows it. POST-62 asks for one QUEUE, not one transaction
- proto field 7 on `SavePostDraftRequest` (the plan guessed 8; 7 was free) and 24 on `Post`
- an answer with no stored row is `enabled` by default in the schema, so the field the write screen renders for a label nobody has answered is switched ON — the field exists because the template requires that data, and a blank one is dropped at the freeze anyway (T057)
- `AttachedImages` had to grow the answers too, not just `Get`: it is the projection the enqueue reads, and without them every data field would have resolved as if the author had answered nothing
- two new public failure reasons are registered on both halves of the cross-language contract (`POST_TEMPLATE_ANSWER_TOO_LONG`, `POST_TEMPLATE_ANSWER_INVALID`); a blank label and a repeated label share the second one because neither is something a screen can produce
- `pnpm gen:sql` mis-slices its own output when a `.sql` file holds a multi-byte character — the first generated constant came back truncated and the next started mid-word. Every other query file in the repo is pure ASCII; this one now says so in a comment at the top
