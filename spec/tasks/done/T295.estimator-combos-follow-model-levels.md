# T295 Estimator combos follow the four model levels
> st:done@260921 | ssot:MODEL-58 QUOTA-39 | base:MODEL@11 QUOTA@14 ARCH@5 | dep:-

## goal
Make every estimator card share the model catalog's four levels and accept only photo-analysis and writing registrations carrying that card's level.

## acceptance
- [v] The estimator combo contract, plan response, admin assignment response and ko/en UI use exactly `value` · `balanced` · `premium` · `top` in model-level order, with no `quality` or `cheapest` value left in active code or generated contract comments.
- [v] An embedded SQLite migration maps `cheapest→value` · `value→balanced` · `balanced→premium` · `quality→top`, recreates the combo constraint, and retains only rows whose photo-analysis and writing registration levels both equal the mapped combo; its migration test pins retained and dropped rows.
- [v] Assignment is refused unless both models are registered for their required purpose and each purpose registration's level equals the combo; reads expose no stale assignment or plan rates after either registration is relevelled, with modelcatalog and RPC tests covering valid, unlevelled, mismatched and relevelled cases.
- [v] Each admin card's photo picker lists only photo-analysis registrations at that card's level and its writing picker lists only writing registrations at that card's level, using purpose-specific catalog reads; a frontend test proves wrong-level and unlevelled models are absent and a valid pair sends the level slug.
- [v] Plan estimator types, fixtures and screen tests accept and label only the shared four levels, and the existing pricing arithmetic remains unchanged.
- [v] `pnpm gen:proto` and `pnpm gen:sql` leave committed generated code current; `pnpm --filter ./frontend test`, `pnpm lint`, `pnpm lint:fsd`, `pnpm lint:style:probe && pnpm lint:style`, `pnpm build:web`, and `cd backend && test -z "$(gofmt -l .)" && go vet ./... && go build ./... && go test ./...` pass.

## impl notes
- Reuse `modelcatalog.Level`/`Levels` and the frontend `LevelName`/`LEVELS` as the combo vocabulary and ordering authority; keep combo assignment as a distinct domain concept but do not maintain a second four-value list.
- Add migration `0071`: rebuild `estimator_combos` because SQLite cannot replace its CHECK constraint in place; copy through a CASE mapping joined twice to `catalog_model_purposes` on `photo-analysis` and `writing`, requiring each joined `level` to equal the mapped destination before renaming the table.
- Validate and read through one service helper that loads each model and checks purpose plus exact level; `Combos` returns the four cards with empty ids for a stale row, while `ComboRates` omits it, so releveling takes effect without deleting or mutating from a read.
- The admin feature must issue separate cached `ListCatalog` reads for `photo-analysis` and `writing`, because `CatalogEntry.level` is the requested purpose's registration level; aggregate their loading/error states and take assignment ids from one response.
- Keep the mutation payload and proto fields as strings for wire compatibility; only the accepted string vocabulary and comments change, so no field numbers move.
