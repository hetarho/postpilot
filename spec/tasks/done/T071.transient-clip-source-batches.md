# T071 Transient clip-source batches and cleanup
> st:done@260910 | ssot:CLIP-2 CLIP-6 CLIP-21 CLIP-22 CLIP-23 CLIP-26 ARCH-6 ARCH-7 ARCH-10 ARCH-11 ARCH-21 ARCH-24 | base:CLIP@1 ARCH@2 | dep:T069

## goal
Accept source videos by direct-to-object-storage upload as an expiring batch, retain metadata only, and make deletion retryable on every exit path.

## acceptance
- [v] migration `0036_clip_source_batches.sql` creates `clip_source_batches` and `clip_source_leases`; rows keep project/user ownership, provider-neutral object identity, metadata, state and expiry only, never source bytes or a durable project attachment
- [v] one `CreateClipSourceBatch` request carries the complete manifest and returns one batch id plus per-source id, presigned PUT URL, required headers and expiry; the API body never carries video bytes
- [v] the authoritative gate accepts 1–20 `mp4|mov|m4v|webm` sources, positive browser-read duration/dimensions, at most 30 minutes combined, at most 2 GiB per file and 8 GiB per batch, unique non-empty fingerprints, and matching extension/content type
- [v] object keys are `clip-inputs/{userID}/{batchID}/{sourceID}.{ext}` with no original filename or project title; the stored filename is display metadata only
- [v] `ConfirmClipSource` HEAD-checks object size and signed content type, deletes a refused object, records the actual byte count and marks the batch ready only after every lease is confirmed
- [v] creating a replacement batch first marks the previous non-consuming batch for cleanup; `DiscardClipSourceBatch` is owner-scoped and idempotent
- [v] cleanup marks a batch `cleanup_pending`, deletes each object idempotently and removes the rows only after every delete succeeds; one failed delete leaves enough identity for the periodic and boot sweep to retry
- [v] abandoned uploading/ready batches expire after six hours and a ten-minute sweep retries them; a consuming batch is cleaned by T076/T078 and is never reclaimed merely because its original upload expiry passed
- [v] deleting a clip project invokes the same cleanup before deleting its row and fails closed if cleanup cannot be made retryable
- [v] config and FE-mirror constants name count, duration, byte, container and TTL limits; both env examples gain only operational sweep/TTL overrides if the existing upload convention requires them
- [v] store/service/RPC/storage-adapter tests cover owner isolation, all aggregate limits, replace, confirm mismatch, partial cleanup failure, boot retry and the absence of bytes from RPC/DB
- [v] ARCH-26 and ARCH-28 pass

## impl notes
- reuse the private R2/MinIO bucket through a `clip.ObjectStore` port and extend `internal/storage` with only the presign/head/delete behavior that port needs; the browser remains the upload data path
- use a batch-level manifest so the server can enforce count and combined duration before handing out the first URL and so T076 can price the exact number of 60-second analysis chunks
- fingerprint = SHA-256 over a version byte, file size, MIME, duration, and the first/last 64 KiB computed in T072; it is a re-selection identity, not proof against a malicious owner, and the media probe in T073 remains authoritative
- states: batch `uploading|ready|consuming|cleanup_pending`; lease `pending|ready`; no completed state survives cleanup
- never put signed URLs in SQLite or logs; they are minted for one response and expire with the existing upload TTL
