# T422 A resolved extraction job keeps neither the post body nor the raw candidates
> st:done@260927 | ssot:MEM-15 MEM-16 | base:MEM@4 | dep:-

## goal
Once an extraction job's candidates are resolved, its payload no longer holds the frozen source or the raw candidate list, and nothing can re-read them.

## acceptance
- [v] resolving the last candidate (approve, dismiss, bulk) clears the extraction job's payload in the same transaction; `Service.Extraction(jobID)` answers nothing for a resolved job — tests
- [v] unresolved candidates still read as before
- [v] verify BE: `cd backend && test -z "$(gofmt -l .)" && go vet ./... && go build ./... && go test -timeout 30m ./...`

## impl notes
- from review/conformance-all-260927 F26
- Pre-alpha: existing resolved payloads may be cleared by a forward migration or left; prefer clearing them in the migration

## result
- the ruling is on the server now: `ResolveMemoryExtraction(job_id, approved)` (memory.proto) creates the approved candidates from the STORED list — by index, with the post as their source, through the same create rules and cap — and discards the rest; once every approved one is stored, `ClearCandidates` → `Queue.ClearResult` → the new `ClearFinishedPayload` query empties the job's payload, and `Service.Extraction` then answers `ErrExtractionResolved` (NotFound `MEMORY_NOT_FOUND`). A refused candidate comes back by index and keeps the extraction readable for a retry; the ones that saved deduplicate on it (`extraction_test.go`: create-and-clear, discard-all, refused-keeps-readable, bad index; `rpc/handler_test.go`; job store `TestClearFinishedPayloadEmptiesOnlyTheOwnersFinishedJobOfTheKind`)
- frontend: the candidate sheet approves with the one call (per-row reasons come back from the response), and closing the sheet is the ruling that approves nothing, so the payload goes with it, as the existing "discarded with the sheet" test says (`ExtractMemoriesButton.test.tsx`)
- migration `0092_clear_resolved_extraction_payloads.sql` empties every finished extraction's payload (there was no server ruling to tell resolved ones apart, and the extraction is repeatable); a queued or running one keeps its frozen source (`migration_0092_test.go`)
- differs from the acceptance's "same transaction": the memories and the job row belong to two contexts, so the clear runs after the creates, only when all succeeded; a crash between them leaves the payload for a retry, which deduplicates, so nothing is stored twice and nothing unresolved is lost
