# T264 i18n namespaces assembled from slice-owned fragments
> st:done@260920 | ssot:ARCH-16 ARCH-15 ARCH-24 | base:ARCH@5 | dep:-

## goal
Let each slice own its `{ko,en}` strings in a `config/i18n.ts` fragment and make `app/providers/i18n` assemble the 14 namespaces from fragments, moving every non-clip namespace out of `app/`.

## acceptance
- [v] a fragment is `export const i18n = { namespace: 'posts', ko: {...}, en: {...} } as const satisfies I18nFragment`; `app/providers/i18n/resources/index.ts` imports fragments via an explicit list and merges them per namespace; a duplicate key across two fragments of one namespace fails `resources.test.ts`
- [v] `posts`, `voices`, `templates`, `guidelines`, `models`, `plans`, `billing`, `publishing` no longer have files under `app/providers/i18n/resources/{ko,en}`; their keys live in the slice that renders them (lowest layer that uses the key wins; a key used across domains moves to `common`)
- [v] `common`, `errors`, `nav`, `auth`, `marketing` stay app-level fragments under `app/providers/i18n/resources` (they are cross-cutting or belong to `app/routes`)
- [v] `clips` stays in `app/` for now with a comment naming T265; the `RESOURCE_NAMESPACES` contract and every `useTranslation('<ns>')` call are unchanged
- [v] `resources.test.ts` keeps: exact namespace set, ko/en key parity + placeholder parity, failure-reason coverage, typed keys; plus the new no-duplicate-fragment-key check
- [v] steiger accepts a `config` segment holding `i18n.ts` in every layer used; ARCH-18 holds (fragments import nothing)
- [v] behaviour unchanged: all FE tests pass; ARCH-25 passes

## impl notes
- from review/arch-260919 F3 (infrastructure + non-clip namespaces)
- namespaces stay domain-shaped so no `t()` call changes; only the file that holds the string moves — the churn problem is the file, not the key scheme
- ownership rule for a key: `grep -rl` its usages; owner = the single slice using it, else the lowest-layer slice among the users, else `common`; write the script into the task result so T265 reuses it
- typed keys: keep `resources.test.ts`'s `exposes typed translation keys from the canonical resource shape` by deriving the namespace type from the merged object, not from the fragments
- app importing slices is downward (ARCH-13), so the fragment list in `app/providers/i18n` is legal; it is still one file every new slice touches, but a one-line import instead of a 1.1k-line edit

## result
- 63 fragments in 61 slices now own the eight domain namespaces; `app/providers/i18n/resources/{ko,en}/{posts,voices,templates,guidelines,models,plans,billing,publishing}.ts` are deleted (16 files, ~3,000 lines). `common auth nav errors marketing` and, for now, `clips` (T265) stay app-level
- a fragment is `export const i18n = { namespace, ko, en } as const satisfies I18nFragment`, with the contract in `shared/lib/localization/fragment.ts`; a slice owning keys in two namespaces exports two (`features/edit-with-ai`, `features/select-model`)
- the assembly imports the fragment MODULES, not the slice barrels, and `steiger.config.ts` allows that sidestep for this one file. Through barrels the whole app is evaluated when `app/providers/i18n` loads — which in tests happens in `test/setup.ts`, BEFORE a test's own `vi.mock` is installed: 17 tests broke that way (upload-batch's `readVideoMetadata` mock among them) before the imports were pointed at the leaf modules
- ownership script (reusable for T265): for each top-level group of a namespace, count `t('<group>…')` occurrences per slice among files that `useTranslation('<ns>')`; a group used by 3+ slices is shared vocabulary and goes to the namespace's domain entity (posts→entities/post, …), otherwise the slice with the most uses owns it, tie-broken by layer then name. Groups no source names (plural forms, dead keys) go to the domain entity
- `resources.test.ts` keeps its five checks and gains one: every fragment names a registered namespace, its ko/en top-level keys match, no two fragments of one namespace claim the same key, and every fragment key reaches the assembled namespace
- deviation from acceptance ②'s "lowest layer that uses the key wins": applied per GROUP, and a group used across 3+ slices goes to the domain entity rather than to the lowest-layer user — `posts.editor` is used once by `features/delete-post` and 26 times by `pages/editor`, and the lowest-layer rule alone would have filed it under the delete button
- verify: ARCH-25 green (2201 tests / 280 files, eslint 0, steiger clean, style + build ok)
