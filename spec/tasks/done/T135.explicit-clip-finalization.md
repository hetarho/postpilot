# T135 Finalize a matching clip result and delete its originals
> st:done@260913 | ssot:CLIP-2 CLIP-20 CLIP-24 CLIP-36 CLIP-75 CLIP-76 CLIP-77 CLIP-82 ARCH-3 ARCH-6 ARCH-7 ARCH-10 ARCH-24 | base:CLIP@12 ARCH@2 | dep:T134

## goal
Make finalization an explicit irreversible project transition that preserves the confirmed result and cleans up originals.

## acceptance
- [v] FinalizeClipProject accepts only an owned valid saved plan with the requested revision, a matching successful render and no active attempt; it performs no AI call, rendering or credit debit.
- [v] Confirmation, its result identity and durable original-deletion intents commit together; the project immediately refuses new original URLs, uploads, editing, generation and rerender while result preview/download remain available.
- [v] Repeated confirmation and ambiguous-response retry return the same finalized result; a concurrent edit/start/delete cannot produce an incorrectly confirmed or replaceable result.
- [v] Cleanup failure/restart retries deletion without reopening editing or losing the confirmed MP4; previous signed PUTs cannot permanently recreate deleted originals.
- [v] Existing completed renders migrate to unfinalized editing with result/plan revisions unchanged; already-deleted originals are reported absent and migration performs no implicit finalization.
- [v] Store/RPC/integration tests cover valid and stale revisions, missing/invalid result, active/queued/cancelling jobs, foreign actor, duplicate requests, simultaneous start/edit/finalize, storage failure, late upload, template deletion and legacy rows.
- [v] Run applicable ARCH-25 through ARCH-29 local gates, deterministic proto/SQL generation and spec lint; preserve unrelated generated changes using a before/after snapshot.

## impl notes
- Add nullable finalized_at, finalized_plan_revision and finalized_result_key to clip_projects with an all-null or all-present consistency constraint. Existing rows remain null; no backfill from rendered_plan_revision. These are domain confirmation records, not a persisted UI step counter.
- Add FinalizeClipProject(project_id, expected_revision, expected_result_id) → ClipProject. Add an opaque result ID to stored results and ClipResult, minted for each committed candidate; backfill legacy results deterministically without revealing object keys. It identifies the render the owner saw even if two renders share a plan revision or timestamp. A revision/result conflict returns failed_precondition with a typed reason and refreshed project; foreign IDs remain not found.
- In one serialized write transaction, check the unchanged valid saved plan, rendered revision/result identity, project fence and absence of queued/running work including pending cancellation, then record finalization, source_access_revoked_at and T133 cleanup intents. Reuse transaction-bound stores/coordinator from T134 through domain-owned ports; do not open a database transaction around object storage deletion.
- Result completeness comes from the committed successful candidate and stored media metadata, not a new provider call or re-encode. A source-expired project can still finalize its matching retained result because confirmation needs no original pixels. A changed draft must be saved and rerendered first; finalization never auto-exports or rolls the draft back to an older render.
- Guard every source/project/plan mutation, quote/start/activation and staged-result commit with finalized_at IS NULL in its write predicate. Keep owner Get/List/result signing/delete available; reusable template edits/deletion must not mutate finalized composition, result or confirmation identity.
- Once confirmation is durable, deny issuance of new original URLs and run object deletion as bounded best effort; a retryable cleanup error does not turn a committed confirmation into an editable project or a failed render. Internal cleanup_pending remains an operations concern, while known physical deletion failures must not be described as already completed cleanup.
- Preserve source tombstones through the last outstanding upload capability expiry and sweep recreated keys under T133. Existing signed GETs may survive until physical deletion/URL expiry; never claim client-side URL revocation alone erased a private object.
- Expose confirmation fields and can_edit/can_finalize refusals through entity adapters as derived server projections. T136 owns the post-like save flush and step transition; direct RPC calls enforce the same conditions independently of UI state.
