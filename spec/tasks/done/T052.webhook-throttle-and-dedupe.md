# T052 A bounded provider webhook
> st:done@260908 | ssot:ARCH-6 ARCH-23 | base:ARCH@2 | dep:-

## goal
Bound how often an anonymous POST to `/webhooks/toss` can spend the product's provider quota, and stop the same provider state from being appended twice.

## acceptance
- [v] the webhook route is rate-limited per client IP before the handler issues any outbound provider call, using the same throttle the authenticated public writes use
- [v] a refused request answers without calling the provider and without writing a row
- [v] the client IP is resolved the same way the auth interceptor resolves it, honouring the configured client-IP header
- [v] `provider_notifications` gains a uniqueness rule over the provider event's identity so a repeat of the same state is not appended again, and the insert is written to tolerate that conflict rather than fail on it
- [v] a genuine new state for the same order is still recorded
- [v] a well-formed notification for a payment the provider does not know still answers without writing a row, as it does today
- [v] tests cover: a burst past the limit being refused with no provider call; the same notification delivered twice producing one row; two different states for one order producing two rows; and the throttle isolating one IP from another
- [v] ARCH-26 passes

## impl notes
- from review/diff-260908 F6
- the defect: `rpcserver.Options.Routes` mounts the route on the bare mux and its own comment says these handlers bypass Connect interceptors by design, so the auth interceptor's throttle never sees it. Every anonymous POST therefore forces one `GET /v1/payments/orders/<id>` against Toss, and a guessed real order id appends to a table with no dedupe key and no retention
- the handler is already right about trust — it re-reads the payment from the provider and never persists facts from the public body — so this task adds only the bound, and changes nothing about what is believed
- reuse rather than duplicate: add a webhook class to `auth`'s `throttleRules` and wrap the route in `cmd/api` with a small middleware that calls `throttle.Allow(class, auth.ClientIP(header, peerAddr, cfg.ClientIPHeader), time.Now())` before delegating. Wiring in the composition root is where ARCH-6 puts it, and it keeps `billing/rpc` from importing `auth`, which ARCH-7 would not allow
- the dedupe key is `(provider, order_id, status, event_type)`: Toss's ordinary payment webhook carries no event id of its own, so the state transition itself is the only available identity. The cost is that a true repeat of one transition is recorded once — acceptable, since the first arrival's `received_at` is the fact that matters
- retention is deliberately NOT in this task: nothing in ARCH or BILLING states a retention rule for provider notifications, and inventing one here would be a policy decision rather than an implementation

## result
- Changed: new migration `0032_provider_notification_identity.sql` (unique index over `(provider, order_id, status, event_type)`, preceded by a one-time dedupe keeping each group's earliest row) · `billing/store/queries/billing.sql` (`InsertProviderNotification` gains `ON CONFLICT DO NOTHING`) and its regenerated sqlc · `auth/throttle.go` (+`ThrottleWebhook`, 60 per minute per IP) · `cmd/api/main.go` (+`throttledRoute`, wrapping the webhook route) · tests: new `cmd/api/webhook_throttle_test.go`, new `billing/store/provider_notification_test.go`, and a payment-not-found case in `billing/rpc/webhook_test.go`.
- The rate is a judgement the task left open: 60/minute/IP is far above the provider's own deliveries and retries at this product's scale, and bounds a hostile IP to 60 provider calls a minute. It sits beside the other classes in `throttleRules`, code-owned like them (ARCH-21).
- The dedupe DELETE was run against a table holding real duplicates (a repeat, a second state for the same order, and two rows with an unknown order): it keeps the first arrival, keeps the distinct state, leaves NULL-order rows alone, and the index then rejects a third identical row while the insert's `ON CONFLICT` tolerates it.
- The throttle burst test does not hardcode the window size — it pins that a burst is refused, that a refused request never reaches the handler, and that one IP's window is its own.
- Retention is deliberately still absent, as the task states: no ARCH or BILLING decision defines one. Worth an update-ssot if the table's growth ever matters.
- Nothing diverged from ARCH-6 / ARCH-23; no update-ssot owed.
