# T181 An answer cannot be typed past its maximum
> st:done@260916 | ssot:CLIP-117 CLIP-102 CLIP-118 CLIP-5 | base:CLIP@25 ARCH@2 | dep:T179

## goal
Enforce a field's effective maximum where the answer is typed, and name the field when an answer stored earlier still exceeds it.

## acceptance
- [v] every answer input carries its field's effective maximum: no character is accepted beyond it, a paste is truncated to it, and a live 글자 수/한도 counter sits with the field, replacing today's single global check against 500 (`ClipCompositionInputs.tsx:33`)
- [v] a field with no maximum of its own still shows the grammar's own ceiling, so no field loses the counter it has today
- [v] required and optional semantics are untouched: the maximum never makes a blank optional field invalid and never relaxes a required one (→CLIP-5 →CLIP-60)
- [v] generation admission refuses an answer above its maximum with the field's label, the maximum and the actual count, naming the field rather than an element and line (→CLIP-102)
- [v] `answer_limit` renders that sentence in ko and en through the existing special case in `shared/lib/localization/failure.ts:13`, the way `items_required` already does
- [v] tests: typing and pasting are capped per field; a stored over-long answer produces the labelled refusal instead of a line-numbered one
- [v] verify BE (ARCH-26) and FE (ARCH-25) pass

## impl notes
- no new failure code: `CLIP_COMPOSITION_INVALID` (`rpc/handler.go:130`) gains `label`, `max` and `actual` parameters and `formatAppFailure` gets `answer_limit` beside `items_required` — that special case exists for exactly this shape, and the allowlist in `shared/api/app-failure.ts:112` is where the new parameters are declared
- the server check lives in `Resolve` (T179), so the quote path, the save path and `composition_admission.go:52` all inherit it without a fourth copy
- the only ways to reach that refusal are an answer saved before the template tightened its number, a project switched to another template, and a direct API call — the browser can no longer produce one; it stays a refusal and never a silent truncation (→CLIP-118)
- truncating a paste is the one place characters are dropped, and it happens while the owner watches the counter, not behind their back
- the counter reads the effective maximum from the parsed document; it does not recompute a cap from the design tokens

## result
- the answer control reads `document.maxima` and bounds what it accepts with `boundedAnswer`, the longest prefix that fits, counted CDS-20's way. Typing simply stops at the bound and a paste is cut to it; the existing `FieldCount` primitive carries the live counter, so a field that reaches no bounded position still counts against the 500 it counted against before
- required and optional are untouched: the bound never inspects presence, and the blank-optional and missing-required messages are the ones that were already there
- `composition.Problem` gained `Label`, `Max` and `Actual`, set only by the `answer_limit` refusal, and one `FailureParams` method now owns the mapping to the failure contract — the durable generation failure (`generation.go:159`) and the RPC boundary (`handler.go:130`) were building that map separately and would have drifted
- `formatAppFailure` gets the `answer_limit` case beside `items_required`, reading label/max/actual; without a label it falls through to the generic sentence, which is what a direct API call with no field still produces
- the TypeScript owner carries the same three fields so both grammars refuse identically; the shared corpus records them on its answer_limit case and the frontend corpus test compares them when a case declares them
- tests: the bounded input (typing stops, paste truncated, counter against the field's number, a stored over-long answer marked invalid), the labelled failure mapping in Go with a regression that other reasons gain nothing, and the ko/en refusal sentence
