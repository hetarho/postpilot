# T285 job addresses a subject instead of naming each product
> st:done@260919 | ssot:ARCH-6 ARCH-10 ARCH-11 ARCH-24 | base:ARCH@5 | dep:T270

## goal
Give `generation_jobs` the one derived subject column it lacks and collapse `job`'s per-product lookups and clip activation into one subject-addressed surface, without rebuilding a single trigger, index or foreign key.

## acceptance
- [v] a goose migration derives the one subject that has no column of its own: a VIRTUAL generated `experiment_id` plus `generation_jobs_experiment_idx`; no existing trigger, index, column or constraint is dropped, rewritten or rebuilt, and `PRAGMA integrity_check` plus the existing migration test still pass on a migrated temp DB
- [v] `job.Store` exposes `ActiveFor(ctx, Subject, Filter)`, `LatestFor(ctx, Subject, Filter)` and `ActiveUnattached(ctx, userID, kind)` in place of `ActiveForPost ActiveForPostUser ActiveForVoice ActiveForVoiceKind ActiveModelExperiment ActiveForClip LatestForClip`; `job.Subject` is `{Dimension, ID}` with dimension strings supplied by callers, and the dimension→column mapping exists only in `job/store`
- [v] `job.Queue` offers `Activate(ctx, user, id)`, `SweepUnactivated(ctx, failure)` and `Snapshot(ctx, user, subject, id)`; the deferred-activation kinds arrive as a constructor argument (ARCH-40) instead of the `kind IN ('generate_clip','render_clip','revise_clip')` literal in `ActivateClip`/`SweepUnactivatedClips`, and `ClipStore` as an optional interface assertion is gone
- [v] `NewJob`/`Job`/`JobSummary` carry `Subjects []Subject` and a `Subject(dimension)` accessor instead of `PostSlug VoiceID ClipProjectID`; the enqueue conflict guards arrive as `NewJob.Guards` from the adapter that knows the kind, so `voiceOwnedKind` and the post/voice/clip branching leave `job`; the rpc projection still emits the same proto fields
- [v] a `job/store` test over a migrated temp SQLite pins: a `learn_voice` job carrying a post is found by BOTH the voice dimension and the post dimension; a clip job is found by its project dimension and not by another user's; a `model_experiment` job is found by its experiment dimension; `ActiveUnattached` still ignores subject-carrying rows
- [v] behaviour unchanged: ARCH-26 passes and ARCH-28's `pnpm gen:sql` diff is clean

## impl notes
- from review/arch-260919 F15 (part 1 of 3; T272 is the credit allowance, T286 the ledger naming)
- owner decision 260919, option C (generated-column bridge): `clip_project_id` is the axis of 13 triggers (`clip_projects_busy_*`, `generation_jobs_clip_owner`, `clip_finalized_job_*`, `video_templates_detach`, …), 2 partial unique indexes and a `clip_projects(id) ON DELETE SET NULL` foreign key. A real `subject_kind`/`subject_id` migration would rebuild all of them and lose the FK to hand-written triggers, so the generic addressing is DERIVED from the columns that stay
- the generated column must be VIRTUAL, not STORED: SQLite's `ALTER TABLE ADD COLUMN` refuses a STORED generated column, and a table rebuild is exactly what this decision avoids. A VIRTUAL generated column can still be indexed, which is where the lookup cost goes
- a single derived `(subject_kind, subject_id)` pair was dropped during implementation because it cannot be read without changing behaviour: a `learn_voice`/`compare_voice_rule` row holds a voice AND a post ([jobs.sql:92](backend/internal/job/store/queries/jobs.sql#L92)) so one pair would hide the second attachment from "is this post busy"; a `model_experiment` row holds post, voice AND its experiment id, so any precedence hides the dimension the experiment lookup needs; and `ActiveUnattached`'s `post_slug IS NULL AND clip_project_id IS NULL` deliberately still matches a voice-only job, which `subject_kind=''` would not. What the bridge is actually for is the one dimension with no column — the experiment id in `payload`, now derived and indexed
- `ActiveFor`/`LatestFor` take the dimension the caller asks for and `job/store` resolves it to that dimension's column (`post_slug`, `voice_id`, `clip_project_id`, `experiment_id`), keeping today's query shapes and plans; the two-dimension test above is what keeps "is this post busy" and "is this voice busy" answering as they do today
- dimension strings belong to the context that owns the subject (`post.JobSubject`, `voice.JobSubject`, `experiment.JobSubject`, `clip.JobSubject`); `job/store` keeps its own column table and refuses an unknown dimension rather than silently matching nothing
- `ActiveUnattached` keeps today's `post_slug IS NULL AND clip_project_id IS NULL` meaning exactly
- out of scope, do not touch: the credit reservation/allowance and the cancellation store (T272), any usage/ledger naming (T286), and the SQL of other contexts that joins `generation_jobs.clip_project_id` (clip/store recovery, checkpoints, generation — the column stays, so they keep working)

## result
- done@260919. `internal/job` addresses work by `Subject{Dimension, ID}`: `NewJob`/`Job`/`JobSummary` carry `Subjects` (+ a `Subject(dimension)` accessor) instead of `PostSlug VoiceID ClipProjectID`, the store's seven per-product lookups collapse into `ActiveFor`/`LatestFor`/`ActiveUnattached`, and `ActivateClip`/`SweepUnactivatedClips`/`ClipJobSnapshot`/`LatestClipSnapshot`/`ClipStore` become `Activate`/`SweepUnactivated`/`Snapshot`/`LatestSnapshot` on the ordinary `Store`.
- Changed: `migrations/0068_job_experiment_subject.sql` (new) · `job/subject.go` (new) · `job/{job,queue,query,ports,clip,cancellation}.go` · `job/store/{store.go,queries/jobs.sql,sqlc/*}` · `job/rpc/handler.go` · `clip/generation_ports.go` (+`clip.JobSubject`) · `post/ports.go`, `voice/ports.go`, `experiment/ports.go` (+`JobSubject`) · `clip/app/{jobs,ports,finalizer,finisher}.go` · `clip/rpc/{handler,cancellation}.go` · `cmd/api/{job_subjects.go (new),jobs,clip,contexts,adapters_*}.go` · tests in 6 packages (+`job/store/subject_store_test.go`, `cmd/api/job_subjects_test.go`, 5 `subjects_helper_test.go`).
- The conflict rules left the queue with the subjects: `NewJob.Guards` states "refuse if work is already active on this subject", so `voiceOwnedKind` and the post/voice/clip branching now live in `cmd/api/postVoiceWork` (unit-tested there), and the queue only walks the list. No guard at all still means the unattached (user, kind) default.
- Differs from the task as written, decided during implementation and recorded in impl notes: the derived pair `subject_kind`/`subject_id` was dropped for a single `experiment_id`. A single pair cannot be read without changing behaviour — a `learn_voice` row holds a voice AND a post, an experiment row holds post, voice and its own id, and `ActiveUnattached` deliberately still matches voice-only work. The one dimension that genuinely had no column (the experiment id inside `payload`, previously scanned) is now a VIRTUAL generated column with an index. No trigger, index, column or foreign key was touched, which was the point of the owner's decision.
- Out of scope, left for T272 as planned: `job` still holds `ClipKind`/`ChargedClipKind`/the three clip kind constants, the clip-shape enqueue validation (behind an unexported `subjectClipProject`), `ClipCancellationStore`, `ClipGuard`/`GuardClips`, the allowance, and the `internal/llm` import.
- Verified: ARCH-26 (gofmt clean, vet, build, `go test ./...` — 58 packages green) and ARCH-28 (`pnpm gen:sql`, generated diff is exactly this change). The clip release smoke was not run: this task changes no media behaviour, and the in-process clip release/cancellation/metering tests in `cmd/api` cover the dispatch path it does touch.
