## goal
A post carries `tag_count` (1–10, default 4) edited in the 글쓰기 옵션 brief beside 목표 글자 수; generation, revision and the write A/B snapshot freeze it and the prompts ask for exactly that many tags, trimming a surplus instead of failing.

## acceptance
- [v] migration `0034_post_tag_count.sql` adds nullable `posts.tag_count`; `GetPost` / `GetLearningSnapshot` / list rows read NULL as 4 without a backfill, and a store test proves a legacy row with NULL comes back as `TagCount == 4`
- [v] `SavePostGenerationOptions` accepts `optional int32 tag_count`: absent preserves the stored value, 1–10 writes it, anything else is `InvalidArgument` `POST_TAG_COUNT_INVALID` and writes nothing (service + rpc tests); a save that changes only the tag count advances no revision and touches no status

- [v] `StartGeneration` reads the owned post's `tag_count` server-side and freezes it in the generate payload; `DecodeGenerationPayload` on a payload without the member yields 4 (payload round-trip test both ways); the generate handler writes the frozen value, not the live post's, into the prompt
- [v] `StartRevision` freezes it the same way in the revision payload (legacy payload → 4), and the revise handler builds its prompt from the payload value

- [v] the Korean write prompt says `정확히 N개의 tags` and the English one `exactly N tags`, `TagsMin` / `TagsMax` and the schema's `minItems: 3, maxItems: 6` are gone, the four goldens are updated, and a prompt test asserts N = 7 appears verbatim

## impl notes
- constants live once, in `internal/platform/config` as typed constants `PostTagCountDefault = 4` · `PostTagCountMin = 1` · `PostTagCountMax = 10`, imported by `internal/post` (validation, NULL mapping) and `internal/generation` (legacy payload and snapshot decode); FE mirrors them in `shared/config` as `POST_TAG_COUNT_DEFAULT` · `POST_TAG_COUNT_MIN` · `POST_TAG_COUNT_MAX` (POST-63 names the FE keys) ← `internal/generation` may not import `internal/post`, and one literal in two contexts drifts
- schema: `ALTER TABLE posts ADD COLUMN tag_count INTEGER;` — plain add, nullable, no default in SQL; the row→domain mapper in `post/store/store.go` (`optionalInt` sites at ~306 and ~762) resolves NULL to the default so the domain type is a concrete `int` (`Post.TagCount`, `LearningSnapshot` needs nothing) ← POST-63: NULL reads as 4, existing posts need no backfill; a `NOT NULL DEFAULT 4` would say the same thing but would rebuild nothing and gain nothing, and a nullable column keeps "never set" visible to a later query
- proto: `Post` gains `optional int32 tag_count = 23` (current max is 22; `optional` only because proto3 has no other way to say "always present, distinguishable from 0" — the server always fills it); `SavePostGenerationOptionsRequest` gains `optional int32 tag_count = 3` with the presence semantics above; `StartGenerationRequest`, `StartRevisionRequest`, `StartWriteExperimentRequest` and `StartVoiceRuleComparisonRequest` gain nothing — the server reads the post (GEN-46: "from the post at start") ← unlike `target_length`, which the client still passes explicitly on start, there is no per-run override to carry
- `post.Service.SaveGenerationOptions(ctx, userID, slug, targetLength *int, tagCount *int)`: `tagCount == nil` keeps `found.TagCount`; the sqlc `SavePostGenerationOptions` statement sets both columns in one UPDATE (`tag_count = ?`), so "preserve" writes the current value back; range failure is `&InvalidContentError{Reason: "tag count must be between 1 and 10"}` mapped in `post/rpc` to `POST_TAG_COUNT_INVALID` the way `GENERATION_TARGET_LENGTH_INVALID` is mapped in `generation/rpc`
- generation: `PostInput.TagCount int` (`json:"tag_count,omitempty"` so a legacy write snapshot decodes 0) filled by the `cmd/api` adapter at `main.go:~1033` from `found.TagCount`; `StartRequest.TagCount` and `GenerateJob.TagCount` set in `Service.StartGeneration` from the loaded post beside `request.TargetLanguage`; `generationPayload.TagCount int json:"tag_count,omitempty"` and `GenerationOptions.TagCount`; the generate handler does `post.TagCount = job.TagCount` next to the `TargetLength` line and every decode path normalises 0 → `config.PostTagCountDefault` in ONE helper `resolveTagCount(n int) int` used by payload decode, snapshot decode and the handlers ← three decode sites, one rule
