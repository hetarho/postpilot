## result
done 260910. `runAgents` gets the real factory, so an armed Mac no longer refuses to start.

### the wiring
- `newPublisher` validates the connection and refuses a browser outside the supported
  Chromium family before returning anything. Arming stays the DAEMON's filter
  (`unseenArmedConnections`), not the factory's, which is where it already was
- nothing is launched at factory time. `connectionPublisher.Run` opens a browser per JOB,
  because the commit port's activation latch (PUB-15) may never be carried from one run to
  the next, and PUB-18 wants a browser this daemon launched closed again after the run it was
  launched for — `session.Close` releases only a browser this process started, so a setup or
  login browser the owner left open is reused and never killed
- the three boundaries — the browser, Naver's own account resolution and the driver release
  this build carries — are struct fields, following the `diagnosticsWith` / `daemonDeps`
  seams T007 extracted rather than adding an injection style
- `ObserveNaverIdentity` is both the navigation and the identity read: Naver's signed-in
  session resolves the id-less writer entry to the account's own blog and reports the id it
  chose, which is why a profile whose login has expired cannot reach its own writer

### what each failure becomes, and how far it gets
Every failure the wiring can see itself is a typed terminal result, and each one stops as
early as it can:
- the driver release disagreeing with what this connection's probe recorded →
  `editor_changed`, decided from the connection record BEFORE a browser is touched (PUB-19
  keeps a connection unready until a fresh probe agrees with the release actually running)
- a browser that will not launch → `browser_lost`, before any page is bound
- a profile that cannot reach its own writer → `login_expired`
- a profile signed in as someone else → `account_mismatch`
- a page that cannot be bound (no sole dedicated page) → `browser_lost`
Everything past that is the deterministic publisher's to classify, because it is the only
thing that observes the editor (PUB-16). The placeholder error and the test asserting it are
gone; a nil factory is now described as the wiring fault it is.

### NOT done, deliberately: the live install/uninstall check
The impl notes ask for the packaging install/uninstall check by hand now that `install` is
usable. It was NOT run, and this is the reason: `install` loads the LaunchAgent, which starts
a daemon that immediately claims queued work — and the owner has a real queued job on this
account (`0182794e…`, `20260905-test`). With the wiring live, that daemon would drive it. It
would not publish today, because this connection's recorded signature is
`smarteditor-one-20260905-a1` while the build carries `…-20260910-a6`, so every job fails
`editor_changed` at the preflight — but relying on that to avoid an unauthorized publication
is exactly the wrong way round, and flipping the owner's queued job to a terminal failure is
itself an outward-facing change nobody asked for.

So the live install belongs in T008's authorized session, where the owner is present, the test
blog is designated and the queued fixture's fate is a decision rather than a side effect. Two
things follow for whoever runs it:
- the owner must re-run `postpilot-agent setup` first, so the connection records the current
  driver signature. Until it does, the preflight refuses every job by design
- the queued `20260905-test` job is claimable the moment the daemon starts. It must be
  canceled, or deliberately used as the smoke's own job, before `install` runs
