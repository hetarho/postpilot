# T186 A project carries its own instruction
> st:done@260916 | ssot:CLIP-121 CLIP-1 CLIP-69 | base:CLIP@28 ARCH@2 | dep:-

## goal
Store one optional free-text instruction of at most 1000 characters on a clip project, typed beside its answers and frozen into every generation.

## acceptance
- [v] migration `0055_clip_project_instruction.sql` adds `clip_projects.instruction TEXT NOT NULL DEFAULT ''`, embedded and run at boot (→ARCH-10)
- [v] `ClipProject.instruction = 30`, `CreateClipProjectRequest.instruction = 11` and `UpdateClipProjectRequest.optional string instruction = 10` carry it; generated code is regenerated, not hand-edited (→ARCH-3)
- [v] the instruction is bounded where it is typed, CLIP-117's way: no character beyond 1000 is accepted, a paste is cut to it, and a live counter sits with the control (→CLIP-121)
- [v] the control sits with the project's answers in `ClipProjectForm`, is optional, and an empty instruction is indistinguishable from never having written one
- [v] generation freezes the instruction into the attempt payload beside the answers and the composition, so editing it mid-flight changes nothing in flight (→CLIP-69)
- [v] a payload written before this field decodes as no instruction, and every existing project reads as having none
- [v] tests: the bounded input and counter, the round trip through create/update/read, and a frozen payload that ignores a later edit
- [v] verify BE (ARCH-26) and FE (ARCH-25) pass

## impl notes
- a column, not a member of `composition_inputs_json`: the instruction belongs to the project (CLIP-1), while that JSON holds answers the template declared
- the 1000 lives once on each side — backend `internal/platform/config` and `frontend/src/shared/config` — never as a literal in a component or handler (→ARCH-21)
- reuse the bounded-input helper T181 built for answers (`boundedAnswer`, `FieldCount`); the counting rule is CDS-20's
- this task stores and freezes only. The writer does not read it yet — T187 does

## result
- storage: migration `0055_clip_project_instruction.sql` adds the column with a default, so every existing project reads as having none; `Project.Instruction`, `ProjectInput.Instruction` and `ProjectPatch.Instruction` carry it through `store.go`, and `UpdateClipInstruction` writes it
- wire: `ClipProject.instruction = 30`, `CreateClipProjectRequest.instruction = 11` and `UpdateClipProjectRequest.optional string instruction = 10`; `pnpm gen:proto` and `pnpm gen:sql` regenerated all four generated trees and a second run reproduces them byte for byte
- bound: `ClipInstructionChars = 1000` lives once per side (`platform/config` → `clip.Limits.InstructionChars`, `CLIP_PROJECT_LIMITS.instruction`); the service refuses an over-long instruction on create and update, and the control cuts a paste to the bound in front of a live counter
- surface: the control sits with the project's answers in `ClipProjectForm`, is labelled optional and starts empty; T181's bounded-input helper moved to `entities/clip-project/lib/bounded-text.ts` as `boundedText` so the form and the answer fields share one counting rule
- frozen: `generationPayload.Instruction` is written beside the answers and the composition and is part of the quote's input digest, so a later edit cannot reach an attempt in flight; a payload written before the field decodes as none, which needed no version bump
- tests: `instruction_test.go` covers the create/update/read round trip, the bound at and one past it, clearing, the frozen payload and the older payload; `ClipInstruction.test.tsx` covers the optional save of an untouched and a written instruction, the refused overflow and the counter
- verify: BE (ARCH-26) green, FE (ARCH-25) green — test 2013, lint (1 pre-existing DraftEditor warning), lint:fsd, lint:style, build:web; agent (ARCH-27) green; ARCH-28 codegen re-run is byte-identical
- the writer does not read the instruction yet — T187 does
