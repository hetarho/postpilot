## goal

- [v] 렌더하기 names the kind it will use — the kind this project last rendered with, and the browser kind where it has rendered none — and offers the other; it reads 다시 렌더 once a render of the current plan exists

- [v] vitest: the dock holds the two rows and nothing else; 렌더하기 names the last render's kind, names the browser kind where the project has none, falls back to server where the browser kind is unavailable, offers the other and becomes 다시 렌더 once a render exists; sending opens the approval without starting; approving starts once with the typed target

## impl notes
- `ClipRevisionRequest` moves from the workspace's panel into the dock and loses its `section`/heading shape; its `useClipRevision` wiring, its `flush` prop and its quote/approval path are unchanged
- the composer row is target + field + send on one line from `sm:`, wrapping to field-over-row on a phone; the target stays a `SegmentedControl` of `CLIP_REVISION_TARGETS` and the send is an icon `Button` named by `revision.send`
- the approval is `ClipQuoteApproval` inside a `Popover` anchored to send with `placement="above"`, `align="end"`, `phone="sheet"`, so it opens over the composer rather than growing the dock
- the kind is what T242 put on `StartClipRender`; the offer of the other kind is a secondary control beside 렌더하기, never a native `<select>` (THEME-29) — a `Menu` on the button or a second ghost control, whichever keeps the row at one line from `sm:`
- the first-offered kind is derived, not stored: the project's last render kind that T242 put on the project read, the browser kind where that is absent, and server wherever the browser kind is unavailable — the derivation is one pure function in `entities/clip-project/model` so the fallback is tested without a dock
- the browser kind is refused by the service until the browser cluster lands, so "unavailable" is a single flag this task sets to true and T250 replaces with its own probe; until then every project names server and the browser offer is absent, and no render changes its kind on its own (CLIP-155)
- the character count moves to the field's own message slot; `boundedText` with `CLIP_PROJECT_LIMITS.instruction` is unchanged
- `revision.help` and `revision.title` are cut; `revision.readOnly` stays for the running row; `timeline.render` is re-worded to 렌더하기 with a separate 다시 렌더 key
- THEME-24 already admits a dock of more than one row, so no primitive changes and `ActionBar` keeps `dock="always"`

## result
- `ClipCorrectionWorkspace` now places the revision composer below the render/finalize row in its one always-docked `ActionBar`; render refusals remain beside their control and download remains under its video. `ClipRevisionRequest` uses a bounded auto-growing field, target segments and an icon send control opening `ClipQuoteApproval` in an above/end popover or phone sheet. Approval alone starts the existing revision flow; its progress and cancellation replace the composer.
- `preferredClipRenderKind` derives the initial kind from the last successful render with browser as the new-project preference and server as the unavailable-browser fallback. `ClipRenderAction` labels the kind, offers the alternate when available and distinguishes a current render from an absent/stale one. Browser availability remains false until the browser cluster supplies its probe and execution path.
- Updated Korean/English labels, page wiring and route/component/domain tests. The finalize button shares its row at phone widths; keyboard resize reveals the whole composer dock without applying timeline-field scrolling to it.
