## goal
Store one operator-set level per (model, purpose) registration and carry it to both surfaces: the admin `CatalogEntry` for the tab being viewed and every stage's `ModelInfo` for users.

## impl notes
- the level is a column on the registration row, exactly the shape the effort took in migration 0021: the PK is already `(model_id, purpose)`, so nothing else changes. NULL is "unset" — the SSOT's "unset until the operator decides" is the absence of a value, not a fifth value, so the CHECK lists four
- `ListCatalogModelPurposes` and `GetCatalogModelPurposes` add `level` to their SELECT; the store's row→domain mapper fills `Model.Levels` beside `Model.Reasoning`. A NULL maps to `""`
- `Combo` (`quality` `balanced` `value` `cheapest`, the plan estimator's pairs) shares two words with `Level` and its ko copy already says 등급. They are different types with different tables and must stay so — do not reuse `Combo` constants, its i18n keys or its RPCs; nothing in this task touches combos
- `llm` stays uninterpreting: `Levels` on `SourceModel`/`ModelInfo` is the same pass-through posture as `Stages` and `Label` (MODEL-27 puts display metadata on this wire). Keying by stage string rather than `Purpose` keeps `llm` free of the modelcatalog type, as `Stages` already is
- `UpdateModelRequest.level` is `optional` so that a request editing only the effort leaves the level alone and vice versa — one RPC, two independent patches, mirroring how `reasoning_effort` is already optional
- field numbers: `CatalogEntry` is used up to 28 (`video_input`), so 29; `ModelInfo` is used up to 18, so 19. `StageLevel` is a repeated message rather than a map because a proto map cannot be keyed by the `Stage` enum and a string-keyed map would leak the stage's wire name to the client
- no frontend change here — T094 (admin) and T095 (selectors) consume the new fields; generated TS is committed by this task's `gen:proto`
