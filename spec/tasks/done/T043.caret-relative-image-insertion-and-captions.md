# T043 Caret-relative image insertion, one-at-a-time upload and captions
> st:done@260910 | ssot:PUB-21 PUB-36 PUB-19 PUB-20 | base:PUB@4 ARCH@2 | dep:T042

## goal
Insert each manifest photo at its own position by placing the caret in the block it must follow, upload it as the only file in that operation, and apply its caption.

## acceptance
- [v] `Apply(upload_image)` performs one atomic sequence: resolve the block the image must follow and place the caret at its end, enable `Page.setInterceptFileChooserDialog`, resolve `button.se-image-toolbar-button` to exactly one match and click its live geometry, then hand `input[type=file]#hidden-file` exactly one enumerated current-job path through `DOM.setFileInputFiles`; the input does not exist before that click and no native dialog is ever accepted (PUB-21)
- [v] the `upload_image` locator entry counts `button.se-image-toolbar-button`, not `input[type=file]#hidden-file`, so `Publisher.mutate`'s pre-check is satisfiable before the click that creates the input; a test pins that the file input is absent at pre-check time and present at upload time
- [v] a photo is counted only after a fresh full snapshot shows exactly one additional editor image; a resolved path or an upload acknowledgement alone is never evidence; an upload that adds zero or two images fails `editor_changed`
- [v] images are uploaded in exact manifest-ordinal order and each lands immediately after the block holding the caret, so the observed block order equals the manifest's; a test with eight photos interleaved between text blocks proves the resulting order, and a test proves a manifest whose FIRST block is an image still produces the image as the first body block
- [v] `Apply(image_caption)` resolves the `.se-module-text.se-caption` module of the addressed image's ordinal and enters the caption; an empty caption is not written at all, and the module's placeholder `사진 설명을 입력하세요.` is never read back as content
- [v] no coordinate survives a mutation: a test walks every reviewed type on the image path and proves none has a field that could hold resolved geometry, and that the rect read for a click is not returned to the caller or reused by the next mutation (PUB-36)
- [v] against a fake CDP editor, table-driven tests cover: eight ordered JPEGs; a leading image; an upload adding zero or two images; ordinal disorder; a caption applied to the wrong ordinal; the file input disappearing between the click and the upload; a path outside the enumerated current-job set being refused; and the caption placeholder never entering the projection
- [v] ARCH-27 passes

## impl notes
- the live mechanics are in T019's `## survey` section, item 1: `#hidden-file` is created on demand by the image button's click, advertises `accept=".jpg,.jpeg,.gif,.png,.bmp,.heic,.heif,.w…"` and is `multiple` but must still receive one file per call, and SmartEditor places the new `.se-component.se-image` immediately AFTER the component holding the caret
- that is why there is no placeholder step and no pre-allocated ordinal: position comes from the caret, which is the rule PUB-36 r4 now states
- for an image whose manifest position is first, place the caret in the editor's leading text component; SmartEditor always has one, and the empty paragraph it leaves before the image is removed by the same trailing-empty-paragraph cleanup the projection already needs. If it turns out not to be removable, record it and treat the leading empty paragraph as expected in the fence snapshot rather than fighting it
- interception must be enabled before the button click, not after: the click is what would otherwise open the native chooser
- caption modules exist one per image and only once the image exists, so `image_caption` is planned after all uploads for that ordinal, never before

## result
done 260910. Photos are inserted at their manifest positions, captioned, and the whole body
path is verified against the live editor. Getting there turned up four defects the task did
not anticipate, three of which would have silently corrupted a published post.

### the placement question, answered — and the plan got simpler
The one mechanic T019 never discriminated: with the caret at the end of a NON-EMPTY paragraph
that has another paragraph after it in the same component, SmartEditor SPLITS the component at
the caret's paragraph and puts the image between the halves. So a photo needs no index and no
pre-allocated slot at all — the caret is the whole position, exactly as PUB-36 states.

That collapses the design. Photos are uploaded INTERLEAVED with the body writes, in manifest
order: right after the write of the block a photo must follow, the caret is already at that
block's end, so `body_end` is the position. A leading image needs no special case either —
the caret sits in SmartEditor's own opening paragraph and the image consumes it, becoming the
first body block with nothing left before it. The expected snapshot therefore carries every
image at its manifest position, which also settles the "Prepare appends images at the end"
defect T042's result left here.

Photos come before the conversion pass, and `assertPlanOrder` now refuses an `upload_image`
or `image_caption` after a quote or list conversion: both place themselves from the caret or
from a paragraph index, and a landed conversion has moved both.

### four defects found live
1. **The photo-library sidebar occludes the editor.** An upload opens
   `aside.se-sidebar.se-sidebar-interaction` — 300 px wide, at x=780, OVERLAYING the editor —
   and a body paragraph's box runs to x=879. Every caret point, taken at 98 % of the width,
   landed on the sidebar; `resolveAndClick` returned success and the caret was left outside
   the document. Same class as the settings-layer occlusion T044 found. Fixed twice over: the
   driver now HIT-TESTS every point against the element its locator resolved and fails closed
   otherwise, and the upload closes the sidebar (`button.se-sidebar-close-button`) on both
   sides of its sequence.
2. **Points were read without regard to the viewport.** With eight photos the target paragraph
   leaves the viewport and `elementFromPoint` returns null. The driver now brings the resolved
   element into view before reading its rect — PUB-19 says scroll and viewport cannot be
   product authority, so normalising them is the driver's job.
3. **An upload returned before the editor settled.** Observing immediately after
   `DOM.setFileInputFiles` catches SmartEditor mid-surgery: the image exists but is not
   processed and the caret's paragraph has its tail detached. The upload now re-observes until
   exactly one more SETTLED image is present (an https resource), with none, two, or a
   never-finishing image all failing closed. It also refuses to start while an earlier photo
   is still processing, so "exactly one more" is an observation rather than a guess.
4. **`Input.insertText` leaves its last word UNCOMMITTED.** Everything after the final space
   stays pending in SmartEditor: the DOM shows the whole string and reads back exact, but the
   first structural change rebuilding that paragraph — an image insertion, a paragraph
   conversion — DISCARDS the pending word. Text with no space at all vanished entirely.
   Measured live over repeated runs: without a trailing key 4 of 5 writes lost their last
   word, with one 0 of 5. A caret-only key (End) does NOT commit, and waiting 0 s, 3 s and
   8 s was not reliable either, so this is a commit and not a settle. Every text entry now
   ends with the Enter that commits it — the title and a caption take it with no observable
   change, a body paragraph opens the next one (which the following write then types into,
   so no empty paragraph accumulates), and a list's last item takes TWO, the first committing
   the word into the empty item that Enter opens and the second dropping that item and leaving
   the list with exactly the manifest's items. Tags already committed each value this way.

   This is the one that mattered most: the pending word survives in the DOM, so the projection
   and the fence snapshot would both look correct while Naver's own model — the thing it
   serialises when publishing — is missing it.

### two more corrections
- the `upload_image` LOCATOR counted `input[type=file]#hidden-file`, which the image button's
  click creates on demand, so `Publisher.mutate`'s pre-check was unsatisfiable for every
  upload. It counts `button.se-image-toolbar-button` now, in the manifest and the observation
- an empty caption module has NO BOX (0x0 measured) until its image is selected, so the
  caption point resolved to nothing. `image_caption` now selects the image first through
  `image_select`, which reveals the field and writes nothing
- the observation script's image ordinals were 1-based while the manifest and every mutation
  are 0-based. No fake caught it because the projection was only ever compared against
  itself; the first real upload would have failed `equalSnapshot`
