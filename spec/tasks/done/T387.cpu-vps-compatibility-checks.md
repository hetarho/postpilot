## goal
Verify the CPU workflow and VPS-compatible release locally, including isolated remote-style execution, without deploying to production or another host.

## acceptance
- [v] A reproducible release fixture runs the API, private object storage and CPU worker as separate processes with no shared data/work directories, through real RPC, lease, artifact and finisher code; model calls use explicit fixtures rather than paid providers.
- [v] The same fixture passes colocated and isolated-network remote-style layouts on the development host, including reopening a job while waiting, unavailable worker, API restart, worker kill/reclaim, cancellation, duplicate completion and cleanup retry; a second physical server is not required.
- [v] Delivered CPU output matches the existing same-host/profile baseline for all supported aspect ratios and representative original-audio, transition and sequence-caption cases; the generation result still stops at a plan and browser rendering remains functional.
- [v] The resource run records combined API/worker peak memory, disk, API responsiveness and prepare/render/upload elapsed times under a VPS-sized envelope with a stated reserve for colocated services; insufficient capacity is a reported failed gate, not a universal compatibility claim.
- [v] Release tooling can check actual host memory/disk and chosen worker limits when the operator deploys; local tests cover sufficient/insufficient resources, and a bounded disposable smoke recipe is provided for staging/current VPS without running it there as part of this task.
- [v] After the gates pass, remove the temporary CLIP_MEDIA_EXECUTION switch and embedded production preparation/final-render dispatch. Same-host and remote server jobs both use the same durable worker protocol; no worker error can select a local fallback.
- [v] Fresh installation and additive upgrade preserve existing projects, results, quotes, source retention, accounting and ordinary model-job restart behavior; same-host rollout starts both services, remote-mode API health survives an offline worker.
- [v] ARCH-25/26/generated-code checks, local execution-image/release smokes and deployment tests pass; the runbook separates local measurements from commands for later host verification and requires neither a live migration nor GPU hardware to complete this CPU release.

## impl notes
- Extend the existing cmd/api clip release harness rather than substituting a fake Renderer at the split. Spawn the real worker process/container, use real FFmpeg/resvg/fonts and local private MinIO, and keep provider stubs visibly identified in the report.
- Use a deterministic fixture/clock to place failures at durable boundaries; the multi-process exercise separately demonstrates that local-memory callbacks, same-volume paths and in-process wakeups are not prerequisites.
- Same-profile identity is checked on the same machine before/after the split. Do not refresh host-dependent golden hashes merely because another architecture differs; GPU compression acceptance remains outside this task.
- Add runnable `pnpm smoke:media-worker` and `pnpm smoke:media-release` entrypoints and include them in the media CI matrix under the existing smoke/deploy policy. Keep build-time tooling checks blocking and real-runtime verification explicit.
- Use a configurable 2-vCPU/1-GiB fixture as the documented historical VPS starting envelope, not evidence of current available capacity. Implement and locally test a preflight that measures actual free resources when the operator invokes it, accounting for existing colocated workloads before suggesting a worker budget.
- Make the operational smoke use a separate disposable project, storage prefix, work directory and alternate internal port; its cleanup must not touch real user originals or the production DB. A passing local envelope test is not recorded as a live VPS measurement.
- The completed release defaults to colocated CPU, one worker job and existing encode/decode defaults. Missing required worker settings produce clear deployment/preflight errors; the API remains healthy while a correctly configured remote worker is temporarily unavailable.
- Keep API-side authored-plan checks, preview rasterization and browser caption assets. Remove only embedded preparation/final-render dispatch, and document the remaining API media dependencies rather than claiming the API contains no media tooling.
- Use the rollback compatibility boundary from T386. Test upgrade from a seeded legacy schema, but never start a legacy API against live parked work or downgrade applied migrations.
- This task produces locally validated release artifacts and procedures; production deployment, friend-PC access, host installation, topology migration and real-GPU performance/quality validation are outside its acceptance criteria. The running VPS is unchanged by authoring or testing these tasks.

## result
- Production `cmd/api/clip.go` always constructs durable media dispatch; the temporary execution setting is removed from config/env/Compose. Server boot requires private worker settings while offline tooling/adduser remain independent. API plan validation, preview and browser-caption tooling remain available.
- `cmd/api/media_release*_test.go` extends the existing synthetic provider, footage, fingerprint and RPC harness through a real API child process, actual private MinIO and an independent worker. `scripts/media-release.py` owns disposable names/networks/storage, configurable CPU/memory limits, bounded execution/cleanup and resource reports; the worker has no API DB/work mounts or provider/storage secrets. Remote mode uses a separate network and RPC/artifact relay. Fixture control routes are absent from the production binary.
- Both layouts pass offline wait/reopen, API process restart before preparation and during an active render lease, worker kill/reclaim, plan-only generation, exact paid-call/balance checks, duplicate accepted completion, cancellation/publication fencing, failed DELETE/retry and retained-result download. Test-only deletion-clock advancement avoids waiting for grant expiry; production clocks and grant fences are unchanged.
- Final Linux/arm64 local fixture: API 256MiB/1CPU + worker 512MiB/1CPU + 256MiB cohost reserve. Colocated/remote combined memory peak upper bounds: 570851328/547688448 bytes; sampled disk peak sums: 17189118/15878398 bytes; max project RPC: 37/12ms. Prepare download+compute: 1371/1183ms, reserve+upload: 13/17ms; render download+compute: 79796/78523ms, reserve+upload: 15/10ms. MinIO/relay are separately capped external-storage/network substitutes, outside the execution envelope. These are synthetic local measurements, not live VPS capacity or maximum-input benchmarks.

- `deploy/media_preflight.py` reads actual MemAvailable, cgroup remaining memory/CPU and free target-filesystem disk, includes selected worker/API/cohost budgets and refuses insufficient capacity. Tests cover sufficient/insufficient resources and no-resource-creation budget failure. DEPLOY §8.6 records measurements and an isolated optional later staging/VPS smoke.
