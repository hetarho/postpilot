# T207 The template grammar keeps only what every clip must carry

## goal
Refuse footage sections, scene-bound text and cut-relative timing in a template body, keep reading them in frozen project snapshots, and convert an existing template's sections into its optional guide.

## acceptance
- [v] `composition.ParseTemplate` (new entry beside `Parse`) refuses `scene`, `repeat`, `basis="cut"`, a content `text` whose role is not `badge`, and any `text` outside the intro/outro skeleton and the badge, each as a problem naming element and line with reasons `unsupported_section` · `unsupported_basis` · `unsupported_role`
- [v] `composition.ReadStored` parses every frozen project snapshot exactly as today, sections included, so existing plans keep resolving and ② cut creation keeps inheriting its section from the origin cut
- [v] root `pace` and `accent` are still read into `Document.Pace/Accent` (a legacy template seeds a project under CLIP-139), but a body without them parses cleanly and the grammar guide no longer documents them
- [v] `composition.ConvertLegacyTemplate(body string, l Limits) (converted string, changed bool, problem *Problem)` moves every `scene`, `repeat`, their guides and every scene-bound `text` into one root `guide` element (an existing root guide stays first), returns changed=false for a conforming body, and returns a `guide_limit` problem instead of truncating when the joined guide would exceed `GuideChars`
- [v] video template read projections (`ListVideoTemplates`, `GetVideoTemplate`) return the converted body with `composition_converted=true` when the stored body needed conversion; the stored body changes only when the owner saves; `UpdateVideoTemplate` refuses a body `ParseTemplate` refuses
- [v] frontend `composition-parse.ts` mirrors the three refusals with the same reason codes, `composition-guide.ts` GRAMMAR and `CLIP_COMPOSITION_EXAMPLE` describe only `field` · `group` · `guide` · intro/outro slots · `badge`, and `composition-skeleton.ts` stops emitting `pace`
- [v] `composition/testdata/corpus.json` gains the refusal cases and the conversion of the restaurant fixture (fields, groups, design, slots, badge, one guide) and both implementations pass it
- [v] tests: Go parse refusals, ReadStored unchanged on the section fixture, conversion round trip; TS corpus mirror; verify FE (ARCH-25), BE (ARCH-26), generated code (ARCH-28)

## impl notes
- today `Parse` serves template saving and snapshot reading alike; `case "scene"` / `case "repeat"` (composition/parse.go:386, 390) stay for `ReadStored`, and `ParseTemplate` adds one template-only pass over the parsed document rather than a second grammar
- the conversion writes prose, not markup: each scene's guide text as a paragraph, and each scene-bound `text` as one line — its id, a colon, then its instruction or literal with a value reference rendered as {field}; paragraphs joined by blank lines. CLIP-140 says nothing is dropped silently, so an over-long result is a problem the editor shows, never a cut
- `composition_converted` is `bool composition_converted = 14` on `VideoTemplate` in proto/postpilot/v1/clip.proto, computed in the rpc mapper from `ConvertLegacyTemplate`; no DB column, because the flag is a property of the stored body
- the FE strict parser shares the corpus oracle (README: "Keep it shared rather than generating one implementation's expected results from the other"); extend `corpus.json` instead of writing one-sided tests
- reason strings for the new codes go in `resources/{ko,en}/clips.ts` next to the existing `reasons` map (the agent map lists it under the template editor); T208 renders them
- unchanged: `Resolve`, the intro/outro skeleton rules (CLIP-112), badge rules, `Limits`, `ReadStored`
