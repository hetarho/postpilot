# T099 ListClipProjects carries each project's latest job
> st:done@260911 | ssot:CLIP-41 | base:CLIP@5 ARCH@2 | dep:-

## goal
The clip directory's answer names each project's latest job, so a row can say 생성 중 or 실패 instead of reading as a draft while a generation runs.

## acceptance
- [v] `ListClipProjects` fills `latest_job` per project through the same `h.jobs.LatestForClip` the detail uses; a project with no job leaves the field unset and a handler wired without a job reader still answers
- [v] nothing else joins the list answer: `editing`, `accounting` and `latest_attempt` stay detail-only, as the proto's own comments say
- [v] `go test`: the list answer carries a running job for one project, a failed one for another and nothing for a third; the detail answer is byte-identical to before
- [v] `cd backend && test -z "$(gofmt -l .)" && go vet ./... && go build ./... && go test ./...` (ARCH-26)

## impl notes
- the lookup sits in the rpc handler beside `GetClipProject`'s, which is where this package already reads the job port; `post` does the same per-row call in a loop (`post/service.go:511` for `ListPosts`), so this is the established shape rather than a new one
- no proto change: `ClipProject.latest_job` is field 12 already and the FE mapper already reads it into `ClipProject.latestJob`
- deliberately not batched: `LatestForClip` is one indexed read, a list is one owner's projects, and a batch query would add a store method with no caller outside this loop

## result
- files: `backend/internal/clip/rpc/handler.go` (the list loop fills `LatestJob`) · `backend/internal/clip/store/list_latest_job_test.go` (new)
- the test lives in `internal/clip/store`'s `package store_test` rather than in `internal/clip/rpc`: `h.jobs` is a concrete `*job.Queue`, not a port, so a fake job reader is not an option, and `generationSetup` is the one harness that already wires a real queue, store and generation service together. It builds the handler on top of that harness — no cycle, since `clip/store` is not imported by `clip/rpc`
- it pins three things: a project with no attempt carries no job and no detail-only field (`editing`, `accounting`, `latest_attempt`); a started generation appears on ITS row and on no other; a `FailQueued` attempt reads as `failed` on the row. Plus a handler built without `WithGeneration` still answers, which is the shape every other clip rpc test uses
- one assertion was dropped while writing it: the detail's `editing` state is not present for a project whose generation never succeeded, so asserting it there was wrong about the fixture rather than about the change. The detail's own latest job is still checked
- gates: `gofmt`, `go vet`, `go build`, `go test ./...` all clean (ARCH-26). No proto change — `ClipProject.latest_job` was already field 12 and the FE mapper already read it, so nothing is owed to ARCH-28 either
