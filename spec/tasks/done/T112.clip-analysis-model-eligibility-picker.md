# T112 Clip-analysis model eligibility picker

## goal
Make the clip creation page show every registered observe model and use T111's live eligibility result to select, explain or refuse it without changing ordinary post and experiment model selection.

## acceptance
- [v] the `clip-project` entity exposes a typed query and mapper for T111's ClipService eligibility RPC through `shared/api`; no feature/page imports generated protobuf code, and an `UNSPECIFIED`, duplicate, unknown or missing model result is never treated as eligible
- [v] the clip analysis-model picker merges eligibility by exact provider/model ref with the existing registered observe list, keeps all of those models visible and enables only `ELIGIBLE`; a currently saved model that becomes ineligible stays visible and selected with its reason, but cannot quote or start and is never cleared, saved over or automatically replaced
- [v] each disabled model shows exactly one localized reason matching CLIP-44: video input absent · compatible inline endpoint unavailable · required request parameters unsupported · complete price ceiling unavailable; provider-disabled/vanished state keeps precedence, and loading or whole-query failure fails the clip action closed with localized availability copy rather than a raw Connect/provider message
- [v] clip quote inputs and generation readiness use the merged eligibility instead of `inlineStaticVideo`; they issue no quote/start request for an ineligible or unresolved selection, invalidate a previously displayed quote when status or model ref changes, and render the same four backend refusal reasons if a server recheck rejects a forged or stale client request
- [v] the reusable stage selector accepts an optional per-model availability contract rather than clip-specific provider logic; post generation, write experiments, the model lab, capability badges, ordering and signed-video-URL warnings behave exactly as before when that contract is absent
- [v] Korean and English `clips` copy covers all four picker reasons plus eligibility loading/failure, and `errors` covers T111's four registered backend reasons with compatible `{model}` placeholders; catalog topology and backend-reason coverage tests pass without exposing translation keys or technical endpoint details
- [v] tests cover an eligible non-Google model, every disabled reason, an eligible route without static processing, a selected model becoming ineligible, loading/fetch failure, duplicate/unknown status, quote invalidation, no automatic substitution/save, keyboard/screen-reader association of each reason and the unchanged ordinary stage selector; the picker remains usable at 360 px
- [v] ARCH-25, ARCH-28 and the relevant ARCH-31 local gates pass with zero generated-code drift

## impl notes
- keep transport/mapping/query state in `entities/clip-project`, the reusable selection mechanics in the existing stage-model feature, and page composition/readiness in `pages/clip`; use the current query library and shared controls rather than a second cache, fetch client or bespoke listbox
- key availability by the full provider/model ref, never by label or model id alone. T111's status is the authority for CLIP; `videoInput` remains a badge/capability and `inlineStaticVideo` may remain in the compatibility mapper for older/non-CLIP consumers but cannot gate this page
- make the optional availability input explicit enough to represent loading and request failure separately from a model's four stable ineligibility statuses. A whole-query failure is a surface-level retryable load state, not a fifth model reason
- retain the user's global observe selection because it can still serve photo-only/posts; the clip page only refuses this workflow. Selection changes continue through the existing model-selection action and no candidate is chosen merely because it is the first eligible row
- disabled copy belongs next to the model option and the action's single readiness/status region; use existing typography, spacing, focus and token primitives, and allow multi-line reason text rather than shrinking it at the phone breakpoint

## result
- files: `entities/clip-project/{model,api}/eligibility.ts` (five statuses, exact-ref lookup that returns `undefined` for a missing or duplicated model, wire mapper that drops `UNSPECIFIED`/unknown rows, `useClipAnalysisEligibility` query) · `entities/model-catalog/model/availability.ts` (`ModelAvailability` = loading | failed(+retry) | ready(resolve→verdict); the optional per-model contract the selector takes) · `features/select-model/ui/StageModelSelect.tsx` (`availability` prop replaces the clip-specific `requireInlineStaticVideo`; a refused model is greyed with its reason after the provider's own state, a refused SAVED choice stays selected with the reason under the field via `aria-describedby`, nothing is pickable while loading/failed, a retry button on failure; without the prop every prior behaviour holds) · `features/generate-clip/{model/preconditions,api/useGenerateClip,api/useClipQuote,ui/ClipApprovalAction}` (readiness = both stages usable AND live status `eligible`; the quote binding carries the status so a status change invalidates a displayed quote; the hook exposes `availability`/`eligibility`/`observeStatus`) · `pages/clip/ui/ClipPage.tsx` (passes the verdict, one readiness line: loading · failed · pick both · the model's reason · unresolved) · `shared/api/index.ts` exports · ko/en `models.availability.*`, `clips.generation.eligibility.*` (the `videoRequired` sentence is retired) · `test/clips.ts` fake gains `eligibility`/`eligibilityFails` · tests in the entity, the selector, the preconditions and the clip page
- the availability contract lives in `entities/model-catalog`, not in `features/select-model`: two features (the selector and clip generation) read it, and FSD forbids a feature importing another feature
- a model the server does not name (or names twice) is "unresolved": greyed with the generic 아직 쓸 수 없어요 note and never eligible; the page never clears, saves over or substitutes the saved observe choice — an eligible row is enabled, not chosen
- `videoInput` stays a badge and `inlineStaticVideo` stays in the catalog mapper for non-CLIP consumers; neither gates this page any more. `requireVideoInput` (post generation) is untouched
- not covered by a browser test: the 360 px layout is asserted by design (the reason runs in the option row and in the multi-line field note, both `break-words`), not by a viewport test; the errors catalog already carried T111's four reasons with `{{model}}`
