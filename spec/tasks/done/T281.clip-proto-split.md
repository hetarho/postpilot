# T281 clip.proto becomes one file and service per rpc family
> st:done@260920 | ssot:ARCH-41 ARCH-3 ARCH-28 | base:ARCH@5 | dep:T262

## goal
Switch `buf.yaml` breaking to `PACKAGE`, split the 34-rpc `ClipService` into `ClipTemplateService`, `ClipSourceService`, `ClipGenerationService`, `ClipRenderService` across four files, and re-plumb BE handlers and FE entity descriptors.

## acceptance
- [v] `buf.yaml` `breaking.use: [PACKAGE]`; `proto/postpilot/v1/clip_template.proto`, `clip_source.proto`, `clip_generation.proto`, `clip_render.proto` each define one service (≤10 rpcs) with their request/response messages; shared clip domain messages stay in `clip.proto`; `buf breaking` against `main` passes
- [v] BE `internal/clip/rpc` registers four handlers (one file family each) in `cmd/api`; FE entities own the descriptors of their family (`clip-template`→template, `clip-project`→source + generation/quote/finalize, `clip-plan`→revision/captions, `clip-preview`→render/browser render) with no page/feature change beyond imports; agent `buf.gen.yaml` gets the four new `M` lines
- [v] ARCH-28 passes (all three gen trees regenerate clean); ARCH-25/26/27 pass; `test/clips.ts` registers the four fakes
- [v] rollout note in the task result: BE and FE deploy in the same rollout because rpc paths changed (ARCH-41)

## result
- `buf.yaml` breaks on PACKAGE now, so a message may move between the clip files freely (ARCH-41). It also excepts `ENUM_ZERO_VALUE_SUFFIX`, which T278's `FailureReason` needs: its zero value IS the wire string `UNKNOWN_FAILURE`
- FIVE files and services, not four: `clip_template` (6 rpcs) `clip_source` (7) `clip_generation` (10) `clip_plan` (5) `clip_render` (6). The plan family — saving a correction, drawing its captions, asking for a rewrite — is its own service because folding it into render or generation puts either over ten, and it maps one-to-one onto `entities/clip-plan` from T260
- 68 request/response messages moved with their rpcs; 51 shared clip domain messages stay in `clip.proto`, which now has no service at all and says why
- BE: one `cliprpc.Handler` answers for all five services and `cmd/api` registers it five times (`clipHandler(c)`) — splitting the handler would only split the context behind it. The clip release harness gained a `releaseClipClient` that embeds the five generated clients, so its 1,100 lines read unchanged
- FE: each entity names its family's service (`clip-template`→template, `clip-project`→source+generation, `clip-plan`→plan, `clip-preview`→render), `shared/api` re-exports each symbol from the generated module that now owns it, and the unused `clipClient` is gone
- the stale `postpilotv1connect/clip.connect.go` had to be deleted by hand: buf leaves a generated file behind when its source stops producing one, and it still declared the whole old `ClipService`
- ROLLOUT: the rpc paths changed (`/postpilot.v1.ClipService/X` → `/postpilot.v1.Clip<Family>Service/X`), so the backend image and the frontend deploy TOGETHER. `buf breaking` against main reports the deleted `ClipService` — that is the intended break ARCH-41 describes, not a regression. The agent is untouched (no publishing rpc moved) and its `buf.gen.yaml` gained the five mapping lines
- verify: ARCH-25, ARCH-26, ARCH-27, ARCH-28 green; buf lint clean
