Give memories the directory screen the other authored layers have, so a wrong memory can be fixed instead of reaching every future prompt.

## acceptance

- [v] the page IS the list: each row shows the text, a kind badge and its tags, in the server's stated order; there is no standing form

## impl notes
- the shape is the 지침 page's, deliberately: a docked add action opening a Sheet over a page that is only the list (GUIDE-20)
- the kind control belongs in `entities/memory/ui` because the create sheet and the row edit both need the identical control and a feature may not import a sibling feature
- i18n lives as slice fragments under the memory slices, assembled by `app/providers/i18n`; no new cross-cutting namespace
- every generic control is a `shared/ui` primitive; the badge, sheet, textarea and confirmation are existing ones

## result
- `/memories` is the fifth destination of the 글 group, registered in `app/routes/templates.ts` (lazily split, like its siblings) and in `CONTENT_GROUPS.writing` after 지침; `tree.test.ts` names the address and `navigation.test.tsx` now expects 기억 in the group menu.
- slices: `entities/memory` (types with the closed five kinds, the two mirrored bounds, the comma-tag parser, the query/mappers/cache/errors and the three write hooks, plus `MemoryKindField` and `MemoryTagsField` — both controls live with the entity because the create sheet and the row edit need the identical ones); `features/create-memory` (the docked `새 기억` and the shared `Sheet`), `features/edit-memory` (a read-first text editor and a read-first kind+tags editor), `features/delete-memory` (a confirmation that states there is no undo), and `pages/memories`, which is composition only.
- the kind and the tags save TOGETHER while the text saves alone: the kind decides whether tags gate the fact at all (MEM-6), so a kind saved without its tags would leave a `place` memory reachable by nothing — while a text edit still carries no facets, so two edits from two places cannot overwrite each other.
- the list query is `memoriesQueryKey(transport, ownerId)` with `staleTime: 0` + `refetchOnMount: 'always'`, invalidated by every create, edit and delete. The client mirrors only the text and tag ceilings (for the live counts) and predicts no refusal: the cap, a duplicate text and an over-long text all render through the shared failure catalogue.
- i18n is five slice fragments in a new `memories` product namespace assembled by `app/providers/i18n`, plus the `nav.memories` label in the two cross-cutting nav catalogues.
- `test/memories.ts` is the fake service (list order, the cap refusal, dedupe-on-create, the recorded updates/creates/deletions), wired into `renderAppAt`. `MemoriesPage.test.tsx` covers the server order with kind and tags, the empty and failed states, a read-first text edit that sends only the text, a facet edit that sends no text and collapses duplicate tags, the sheet's create (with an empty source slug — a fact written by hand links no post), the cap refusal inside the still-open sheet, and the delete confirmation.
- ARCH-25 green: 2226 vitest tests in 284 files, `pnpm lint`, `lint:fsd` (steiger clean — no same-layer import), `lint:style` and `build:web`.
- No SSOT deviation. T293's candidate sheet can reuse `MemoryKindField`, `MemoryTagsField` and `useCreateMemoryCall` as they stand.
