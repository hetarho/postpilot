# T731 Make the source cadence measurement deterministic

## goal
The same original measures the same `CadenceVerified` on every run, so `Verify media`'s worker parity gate cannot flip on an unchanged tree.

## acceptance
- [v] The cause is identified from captured ffmpeg logs (a repeated preparation run on a linux/amd64 runner-like host, or the decode command alone over the smoke fixture), and recorded in result.
- [v] `constantCadenceReport`/`decodeMeasurement` read the vfrdet report so a nondeterministic log shape cannot change the verdict for an unchanged source, without accepting a source whose decoded timestamps vary.
- [v] `probe_test.go` (or the existing media unit tests) pins the log shapes found: the report split from its prefix by a concurrent `-progress pipe:2` write, an extra early-closed graph report, and a genuinely varying report.
- [v] `TestWorkerExecutionParity/preparation` passes repeatedly in the worker smoke image (`docker run … /media.test -test.run=^TestWorkerExecutionParity$/^preparation$ -test.count=N`).
- [ ] exit: when the 2h timebox ends without a reproduction, record the runs and log captures tried, keep the measurement unchanged, and leave the gate as a recorded runner flake.

## impl notes
- Evidence: Verify media run 41469072328 (commit 70811b8c, T730 — only a browser-composition constant changed), job `Media worker`, step `Run CPU worker parity, isolation and health`: `worker_smoke_test.go:178: original measurement changed`. Worker and embedded measurements of the same fixture match in every field except `CadenceVerified` (worker true, embedded false); DecodedFrames 1200 and all durations equal. The same subtest passed on GitHub at 05c8d739 and earlier, locally on 70811b8c, and 12 more local repeats under amd64 emulation.
- Both measurements run `-vf vfrdet` with `-progress pipe:2` (probe.go `Probe`, chunks.go:148) and parse stderr; `constantCadenceReport` requires exactly one `[Parsed_vfrdet_…] VFR:x (v/c)` match with c>0. Two nondeterministic shapes fit a false verdict with intact frame counts: the av_log prefix and message written in separate writes with a progress block between them (no match), or the negotiation graph closing after it already saw frames (two matches).
- Preferred fixes, in order: send progress to its own descriptor so the log cannot interleave with it; otherwise parse the `VFR:x (v/c)` message independently of its prefix and accept one or more graphs with c>0 as long as every report has v=0. Keep the (0/0) negotiation report ignored.
- A measurement change moves no media identity unless its output changes; if `MediaRendererVersion`/asset identities would move, follow reference-clip-data-migration-traps (Dockerfile labels follow the Go constants).

## result
- outcome: Cause found and removed. FFmpeg 9.0.1 (the worker image's static musl build) writes a log line's `[Parsed_vfrdet_0 @ 0x…] ` prefix, its `VFR:x (v/c)` message and the newline as three separate writev calls (ptrace trace of the copy command over the parity fixture), while the two-output analysis-copy command writes an intermediate `-progress pipe:2` block, outside the log lock, as soon as the null verification output's muxer finishes — the moment the filter thread frees the vfrdet graph (every captured log shows that block directly after the report). Holding the filter thread 300 ms after its prefix write reproduced the CI log with the real binary: `[Parsed_vfrdet_0 @ …] frame=1200`, the progress block, then a bare `VFR:0.000000 (0/1199)`, which the old parser reads as 1200 frames, 20000000 µs and cadence false — run 41469072328's worker/embedded difference. No early-closed graph that had seen frames appeared in any run: only the parse-time (0/0) report and one measured graph. Probe and the copy command now send `-progress pipe:1` (their null outputs write nothing to stdout), `ExecRunner` returns a `CaptureStderr` command's stdout ahead of its stderr, and the cadence regex reads the `VFR:x (v/c)` message without its prefix, which also covers a prefix FFmpeg drops after another thread's unterminated line. Every report must still have v=0 and exactly one graph c>0: the impl note's "one or more graphs" alternative was not taken, because a second measured graph is a mid-decode reconfiguration whose boundary step vfrdet never measured, and no nondeterministic second graph exists here. With `pipe:1` the same 300 ms hold leaves the report whole on stderr and both progress blocks on stdout. Copy bytes, the measurements of unchanged sources and every media identity and renderer version are unchanged.
