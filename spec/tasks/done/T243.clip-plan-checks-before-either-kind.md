# T243 every plan check runs on the server before a render of either kind
> st:done@260918 | ssot:CLIP-154 CLIP-109 CLIP-88 | base:CLIP@38 | dep:T242

## goal
The checks knowable from the plan alone run on the server before any render starts, whichever kind is about to run it, and the server accepts a file verdict measured by whoever produced the file.

## acceptance
- [v] every plan-derived check that runs today inside the render path runs before the render starts, for both kinds, and a refusal names what it named before
- [v] a server render keeps checking its own output file as it does today
- [v] the server accepts a reported file verdict — resolution, frame rate, codec, loudness, duration — for a render it did not produce, and records a failing verdict as a CLIP-109 notice rather than silently accepting the file
- [v] the verdict settles the render without the server decoding the stored file again, whichever side produced it
- [v] go test: a plan failing a check is refused before the render starts for both kinds; a reported verdict outside the output contract is recorded; a passing verdict settles the render
- [v] verify: `cd backend && test -z "$(gofmt -l .)" && go vet ./... && go build ./... && go test ./...` (`-timeout 30m` for `clip/store`) · `pnpm gen:proto && git diff --exit-code -- backend/internal/gen frontend/src/shared/api/gen agent/internal/gen` · `pnpm --filter ./frontend test` · `pnpm lint` · `pnpm build:web`
- [v] docker: the media smoke stage green (ARCH-37)

## impl notes
- the plan checks already live in the render admission path (`clip/media/composition_admission.go` and its callers); this task lifts them ahead of the kind branch rather than rewriting them
- proto: one RPC carrying the measured verdict for a render the server did not run, keyed by the render it settles; the measurements are the CDS-52 output contract's own fields
- the browser side of this — actually measuring an output — belongs to the browser cluster and is not built here; this task makes the server able to receive a verdict
- a browser render's file IS stored like any result under CLIP-158; what never happens is the server decoding it to check it, which is the decode the browser kind exists to avoid
