# T054 Every backend failure reason the browser can be handed
> st:done@260908 | ssot:ARCH-24 ARCH-3 | base:ARCH@2 | dep:-

## goal
Register the three reasons the backend already emits but the browser cannot display, and add the gate that would have caught them.

## acceptance
- [v] `BILLING_SELECTION_INVALID`, `COMBO_INCOMPLETE` and `COMBO_UNKNOWN` are registered in `appFailureSpecs` and carry a message in both the Korean and English error catalogs
- [v] each message says what the person can do about it, matching the specificity of the handler that chose the reason
- [v] a backend test pins the complete inventory of reason strings the API can return, so adding a reason without registering it fails a test rather than reaching a user as the generic unknown failure
- [v] that inventory names, in its own doc comment, the browser file a new entry must also be added to
- [v] the existing frontend check that both catalogs cover every registered failure still passes
- [v] ARCH-26 and the frontend test suite pass

## impl notes
- from review/diff-260908 F8
- the defect: the three reasons are emitted at `billing/rpc/handler.go:154` and `auth/rpc/admin.go:113,119` but appear in neither `appFailureSpecs` nor `resources/{en,ko}/errors.ts`, so `appFailureFromConnect` cannot match them and the operator assigning an unknown combo, or a client quoting an unbillable tier, reads the catch-all copy instead
- the frontend gate is not broken, it is one-sided: `resources.test.ts` compares the two catalogs against `appFailureSpecs`, which only proves the browser agrees with itself. A reason missing from all three is invisible to it, which is exactly what happened
- so the missing half belongs on the Go side, where the reasons are actually created: one committed inventory the API's own tests assert against. Several rpc packages already pin their reason strings in tests (`auth/rpc/plan_test.go`, `provider/rpc/errors_test.go`), so this consolidates a habit rather than inventing a mechanism
- the proto carries no enum for these reasons, so a generated cross-language check is not available; a committed list plus a pointer in its comment is the honest gate at this stack's seam (ARCH-3 keeps the proto the only generated contract)

## result
- Changed: new `backend/internal/platform/rpcserver/failure_reasons_test.go` (the committed inventory of 169 reasons plus the AST scan that rebuilds it from source) · `frontend/src/shared/api/app-failure.ts` · `frontend/src/app/providers/i18n/resources/{ko,en}/errors.ts`.
- The gate found EIGHT unregistered reasons, not three. Besides `BILLING_SELECTION_INVALID` `COMBO_INCOMPLETE` `COMBO_UNKNOWN`, the browser could not display `MODEL_PURPOSE_INVALID` `MODEL_PURPOSE_INELIGIBLE` `MODEL_PURPOSE_NOT_REGISTERED` (modelcatalog/rpc/handler.go:162-166), `POST_PHOTO_LIMIT` (post/rpc/handler.go:251) or `PURPOSE_NOT_FOUND` (post/rpc/handler.go:283). All eight are registered with copy in both catalogs — leaving the five out would have failed the new test on its first run, which is the gate working.
- How the scan reads a reason: the literal third argument of every `NewAppError` call, plus any constant, variable or assignment whose NAME mentions a reason and whose VALUE is SCREAMING_SNAKE — which is how the typed failures reached through the `Failure` interface (`plan.ReasonInsufficientCredits`, `provider.ReasonSetUnavailable`) and the two handlers that pick a reason into a local variable are picked up. A `NewAppError` whose reason the scan cannot read fails the test by name and position rather than being skipped.
- Two reasons are registered in the browser and emitted by no handler: `NETWORK_UNAVAILABLE` (the browser synthesises it for a dead transport) and `VOICE_PROFILE_FIELD_REQUIRED`. The backend inventory deliberately does not fail on browser-only entries — the first is legitimately client-side; the second may be dead copy and is worth a look, but deleting frontend copy was not in this task.
- Mutation-checked: renaming one emitted reason fails the test with both halves of the diff named.
