# T389 Initialize the existing VPS CPU worker on its first automated deployment
> st:done@260925 | ssot:ARCH-24 ARCH-32 ARCH-47 ARCH-54 ARCH-59 | base:ARCH@11 | dep:T388

## goal
Fix automated backend rollout when an existing colocated VPS has no worker.env, without resetting existing workers or weakening subsequent rollback checks.

## acceptance
- [v] The backend deployment workflow explicitly opts into idempotent colocated CPU initialization before the first service replacement; missing worker.env no longer requires manual credential creation on the default VPS.
- [v] Initialization writes a private worker.env from the execution-only template, creates a random deployment-specific worker credential and merges it into the API env while preserving unrelated settings and credentials; existing worker files and remote/GPU placement are not overwritten or guessed.
- [v] Interrupted or failed first initialization reuses its credentials and retains the original configuration; the first forward-only transition saves a consistent read-only SQLite backup before downtime, and a retry can finish without accidentally booting a legacy API against migrated data.
- [v] Existing deployments retain contract checks, drain, health-gated rollback and independent worker pins; automatic initialization cannot bypass the rollback floor after a supported last-good deployment exists.
- [v] Regression tests cover the reported missing-file shape, retries/partial initialization, credential preservation, DB backup and failures, existing/remote configurations and workflow wiring; required repository checks pass and DEPLOY.md describes the automated first transition.

## impl notes
- Direct user-reported regression follow-up to T386/T388; consume no pending GPU/product SSOT deltas and do not modify other task waves.
- Add an explicit --init-worker deployment option used by GitHub Actions; routine manual commands remain strict. Reject combining initialization with --check/--drain/--rollback so their existing side-effect contracts remain clear.
- Initialize only an absent worker.env in the default colocated CPU API role with no last-good snapshot; resolve .env through Compose, generate a project-scoped identity and secrets.token_urlsafe(32), preserve any existing credential for that identity, and save original configuration before atomic file writes.
- API credential write precedes worker.env publication so retry after interruption reuses the same token. Never print env values or credentials. An initialization snapshot plus absence of last-good permits retry of this specific first forward-only transition only; remote/GPU/ordinary established deployments retain existing explicit bootstrap rules.
- Before the first automatic forward-only replacement, use Python sqlite3's online backup API against the existing API bind-mounted DB in read-only mode, with a finite deadline, private temporary destination and atomic completion; no database restore or migration is performed by deployment tooling.
- Existing user authorization to fix deployment and commit each task covers repository changes and their tests; no live SSH, deployment or push is needed to verify this fix.
