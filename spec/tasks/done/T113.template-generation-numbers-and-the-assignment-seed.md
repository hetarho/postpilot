# T113 A template carries a target length and a tag count, and assigning it seeds the post

## goal
Give a template two optional authored numbers (`target_length`, `tag_count`) and copy the ones it has set onto the post's own options inside the transaction that assigns the template.

## acceptance
- [v] `proto/postpilot/v1/template.proto` carries the two numbers on `Template`, `CreateTemplateRequest` and `UpdateTemplateRequest` as `optional int32`, documented as absent = 값 없음 on both write messages; `TemplateRef` is unchanged; `pnpm gen:proto` leaves no diff (ARCH-28)
- [v] a migration adds `templates.target_length` and `templates.tag_count`, both nullable with no default and no backfill, and its `migration_0043_test.go` proves an existing template row survives with both NULL
- [v] the template context validates a present `target_length` as a positive integer within the post's own bounds and a present `tag_count` within `PostTagCountMin`…`PostTagCountMax`, refusing out-of-range as `InvalidArgument` `TEMPLATE_NUMBER_OUT_OF_RANGE` with `field` `min` `actual` params plus `max` where there is one; NULL stays valid on both and is what an absent field writes
- [v] CreateTemplate stores both numbers and UpdateTemplate writes both columns on every call (absent = NULL), while `name`/`description`/`body` keep their per-present-field statements; a patch carrying only the two numbers is still an edit and is not short-circuited by the empty-patch path
- [v] `post.TemplateRef` carries the two numbers, `postTemplates` in `cmd/api` fills them from the template service, and SaveDraft seeds them: the update path writes them in the same statement as `template_id` (a set number overwrites, an unset one leaves the post's value alone) and the create path stores them with the inserted post
- [v] seeding happens only when a template is assigned: a present-empty `template_id` (없음), an absent one, a re-assignment of the id already stored, a rename, a body edit and a delete change neither number; an assignment refused for an unknown or foreign id writes nothing at all
- [v] a seeded post advances no revision, moves no baseline and demotes nothing, and GetPost/SavePostDraft report the seeded values on the same response (POST-70)
- [v] no prompt, payload, freeze, snapshot or input hash reads a template's numbers — the generation and revision paths keep freezing the post's `target_length`/`tag_count` and their golden prompts stay byte-identical (TMPL-47)
- [v] tests: template service/store round-trip and both range refusals, the update writing an unset number back to NULL, post seeding on create and on re-assign (set · unset · 없음 · same id · refused id), and a generation-freeze test proving the template's numbers never reach the payload
- [v] `cd backend && test -z "$(gofmt -l .)" && go vet ./... && go build ./... && go test ./...` (ARCH-26) and ARCH-28 pass

## impl notes
- bounds are the post's, not a second set: reuse `config.PostTagCountMin`/`Max` and the post's positive-length rule (`backend/internal/platform/config`) rather than adding a `TEMPLATE_*` key — the number only ever lands in a post option, so a template must not be able to store one the post would refuse (TMPL-6, ARCH-21)
- the migration number is whatever is free at implementation time (0043 as of writing; the CDS session is adding migrations in the same tree — take the next unused number and name the test file after it)
- `template.Template` and `template.Patch` gain `TargetLength *int` and `TagCount *int`. `Patch.empty()` must count them, and the store's `Update` writes `target_length`/`tag_count` unconditionally in its existing transaction (one extra statement, or two, alongside the per-field ones) — this is the deliberate exception in TMPL-8: the template screen holds both numbers and always sends them, so a second presence meaning would only give an unset number two ways to be written
- `AssignPostTemplate` seeds with `COALESCE`: `target_length = COALESCE(sqlc.narg(seed_target_length), target_length)`, same for `tag_count`. A seed parameter is non-NULL only when the template has that number set, so COALESCE says exactly "overwrite when set, keep otherwise" in one statement with the assignment (POST-26)
- `assignableTemplate` currently answers with the id string; have it answer with the `TemplateRef` from the directory it already lists, so the seed needs no new port and no second read of the templates table (ARCH-7, ARCH-8)
- clearing to 없음 passes no seed at all rather than a NULL-meaning-clear: TMPL-48 keeps the values the post last received
- `SaveGenerationOptions` is untouched — the seed is a different writer of the same two columns, not a call into the options path, and it must not go through an rpc the assignment would then depend on
- the template rpc handler maps the new error the way `FieldTooLongError` is mapped today (typed error in `types.go`, one case in the handler's switch, allowlisted params only)
- `model_experiments`, the generation payload and every prompt builder stay as they are; if a test has to prove a negative, assert on the frozen payload rather than on the prompt text

## result
- contract: `proto/postpilot/v1/template.proto` r+2 fields on `Template`, `CreateTemplateRequest`, `UpdateTemplateRequest`; `TemplateRef` untouched, so no post read model carries a template's number. Regenerated Go/TS/agent code committed with it and stable across a second `pnpm gen:proto`
- schema: `migrations/0043_template_generation_numbers.sql` + `migration_0043_test.go` (existing rows keep both NULL, an insert naming neither writes NULL)
- template context: `Template.TargetLength/TagCount`, `Patch.Numbers` (the pair written together), `Limits.TargetLengthMin/TagCountMin/TagCountMax`, `NumberOutOfRangeError`, `validNumbers`, `UpdateTemplateNumbers` query, `nullNumber`/`numberOf` at the SQL edge, `TEMPLATE_NUMBER_OUT_OF_RANGE` in the rpc handler and in the `publicFailureReasons` list
- post context: `TemplateRef` carries the numbers, `TemplateNumbers`/`TemplateRef.Seeds()`, `assignableTemplate` answers with the ref, `AssignTemplate` takes the seed and the SQL seeds with `COALESCE` in the assigning statement, `CreatePost` inserts the seeds, `postTemplates` in `cmd/api` fills them
- deviation from the task's wording, worth knowing: the target length has a FLOOR and no ceiling, because the post's own option has none (POST-20 accepts any positive value). `NumberOutOfRangeError.Max` 0 means unbounded and the rpc then omits the `max` param rather than claiming a ceiling nobody set. The tag count carries both bounds
- `TEMPLATE_NUMBER_OUT_OF_RANGE` is registered on the backend half of the cross-language contract only; the browser allowlist and the ko/en copy are T114's (no surface sends a number yet, so nothing can raise it in the product today)
- gotcha for the next session: a NON-ASCII character anywhere in a `queries/*.sql` file breaks sqlc's parameter rewriting for the WHOLE file (it computes byte offsets and rewrites at rune positions), and it fails in queries you never touched. Both query files stay ASCII-only; Korean belongs in the Go comments
- verify: `gofmt -l` clean · `go vet ./...` · `go build ./...` · `go test ./...` all green; generated code stable after regeneration (ARCH-28).
