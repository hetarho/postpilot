# T055 The `ask` construct in both parsers and in the builder's block model

## goal
Teach one grammar rule to both parsers and the builder's block model: `<ask>` parses, serializes byte-exactly, refuses the three new ways it can be wrong, and reads back as a row — with no UI and no rendering yet.

## impl notes
- node shape: `ask{label, text}` — `text` empty is the verbatim flavor and non-empty is the instruction flavor, which is the one bit that decides everything downstream (→TEMPLATE-43). Keep the raw source slice like `write` does so byte-exact serialization stays true by construction (→TEMPLATE-19)
- both empty forms (`/>` and `></ask>`) parse to the same node and each serializes back to what it was written as — the source slice already does this, so no canonicalization pass. `slot`'s malformed_tag-on-closing-tag rule does NOT apply to `ask`
- `label` is validated in the parser, not only at save: `missing_attribute` for absent or empty after trim, `too_many_asks` past `askMaxPerBody`, `duplicate_ask_label` on the second identical label (compare decoded and trimmed), `ask_in_repeat` when the node is a `repeat` child. `ask_in_repeat` is its own reason rather than `unknown_tag` because the tag is real and it is the PLACE that is wrong (→TEMPLATE-43)
- a label's LENGTH is not a parse reason: TEMPLATE-20's list is authoritative and adding a fourth reason would put a configured ceiling inside the shared fixture's semantics. `TEMPLATE_ASK_LABEL_MAX_CHARS` is enforced on the save path beside the other field bounds — `FieldTooLongError{Field: "ask_label"}` → `TEMPLATE_FIELD_TOO_LONG`, which the editor already renders — and the browser mirrors it as a live counter on the 제목 field (T058)
- `ask` holds text only: a `<write>`, `<slot>`, `<note>` or `<repeat>` inside it is `unknown_tag` at that inner tag's line, matching how `write` already refuses nesting
- `askFields` is what the write screen reads (T059) and it must never throw: a body that does not parse yields `[]`, because ① is not where a broken template is fixed
- blocks.ts: `BuilderBlock` gains an optional `ask?: string` on the `write` and `text` variants only. A `text` block with `ask` set ignores its `text` field entirely on the way out — the title IS the authored content of that row (→TEMPLATE-44)
- no UI in this task and no rendering: `template.Render` still ignores an ask node (T057 gives it meaning), so a body with one is parseable and storable but reaches no prompt yet. Nothing can author one until T058, so no stored body can hit that gap
