# T320 The backend gate reports a result
> st:done@260922 | ssot:ARCH-26 ARCH-31 | base:ARCH@9 | dep:-

## goal
- The documented backend verify command and the CI step that runs it finish on the two packages that pass Go's per-package default, so a failure means a failure rather than a clock.

## acceptance
- [v] Every place that runs the backend suite carries the same bound the decision names: the CI workflow's `go test` step and any script or doc that repeats the command.
- [v] `cd backend && go test -timeout 30m ./...` completes and reports per-package results, `cmd/api` and `internal/clip/store` included.
- [v] Nothing else about the gate moves: the same packages run, `gofmt`, `go vet` and `go build` are untouched, and no test is skipped or shortened to fit.

## impl notes
- `.github/workflows/ci.yml`: `- run: go test ./...` becomes `- run: go test -timeout 30m ./...`. The job's own timeout already exceeds that, so the flag bounds the suite rather than the runner.
- Grep for any other copy of the command (`README`, `DEPLOY.md`, scripts) and give it the same bound; the decision is the one place the command is defined, and a second copy that disagrees is what let this drift.
- No test changes. The two packages are long because they run real SQLite and the whole boot sequence, which is what makes them worth having; making them fit a ten-minute budget would mean removing that.
- No new test: this task changes a command, and the acceptance is the command finishing. Running it is the verification (ARCH-24's test requirement is about behaviour changes, and this changes none).

## result
- `.github/workflows/ci.yml` is the only place that actually ran the command; every other copy the grep found is a finished task's own record of a run, which is history and stays as it was written.
- Measured before changing anything, each package on its own: `cmd/api` 1018s, `internal/clip/store` 828s. Both are past Go's ten-minute per-package default, so the documented gate could only ever report a clock. `internal/platform/db` is not one of them — it takes 99–166s alone and only expired while three suites of mine shared the machine.
- The bounded run finishes and names a result per package, which is the point: it immediately surfaced `TestTheSoundSettingDoesNotInvalidateAnInterruptedCandidate` failing inside `internal/clip/store`. That test passes on its own and was invisible while the package only ever reported a clock. It is a finding this task uncovered rather than one it caused, and it is recorded in STATE for its own task.
- No test was skipped, shortened or moved. The two packages are long because they run real SQLite and the whole boot sequence, which is the reason they are worth having.
