# T289 memories are a table, a context and a directory RPC family
> st:done@260920 | ssot:MEM-1 MEM-3 MEM-4 MEM-5 MEM-9 MEM-11 MEM-12 MEM-16 MEM-17 MEM-23 MEM-25 ARCH-5 ARCH-6 ARCH-10 ARCH-41 ARCH-24 | base:MEM@1 | dep:-

## goal
Create the memory aggregate end to end on the backend: schema, domain context, field rules, deduplication, cap, source links and the four directory procedures.

## acceptance
- [v] a goose migration creates `memories`, `memory_tags` and `memory_sources`: the five-value `kind` CHECK, `memories(user_id, text)` UNIQUE, `memories(id, user_id)` as the composite target, an index on `memory_tags(user_id, tag)`, and `memory_sources` cascading on its memory; `PRAGMA integrity_check` and the existing migration test pass on a migrated temp DB
- [v] `internal/memory` holds the domain types, service, consumer-owned ports and store; `kind` is a typed enum whose zero value is invalid and whose parser refuses an unknown string
- [v] `proto/postpilot/v1/memory.proto` carries one `MemoryService` with `CreateMemory` `ListMemories` `UpdateMemory` `DeleteMemory`; generated code is committed and `pnpm gen:proto` leaves no diff
- [v] create: trimmed non-empty `text` of at most `MemoryTextMaxChars`, at most `MemoryTagsMax` distinct trimmed tags (duplicates within one request collapse), an explicitly present supported `kind` refused otherwise as `InvalidArgument`
- [v] an exact duplicate text after trim inserts nothing: it adds the source link, advances `last_seen_at` and answers the existing memory; no similarity, fuzzy or semantic matching exists anywhere
- [v] the cap is read inside the insert transaction and a create beyond `MemoryMaxPerAccount` is `FailedPrecondition` naming the cap; nothing is evicted
- [v] deleting a post drops its source links and deletes only the memories whose last link it was, after the post row is gone; a failure is logged and never fails the post delete
- [v] every query is scoped by the authenticated user; a foreign id is indistinguishable from an unknown one (`NotFound`)
- [v] the memory queries file is ASCII-only and `pnpm gen:sql` leaves no diff
- [v] store and service tests over a migrated temp SQLite pin: a duplicate adds a link instead of a row, the cap refuses, a foreign id is `NotFound`, a post delete removes a single-linked memory and leaves a multi-linked one
- [v] ARCH-26 and ARCH-28 pass

## impl notes
- bounds mirror the guideline ceilings exactly — `MEMORY_TEXT_MAX_CHARS` (120), `MEMORY_TAGS_MAX` (5), `MEMORY_MAX_PER_ACCOUNT` (300), `MEMORY_INJECT_MAX` (8) read in `platform/config` with those defaults and mirrored as `VITE_*` in the FE's `shared/config`; the frontend hardcodes none
- tags are their own table rather than a JSON column: retrieval (T290) matches on them and the index is the entire reason
- `memory_sources` holds the post slug, never a post row id, and its FK cascades so a deleted post cannot leave a dangling link; the orphan deletion is still an explicit statement because CASCADE cannot express "only when it was the last link" (MEM-17)
- the post-delete hook is a consumer-declared port on the post context, wired in `cmd/api`, following GUIDE-13's candidate detach: it runs after the post row is gone and its failure is logged
- a dedupe hit advances `last_seen_at` and does NOT touch `updated_at`: ordering reads the former, and the latter belongs to an authored edit
- `CreateMemory` is also the hand-authoring path (MEM-25); there is no separate procedure for it

## result
- schema: `0069_memories.sql` creates `memories` (five-value `kind` CHECK, `UNIQUE(user_id, text)`, `UNIQUE(id, user_id)` as the composite target), `memory_tags` (PK `(memory_id, tag)`, `idx_memory_tags_lookup(user_id, tag)`) and `memory_sources` (PK `(memory_id, post_slug)`, `idx_memory_sources_post`), both children cascading on their memory. `migration_0069_test.go` pins the kind CHECK, per-account text uniqueness, the cross-account child refusal, the cascade, `PRAGMA integrity_check` and `pragma_foreign_key_check`.
- domain: `internal/memory` — `types.go` (typed `Kind` whose zero value is invalid, `ParseKind` refusing an unknown string, `Kind.AlwaysCandidate()` carrying MEM-6's split for T290, the four errors and the two count-carrying ones), `ports.go` (consumer-declared `Store`), `service.go` (one `Create` that is both the approval and the hand-authoring path, presence-based `Update`, `Delete`, `DetachPost`). `service_test.go` covers every field rule in one table, the cap/source hand-off, the dedupe report and the kind enum.
- store: `store/store.go` does the lookup, the cap and the write in ONE transaction; a duplicate text touches `last_seen_at`, links the post and answers the existing row untouched. `store_test.go` pins the dedupe, the cap (and that a re-approval at the cap still works), the foreign-id `NotFound` on get/update/delete, the post-delete rule and the list order. Queries are ASCII-only; `pnpm gen:sql` is idempotent.
- rpc: `memory.proto` carries `MemoryService` with the four procedures, `MemoryKind` and a `deduplicated` flag on the create response; `rpc/handler.go` maps every sentinel to a stable reason and `handler_test.go` pins the codes, the param-carrying refusals, the session requirement, the absence of any user id in the contract and the kind round-trip.
- wiring: `platform/config` reads `MEMORY_TEXT_MAX_CHARS` (120) `MEMORY_TAGS_MAX` (5) `MEMORY_MAX_PER_ACCOUNT` (300) `MEMORY_INJECT_MAX` (8); `cmd/api` constructs the context and serves the handler (the wiring test's handler count is now 23); `.env.example` and the FE's `shared/config` `ENV_LIMIT_OVERRIDES` carry all four as `VITE_*`. Eight `MEMORY_*` failure reasons were added to `error.proto` with their FE specs and both error catalogues. `agent/buf.gen.yaml` gained the `memory.proto` mapping the agent module needs.
- post-delete: a new consumer-declared `post.MemorySourceDetacher`, wired through `postMemoryLinks`, called after the post row is gone; its failure is logged and never fails the delete (`TestDeletePostDetachesMemorySources`).
- DEVIATION from the impl notes: `memory_sources.post_slug` is a plain column with NO foreign key to `posts`, the way `guideline_candidates.post_slug` is. An `ON DELETE CASCADE` there would take the links away BEFORE the post context's after-the-row hook could count them, and "the memory goes only when that post held its LAST link" (MEM-17) would then be indistinguishable from "the memory has no links at all", which is exactly a hand-written memory (MEM-25). The orphan deletion is the explicit statement the note asks for, scoped to the memories that just lost a link. The cost is the same one the guideline candidate link accepts: a hook that fails leaves a dead link, not a leak.
- gates: ARCH-26 (gofmt, vet, build, full `go test ./...`), ARCH-27 (agent), ARCH-28 (both generators re-run with no change) and ARCH-25 (2218 vitest tests, lint, lint:fsd, lint:style, build:web) are green.
- No SSOT deviation. T290 can take `Kind.AlwaysCandidate()`, `MemoryInjectMax` and the tag index as they stand.
