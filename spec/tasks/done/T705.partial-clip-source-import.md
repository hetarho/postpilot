## goal
A new clip imported from a post keeps the videos whose uploads were verified when another transfer fails, without re-uploading successful files, starting AI or changing original-retention policy.

## acceptance
- [v] An owner-scoped `CompleteClipSourceImport` RPC completes the current initial source batch with every confirmed source and excludes only pending sources. Refuse a foreign/stale batch, finalized/deleting/revoked project, active job/attempt or a project with analysis/storyline/edit-plan material before changing anything. An already completed request returns its owned receipt without changing retention or source identities.
- [v] Partial completion atomically creates a ready batch and moves its existing ready leases there, preserving canonical IDs, object keys/bytes, metadata, audio choices, original order and retention timestamps. The old batch contains only pending leases and follows existing durable cleanup/late-PUT handling. An entirely ready batch stays unchanged; an entirely pending batch uses the existing discard behavior and leaves an empty clip. No storage copy, provider call or new migration is needed.
- [v] A narrow import confirmation option on `ConfirmClipSource` verifies each object under the same bounds as ordinary confirmation, but a single invalid object does not discard already confirmed siblings. It is refused outside the same initial, owned, idle import scope. Ordinary confirmation keeps its present behavior.
- [v] `entities/clip-project` exports typed completion calls and the optional confirmation flag; proto descriptors/mapping stay inside its API segment. `upload-clip-sources` exports a one-shot file-transfer entry through the existing pipeline: independently validate files and aggregate count/duration/bytes, reserve once, put/confirm individually, reconcile the final completion receipt, report omitted/failed filenames, and retain successful originals after partial failure or an uncertain response. No automatic AI starts.
- [v] Tests: `internal/clip/store/source_import_test.go` covers owned/current/idle initial scope, foreign/stale/active/finalized refusals, exact lease/key/order/expiry preservation, lost-ack replay and cleanup that cannot delete moved originals; `internal/clip/app/source_import_test.go` covers invalid-object sibling preservation and unchanged ordinary confirmation; RPC tests pin auth and request mapping. `features/upload-clip-sources/api/import.test.ts` covers a fetched File through the real pipeline collaborators, transfer failures, lost confirmation acknowledgements and count/duration/byte/duplicate bounds.
- [v] Generated proto/SQL outputs are committed and reproduce without a diff. Task checks cover the affected source lifecycle/store/RPC/root consumers, frontend source pipeline and existing sessions; ARCH-31 CI and deployment/media parity pass before push.

## impl notes
- Supports T692's existing partial-transfer acceptance. Its current `ClipSourceSession.select` discards the entire batch on failure, so T692 is temporarily blocked on this primitive; its acceptance is unchanged. Keep ordinary picker/session cancellation semantics intact.
- Use an optional consumer-owned source-store port for initial-import validation and completion rather than widening unrelated stores. All mutation guards and current-batch selection run in the serialized writer transaction; object HEAD/signing/deletion stay outside it.
- New ready batch IDs are deterministically derived from a versioned prefix plus owner/project/original batch ID (SHA-256 truncated to the normal 128-bit hex shape). Repeating completion recognizes only that project's currently selected derived batch as the receipt. This avoids a new persistence format or retention extension. All-ready completion returns the original batch.
- Reparent ready leases rather than recreating or copying them. Their object keys may still contain the old batch prefix, as existing canonical identities already survive lease reselection; key reachability remains authoritative for cleanup. Mark the now pending-only old batch through existing cleanup statements after the move, without deleting ready originals or allowing late PUTs to survive the existing sweep.
- An import-only confirmation flag defaults off and is accepted only before derived clip material or any job exists. An invalid/absent object stays pending for completion/cleanup; it never becomes ready. A failed confirmation response is reconciled against the completion receipt before a filename is reported missing.
- Aggregate limits use the existing clip-design source constants and actual browser metadata/fingerprints, not the post's reported duration alone. Read one file at a time; do not retain the whole post's downloaded videos beyond the source limit. Fetch orchestration, dialog, navigation and the post-to-clip draft belong to T692.
- No new library, pricing/security policy, original-retention duration or platform publishing operation is introduced; the proto and entity API own the internal RPC shape under ARCH-17.
