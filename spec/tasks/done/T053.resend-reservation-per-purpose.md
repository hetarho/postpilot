# T053 One resend reservation per purpose
> st:done@260908 | ssot:ARCH-23 | base:ARCH@2 | dep:-

## goal
Stop an email verification and a password reset for the same address from suppressing each other.

## acceptance
- [v] the resend reservation is scoped to the purpose as well as the address, so a verification reservation cannot refuse a password-reset request and the reverse
- [v] the 60-second floor still holds within one purpose, for both purposes
- [v] the reservation is still released on every failure path that releases it today, and releasing one purpose leaves the other untouched
- [v] the sweep of expired reservations still runs and drops only expired ones
- [v] tests cover: a signup followed within the floor by a reset request producing a stored link and a sent mail; the reverse order; a second request in the same purpose inside the floor still refused; and the floor expiring per purpose
- [v] ARCH-26 passes

## impl notes
- from review/diff-260908 F7
- the defect: `reserveResend` keys `lastResend` by email alone and both `sendVerification` and `RequestPasswordReset` reserve through it, so whichever came first silently returns `nil` for the other — no link stored, no mail sent, while the handler still reports success to avoid address enumeration. The user waits for a mail that will never arrive
- the fix is the map's key, not the flow: the existing `LinkPurpose` values already name the two purposes, so a `{purpose, email}` key reuses vocabulary that is already there. `releaseResend` takes the same key
- the per-IP throttle classes (`ThrottleResend`, `ThrottleResetRequest`) are already separate, which is the shape this in-process floor should have matched

## result
- Changed: `backend/internal/auth/service.go` (`lastResend` is keyed by a new `resendKey{purpose, email}`; `reserveResend`/`releaseResend` take the purpose; all eleven call sites pass `LinkPurposeVerifyEmail` or `LinkPurposeResetPassword`) · `auth/service_test.go` (+two tests).
- One deviation from the acceptance's test list, because the flow it names cannot happen: a reset only acts on a VERIFIED address and a verification only on an unverified one, so "a signup followed within the floor by a reset request" is reachable only as verify-then-reset (the account verifies, then asks for a reset in the same minute) and the reverse order is not reachable through the RPCs at all. The flow test pins the reachable sequence end to end — two mails, one link of each purpose — and a second test pins the reservation primitive in BOTH orders, which is where the defect actually lived.
- That primitive test also covers the rest of the list: the floor holding inside one purpose, a release freeing only its own purpose, expiry per purpose, and the sweep leaving an unexpired reservation of the other purpose alone.
- Mutation-checked: with the key's purpose field dropped, both tests fail — the flow test on a single mail with only a verify link.
- Nothing diverged from ARCH-23; no update-ssot owed.
