# T194 The overlay and the delivery encode become one
> st:done@260916 | ssot:CLIP-124 CLIP-125 | base:CLIP@30 ARCH@2 | dep:T191

## goal
Stop writing a lossless full-length intermediate between the overlay pass and the delivery encode when the clip has a single overlay window.

## acceptance
- [v] a clip whose elements fit one window is overlaid and encoded for delivery in one invocation, writing no intermediate between them
- [v] a clip needing more than one window keeps today's windowed path, and the window boundaries are chosen exactly as they are now (→CDS-9)
- [v] the audio track joins at the same point it joins today, and the clip is still produced by one AAC encode (→CDS-35)
- [v] the loudness measurement and correction still read the assembled track, and the delivered file still passes the output checks it passes today (→CDS-52)
- [v] the delivered clip is unchanged (→T191)
- [v] tests: filter-graph goldens for the fused single-window case and for the unchanged multi-window case, plus the identity regression from T191
- [v] verify BE (ARCH-26) passes

## impl notes
- `overlayComposition` (`media/composition_plates.go`) writes each window losslessly and `renderComposition` (`media/composition_render.go:171`) then reads those pieces back for the delivery encode; with one window that round trip costs a lossless encode, a decode and nothing else
- `compositionWindows` (`media/composition_batches.go`) already reports how many windows a plan needs and `OverlayBatchSize` is 8 (`platform/config/clip_render.go`), so the single-window condition is one layer batch and one window
- the delivery arguments are `encodeArgs` (`media/render.go`) and the audio input is appended by `compositionInputs`; fusing means appending those to the overlay graph's output rather than to a fresh invocation
- measured on prod for a 30-second clip: the lossless overlay write is about 67 s, reading it back about 45 s and the delivery encode about 75 s, so the fused pass replaces roughly 187 s of work with roughly 90 s

## result
- `media/composition_plates.go`: new `deliveredOverlayArgs` builds one invocation that overlays AND delivers — the raw composition, this window's plates and (when there is one) the assembled track as inputs, the overlay graph carrying straight on into the delivery format
- the fused graph's tail repeats exactly what the windowed path's delivery pass does to its piece (`,settb=AVTB,setpts=PTS-STARTPTS,trim=end_frame=N,setpts=PTS-STARTPTS,format=yuv420p`), so only the lossless round trip is removed and the filter chain a pixel travels is otherwise identical
- `media/composition_render.go`: `compositionWindows` is now called once in the caller and passed to `overlayComposition`, and a plan of one window whose layers fit one batch takes the fused path; anything else keeps today's pieces and its separate delivery pass, with the boundaries chosen by the same unchanged planner
- the audio joins where it always did — one already-measured track entering the single delivery invocation, still one AAC encode, with `measureLoudness`/`finishLoudness` and `validateRenderedOutput` untouched
- tests: three new goldens (`testdata/overlay-{fused,fused-audio,windowed}.filter`) record the graph and input count of each path, and the test refuses a case that silently takes the wrong one
- identity held: `TestDeliveredClipIdentity` passes against T191's baseline (94.2 s, was 105.5 s before this change on this box — the baseline plan is a single window, so it takes the fused path). On prod the pair it replaces measured about 187 s of a 30-second clip's render
- no SSOT difference; verify BE (ARCH-26) passes (`go test ./...` with `-p 2`: the full-parallel run is OOM-killed on this box)
