# T196 Preparation decodes each original once
> st:done@260916 | ssot:CLIP-33 CLIP-124 CLIP-32 | base:CLIP@30 ARCH@2 | dep:-

## goal
Verify a source and produce its analysis copies from the same decode, so an original is never decoded twice before the first AI call.

## acceptance
- [v] each original is decoded once during preparation, and source verification reads its measurements from that decode (→CLIP-33)
- [v] the decoded duration, the decoded frame count and the constant-cadence verdict are the values today's separate verification pass produces, for a single-chunk and for a multi-chunk source
- [v] every source and every analysis copy is still verified before the first AI call, and a container that overstates its duration is still refused with the media cause it is refused with today (→CLIP-32)
- [v] the analysis copies are byte-identical to the ones produced before the change, so the observations and the plan they feed are unaffected
- [v] a source whose cadence cannot be verified still resolves to the playback rates it resolves to today (→CLIP-98 →CDS-68)
- [v] tests: the measured duration, frame count and cadence verdict agreeing with the separate pass for a constant-rate source, a variable-rate source and a source spanning more than one chunk; plus a copy-byte comparison
- [v] verify BE (ARCH-26) passes

## impl notes
- today `Probe` (`media/probe.go:128`) decodes the whole original with vfrdet and `-fps_mode passthrough`, and `prepareChunk` (`media/chunks.go`) then decodes the same original again to encode each copy; on prod this is most of the 285 s preparation stage, where HEVC decode measured 27 fps and the copy encode 25 fps
- one invocation can carry both: a verification output (`-vf vfrdet -fps_mode passthrough -f null -`) and the copy output, from one decode. Measured on prod against real HEVC, the two-output command took 10.96 s where the two separate commands took 9.70 s and 10.87 s, and the copy was identical in size
- output order decides what `-progress` reports: `frame=` follows the FIRST output, while `out_time_us` is the maximum across outputs. Put the verification output FIRST and `frame=` and `out_time_us` describe the source decode exactly as they do today — verified with a source whose two outputs differ in length (45 frames on the capped copy, 300 reported for the verification decode)
- the second filter graph also emits vfrdet's `(0/0)` negotiation line; `constantCadenceReport` (`media/probe.go`) already ignores a report with a zero constant count and requires exactly one measured graph, so it needs no change
- the container duration from ffprobe stays the cheap first read that decides how many copies a source needs; the decode then confirms or refuses it, which keeps the refusal before any AI call rather than before any encode
- for a source of more than one chunk, sum the per-chunk verification measurements — the seeks are accurate, so the chunks tile the source exactly

## result
- `media/probe.go`: `Probe` split into `probeContainer` (the ffprobe read), the new `ProbeContainer` (that read plus the length a header alone can settle — the shorter of container and video track) and `measuredInfo`, which applies today's unchanged length rules to a decode's measurement. `decodeMeasurement` parses `-progress` output for both callers
- `media/chunks.go`: the analysis-copy command now carries a verification output (`-vf vfrdet -fps_mode passthrough -f null -`) FIRST, from the same decode, so `frame=` follows the source decode exactly as the separate pass reported it while `out_time_us` stays the maximum. `PrepareAnalysisChunks[Except]` returns the source's measured `MediaInfo`, summing the per-chunk measurements
- `media/capacity.go`: `runBoundedLog` — a bounded run whose own log is a result. `StderrLimit` 8 KiB→16 KiB, because the copy command now logs at `-v info` (measured 4.9 KiB for a 20 s source with audio)
- `clip.Media.PrepareAnalysisChunks` returns `(MediaInfo, error)`; `generation.go` reads the container claim through `probeSource` (`ProbeContainer` when the adapter offers it), admits on it, prepares, and then re-admits on the measured info, refusing as `ErrInvalidMedia` any claim that would have produced a different number of copies
- exception, stated plainly: when a recovery reuses SOME chunks of a source, the intervals it re-prepares do not measure the whole original, so preparation falls back to the separate verification pass for that source rather than settle a length on a partial measurement. Every other path decodes an original once
- tests: `TestPreparationDecodesEachOriginalOnce` (real binaries) builds a constant-cadence, a variable-cadence and a two-chunk source, and asserts the prepared measurement equals what `Probe`'s separate pass measures for duration, frame count and cadence verdict — then rebuilds the first copy from the same command WITHOUT its verification output and compares the bytes. The fake chunk runner reports the same two-output shape
- identity held: `TestDeliveredClipIdentity` still passes against T191's baseline (93.6 s)
- no SSOT difference; verify BE (ARCH-26) passes (`go test ./...` with `-p 2`: the full-parallel run is OOM-killed on this box)
