# T048 A purchase refund that can be finished after a crash
> st:done@260908 | ssot:ARCH-10 | base:ARCH@2 | dep:-

## goal
Make `RefundPurchase` resumable so a failure after the provider has refunded finishes the refund instead of reporting the purchase as spent.

## acceptance
- [v] `RefundPurchase` treats an unrefunded purchase whose lot is already voided as a refund in progress: it asks the provider for the payment's current state and, when that state is no longer a live charge, skips straight to marking the row and writing the `refund` event
- [v] the provider is never asked to refund twice: a resumed refund issues no second `Refund` call, and a test with a provider that counts its calls pins exactly one
- [v] a refund whose `MarkPurchaseRefunded` step fails leaves state a retry can finish, and the retry ends with `refunded_at` set, a `refund` ledger row present, and the purchase reported as refunded rather than `PURCHASE_SPENT`
- [v] a genuinely spent purchase still answers `PURCHASE_SPENT`, and a lot that was voided by a refund is told apart from one whose credits were consumed
- [v] the provider refund still happens outside any write transaction (ARCH-10)
- [v] table-driven tests cover: the happy path; a mark failure followed by a retry; a resume whose provider state is still a live charge; a spent purchase; and a purchase already marked refunded
- [v] ARCH-26 passes

## impl notes
- from review/diff-260908 F3
- the defect: `VoidUntouchedLot` → `provider.Refund` → `MarkPurchaseRefunded` are three separate steps. A failure at the third leaves the money refunded, the credits gone, `refunded_at IS NULL` and no `refund` row, which BILL-15 requires; the retry re-enters `VoidUntouchedLot`, now sees `remaining(0) != granted`, and reports `ErrPurchaseSpent` for a purchase that was already refunded
- resume through the provider rather than through a new marker column: `chargeSubscription` and `chargePurchase` already establish the pattern of asking `PaymentByOrder` before acting, and reusing it needs no migration and keeps the payment provider as the single truth about whether money moved
- reuse the existing status vocabulary instead of naming a Toss constant: those two functions already treat `Status == "DONE"` as the only live charge, so a resumed refund reads "anything other than DONE" as money that has already left. `tosspay.Client.Refund` returns only an error, which is why the state has to be re-read rather than inferred from the refund call
- telling a voided lot from a spent one: a refunded lot has `remaining = 0` with `granted` intact, which `LotUntouched`'s `remaining = granted` predicate already fails for both cases — the purchase row's own `refunded_at`, plus the provider's state, are what separate them, so no new lot column is needed

## result
- Changed: `backend/internal/billing/purchase.go` (`RefundPurchase` resumes, +`paymentAlreadyRefunded`, +`finishRefund` shared by a fresh refund and a resumed one) · `billing/purchase_test.go` (+table-driven `TestRefundPurchaseResumesAfterAFailedMark`) · `billing/subscription_test.go` (the fake provider now reports a refunded payment as no longer DONE, the fake store can fail the mark step, and `InsertPurchase` stops storing the derived `Refundable` flag the real store has no column for).
- No migration, no new port method, no proto change: the resume reads the provider through the existing `PaymentByOrder`, and both provider calls stay outside every write transaction (ARCH-10).
- An order the provider has no record of answers `PURCHASE_SPENT` rather than resuming — absence of a payment record is not evidence that money moved, and marking on no evidence would hand back credits nobody refunded. That case is in the table.
- Mutation-checked: with the resume forced back to `ErrPurchaseSpent`, only the mark-failure retry case fails, which is the defect F3 describes.
- Nothing diverged from ARCH-10; no update-ssot owed.
