# T154 Declare an item group's name and admitted count, and refuse a short one before paid work
> st:done@260915 | ssot:CLIP-61 CLIP-102 | base:CLIP@19 | dep:-

## goal
Let a template name its repeated item group and state how many items it admits, and refuse a generation whose groups fall short before any source preparation or AI call.

## acceptance
- [v] `<group>` accepts optional `label`, `min` and `max` in both parsers, and a body carrying none of them parses exactly as it does today
- [v] a bound that is not a non-negative integer, or `min > max`, or `max` above the shared item limit, is a composition problem refused at template save
- [v] the parsed group carries id, label, min and max instead of a bare id, in the Go document and in the TypeScript one
- [v] the approval gate refuses an input set with a group below its minimum and names that group; saving a draft with too few items still succeeds
- [v] the refusal reaches the owner as the group's own name with an actionable message, in ko and en
- [v] Go tests cover the grammar, the bounds and the gate; vitest covers the TypeScript parser and the new message
- [v] verify BE `cd backend && test -z "$(gofmt -l .)" && go vet ./... && go build ./... && go test ./...`
- [v] verify FE `pnpm --filter ./frontend test` · `pnpm lint` · `pnpm lint:fsd` · `pnpm lint:style:probe && pnpm lint:style` · `pnpm build:web`

## impl notes
- Grammar lives in [composition/parse.go:210](backend/internal/clip/composition/parse.go#L210): `attrs(n, "id")` becomes `attrs(n, "id", "label", "min", "max")`, and `d.Groups` changes from `[]string` to a struct carrying the four values ([composition/types.go](backend/internal/clip/composition/types.go)). Defaults when absent: `label` empty, `min` 0, `max` the shared `Limits.Items` — so every template saved before this task keeps its exact current behaviour, which CLIP-61 requires.
- **The frontend parses the body itself** ([entities/clip-template/lib/composition-parse.ts:236](frontend/src/entities/clip-template/lib/composition-parse.ts#L236)), so both parsers must change in the same task. ARCH-3's proto seam does not cover the composition body; a grammar accepted by only one side means the owner's form refuses a template the server took, or the reverse.
- The gate is already in the right place: `ValidateCompositionInputs(d, in, l, required)` ([composition_state.go:193](backend/internal/clip/composition_state.go#L193)) is called with `required=true` only from `GenerationComposition` ([composition_state.go:304](backend/internal/clip/composition_state.go#L304)), reached through `RequiredAnswers` from the quote gate ([quotes.go:195](backend/internal/clip/quotes.go#L195)). Put the minimum check in that `required` branch and nowhere else — every other caller passes `false`, which is what keeps a half-filled draft saveable while generation refuses it.
- Report it through the existing channel rather than a new failure reason: return `&composition.Problem{ElementID: <the group's label, or its id when undeclared>, Line: <the group's span line>, Reason: "items_required"}`. `toConnectError` already maps a `*composition.Problem` to `CLIP_COMPOSITION_INVALID` with `element_id`/`line`/`reason`, and the owner's screen already renders that. Add `items_required` (and the bounds problem's reason) to the TypeScript reason union and to the `composition.problem` catalogs in both `ko/clips.ts` and `en/clips.ts` — an unlisted reason degrades to the generic message (LANG-24).
- Do not add a per-group `required` attribute. CLIP-61 gives the group a count, and a required field inside an item keeps meaning exactly what it means now: required once that item exists.
