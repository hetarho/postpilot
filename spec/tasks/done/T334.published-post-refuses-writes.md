# T334 A published post refuses every write except replacing or clearing its URL and deleting it
> st:done@260924 | ssot:POST-74 GEN-56 MODEL-31 MODEL-37 ARCH-7 ARCH-24 | base:POST@11 GEN@10 MODEL@16 ARCH@9 | dep:T329

## goal
- R7's and R10's lock holds on the server: on a published post every content, draft, option, observation, media, generation, revision, winner and finalize write is refused before anything changes, and a SQL check backs each refusal.

## acceptance
- [v] On a published post each of these answers FailedPrecondition `POST_PUBLISHED_LOCKED` and leaves the post row, its `updated_at`, its answers, images, videos, uploads and storage objects exactly as they were: SavePostDraft (title/memo, voice, template, answers, target language), a changed SavePostContent, SavePostGenerationOptions, FinalizePost, CreateUpload, ConfirmUpload (photo and video), DeleteImage, DeleteVideo.
- [v] An identical SavePostContent at the current revision on a published post is still a no-op answer, not a refusal (POST-15).
- [v] SavePostPublishedUrl (replace and clear) and DeletePost still work on a published post; DeletePost is still refused with `POST_BUSY` while any job is active (POST-29).
- [v] StartGeneration and StartRevision on a published post answer `POST_PUBLISHED_LOCKED`; no rule is appended, no template, guideline or memory is frozen, no job or credit hold exists and no provider is called (GEN-56).
- [v] An editor-origin write comparison start on a published post answers `POST_PUBLISHED_LOCKED` with no experiment row, snapshot or job; a lab-origin write or observe comparison on it starts and runs, and writes nothing to it (MODEL-31).
- [v] Applying a winner to a published post answers `POST_PUBLISHED_LOCKED` with nothing recorded, whether it is a lab application or an editor verdict (DecideWrite, or Choose of a single survivor), and so does an editor-origin Retry. A lab application on a finalized post stays `EXPERIMENT_POST_FINALIZED`, and only draft and review accept one (MODEL-37).
- [v] A write that passes the service check but loses the race to a publish is refused by its SQL check and answers `POST_PUBLISHED_LOCKED`.
- [v] `payload_golden_test`, the experiment snapshot hashes and every existing prompt golden stay byte-identical.
- [v] Tests: `internal/post/lifecycle_test.go` (`TestPublishedPostRefusesEveryWriteBeforeChangingAnything` with one subtest per locked operation, `TestIdenticalContentSaveOnAPublishedPostIsStillANoOp`, `TestDeletePostStillRemovesAPublishedPost`, `TestAWriteThatLosesTheRaceToAPublishIsRefusedAsLocked`); `internal/post/store/published_lock_store_test.go` `TestEveryGuardedStatementRefusesAPublishedPost` (one subtest per statement); `internal/generation/generation_test.go` (`TestStartAndStartRevisionRefuseAPublishedPostBeforeAnything`, `TestWriteSnapshotRefusesAPublishedPostOnlyForTheEditor`, `TestApplyWriteWinnerRefusesAPublishedPost`); a `POST_PUBLISHED_LOCKED` row in `internal/generation/rpc/handler_test.go` `TestGenerationErrorsHaveStableReasonsCodesAndAllowlistedParams` and in `internal/experiment/rpc/handler_test.go` `TestExperimentErrorsHaveStableReasonsCodesAndAllowlistedParams`; `internal/experiment/origin_test.go` (`TestLabApplicationFollowsThePostStatus` + published, the editor subtest below, `TestEditorComparisonIsRefusedOnAPublishedPost`); `cmd/api/published_post_test.go` (`TestExperimentPostStatusMirrorsThePostContext`, `TestPublishedRefusalsCrossTheAdapters`, `TestGenerationPostsCarriesThePublishedFlag`).
- [v] Verify: `cd backend && test -z "$(gofmt -l .)" && go vet ./... && go build ./... && go test -timeout 30m ./...`
- [v] Verify: `pnpm gen:sql && git diff --exit-code -- backend`

## impl notes
- T322 left `post.ErrPostPublished` → FailedPrecondition `POST_PUBLISHED_LOCKED` in post/rpc `toConnectError`. T329 left `StatusPublished` and the fixture path to a published post (SetGeneratedContent → Finalize → SavePublishedURL). No proto or migration changes here.
- `service.go` gains `lockedOrGone(ctx, userID, slug string, otherwise error) error`: re-read with `ownedPost`; its error wins, a published post is `ErrPostPublished`, anything else is `otherwise`.
- Its `otherwise` is each call's error today: UpdateDraft, AssignTemplate (whose bool is now read), SaveGenerationOptions and SetObservations → `ErrNotFound`; SaveContent and Finalize → `ErrStaleContentRevision`. `reassignVoice`'s and `SetGeneratedContent`'s existing zero-row re-reads gain the published check ahead of their `ErrNotFound`.
- Order in SaveDraft: `ownedPost` → refuse published → reassign, assign, answers, UpdateDraft. The create path cannot meet a published post.
- Order in SaveContent: `ownedPost` → stale-revision check → identical no-op → refuse published → validate → write. The no-op comes first so POST-15 holds.
- Order in SaveGenerationOptions, Finalize, SetGeneratedContent and SetObservations: `ownedPost` → refuse published → the method's existing equality or idempotence check → write.
- Order in CreateUpload and ConfirmUpload: `ownedPost` (of `upload.PostSlug` for ConfirmUpload) → refuse published, before reserve, presign, HEAD or `dropRejectedUpload`. The upload row and its object are left for the sweep, so a retry after clearing the URL can still confirm. The `alreadyConfirmed` path writes nothing and stays open.
- Order in DeleteImage and DeleteVideo: `ownedPost` → refuse published, before `blobs.Delete`, so no object is touched.
- DeletePost and SavePublishedURL are untouched (R7). Reads are untouched: Get, AttachedImages, List, LearningSnapshot, PostStatus.
- SQL predicate `AND status <> 'published'` (queries stay ASCII) goes on UpdatePostDraft, UpdatePostObservations, SavePostContent, SavePostGenerationOptions, FinalizePost, ReassignPostVoice and AssignPostTemplate.
- On UpdateGeneratedContent the predicate is ANDed before the existing parenthesized idempotence group, because that group's `status <> 'review'` alone would let a published row through.
- UpdatePostObservations is beyond the plan's list. POST-74 locks every write, and its own reason warns that a named list leaves the unnamed ones open. Every product path to it on a published post is already refused upstream (Start, the editor snapshot, observe apply, image delete), so here it is a backstop.
- `images.sql` DeleteImage and `videos.sql` DeleteVideo become `:execrows` with `AND post_slug IN (SELECT slug FROM posts WHERE status <> 'published')`. The ports become `DeleteImage(ctx, id string) (bool, error)` and `DeleteVideo(ctx, id string) (bool, error)`.
- In the service, a false from either delete goes through `lockedOrGone(..., nil)`: a row already gone stays the idempotent success it is today.
- Inserts use a guard in the same write transaction rather than an INSERT…SELECT. A statement selecting from posts inserts zero rows for an unknown post too, which would drop the composite-FK refusal `TestImageRequiresItsPost` pins and make zero rows ambiguous. The single serialized writer makes guard plus insert atomic.
- New `posts.sql` guard `PostIsPublished :one` is `SELECT EXISTS (SELECT 1 FROM posts WHERE slug = ? AND status = 'published')`.
- `store.go` runs PostIsPublished first inside the transaction of CreateUpload (today a lone statement, now wrapped in `writer.BeginTx`), ConfirmUpload, ConfirmVideoUpload and UpsertTemplateAnswers. A true result rolls back and returns `post.ErrPostPublished`.
- On that error the service calls `lockedOrGone(..., ErrNotFound)`.
- The test-only standalone `Store.CreateImage` and `Store.CreateVideo` keep their plain INSERT; no service path calls them.
- `post_template_answers.sql`'s header comment gains one line: the published guard runs in the store's transaction, not in the upsert.
- `store/published_lock_store_test.go` seeds a published row (UpdateGeneratedContent → Finalize → PublishPost, with an image, a video and an upload confirmed or created before the publish). Each guarded store method then answers false, zero rows or `post.ErrPostPublished`, and the row and child tables read back unchanged.
- `fake_test.go`: every guarded fake write refuses a `StatusPublished` row the way its statement does, and the fake delete methods return the bool.
- `fakeStore` gains `beforeGuardedWrite func(slug string)`, called first in each guarded fake write, beside `slugTaken`. The race test uses it to flip the stored status to published after the service check, for UpdateDraft (a row update) and CreateUpload (a guarded insert).

- The lifecycle refusal test snapshots `store.posts[slug]`, `store.answers`, `store.images`, `store.videos`, `store.uploads` and `blobs.deleted`, runs one operation, and asserts `errors.Is(err, ErrPostPublished)` with all six `reflect.DeepEqual` to before.

- `types.go` PostInput gains `Published bool` with the tag `json:"-"`, because an experiment snapshot marshals PostInput by Go field name and any new key would re-hash every stored snapshot. If the TagCount comment still says "the one struct tag in this file", fix it.
- `service.go` `Start` and `StartRevision` return ErrPostPublished immediately after `s.posts.AttachedImages`, before every other check. In StartRevision that is ahead of `rules.AppendRule`, which writes to the voice.
- `experiment_surface.go` `SnapshotWriteInput` returns ErrPostPublished right after its read when `post.Published && !snapshotOnly`. The lab's snapshot-only comparison reads a published post freely (MODEL-31, T319).
