## goal
ListExperiments reads summaries in three queries without snapshots or outputs, GetExperiment measures a voice comparison against one loaded analysis, candidates call providers at most two at a time, and a comparison's hold counts every observe call a candidate really makes.

## acceptance
- [v] `experiment/store` List: one experiments query selecting every column except `input_snapshot`, one batched candidates query and one batched badges query for all listed ids (`json_each`), candidate `output` not decoded or returned in list results; the history page, the posts page and every other list consumer keep working (they read status, labels and ids only — grep the FE to confirm before dropping a field)
- [v] `GetExperiment` keeps returning full candidates; its voice-comparison detail loads the voice and its current analysis once per request and measures every succeeded candidate against it (one voice read, one analysis decode)
- [v] `runCandidates` runs at most `config.ExperimentCandidateConcurrency` (2) candidates at once; the constant's comment says it is the concurrency bound, not the pair width
- [v] the comparison hold (`cmd/api/adapters_experiment.go`) counts each observe candidate and the shared preparation observe as the number of observe calls the snapshot's photos and videos require — the same batch arithmetic generation's `observeCalls` uses — instead of 1
- [v] tests: store list issues 3 queries for N experiments and carries no output; detail compares K candidates with one analysis load; a 5-candidate run never has more than 2 in flight; a 9-photo + 1-video observe comparison holds ⌈9/batch⌉+1 calls per candidate
- [v] behaviour unchanged otherwise: ARCH-26 green; FE suite green
