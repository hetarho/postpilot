## goal
Browser analysis copies carry AAC mono audio at 96 kbps under profile clip-browser-analysis-v2, so a source with sound prepares on Windows Chrome/Edge as on macOS.

## acceptance
- [v] The server returns profile clip-browser-analysis-v2 with audio bitrate 96000 for browser preparations, while native server copies keep 64 kbps; BrowserAnalysisQualified stays false.
- [v] The client encodes analysis audio at 96 kbps and refuses any returned profile whose version or audio bitrate differs; readiness JSON names the v2 profile with qualified/enabled false and every missing gate retained.
- [v] Go test in backend/internal/clip pins the browser profile version/audio bitrate apart from DefaultMediaConfig's native AudioBitrate, and an rpc-level assertion pins the ClipAnalysisProfile values; affected clip, clip/app, clip/store, clip/worker, clip/rpc and diagnostic/analysisquality packages pass.
- [v] FE tests updated and passing: entities/clip-project/api/analysis-preparation.test.ts (profile 96_000/v2, refusal of 64_000), features/prepare-clip-browser/model/prepare.test.ts, shared/lib/media/analysis-original.test.ts, pages/clip/ui/ClipGeneration.test.tsx, plus FE type/lint/format checks.
- [v] Installed Windows Chrome runs the production analysis encoder on authorized owner originals with sound and every copy passes the production Go verifier (TestLocalVerifierExistingAuthorizedSyntheticCopy); measured device, versions and timings are recorded in a docs/qa evidence file without footage, signed links or hashes of private prose.

## impl notes
- Add `BrowserAnalysisAudioBitrate = 96000` beside `BrowserAnalysisProfileVersion` in backend/internal/clip/analysis_preparation.go and bump the version to `clip-browser-analysis-v2` (CLIP-93: a changed copy profile must not reuse v1 identity). Keep `DefaultMediaConfig` AudioBitrate 64000 for native chunks; the rpc response's `AudioBitrate` reads the new constant, not `cfg.AudioBitrate`.
- FE: `ANALYSIS_PREPARATION_LIMITS.audioBitrate` becomes 96_000 with a comment naming the Windows Media Foundation AAC set (96/128/160/192 kbps). entities/clip-project cannot import a feature, so its profile check uses its own model constant beside the v2 version string rather than a literal in the api file.
- No proto, migration or stored-format change: the profile already carries audio_bitrate. Expired v1 preparations simply fail the version check; do not add a migration.
- The analysis encoder already probes `canEncodeAudio('aac', …)` with the profile bitrate, so no device branch is needed; a platform refusing 96 kbps keeps the existing CLIP_ANALYSIS_ENCODER_UNSUPPORTED refusal (CLIP-204: never a per-device downgrade).
- The Windows evidence reuses the private WSL-served harness around frontend/src/test/browser-media/analysis-entry.ts driven by Windows node.exe + playwright-core; private originals stay in the session scratch directory. This is technical evidence only: T603 semantic qualification, readiness activation and distribution remain closed.
