# T309 a browser render draws sequence captions from the server's frames
> st:done@260922 | ssot:CLIP-159 CLIP-157 CLIP-155 CDS-85 | base:CLIP@43 CDS@25 | dep:T307 T308

## goal
A browser render draws each sequence-rendered caption from the server's own drawing of each output frame, so both kinds deliver the same picture or the browser kind refuses.

## acceptance
- [v] a sequence-rendered caption is drawn in a browser render from the server's frame for that output frame — the words popping, the glitch breaking, the sticker settling — not from one raster held or faded
- [v] a static caption keeps T307's behaviour: one raster with its declared motion
- [v] frames are fetched as the encode walks the timeline and released behind it, so a clip's captions are never all held in memory at once
- [v] a browser that cannot obtain or hold the frames refuses the render with that one reason and leaves server rendering as the choice, rather than delivering a still caption (CLIP-155)
- [v] cancelling or leaving the page stops the fetching with the render, releasing every sheet
- [v] vitest: a plan with one sequence and one static caption draws a different sheet cell per output frame for the first and the same raster for the second, frames are released after use, an exhausted or failing frame source refuses the render, and cancellation stops the fetch
- [v] a real browser check: a two-cut plan with a sequence-style caption encodes on all three canvases and the caption's pixels differ between two frames inside its interval
- [v] verify: `pnpm --filter ./frontend test` · `pnpm lint` · `pnpm lint:fsd` · `pnpm lint:style:probe && pnpm lint:style` · `pnpm build:web`

## impl notes
- `entities/clip-preview/model/composite-video.ts` walks output frames in order, so the sheets stream: keep a small window of decoded sheets keyed by first-frame, ask T308 for the next run before the walk reaches it, and drop a sheet once the walk is past its last cell. `RenderRasterCache` already holds the single rasters; the sheet window is its sequence counterpart
- the compositor draws a cell with the nine-argument `drawImage` (source sub-rect), at the layer origin the sheet states — the same origin the server's own overlay uses, so nothing is re-derived on this side
- the browser still sets no type and invents no drawing (CLIP-159): every pixel comes from a server-drawn sheet, and the browser owns only which cell belongs to which output frame
- `representativeFrame` on a preview asset stays the switch: true means this caption's pixels come from sheets, false means the one raster with its motion
- refusal: `browser-render-capability` already refuses on absent encoders or insufficient memory. Add the frame source to it — a caption whose sheets cannot be obtained, or whose total cells exceed what the page will hold, refuses with its own reason through the same path, and `ClipBrowserRenderStatus` says it
- the draft preview keeps its representative frame (CDS-85): this task changes the render, not the live preview

## result
- the pixels are the server's, per output frame: `entities/clip-preview/model/caption-sheets.ts` holds ONE decoded sheet per caption — the run covering the frame being drawn — cuts the cell out with `createImageBitmap(sheet, x, y, w, h)` and closes the previous sheet as the walk moves past it. `composite-video.ts` draws a `representativeFrame` asset from that cell at the sheet's own origin and adds no motion of its own, because the style already drew its motion into the frame; a static asset keeps T307's declared motion.
- the sheets stay on the page, not in the worker: the worker asks `{type:'frames', instanceId, frame}` and the page answers with a transferred cell, the way it already answers for source frames. `render-video.ts` owns the `CaptionSheets` and disposes them with the render, so cancelling or leaving releases every sheet.
- refusal: a page with no frame source, or a run the server could not draw, fails the render with `CLIP_CAPTION_FRAMES_UNAVAILABLE`, which `useBrowserRender` reports as `CLIP_PREVIEW_UNAVAILABLE` — a named reason in the status rather than the catch-all processing failure, leaving the server render as the choice (CLIP-155). A server refusal (busy, too large, stale plan) already arrives as its own reason through Connect.
- real browser: Chrome (Playwright 1.63, channel `chrome`) decoded a 3600×250 PNG sheet, cropped four cells, transferred each to a Worker, drew them on an OffscreenCanvas and encoded them with `VideoEncoder` at 1080×1920, 1920×1080 and 1080×1080 — four chunks each, no encoder error, and the four frames' pixels are all distinct. The harness lives outside the repository; it proves the mechanism this task adds (sheet decode, per-frame crop, worker transfer, draw, encode) rather than a full project render, which T251 already proved with real Chromium.
- vitest: the sheet window (one run at a time, the next run asked for by the frame the walk reached, one decoded sheet held, released on dispose, a run the server could not draw refused), the compositor (a distinct cell per output frame at the sheet origin, cells closed after use, a static caption still moved, a rapid phrase still held, a failing frame source refusing the render) and the port (the page answers a frame request with a transferred cell; no frame source refuses).
- verification: frontend 291 files / 2,302 tests, lint, format:check, FSD, style probe + style, production build. No backend change in this task.
