# T318 The A/B pair saves as it is chosen
> st:done@260922 | ssot:MODEL-23 MODEL-25 MODEL-65 ARCH-13 ARCH-20 ARCH-24 THEME-23 | base:MODEL@15 ARCH@7 THEME@17 | dep:-

## goal
- Changing either candidate writes the pair the moment it names two distinct registered models, so the comparison always starts against the pair the screen is showing.

## acceptance
- [v] Choosing a candidate on a stage that already has a complete pair writes it at once, with no separate action; `A/B 조합 저장` and its success line are gone from the form.
- [v] A change that leaves the pair incomplete (one side still 모델을 선택하세요) writes nothing and leaves the stored pair as it was.
- [v] Choosing the model the other side already holds writes nothing, keeps the existing `두 모델은 달라야 해요` message on the field, and leaves the stored pair as it was.
- [v] A refused write is reported under the candidate that was just changed, through the same `ModelSelect` error slot the active selection uses; both candidate fields are disabled while a write is in flight.
- [v] Starting a comparison immediately after a change uses the change: the existing save-pending guard still blocks the start until the write resolves.
- [v] Tests: the pair form (writes on a completing change, silent on an incomplete or identical one, failure placement, both fields disabled while saving), and the comparison page's existing start assertions still pass with no save press.

## impl notes
- `features/configure-model-pair/ui/ModelPairForm.tsx`: drop the `Button`, the success line and the `savePair.failure` block. Keep the local `a`/`b` state — the fields still need their own value while a write is out — and move the write into a `commit(nextA, nextB)` the two `onChange` handlers call. Commit only when both resolve to a model in `suitable` and their keys differ; otherwise set state and return.
- Remember which side was changed last (`useState<'a' | 'b' | ''>`) and pass `error={savePair.failure}` to that field alone, so the refusal sits under the control that caused it rather than under both. Pass `saving={savePair.isPending}` to both, because the pair is written as one row and neither half may move while it is in flight (MODEL-23).
- The remount key in `ModelPairForm` stays: a pair arriving from the server still reseeds the fields. `useSaveComparisonPair` already writes the new pair into the cache synchronously, so the reseed after a successful commit is a no-op rather than a flash of the previous value.
- Copy: remove `savePair` and `pair.saved` from `features/configure-model-pair/config/i18n.ts` in both locales; keep `pair.saveFailed` (the normalized failure still renders through it) and `differentModels`.
- `pages/ai-models/ui/ModelComparisonPage.test.tsx` and any editor test that presses `A/B 조합 저장` must stop pressing it; the pair fixture already arrives saved in most of them.
- Nothing on the server changes: `SaveComparisonPair` is already one atomic write of both slots and already refuses an identical or unregistered pair (MODEL-25).

## result
- `ModelPairForm` writes through one `commit(side, key)` the two selects call. It writes only when both sides resolve to a model in the stage's list and their keys differ, so an incomplete or identical choice leaves the stored pair as it was and the screen says why through the existing `두 모델은 달라야 해요` message.
- The refusal is passed to the candidate that was just changed, through the same `ModelSelect` error slot the active selection uses; both fields take `saving` while the write is out, because the pair is one row (MODEL-23).
- `A/B 조합 저장`, its success line and the form's own failure block are gone, along with the `savePair` and `pair.saved` strings in both locales. `pair.saveFailed` stays: the normalized refusal still renders through it.
- No test pressed the button by name outside this feature's own; the one that did now asserts the write happens on the completing change and that the refusal lands on candidate B alone.
- A refusal is forgotten as soon as a later change writes nothing: the mutation's failure outlives its mutation, so keeping which field it belonged to is what decides whether it is still on screen.
- `test/providers.ts` gained `onSavePair`, because a form that writes as it is chosen is tested by what it wrote and when rather than by what it rendered.
- Validation: the pair form (8 tests), the model, generation and editor suites (173 tests), frontend typecheck, lint with format:check, the FSD boundary lint and the production build all pass. The whole-suite clip, plans, voice and editor failures reproduce only under load; each passes on its own.  reports two escapes in an untracked `RailNav.tsx` another session is writing, which this task does not touch.
- Nothing on the server changed. The existing save-pending guard still holds a comparison start until the write resolves, so a start right after a change uses the change.
