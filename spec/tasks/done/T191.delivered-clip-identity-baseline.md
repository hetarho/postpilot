# T191 A delivered-clip identity baseline the speed work must hold
> st:done@260916 | ssot:CLIP-125 CLIP-97 | base:CLIP@29 ARCH@2 | dep:-

## goal
Pin the delivered clip of a fixed plan so any later change made for speed can be shown to deliver the identical file.

## acceptance
- [v] rendering one fixed plan twice from the same inputs produces the identical delivered file; if it does not, the source of the difference is removed before a baseline is recorded
- [v] a recorded baseline covers a plan exercising hard cuts, a 200 ms fade, an overlay element and an audio track, in one ratio
- [v] the check fails with a readable difference — which frame and which property — rather than only an unequal digest
- [v] the existing filter-graph goldens continue to cover the graphs themselves, so a graph change is visible without running a render
- [v] tests: the identity regression, gated like the other real-binary tests so ordinary `go test` stays green without Docker
- [v] verify BE (ARCH-26) passes

## impl notes
- the production image's ffmpeg carries no `framemd5` or `md5` muxer — its muxers are image2, mov, mp4, null and wav, and its only protocols are file and pipe — so identity is a hash of the delivered MP4, with PNG frames through the image2 muxer for the readable difference
- the delivered encode already strips metadata (`-map_metadata -1`, `-map_chapters -1`) and runs libx264 at a fixed thread count, which is what makes a byte hash a fair check; confirm the repeat-render equality first, because recording a baseline over a nondeterministic encode would pin noise
- follow the existing gate convention: the real-binary tests in this package skip on an env var (`CLIP_MEDIA_SMOKE`, and the per-file gates beside it) and run inside Docker
- the goldens live in `media/testdata/*.filter` through the `golden` helper in `media/render_test.go`; keep them as the cheap first line of defence
- this task ships no behaviour change — it is the acceptance instrument T192, T193, T194 and T195 each depend on

## result
- `backend/internal/clip/media/identity_smoke_test.go` (new): `TestDeliveredClipIdentity` renders the release QA's first plan twice — three cuts, the second fading in over 200 ms and the others hard, the authored overlay elements above them, the owner's source sound on, vertical — and compares the delivered files, then compares the first against `deliveredIdentityBaseline`
- nothing had to be removed to make the render repeatable: the two renders were byte-identical on the first attempt, so the baseline pins today's clip rather than a change made to reach it. The delivery encode's existing `-map_metadata -1` / fixed thread count is what makes that true; a standalone two-encode check in the image confirmed the container carries no timestamp either
- the fingerprint is the delivered file's SHA-256, the container/stream properties a player reads, and one PNG frame per second of output through the image2 muxer (the image has no framemd5 muxer, and its filter set has `fps` but not `select`, so a second is the finest position a mismatch can name)
- a mismatch is reported as `property <name>: want X got Y` and `frame at Ns: want <digest> got <digest>`, with bytes that move where neither does still reported; `TestIdentityMismatchNamesTheFrameAndTheProperty` pins that reporting and runs in ordinary `go test`
- `backend/Dockerfile`: new `identity-smoke` stage (ENTRYPOINT, like `release-smoke`) so the check is run on purpose — `docker build -f backend/Dockerfile --target identity-smoke -t postpilot-identity . && docker run --rm postpilot-identity`. It is deliberately NOT a production-build RUN step: it renders twice and took 112 s here
- recorded digest `ba5a3fb9…`, 474 video frames, 15.800 s, 1080x1920 yuv420p High, aac 48 kHz stereo. Re-record only for a deliberate change to the picture; T192–T195 must leave it untouched
- no production code changed, so no SSOT difference; the filter-graph goldens are untouched and still run without a render
- verify BE (ARCH-26) passes (`go test ./...` with `-p 2`: the full-parallel run is OOM-killed on this box)
