# T291 extract_memory is a job that proposes candidates and stores none
> st:done@260920 | ssot:MEM-13 MEM-14 MEM-15 QUOTA-13 ARCH-11 ARCH-24 | base:MEM@1 QUOTA@13 | dep:T289

## goal
Turn a finished post into memory candidates through one durable credit-gated job that writes no memory.

## acceptance
- [v] job kind `extract_memory` addressed by the post dimension, guarded so it is refused while other work is active on that post
- [v] it passes the shared enqueue credit gate like every other LLM job; an insufficient balance answers `resource_exhausted` / `INSUFFICIENT_CREDITS` and leaves no job row
- [v] exactly one provider call against the account's current enabled analyze-stage selection, attaching the embedded JSON schema when the resolved model declares `structured_output` and falling back to the prompt alone otherwise
- [v] each candidate carries text, a proposed kind from the five and proposed tags, all inside the bounds a create enforces
- [v] nothing is written to `memories`, `memory_tags` or `memory_sources` by this job, and the post's content, status, revision and baseline are untouched on success and on every failure
- [v] `GetMemoryExtraction(job_id)` answers the candidates for a done job the caller owns and refuses anything else
- [v] approving a candidate is the ordinary `CreateMemory`; unchecked candidates are discarded with the job and never reappear
- [v] tests: the credit refusal before the job row, the active-work guard, a stubbed provider driven through completion, the ownership refusal, and an assertion that a completed extraction left the memory tables empty
- [v] ARCH-26 and ARCH-28 pass

## impl notes
- the analyze stage is the model class for reading finished prose; `seed_voice` and `analyze_voice` already select it, so no new per-account setting appears
- the candidates ride the job row's kind-specific payload (GEN-30) and live nowhere else. MEM-15 forbids a durable review queue, and a job row is transient work state nothing re-surfaces — state this in the code comment so it is not turned into a table later
- the extraction prompt is a code constant beside the other prompt constants: it receives the post's canonical content and its memo, and asks for atomic one-sentence facts about the author's world, each with one of the five kinds — never opinions about the writing, never a summary of the post
- schema file `internal/memory/schemas/memory_candidates.schema.json`, `//go:embed`-ed, following VOICE-27's attach-or-fall-back rule
- the schema must contain NO integer enum: a numeric enum in a response schema makes Gemini answer `{}` for the whole object, measured on this codebase. Kinds are string values
- the job freezes the post slug and the content it read at enqueue, so an edit during the call cannot change what was extracted

## result
- the job: `job.KindExtractMemory` addressed by the post dimension through the existing `postVoiceWork` helper, so the ordinary one-job-per-post guard applies unchanged; registered in `cmd/api/jobs.go` and enqueued through `memoryExtractions`, which adds no gate of its own — the shared enqueue seam is the credit gate (QUOTA-13).
- the queue gained the two methods a result-on-the-row kind needs: `Queue.SaveResult` (writes a RUNNING job's payload, guarded by status in SQL) and `Queue.Result` (owner-scoped read by id alone), plus `SaveJobPayload` in the job store. `Snapshot` was left as it is — its callers already know the subject.
- `internal/memory/extraction.go`: `ExtractionPrompt` (a code constant asking for atomic one-sentence facts about the author's world, naming the five kinds, forbidding a summary or an opinion about the writing), one provider call on the analyze stage with the embedded schema attached only when the model declares `structured_output`, and candidate parsing that applies the SAME bounds a create enforces (over-long text, unknown kind and empty text dropped; an over-tagged candidate keeps its fact and loses its tags; identical texts collapse). The file's head states why the candidates live on the job row and must not become a table.
- `schemas/memory_candidates.schema.json` + `schemas.go`, with the kind as a STRING enum and a test that walks every `enum` in the schema and fails on a non-string value — the Gemini `{}` failure this codebase already paid for once.
- `StartExtraction` resolves the account's enabled analyze selection (refusing with `MEMORY_ANALYZE_MODEL_REQUIRED` rather than substituting one), reads the post once and freezes it onto the job row; `GetMemoryExtraction` answers only a finished, owned `extract_memory` job — an unfinished one is `MEMORY_EXTRACTION_NOT_READY`, a foreign one is `MEMORY_NOT_FOUND`, and the two are never confused with "this post yielded nothing".
- ports and adapters: `Models`, `Posts` and `ExtractionJobs` declared in `internal/memory/ports.go`, implemented in the new `cmd/api/adapters_memory.go`. `memoryModels` takes the METERED registry, so an extraction's call is on the ledger; `memoryPosts` flattens the canonical blocks to prose in the adapter (IMAGE/VIDEO contribute their caption only), so the memory context never learns what a block is.
