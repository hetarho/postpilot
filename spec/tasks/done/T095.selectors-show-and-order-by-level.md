# T095 User selectors show the level and order 가성비 → 최고
> st:done@260911 | ssot:MODEL-44 MODEL-57 MODEL-58 MODEL-27 LANG-7 | base:MODEL@9 LANG@3 ARCH@2 | dep:T092

## goal
Every list `ListModels` feeds — the per-stage selectors and the A/B pair fields — names each model's level for that stage and orders levelled models 가성비 → 최고 with unlevelled ones last.

## acceptance
- [v] `entities/model-catalog/model/types.ts` gains `LevelName` (`'value' | 'balanced' | 'premium' | 'top'`) and `LEVELS` in that order; `CatalogModel.levels: Partial<Record<StageName, LevelName>>`; `toCatalogModel` fills it from `ModelInfo.levels` through `stageFromProto`, dropping unknown stages and unknown level strings
- [v] a pure `orderModelsForStage(models, stage)` in the slice's `model` segment: ascending `LEVELS` rank of `levels[stage]`, models without a level for that stage after every levelled one, and the server's order preserved inside a rank (stable)
- [v] `useStageSelection(stage).models` and the `suitable` list `CandidatePairSelect` builds are both ordered through that helper — no component sorts on its own
- [v] an option's label leads with the level's copy when the model has one for that stage — `가성비 · <label> …badges …reason` — and is unchanged when it has none; the closed trigger therefore reads the level first
- [v] ko/en `models` namespace gains `level: { value, balanced, premium, top }` — ko 가성비 · 밸런스 · 고급 · 최고, en Value · Balanced · Premium · Top — and the locale parity test passes; `combos.name.*` is not reused
- [v] the level changes nothing else: `disabled`, affordability and the vanished/unsuitable entries render exactly as before (existing `StageModelSelect.test.tsx` and `ModelPairForm.test.tsx` pass with only ordering/label expectations added)
- [v] vitest: `orderModelsForStage` (mixed levels, unlevelled last, stability, per-stage independence — one model `value` for observe and unset for write); `StageModelSelect` rendering options in level order with level-led labels; `CandidatePairSelect` doing the same for both fields
- [v] the `frontend/src/test` fake that serves `ListModels` accepts per-stage levels so the page tests drive the real shape
- [v] `pnpm --filter ./frontend test` · `pnpm lint` · `pnpm lint:fsd` · `pnpm lint:style:probe && pnpm lint:style` · `pnpm build:web` (ARCH-25)

## impl notes
- ordering lives in the entity's pure `model` segment and is applied where the stage list is produced (`useStageSelection`) and where the pair fields derive `suitable`, because both surfaces must agree and neither should own a sort (ARCH-14/15; `entities/*/model` imports no react, ARCH-18)
- "badge" from MODEL-44 is rendered as the leading token of the option string: `ListboxOption.label` is `string`, and widening the primitive to a node is out of this task's scope. The level goes FIRST, ahead of the model label, because the closed trigger truncates at ~284px on a 360px phone and a `provider/model` path alone fills it — a trailing token would be cut off
- a level is per stage, not per model (MODEL-57): the pair form and the selector both know their stage, so they read `levels[stage]`; nothing aggregates across stages
- unlevelled models sort after levelled ones and show no level text (MODEL-58) — they are not disabled and carry no warning here; the operator sees the gap in 모델 관리 (T094)
- the new i18n keys are owned by this task; T094 depends on it and reuses `models.level.*` for the admin Listbox and the document diff

## result
- files: `entities/model-catalog/model/level.ts` + `level.test.ts` (new: `LevelName` `LEVELS` `isLevelName` `levelOf` `orderModelsForStage` `levelPrefix`) · `model/types.ts` (`CatalogModel.levels`, `filterForStage` now orders) · `api/catalog-mappers.ts` · `index.ts` · `features/select-model/ui/StageModelSelect.tsx` + test · `features/configure-model-pair/ui/CandidatePairSelect.tsx` + new test · `ModelPairForm.tsx` + test · ko/en `models.ts` (`level.*`) · `test/providers.ts` (the fake serves per-stage levels)
- ordering composes INTO `filterForStage` rather than being applied at each call site. There are three call sites, not the two the task named — `useStageSelection`, `CandidatePairSelect` and `ModelPairForm` — and a fourth forgetting to sort would read as a catalog bug. `orderModelsForStage` stays exported and separately tested, so the acceptance's "no component sorts on its own" holds by construction
- `ModelPairForm` covers three fields (active + both candidates), not the two the task anticipated; all three are graded and ordered alike, and `ModelSelect` gained a `stage` prop to know which grade to show
- `levelPrefix` lives in the entity because two FEATURES need it and same-layer cross-import is forbidden (ARCH-13). It uses `i18next.t` directly, which ARCH-18 permits — that rule bars react/react-dom, and `StageModelSelect` already used i18next this way
- the grade LEADS the option label. `ListboxOption.label` is a string and the closed trigger truncates (~284px at 360px, which a `provider/model` path alone fills), so a trailing grade is the half nobody reads; widening the primitive to a node was out of scope
- `CandidatePairSelect` had no test file — added. Note its placeholder is a FIELD PROP, not a listed option, unlike `ModelPairForm`'s; the two tests differ by exactly that
- unknown stage AND unknown level strings are dropped at the mapper, so a newer server cannot make a picker render a word the copy has no entry for
- FE gate: 187 files / 1486 tests, lint, fsd, style and build all pass (`pnpm format` was needed for two files)
- no deviation from MODEL@9 or LANG@3; LANG-7's `models` namespace already existed, so no LANG rev is owed
