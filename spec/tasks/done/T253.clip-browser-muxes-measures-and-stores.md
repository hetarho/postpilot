# T253 the browser muxes its output, measures it and stores it before it is shown
> st:done@260918 | ssot:CLIP-158 CLIP-157 CLIP-154 CLIP-153 CLIP-27 CLIP-76 | base:CLIP@38 | dep:T252 T243

## goal
The browser's two tracks become one MP4, the browser measures it, the file reaches the project's private storage, and only then is the render successful.

## acceptance
- [v] the encoded tracks are muxed into an MP4 accepted by the same short-form contract a server render satisfies
- [v] the browser measures its own output's resolution, frame rate, codec, loudness and duration and reports that verdict with its measurements
- [v] the file is stored in the project's private storage as a browser-to-storage transfer, never through the RPC body
- [v] the render becomes successful only once the file is stored; a store that does not finish leaves the render unsuccessful with the previous result standing
- [v] ② plays and offers the stored file, never the local one, and the local copy is released once stored
- [v] a failing verdict is recorded as a notice rather than a silently accepted file
- [v] vitest: a completed render stores before it reports; a failed store leaves the project's previous result and reports the render unsuccessful; the reported measurements come from the produced file
- [v] go test: the recorded result carries the browser kind and its verdict; a failing verdict lands as a notice
- [v] verify: `cd backend && test -z "$(gofmt -l .)" && go vet ./... && go build ./... && go test ./...` (`-timeout 30m` for `clip/store`) · `pnpm gen:proto && git diff --exit-code -- backend/internal/gen frontend/src/shared/api/gen agent/internal/gen` · `pnpm --filter ./frontend test` · `pnpm lint` · `pnpm lint:fsd` · `pnpm build:web`

## impl notes
- muxer: a small MP4 muxer from npm rather than a wasm ffmpeg; read its current official docs before adding it (ARCH-33) and pin it through `pnpm add`
- the upload follows the path the originals already take — a signed PUT straight to private storage, the same shape `features/upload-clip-sources` uses — so the rendered bytes never enter an RPC body (CLIP's transfer constraint)
- T243 built the server's side of receiving a verdict; this task adds the client that sends it, together with the stored object's identity, and the server promotes it to the project's latest successful result
- measuring: resolution, frame rate and codec come from the encoder configs the render actually used; duration from the muxed track's own frame count; loudness from T252's measurement of the rendered buffer — the browser does not re-decode its own file to measure it
- CLIP-157 (r37) sets what "the same short-form contract" means here: the file is checked against CDS-52's V12 and CLIP-27's playability, never against a server render's bytes, size or bitrate — the compression is this side's own
- ② must not hold a blob URL of the result at all, so nothing can play the local copy by accident (CLIP-158)


## result
- `shared/lib/media/mux-mp4.ts` muxes the encoded H.264/AAC packets with Mediabunny 1.58.0, installed through the latest resolver after reading its [writing guide](https://mediabunny.dev/guide/writing-media-files), [packet-source API](https://mediabunny.dev/guide/media-sources), [packet timing](https://mediabunny.dev/guide/packets-and-samples), and [MP4 format options](https://mediabunny.dev/guide/output-formats). The MP4 has its index at the front. Measured AAC priming becomes a negative presentation timestamp/edit list, and trailing padding is trimmed to the authored sample window.
- `features/render-clip-browser` derives the verdict from the encoded configs, actual packet count/timing and T252's delivered-audio loudness. Its store operation consumes the local packets, reserves an immutable server-derived object, PUTs directly to storage, reports the verdict, and completes only after the server verifies the stored object's size and content type. It returns only the stored project and creates no local result URL; the existing preview/download read that project's signed storage links. T254 connects this operation to the render control.
- Migration 0066 retains the upload size and completion marker alongside the admitted revision and verdict. Reservation, revision/activity checks, result replacement and the completion marker use the serialized writer; promotion and cleanup of the former result are atomic and retry-safe. Ownership, finalization and revoked access are rechecked. An expired attempt cannot promote an orphan after its deletion grace period. Failed, partial or mismatched uploads leave the former result intact without server decoding or credit use.
- Chromium produced a six-second MP4 with 180 video frames and measured −16.00 LUFS audio. The runtime ffprobe identified 1080×1080 H.264 High at 30/1 and AAC-LC at 48 kHz, both starting at zero and lasting exactly six seconds. Independent ffmpeg decoding yielded exactly 288,000 stereo samples, a 2:1 cut-volume ratio, the declared −6 dB intro dip and a silent disabled-source cut, proving that the measured 2,112-sample priming is excluded by the container.
