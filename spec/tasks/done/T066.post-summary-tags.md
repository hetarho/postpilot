# T066 The list answer carries each post's tags
> st:done@260909 | ssot:POST-65 | base:POST@5 ARCH@2 | dep:-

## goal
`ListPosts` reports each post's current tags so the list can be narrowed by tag.

## acceptance
- [v] `PostSummary` gains `repeated string tags = 11` in `proto/postpilot/v1/post.proto`, with the generated code committed
- [v] `post.Summary` gains `Tags []string`, filled by the store from the newest content revision's tags; a post with no content, or content with an empty tag array, reports none
- [v] the store unmarshals a row's `content` at most once and uses it for both the blank-title fallback and the tags
- [v] the rpc mapper sets `Tags`; no tags maps to an empty repeated field
- [v] store test: tags are reported in stored order for a post with content, and absent for one without
- [v] rpc test: `ListPosts` answers with each post's tags
- [v] ARCH-26 and ARCH-28 gates green

## impl notes
- field 11 is the next free number on `PostSummary` (10 is `content_language`); numbers are never reused
- tags come from `content` (`PostContent.Tags`), not from a column — POST-14 keeps the block array canonical and there is no tags table, so this task has NO migration and no schema change
- `store.ListPosts` (`backend/internal/post/store/store.go:331`) already selects `content` and unmarshals it only when the trimmed title is blank; restructure to unmarshal once when `row.Content.Valid` and reuse the value ← a second unmarshal per row would double the JSON cost of the list read for every post
- case and order are preserved exactly as stored; normalization belongs to the client search (POST-65), so the server neither lowercases nor de-duplicates here
- `Summary` is a read model the store fills, so no service behavior, port or use-case changes (ARCH-8)
- `PostSummary` is also consumed by the FE mapper; leaving that untouched is deliberate — T068 owns the frontend side
