# T204 What the owner asked for is kept
> st:done@260917 | ssot:CLIP-133 CLIP-1 CLIP-24 | base:CLIP@31 ARCH@3 | dep:T202

## goal
Keep the verbatim instruction each generation used and the verbatim text of each revision request, with the time it was made, and show the owner that record.

## acceptance
- [v] an accepted generation records the instruction it froze; an accepted revision request records its request text and its target; each entry carries the time it was made
- [v] nothing is recorded by autosave: an instruction typed and saved but never used by a generation leaves no entry
- [v] a generation started with no instruction records an entry saying so rather than nothing, so the record explains a clip written without one
- [v] entries are readable by the owner in the project and are ordered newest first
- [v] a failed or cancelled attempt keeps its entry — what was asked for is what happened, whatever the outcome
- [v] deleting the project removes every entry with it, and no previous result, plan snapshot or direct-edit summary is stored
- [v] the record is project content, never diagnostics: nothing about it enters logs, which CLIP-88 keeps free of prompts and answers
- [v] tests: BE — an accepted generation and an accepted revision each write one entry, autosave writes none, project deletion removes them; FE — the record renders in order and states a generation with no instruction
- [v] verify FE (ARCH-25), BE (ARCH-26) and generated code (ARCH-28) pass

## impl notes
- migration 0056 adds `clip_project_requests(id, user_id, project_id, kind, body, created_at)` with a `(project_id, created_at)` index and a cascade to `clip_projects`; kind distinguishes the frozen instruction from a revision request and carries the revision target (`instruction` · `revision:flow` · `revision:narration` · `revision:both`). Queries go in store/queries/clips.sql and `pnpm gen:sql` runs sqlc through Docker (ARCH-28)
- the write point is acceptance, not save: the owner chose to record what the AI actually read, so write the entry where the generation payload freezes its inputs (clip/quotes.go's start path, which already marshals `Instruction` into `generationPayload`) and where T202's revision job is accepted. An entry written at enqueue time survives a later failure, which is what the acceptance asks for
- store the text verbatim: no trimming, no normalisation, no deduplication against the previous entry. CLIP-133 says verbatim, and a deduplicated record cannot answer "what did I ask for that time"
- read path: extend `GetClipProject` rather than adding an RPC — the record is project content under CLIP-1 and the page already loads the project once
- FE placement: the record is owner-facing history, not a control. Put it where the observations panel sits (a read-only disclosure in ① and ②) so it needs no dock action and no step of its own
- retention is the project's, not the sources': entries outlive the 24-hour original retention (CLIP-73) and are removed only with the project (CLIP-24). Nothing here extends source retention
- unchanged: `clip_attempt_checkpoints` and the diagnostics CLIP-88 bounds stay exactly as they are — this record is a separate, owner-facing table

## result
- migration `0060_clip_project_requests.sql` (NOT 0056 as the note said — that number was
  taken by T200's duration CHECK): `clip_project_requests(id, project_id, user_id, kind,
  body, created_at)`, a `(project_id, created_at)` index and the composite cascade to
  `clip_projects(id, user_id)`; `kind` is CHECK-bounded to the four the domain declares.
- queries `RecordClipProjectRequest` / `ListClipProjectRequests` in
  `store/queries/clips.sql` (newest first, `rowid` breaking a tie inside one instant),
  regenerated with `pnpm gen:sql`; `clip/store/requests.go` implements both.
- `clip/types.go`: `ProjectRequest`, `RequestInstruction`, `RevisionRequestKind`,
  `ValidRequestKind`, and `Project.Requests`; `clip/ports.go` widens the one `Store`.
- write point: `GenerationStart.Request`, written inside `clip/generation.go#enqueue`
  BETWEEN the source/quote link and the activation. That seam is the only place where the
  job row exists but is still invisible to the dispatcher, so a record that cannot be
  written fails the start instead of letting a clip run unexplained — and a job that is
  accepted always has its entry, whatever it goes on to do. `quotes.go#startApproved`
  passes the frozen instruction (empty body included), `revision.go#StartRevision` the
  owner's words and target; a re-render passes nothing.
- read: `Service.GetProject` fills `Requests` — the OWNER's read path only, so no job pays
  for it — mapped by `rpc/handler.go#projectProto` into the new proto
  `ClipProjectRequest` (ClipProject field 33).
- FE: `entities/clip-project/model/revision.ts` gains `ClipProjectRequest` and
  `isClipRequestKind`, `api/clip-project.ts` maps them, and
  `ui/ClipRequestRecord.tsx` reads them back as a closed disclosure beside the
  observations in ① and ② (and in ②'s waiting state). New `record` copy in ko/en.
- tests: `clip/store/request_record_test.go` (an accepted generation and an accepted
  revision each record one, verbatim with its time; a save records none; a generation
  with no instruction records that it had none; a failed revision keeps its entry; an
  undeclared kind is refused; deleting the project takes the entries with it) and
  `pages/clip/ui/ClipRequestRecord.test.tsx` (newest first, and the no-instruction line).

특이사항
- Nothing about the record is logged, and no plan snapshot, result or edit summary is
  stored beside it — `clip_attempt_checkpoints` and CLIP-88's diagnostics are untouched.
- Out of scope, logged: `useClipProject`'s poll stops at a terminal `revise_clip` job, so
  a revision's settlement lands only on the next read (the same condition keeps polling a
  generation until it settles).
