# T205 The smokes run beside the deploy, not ahead of it
> st:done@260916 | ssot:ARCH-38 ARCH-36 | base:ARCH@3 | dep:-

## goal
Let the image build and the rollout finish without waiting for the smokes, while the smokes still run on the same commit and still fail the workflow.

## acceptance
- [v] the pushed image no longer depends on a smoke stage, and the rollout does not wait for one
- [v] the pushed image carries the same files it carries today, shown by comparing the two targets' contents rather than assumed
- [v] the smokes still run on the same commit in their own job, reusing the build job's cache instead of recompiling, and a smoke failure fails the workflow run
- [v] `DEPLOY_ENABLED` unset still skips the push and the rollout while leaving the run green, exactly as today
- [v] the workflow records, in one place, what to change to restore the blocking gate when closed beta opens (→ARCH-38)
- [v] tests: a check under `deploy/` asserting the workflow still builds the `production` target in some job and that its failure is not ignored, so removing the gate cannot pass as "moved"

## impl notes
- the pushed target is `runtime`. `production` is `runtime` plus two `COPY --from=<smoke>` lines re-copying `/usr/local/bin/ffmpeg` and `/usr/local/bin/ffprobe`, and both smoke stages derive from `runtime` without touching either file, so the contents match and only layer ids differ. Prove it by comparing the two targets' file lists; do not trust this note.
- job order: the smoke job takes `needs: build` so it restores the cache the build job exported rather than recompiling the builder stage's Go (~170 s measured). The deploy is therefore already complete when the smoke job starts.
- the smoke job builds `--target production` and pushes nothing. `cache-from` only — the build job owns `cache-to`.
- restoring the gate is a workflow edit, not a variable (owner's choice): point the pushed target back at `production` and give the rollout `needs: [build, smoke]`. Keep both notes in one comment beside the target so the closed-beta change is a single place.
- measured today: `Build image` is 630 s of a 12 min run and rollout is 47 s, so the deploy after this change is the Go build plus the push.
- unrelated and out of scope: the Actions cache is at 11.03 GB against a 10 GB limit and evicting, so a run whose ffmpeg/resvg stages miss pays ~842 s extra. This task does not address it.

## result
- changed: `.github/workflows/deploy-backend.yml` (pushed target `runtime`, new `smoke` job, trigger path `deploy/*_test.py`, discover pattern), `.github/workflows/ci.yml` (same discover pattern so the new check is a merge gate too), `deploy/backend_deploy_workflow_test.py` (new), `.gitignore` (`__pycache__/`, which the deploy tests now produce on every local run).
- the pushed image is proven unchanged from inside the image rather than by diffing two builds: `production`'s two `COPY --from=<smoke>` layers are EMPTY (0 files each), because they re-copy bytes already present, so `usr/local/bin/ffmpeg` and `ffprobe` exist in exactly one layer of the image. `production` therefore adds nothing to `runtime` but two empty layers.
- a first attempt did diff the two targets' exported filesystems and found every file identical except `/api`. That difference was not the target: another session was committing backend changes throughout (17:01-17:08), so the two builds compiled different sources. The layer check above is immune to that and is what the acceptance rests on.
- cache reuse by the smoke job is structural, not measured here: `needs: build` orders it after that job's `cache-to: type=gha,mode=max`, and it carries `cache-from` only. Note that `build` now exports only the `runtime` path, so the smoke job restores builder/media-build/render-build and runs just the smoke stages — which is the intent, not a gap.
- measured locally while verifying: media-smoke 574.7 s, clip-input-smoke 129.8 s (they run in parallel as BuildKit stages), `go build` 64.3 s, `go test -c ./cmd/api` 80.6 s. The critical path this task removes from the deploy is the 574.7 s one.
- the smoke gate check catches all four ways the gate could be lost rather than moved: deleting the job, `continue-on-error`, hiding it behind an `if:`, and switching the target to `runtime`. Verified by mutating a parsed copy of the workflow.
- no SSOT divergence.
