# T391 Separate fast backend deployment from long media verification
> st:done@260925 | ssot:ARCH-24 ARCH-31 ARCH-32 ARCH-36 ARCH-38 | base:ARCH@11 | dep:T390

## goal
Restore a normal cached backend deployment target below five minutes, with long media verification unable to hold up a later deployment.

## acceptance
- [v] Deploy backend contains only image/configuration checks, production image publishing and the protected health-gated rollout; a separate workflow verifies the exact successfully deployed revision without sharing a deployment concurrency lock.
- [v] Only the rollout is serialized against production changes, an active rollout is never cancelled automatically, and superseded builds/runs cannot overwrite a newer deployment.
- [v] Image, worker and separate-process release smokes remain enabled but run independently; all fixture images use Buildx/GHA caches, and the release runner can consume explicitly prebuilt storage/API/worker images without recompiling FFmpeg or MinIO in another builder.
- [v] Workflow regression tests verify the dependency graph, cancellation/serialization boundaries, trusted revision selection and cache/prebuilt-image wiring; required repository checks and relevant real fixture execution pass.
- [v] DEPLOY.md distinguishes deployment completion from asynchronous media verification and documents the measured target and cold-build/runner-queue limits; after the authorized push, actual rollout duration is measured rather than inferred from the smoke duration.

## impl notes
- Direct follow-up to the confirmed T386/T387 regression: the 33m20s workflow included sequential image (11m59s), worker (7m20s) and release (9m43s) checks; the release script used the default Docker builder without the shared cache and rebuilt media tools for 567.3s. Workflow-level concurrency then blocked subsequent releases despite the production swap already being complete.
- Preserve ARCH-38's pre-beta policy: full media verification reports failures separately and does not gate production. Do not remove coverage, relax health/rollback checks, activate GPU behavior or consume pending SSOT changes.
- Use a separate media verification workflow after successful Deploy backend completion, with explicit source revision checkout, read-only permissions and independent cancellable concurrency. It must also support an intentional manual run.
- Serialize server mutation only, preserve immutable image pins and reject a superseded deployment while holding the rollout lock. Superseded build cancellation must not cancel a running rollout.
- Reuse Buildx and scoped GHA caches for all fixture targets; provide an explicit prebuilt-storage option while preserving the ordinary local source-build path. Document the new workflow and avoid arbitrary five-minute termination of a healthy in-progress server swap.
- Keep deployment regression tests in the existing CI backend job, removing the duplicate serial invocation from the publish path; Compose validation and image tooling/health gates remain blocking. This gives routine backend changes margin under the five-minute target without dropping coverage.
- Existing user authorization includes one commit for this task, push and production deployment verification. GitHub runner availability and a cold toolchain build are external to the normal cached target; report actual timings and any unmet target honestly.
