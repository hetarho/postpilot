# T192 Decoding uses the cores the encode cannot
> st:done@260916 | ssot:CLIP-124 CLIP-125 | base:CLIP@29 ARCH@2 | dep:T191

## goal
Let media decoding use more than one thread while every encoder stays single-threaded, so decode-bound stages speed up without moving a delivered byte.

## acceptance
- [v] the decoder thread count is configured separately from the encoder thread count, and every encoder invocation still passes the single-threaded value it passes today
- [v] source probing, analysis-copy preparation and footage rendering pass the decoder value on their inputs
- [v] filter threads are unchanged
- [v] the delivered clip is unchanged (→T191), and the analysis copies are byte-identical to the ones produced before the change
- [v] tests: argument assertions that an input carries the decoder value and every output the encoder value, and the identity regression from T191
- [v] verify BE (ARCH-26) passes

## impl notes
- the constructor currently refuses any value but one (`media/workspace.go:51`, `cfg.Threads != 1`) and one field feeds both roles; split it into a decode value and an encode value, keeping the encode value pinned at 1 so libx264 output stays bit-identical
- placement already separates the two roles: `-threads` before `-i` is the decoder (`chunks.go` chunk args, `composition_footage.go:21`, `probe.go:128`), and the `-threads` inside `encodeProfile` (`render.go`) is the encoder
- the config lives in `platform/config/clip.go` `ClipMedia`; default the decode value to 2 — prod is a single physical core with two hyperthreads, where HEVC 1080p decode measured 27 fps at one thread and 35 fps at two, while encoding measured no gain at all (13.4 vs 13.7 fps lossless, 12.0 vs 12.0 fps delivery)
- decoder multithreading is bit-exact by specification, which is what keeps this inside CLIP-125; encoder multithreading is not, which is why the encode value stays 1

## result
- `clip.MediaConfig.Threads` became `DecodeThreads` + `EncodeThreads` (`internal/clip/media.go`), defaulted to 2 and 1 in `platform/config/clip.go`; the constructor (`media/workspace.go`) still pins the encode value at 1 and now bounds the decode value to 1..8
- decoder positions (every `-threads` before an `-i`) take the decode value: `probe.go` decode pass, `chunks.go` analysis-copy input, `composition.go` `inputArgs`, `composition_footage.go`, `composition_plates.go`, `luminance.go`, `loudness.go`, `render.go` cut source and layer images. The encoder's own `-threads` in `encodeProfile` and in `chunkArgs`' output takes the encode value; `-filter_threads`/`-filter_complex_threads` take it too, so filter threading is byte-for-byte what it was
- tests: `TestDecodingUsesTheCoresTheEncodeCannot` (media_test.go) splits each argument list at its first `-i` and asserts the decoder count before it, no decoder count after it, the encoder pinned at 1 and the filter threads unmoved — over the probe decode pass and the analysis-copy arguments; `TestEachRenderInputHasItsOwnResourceLimits` and the sampler test now assert the same split on footage rendering; `clip_media_test.go` pins both defaults
- identity held in the pinned image: `TestDeliveredClipIdentity` passes unchanged against T191's baseline (101.9 s, was 112.1 s before the split on this 16-core box — prod is one physical core with two hyperthreads, where the measured decode gain is 27→35 fps), and the new `TestAnalysisCopyIdentityAcrossDecoderThreads` prepares the same original at 1 and 2 decoder threads and compares the proxies, which are identical
- run both with `docker build -f backend/Dockerfile --target identity-smoke -t postpilot-identity . && docker run --rm postpilot-identity`
- no SSOT difference; verify BE (ARCH-26) passes (`go test ./...` with `-p 2`: the full-parallel run is OOM-killed on this box)
