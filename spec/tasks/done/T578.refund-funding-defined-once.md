# T578 Define what a refunded payment funded once
> st:done@261005 | ssot:BILL-11 ARCH-7 ARCH-24 | base:BILL@9 ARCH@15 | dep:T570 | touches:backend/internal/billing/ backend/internal/usage/store/refund_funding.go backend/internal/clip/store/refund_funding.go backend/internal/platform/db/migrations/ backend/cmd/api/refund_benefits.go

## goal
"What this payment funded" — its credit lots, its export windows and its funding end — is computed once from the payment and handed to the usage and clip stores and the database guards, so refund evidence and refund enforcement can no longer disagree (BILL-11: a confirmed refund voids only the entitlements funded by that payment).

## acceptance
- [v] billing computes one funding value per refundable payment (kind, coverage, lot id or correlation, funding window start/end) — `FundingEnd` included — and the usage and clip predicates take that value's fields as arguments instead of re-deriving the window
- [v] for an upgrade, the funded set includes the higher-tier daily lots issued in its window, matching what the 0120 trigger already treats as upgrade-funded (the code side follows the trigger, so the guard and the evidence agree)
- [v] the 0120 refund-guard triggers read a guard row that carries the funding window billing computed (written when the refund is requested), instead of recomputing the window in SQL; a forward migration replaces them
- [v] the clip funded/used arithmetic exists once (shared by RefundFundingEvidence and ConfirmRefundFunding)
- [v] tests: subscribe, renew, pack and upgrade payments each produce the same funded set in the evidence and in enforcement (a grant blocked by the guard is counted as funded and vice versa), including an upgrade whose window issued lazy daily lots
- [v] behaviour unchanged otherwise: ARCH-26 green; `pnpm gen:sql` clean
