## goal
Cut frames and transition windows are computed by one Go timeline that both the ffmpeg composition graph and the ground sampler read, and the browser draws CDS-36's fades with the same curve the server's ffmpeg draws, pinned by a fixture Go writes — so a browser export and a server export of one plan show, and sample, the same frames (CLIP-192).

## acceptance
- [v] one Go timeline type (frames per cut, transition windows and kinds at the output frame rate) replaces `cutFrames`/`transitionFrames` in `render.go` and `footageTimeline` in `ground_sampler.go`; `compositionGraph` and the sampler both build from it
- [v] `fadeBlackMean` reads its window from that timeline and keeps mirroring ffmpeg's xfade fade-through-black curve
- [v] a Go test writes a JSON fixture (as the region-layout fixture is written) with, for a set of plans covering a hard cut, a 200 ms fade, a 300 ms fade-through-black and a rate-changed cut, each output frame's source cut, source time and fade weights; the FE `draft-preview.ts`/`composite-video.ts` tests load it and match frame for frame (weights within 1/255)
- [v] the browser's fade and fade-through-black drawing follows the server curve (the smoothstep/phase ffmpeg uses, as `fadeBlackMean` mirrors), replacing the linear two-phase fade
- [v] ARCH-37: `production` target media smokes pass, identity digest unchanged on this host (the server's pixels must not move); FE suite green
- [v] behaviour unchanged otherwise: ARCH-26 green; FE gates (`pnpm --filter ./frontend test`, lint, lint:fsd, lint:style, build:web) green
