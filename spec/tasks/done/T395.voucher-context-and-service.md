# T395 voucher context, VoucherService and the vouchers table
> st:done@260925 | ssot:GIFT-1 GIFT-2 GIFT-3 GIFT-4 GIFT-5 GIFT-6 GIFT-7 GIFT-8 GIFT-9 GIFT-10 GIFT-12 GIFT-14 QUOTA-58 | base:GIFT@2 QUOTA@20 | dep:T394

## goal
Add the backend `voucher` bounded context: issue, list and revoke for the operator; a public read by token; single-use redemption that opens a voucher lot.

## acceptance
- [v] `proto/postpilot/v1/voucher.proto` defines `VoucherService` with five rpcs: `GetVoucher`, `RedeemVoucher`, `IssueVoucher`, `ListVouchers`, `RevokeVoucher` (messages in impl notes). BE and FE code is regenerated and ARCH-28 passes
- [v] the auth interceptor treats the five rpcs as follows:
    - `GetVoucher` is in `publicProcedures`
    - `IssueVoucher`, `ListVouchers` and `RevokeVoucher` are in `masterProcedures`
    - `RedeemVoucher` needs only a session
    - an interceptor test pins all three sets
- [v] IssueVoucher validation
    - accepts: credits 1..100000, validity_days 1..365, a message of at most 80 characters, and either no sale or a sale with amount 1..10000000 KRW and a payer of 1..40 characters
    - anything else is refused with `invalid_argument` and `VOUCHER_INVALID`
    - an accepted issue stores a new voucher whose link expires 90 days after issue and returns it with its token
- [v] ListVouchers returns every voucher, newest first, with state, sale, redeemer, redemption time and remaining credits. It returns the token only while the voucher is redeemable, and also returns presets basic/pro/max read from `plan.MonthlyCredits` at 30 days
- [v] GetVoucher by token returns only credits, validity_days, message, state and link expiry (never issuer, sale, payer or redeemer). An unknown token is `not_found` with `VOUCHER_NOT_FOUND`
- [v] RedeemVoucher runs in one write transaction:
    - it opens one voucher lot through the usage port, expiring `validity_days × 24h` after the redemption instant
    - it marks the voucher redeemed by the caller
    - redeemed, expired and revoked vouchers are refused with `failed_precondition` and `VOUCHER_REDEEMED`, `VOUCHER_EXPIRED` or `VOUCHER_REVOKED`
    - two concurrent redemptions of one token yield exactly one lot
- [v] RevokeVoucher
    - unredeemed: sets `revoked_at` and the token stops resolving to a redeemable state
    - redeemed: also expires the voucher lot at the revoke instant (T394 `ExpireVoucherLot`)
    - revoking twice is idempotent
- [v] the token appears in no log line, error message or error detail
- [v] Go tests cover validation bounds, state derivation (precedence revoked > redeemed > expired), the public view's field set, the concurrent redemption, revoke in both states and the store mapping
- [v] the FE error catalogues and `appFailureSpecs` carry the five new reasons in ko and en, so ARCH-25 passes with the regenerated enum
- [v] ARCH-25, ARCH-26 and ARCH-28 pass

## impl notes
- Placement follows `billing` (ARCH-5/6/7):
    - `backend/internal/voucher/{types.go,service.go,ports.go}`
    - `voucher/store` (sqlc `store/queries/voucher.sql` → `store/sqlc`)
    - `voucher/rpc`
    - wiring in `cmd/api/contexts.go`
    - add `voucher` to the context list the next time ARCH is touched (ARCH-5 names contexts; no SSOT edit in this task)
- Migration: next free number after T394's.
    - Table `vouchers`:
        - `id TEXT PRIMARY KEY`
        - `token TEXT NOT NULL UNIQUE`
        - `credits INTEGER NOT NULL CHECK (credits > 0)`
        - `validity_days INTEGER NOT NULL CHECK (validity_days > 0)`
        - `sale_krw INTEGER CHECK (sale_krw > 0)`
        - `payer_name TEXT`
        - `message TEXT NOT NULL DEFAULT ''`
        - `issued_by TEXT NOT NULL`
        - `issued_at TEXT NOT NULL`
        - `link_expires_at TEXT NOT NULL`
        - `redeemed_by TEXT REFERENCES users(id) ON DELETE SET NULL`
        - `redeemed_at TEXT`
        - `lot_id TEXT`
        - `revoked_at TEXT`
        - `CHECK ((sale_krw IS NULL) = (payer_name IS NULL))`
    - Index `idx_vouchers_issued ON vouchers(issued_at)`.
    - Write nullable columns as bare `TEXT`/`INTEGER`: an explicit `NULL` makes sqlc generate `interface{}`.
    - `lot_id` is a reference by id into usage's table, with no FK (ARCH-7: a context reads another's data only through its behaviour).
- Token storage
    - 32 random bytes → `base64.RawURLEncoding` (the `auth.NewLinkToken` entropy)
    - stored raw, not hashed: GIFT-14 requires copying an unredeemed link again, and whoever reads the DB can already grant credits
    - never passed to `slog` or into `NewAppError` params
- Voucher id: 16 random bytes hex, like `billing.newID`.
- Domain constants in `voucher/types.go`: `LinkLifetime = 90*24h`, `PresetDays = 30`, `MaxMessageRunes = 80`, `MaxPayerRunes = 40`, `MaxCredits = 100000`, `MaxDays = 365`, `MaxSaleKRW = 10000000`. Message and payer are trimmed, and counted in runes.
- State is derived, not stored: `State(at)` = revoked if `revoked_at` is set, else redeemed if `redeemed_at` is set, else expired if `at ≥ link_expires_at`, else redeemable.
- Ports (consumer-declared, in `voucher/ports.go`):
    - `Store` with `InWriteTx(ctx, fn func(Store, Credits) error)`
    - `Credits{OpenVoucherLot, ExpireVoucherLot, VoucherLotStandings}`, implemented in `cmd/api` by a thin adapter over `usage.Service` (like `billingCredits`); `VoucherLotStandings` returns each lot's remaining (0 once expired) and its expiry
    - the tx-scoped `Credits` comes from `SetCreditsForTx(func(*sql.Tx) voucher.Credits)`, built on `usage.NewService(usagestore.NewTx(tx), nil, 0, anchors, approvedCeilingKinds()...)` exactly as billing does
- Redeem inside `InWriteTx`
    1. load the voucher by token
    2. derive the state at `now`; refuse unless redeemable
    3. `OpenVoucherLot`
    4. `UPDATE vouchers SET redeemed_by=?, redeemed_at=?, lot_id=? WHERE id=? AND redeemed_at IS NULL AND revoked_at IS NULL`
    5. if that updates 0 rows, return the redeemed refusal; the transaction rolls the lot back
    - SQLite's single writer serializes the two racers; the test drives two goroutines through the real store.
- Revoke inside `InWriteTx`: set `revoked_at` only where it is NULL; if the voucher was redeemed, call `ExpireVoucherLot(lot_id, now)`.
- The redeemer shown in ListVouchers is `redeemed_by` itself. A self-signup account's user id is its email (AUTH-33) and an operator account's id is its login id, so no auth port is needed.
- `remaining_credits` comes from `VoucherLotStandings` at `now` (0 when unredeemed, revoked or lapsed); `credits_expire_at` is the lot expiry, read from the same call.
- Proto: RFC3339 strings for instants, as in `plan.proto`; an empty string means absent.
    - `enum VoucherState { VOUCHER_STATE_UNSPECIFIED = 0; VOUCHER_STATE_REDEEMABLE = 1; VOUCHER_STATE_REDEEMED = 2; VOUCHER_STATE_EXPIRED = 3; VOUCHER_STATE_REVOKED = 4; }`
    - `message VoucherSale { int64 amount_krw = 1; string payer_name = 2; }`
    - `message Voucher { string id = 1; int32 credits = 2; int32 validity_days = 3; VoucherSale sale = 4; string message = 5; VoucherState state = 6; string issued_at = 7; string link_expires_at = 8; string redeemed_by = 9; string redeemed_at = 10; int32 remaining_credits = 11; string credits_expire_at = 12; string token = 13; }`
    - `message VoucherPreset { Plan plan = 1; int32 credits = 2; int32 validity_days = 3; }`
    - `GetVoucherRequest{token}` → `GetVoucherResponse{credits, validity_days, message, state, link_expires_at}`
    - `RedeemVoucherRequest{token}` → `RedeemVoucherResponse{credits, credits_expire_at}`
    - `IssueVoucherRequest{credits, validity_days, VoucherSale sale, message}` → `IssueVoucherResponse{Voucher voucher}`
    - `ListVouchersRequest{}` → `ListVouchersResponse{repeated Voucher vouchers, repeated VoucherPreset presets}`
    - `RevokeVoucherRequest{id}` → `RevokeVoucherResponse{Voucher voucher}`
- `FailureReason`: append `VOUCHER_EXPIRED`, `VOUCHER_INVALID`, `VOUCHER_NOT_FOUND`, `VOUCHER_REDEEMED`, `VOUCHER_REVOKED` after the current highest value (243 at task creation; re-check). Never renumber.
- `GetVoucher` is left out of `throttledProcedures`: it is a read, and 256-bit tokens make enumeration pointless. Add a one-line reason beside the public set.
- `ListVouchers` has no paging: operator-issued pilot volume is tens of rows. Revisit if it grows.
