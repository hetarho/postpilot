# T399 the tail trim never leaves a sliver cut
> st:done@260926 | ssot:- | base:ARCH@11 | dep:-

## goal
Trimming a generated flow to its target duration stops each cut at CDS's 1.2 s cut floor and takes the rest from the cut before it. The old overlap floor is used only for an overrun the 1.2 s floors cannot absorb, so no cut becomes a sliver when the flow could avoid it.

## acceptance
- [v] Failing-first regression test (F3 bug): a flow whose tail cut must give up more than its length minus 1.2 s ends with that cut at exactly 1200 ms of output and the cut before it shortened by the remainder. The total equals the target, and each trimmed cut carries its `plan_target_duration` notice
- [v] a cut already shorter than 1.2 s is neither trimmed nor lengthened by the floor pass
- [v] an overrun larger than every cut's room above 1.2 s still reaches the target through the old floor (`transition + 1`, plus the next cut's transition), so `validatePlan` does not refuse it
- [v] Behavior otherwise unchanged: `TestPresetTargetYieldsToTheApprovedDuration`, the multi-source tests and existing tests pass as written
- [v] verify BE: `cd backend && test -z "$(gofmt -l .)" && go vet ./... && go build ./... && go test -timeout 30m ./...`

## impl notes
- from review/clip-narrate-failure-260926 F3
- `plan_ladder.go` `trimGeneratedOverrun` walks the tail twice with the same loop body. The first pass uses floor `max(overlap floor, cut_min)` with `cut_min` = `design.Timing.CutMinS` in ms (1200). The second pass runs only while the total is still over the target, with today's overlap floor ← one loop parameterised by the floor keeps the word and caption clamping in one place
- no cut is removed: removal would renumber `Written`, the copies and every cut-scoped notice, and `validatePlan`'s overrun refusal already bounds what is left
- both callers share the function: `timeline.go:150` (native composition) and `service.go:371` (legacy)

## result
- `ai/plan_ladder.go`: `trimGeneratedOverrun` runs `trimTail` twice. The first pass uses floor `max(overlap floor, 1200)` (`design.Timing.CutMinS`), and the second pass, only when still over the target, uses today's overlap floor. `trimTail` is the old loop body, with the floor as a parameter
- `plan_ladder_test.go` `TestTailTrimStopsEachCutAtTheCutFloor` covers three cases. The prod shape reproduced `[5000 2999 1]` before the fix and gives `[5000 1800 1200]` after it. A cut under the floor is left alone. When every cut is at its floor, the target is still reached through the old floor, as `[1200 1200 600]`
- deviation from the acceptance as written: `TestEightShortSourcesComposeWithExactTransitionTimeline` pinned `DurationMS` 15760, the old algorithm's product. There, the last cut was trimmed to 800 ms and then re-extended to 1560 ms for its copy's exposure. The last cut now stops at 1200 ms, the cut before it gives the other 400 ms, and the last cut then extends to 1830 ms, for 15630 ms. Both are inside the ±1000 ms target tolerance and every other assertion held, so the pin moved to 15630 with a comment
- no cut is removed and no SSOT changes. A flow whose cuts all sit near 1.2 s can still end with a short tail cut, because validatePlan refuses an overrun
