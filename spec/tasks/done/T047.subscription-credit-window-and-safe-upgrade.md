# T047 The subscription's own credit window, and an upgrade that cannot lose a charge
> st:done@260908 | ssot:QUOTA-42 QUOTA-35 QUOTA-37 | base:QUOTA@6 ARCH@2 | dep:-

## goal
Give a starting subscription its own monthly window at the tier's whole grant, stop an upgrade from rolling back a charge that already left, and put both under a test that drives billing against the real `usage.Service`.

## acceptance
- [v] `usage.Service` gains one operation for QUOTA-42 that, in one write tx, expires the account's current monthly lot at the window's start and then writes the window's lot with `granted = remaining = plan.MonthlyCredits(tier)` and the window's end, whatever that id already held
- [v] `billing.Subscribe` opens its window through that operation instead of `OpenMonthlyLot`, and `OpenMonthlyLot` keeps its absent-only insert for the renewal paths, whose anchor does not move
- [v] an account that signs up and subscribes on the SAME Seoul date holds exactly the tier's whole grant afterwards, in exactly one non-expired monthly lot — a test pins the balance and the lot count, because this is the id collision the fix exists for
- [v] an account that subscribes on a different date than its free window's start holds the tier's whole grant and no second non-expired monthly lot: the free remainder does not carry over (QUOTA-42)
- [v] the operation is idempotent: running it twice for the same window leaves the same single lot with the same granted, remaining and expiry
- [v] `usage.RaiseMonthlyLot` answers an account with no current monthly lot with a no-op instead of `ErrLotNotFound`, the way `TopUpMonthlyLot` already documents, and `ErrLotNotFound` keeps its other caller
- [v] a test proves an upgrade whose account holds no current monthly lot still commits: the subscription row, the `charge` event, the `tier_change` event and `AssignTier` all survive, so a captured payment can never be discarded by the credit step
- [v] a billing test harness drives `billing.Service` against a real `usage.Service` over `usage/store` on a `db.Open(filepath.Join(t.TempDir(), …))` database — the way `billing/store/registration_test.go` already opens one — and the four checks above run through it, not through a `Credits` stub
- [v] ARCH-26 passes

## impl notes
- from review/diff-260908 F1 F2 F13
- F1's mechanism, verified by running `plan.AnchorWindow` and `monthlyLotID`'s arithmetic: the free lot's id is keyed on its WINDOW START while `Subscribe` keys its own on the subscribe INSTANT, and both format to the same Seoul date whenever the account subscribes on its anchor day of month — signing up and subscribing the same day hits it every time (both become `monthly:<user>:2026-09-08`). `InsertLotIfAbsent` then keeps the free 50 and discards the tier's grant, returning `(false, nil)` that `OpenMonthlyLot` drops on the floor
- so the fix is an upsert, not a new id scheme: `INSERT … ON CONFLICT(id) DO UPDATE SET granted = excluded.granted, remaining = excluded.remaining, expires_at = excluded.expires_at` needs no migration and no rewrite of ids already in the table, and it is idempotent because the values are derived from the tier and the window rather than from what is there
- expire before upsert, in that order: when the two windows share an id the expire touches the row the upsert then overwrites, and when they do not it closes a lot the upsert would otherwise leave beside the new one. `UPDATE credit_lots SET expires_at = ? WHERE user_id = ? AND kind = 'monthly' AND expires_at IS NOT NULL AND expires_at > ?`
- both statements belong in `usage/store/queries` and the operation in `usage/service.go`; `billing.Credits` (`billing/ports.go`) gains the method and `cmd/api`'s `billingStore.SetCreditsForTx` already hands billing a tx-scoped `usage.Service`, so no new wiring is needed
- F2's window is real but narrow: an active subscriber's monthly lot expires at `NextGrantAt`, and nothing re-opens it until the 10-minute `RunDue` tick or the account's next metered request. An upgrade inside that gap charges the card (correctly outside the tx, ARCH-10) and then throws the whole tx away on `ErrLotNotFound`
- the no-op is not a guess: `TopUpMonthlyLot`'s own comment states the product rule ("An account with no current monthly lot is a no-op, not an error: its next request opens one at the new tier's size anyway") and `RaiseMonthlyLot` is the same operation reached from the RPC path
- F13 is why both shipped green: every `Credits` fake in `billing/subscription_test.go` and `billing/service_test.go` returns `nil` unconditionally, so no test has ever run billing's credit calls against real SQL. Keep the existing fakes for the cases that only need to observe a call; the new harness is for the ones that need the real ledger
