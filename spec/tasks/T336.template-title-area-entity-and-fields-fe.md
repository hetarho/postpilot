# T336 FE templates carry the title area, and ① lists title-area asks first
> st:todo | ssot:TMPL-2 TMPL-8 TMPL-55 ARCH-21 ARCH-24 | base:TMPL@10 ARCH@9 | dep:T333

## goal
- The FE template entity round-trips `titleArea` untrimmed on every create and save, bounds it with a mirrored 200-character ceiling, and builds ①'s data fields from both areas with title labels first.

## acceptance
- [ ] `Template.titleArea` is mapped from proto and is `''` when the template has none.
- [ ] `useCreateTemplate`'s `create` and `useUpdateTemplate`'s `saveAll` send `titleArea` on every call, byte for byte and never trimmed. A `''` on update clears the area (TMPL-8).
- [ ] `TEMPLATE_TITLE_AREA_MAX_CHARS` defaults to 200 and can be overridden by `VITE_TEMPLATE_TITLE_AREA_MAX_CHARS`; a malformed override falls back to 200. `TEMPLATE_LIMITS.titleArea` exposes it, and `canSaveTemplate` refuses a title area over it while allowing an empty one.
- [ ] The template screen's draft carries the loaded `titleArea` unchanged:
  - saving an edit of the name alone sends the stored title area byte-identical;
  - `/templates/new` sends `''`.
- [ ] ①'s `answerFields` behaves as follows:
  - it lists title-area fields first, then body fields, each with this post's stored answer;
  - with an empty title area it returns exactly what it did before;
  - a label used in both areas gives no fields;
  - a title area that does not parse gives no fields.
- [ ] Tests:
  - `features/fill-template-answers/model/answers.test.ts`: title first, the empty-title result unchanged, a cross-area duplicate giving `[]`, a failing title giving `[]`;
  - `entities/template/model/types.test.ts`: `canSaveTemplate` against the title ceiling;
  - `pages/template/ui/TemplatePage.test.tsx`: `keeps a stored title area when only the name is saved` and `creates with an empty title area`.
- [ ] Verify: `pnpm --filter ./frontend test` · `pnpm lint` · `pnpm lint:fsd` · `pnpm lint:style:probe && pnpm lint:style` · `pnpm build:web`

## impl notes
- The ceiling lives in `entities/template/config/index.ts`:
  - it holds `export const TEMPLATE_TITLE_AREA_MAX_CHARS = positiveIntEnv(ENV_LIMIT_OVERRIDES.templateTitleAreaMaxChars, 200)`;
  - `shared/config/index.ts` gains only the env read, `templateTitleAreaMaxChars: import.meta.env.VITE_TEMPLATE_TITLE_AREA_MAX_CHARS`, in `ENV_LIMIT_OVERRIDES`;
  - so the plan's "mirrored in shared/config" means the read alone. `shared/config/index.test.ts` refuses a `TEMPLATE_*` export there (T258).
- Add `VITE_TEMPLATE_TITLE_AREA_MAX_CHARS=200` beside T333's `TEMPLATE_TITLE_AREA_MAX_CHARS` in `.env.example` and `.env.production.example` (ARCH-21).
- `entities/template/model/types.ts`:
  - `Template.titleArea: string` is required, `''` meaning none, with a one-line doc naming TMPL-50;
  - `TEMPLATE_LIMITS.titleArea` is `TEMPLATE_TITLE_AREA_MAX_CHARS`;
  - `canSaveTemplate`'s fields gain `titleArea: string`, and the rule adds `templateChars(fields.titleArea) <= TEMPLATE_LIMITS.titleArea`. `templateChars` trims, which matches the server's edge trim.
- `api/template-queries.ts` `toTemplate` adds `titleArea: template.titleArea`.
- `api/useCreateTemplate.ts`: `create`'s fields gain `titleArea: string`, sent as is. `CreateTemplateRequest.title_area` is a plain string, and `''` means none.
- `api/useUpdateTemplate.ts`: `saveAll`'s fields gain `titleArea: string`, sent as `titleArea: fields.titleArea`. It is always present and never trimmed, like `body`. The doc comment's "three fields" becomes all six (TMPL-8).
- `pages/template/ui/TemplatePage.tsx`:
  - `Draft` gains `titleArea: string`, and `draftOf` fills it with `stored?.titleArea ?? ''`;
  - `trimmed.titleArea = draft.titleArea`, untrimmed;
  - `canSaveTemplate(trimmed)` now receives it.
- No title UI, dirty check or parse-gate change here; those belong to T340. The draft carries the stored value only so that a save made before T340 cannot clear it.
- A known interim until T340: the body builder does not see title labels yet. A body edit reusing a stored title label is refused by the server as `TEMPLATE_PARSE_FAILED` (`duplicate_ask_label` in the body, no `area` param) and renders through the existing error line.
- `features/fill-template-answers/model/answers.ts`:
  - `answerFields` calls T327's `templateAskFields(template.titleArea, template.body, TEMPLATE_PARSE_OPTIONS)` instead of `askFields(template.body, …)`;
  - the doc's "in BODY order" becomes "title area first, then body";
  - answers still match by label, and `toAnswerPatch`, `withAnswer` and `pages/editor/ui/DraftEditor.tsx` stay unchanged.
- `frontend/src/test/templates.ts`:
  - `FakeTemplateRow.titleArea?: string`;
  - `Row.titleArea: string`, defaulting to `''`;
  - `creates` and `updates` records gain `titleArea` exactly as it arrived;
  - CreateTemplate stores `req.titleArea.trim()`;
  - UpdateTemplate sets `row.titleArea = req.titleArea.trim()` only when `req.titleArea !== undefined`, a presence rule like the server's;
  - `toProto` carries it through the row spread.
- The only `Template` literal in FE tests is the `template()` helper in `answers.test.ts`, which gains a `titleArea` (default `''`). Page tests build `FakeTemplateRow`s, whose new field is optional.
- Out of scope, all owned by T340:
  - the builder and 원문 UI;
  - dirty tracking of the title;
  - the `parseTemplate` save gate and failure routing;
  - the FE `area` param spec.
