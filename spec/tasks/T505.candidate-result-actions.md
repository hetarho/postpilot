## goal
Offer candidate-specific content application and active-model adoption after a new comparison's ranking is submitted or skipped.

## acceptance
- [ ] New blind comparisons offer no apply/adopt action before completion. After completion, each successful candidate can be selected explicitly for an allowed action without presenting that selection as a quality verdict; failed candidates cannot be used.
- [ ] Editor write results offer apply and apply-plus-adopt for the selected candidate, preserving its storyline and content; until successful application the pending-result link and ordinary-generation guard remain visible. A failed apply/adopt offers a retry for the same candidate, with no duplicate post write or repeat adoption.
- [ ] Lab post comparisons offer one candidate's output application only while the source post is draft/review, and any successful candidate's model adoption independently. Voice comparisons offer adoption only. Published/finalized post restrictions, changed/deleted voice, unavailable model and once-only action guards are explained in place from server reasons.
- [ ] After application or adoption, the detail shows the actual candidate used and persisted timestamps. Legacy winner-based records continue to use their existing actions. FE tests cover every origin/stage, two/five candidates, retries, post status changes, voice deletion, reload and legacy records; run ARCH-25 verification.

## impl notes
- Add entity hooks for T501's `ApplyCandidateOutput` and `AdoptCandidateModel`, passing the opaque candidate id the owner selected. Keep old winner RPC hooks for legacy records. The server, not the client, decides eligibility and idempotency; client-side disabled states are explanatory affordances.
- Rework `ExperimentActions` around a selected candidate and the new completed status. Separate ranking completion from result actions: button presses never submit a rank or badge, and submitting a ranking never invokes apply/adopt.
- Preserve the existing owner-query invalidation and post/editor navigation context. For an editor apply-plus-adopt retry, the persisted requested candidate id and adoption marker must drive the button, not whichever candidate the phone switch currently displays.
- Keep all failure and success notices adjacent to their controls; use the existing `shared/ui` action bar, buttons and localized reasons.
