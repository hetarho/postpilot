# T352 A durable generate carries its frozen memories into the write prompt
> st:todo | ssot:MEM-19 MEM-20 MEM-21 MEM-22 GEN-15 ARCH-24 | base:MEM@1 GEN@10 ARCH@9 | dep:-

## goal
- The memories StartGeneration froze into the payload reach the durable write prompt's `[기억]` section, as MEM-19/20 decide; today `Generate` drops them, so a post with `기억 사용` on is written as if it were off.

## acceptance
- [ ] A durable generate whose `GenerateJob.Memories` holds texts builds a write prompt whose per-post half carries one `[기억]` section with exactly those texts in payload order, closed by `memoryPrecedence`; the system half is byte-identical to the same run without memories (MEM-20).
- [ ] The drain uses the payload, never a live read: memories changed or deleted between the enqueue and the drain do not change that run's prompt, and the memory port is not called by `Generate`.
- [ ] A job with no memories (option off, or a payload written before memories existed) builds a prompt byte-identical to `write_prompt_no_template.golden`'s path today.
- [ ] A revision still carries no memories (MEM-22): `Revise` is untouched.
- [ ] Tests: `internal/generation/memory_test.go` new `TestADurableGenerateCarriesItsFrozenMemories` (Start with the option on and a recording memory port, replace the port's answer, then `svc.Generate` with the frozen `GenerateJob.Memories`; the write request's `Messages[0].Parts[0].Text` contains `[기억]` and both frozen texts, not the replaced ones; the port recorded one call, from Start) and `TestADurableGenerateWithoutMemoriesIsUnchanged` (a `GenerateJob` without memories carries no `[기억]` bytes).
- [ ] Verify: `cd backend && test -z "$(gofmt -l .)" && go vet ./... && go build ./... && go test -timeout 30m ./...`
