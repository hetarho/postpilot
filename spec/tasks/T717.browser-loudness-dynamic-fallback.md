# T717 Reach the clip loudness target on transient-heavy audio in the browser

## goal
A browser final render with source sound meets CDS-35's −16 LUFS / −1.5 dBTP / 11 LU mix on real phone audio instead of refusing it, as the server's loudnorm dynamic fallback does.

## acceptance
- [ ] When one linear gain cannot reach −16 LUFS ±1 under the −1.5 dBTP ceiling, the browser normalizer applies a bounded true-peak limiter (lookahead, attack/release smoothing) and re-measures until the integrated loudness is within ±1 LU and the true peak at or below the ceiling; audio that one gain already satisfies is unchanged from today.
- [ ] Unit tests in shared/lib/media/audio/loudness.test.ts cover (replacing 'preserves the peak ceiling instead of compressing a high-crest signal', which pinned the refused one-gain shortfall): a transient-heavy synthetic mix (short +18 dB clicks over speech-level noise) reaching the target, an already-compliant mix staying linear (gain only, bit-identical to the current path), silence staying silent, and a mix whose loudness range exceeds 11 LU still refusing with AUDIO_LOUDNESS_RANGE_UNSUPPORTED.
- [ ] render-clip-browser audio tests keep refusing an encoded track outside ±1 LU or above the ceiling (CLIP_BROWSER_AUDIO_AUDIO); affected FE type/lint/format checks pass.
- [ ] The private owner-original diagnostic (4 HLG HEVC cuts with sound, Windows Chrome) that measured −20.97 LUFS / −1.54 dBTP on 261029 now passes browserRenderVerdict, with the measured loudness, true peak and range recorded beside docs/qa/browser-render-windows-chrome-261029.json.

## impl notes
- Keep `normalizeLoudness48k(channels, targetLUFS, ceilingDBTP)` as the single entry (processing.worker.ts `normalize` request and the audio-range diagnostic call it). Linear gain first, exactly as now; only when `targetLUFS - before > ceilingDBTP - peak` (the ceiling binds) run the limiter path.
- Limiter: gain to the target, then a lookahead peak limiter on the sample-domain envelope with the existing 4x `truePeak48k` estimate as the check (lookahead ≈ 1.5 ms, attack within the lookahead, release ≈ 100 ms, ceiling a small margin below `ceilingDBTP`); re-measure with `integratedLoudness48k` and raise the pre-gain by the shortfall, at most a few bounded iterations. Name these as constants in loudness.ts; do not add a dependency.
- Return the same shape plus a flag/name of the applied mode so diagnostics can tell linear from limited output; nothing downstream may treat limited output as a different verdict.
- Bound work: the limiter runs once per render over the already-reserved mix (`CLIP_AUDIO_PROCESSING.maxPcmBytes`), allocates at most one envelope buffer, and checks the abort signal between iterations.
- The server path is unchanged; browser/native output parity stays measured, not assumed (ARCH-67). This does not open finalRender readiness or any T604 gate.
