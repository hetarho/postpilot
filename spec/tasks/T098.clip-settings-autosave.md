# T098 The clip settings autosave and lose their save button
> st:todo | ssot:CLIP-39 POST-4 THEME-39 | base:CLIP@5 POST@5 ARCH@2 | dep:T097

## goal
The settings on `/clips/$clipId` autosave on a pause like a draft's title and memo, so the screen loses its 저장 button, its dirty gate on 생성 and its leave-confirmation dialog, while `/clips/new` keeps one 클립 만들기.

## acceptance
- [ ] `shared/lib/save-state`: `SaveState` (`idle | dirty | saving | saved | error`), `SaveStatusState` and `useSaveStatus` lifted out of `features/save-draft` unchanged in behaviour — labels stay in the `common` namespace, the settled-quiet timer stays `SAVE_STATUS_SETTLED_MS`, the during-render adjustment stays; `features/save-draft` re-exports from there and every existing post autosave and `EditorStatus` test passes untouched
- [ ] `features/edit-clip-project/model/useClipProjectAutosave.ts`: debounced at `AUTOSAVE_DEBOUNCE_MS` after each pause, one save in flight at a time with the latest draft queued behind it, retry on failure with `AUTOSAVE_RETRY_BASE_MS` → `AUTOSAVE_RETRY_MAX_MS` backoff, a `SaveState` for the status line, and a `flush()` that resolves once the queue is empty
- [ ] an invalid draft is never sent: the existing `validClipProject` gate decides what is queued, and an invalid field reports through its own `FieldMessage` as it does now while the status line says nothing new
- [ ] `ClipProjectForm` on an existing project renders no 저장 button, no `useBlocker` dialog and no `beforeunload`, and its `onSaveStateChange`/`showStatus`/`status` props go — the page's one status line is the only place a save is reported (CLIP-38)
- [ ] `생성` no longer requires `!dirty`: `ClipApprovalAction` is gated on validity and the models alone, and `useGenerateClip.start` awaits `flush()` before it quotes and approves, so the approved ceiling is priced on the saved project
- [ ] a save that keeps failing leaves the status line in its failing state and does not block 생성 — the approval's own `flush()` rejection is what refuses it, reported through the existing failure surface
- [ ] `/clips/new` keeps exactly one committing action, 클립 만들기, in its own `ActionBar`, still carrying the ratio; its unsaved-input `useBlocker` dialog stays, and nothing about `CreateClipProject` or `ProjectPatch` changes
- [ ] the correction draft is untouched: `useClipCorrection` keeps its explicit 저장, its revision check and its own blocker (CLIP-17, CLIP-39 covers the settings only)
- [ ] vitest: a pause saving once for several keystrokes, a save in flight queueing the next draft rather than racing it, a failed save retrying with backoff and reporting `error`, `flush()` resolving before the approval quotes, an invalid draft never reaching the RPC, no 저장 button and no leave dialog on an existing project, 클립 만들기 still present on `/clips/new`
- [ ] `pnpm --filter ./frontend test` · `pnpm lint` · `pnpm lint:fsd` · `pnpm lint:style:probe && pnpm lint:style` · `pnpm build:web` (ARCH-25)

## impl notes
- the save-state shape moves to `shared/lib` because two slices now need it and same-layer cross-import is forbidden (ARCH-13); it is already domain-agnostic — `useSaveStatus` reads the `common` namespace, not `posts` — so the lift is a move, not a rewrite, and the post's tests are the regression proof
- the autosave itself does NOT move to `shared`: it calls `UpdateClipProject` with a clip draft, so it belongs to the feature that owns the form (ARCH-14). What it copies from `features/save-draft` is the queue's semantics — debounce, one in flight, latest-wins, backoff — not its code
- `/clips/new` keeps a button because the ratio it carries can never be changed again (CLIP-9) and the server has no representation for changing it (`// Ratio deliberately has no update representation.` in `clip/types.go`). Minting a project from an incidental first keystroke would freeze a ratio the user never chose, so the create screen is the one place a commit is explicit
- `flush()` before the quote, not before the button is enabled: a dirty gate is a refusal the user has to clear by waiting, which is exactly what POST-4's autosave exists to avoid. The approval already has an await point, so the flush costs nothing visible
- no BE or proto work: `UpdateClipProject` is already idempotent per field and `UpdateProject` refuses while a job is active (`ErrBusy`), which the autosave surfaces as a failed save rather than retrying forever — treat `ErrBusy` as terminal for the queue and let the next edit start a new one
