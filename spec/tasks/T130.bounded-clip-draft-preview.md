## goal
Provide a reusable draft player that shows current footage and server-shaped text without exporting the whole clip.

## acceptance
- [ ] The player renders selected source ranges with the current draft crop and text intervals, seeks on the output timeline and keeps a rendered-result comparison explicitly separate.
- [ ] Server-prepared overlay assets use the same font shaping/layout as export and are keyed by draft content; stale responses never paint an older edit as current text.
- [ ] Reload reuses T133 retained originals, while expired playback URLs refresh once without extending retention; missing source bytes, unsupported local codecs, preview preparation errors and final-only contrast/audio differences have explicit states while text editing stays available.
- [ ] Preparation calls are owner-scoped, credit-free and bounded, consume no LLM work, persist no source media and cannot change the edit plan, result or job state.
- [ ] Unit/RPC/browser tests cover all ratios, cut mapping across fades, 300 ms rapid cues, output-level fixed text, stale request races, seek boundaries, unavailable media and asset cleanup.
- [ ] Run the applicable local ARCH-25 through ARCH-29 checks, deterministic proto/SQL regeneration when changed, and spec lint; use a before/after generation snapshot when unrelated generated changes already exist.

## impl notes
- Add PrepareClipPreview as an owned unary RPC over project ID, expected saved revision, current correction draft hash/body and a bounded requested element-ID page. Reuse T128 validation/layout and resvg to return cropped transparent PNG bytes with exact canvas coordinates, dimensions, output intervals, motion and typed parity flags; return no arbitrary HTML/SVG from user text.
- Keep preparation source-free and limited to 8 overlay assets / 4 MiB per response, 512 KiB per asset, a 5 s deadline and one rasterization preparation per owner at a time; cap total request body under the existing RPC limit and expose a typed too-large/busy refusal rather than truncating text. Page assets for the selected cut and next cut, with a 32 MiB client LRU and revocation on eviction/unmount. Media-source contrast adaptation remains explicitly final-render-dependent when no verified ground is available.
- Implement the reusable player in entities/clip-project/ui with pure output-to-source mapping in its model. Prefer matching local object URLs through a source-access interface; consume T133 owner-authorized temporary playback URLs for unexpired originals after reload, without making the player own retention or upload.
- Use two native video elements at most for current/next cut, CSS crop and transparent overlay images positioned from the manifest; bind the playhead to media frame time using requestVideoFrameCallback when available, with requestAnimationFrame/currentTime fallback and seeked synchronization. Do not re-create the final encoder or introduce a video-editor framework.
- Debounce content preparation by 250 ms, cancel obsolete requests and require the response draft hash to match. While new glyph assets are pending, identify that preview as updating; never reuse old burned-in result pixels as new draft text. Local trim/seek changes reuse already valid assets when the content/layout key agrees.
- Browser timing is best-effort rather than a frame-accurate export guarantee; compare requested media time to displayed frame metadata and identify missing precision. Final audio normalisation and source-dependent contrast may differ and must remain labelled in preview capability metadata.
- API references checked during task design: https://developer.mozilla.org/en-US/docs/Web/API/HTMLVideoElement/requestVideoFrameCallback and https://developer.mozilla.org/en-US/docs/Web/API/HTMLMediaElement/currentTime. Recheck browser coverage under ARCH-33 during implementation; no new dependency is required.
