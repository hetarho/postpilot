# T394 voucher lot kind and expiring-first consumption order
> st:todo | ssot:QUOTA-9 QUOTA-12 QUOTA-58 GIFT-11 GIFT-13 | base:QUOTA@20 GIFT@2 | dep:-

## goal
Add the `voucher` credit lot kind with the usage behaviour the voucher context will call, and switch consumption to expiring lots first.

## acceptance
- [ ] a migration widens `credit_lots.kind` to `monthly · bonus · purchased · voucher`, and every existing row survives with its kind, amounts and expiry unchanged
- [ ] `LotsInConsumptionOrder` returns every non-purchased lot that has an expiry first, ordered by `expires_at` then `created_at` then `id`; never-expiring `bonus` lots come next and `purchased` lots come last
- [ ] `usage.Service.OpenVoucherLot(ctx, userID, credits, expiresAt) (lotID, error)` opens one `voucher` lot with `granted = remaining = credits` and refuses an empty user, credits ≤ 0 or a zero expiry
- [ ] `usage.Service.ExpireVoucherLot(ctx, lotID, at) error` moves a `voucher` lot's `expires_at` to `at` only when the lot's current expiry is later than `at`. It is a no-op on an already-expired lot and refuses any other kind
- [ ] after an expiry, the lot's `remaining` stays stored as history but counts toward no balance and no hold. A settlement refund that lands in that lot afterwards does not bring the credits back
- [ ] `usage.Service.VoucherLotRemaining(ctx, lotIDs, at) (map[string]int, error)` reads on the read pool and returns each lot's `remaining`, or 0 once the lot has expired at `at`
- [ ] GetMyPlan lists a voucher lot with kind `voucher`. The FE `CreditLot['kind']` union and the mapper accept `voucher`, and the account menu labels it (ko 이용권 / en Voucher)
- [ ] Go tests cover the migration, the new consumption order and the three new methods. Order cases:
    - a voucher expiring before the monthly lot burns first
    - an expiring bonus burns before a never-expiring bonus
    - purchased burns last
    - a hold against a voucher that is then expired returns nothing spendable on refund
- [ ] FE tests cover the account-menu label and the mapper
- [ ] ARCH-25, ARCH-26 and ARCH-28 pass

## impl notes
- Migration: take the next free number under `backend/internal/platform/db/migrations` at implementation time. Parallel sessions race for numbers, so re-check just before writing.
    - Copy 0027's rebuild shape exactly: `-- +goose NO TRANSACTION`, `PRAGMA foreign_keys=OFF`, explicit `BEGIN/COMMIT`, the `foreign_key_check` guard table, then `PRAGMA foreign_keys=ON`.
    - Recreate `idx_credit_lots_consumption ON credit_lots(user_id, kind, expires_at, created_at)` unchanged.
    - Down: fold `voucher` rows into `bonus`, keeping their expiry, the same way 0027 folds `purchased`.
- New order in `store/queries/usage.sql`: `ORDER BY CASE WHEN kind = 'purchased' THEN 2 WHEN expires_at IS NULL THEN 1 ELSE 0 END, expires_at, created_at, id`.
    - Rewrite the query's comment to state the new rule and its reason (a credit that can lapse burns before one that cannot, and a purchase still burns last).
    - Keep every comment in the file ASCII: sqlc slices the query text by byte offset, so one multi-byte character breaks codegen for the whole file.
- New queries:
    - `ExpireVoucherLot :execrows`: `UPDATE credit_lots SET expires_at = ? WHERE id = ? AND kind = 'voucher' AND expires_at > ?`
    - `VoucherLots :many`: `SELECT id, remaining, expires_at FROM credit_lots WHERE id IN (sqlc.slice('ids')) AND kind = 'voucher'`, read pool like `UntouchedPurchasedLots`.
- Voiding by expiry, not by zeroing `remaining`: `RefundToLot` adds back into any lot up to `granted`, so zeroing would let an open hold's settlement resurrect revoked credits. Expiry is already read-time (QUOTA-12), so a late refund is inert without a new column.
- `usage.go`:
    - add `LotVoucher LotKind = "voucher"`
    - rewrite the `LotKind` and `Lot.ExpiresAt` comments ("within one kind" no longer holds)
- Lot ids: `voucher:` + the service's `newID()`, mirroring `purchased:`.
- `plan.proto` `CreditLot.kind` comment: list the four kinds and state that lots arrive in consumption order. Regenerate with `pnpm gen:proto` and never hand-edit its output (the generator normalizes trailing newlines itself).
- FE files:
    - `frontend/src/entities/plan/model/types.ts`: kind union + the order comment
    - `entities/plan/api/plan-mappers.ts`: `toLot` passes `voucher` through; unknown kinds still read as bonus
    - `widgets/account-menu/ui/AccountMenu.tsx`: `LOT_LABEL.voucher = 'Voucher'` and a `balance.lotVoucher` key in both locale resources (key parity is tested)
- Do not touch the `api grantcredits` path: it keeps creating `bonus` lots with an optional expiry, and those now burn with the expiring group.
