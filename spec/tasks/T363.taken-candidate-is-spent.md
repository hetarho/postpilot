# T363 A taken replacement candidate is spent
> st:todo | ssot:GEN-53 POST-79 | base:GEN@11 POST@14 | dep:T355 T362

## goal
Taking a phrase removes that candidate from the post's stored list in the same write that saves the content, so its mark never returns, even where the phrase contains its source (제주 → 제주도), and every other candidate keeps its mark.

## acceptance
- [ ] Wire: `SavePostContentRequest` gains `repeated int32 taken_candidates = 5` (4 stays reserved).
  - The values are indices into the post's stored replacement-candidate list as GetPost returned it at `expected_revision`.
  - The server removes every one of them in the same statement that saves the content: one transaction, one revision bump.
  - A duplicate, or any index outside the list, is `InvalidArgument` / `POST_CONTENT_INVALID`, and nothing is written.
  - An empty list is today's save.
  - An identical-content save still writes nothing, the indices included.
  - No other provenance is stored (POST-80).
- [ ] BE `post.Service.SaveContent(ctx, userID, slug, content, expectedRevision, taken []int)` checks, in order: the revision (stale → `ErrStaleContentRevision`), the indices (each in range, none repeated), the identical-content no-op, the published lock and content validation. Then one guarded write carries the remaining list.
- [ ] FE, the queue:
  - A take's index rides a content save whose content includes that take.
  - It is resolved against the candidate list at the revision that save carries, not the list the screen showed.
  - Takes and typing inside one debounce coalesce into ONE save carrying the union of their indices.
  - A take is never dropped, including across a failed save that later typing merged into.
  - After a save lands, its takes no longer resolve, so the next save carries only takes made since.
- [ ] FE, the screen: the taken mark is gone at once and never comes back, and the other marks stay.

- Why the queue keeps candidates by value and resolves them at send time, instead of holding raw indices or clearing the set when a save lands:
  - A take made against the screen's list can be sent at a later revision whose list is shorter, and a raw index would then name the wrong entry.
  - The machine retries whatever is pending, and pending may already have absorbed the draft in flight. If the set were cleared when that flight started, a failed flight's takes would be lost.
  - Resolving against the answered list gives the owner's behaviour without either hazard. The coalesced save carries the union, and once a save lands its takes stop resolving, so the next save carries only newer ones.
