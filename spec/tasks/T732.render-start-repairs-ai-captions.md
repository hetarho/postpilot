# T732 Repair or omit a refused writer caption at render start instead of refusing

## goal
A render (server or browser kind) of a plan whose writer-authored caption fails the start's own checks succeeds with that caption repaired or omitted and noticed, instead of `CLIP_COMPOSITION_INVALID`.

## acceptance
- [ ] `GenerationService.repairWriterCaptions` runs the start's element checks (ApplyCorrection over CorrectionFromPlan, ValidateCompositionEvidence, the project's design + HideDisclosure, RefuseUnrenderableRates, then ValidateRenderPlan or LayoutComposition) and loops: a `*composition.Problem` naming a caption with `Kind == "ai"`, no `OwnerEdited` and no owner caption first loses its Placement and Phrases, then on a second refusal is removed with one `AddPlanNotice(…, "omitted")`; any other refusal is returned unchanged; the loop is bounded.
- [ ] `startRenderWithBrowserVersion` calls it after the revision and active-job checks and before speech assets; a changed plan is saved through `store.SaveCorrection` at the requested revision, and admission continues on the saved project and its new revision.
- [ ] Notice reason is the refusal's own reason when the frontend names it (copy_limit, readability, rapid_readability, automatic_placement, invalid_interval, unsupported_glyph, safe_area), otherwise `dropped`.
- [ ] `caption_repair_test.go`: a writer caption the layout refuses is omitted with a notice and the next check passes; a placed writer caption is first freed and kept when that fits; an owner-edited caption still refuses; a non-caption refusal is returned unchanged.
- [ ] Existing render admission tests in `internal/clip/app`, `internal/clip/store` and `cmd/api` stay green.

## impl notes
- Narration captions are built with `Basis: "output-start"` and fixed times (`NarrationCaption`), so `AutomaticCompositionRepair` is always false for them. Generation's layout also writes a `Placement` onto every AI caption, which pins its anchor and style at the next layout. Any later difference therefore refuses with no ladder, e.g. a design selection changed in ①, a glyph fallback or a re-resolved interval. That is the observed `narration-2` refusal on prod (261102; the exact reason was not readable).
- ApplyCorrection reads the project's stored plan as the old plan: each check iteration sets `p.EditPlan` to the encoded candidate.
- Match the problem's ElementID against both `Resolved.Element.ID` and `Resolved.InstanceID`.
- The client already adopts a newer server revision when its draft is clean (`useClipCorrection` adopt), and the render flushes before starting, so no frontend change is required. A retried start naming the old revision meets `CLIP_PLAN_CONFLICT`, which is a definite refusal.
