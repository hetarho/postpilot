# T042 The r4 mutation vocabulary and the body mutations
> st:todo | ssot:PUBLISH-21 PUBLISH-36 PUBLISH-37 PUBLISH-19 PUBLISH-20 | base:PUBLISH@4 ARCH@2 | dep:T018

## goal
Replace the r3 mutation vocabulary with r4's, reorder `Prepare`'s plan to body → photos → settings, and implement `Apply` for the five body kinds against the live SmartEditor's verified mechanics.

## acceptance
- [ ] `MutationKind` drops `image_placeholder` and gains `open_settings`; the constant, its `Prepare` branch, its locator entry and every test that names it are gone, and no code path can emit it
- [ ] `Prepare` plans in exactly this order: `title` → the body blocks in manifest order → `upload_image` per photo in ordinal order → `open_settings` → `tags` → `category` → `visibility`; a plan that puts any body or image mutation after `open_settings` is refused by a `Prepare`-level assertion, not only by the driver (PUBLISH-37)
- [ ] `CDPPort.Apply` implements `title`, `text`, `heading`, `quote` and `list` as typed data only: it resolves the kind's versioned locator, requires exactly one match, reads that element's `getBoundingClientRect()` in the same reviewed script, dispatches one `Input.dispatchMouseEvent` press/release at it, discards the rect, and enters text with `Input.insertText`; no selector, script, coordinate, key sequence or native-dialog operation is accepted from the caller
- [ ] the caret rule is the paragraph's right edge, not its box centre: the click point is taken at 98 % of the resolved paragraph's own width so the caret lands at the text's end on a paragraph of any length, and a test on a long wrapped paragraph proves a centre click would have landed mid-text
- [ ] `heading` and `quote` convert the caret's paragraph through `button.se-text-format-toolbar-button` then `button.se-toolbar-option-text-format-{sectionTitle,quotation}-button`; `list` opens `button.se-list-bullet-toolbar-button` then `button.se-toolbar-option-list-{bullet,decimal}-button`; each asserts the caret's component kind before resolving the control, because the property toolbar carries the list control only while the caret sits in a text block
- [ ] a second and later `text` block is appended by `Input.dispatchKeyEvent` Enter followed by `Input.insertText`, and the projection counts PARAGRAPHS rather than `.se-component.se-text` nodes, since Enter appends a paragraph inside the same component
- [ ] `Publisher.mutate`'s post-condition still holds for every body kind: the snapshot token moves and the observed snapshot equals the expected one
- [ ] against a fake CDP editor, table-driven tests cover: each of the five kinds; a paragraph appended after another; a heading and a quote applied to the right paragraph; a list of three items; text that reads like a CSS selector, a `<script>`, a coordinate pair, a keystroke phrase or a setting label entering verbatim; a locator matching 0, 2 or a renamed control failing closed before the page is touched; and a mutation planned after `open_settings` being refused
- [ ] ARCH-27 passes

## impl notes
- every DOM fact here was verified live on 260907 and is recorded in T019's `## survey` section — read it before writing code; do not re-derive selectors
- the vocabulary is eleven kinds again by coincidence, not by design: `image_placeholder` out, `open_settings` in
- the format controls CONVERT the caret's paragraph rather than inserting a block, so `heading` and `quote` must be planned as "write the text, then convert", which is what `Prepare` already emits for text; `quote` must NOT use `button.se-insert-quotation-default-toolbar-button` even though it exists and inserts a fresh block — it also creates a `출처 입력` source placeholder that enters the projection and would have to be cleared
- the quotation's source placeholder and the image component's own control labels (`대표`, `오른쪽 정렬`, `사진 편집`, `작게`) are why the projection may never use `innerText` on a component; keep T018's per-kind extraction
- `open_settings` is implemented in T044; this task only reserves the constant, plans it last and refuses anything after it, so T042 and T044 can land in either order without a contract conflict
- `mutate`'s `before.LocatorMatches[kind] != 1` pre-check stays as it is for body kinds; the kinds whose locator is 0 until an earlier step ran are T043's and T044's problem and are documented there
- the paragraph-vs-component finding changes `semanticBlocks`: iterate `.se-text-paragraph` inside each text component, not the components
