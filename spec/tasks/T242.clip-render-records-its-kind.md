# T242 a render is started per kind and records the kind with its result
> st:doing@260918.knd | ssot:CLIP-153 CLIP-1 CLIP-20 CLIP-27 CLIP-73 CLIP-76 CLIP-78 CLIP-79 | base:CLIP@37 | dep:T241

## goal
Starting a render names the kind that will produce it, and the stored result carries the kind that did.

## acceptance
- [ ] `StartClipRender` takes the render kind and refuses an unknown one
- [ ] a stored result carries its kind and a legacy result reads as a server render
- [ ] a project read carries the kind its last successful render used, and a project with no result carries none — this is the kind CLIP-153 offers first
- [ ] a server render behaves exactly as it does today: a durable job under CLIP-78 with its focused view, its cancellation under CLIP-79 and its retention renewal under CLIP-73
- [ ] both kinds are credit-free and neither consumes a reservation
- [ ] finalization accepts a matching successful render of either kind
- [ ] go test: a server render records its kind; a legacy row reads as server; an unknown kind is refused before any work; a project read carries its last render's kind and a project with no result carries none
- [ ] verify: `cd backend && test -z "$(gofmt -l .)" && go vet ./... && go build ./... && go test ./...` (`-timeout 30m` for `clip/store`) · `pnpm gen:proto && git diff --exit-code -- backend/internal/gen frontend/src/shared/api/gen agent/internal/gen` · `pnpm gen:sql && git diff --exit-code -- backend` · `pnpm --filter ./frontend test` · `pnpm lint` · `pnpm lint:fsd` · `pnpm build:web`

## impl notes
- proto: `ClipRenderKind` enum (`CLIP_RENDER_KIND_SERVER`, `CLIP_RENDER_KIND_BROWSER`) on `StartClipRenderRequest` and on the result message; `UNSPECIFIED` is refused rather than defaulted, so an old client cannot start a render whose kind nobody recorded
- migration: one `render_kind TEXT NOT NULL DEFAULT 'server'` column on the result table; goose, `NNNN_<slug>.sql`, and the ASCII-only rule holds for the sqlc query files (a non-ASCII comment breaks `gen:sql` wholesale)
- this task wires the BROWSER kind through the contract but starts no browser render — T243 and the browser cluster own that; a browser-kind start is accepted by the schema and refused by the service with `unimplemented` until then
- the kind CLIP-153 offers first is read off the project's latest successful result (CLIP-1), which is the only render the project keeps — no separate `last_render_kind` column, since a result and the render that made it are the same row
- the project message carries the kind as an optional field: absent means the project has rendered nothing, which T247 turns into the browser kind rather than into a default of server
- `pnpm gen:proto` and `pnpm gen:sql` run through Docker (ARCH-28); generated code is committed and never hand-edited
