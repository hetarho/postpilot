# T392 ListPosts answers in pages and narrows on the server
> st:todo | ssot:POST-90 POST-91 POST-65 POST-66 POST-3 | base:POST@15 ARCH@11 | dep:-

## goal
ListPosts takes a page size, a page token, a search query and a status, and answers one keyset page of the caller's narrowed posts plus the token of the next, reading only the columns a row shows.

## acceptance
- [ ] proto `ListPostsRequest` gains `int32 page_size = 1`, `string page_token = 2`, `string query = 3`, `string status = 4`; `ListPostsResponse` gains `string next_page_token = 2`; `pnpm gen:proto` output is committed and the ARCH-28 diff check is clean
- [ ] `page_size` 0 answers every narrowed post with no next token (a client that sends `{}` sees exactly today's answer); 1..100 answers at most that many; above 100 is clamped to 100; negative is `InvalidArgument`
- [ ] the order is `updated_at DESC, slug DESC`; walking the tokens returns every narrowed post exactly once with no gap, including ties on `updated_at`
- [ ] a page token that does not decode is `InvalidArgument`; an empty token is the first page
- [ ] `status` empty is every status; `draft` `review` `finalized` `published` keep that status only; any other value is `InvalidArgument`
- [ ] `query` narrows by the POST-65 match (title as listed — the 가제, or `content.title` when the 가제 is blank — or any current tag) on the normalized query; a query that normalizes to empty narrows nothing; the query composes with `status` as AND; matches further down than any page size are found
- [ ] the list read no longer decodes the content JSON in Go; SQL reads only the listed columns plus `json_extract` of the content's `title` and `tags`
- [ ] active job, pending experiment, voice and template are resolved for the answered page only
- [ ] tests: store (keyset walk with `updated_at` ties, status filter, limit/unlimited), service (query normalization parity cases incl. `#제주`, `  제주  도`, `JEJU`→`jeju`; query+status AND; query match found past the first page; token round trip; bad token and bad status), rpc (request → service mapping, clamp, negative size, response token)
- [ ] ARCH-26 BE gate and ARCH-28 generated-code check pass; `pnpm --filter ./frontend test` and `pnpm build:web` still pass on the regenerated TS

## impl notes
- `page_size` 0 = unpaged keeps both deploy orders safe: an old FE against the new API sends `{}` and gets everything; the new FE against an old API gets everything with no token and simply never asks for more. It also serves `pages/ai-models` ModelComparisonPage, whose photo-post picker keeps reading the whole list through `usePosts()` (not a POST-90 screen). Clamp `listPostsPageSizeMax = 100` as an unexported service constant.
- Status travels as `string`, matching `PostSummary.status`; validate against the post package's status set (a `post.IsStatus`-style helper if one exists, else add one beside the status constants).
- Query normalization must equal the FE's `features/filter-posts/model/narrow.ts` `normalize` byte for byte in intent, same order: `strings.TrimSpace` → strip leading `#`s → collapse every whitespace run to one space → `strings.ToLower`. Put it in the post package as `normalizeListQuery` and the match as `summaryMatches(title string, tags []string, q string) bool` (substring on the normalized title, or any normalized tag containing it). The FE keeps its own copy only to name the matched tags on a row (T393).
- Where the text match runs: in Go, not SQL. SQLite `lower()` folds ASCII only and cannot collapse whitespace inside the stored text, so a SQL `LIKE` would disagree with POST-65 on exactly the cases the rule names. With a query: the store returns the status- and cursor-bounded rows unlimited (`LIMIT -1`), the service filters them and keeps `page_size + 1`. Without a query: the store applies `LIMIT page_size + 1` itself. The scan is per account and reads two short JSON paths, not the content; accepted for an account-sized list.
- sqlc query `ListPostSummariesByUser :many` replaces `ListPostsByUser` in `store/queries/posts.sql` (delete the old one; nothing else calls it):
  `SELECT slug, title, status, updated_at, voice_id, template_id, target_language, content_language, json_extract(content, '$.title') AS content_title, json_extract(content, '$.tags') AS content_tags FROM posts WHERE user_id = sqlc.arg(user_id) AND (sqlc.arg(status) = '' OR status = sqlc.arg(status)) AND (sqlc.arg(after_updated_at) = '' OR updated_at < sqlc.arg(after_updated_at) OR (updated_at = sqlc.arg(after_updated_at) AND slug < sqlc.arg(after_slug))) ORDER BY updated_at DESC, slug DESC LIMIT sqlc.arg(row_limit);`
  The `.sql` file must stay ASCII-only (sqlc breaks every statement in a file that holds one Hangul character). If sqlc types the two `json_extract` columns as `interface{}`, convert in the store with a type switch (`nil`, `string`, `[]byte`); `content_tags` is a JSON array text decoded with `json.Unmarshal` into `[]string`. The expanded OR form instead of a row-value comparison keeps sqlc's parser out of it.
- The cursor is the row's RAW stored `updated_at` string plus its slug, never the parsed time re-formatted: `parseTime` accepts rows written before `writeLayout` pinned the fraction width, and the ORDER BY compares the stored strings, so only the stored string keeps the keyset consistent with the order. Domain type `post.ListCursor{UpdatedAt, Slug string}`; the store returns it with each row (a `Cursor ListCursor` field on `post.Summary`, documented as the row's position in the list order, opaque outside the post package). Token = base64 RawURLEncoding of `updated_at + "\x00" + slug`; decode failure or a missing separator → `post.ErrInvalidListToken` → `InvalidArgument`.
- Port change: `PostStore.ListPosts(ctx, userID string, filter ListFilter) ([]Summary, error)` with `ListFilter{Status string; After *ListCursor; Limit int}` (Limit -1 = all); service `List(ctx, userID string, q ListQuery) (ListPage, error)` with `ListQuery{PageSize int; PageToken, Query, Status string}` and `ListPage{Summaries []Summary; NextPageToken string}`. Update `fake_test.go` and every other fake of the port to honour the filter the same way (order, status, cursor, limit) so service tests exercise the real contract.
- Next token: when more than `page_size` rows survive, answer the first `page_size` and encode the last answered row's cursor; otherwise empty.
- The N+1 `ActiveForPost` / `PendingForPost` calls now run over at most one page (or the whole list when unpaged, as today).
- No migration: `idx_posts_user_updated (user_id, updated_at)` already serves the keyset seek; the slug tiebreak only orders ties.
