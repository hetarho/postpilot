## impl notes
- Split from T604 (inbox 261111 decided T604). The harness shape follows docs/qa/browser-render-windows-chrome-261029.json, which drove the production path from a private entry; reuse frontend/src/test/browser-media/export-entry.ts or the comparison entry rather than a new production module.
- Serve from WSL with host `0.0.0.0`; Windows reaches it as `http://localhost:<port>` (Windows→WSL only, a secure context for WebCodecs). A server started with `watch: null` ignores edits, so restart on a new port and cacheDir after a change.
- Run the driver with the Windows Node over stdin, because a UNC script path fails the package lookup: `"/mnt/c/Program Files/nodejs/node.exe" - <args> < scripts/browser-render-comparison/windows-driver.cjs`, with a working directory on the Windows drive.
- Load playwright-core from the workspace through its UNC path, built from `wslpath -w` of the checkout plus `node_modules/.pnpm/playwright-core@<lockfile version>/node_modules/playwright-core`; never hard-code a user name. Executables: `C:\Program Files\Google\Chrome\Application\chrome.exe` and `C:\Program Files (x86)\Microsoft\Edge\Application\msedge.exe`.
- Launch with a temporary user-data directory and default arguments; never pass `ignoreDefaultArgs: true` or the owner's profile, which attaches to the owner's running browser. Close each browser at the end.
- Known Windows limits measured 261029: WebCodecs AAC encodes only at 96/128/160/192 kbps, and D3D11 HEVC frames report a null format. A failure caused by such a limit is a finding to record, not a reason to change product settings in this task.
- Integrated-GPU Windows, macOS Chrome reruns and lower-resource devices stay in T604 and reuse this driver.
