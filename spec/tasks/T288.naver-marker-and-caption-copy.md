# T288 the Naver photo marker is a number and the caption copies itself
> st:todo | ssot:EXPORT-5 EXPORT-24 EXPORT-4 EXPORT-9 EXPORT-12 ARCH-24 | base:EXPORT@3 | dep:-

## goal
Replace the Naver photo marker with `사진_<n>_사진` carrying neither filename nor caption, and give each caption its own copy control.

## acceptance
- [ ] `toNaver` emits `사진_<n>_사진` for Korean content and `photo_<n>_photo` for English, numbered from 1 in marker order, carrying neither the filename nor the caption
- [ ] an `IMAGE` block with an empty `file` still consumes its number, so later photos cannot shift against their markers
- [ ] video markers are byte-identical to today, caption included
- [ ] an unfilled template slot still renders bracketed and a test asserts it cannot be read as a photo marker now that the photo marker carries no filename
- [ ] each caption in the Naver preview is its own copy control under its photo, following the text-copy discipline (1500 ms confirmation, manual fallback, staleness invalidation); a block with no caption renders no control
- [ ] the manual fallback for a caption reveals a read-only field holding that caption and selects it, the way the Naver tab reveals its raw text field
- [ ] the photo copy control is named by its marker number and its filename
- [ ] Tistory, site and Markdown outputs are byte-identical (snapshot tests over the existing fixture)
- [ ] vitest covers the numbering, the empty-file hole, a caption copy and a caption fallback
- [ ] ARCH-25 passes

## impl notes
- `CopyTarget` gains `caption:${number}`; the number is the marker index, the same identity a photo copy already uses, so one file carrying two markers stays two independent captions
- `naverPhotoOrder` keeps returning one entry per marker including the empty one — the numbering and the strip must agree by position, which is the whole reason that function exists
- the caption leaves the marker, so nothing in the pasted body carries it any more; that is the point of EXPORT-24 and the panel's Naver guidance line has to say so
- i18n strings go into the export slice fragments, not a new namespace
