# T396 public gift page and redemption
> st:todo | ssot:GIFT-5 GIFT-7 GIFT-8 GIFT-9 GIFT-13 | base:GIFT@2 | dep:T395

## goal
Ship the public `/gift/$token` page: anyone sees what the voucher holds; a signed-in account redeems it; an anonymous visitor signs in or up and comes back to it.

## acceptance
- [ ] `/gift/$token` is a public route, a direct child of the root route beside `/about`. It deep-links anonymously and renders the voucher from `GetVoucher`
- [ ] the page renders each state:
    - redeemable: credits, "N일 동안 사용" days, the message or a default line, and the link's own expiry date
    - redeemed, expired, revoked and not found: each with its own copy and no redeem action
    - a network failure: the shared failure message
- [ ] signed in and redeemable: one `받기` button calls `RedeemVoucher`
    - success: shows the credits received and their expiry date, invalidates the plan/balance queries so the header figure updates, and offers a link to the signed-in home
    - a refusal (`VOUCHER_REDEEMED` / `EXPIRED` / `REVOKED`): shows that state's copy
- [ ] anonymous and redeemable: the page offers `로그인하고 받기` → `/login?redirect=/gift/<token>` and `가입하고 받기` → `/signup?redirect=/gift/<token>`, and records the token as a pending gift
- [ ] a pending gift survives the email-verification detour. On entering the authenticated layout with a pending gift under 24 h old, the app clears it and navigates (replace) to `/gift/<token>`. The gift page clears it once it reaches any terminal state or a redemption succeeds
- [ ] the page never redeems on open. The token is sent only in the RPC body and appears in no analytics, title or console output
- [ ] a `gift` i18n namespace in ko and en at key parity lives in the page slice's `config`
- [ ] vitest covers:
    - each render state
    - signed-in redeem success and refusal
    - the anonymous actions and their `redirect` targets
    - pending-gift storage (including storage that throws)
    - the authenticated-layout hand-back
    - a router test proving `/gift/x` resolves anonymously
- [ ] ARCH-25 passes

## impl notes
- FSD placement (ARCH-13/14/15):
    - `entities/voucher`: `model/types.ts` (a domain `Voucher` view and state union), `api/` with the Connect calls and mappers, reaching `shared/api` only (ARCH-17)
    - `features/redeem-voucher`: the redeem mutation, the button and the pending-gift store in `model/pendingGift.ts`
    - `pages/gift`: `GiftPage` and its search/params
    - route group `app/routes/gift.ts` added to `tree.ts` beside `marketing`
- Route: no `beforeLoad` guard. A `loader` resolves `hasActivePublicSession(context)` (the same probe `/login` uses; it swallows outages) and passes `signedIn` to the page; a stale probe only picks which buttons show, since the server decides on redeem.
- Pending gift storage:
    - key `postpilot.pendingGift` in `localStorage`, value `{ token, savedAt }`; 24 h freshness matches the verification link TTL (`auth.VerifyLinkTTL`)
    - `localStorage` rather than `sessionStorage` because the verification link opens a new tab
    - every read and write sits in try/catch and a failure behaves as "no pending gift" (the visitor can reopen the link from the message it came in)
- Hand-back: `app/routes/AuthenticatedLayout.tsx` reads the pending gift once on mount and navigates with `replace: true`. The gift route sits outside the authenticated layout, so it cannot loop.
- The link path is built with `isInAppPath`-safe values only. The token is URL-encoded in both the route path and the redirect param.
- Default message line (ko): "Postpilot 이용권이 도착했어요"; en: "A Postpilot voucher for you". Dates are formatted with i18next like the account menu's lot expiries.
- Invalidate the query keys the header credit control and `/plans` read (see `entities/plan` query keys) after a successful redeem.
- Controls come from `shared/ui` primitives only (ARCH-20); a single column works at 320 px (THEME floors).
