# T052 A bounded provider webhook
> st:todo | ssot:ARCH-6 ARCH-23 | base:ARCH@2 | dep:-

## goal
Bound how often an anonymous POST to `/webhooks/toss` can spend the product's provider quota, and stop the same provider state from being appended twice.

## acceptance
- [ ] the webhook route is rate-limited per client IP before the handler issues any outbound provider call, using the same throttle the authenticated public writes use
- [ ] a refused request answers without calling the provider and without writing a row
- [ ] the client IP is resolved the same way the auth interceptor resolves it, honouring the configured client-IP header
- [ ] `provider_notifications` gains a uniqueness rule over the provider event's identity so a repeat of the same state is not appended again, and the insert is written to tolerate that conflict rather than fail on it
- [ ] a genuine new state for the same order is still recorded
- [ ] a well-formed notification for a payment the provider does not know still answers without writing a row, as it does today
- [ ] tests cover: a burst past the limit being refused with no provider call; the same notification delivered twice producing one row; two different states for one order producing two rows; and the throttle isolating one IP from another
- [ ] ARCH-26 passes

## impl notes
- from review/diff-260908 F6
- the defect: `rpcserver.Options.Routes` mounts the route on the bare mux and its own comment says these handlers bypass Connect interceptors by design, so the auth interceptor's throttle never sees it. Every anonymous POST therefore forces one `GET /v1/payments/orders/<id>` against Toss, and a guessed real order id appends to a table with no dedupe key and no retention
- the handler is already right about trust — it re-reads the payment from the provider and never persists facts from the public body — so this task adds only the bound, and changes nothing about what is believed
- reuse rather than duplicate: add a webhook class to `auth`'s `throttleRules` and wrap the route in `cmd/api` with a small middleware that calls `throttle.Allow(class, auth.ClientIP(header, peerAddr, cfg.ClientIPHeader), time.Now())` before delegating. Wiring in the composition root is where ARCH-6 puts it, and it keeps `billing/rpc` from importing `auth`, which ARCH-7 would not allow
- the dedupe key is `(provider, order_id, status, event_type)`: Toss's ordinary payment webhook carries no event id of its own, so the state transition itself is the only available identity. The cost is that a true repeat of one transition is recorded once — acceptable, since the first arrival's `received_at` is the fact that matters
- retention is deliberately NOT in this task: nothing in ARCH or BILLING states a retention rule for provider notifications, and inventing one here would be a policy decision rather than an implementation
