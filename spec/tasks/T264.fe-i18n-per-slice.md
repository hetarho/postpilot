# T264 i18n namespaces assembled from slice-owned fragments
> st:todo | ssot:ARCH-16 ARCH-15 ARCH-24 | base:ARCH@5 | dep:-

## goal
Let each slice own its `{ko,en}` strings in a `config/i18n.ts` fragment and make `app/providers/i18n` assemble the 14 namespaces from fragments, moving every non-clip namespace out of `app/`.

## acceptance
- [ ] a fragment is `export const i18n = { namespace: 'posts', ko: {...}, en: {...} } as const satisfies I18nFragment`; `app/providers/i18n/resources/index.ts` imports fragments via an explicit list and merges them per namespace; a duplicate key across two fragments of one namespace fails `resources.test.ts`
- [ ] `posts`, `voices`, `templates`, `guidelines`, `models`, `plans`, `billing`, `publishing` no longer have files under `app/providers/i18n/resources/{ko,en}`; their keys live in the slice that renders them (lowest layer that uses the key wins; a key used across domains moves to `common`)
- [ ] `common`, `errors`, `nav`, `auth`, `marketing` stay app-level fragments under `app/providers/i18n/resources` (they are cross-cutting or belong to `app/routes`)
- [ ] `clips` stays in `app/` for now with a comment naming T265; the `RESOURCE_NAMESPACES` contract and every `useTranslation('<ns>')` call are unchanged
- [ ] `resources.test.ts` keeps: exact namespace set, ko/en key parity + placeholder parity, failure-reason coverage, typed keys; plus the new no-duplicate-fragment-key check
- [ ] steiger accepts a `config` segment holding `i18n.ts` in every layer used; ARCH-18 holds (fragments import nothing)
- [ ] behaviour unchanged: all FE tests pass; ARCH-25 passes

## impl notes
- from review/arch-260919 F3 (infrastructure + non-clip namespaces)
- namespaces stay domain-shaped so no `t()` call changes; only the file that holds the string moves — the churn problem is the file, not the key scheme
- ownership rule for a key: `grep -rl` its usages; owner = the single slice using it, else the lowest-layer slice among the users, else `common`; write the script into the task result so T265 reuses it
- typed keys: keep `resources.test.ts`'s `exposes typed translation keys from the canonical resource shape` by deriving the namespace type from the merged object, not from the fragments
- app importing slices is downward (ARCH-13), so the fragment list in `app/providers/i18n` is legal; it is still one file every new slice touches, but a one-line import instead of a 1.1k-line edit
