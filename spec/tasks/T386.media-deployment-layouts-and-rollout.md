## goal
Deliver colocated and remote worker configuration and rollout tooling with the current CPU VPS as the default, without provisioning or moving a live service.

## acceptance
- [ ] The default configuration starts the existing API/SQLite/Caddy layout plus one CPU worker without NVIDIA dependencies; an explicit remote configuration prepares the API/DB VPS and a separate worker-only stack, with no application code edit or database move between layouts.
- [ ] Production build/push produces separately addressable immutable API and worker images; the existing API-only `compose pull/up api` rollout is extended to the services actually selected by the layout.
- [ ] Each service's image/version and env backup is restored consistently on a supported rollback; mixed API/worker protocol or renderer/asset incompatibility is detected before work is admitted.
- [ ] The internal listener is private: colocated traffic stays on a private Compose network, and remote access uses loopback host binding plus an explicitly configured Tailscale serve path or equivalent private TLS endpoint; public Caddy never exposes worker operations.
- [ ] The remote worker env contains its API URL, unique worker credential, selected image, acceleration and resource settings, with no DB, provider, billing or broad R2 credentials.
- [ ] Current-VPS upgrade and rollback commands are documented; colocated/remote env examples and service/file selections are available for the complete three-environment guide in T388.
- [ ] Deployment-script tests exercise colocated and remote selection, pull/start/health failure, env/tag restoration, protocol mismatch, old-binary rollback hazards, missing GPU configuration on a CPU host and private port binding; Compose configurations validate.
- [ ] Validation uses local fixtures and mocked deployment commands; completing this task requires no production SSH, friend-PC setup, remote-host installation or live topology migration.

## impl notes
- Retain docker-compose.prod.yml as the API base, add a colocated worker override, and add `deploy/media/docker-compose.yml` for a standalone worker. Choose files/services in the rollout script from MEDIA_TOPOLOGY=colocated|remote; default colocated in the completed configuration. Writing/testing rollout tooling does not execute a production deployment.
- Keep IMAGE_TAG for the API and add MEDIA_WORKER_IMAGE_TAG for the worker. The worker image is `ghcr.io/hetarho/postpilot-media-worker`; CI builds it from the matching target but does not SSH to a friend's machine. That machine pulls/runs the documented pinned image itself.
- Use a separate worker env file and a private media network on the VPS. MEDIA_INTERNAL_ADDR is disabled while the legacy path is the default and set to :9000 for worker layouts; publish only 127.0.0.1:9000 when remote private-network ingress is configured.
- Topology selects explicit Compose file lists rather than relying on an inactive GPU profile to hide required device/runtime fields. T388 adds NVIDIA setup examples for both colocated and standalone workers; CPU startup must not try to reserve a GPU and diagnostics never claim production GPU readiness.
- Provide MEDIA_WORKER_CPUS and MEDIA_WORKER_MEMORY as explicit per-host container limits and preserve finite workspace limits. Example values are starting points, not a claim that the shared VPS has spare capacity; T387 records the measured envelope and fails preflight on insufficient memory/disk.
- Worker credentials are unique per deployment/worker, generated during provisioning and stored in restrictive env files. Changing topology never reuses a user session or distributes the API's complete .env.
- The documented upgrade/drain procedure preserves the DB volume. Draining stops new claims, waits for active work to finish or be safely relinquished, then replaces/stops that worker; do not use --remove-orphans to kill a busy worker implicitly. The operator runs this procedure when deploying, outside task verification.
- API /health remains independent of remote-worker uptime so a powered-off PC does not turn the web/API into an outage. First activation requires a successful compatible-worker smoke; routine remote-mode API rollout checks version compatibility separately from transient worker liveness.
- Rollback to a pre-worker API is unsafe while parked jobs exist because its boot sweep fails all running jobs. Record a minimum compatible rollback version and reject such a rollback unless a deliberate drain/maintenance procedure proved no durable remote work remains; never delete wait records or rewind the DB to force compatibility.
- Document the initial supported remote host as Linux + Docker. NVIDIA driver/toolkit/device exposure is a one-time installation for the later GPU profile; a Windows PC needs a separately verified Linux/WSL2 setup and is not silently claimed as supported.
- Update DEPLOY.md with the current CPU VPS procedure and backend/build/RENDER.md with the implemented runtime contract. T388 completes the three-environment matrix and README entry point. Mark root RENDER-INFRA-PLAN.md as historical where it contradicts implemented contracts; do not reuse its old timings as current measurements.
- Official deployment reference checked 2026-09-25: https://docs.docker.com/compose/how-tos/profiles/ .
