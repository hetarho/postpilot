# T033 Google sign-in: SPA-initiated code + PKCE, exchanged by the backend into a session
> st:todo | ssot:AUTH-39 AUTH-1 AUTH-17 AUTH-30 AUTH-33 AUTH-34 AUTH-36 AUTH-8 ARCH-6 ARCH-21 ARCH-33 | base:AUTH@2 ARCH@2 | dep:T032

## goal
Add Google as the one social provider: a verified Google address joins the matching account or creates a verified one, an unverified or absent address is refused, and the exchange is a public Connect procedure that sets the same cookie Login does.

## acceptance
- [ ] `auth.proto`: `SignInWithGoogle{code, code_verifier, redirect_uri}` → `SignInWithGoogleResponse{User user, Plan plan}` (the Login response shape); `pnpm gen:proto` committed; `publicProcedures` gains it and `throttledProcedures` maps it to `google` (T032)
- [ ] `auth/ports.go`: `type GoogleClaims struct{ Subject, Email string; EmailVerified bool }` and `type GoogleIdentity interface{ Exchange(ctx, code, codeVerifier, redirectURI string) (GoogleClaims, error) }`; `auth.Service.SetGoogle(GoogleIdentity)`; a nil identity makes the procedure answer `GOOGLE_SIGNIN_DISABLED` (failed_precondition)
- [ ] `backend/internal/googleauth`: `googleauth.New(clientID, clientSecret string, client *http.Client)` posts `grant_type=authorization_code`, `code`, `code_verifier`, `redirect_uri`, `client_id`, `client_secret` to `https://oauth2.googleapis.com/token`, decodes the `id_token` payload and validates `iss ∈ {accounts.google.com, https://accounts.google.com}`, `aud == clientID`, `exp > now`, then returns `sub`, `email`, `email_verified`; a non-2xx token response, a missing id_token, a wrong `aud` or an expired token each return an error; httptest-based tests cover the request body and every refusal ← read Google's current OAuth 2.0 for web server apps + OIDC docs first (ARCH-33) and copy parameter names from there
- [ ] `auth.Service.SignInWithGoogle(ctx, claims)`: refuses `!EmailVerified || Email == ""` with `ErrGoogleEmailUnverified` → `GOOGLE_EMAIL_UNVERIFIED` (failed_precondition); looks the account up by `google_subject`, else by the normalized email: an existing account is JOINED (its `google_subject` set; `email_verified_at` set if it was NULL) and never duplicated; an email that matches an account already bound to a DIFFERENT Google subject is refused with `GOOGLE_ACCOUNT_MISMATCH`; no account → one is created with `ID = Email = email`, `password_hash = ''`, `email_verified_at = now`, `google_subject`, plan `free`, then the T030 bootstraps run; the result is a session issued exactly as `Login` issues one (raw token returned once, cookie set by the handler with the identical attributes); tests cover join-by-subject, join-by-email including the verification side effect, mismatch, create, and refusal
- [ ] a locked account (T032) may still sign in with Google — the lock protects password guessing, not identity Google has proven; a test pins it; a password login on a Google-only account stays the dummy-verified `INVALID_CREDENTIALS` from T030
- [ ] config: `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` (BE; both empty ⇒ the identity port is nil and the button is hidden; one of the two set ⇒ boot fails), `VITE_GOOGLE_CLIENT_ID` (FE); all three in `.env.example` and `.env.production.example`, DEPLOY.md gains the rows plus the operator step "register `<web origin>/login/google/callback` as an authorized redirect URI in the Google Cloud console"
- [ ] FE `features/sign-in-with-google`: `startGoogleSignIn(redirect?)` generates `state` (16 random bytes, base64url) and a PKCE verifier (32 random bytes, base64url) with an S256 challenge through Web Crypto, stores `{ state, verifier, redirect }` under `sessionStorage['postpilot.google-signin']`, and navigates to `https://accounts.google.com/o/oauth2/v2/auth` with `client_id`, `redirect_uri = <origin>/login/google/callback`, `response_type=code`, `scope=openid email`, `state`, `code_challenge`, `code_challenge_method=S256`, `prompt=select_account`; the button is a `shared/ui` secondary `Button` labelled `Google로 계속하기 / Continue with Google` with an inline SVG mark (no third-party asset), rendered below the CTA and outside the form on `/login` and `/signup` only when `VITE_GOOGLE_CLIENT_ID` is non-empty; a test proves the challenge is the base64url SHA-256 of the verifier

## impl notes
- authorization code + PKCE started by the SPA and exchanged by the backend ← it is literally "the Google sign-in exchange" AUTH-1 names as a procedure; the cookie is then set by a Connect response like Login's (no cross-origin redirect has to carry it), the button is fully ours (no GIS script, no iframe), and the client secret never reaches the browser. Google's Identity Services ID-token flow was rejected because it loads Google's script and renders Google's button on our login page
- skipping the id_token signature check is permitted by OIDC Core §3.1.3.7 item 6 when the token was received directly from the token endpoint over TLS, which is the only way this adapter receives one; still validate `iss`, `aud` and `exp`. Do not add a JWKS fetch or a JWT library
- no `golang.org/x/oauth2`: one POST and one JSON decode do not justify a dependency (ARCH-33 would also require reading its docs); the adapter is under 150 lines
- `redirect_uri` is sent by the client and forwarded verbatim because Google requires the exchange to repeat the exact value used in the authorization request; the adapter must refuse a value whose origin is not `cfg.CORSOrigin` before calling Google
- `scope=openid email` only — no profile, no display name (the product stores none)
- a Google-created account has `password_hash = ''`; T030's Login already treats that as the dummy path and T031's `ChangePassword` refuses it with `PASSWORD_NOT_SET`; the owner adds a password through the reset flow
- the join rule when the email matches an unverified self-signed account is to VERIFY it: Google asserts the present user controls the address, which is what the verification mail would have proven
- state and verifier live in `sessionStorage` (per tab, cleared on close) rather than `localStorage`; wrap every access in try/catch like the theme preference does
