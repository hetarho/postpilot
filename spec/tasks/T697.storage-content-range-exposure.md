## goal
Make browser-first clip generation read originals again in production, and make a deploy fail when the bucket hides `Content-Range` from the web origin.

## acceptance
- [ ] The production bucket's CORS policy matches `deploy/r2-cors.json`. A presigned ranged GET sent from `WEB_ORIGIN` returns 206, and its `Access-Control-Expose-Headers` lists `Content-Range`. The owner applies the policy (Cloudflare → R2 → bucket → Settings → CORS policy), and the result records when it was applied.
- [ ] A new `check-storage-cors <origin>` API command, run as the API process, does four things. It writes a 2-byte probe object under `cors-probe/`. It presigns a GET for that object against the browser-facing endpoint. It sends `Range: bytes=0-0` with `Origin: <origin>`. Then it fails unless all of these hold: the status is 206, `Access-Control-Allow-Origin` is the origin or `*`, `Access-Control-Expose-Headers` lists `content-range` or `*` (case-insensitive), and `Content-Range` is exactly `bytes 0-0/2`. It deletes the probe at the end. A failed delete only warns, but a failed check exits non-zero with a message naming `deploy/r2-cors.json`.
- [ ] After the health gate, `deploy-backend.yml` runs the command inside the running API container with `WEB_ORIGIN`. If `Content-Range` is hidden, the deploy fails with that message.
- [ ] `storage.Bucket.HeadSource` keeps the SDK error as the wrapped cause. When the caller's context is cancelled or past its deadline, it returns `ctx.Err()`. `toConnectError` in `internal/clip/rpc` maps `context.Canceled` and `context.DeadlineExceeded` to Connect's canceled/deadline codes with no ERROR log. Any other unknown failure is logged together with its wrapped cause.
- [ ] Tests:
  - `backend/internal/storage/cors_probe_test.go` drives the probe against an `httptest` server. Cases: `TestCORSProbePasses`, `TestCORSProbeHiddenContentRange`, `TestCORSProbeForeignOrigin`, `TestCORSProbeNotPartial`, `TestCORSProbeDeletesProbeObject`.
  - `backend/internal/storage/clip_test.go` covers `TestHeadSourceKeepsCause` and `TestHeadSourceReturnsCallerCancellation`.
  - `backend/internal/clip/rpc` covers `TestToConnectErrorCancellationIsNotLogged`.
  - The existing storage and clip rpc tests still pass.
- [ ] The ARCH-31 pre-push gate passes. After the push, the deploy workflow's new step passes against production, and that must happen after the live policy is applied. A real production clip generation then gets past source reading without `CLIP_SOURCE_RANGE_INVALID`.

## impl notes
- Evidence (261015, project `a2a2302a…`, 참선주면옥, 11 sources):
  - A live ranged GET from `https://postpilot.haeram.me` returns 206 with `Content-Range: bytes 0-0/11908495`, but the response carries only `Access-Control-Expose-Headers: ETag`.
  - The preflight allows GET and PUT and the `range` header, so the live policy was only partly updated.
  - Because the header is hidden, `range-source.ts:91` reads `Content-Range` as null and fails with `CLIP_SOURCE_RANGE_INVALID` in the browser. This happens before any server job exists, so there is no `generation_jobs` row and no server log, only an unconsumed quote.
- T604 (48c574de) added `range` and `content-range` to `deploy/r2-cors.json`, but the live rollout stayed open (see the T604 limits).
- The deploy gate only sends OPTIONS preflights. A preflight never carries expose headers, so the gate cannot see this fault.
- Why a probe object rather than `GetBucketCors`: the stack's R2 token is scoped to objects, and reading bucket CORS needs an admin token the stack does not hold. A real ranged GET also checks what the browser actually receives, which is the thing that failed.
- Sign the probe against `R2_PUBLIC_ENDPOINT` if it is set, otherwise `R2_ENDPOINT`, like `storage.New`. Use the same presign client as `PresignSourcePlayback`. Apply `range-source.ts`'s exact Content-Range and Content-Length rule, so the probe and the browser agree.
- Probe key: `cors-probe/<random hex>.bin`, content type `application/octet-stream`. It lives outside `clip.SourcePrefix`, so the clip source sweeps never see it.
- Add the command to the `switch` in `cmd/api/commands.go`, next to `adduser` and `setplan`.
- The runtime image is distroless (`ENTRYPOINT ["/api"]`) and has no shell. The workflow runs `docker compose -f docker-compose.prod.yml exec -T api /api check-storage-cors "$WEB_ORIGIN"`. Keep the existing preflight checks, since they cover PUT admission.
- Update DEPLOY.md's bucket-CORS section in place, keeping current truth only. State that `content-range` must be exposed, and that the deploy now proves it with a real ranged GET.
- The unexplained `clip source availability check failed` at 11:43:25 is the reason for the HeadSource and `toConnectError` change. The quote query passes its abort signal, so a quote the client abandons cancels the server's R2 HEAD. Today that cancellation surfaces as an UNKNOWN_FAILURE ERROR log with no cause.
- Out of scope: the failure copy for this code ("원본 영상을 다시 선택해 재시도해 주세요") misleads the owner when the fault is in the deployment. Changing that copy is a CLIP failure-copy decision for update-ssot, not this task.
