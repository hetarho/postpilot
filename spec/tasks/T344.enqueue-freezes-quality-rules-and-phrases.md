# T344 Generation freezes the ticked rule texts and the 분야 phrase list at enqueue
> st:todo | ssot:GEN-14 GEN-48 GEN-51 GEN-57 POST-81 QUAL-13 QUAL-29 QUAL-41 GUIDE-30 GUIDE-31 ARCH-7 ARCH-40 ARCH-24 | base:GEN@10 POST@11 QUAL@3 GUIDE@5 ARCH@9 | dep:T335 T342 T341 T333

## goal
- StartGeneration and the write-comparison snapshot freeze the ticked rule texts still over band and the first 30 phrases of the post's 분야, handlers read only the payload, and a post with nothing ticked and no list keeps byte-identical payloads and prompts.

## acceptance
- [ ] Start for a post with ticks asks the quality port once, with the post's `QualityRuleIDs` and its frozen target language, and freezes exactly the texts returned in their order; a post with no ticks never reaches the port; a tick the port returns nothing for (within band, below minimum, absent) freezes nothing.
- [ ] Start for a post with a 분야 asks the phrase port once and freezes the first 30 phrases in stored order; a post with no 분야 never reaches the port; an empty or missing list freezes nothing, exactly like no 분야 (QUAL-41); the preset plays no part in the phrase freeze (GEN-48, GUIDE-31).
- [ ] The generate payload carries `quality_rules` and `field_phrases` (both `omitempty`) right after `memories`; a payload without them decodes as none; a post with nothing ticked and no list encodes byte-identically to HEAD.
- [ ] `EnqueueGeneration` copies both into the payload, the `KindGenerate` mapping copies both into `GenerateJob`, and `Generate` copies both onto the `PostInput` the write reads. A test through the real adapter and the stored job row proves neither is dropped.
- [ ] The drain never re-reads them: editing ticks, publishing posts or replacing the stored list after the enqueue changes nothing in that run's prompt, and `Generate` calls neither port.
- [ ] A run with frozen rules makes exactly one write-stage provider call and no measurement: no post-hoc correction pass exists (QUAL-29).
- [ ] `SnapshotWriteInput` freezes both onto the snapshot's `PostInput` through the same helpers, so both candidates' system prompts and per-post halves are identical. A different rule set or phrase list gives different snapshot bytes (so a different hash), and none gives snapshot bytes identical to HEAD.
- [ ] `StartRevision` calls neither port and its payload carries neither member (GEN-51 is write-only; GEN-57).
- [ ] `buildContexts` wires both ports over the quality service, and `TestBuildContextsWiresEveryRequiredCollaborator` passes.
- [ ] End to end on real stores: a post with 분야 `restaurant`, a stored list for it and the preset on for `restaurant` freezes a write prompt whose per-post half carries the phrase section under `FieldPhrasesHeading` and whose `[작문 지침]` carries `guideline.PresetText`; a revision of a post in that 분야 carries neither.
- [ ] Tests: `internal/generation/quality_freeze_test.go` (`TestStartFreezesOnlyTheReturnedRuleTexts`, `TestStartFreezesTheFirstThirtyFieldPhrases`, `TestNoTicksAndNoListLeaveThePayloadAndPromptByteIdentical`, `TestTheDrainIgnoresRowsChangedAfterEnqueue`, `TestAFrozenRuleRunMakesOneWriteCall`, `TestTheRevisionFreezesNeither`, `TestWriteSnapshotFreezesRulesAndPhrasesForBothCandidates`); `internal/generation/payload_golden_test.go` (`TestGenerationPayloadWireShapeIsPinned` extended); `cmd/api/generation_freeze_test.go` (`TestEnqueueGenerationCarriesRulesAndPhrasesThroughTheJobRow`, `TestFieldPhrasesReachTheWritePromptAndNeverTheRevisePrompt`, `TestPostTickIdsAreTheQualityMetrics`); `cmd/api/wiring_test.go` green.
- [ ] Verify: `cd backend && test -z "$(gofmt -l .)" && go vet ./... && go build ./... && go test -timeout 30m ./...`

## impl notes
- `backend/internal/generation/ports.go` gains `type QualityRulesForPrompt interface { RulesFor(ctx context.Context, userID, slug string, ticked []string, language Language) ([]string, error) }`.
- It also gains `type FieldPhrasesForPrompt interface { For(ctx context.Context, field string) ([]string, error) }`.
- They are named after `GuidelinesForPrompt`/`MemoriesForPrompt`: the plan's bare `QualityRules`/`FieldPhrases` would read as the `PostInput` members of the same name. The method names are the plan's.
- Both return an error, which R23's shorthand omits: a failed read stops the start exactly as `freezeGuidelines` does, rather than silently dropping what the owner ticked.
- `Deps` gains `QualityRules QualityRulesForPrompt` and `FieldPhrases FieldPhrasesForPrompt`; `NewService`'s nil-panic map gains `"quality rules"` and `"field phrases"` (ARCH-40); `Service` gains `qualityRules` and `fieldPhrases`.
- `deps_test.go` `testDeps()` gains `neutralQualityRules{}` and `neutralFieldPhrases{}`, both answering `nil, nil`, which is the context's behaviour before this task.
- `config.go`: `FieldPhrasesMax = 30` (GEN-48).
- `service.go` `freezeQualityRules(ctx, post PostInput) ([]string, error)`: returns `nil, nil` without a call when `len(post.QualityRuleIDs) == 0`. Otherwise it calls `s.qualityRules.RulesFor(ctx, post.UserID, post.Slug, post.QualityRuleIDs, post.TargetLanguage)`, wraps errors as `"load quality rules: %w"`, and returns `cloneTexts` (nil when empty).
- `freezeFieldPhrases(ctx, post PostInput) ([]string, error)`: returns `nil, nil` without a call when `post.Field == ""`. Otherwise it calls `s.fieldPhrases.For(ctx, post.Field)`, wraps errors as `"load field phrases: %w"`, keeps the first `FieldPhrasesMax` in returned (rank) order, and returns `cloneTexts`, so an empty list is nil (QUAL-41).
- `PostInput.QualityRuleIDs` and `PostInput.Field` are T337's `json:"-"` resolution inputs, filled by `generationPosts`. The frozen texts, T324's `PostInput.QualityRules` and T330's `PostInput.FieldPhrases`, carry the identity.
- `Start` calls both helpers after `freezeMemories`, after every refusal (T334's published check included), and sets `request.QualityRules` and `request.FieldPhrases`. `StartRequest` and `GenerateJob` each gain `QualityRules []string` and `FieldPhrases []string`.
- `generation_payload.go`: `generationPayload` gains `QualityRules []string \`json:"quality_rules,omitempty"\`` and `FieldPhrases []string \`json:"field_phrases,omitempty"\`` directly after `Memories`, and `GenerationOptions` gains both. `EncodeGenerationPayload`/`DecodeGenerationPayload` pass them through `cloneTexts`.
- `TestGenerationPayloadWireShapeIsPinned`'s full case gains `"quality_rules":["…"],"field_phrases":["…"]` after `memories`, and its `absent` case still equals `{"target_language":"ko","observe_files":null}`.
- `generate_handler.go` `Generate` sets `post.QualityRules = cloneTexts(job.QualityRules)` and `post.FieldPhrases = cloneTexts(job.FieldPhrases)` beside the `Template`/`Guidelines` copies.
- The same function never copies `job.Memories` onto `post` today: frozen memories never reach a durable generate's write prompt. That is pre-existing and not fixed here. The two new copies must not repeat the omission, and the handler-level tests are what prove it.
- `StartRevision` calls neither helper and `revisionPayloadJSON` is unchanged (R30).
- `experiment_surface.go` `SnapshotWriteInput` sets `post.QualityRules` and `post.FieldPhrases` through the same two helpers after `freezeGuidelines`; `post.TargetLanguage` is already validated above.
- Those two members marshal inside `post` as `quality_rules`/`field_phrases`, so a snapshot's bytes and hash move only when one is present. `RunWriteCandidate → writeCandidate` reads them from `snapshot.Post`, and nothing re-reads a port.
- `backend/cmd/api/adapters_generation.go` gains `type generationQuality struct{ service *quality.Service }`. Its `RulesFor` maps `generation.Language` to quality's language type through a closed switch (an unknown value returns an error), passes the ASCII metric ids through, and returns T335's `RulesFor` texts.
- It also gains `type generationFieldPhrases struct{ service *quality.Service }`, whose `For(ctx, field)` returns T335's `PhrasesFor(ctx, field)`.

The closure calls it, so the test drives the mapping the worker uses.
