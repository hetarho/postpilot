# T043 Caret-relative image insertion, one-at-a-time upload and captions
> st:todo | ssot:PUBLISH-21 PUBLISH-36 PUBLISH-19 PUBLISH-20 | base:PUBLISH@4 ARCH@2 | dep:T042

## goal
Insert each manifest photo at its own position by placing the caret in the block it must follow, upload it as the only file in that operation, and apply its caption.

## acceptance
- [ ] `Apply(upload_image)` performs one atomic sequence: resolve the block the image must follow and place the caret at its end, enable `Page.setInterceptFileChooserDialog`, resolve `button.se-image-toolbar-button` to exactly one match and click its live geometry, then hand `input[type=file]#hidden-file` exactly one enumerated current-job path through `DOM.setFileInputFiles`; the input does not exist before that click and no native dialog is ever accepted (PUBLISH-21)
- [ ] the `upload_image` locator entry counts `button.se-image-toolbar-button`, not `input[type=file]#hidden-file`, so `Publisher.mutate`'s pre-check is satisfiable before the click that creates the input; a test pins that the file input is absent at pre-check time and present at upload time
- [ ] a photo is counted only after a fresh full snapshot shows exactly one additional editor image; a resolved path or an upload acknowledgement alone is never evidence; an upload that adds zero or two images fails `editor_changed`
- [ ] images are uploaded in exact manifest-ordinal order and each lands immediately after the block holding the caret, so the observed block order equals the manifest's; a test with eight photos interleaved between text blocks proves the resulting order, and a test proves a manifest whose FIRST block is an image still produces the image as the first body block
- [ ] `Apply(image_caption)` resolves the `.se-module-text.se-caption` module of the addressed image's ordinal and enters the caption; an empty caption is not written at all, and the module's placeholder `사진 설명을 입력하세요.` is never read back as content
- [ ] no coordinate survives a mutation: a test walks every reviewed type on the image path and proves none has a field that could hold resolved geometry, and that the rect read for a click is not returned to the caller or reused by the next mutation (PUBLISH-36)
- [ ] against a fake CDP editor, table-driven tests cover: eight ordered JPEGs; a leading image; an upload adding zero or two images; ordinal disorder; a caption applied to the wrong ordinal; the file input disappearing between the click and the upload; a path outside the enumerated current-job set being refused; and the caption placeholder never entering the projection
- [ ] ARCH-27 passes

## impl notes
- the live mechanics are in T019's `## survey` section, item 1: `#hidden-file` is created on demand by the image button's click, advertises `accept=".jpg,.jpeg,.gif,.png,.bmp,.heic,.heif,.w…"` and is `multiple` but must still receive one file per call, and SmartEditor places the new `.se-component.se-image` immediately AFTER the component holding the caret
- that is why there is no placeholder step and no pre-allocated ordinal: position comes from the caret, which is the rule PUBLISH-36 r4 now states
- for an image whose manifest position is first, place the caret in the editor's leading text component; SmartEditor always has one, and the empty paragraph it leaves before the image is removed by the same trailing-empty-paragraph cleanup the projection already needs. If it turns out not to be removable, record it and treat the leading empty paragraph as expected in the fence snapshot rather than fighting it
- interception must be enabled before the button click, not after: the click is what would otherwise open the native chooser
- caption modules exist one per image and only once the image exists, so `image_caption` is planned after all uploads for that ordinal, never before
