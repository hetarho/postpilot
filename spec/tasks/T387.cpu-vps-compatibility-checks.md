## goal
Verify the CPU workflow and VPS-compatible release locally, including isolated remote-style execution, without deploying to production or another host.

## acceptance
- [ ] A reproducible release fixture runs the API, private object storage and CPU worker as separate processes with no shared data/work directories, through real RPC, lease, artifact and finisher code; model calls use explicit fixtures rather than paid providers.
- [ ] The same fixture passes colocated and isolated-network remote-style layouts on the development host, including reopening a job while waiting, unavailable worker, API restart, worker kill/reclaim, cancellation, duplicate completion and cleanup retry; a second physical server is not required.
- [ ] Delivered CPU output matches the existing same-host/profile baseline for all supported aspect ratios and representative original-audio, transition and sequence-caption cases; the generation result still stops at a plan and browser rendering remains functional.
- [ ] The resource run records combined API/worker peak memory, disk, API responsiveness and prepare/render/upload elapsed times under a VPS-sized envelope with a stated reserve for colocated services; insufficient capacity is a reported failed gate, not a universal compatibility claim.
- [ ] Release tooling can check actual host memory/disk and chosen worker limits when the operator deploys; local tests cover sufficient/insufficient resources, and a bounded disposable smoke recipe is provided for staging/current VPS without running it there as part of this task.
- [ ] After the gates pass, remove the temporary CLIP_MEDIA_EXECUTION switch and embedded production preparation/final-render dispatch. Same-host and remote server jobs both use the same durable worker protocol; no worker error can select a local fallback.
- [ ] Fresh installation and additive upgrade preserve existing projects, results, quotes, source retention, accounting and ordinary model-job restart behavior; same-host rollout starts both services, remote-mode API health survives an offline worker.
- [ ] ARCH-25/26/generated-code checks, local execution-image/release smokes and deployment tests pass; the runbook separates local measurements from commands for later host verification and requires neither a live migration nor GPU hardware to complete this CPU release.

## impl notes
- Extend the existing cmd/api clip release harness rather than substituting a fake Renderer at the split. Spawn the real worker process/container, use real FFmpeg/resvg/fonts and local private MinIO, and keep provider stubs visibly identified in the report.
- Use a deterministic fixture/clock to place failures at durable boundaries; the multi-process exercise separately demonstrates that local-memory callbacks, same-volume paths and in-process wakeups are not prerequisites.
- Same-profile identity is checked on the same machine before/after the split. Do not refresh host-dependent golden hashes merely because another architecture differs; GPU compression acceptance remains outside this task.
- Add runnable `pnpm smoke:media-worker` and `pnpm smoke:media-release` entrypoints and include them in the media CI matrix under the existing smoke/deploy policy. Keep build-time tooling checks blocking and real-runtime verification explicit.
- Use a configurable 2-vCPU/1-GiB fixture as the documented historical VPS starting envelope, not evidence of current available capacity. Implement and locally test a preflight that measures actual free resources when the operator invokes it, accounting for existing colocated workloads before suggesting a worker budget.
- Make the operational smoke use a separate disposable project, storage prefix, work directory and alternate internal port; its cleanup must not touch real user originals or the production DB. A passing local envelope test is not recorded as a live VPS measurement.
- The completed release defaults to colocated CPU, one worker job and existing encode/decode defaults. Missing required worker settings produce clear deployment/preflight errors; the API remains healthy while a correctly configured remote worker is temporarily unavailable.
- Keep API-side authored-plan checks, preview rasterization and browser caption assets. Remove only embedded preparation/final-render dispatch, and document the remaining API media dependencies rather than claiming the API contains no media tooling.
- Use the rollback compatibility boundary from T386. Test upgrade from a seeded legacy schema, but never start a legacy API against live parked work or downgrade applied migrations.
- This task produces locally validated release artifacts and procedures; production deployment, friend-PC access, host installation, topology migration and real-GPU performance/quality validation are outside its acceptance criteria. The running VPS is unchanged by authoring or testing these tasks.
