# T095 User selectors show the level and order 가성비 → 최고
> st:todo | ssot:MODEL-44 MODEL-57 MODEL-58 MODEL-27 LANG-7 | base:MODEL@9 LANG@3 ARCH@2 | dep:T092

## goal
Every list `ListModels` feeds — the per-stage selectors and the A/B pair fields — names each model's level for that stage and orders levelled models 가성비 → 최고 with unlevelled ones last.

## acceptance
- [ ] `entities/model-catalog/model/types.ts` gains `LevelName` (`'value' | 'balanced' | 'premium' | 'top'`) and `LEVELS` in that order; `CatalogModel.levels: Partial<Record<StageName, LevelName>>`; `toCatalogModel` fills it from `ModelInfo.levels` through `stageFromProto`, dropping unknown stages and unknown level strings
- [ ] a pure `orderModelsForStage(models, stage)` in the slice's `model` segment: ascending `LEVELS` rank of `levels[stage]`, models without a level for that stage after every levelled one, and the server's order preserved inside a rank (stable)
- [ ] `useStageSelection(stage).models` and the `suitable` list `CandidatePairSelect` builds are both ordered through that helper — no component sorts on its own
- [ ] an option's label leads with the level's copy when the model has one for that stage — `가성비 · <label> …badges …reason` — and is unchanged when it has none; the closed trigger therefore reads the level first
- [ ] ko/en `models` namespace gains `level: { value, balanced, premium, top }` — ko 가성비 · 밸런스 · 고급 · 최고, en Value · Balanced · Premium · Top — and the locale parity test passes; `combos.name.*` is not reused
- [ ] the level changes nothing else: `disabled`, affordability and the vanished/unsuitable entries render exactly as before (existing `StageModelSelect.test.tsx` and `ModelPairForm.test.tsx` pass with only ordering/label expectations added)
- [ ] vitest: `orderModelsForStage` (mixed levels, unlevelled last, stability, per-stage independence — one model `value` for observe and unset for write); `StageModelSelect` rendering options in level order with level-led labels; `CandidatePairSelect` doing the same for both fields
- [ ] the `frontend/src/test` fake that serves `ListModels` accepts per-stage levels so the page tests drive the real shape
- [ ] `pnpm --filter ./frontend test` · `pnpm lint` · `pnpm lint:fsd` · `pnpm lint:style:probe && pnpm lint:style` · `pnpm build:web` (ARCH-25)

## impl notes
- ordering lives in the entity's pure `model` segment and is applied where the stage list is produced (`useStageSelection`) and where the pair fields derive `suitable`, because both surfaces must agree and neither should own a sort (ARCH-14/15; `entities/*/model` imports no react, ARCH-18)
- "badge" from MODEL-44 is rendered as the leading token of the option string: `ListboxOption.label` is `string`, and widening the primitive to a node is out of this task's scope. The level goes FIRST, ahead of the model label, because the closed trigger truncates at ~284px on a 360px phone and a `provider/model` path alone fills it — a trailing token would be cut off
- a level is per stage, not per model (MODEL-57): the pair form and the selector both know their stage, so they read `levels[stage]`; nothing aggregates across stages
- unlevelled models sort after levelled ones and show no level text (MODEL-58) — they are not disabled and carry no warning here; the operator sees the gap in 모델 관리 (T094)
- the new i18n keys are owned by this task; T094 depends on it and reuses `models.level.*` for the admin Listbox and the document diff
