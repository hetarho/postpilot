# T308 the server serves a sequence caption's own frames
> st:todo | ssot:CLIP-159 CDS-85 CDS-81 CLIP-154 | base:CLIP@42 CDS@25 | dep:-

## goal
A browser render can obtain the server's own drawing of every output frame of a sequence-rendered caption, as bounded sprite sheets over the plan it is rendering.

## acceptance
- [ ] one RPC returns, for one caption instance of a validated plan, the style's own drawing for a requested run of output frames as a sprite sheet: one PNG holding the frames in order, with the cell size, the cell count, the first output frame and the layer's canvas origin
- [ ] the frames are the ones a server render would draw for that caption — same crop, same progress per frame, same painter
- [ ] a request is owner-scoped and pinned to the plan's draft hash: a foreign or unknown project is not found, a stale hash is refused, and a finalized project is refused
- [ ] a static style is refused by name: its one raster is what the preview already serves
- [ ] the response respects a stated ceiling on cell count and bytes, and a run larger than the ceiling is answered with what fits plus the next frame to ask for
- [ ] serving frames changes no project state, starts no job, consumes no credits and never renders a video
- [ ] go test: the sheet's cells match the frames the render's own sequence writes for the same caption, a stale hash and a static style are refused, and the ceiling pages a long caption
- [ ] the media image stage is built and run locally (ARCH-37): `docker buildx build --target media-smoke -f backend/Dockerfile .`
- [ ] verify: `cd backend && test -z "$(gofmt -l .)" && go vet ./... && go build ./... && go test ./...` · `pnpm gen:proto && git diff --exit-code -- backend/internal/gen frontend/src/shared/api/gen agent/internal/gen`

## impl notes
- the drawing already exists whole: `media/sequence.go` `captionSequence` writes one PNG per output frame for a server render, from `captionFrame(canvas, copy, layout, duration, progress)` + `design.DrawCaptionFrame`, cropped by `sequenceCrop`. This task exposes the same frames without a workspace or a render
- sheet over single frames (owner decision 2026-09-22): a 2 s caption is 60 frames, and one request and one decode per sheet beats sixty of each. Cells are the crop box, laid left-to-right in rows; the browser blits a sub-rect
- one resvg run per sheet, not per cell: tile the frames into ONE document by repeating each frame's body inside `<g transform="translate(col*w, row*h)">` against a sheet-sized viewBox. The painters use fixed filter and clip ids (`cbi`, `cneon`, `cgs%d-%d`), so each cell's body and defs go through `prefixIDs` with the cell index, exactly as `captionFragment` prefixes a fragment with its instance id — two cells sharing an id would draw one cell's filter over the other
- bounds belong with the preview's, in `clip.PreviewConfig`'s neighbourhood: a cell-count ceiling and a byte ceiling per response, checked before rasterising rather than after, and `ErrPreviewTooLarge` when one sheet's own cell cannot fit
- the request carries the project id, the draft hash, the caption's `instance_id` and the first output frame; the response carries the sheet, the cell box, the count, the first frame and the next frame (-1 at the end), mirroring `ClipPreviewAsset`'s paging shape
- reuse the preview's admission path (`app/preview.go`): same ownership, same finalized refusal, same plan validation and draft-hash check, so a browser render cannot ask for frames of a plan the server has not validated (CLIP-154)
- this is the cost the owner accepted: the server rasterises the same frames it would for its own render, but no encode, no merge and no footage pass
