# T204 What the owner asked for is kept
> st:todo | ssot:CLIP-133 CLIP-1 CLIP-24 | base:CLIP@31 ARCH@3 | dep:T202

## goal
Keep the verbatim instruction each generation used and the verbatim text of each revision request, with the time it was made, and show the owner that record.

## acceptance
- [ ] an accepted generation records the instruction it froze; an accepted revision request records its request text and its target; each entry carries the time it was made
- [ ] nothing is recorded by autosave: an instruction typed and saved but never used by a generation leaves no entry
- [ ] a generation started with no instruction records an entry saying so rather than nothing, so the record explains a clip written without one
- [ ] entries are readable by the owner in the project and are ordered newest first
- [ ] a failed or cancelled attempt keeps its entry — what was asked for is what happened, whatever the outcome
- [ ] deleting the project removes every entry with it, and no previous result, plan snapshot or direct-edit summary is stored
- [ ] the record is project content, never diagnostics: nothing about it enters logs, which CLIP-88 keeps free of prompts and answers
- [ ] tests: BE — an accepted generation and an accepted revision each write one entry, autosave writes none, project deletion removes them; FE — the record renders in order and states a generation with no instruction
- [ ] verify FE (ARCH-25), BE (ARCH-26) and generated code (ARCH-28) pass

## impl notes
- migration 0056 adds `clip_project_requests(id, user_id, project_id, kind, body, created_at)` with a `(project_id, created_at)` index and a cascade to `clip_projects`; kind distinguishes the frozen instruction from a revision request and carries the revision target (`instruction` · `revision:flow` · `revision:narration` · `revision:both`). Queries go in store/queries/clips.sql and `pnpm gen:sql` runs sqlc through Docker (ARCH-28)
- the write point is acceptance, not save: the owner chose to record what the AI actually read, so write the entry where the generation payload freezes its inputs (clip/quotes.go's start path, which already marshals `Instruction` into `generationPayload`) and where T202's revision job is accepted. An entry written at enqueue time survives a later failure, which is what the acceptance asks for
- store the text verbatim: no trimming, no normalisation, no deduplication against the previous entry. CLIP-133 says verbatim, and a deduplicated record cannot answer "what did I ask for that time"
- read path: extend `GetClipProject` rather than adding an RPC — the record is project content under CLIP-1 and the page already loads the project once
- FE placement: the record is owner-facing history, not a control. Put it where the observations panel sits (a read-only disclosure in ① and ②) so it needs no dock action and no step of its own
- retention is the project's, not the sources': entries outlive the 24-hour original retention (CLIP-73) and are removed only with the project (CLIP-24). Nothing here extends source retention
- unchanged: `clip_attempt_checkpoints` and the diagnostics CLIP-88 bounds stay exactly as they are — this record is a separate, owner-facing table
