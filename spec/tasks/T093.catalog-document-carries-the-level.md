# T093 The catalog document carries the level: `<id> [level]` lines, relevel preview, level-aware sync and export
> st:todo | ssot:MODEL-59 MODEL-52 MODEL-53 MODEL-54 MODEL-55 MODEL-57 | base:MODEL@9 ARCH@2 | dep:T092

## goal
Extend the `# postpilot models v1` document so each id line may name the registration's level, the preview reports level changes, the apply writes them in the same transaction, and the export emits them.

## acceptance
- [ ] `ParseDocument` accepts an id line as `<id>` or `<id><whitespace><level>`: the first token must still pass `looksLikeModelID`, a second token must be one of the four `Level` values, a third token is `malformed_line`; the version line stays `# postpilot models v1` and every document valid before this task still parses to the same registrations with every level unset
- [ ] a second token outside the four values is rejected as a new cause `unknown_level` with its line number and text, and like every other issue refuses the whole document (MODEL-53)
- [ ] `DocumentSection` holds `Entries []DocumentEntry{ModelID, Level, Line}` (replacing the parallel `ModelIDs`/`Lines`), and a duplicate id inside one section stays `duplicate_id` whatever the levels say
- [ ] `PurposeWrite` gains `Level`; `planDocument` emits one write per listed id with the document's level (`""` when the line carried none) and `Store.SyncPurposes` sets the registration's `level` for EVERY listed id after its `INSERT OR IGNORE` — a line without a level clears an existing one (MODEL-59), all inside the one transaction; a deregistration still deletes the row and its level
- [ ] `DocumentPurposePlan` gains `Relevel []LevelChange{ModelID, From, To}`: the ids that already hold the purpose and whose level the document would change (including to or from unset); a newly registered id is listed under `Register` only, an id whose level is unchanged stays under `Unchanged`
- [ ] proto `CatalogDocumentPurposePlan` gains `message CatalogDocumentLevelChange { string model_id = 1; string from = 2; string to = 3; }` as `repeated CatalogDocumentLevelChange relevel = 5`; the handler maps it
- [ ] `RenderDocument` takes the level per id and writes `<id> <level>` with one space when set and `<id>` otherwise, ids still sorted within a section, output still byte-stable; `ExportDocument` feeds it the current levels
- [ ] `protocol_test.go` covers: id-only, id+level, three tokens, unknown level, tab-separated tokens, a mix within one section, and render of set/unset lines
- [ ] `service_test.go` / `document_test.go` cover: preview reporting `Relevel` and writing nothing, apply clearing a level via an id-only line, apply setting a level on an already-registered id, the round trip `ExportDocument` → `ParseDocument` → `PreviewDocument` reporting no register, deregister or relevel, and a mid-apply failure leaving levels untouched (`store_test.go`)
- [ ] `cd backend && test -z "$(gofmt -l .)" && go vet ./... && go build ./... && go test ./...` (ARCH-26)
- [ ] `pnpm gen:proto && git diff --exit-code -- backend/internal/gen frontend/src/shared/api/gen agent/internal/gen` (ARCH-28)

## impl notes
- MODEL-59 keeps the version at `v1` because the grammar only widens: every old document is a valid new document with the same meaning. A document written with levels and pasted into an older build is refused line by line (`malformed_line`, since the old `looksLikeModelID` rejects whitespace) rather than misapplied — the failure mode is loud, which is what the version line is for
- the level is written by the sync for every listed id, not only for changed ones: MODEL-52 says a section is the purpose's whole state, and the write is idempotent. This is also why an exported document pasted back is a no-op — the export writes every set level, so the sync sets each to what it already is and `Relevel` is empty
- `Relevel` is separate from `Unchanged` so the panel can make level changes visible without inflating the deregistration list (MODEL-54); the FE side lands in T094
- the level write in `SyncPurposes` is the same `UpdateCatalogModelPurposeLevel` statement T092 added for the single-row edit, run inside the sync's transaction after `AddCatalogModelPurpose` — one statement, two callers, as `AddCatalogModelPurpose` already is
- the test fake `Store` in `service_test.go` must model the level per registration so the round-trip test drives the real contract rather than a stub that ignores the second token
