# T384 Clip progress distinguishes waiting, execution and media recovery
> st:todo | ssot:ARCH-14 ARCH-16 ARCH-17 ARCH-20 CLIP-78 CLIP-79 CLIP-81 CLIP-86 CLIP-88 CLIP-96 CLIP-161 CLIP-162 CLIP-164 | base:ARCH@11 CLIP@44 | dep:T383

## goal
Show the actual media stage and actionable failures while keeping the current focused clip view and cancellation controls.

## acceptance
- [ ] Preparation/render waiting and retry states have ko/en owner-facing labels; they do not show fabricated percentage advancement or claim that a disconnected worker is still rendering.
- [ ] Reopening/polling the same active job restores its durable state, completed-work counts and cancellation availability; an internal media retry keeps the same job id.
- [ ] Cancellation remains 취소 중 until the durable terminal acknowledgement, and completion already committed retains the completed result.
- [ ] Worker-unavailable, total-timeout and retry-exhausted failures explain the next owner action through the existing FailureNotice/explicit continuation flow, preserving previous results and completed observations.
- [ ] No hostnames, GPU model names, lease tokens or deployment controls enter the product UI, and the existing browser/server render choice and credit wording retain their meaning.
- [ ] Backend stage/failure mapping tests plus FE polling, progress and ClipStatus tests cover waiting→running→retry→done, exhausted/offline, cancellation and reopen; ARCH-25 and relevant ARCH-26/generated-code checks pass.

## impl notes
- Add allowlisted stage strings prepare_wait, render_wait, prepare_retry and render_retry at the clip stage vocabulary and job reporting boundary. Keep ordinary prepare/render substages and existing public job status values.
- Progress waiting/retry states are indeterminate unless a real completed/total count belongs to the current operation; never infer a duration or queue position from lease age.
- Update `entities/generation-job` domain progress helpers and transport adapter, `entities/clip-project` owned i18n/failure catalog, and `widgets/clip-workspace/ui/ClipStatus`; pages remain composition only.
- Use existing CancelClipGeneration and polling contracts; do not add a user-facing worker status API or hardware selector. Backend worker liveness belongs to internal operations.
- Preserve source inspection, original playback and focused-view restrictions under CLIP-78. Test with the current mounted workspace lifecycle rather than only snapshots of strings.
- Reason translations follow the existing shared API reason mapper and owning slice resources, with exact ko/en key parity and unknown-reason fallback retained.
