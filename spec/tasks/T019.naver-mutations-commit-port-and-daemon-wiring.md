# T019 Naver editor mutations, the commit port and the daemon publisher wiring
> st:todo | ssot:PUBLISH-21 PUBLISH-22 PUBLISH-15 PUBLISH-19 PUBLISH-23 PUBLISH-29 | base:PUBLISH@2 ARCH@1 | dep:T018 T007

## goal
Implement `Apply` and the `CommitPort` extension against the live SmartEditor and wire the real publisher into `runAgents`, so an armed Mac claims a queued job and drives it to a verified published URL instead of refusing to start.

## acceptance
- [ ] `Apply` executes all eleven `MutationKind`s — title, text, heading, quote, list, image_placeholder, upload_image, image_caption, tags, category, visibility — as typed data only; no mutation accepts a selector, script, coordinate, key sequence or native-dialog operation, and text that resembles an instruction or a setting label is entered verbatim
- [ ] every `Apply` resolves its versioned semantic locator against current evidence and requires exactly one match; a missing, renamed, duplicated or unexpected control, a keyboard submission path and a native dialog fail closed before the page is touched
- [ ] JPEGs upload one at a time through the restricted file-input operation in exact manifest-ordinal order, from the enumerated current-job paths only; each is counted only after a fresh full snapshot shows exactly one additional editor image, and neither a resolved path nor an upload acknowledgement alone is evidence
- [ ] `ArmFinal` observes the same bound target, requires the arming token to still equal a current observation, and returns exactly one control whose accessible name is in the versioned allowlist; scheduled, generic, renamed or duplicate publish-like controls return a count that refuses to arm
- [ ] `ActivateFinal` sends exactly one low-level activation with automatic retry disabled, and a second call — or any other mutation after it — is refused by the port itself, not only by the publisher
- [ ] `Readback` navigates the same bound target to the published post and returns the verified `https://blog.naver.com/<blog-id>/<numeric-id>` URL plus a snapshot whose title, block/image/caption order, image count, tags and category are read from the published post; visibility is carried from the verified pre-fence snapshot rather than re-observed, since the post page does not render it
- [ ] `runAgents` receives a real factory: `postpilot-agent run` starts an armed connection, claims a queued job and reaches a terminal result; the placeholder error and the test asserting it are replaced by coverage of the real path
- [ ] against a fake CDP editor, table-driven tests cover: every block kind and eight ordered JPEGs; an upload that adds zero or two images; ordinal disorder; a caption applied to the wrong image; a locator that disappears mid-run; an arming token that no longer matches; a duplicate and a renamed final control; a second activation attempt; a readback URL for another account, a non-numeric post id, a foreign host or a different target; a readback whose body drifted from the frozen snapshot
- [ ] a process death simulated before the fence requeues and one simulated after it yields `outcome_unknown` with no second activation
- [ ] ARCH-27 passes

## impl notes
- continues T018's `agent/internal/naver/port.go`; `CommitPort` is the same bound session, not a second connection — `Readback` must keep `TargetID` equal to the prepared snapshot's or `validateReadback` rejects it
- upload uses `DOM.setFileInputFiles` against the resolved `input[type=file][accept*=image]`; it is the only filesystem-touching operation on this path and accepts only paths the manifest enumerated for the current job. Never open a native file dialog — PUBLISH-21 forbids native-dialog acceptance outright
- image order: create every image position first (`image_placeholder`) and then upload in ordinal order, which is what `Prepare` already expects; do not interleave placeholder creation with uploads
- `ActivateFinal` is one `Input` activation on the armed control. No loop, no fallback, no coordinate path, and no retry wrapper anywhere in its call chain — an ambiguous outcome after it is the designed result, not a failure to fix
- the port holds an `activated` latch set before the activation call is issued; every later `Apply`, `ArmFinal` or second `ActivateFinal` returns a `PortError` immediately. The publisher already consumes authorization once, but the port must not depend on its caller for this
- readback visibility: PUBLISH-15 binds visibility to the pre-fence editor snapshot on purpose. Copy it from the prepared snapshot into the readback snapshot; observing it from the post page is both impossible and out of contract
- wiring: `newPublisher` builds `naver.Publisher{Port: …}` from a `config.Connection` — it launches or reuses the connection's dedicated browser through `browser.OpenEditor` and binds T018's session. Keep the factory in `main.go` behind the existing `publisherFactory` type so `runAgents` stays testable with a fake
- T007 is editing `main.go` concurrently (it enabled `install`, which crash-loops until this task lands); rebase onto its committed state before wiring rather than resolving a three-way conflict in the run loop
- the owner's queued job `0182794e…` (`20260905-test`) is a live queued fixture, not a test target — do not publish it here. Live publication is T008's explicitly authorized smoke and must not happen as a side effect of this task
