# T285 job addresses a subject instead of naming each product
> st:todo | ssot:ARCH-6 ARCH-10 ARCH-11 ARCH-24 | base:ARCH@5 | dep:T270

## goal
Give `generation_jobs` derived subject columns and collapse `job`'s per-product lookups and clip activation into one subject-addressed surface, without rebuilding a single trigger, index or foreign key.

## acceptance
- [ ] a goose migration adds VIRTUAL generated columns `subject_kind` and `subject_id` to `generation_jobs` plus `generation_jobs_subject_idx(subject_kind, subject_id, status)`; no existing trigger, index, column or constraint is dropped, rewritten or rebuilt, and `PRAGMA integrity_check` plus the existing migration test still pass on a migrated temp DB
- [ ] `job.Store` exposes `ActiveFor(ctx, Subject, Filter)`, `LatestFor(ctx, Subject, Filter)` and `ActiveUnattached(ctx, userID, kind)` in place of `ActiveForPost ActiveForPostUser ActiveForVoice ActiveForVoiceKind ActiveModelExperiment ActiveForClip LatestForClip`; `job.Subject` is `{Dimension, ID}` with dimension strings supplied by callers, and the dimension→column mapping exists only in `job/store`
- [ ] `job.Queue` offers `Activate(ctx, user, id)`, `SweepUnactivated(ctx, failure)` and `Snapshot(ctx, user, subject, id)`; the deferred-activation kinds arrive as a constructor argument (ARCH-40) instead of the `kind IN ('generate_clip','render_clip','revise_clip')` literal in `ActivateClip`/`SweepUnactivatedClips`, and `ClipStore` as an optional interface assertion is gone
- [ ] `Job`/`JobSummary` and the rpc projections read `SubjectKind`/`SubjectID` rather than three nullable product ids; no behaviour change in what the client sees
- [ ] a `job/store` test over a migrated temp SQLite pins: a `learn_voice` job carrying a post is found by BOTH the voice dimension and the post dimension; a clip job is found by its project dimension and not by another user's; a `model_experiment` job is found by its experiment dimension; `ActiveUnattached` still ignores subject-carrying rows
- [ ] behaviour unchanged: ARCH-26 passes and ARCH-28's `pnpm gen:sql` diff is clean

## impl notes
- from review/arch-260919 F15 (part 1 of 3; T272 is the credit allowance, T286 the ledger naming)
- owner decision 260919, option C (generated-column bridge): `clip_project_id` is the axis of 13 triggers (`clip_projects_busy_*`, `generation_jobs_clip_owner`, `clip_finalized_job_*`, `video_templates_detach`, …), 2 partial unique indexes and a `clip_projects(id) ON DELETE SET NULL` foreign key. A real `subject_kind`/`subject_id` migration would rebuild all of them and lose the FK to hand-written triggers, so the generic addressing is DERIVED from the columns that stay
- the generated columns must be VIRTUAL, not STORED: SQLite's `ALTER TABLE ADD COLUMN` refuses a STORED generated column, and a table rebuild is exactly what this decision avoids. A VIRTUAL generated column can still be indexed, which is where the lookup cost goes
- expression: `subject_kind` = `CASE WHEN clip_project_id IS NOT NULL THEN 'clip_project' WHEN voice_id IS NOT NULL THEN 'voice' WHEN post_slug IS NOT NULL THEN 'post' WHEN kind='model_experiment' THEN 'model_experiment' ELSE '' END`, `subject_id` = the matching column (`payload` for the experiment dimension, which is how `ActiveModelExperiment` already keys)
- a job may carry TWO attachments — `learn_voice`/`compare_voice_rule` rows hold a voice AND a post ([jobs.sql:92](backend/internal/job/store/queries/jobs.sql#L92)) — so the single derived pair names the OWNING subject only and must not become the only lookup key. `ActiveFor`/`LatestFor` take the dimension the caller asks for and the store resolves it to that dimension's column (`post_slug`, `voice_id`, `clip_project_id`, `payload`); the derived pair serves projections, snapshots and the index. The two-dimension test above is what keeps "is this post busy" and "is this voice busy" answering as they do today
- `ActiveUnattached` keeps today's `post_slug IS NULL AND clip_project_id IS NULL` meaning; express it as `subject_kind=''` so a future attachment cannot silently slip past it
- out of scope, do not touch: the credit reservation/allowance and the cancellation store (T272), any usage/ledger naming (T286), and the SQL of other contexts that joins `generation_jobs.clip_project_id` (clip/store recovery, checkpoints, generation — the column stays, so they keep working)
