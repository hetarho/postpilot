# T253 the browser muxes its output, measures it and stores it before it is shown
> st:todo | ssot:CLIP-158 CLIP-154 CLIP-153 CLIP-27 CLIP-76 | base:CLIP@36 | dep:T252 T243

## goal
The browser's two tracks become one MP4, the browser measures it, the file reaches the project's private storage, and only then is the render successful.

## acceptance
- [ ] the encoded tracks are muxed into an MP4 accepted by the same short-form contract a server render satisfies
- [ ] the browser measures its own output's resolution, frame rate, codec, loudness and duration and reports that verdict with its measurements
- [ ] the file is stored in the project's private storage as a browser-to-storage transfer, never through the RPC body
- [ ] the render becomes successful only once the file is stored; a store that does not finish leaves the render unsuccessful with the previous result standing
- [ ] ② plays and offers the stored file, never the local one, and the local copy is released once stored
- [ ] a failing verdict is recorded as a notice rather than a silently accepted file
- [ ] vitest: a completed render stores before it reports; a failed store leaves the project's previous result and reports the render unsuccessful; the reported measurements come from the produced file
- [ ] go test: the recorded result carries the browser kind and its verdict; a failing verdict lands as a notice
- [ ] verify: `cd backend && test -z "$(gofmt -l .)" && go vet ./... && go build ./... && go test ./...` (`-timeout 30m` for `clip/store`) · `pnpm gen:proto && git diff --exit-code -- backend/internal/gen frontend/src/shared/api/gen agent/internal/gen` · `pnpm --filter ./frontend test` · `pnpm lint` · `pnpm lint:fsd` · `pnpm build:web`

## impl notes
- muxer: a small MP4 muxer from npm rather than a wasm ffmpeg; read its current official docs before adding it (ARCH-33) and pin it through `pnpm add`
- the upload follows the path the originals already take — a signed PUT straight to private storage, the same shape `features/upload-clip-sources` uses — so the rendered bytes never enter an RPC body (CLIP's transfer constraint)
- T243 built the server's side of receiving a verdict; this task adds the client that sends it, together with the stored object's identity, and the server promotes it to the project's latest successful result
- measuring: resolution, frame rate and codec come from the encoder configs the render actually used; duration from the muxed track's own frame count; loudness from T252's measurement of the rendered buffer — the browser does not re-decode its own file to measure it
- ② must not hold a blob URL of the result at all, so nothing can play the local copy by accident (CLIP-158)
