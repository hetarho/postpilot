# T032 Per-IP throttling of the public writes and the auto-releasing account lockout
> st:todo | ssot:AUTH-36 AUTH-37 AUTH-38 AUTH-8 AUTH-9 AUTH-17 ARCH-21 | base:AUTH@2 ARCH@2 | dep:T031

## goal
Refuse an IP that hammers the public write procedures with a stable `TOO_MANY_ATTEMPTS`, lock an account after five consecutive password failures for fifteen minutes with nothing visible on the wire, and let both release themselves.

## acceptance
- [ ] `auth/throttle.go`: `type Throttle` with `Allow(class, ip string, now time.Time) (retryAt time.Time, ok bool)` — fixed windows per class, code-owned in one table: `login` 10 / 5 min · `signup` 5 / 1 h · `resend` 5 / 1 h · `reset_request` 5 / 1 h · `reset` 10 / 1 h · `google` 10 / 5 min; in-memory map keyed by `(class, ip)`, an expired window is dropped when its key is next read and `Sweep(now)` drops the rest; tests cover the boundary count, `retryAt` = window end, isolation between two IPs and between two classes, and the sweep
- [ ] `auth/clientip.go`: `ClientIP(header http.Header, peerAddr, trustedHeader string) string` — with an empty `trustedHeader` the peer address's host is the IP; with `X-Forwarded-For` the RIGHTMOST non-empty entry is used (the one the edge appended) and a client-supplied header is ignored when the setting is empty; tests cover both modes, IPv6 with a port, and a spoofed leftmost entry
- [ ] the auth `Interceptor` gains `throttledProcedures` mapping Login → `login`, Signup → `signup`, ResendVerification → `resend`, RequestPasswordReset → `reset_request`, ResetPassword → `reset` (T033 adds the Google exchange → `google`) and checks the throttle BEFORE any credential work; a refusal is `resource_exhausted`, reason `TOO_MANY_ATTEMPTS`, params `retry_at` (RFC3339 UTC); an httptest rpc test sends 11 logins from one peer and asserts the 11th carries that detail while a different peer still gets `INVALID_CREDENTIALS`
- [ ] the throttle refusal increments no account counter: the same rpc test then logs in correctly from the other peer and proves `failed_logins` stayed 0 for the hammered account
- [ ] config: `CLIENT_IP_HEADER` (empty, or exactly `X-Forwarded-For`; any other value fails at boot); `.env.example` leaves it empty with the reason, `.env.production.example` sets `X-Forwarded-For` because the edge Caddy is the only ingress, DEPLOY.md's env table gains the row; `cmd/api` passes it to the interceptor
- [ ] lockout in `auth.Service.Login`: a wrong password on an existing account calls `RecordLoginFailure(id, now)` (one UPDATE incrementing `failed_logins`, returning the new count); on the 5th consecutive failure the store sets `locked_until = now + 15 min` and `failed_logins = 0` in the same statement (`auth.LockThreshold = 5`, `auth.LockDuration = 15 * time.Minute`) and the service sends `lockNoticeMail` when the account has a reachable email; a correct password calls `ClearLoginFailures`; tests cover count → lock, the mail sent once per lock, and the clear on success
- [ ] while `locked_until > now` `Login` still runs the real argon2id verification and returns `ErrInvalidCredentials` whether the password is right or wrong, records no further failure and sends no further mail; a service test with a frozen clock proves a correct password is refused at 14 min 59 s and accepted at 15 min with the counter at 0 — no operator step, no link
- [ ] the lock is invisible on the wire (AUTH-38): the rpc test asserts a locked-account response equals a wrong-password response byte for byte
- [ ] the unknown-id path is unchanged: no counter, no lock, the dummy verification (AUTH-9)
- [ ] FE: `errors.TOO_MANY_ATTEMPTS` in ko and en renders the `retry_at` param through the datetime adapter (LANG-9), e.g. `요청이 너무 많아요. {{at}} 이후 다시 시도해 주세요.`; the login, signup, forgot-password and reset-password forms show it in their existing failure slot; a test per form
- [ ] gates: ARCH-25 · ARCH-26 · ARCH-28

## impl notes
- the throttle lives in the interceptor rather than in each handler ← one map says which procedures are throttled, the same way `publicProcedures` says which are open; a new public write must be added to both maps in the change that adds it
- limits are fixed windows, not token buckets ← simpler to test and to explain in `retry_at`; the window end is the instant the SSOT asks to carry
- in-memory only: a restart forgets counts and locks stay in the database. AUTH-36 asks for a throttle, not a durable audit; SQLite writes per login attempt would put the single writer on the hot path for an attacker's traffic
- `Sweep` is run by a goroutine in `cmd/api` every minute (`config.ThrottleSweepInterval` constant), the way the orphan sweep is scheduled
- Connect exposes the peer through `req.Peer().Addr` in unary interceptors and `conn.Peer().Addr` in streaming ones; both paths must throttle the same way
- the lock counts only password failures on an existing account; a throttle refusal, an unknown id and a Google sign-in never touch the counter
- the lock notice goes to the account's email only when one is set and not marked unreachable; the two legacy accounts have none and simply release silently
- the 5th failure locks AND resets the counter in one statement so the release needs no second write: after `locked_until` passes the next wrong password starts a fresh count of 1
