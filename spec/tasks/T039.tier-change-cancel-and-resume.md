# T039 Upgrade at once, schedule downgrades and term shortening for the next anchor, cancel and resume
> st:todo | ssot:BILLING-5 BILLING-6 BILLING-7 BILLING-12 BILLING-14 BILLING-15 QUOTA-35 QUOTA-3 QUOTA-28 | base:BILLING@2 QUOTA@5 ARCH@2 | dep:T038

## goal
Give a subscriber every change BILLING decides: an upgrade charges the difference now and raises this cycle's lot, a downgrade or annual→monthly waits for the next anchor and can be cancelled or replaced, and cancellation is a scheduled stop that can be switched back on.

## acceptance
- [ ] `billing.proto`: `ChangeSubscription{Plan plan, Term term}` → `{ Subscription subscription, bool applied_now }`, `CancelScheduledChange{}`, `CancelSubscription{}`, `ResumeSubscription{}` → each `{ Subscription subscription }`; `pnpm gen:proto` committed
- [ ] `billing.Service.ChangeSubscription(ctx, userID, tier, term)` classifies against the `active` row (`SUBSCRIPTION_REQUIRED` when none): same tier and term → `NO_CHANGE`; tier rank up with the same term → UPGRADE now; tier rank down, or `annual → monthly` at any tier, or `monthly → annual` → SCHEDULED for `term_end`; a request that changes BOTH tier and term at once is refused fail-closed with `CHANGE_UNSUPPORTED` (invalid_argument) — one change per request; a scheduled change replaces any existing one rather than stacking, and an upgrade clears a scheduled downgrade (QUOTA-35); tests cover every branch
- [ ] UPGRADE: `diffCents` = monthly price difference for a monthly term, or `remainingWholeMonths × monthly difference` for annual where `remainingWholeMonths` = the number of anchor windows from the next anchor up to `term_end` (a test pins 7 for a term with seven anchors left, 0 in the final month → nothing charged, only the lot rises); charge `KRWFor(diffCents, rate)` with `orderID = "upg:<user>:<now RFC3339>"` outside the tx; on success in one tx: `tier` updated, `charge` + `tier_change` events; then `Plans.AssignTier(tier)` and `Credits.RaiseMonthlyLot(userID, MonthlyCredits(new) − MonthlyCredits(old))` — only the current month's lot rises, the anchor never moves; a second upgrade in the same cycle charges and raises only the difference from the tier then in force; a failed charge appends `charge_failed` and changes nothing (`CHARGE_FAILED`)
- [ ] SCHEDULED: `scheduled_tier`/`scheduled_term` written with a `cancel_scheduled`-style event kind `change_scheduled` (add it to the CHECK by rebuilding `billing_events` in migration `0031_billing_change_scheduled.sql`, following 0027's shape) and applied by `RunDue` at `term_end` (T038's case b): the next term is charged at the SCHEDULED tier and term and the row moves to them; `CancelScheduledChange` clears both columns (`NO_SCHEDULED_CHANGE` when none); tests cover replace-not-stack, apply at the anchor, and cancel
- [ ] `CancelSubscription`: `auto_renew = 0`, `cancel_scheduled` event, clears any scheduled change; the tier and every granted credit stand until `term_end` (T038's case c performs the stop and the mail); `ResumeSubscription` before `term_end`: `auto_renew = 1`; after `term_end` there is nothing to resume (`SUBSCRIPTION_REQUIRED`); tests cover both and that a cancelled-then-resumed row renews normally
- [ ] `QuotePrice` gains an `upgrade_from` reading: `QuoteChange{Plan plan, Term term}` → `{ int32 usd_cents, int64 krw, …, bool applied_now, string effective_at }` so the screen can show what an upgrade costs now or when a scheduled change lands; served by the same classification code as `ChangeSubscription`
- [ ] FE `/plans` for an active subscriber: a higher rung's action reads `업그레이드 / Upgrade` and opens the checkout with the `QuoteChange` figure (`지금 결제 / charged now`), a lower rung's action reads `다음 결제일부터 / From the next billing date` and confirms in a `Dialog` (no charge, states the effective date), the current rung shows `지금 쓰는 플랜`; `free` for a subscriber shows `구독 해지는 결제 관리에서 / Cancel from Billing` as a link, not an action

## impl notes
- `monthly → annual` at the same tier is not decided by BILLING-5/6 (they speak of tier upgrades and of annual→monthly); it is treated as a SCHEDULED change ← charging a year now would need day-level proration of the running month, which BILLING-17 rules out; record the reading in the result for update-ssot BILLING; a combined tier+term change is likewise undecided and is refused rather than invented
- "remaining whole months" for an annual upgrade counts anchor windows that have not started yet; the running window is never charged for (BILLING-17: only whole-month differences)
- the upgrade order is: charge → tier → lot, and a failure after the charge is repaired like T038 (the unique order id lets the next attempt find the payment); the tier write and the lot raise stay two statements as T021 recorded, with the error naming the half that failed
- rank comparison uses `plan.Plan.Rank()` — this is the one place the product compares tiers, and only to classify a change as up or down (QUOTA-2 still gates nothing on rank)
- a scheduled change and a cancellation are mutually exclusive on the row: cancelling clears the schedule, and scheduling while cancelled turns auto-renew back on (the owner asked for a future tier, which implies renewing) — pin both in tests
- the `billing_events.kind` CHECK grows by rebuild (SQLite cannot alter a CHECK); the Down half maps `change_scheduled` back to `cancel_scheduled`
