# T250 the browser states whether it can render, and refuses with one reason
> st:todo | ssot:CLIP-155 CLIP-153 CLIP-34 | base:CLIP@37 | dep:T242

## goal
② knows before it offers the browser kind whether this browser can produce the output contract, and a browser that cannot says which one reason stops it.

## acceptance
- [ ] ② decides the browser kind's availability from the encoders this browser actually admits for the project's ratio and the memory it reports, and from nothing else
- [ ] a browser that cannot render says exactly one reason — the capability is absent or the memory is insufficient — and leaves the server kind as the choice, including where CLIP-153 would have offered the browser kind first
- [ ] an original the page does not hold never refuses the kind: the probe does not look at the originals at all
- [ ] no render ever changes kind on its own
- [ ] the probe makes no network call and runs no encode
- [ ] vitest: each of the two reasons is produced in isolation with the other satisfied; an admitting browser offers the kind; a refusing one never starts a render and a project with no render falls back to server rather than naming the browser kind
- [ ] verify: `pnpm --filter ./frontend test` · `pnpm lint` · `pnpm lint:fsd` · `pnpm lint:style:probe && pnpm lint:style` · `pnpm build:web`

## impl notes
- the probe is `VideoEncoder.isConfigSupported` for H.264 High at the ratio's canvas and 30 fps, plus `AudioEncoder.isConfigSupported` for AAC-LC at 48 kHz, both from CDS-52's V12; the whole WebCodecs surface being absent is the same one reason
- AAC encoding is the narrow one — a browser may admit the video config and refuse the audio; a plan whose sources all have original sound off needs no audio track, so the audio probe applies only when the plan carries audio
- memory: `navigator.deviceMemory` where present against a floor in `shared/config`, never a device or browser name
- the originals are NOT a refusal any more (CLIP-155 at r37): one the page does not hold is fetched for the render under CLIP-23, which T251 owns. `useGenerateClip.render`'s `readyClipBatch` + fingerprint check stays exactly where it is — it guards the RETAINED originals a render of either kind needs, which is a different thing from what this page currently holds
- the probe is pure logic over injected capability answers, in `entities/clip-project/model`, so the test does not need a real encoder; the thin wrapper that asks the real globals lives in `shared/lib`
- new ko/en keys under `render.refusal.*` for the two reasons
- this task replaces the single "unavailable" flag T247 set to true with the real probe; the fallback T247 already tests (a project with no render naming server where the browser kind is unavailable) must keep passing
