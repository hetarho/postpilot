# T353 Toggling 기억 사용 keeps the post's 목표 글자 수
> st:todo | ssot:POST-20 POST-71 MEM-18 ARCH-24 | base:POST@11 MEM@1 ARCH@9 | dep:-

## goal
- Ticking or unticking ①'s `기억 사용` saves only that flag in effect: the post's stored target length survives, as POST-20 and MEM-18 decide; today the toggle clears it.

## acceptance
- [ ] On a post with a stored target length (e.g. 1500), ticking `기억 사용` sends `SavePostGenerationOptions` with `useMemory: true` and `targetLength: 1500`, and after the refetch the brief still shows 1500 and the box is ticked.
- [ ] Unticking it keeps 1500 the same way; on a post with natural length (no target) the toggle sends no `targetLength` and the post stays at natural length.
- [ ] The tag count is untouched by the toggle, as today (the server keeps an absent `tag_count`).
- [ ] The frontend fake mirrors the server exactly: an absent `targetLength` on `SavePostGenerationOptions` stores natural length, so the test fails on HEAD's `saveUseMemory` and passes after the fix.
- [ ] Tests: `features/use-post-memories/ui/UseMemoriesField.test.tsx` new cases `ticking keeps the stored target length` and `a natural-length post stays natural` (read `generationOptionSaves` and `memoryOptionSaves` from `frontend/src/test/posts.ts`); `pages/editor/ui/EditorPage.test.tsx` one case that sets 목표 글자 수, ticks `기억 사용`, and still reads the number after the refetch.
- [ ] Verify: `pnpm --filter ./frontend test` · `pnpm lint` · `pnpm lint:fsd` · `pnpm lint:style:probe && pnpm lint:style` · `pnpm build:web`

## impl notes
- Found while writing T349. The wire contract is asymmetric at HEAD: on `SavePostGenerationOptionsRequest`, an absent `tag_count` and `use_memory` keep the stored value, but an absent `target_length` means natural length (POST-20: NULL is natural), so the server stores NULL.
- Server side, `internal/post/service.go` `SaveGenerationOptions` (line 780) compares `found.TargetLength` with the nil it received and writes nil. `rpc/handler.go:79` maps an absent `target_length` to nil.
- `frontend/src/entities/post/api/useGenerationOptions.ts:34` `saveUseMemory(slug, useMemory)` sends `{ slug, useMemory }` only. Its doc comment ("sending only the flag cannot disturb the two numbers the brief saves") is wrong for `targetLength`.
- Fix on the client, not the wire: `saveUseMemory(slug: string, useMemory: boolean, targetLength: number | undefined)` sends `{ slug, useMemory, targetLength }`, and the doc comment says why the number rides along.
- The argument is required, not optional, so a future caller cannot forget it; `undefined` is the explicit natural-length value.
- Changing the server to presence semantics would change what every existing `save` call means (it sends `undefined` to clear), so the wire stays as it is.
- `features/use-post-memories/ui/UseMemoriesField.tsx` gains a `targetLength?: number` prop and passes it through. `pages/editor/ui/EditorGeneratePanel.tsx`, its only caller, passes the post draft's `targetLength`, the value `GenerationBrief` already reads.
- `frontend/src/test/posts.ts`'s `savePostGenerationOptions` already mirrors the server (`row.targetLength = req.targetLength`), so it needs no change. Keep it that way, because it is what makes the new test fail on HEAD.
- T349's `saveQualityRules(slug, ids, targetLength)` resends the target length for the same reason; this task establishes that shape first.
- Out of scope: the brief's own save (`save`), which already sends both numbers; the tag count, which the server keeps when absent.
