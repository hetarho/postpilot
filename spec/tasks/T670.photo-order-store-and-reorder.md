# T670 Store the owner's photo order and reorder it

## goal
A post's photos carry a stored position that every photo read follows, a confirm appends at the end, and a `ReorderImages` RPC rewrites the order.

## acceptance
- [ ] migration 0158 adds `images.position INTEGER NOT NULL DEFAULT 0` and backfills each post's photos 0..n-1 by `created_at, id`; an index on `(post_slug, position)`
- [ ] `ListImagesByPost` orders by `position, id`; a confirmed photo takes `MAX(position)+1` of its post in the confirm's own insert (0 for the first)
- [ ] `ReorderImages(post_slug, image_ids)` with ownership through `writablePost`: the list must be exactly the post's current photos (each once, no video ids), otherwise `FailedPrecondition` and nothing changes; it writes positions 0..n-1 in one transaction with `AdvancePostInputRevision`; a published post refuses it as `DeleteImage` and `RotateImage` do (POST-74); an unchanged order is a no-op success that advances nothing
- [ ] proto, Connect handler, generated Go and TS (`pnpm gen` / buf, the EOF normalizer keeps generated TS as is) and the RPC's auth/ownership tests
- [ ] tests: store test for the confirm append and the reorder write (`backend/internal/post/store`), service tests for the set mismatch, the published lock, the no-op and the input revision (`backend/internal/post`), the default-deny published-lock store test extended with the reorder statement (`published_lock_store_test.go`)
- [ ] generation receives photos in position order with no generation code change (`cmd/api/adapters_generation.go` already iterates `found.Images`)

## impl notes
- position is per post and dense after a reorder; a delete leaves a gap, which is harmless because only the order is read
- the append rides the confirm insert as `INSERT … SELECT … COALESCE(MAX(position), -1) + 1 FROM images WHERE post_slug = ?`, so two confirms in one post never read the same max outside a statement
- keep every `.sql` ASCII-only and write a nullable column as bare `TEXT`-style types (sqlc quirks); `position` is NOT NULL so it generates `int64`
- video ordering is unchanged (videos follow photos by `created_at`, POST-116)
- reuse the existing refusal plumbing: a stale list maps to the code the client already treats as "refetch" (`FailedPrecondition`); if a new app-failure reason is introduced, add its params to the frontend app-failure allowlist
- pre-alpha: no compatibility path beyond the backfill
