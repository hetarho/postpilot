# TMPL post templates (템플릿)
> r29 | Owner-scoped post forms made through a guided, visually previewed target wizard with owner-named sections, explicit literal, instruction and supplied-fact boundaries and minimum tag seeds.

## decisions
- TMPL-1 [o] a template decides the form of a post; three authored axes stand beside each other and each owns one question — the voice decides how sentences sound (VOICE), the template what form the post has and what each of its places is about, a guideline what kind of writing is wanted (GUIDE); a post combines at most one voice and at most one template ← prose about shape must be re-derived by the model every run, cannot require a literal line, and cannot bind output to the attachments
- TMPL-2 [o] a template has six authored fields — `name`, `description`, `body`, `title_area`, `target_length`, `tag_count` — plus timestamps; `body` is the single source of truth for the body's shape and `title_area` for the title's (→TMPL-50): what the database stores, what the prompt receives after expansion, and what the builder round-trips; the builder is a parser plus a renderer over that string and never a second representation; the two numbers stand outside the body, are seeds for the post's own options and reach no prompt (→TMPL-47)
- TMPL-3 [o] every store query and RPC is scoped by the authenticated user and no request carries a user id; a foreign template id is `NotFound` like an unknown one; `templates_id_user` is the composite target `posts.template_id` points at, so a post can never name another account's template; `templates_user_name` keeps display names unique per account
- TMPL-4 [o] there is no tombstone: a deleted template is gone and its name is free again at once ← unlike a voice, a template is not something a post was written in, only something the next machine run is told
- TMPL-6 [o] field rules:
  - `name` trimmed, non-empty, ≤ `TEMPLATE_NAME_MAX_CHARS` (40), unique among the account's templates after trim (`AlreadyExists`, `TEMPLATE_NAME_TAKEN`)
  - `description` trimmed, may be empty, ≤ `TEMPLATE_DESCRIPTION_MAX_CHARS` (200), management copy that never reaches a prompt
  - `body` trimmed at the edges only, non-empty, ≤ `TEMPLATE_BODY_MAX_CHARS` (4000) and it must parse
  - `title_area` trimmed at the edges only, may be empty, ≤ `TEMPLATE_TITLE_AREA_MAX_CHARS` (200) and it must parse under the title area's grammar (→TMPL-50)
  - creating beyond `TEMPLATE_MAX_PER_ACCOUNT` (50) is `FailedPrecondition`, checked inside the insert transaction
  - `target_length` and `tag_count` are nullable and NULL is 값 없음, a present `target_length` is within `POST_TARGET_LENGTH_MIN` … `POST_TARGET_LENGTH_MAX` (100 … 10,000) and a present `tag_count` within `POST_TAG_COUNT_MIN` … `POST_TAG_COUNT_MAX` (→POST-20 →POST-63), each range the same on both sides, a violation being `InvalidArgument` `TEMPLATE_NUMBER_OUT_OF_RANGE` with `field` `min` `actual` params and `max` when the field has a ceiling
  - limits are Unicode scalar-value counts on both sides
  - a length violation is `InvalidArgument` `TEMPLATE_FIELD_TOO_LONG` with `field` `max` `actual` params
  - the backend is authoritative and the frontend mirrors ten limits in `entities/template/config` — the name, description, body and title-area ceilings, `TEMPLATE_PHOTO_ROW_MAX`, the three `TEMPLATE_ASK_*` limits, `TEMPLATE_REQUEST_MAX_CHARS` and `TEMPLATE_MAX_PER_ACCOUNT` — for live counters and the refusals it states before a save or a request
- TMPL-7 [o] parsing is part of validation: a body that does not parse has no meaning and cannot be saved; the refusal is `InvalidArgument` `TEMPLATE_PARSE_FAILED` with allowlisted `line` and `reason` params ← the editor must point at the offending line without parsing wire prose
- TMPL-8 [o] UpdateTemplate is presence-based with one statement per present field inside one transaction, so an omitted field is never named by any statement and no read-modify-write can restore a stale value
  - a present empty `description` or `title_area` clears it, a present empty `name` or `body` is refused
  - the template screen sends all six fields in one call because they are one draft edited in one place, and each number is sent on every save with absence meaning 값 없음 ← the screen always holds both, so a second presence meaning would only give an unset number two ways to be written
  - the `body` is never trimmed on its way to the server ← it is the canonical serialization
- TMPL-9 [o] DeleteTemplate removes the template and returns `detached_posts`; the detach is the schema trigger `templates_detach_posts_on_delete` running in the delete's own transaction ← `ON DELETE SET NULL` on a composite child key would null `posts.user_id` too; the delete also cascades the template's `guideline_templates` rows while every guideline survives (one left with no links applies nowhere and lists as 적용 대상 없음); no post, content, photo, guideline or history is deleted; frozen payloads and snapshots keep the rendered body; the confirmation names detached posts only
- TMPL-10 [o] assignment to a post is presence-aware with three meanings (absent preserves, present-empty clears to 없음, present value assigns), validated before anything else in the request, allowed in every status except `published` (→POST-74) and while a job runs, seeds the post's two generation options when a value is assigned (→TMPL-48), and touches no content, revision, baseline, finalization or learn eligibility ← nothing is ever learned from a template; `TemplateRef {id, name}` reaches the post through the consumer-owned `TemplateDirectory` port (→POST-26)
- TMPL-11 [o] the template is resolved once, at enqueue, and what gets frozen is the rendered body — filled with the post's answers to the template's data fields (→TMPL-45), its photo places and repeats rendered unbound (→TMPL-21) ← resolving inside the freeze is what makes "editing an answer or the template after the start cannot change the run" true
- TMPL-12 [o] one `[글 템플릿: {name}]` section enters the write and revise prompts after the voice projection — after the static rules for a post with 말투 없음 — and before the per-post material, with `[작문 지침]` after it; it carries a fixed grammar legend, the rendered body between `---` fences, then a fixed precedence sentence, which names no voice for 말투 없음 (→GEN-74); absent a template the builder adds no bytes at all ← the position is load-bearing twice: the voice-profile prefix stays byte-stable across posts of different templates, and the section stays in the stable half so every revision re-injects the identical block
- TMPL-13 [o] the heading, legend and precedence sentence never use the word 지침 ← the `[작문 지침]` section follows one section later, and one word must not name two different things one section apart; the framing stays Korean for every target language (it frames user-authored text, not the output-language contract) and the target language outranks a conflicting language instruction inside a template (LANG)
- TMPL-14 [o] handlers read the frozen copy from the payload and never the live row: editing or deleting the template after StartGeneration or StartRevision returns — including across a restart-resume or an explicit retry — cannot change the prompt; a template deleted between the save and the start is simply absent; a payload with no template field decodes as no template
- TMPL-15 [o] MODEL tests freeze template identity/version/rendered body in the common snapshot unless template is the chosen factor; template tests freeze one validated candidate body per entrant while retaining all shared material, guideline texts and numeric options. Recorded names/versions remain readable after source changes or payload retention.
- TMPL-16 [o] templates are never selected or inferred automatically from post material, and the product ships no finished template or heading: it ships the wizard's section-role catalog alone (→TMPL-72) ← the owner's own headings keep posts made on this platform different from one another. The wizard's explicit heading suggestions (→TMPL-73), EDIT refinement of saved templates and MODEL candidate tests are the only AI template actions; listing/manual typing/parsing/preview/selection performs no AI work, and observation sees no template.
- TMPL-17 [o] the grammar is XML-tag delimited ← an LLM reads tag-delimited structure most reliably and the write prompt already asks for protojson, so a second brace language is the one thing to avoid; closing tags make nesting decidable; and attributes carry the machine-readable parts
- TMPL-18 [o] five constructs:
  - bare text is literal (verbatim in prompt and post)
  - `<write>메뉴 소개</write>` is prose the writer writes here about what its text names (tags intact in the prompt)
  - `<slot kind="photo" count="n"/>` is a place where photos the writer chooses stand, `count` the number of photos the author suggests standing together there (a marked place in the prompt; single photos or photo groups in the post →GEN-77)
  - `<repeat each="photo">…</repeat>` is a part the writer repeats once per photo group of its storyline
  - `<ask label="제목">…</ask>` takes the facts for its position from the post's author instead of the model; `required="true"` marks an answer required before a new write (→TMPL-43 →TMPL-68)
  - `slot` is self-closing only, `kind` is required and the only authorable value is `photo`, `count` is optional (1 … `TEMPLATE_PHOTO_ROW_MAX`, default 1)
  - `place` · `link` kinds and `slot`'s `label` attribute are not authorable and parse only as read-compatibility for stored bodies (→TMPL-37)
  - `repeat` requires `each` whose only value is `photo` and may hold literal · write · slot
  - `write` holds text only
  - everything else is a parse error with no lenient fallback ← a body that half-parses would silently drop the structure the user asked for
- TMPL-19 [o] a body parses to an ordered node list
  - literal and text-holding nodes keep their raw source slice and serialization re-emits those slices, so parse → serialize is byte-exact by construction for hand-written and builder bodies alike
  - `<` opens a tag when followed by an identifier and then whitespace, `>` or `/`, and closes one when followed by `/`, an identifier and at once `>` (`</write >` is literal text)
  - anything else is literal text (`3 < 5` needs no escape)
  - outside write and ask text an identifier that is not a tag the grammar names is `unknown_tag`, not literal ← a mistyped tag printing itself into every post is worse than needing `&lt;` for a rare literal tag
  - inside write and ask text every opening tag, the grammar's own or an unknown one, is `malformed_tag` and every closing tag but the element's own is `unexpected_close`
  - entities `&lt;` `&gt;` `&quot;` `&amp;` decode when a node's text or an attribute value is read, never in the stored slice
- TMPL-20 [o] a body that does not parse cannot be saved and every error names a 1-based line and one reason:
  - `unknown_tag` · `unclosed_tag` · `unexpected_close` · `malformed_tag` (unparsable, unknown or duplicate attributes, `slot` with a closing tag, a self-closing `write` or `repeat`, a tag inside write or ask text, or `count` on a slot that is not a photo) · `missing_attribute` · `unknown_slot_kind` · `unknown_repeat_each` · `nested_repeat` · `empty_write` · `invalid_count` (not an integer in 1 … `TEMPLATE_PHOTO_ROW_MAX`) · `duplicate_ask_label` · `ask_in_repeat` · `too_many_asks` (more than `TEMPLATE_ASK_MAX_PER_BODY` across the title area and the body together) · `not_in_title` (a slot or repeat inside the title area)
  - each error naming the area it sits in, an `ask` with no `label` or an empty one being `missing_attribute`
  - the Go parser (`backend/internal/template`) and the TypeScript parser (`frontend/src/entities/template/lib`) are tested against one shared fixture file `backend/internal/template/testdata/grammar/cases.json` plus a committed differential corpus, and a new rule lands in the fixture first ← that file is the only mechanism keeping two implementations of one grammar honest
- TMPL-21 [o] a photo place binds no photo ← binding the attached photos in attachment order put each where the upload order said, which is whichever upload finished first and says nothing about the visit
  - the rendered body marks each place with its `count` as a suggested group size, and the writer chooses which attached photos stand there, and whether alone, as one group or as several, from the storyline it follows (→GEN-67 →GEN-70), by what the section around the place is about
  - a `<repeat each="photo">` renders once, marked as a part the writer repeats once per photo group its storyline gives there
  - zero photos drops every repeat block whole including its literals
  - rendering preserves literal text and writing-instruction meaning in distinguishable roles (→TMPL-70)
  - nothing expands per photo, so no expansion bound exists
  - photo placement follows section meaning and GEN-82; upload/capture order establishes no visit or event chronology

- TMPL-22 [o] a run's output is taken as the model wrote it: its single photos and photo groups pass the attachment filter like any other block (→GEN-2 →GEN-78), and literal fidelity, section order and whether every photo token came back are neither verified nor repaired — no deviation fails, retries or discards a usable generation
- TMPL-24 [o] /templates is a named directory of the Naver Blog channel (→THEME-38) with shared one-target rows showing name, description, saved usability and EDIT-22 unpublished/job state; post count is operational metadata rather than draft status. 새 템플릿 opens the wizard (→TMPL-71), and unified tests can prepare/adopt template candidates.
- TMPL-25 [o] saved template detail first shows the named saved structure and state, then offers AI editing or direct editing against one captured baseline under EDIT-14/21. New creation and explicit Save retain the domain name/description/composition and number/link rules; unsaved changes are retained or explicitly discarded, and confirmed publication supplies the new clean baseline.
- TMPL-26 [o] the composition is authored through one control in two modes over the same `body` string: the block builder (default) and `원문`, a plain text view of the stored body with the title area as its own field above it, the 형식 안내 staying body-only (→TMPL-41)
  - both edit the one draft behind the one 저장, switching is lossless because neither holds a second representation (→TMPL-2); ordinary composition shows grammar only inside `원문`, with the explicit technical-inspection exception below ← the builder supports ordinary authoring while stored grammar also accepts outside-AI output (→TMPL-41)
  - one row is one block, collapsed to its kind name (→TMPL-36) and a one-line summary of its own text so the rows read as the outline of the post
  - a `repeat`'s children are a nested list beneath it, always visible
  - the title area and the body are two compositions, each with at most one row expanded at a time, whose fields and delete edit in place
  - `원문` and its 형식 안내 (→TMPL-41) sit behind the editor's 고급 entry ← a first-time owner edits through blocks and never meets the grammar unless they ask for it
  - explicitly opened technical inspection under MODEL-94/95 may display grammar for post requests and setting authoring (→POST-115 →EDIT-24); ordinary authoring replies and prose previews remain free of raw syntax

- TMPL-27 [o] each of the two compositions carries its own always-visible add toolbar, which inserts at that composition's current position — after the row last touched, and inside a `repeat` when that is where the position is — with that position drawn in the list before the click
  - an aim whose block is gone resolves to the end, where the marker is drawn too ← one toolbar serves every position only while the position it inserts at is visible
  - only the body's toolbar is sticky to the top ← two sticky bars would stack under the header, and a title area is a line or two long
- TMPL-28 [o] reordering offers both pointer drag and move buttons ← HTML5 drag events do not fire on touch and the base breakpoint is a 360 px phone
  - both are scoped to a sibling group (a `repeat`'s children are their own list) ← the grammar cannot express a block that left its repeat
  - drag events stop propagating so a nested list's drag never moves its parent
  - `SortableList` carries a `compact` density for the collapsed rows
- TMPL-29 [o] the controlled composition editor retains its complete and incomplete rows in the EDIT working draft; changes remain unpublished and preview uses the last valid parse with a clear current error. AI/direct/raw mode changes retain the same user work, and publication requires a fully valid current composition.
- TMPL-30 [o] a body the parser cannot read (pasted or edited outside the app) shows the composition as unreadable and offers exactly two actions: `원문에서 고치기`, which opens `원문` with the parse error at its line in whichever area failed (→TMPL-20), and `구성 비우고 다시 만들기` on the body or `제목 비우고 다시 만들기` on the title area, which empties that composition in the draft; name and description stay editable and nothing is written until 저장 ← inventing a structure the author did not write would be worse than saying so; a body that does not parse still cannot be saved from either mode (→TMPL-7)
- TMPL-31 [o] the directory query is re-read on every mount (`staleTime: 0`, `refetchOnMount: 'always'`) ← `post_count` is a projection over posts that no template mutation can invalidate, and it is the number the user confirms a destructive detach against; a rename also invalidates the post caches because the name is projected onto every assigned post
- TMPL-32 [o] the editor and `/posts/new` show a 템플릿 picker defaulting to 없음 on ①'s dock row beside the 말투 picker (→POST-51) with an `sr-only` label and no description line; selecting writes a presence-aware patch through the draft queue; on a create 없음 sends no field at all
  - it lists 없음, the account's templates, then `새 템플릿 만들기`, which opens the wizard (→!TMPL-71) ← an owner with no template otherwise meets a picker whose only choice is 없음; the 말투 picker offers its creation the same way (→~POST-101)
  - the wizard opened from a saved post returns to that post on 저장 with the new template assigned through the ordinary assignment (→!TMPL-10 →TMPL-48); opened from an unsaved draft it returns to a new draft with that template selected; leaving the wizard unsaved assigns nothing
  - the select stays enabled while a job runs and says the running job keeps the template it started with
  - a failed directory read shows a failure with a retry, never an empty directory ← that would leave clearing as the only available action
  - the post list shows the template name beside the voice for an assigned post
- TMPL-33 [o] the composition editor lives in `entities/template/ui` ← it performs no mutation, it is a controlled input over one of the entity's own fields, and the shape of a block is the entity's business
  - the create and update hooks (`useCreateTemplate`, `useUpdateTemplate`) live in `entities/template/api` beside the reads ← a bare hook nobody renders is entity `api` (→ARCH-14)
  - the page composes the controlled editor with the shared EDIT draft and publication actions; session revision owns the working state
- TMPL-34 [o] automatic template inference/selection, unsolicited AI writing, finished seed templates or headings and automatic place/map/platform lookup are outside templates. The wizard's role catalog and explicit heading suggestions (→TMPL-71–74), conversational editing of saved templates and seed-free actual-writing tests follow TMPL/EDIT/MODEL.
- TMPL-35 [o] the shared fixtures pin two cross-language cases: Go and JS agree on blank characters (`U+FEFF` vs `U+0085`), and a label containing `"` — a data field's title or a stored slot's — round-trips through `&quot;` into a body the builder's own parser accepts
- TMPL-36 [o] every block kind is named by what the reader of the finished post gets, in plain Korean a first-time user needs no legend for, and the add toolbar shows each name with its one-line help on the button itself rather than in a tooltip
  - the four names are `AI가 쓰는 글` (write) · `고정 문구` (literal) · `사진` (photo) · `사진마다 반복` (repeat), and the collapsed row badge uses the same name as the toolbar button
  - verb-nouns that name the mechanism (작성, 삽입, 반복 alone) are not used ← a name like 작성 does not tell what it adds to the post; a name and its help must answer that without a click
- TMPL-37 [o] there is no `place` or `link` position: a map, address, link or any other thing the author fills in later is written as a 고정 문구 in the author's own words (e.g. `지도는 아래에`) ← a reserved position gives the model a token to copy and the user a placeholder to hunt for after pasting, and a fixed line does the same job with nothing to fill
  - a stored body carrying a `place`/`link` slot still parses (→TMPL-18) and is literal text wherever it appears: the builder shows it as a 고정 문구 row whose text is the slot's label (falling back to 지도 · 링크), so no saved body is unreadable (→TMPL-30)
  - a composition edit writes it back as that literal text, while a save that leaves the composition untouched sends the body as stored
  - expansion renders it as the same text, so no run carries a slot token, a slot block or a slot marker and nothing downstream renders one
  - the app fills nothing (TMPL-34 stands)
- TMPL-38 [o] a photo position carries how many photos the author suggests standing together there: `count` 1 … `TEMPLATE_PHOTO_ROW_MAX` (3), default 1, a count above 1 suggesting one photo group of about that size while the writer decides the group, its layout and whether to group at all (→TMPL-21 →GEN-77) ← Naver shows several photos as one collage or slide and a template that could only stack them could not describe the posts people already write
  - it is edited on the expanded 사진 row with a stepper and read in the collapsed summary as `n장 묶음`, a count of 1 as `1장`
  - inside a 사진마다 반복 the help says the part repeats once per photo group of the story
  - the ceiling is `PHOTO_GROUP_MAX` (3) ← a count suggests one group, and no group holds more (→GEN-77)
  - a stored count above the group cap renders as the cap
- TMPL-39 [o] a photo position's suggested group travels as a photo group: the writer puts the photos it chooses there as one GALLERY block with one caption, or as single photos (→GEN-77), and export maps a group to one place (→EXPORT-26)
- TMPL-41 [o] `원문` carries a copyable 형식 안내: one button puts on the clipboard a self-contained instruction a user can hand to any outside AI (ChatGPT, Claude, …) so it writes a body in our format — the five authorable constructs of →TMPL-18 with their meaning — a `<write>` or an instructing `<ask>` naming what stands at its place and never how to write it (→TMPL-57) — the rules that make a body refuse (→TMPL-20), the size ceilings, one worked example, and the instruction to answer with the body only ← the owner wants to describe a post to an AI and import the result rather than click a shape together, and an AI can only write our format if it is told the format exactly
  - it teaches no read-compatibility-only construct (`place` · `link`, `slot`'s `label`)
  - the prose follows the UI language (LANG) while tags, attributes and the example stay as they are
  - the backend owns it as code — the prose in both UI languages, the example and the limits — and the client reads it through the template service for 형식 안내 복사, so copied guidance and EDIT template authoring use the same backend-owned grammar version (→EDIT-13) ← one grammar must have one teacher, changed in the same commit as the parser; a stored row could teach a grammar the parser refuses
  - it is prompt text, code under LANG-27, not a UI catalog resource (LANG-7 stands); a read that fails shows the failure with a retry, never an empty or stale guide
  - its example is parsed by the real parser in a test, so an example that drifted from the grammar fails the build
  - the guide and the grammar rule change together — a construct added to or removed from TMPL-18 lands in the guide in the same rev
- TMPL-42 [o] import is pasting or typing into `원문`: the text becomes the draft's body byte-exact (no trim, no normalization →TMPL-8 →TMPL-19), is parsed on the client as the user types with the first error shown at its 1-based line with its reason in plain words (the same `builder.reasons` copy the builder uses), and 저장 stays disabled while it does not parse or exceeds `TEMPLATE_BODY_MAX_CHARS`, with the live counter beside it
  - switching back to the builder reseeds the rows from the body (→TMPL-29) so what was pasted is what the outline shows
  - a pasted body with a `place`/`link` slot is accepted as read-compatibility and shows as 고정 문구 (→TMPL-37)
  - `원문 복사` puts the current body on the clipboard so an existing template can be handed to an AI as a sample
  - the server applies the same field rules and parse refusal as to any body and is authoritative (→TMPL-6 →TMPL-7)
- TMPL-43 [o] `<ask label="총평 별점">지시</ask>` is a position whose facts the post's author supplies instead of the model inventing them ← a template can require a section the memo has no way to anticipate (a rating, a price, a date), and prose about a shape cannot ask a question
  - `label` is required, non-empty, ≤ `TEMPLATE_ASK_LABEL_MAX_CHARS` and unique across the body and the title area, and it is both the answer's key (→POST-62) and the title shown over the field in the write screen
  - `required="true"` is optional and its only accepted value is `true`; an absent attribute means optional, and any other value is `malformed_tag` ← existing templates keep their current behavior without migration
  - an empty element puts what the author typed on the page verbatim (the 고정 문구 flavor); an element holding text asks the author for the facts of that position, shows the question as field help on ①, and names the position's topic for the writer (the AI가 쓰는 글 flavor, →TMPL-57)
  - it holds text only and may not appear inside a `repeat` ← how many fields a template asks for is the template's own answer and must not depend on how many photos this post happens to carry
  - a body carries at most `TEMPLATE_ASK_MAX_PER_BODY` of them ← a form long enough to push the memo off a 360 px screen would cost more than the invented sentence it prevents
- TMPL-44 [o] the builder offers 데이터 받기 as a switch on the AI가 쓰는 글 and 고정 문구 rows and on no other kind ← those are the two positions whose text a post decides, a 사진 holds an attachment
  - turning it on adds a 제목 field seeded from the row's own text and the row keeps its kind with its badge extended, turning it off restores the authored text and drops the title
  - a data-receiving row offers 필수 입력; on emits `required="true"`, off removes that attribute, and a parsed row round-trips it through the builder
  - on a row inside 사진마다 반복 the switch is shown disabled with its reason in place ← a control that silently disappears in a nested list reads as a bug
  - the flip is an edit of that block like any other and makes the draft dirty by itself
- TMPL-45 [o] a field is resolved at enqueue against the post's answers, before expansion:
  - an optional field whose switch is off or whose text is blank after trimming has its whole `ask` node removed, so the frozen body neither names it nor leaves a gap and a template with the field off produces a byte-identical prompt to one that never carried it ← the guarantee being bought is that the model is never handed a section it has no facts for, and a blank answer must not buy less than the switch does
  - a required field is never removed; a blank or disabled answer is refused before a new writing job is enqueued (→TMPL-68)
  - a field with a value renders the verbatim flavor as literal text and the AI가 쓰는 글 flavor as what the position is about with the value beside it as that position's facts
  - the frozen copy rules apply as to the body, so editing an answer after a start cannot reach the run (→TMPL-11 →TMPL-14)
- TMPL-47 [o] a template carries two optional generation numbers beside its shape, `target_length` and `tag_count`, each saying what the posts this template shapes usually want and each meaning 의견 없음 when left unset; they are seeds for the post's own options and nothing else — no prompt, payload, freeze, snapshot or experiment hash reads a template's number, and a run freezes the post's values (→GEN-5 →GEN-46) ← the two numbers belong to the shape that decides them, but a second place a prompt could read a length from would give one run two answers to one question
  - tag_count seeds the minimum from POST-63; quality selection stays under GEN-50

- TMPL-48 [o] assigning a template to a post copies each number the template has set onto the post's own option in the same save, overwriting whatever stood there; a number the template leaves unset is not copied and the post keeps its own; clearing the template to 없음, renaming, editing or deleting the template copies nothing and the post keeps the values it last received; a value edited afterwards is an ordinary option edit and the template is never consulted again until it is assigned once more ← assigning is an explicit act whose effect must be visible at once, and remembering per post which number the author had touched would be invisible state no screen could explain (→POST-26 →POST-70)

## flow
- render evidence: authored literal/write/ask roles → explicit answers → role-preserving frozen brief → stage composition → current-result source review without treating template shape as visit facts
- wizard: 네이버 블로그 → 템플릿 → 새 템플릿 | ① 템플릿 picker → 새 템플릿 만들기 → target(one question per screen → leaf) → sections(check roles · 직접 추가) → order → headings(fields · 제목 제안 받기 → sheet(style request | example) → 제안 받기, optional, explicit) → one step per section(heading · content kind cards(글 쓸 때 | 완성된 글) · photos) → name → 저장(standard create) → from ①: back to the post with the template assigned; preview beside every step from sections on(lg right | below lg 미리보기 → sheet)
- edit: saved template → blocks(toolbar names: AI가 쓰는 글 · 고정 문구 · 사진(n장) · 사진마다 반복 → rows(데이터 받기 → 제목)) | 고급 → `원문` → 저장(parse ok → row | TEMPLATE_PARSE_FAILED line + reason)
- import: saved template → 고급 → `원문` → `형식 안내 복사` → outside AI writes a body → paste(parse ok → outline in builder | error line + reason, 저장 disabled) → 저장 → same run/delete paths as any body
- assign: post picks template → each set number copied onto the post's option in the assigning save(unset → post's own value kept) → 없음 or a later template edit copies nothing
- run: post picks template → ① fills the template's data fields (제목 + textarea + switch, autosaved →POST-62) → StartGeneration / StartRevision(resolve once → drop every off or blank field's node → render photo places and repeats unbound → freeze) → prompt section after the voice projection → model output(the storyline → photos placed along it) → attachment filter(→GEN-2) → post with single photos and photo groups(→TMPL-39)
- AI refinement: saved template → explicit EDIT chat → validated private draft → optional direct editing → explicit named publication
- from a post: ③ 이 글 형식으로 템플릿 만들기 → wizard(target → the post's headings as checked custom sections)
- preview: any draft change(builder | `원문` parsable | result | undo) → preview redrawn from stand-ins
- delete: DeleteTemplate → trigger detaches posts (count returned) + cascades guideline links → name free again
