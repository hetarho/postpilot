# AUTH accounts, passwords, sessions
> r8 | Self-signed-up and operator-provisioned accounts, email + password or Google login, HttpOnly sessions with opt-in 30-day persistence, and the single interceptor that turns a request into an acting user.

## decisions
- AUTH-1 [o] anyone may sign themselves up: AuthService carries Login · Logout · GetMe plus Signup, ResendVerification, VerifyEmail, RequestPasswordReset, ResetPassword and the Google sign-in exchange, and every one of the added procedures is public (→AUTH-17) ← paid subscriptions need an account a stranger can open without the operator
- AUTH-2 [o] an account is created by its own owner (→AUTH-1) or by the operator: `api adduser <login_id> [--plan=<tier>]` against the deployed image, or `go run ./cmd/adduser <login_id>` on a host; the password is read twice from stdin (echo off on a TTY, line by line when piped) and must match; an existing id exits non-zero (`auth.ErrDuplicateUser`, enforced by the primary key)
- AUTH-3 [o] every account carries a plan (default `free`); creating one opens the tier's first monthly lot in the same transaction, idempotently (lot id derived from the account), and grants no bonus — the bonus follows a registered payment method (→QUOTA-9, →BILL-10) — ladder and grants in QUOTA
- AUTH-4 [o] a forgotten password is reset by a single-use emailed link that expires in 1 hour, invalidates every other outstanding link for that account, and ends every live session on use ← a reset is the one moment a stolen session must not survive; a signed-in password change is the same store path with the current password verified instead of a link
- AUTH-5 [x] roles, organizations and MFA — out of scope
- AUTH-6 [o] passwords are stored only as argon2id PHC strings (`$argon2id$v=19$m=65536,t=3,p=2$<salt>$<key>`): time 3, memory 64 MiB, parallelism 2, 16-byte random salt, 32-byte key; the parameters live inside each hash so raising them affects only new hashes, no schema change, no forced reset
- AUTH-7 [o] verification is constant-time; a stored hash that will not parse (including out-of-range cost parameters that would panic inside `argon2.IDKey`) is logged and answered as an ordinary wrong password
- AUTH-8 [o] every credential rejection is byte-identical: `CodeUnauthenticated`, message `invalid credentials`, stable reason `INVALID_CREDENTIALS`; unknown id, wrong password, and unusable hash are indistinguishable; a missing or expired session answers `AUTH_REQUIRED`; a login/logout infrastructure failure is `CodeInternal` with reason `UNKNOWN_FAILURE`, never collapsed into invalid credentials; a session-lookup infrastructure failure fails closed as `AUTH_REQUIRED`
- AUTH-9 [o] an unknown id runs a real argon2id verification against a dummy hash derived at boot with the current cost parameters ← id existence must not leak by timing; a hardcoded dummy would drift cheaper when the parameters are raised, and a lazily built one would double-cost the first probe
- AUTH-10 [o] session token = 32 bytes from `crypto/rand`, base64url, sent only in the cookie; the database stores `hex(sha256(raw_token))` — plain sha256, not a KDF ← 256 bits of uniform randomness leave nothing to brute-force
- AUTH-11 [o] server sessions have a fixed, non-sliding 30-day upper lifetime: `expires_at = login_time + 720h` (`SessionTTL`); automatic login preserves the cookie for that duration, while ordinary login issues a browser-session cookie
- AUTH-12 [o] `pp_session` is host-only with `Path=/; HttpOnly; Secure; SameSite=Lax`; automatic login adds `Max-Age` derived from `SessionTTL`, otherwise both `Max-Age` and `Expires` are absent; logout still clears it with `Max-Age=0`
- AUTH-13 [o] Logout deletes the session row (server-side revocation) and then clears the cookie with the same attributes and `Max-Age=0`; a Logout that fails is reported and the user stays signed in ← clearing the cookie alone would leave a stolen copy valid, and a "logged out" screen would promise safety the live cookie does not give
- AUTH-14 [o] expired rows are deleted by the lookup that finds them and swept once at boot (a sweep failure is logged, not fatal); timestamps are fixed-width RFC3339 in UTC so `expires_at < ?` is a correct string comparison
- AUTH-15 [o] one Connect interceptor in `internal/auth/rpc` is the only place a request becomes an acting user: it resolves the cookie, checks expiry, and puts the user id and the account's current plan (read from the row on every request) into the context; it is a full `connect.Interceptor` so streaming handlers are covered too
- AUTH-16 [o] the interceptor fails closed: missing, forged, expired, and store-down all answer `CodeUnauthenticated` (HTTP 401) with message `unauthenticated`; a newly mounted service is protected the moment it exists
- AUTH-17 [o] the public set listed in one map (`publicProcedures`) is `AuthService/Login`, `AuthService/Logout`, `HealthService/Ping` plus every procedure a visitor with no account must reach — Signup, ResendVerification, VerifyEmail, RequestPasswordReset, ResetPassword and the Google exchange (→AUTH-1); plain `/health` sits outside the Connect stack and is likewise open; the public `/about` route adds nothing on the wire ← Logout must always be able to clear an HttpOnly cookie, a 401 would strand it for its full 30 days
- AUTH-18 [o] the closed masterProcedures set contains the administrative procedures required by QUOTA-25 and refuses other tiers with permission_denied and MASTER_ONLY; a new privileged procedure joins this set with its implementation
- AUTH-19 [o] GetMe and Login both report the acting tier so the app gates master-only surfaces on first paint without a second round-trip; the server still refuses on its own
- AUTH-20 [o] authenticated handlers take the acting user from the context, never from a request payload — a user id in a message is a claim by the caller, not a fact
- AUTH-22 [o] the token never reaches JavaScript and no `Authorization` header exists anywhere; the SPA and the API are different origins in production, so every RPC opts into credentials through a fetch wrapper the transport is built with ← connect-web has no credentials option
- AUTH-23 [o] a 401 returns the app to `/login` only from a screen that required a session; on a public page it is the expected answer to that page's own reverse guard and changes nothing, and Login's 401 is the form's own wrong-password message ← read as a lost session from anywhere, a visitor's own probe would throw them off `/signup` and `/forgot-password` before either form could render
- AUTH-24 [o] every protected screen is a child of one pathless guard route (`id: 'authenticated'`) — protected by placement, not by remembering; `/login`, `/signup` and `/forgot-password` each carry the reverse guard and, unlike the protected one, swallow an outage so the form always renders
- AUTH-25 [o] the guard trusts a resolved session for `SESSION_STALE_MS` (30 s) before re-checking ← a session revoked elsewhere must stop granting access without a full reload, without paying a round-trip per click
- AUTH-26 [o] `loadSession` answers `active | signed-out` and throws only for failures that are not an answer; a 200 with no user is signed-out; an HTTP 5xx, proxy failure or network failure is an outage, never a logout, so it preserves client session state and reaches the error boundary instead of `/login`, where authentication cannot work
- AUTH-27 [o] the post-login `redirect` param is followed only if resolving it against the origin stays in the app (`//host` and `/\host` both leave); anything else falls back to `/` ← the router does not check `to` against known routes
- AUTH-28 [o] one cache entry is the session: `entities/session` owns the GetMe query, `useLogin` seeds it from the login response, `useLogout` removes it on success; the connect-query key takes the transport object the router carries ← a guard built on a different transport would silently read a different entry
- AUTH-29 [o] logout lives in the header avatar popover (`widgets/account-menu`) beside the account id and plan material: pending state held in place, a failure stays in the open popover as a notice, only success drops the cache and navigates to `/login`
- AUTH-30 [o] the login form composes `shared/ui` field primitives, independent automatic-login and saved-id checkboxes, and a single CTA, with the Google button, the sentence leading to `/signup` (→AUTH-42), 비밀번호 찾기 / Forgot password and the About link outside the form and below that CTA (→MKT-3); a rejected login marks both fields invalid with the localized generic message for `INVALID_CREDENTIALS` and shows distinct localized `UNKNOWN_FAILURE` copy for an outage, never raw transport prose
- AUTH-31 [o] CORS allows exactly one origin (`CORS_ORIGIN`) with credentials; any `*` anywhere in the value is rejected at boot ← `rs/cors` reads an embedded `*` as a pattern and would reflect sibling subdomains with credentials
- AUTH-32 [o] the session token appears in no proto message, response body, log line, or URL; it travels only in `Set-Cookie` / `Cookie`
- AUTH-33 [o] the email address IS the login identifier for every self-signed-up account: one field, normalized to lower case, unique across accounts, and the same string verification and reset are sent to ← a separate display id would be a second unique key to explain, collide on and support; the operator CLI may still create an account whose identifier is not an email (→AUTH-40)
- AUTH-34 [o] an unverified account cannot hold a session: Signup writes the account, sends the verification mail and returns nothing a client can log in with, VerifyEmail marks the address verified, and only then does Login succeed
- AUTH-35 [o] neither Signup nor a password reset request ever reveals whether an address already exists: both answer identically and the mail carries the difference — a sign-up on a taken address mails the owner that an account already exists instead of creating one, and correct credentials against an unverified account keep AUTH-8's identical rejection while re-sending the verification mail (rate-limited) ← public signup makes address enumeration a real attack and AUTH-9's timing work is only half the defence
- AUTH-36 [o] every unauthenticated write is throttled per client IP — login, signup, verification resend, reset request and reset — refused as `resource_exhausted` with reason `TOO_MANY_ATTEMPTS` carrying the instant it lifts, and never counted against the account itself ← the IP limit is what makes an auto-releasing lockout (AUTH-37) safe to leave alone
- AUTH-37 [o] 5 consecutive password failures lock an account for 15 minutes and it then releases itself with no operator step and no unlock link; a successful login clears the counter ← a manual unlock path is a support queue this product has no one to staff, and an emailed unlock link would let anyone lock a stranger out and fill their inbox
- AUTH-38 [o] the lock is invisible on the wire: a locked account answers the same `INVALID_CREDENTIALS` as a wrong password and the lock is told to the address by mail, not in the response (→AUTH-8)
- AUTH-39 [o] Google is the only social provider, and its verified email joins the matching existing account automatically — the account then has two ways in and one identity; a provider that hands over an unverified or absent address is refused rather than trusted, and no provider account ever creates a second account for an address that already has one
- AUTH-40 [o] an operator-created account works with no email: it logs in with its login id and is asked to register and verify one only where the product cannot proceed without it (a payment method, a reset) ← operator-made accounts are a handful, and a forced email screen would be a whole surface built for them
- AUTH-41 [o] the product must be able to send transactional mail — verification, reset, lock notice, and BILL-12's charge events — and an address that bounces is recorded as unreachable rather than retried forever; which service delivers it is engineering's choice
- AUTH-42 [o] `/login` and `/signup` are told apart before the first field is read: each carries its own title as the page heading under the shared logo lockup — 로그인 / Log in · 회원가입 / Sign up — a one-line intro naming what the screen does, a CTA carrying the same verb, and the way to the other screen written as a question with its answer (계정이 없으세요? 회원가입 · 이미 계정이 있으세요? 로그인) rather than a bare label; signup alone asks for the password twice (비밀번호 확인 / Confirm password) and refuses a mismatch in the form before anything is sent, so its three fields against login's two are a second tell ← the two screens share one lockup, one field pair and one link row, so without these tells a visitor on the wrong one learns it only from the failure message
- AUTH-43 [o] Google sign-in is a live path in production, offered on both `/login` and `/signup`: the exchange (→AUTH-1, →AUTH-39) is switched on by one Google OAuth client registered for the app origin with `<origin>/login/google/callback` as its redirect, its id given to the API (`GOOGLE_CLIENT_ID` + `GOOGLE_CLIENT_SECRET`) and to the app build (`VITE_GOOGLE_CLIENT_ID`); until both ends carry it the button is absent, never present and broken ← a visible button with no client behind it promises a path the deploy does not have
- AUTH-44 [x] a hosted identity platform (Supabase Auth, Firebase Auth, Clerk, Auth0) in front of or instead of the product's accounts ← the plan on the row, the lockout, the enumeration-proof answers, the operator CLI and the `pp_session` cookie all rest on the product's own `users` table, and a platform would add a second user store and a JWT to reconcile with each of them for a provider the product already exchanges itself
- AUTH-45 [x] signed-out use of the free tier against a browser-held device identity (as ChatGPT's signed-out chat) — an account stays the way in, and the friction it costs is answered by the live Google path (→AUTH-43) rather than by a guest mode ← every free post here costs real provider money, a device key can be cleared at will, and QUOTA-9 keeps the only ungated grant behind a card for the same reason

- AUTH-47 [o] automatic login is unchecked on a fresh login screen and applies to both password and Google login; the choice travels with the single Google authorization attempt, defaults to false when absent, and is never a stored password or token in JavaScript storage; Google entry from signup defaults to ordinary login
- AUTH-48 [o] save login id is independent of automatic login and off until an id has been saved: only a successful password login stores the submitted id on that browser, later visits prefill it, unchecking immediately removes it, and logout retains it; failed login never overwrites it, and unavailable storage never prevents login
- AUTH-49 [o] local development seed accounts are `free`, `base`, `pro`, `max`, `master`, mapped to the free, basic, pro, max and master plans, with no email address attached; the shared password is `seed-only`, and the seed keeps its post-count and credit fixtures

## flow
- signup: email + password → account written unverified → verification mail → VerifyEmail → login is possible
- login: id or email + password + automatic-login/save-id choices → IP throttle → lookup(present → verify | absent → dummy verify) → ok(verified and unlocked → set session or persistent cookie → save id when selected → seed session cache → follow safe redirect) | reject(identical error, counter++, mail on lock) | infra failure(CodeInternal)
- google: provider exchange → verified address(existing account → joined | none → account created verified) → set session or persistent cookie from the authorization attempt
- reset: request → identical answer → mail with a 1-hour single-use link → new password → every session ended
- request: cookie → interceptor(public procedure → pass | hash → row → expiry → ctx{user, plan}) → master-set check → handler reads actor from ctx
- logout: delete row → clear cookie → drop cache → `/login`; failure → stay signed in + notice

## constraints
- config: `CORS_ORIGIN` · `DB_PATH` · `GOOGLE_CLIENT_ID` · `GOOGLE_CLIENT_SECRET` (BE env, the Google pair set together or not at all) · `VITE_GOOGLE_CLIENT_ID` (FE build env) · `SessionTTL` 720h · cookie name `pp_session` · argon2id parameters · boot-derived dummy hash (BE constants) · `VITE_API_URL` (FE env) · `SESSION_STALE_MS` 30000 (FE constant); the lockout threshold (5), its window (15 min), the reset link lifetime (1 h) and the per-IP limits are code-owned product rules, not env knobs
- schema: `users(id PK, password_hash, created_at, plan)` with a unique normalized email and its verified state, the failure counter and lock instant, and the Google subject; `sessions(token PK = sha256 hex, user_id FK cascade, expires_at, created_at)` with indexes on user_id and expires_at; single-use verification and reset links are rows, never signed self-contained tokens ← a link must be revocable the moment it is used
- placement: `backend/internal/auth` (types, service, store, rpc interceptor, provision, throttle and lockout state, mail ports) · `frontend/src/entities/session` · `pages/login` and the public signup, verification-landing, Google-callback and reset pages beside it · `features/sign-in-with-google` · `shared/api` (credentialed transport, 401 event bus) · `shared/lib` (redirect validation) · `app/routes` (guard, and the public routes beside `/login` and `/about`) · `widgets/account-menu`
- tests that pin it: dummy-path timing test (AUTH-9) · 401 on every non-public procedure · exact cookie attributes · replayed cookie after Logout is 401 · redirect validation · guard and reverse-guard behaviour
