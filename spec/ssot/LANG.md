# LANG languages, locale, stable failures
> r7 | Exactly Korean and English. Three independent language values — the browser UI locale, a post's target language, a post's content-language provenance — beside voices that are Korean, with no detection and no translation, plus the stable localized failure contract every surface renders from.

## decisions
- LANG-1 [o] the product supports exactly `ko` and `en`; the proto enum is `UNSPECIFIED = 0`, `KOREAN = 1`, `ENGLISH = 2`; owning contexts persist only checked `ko|en` tags; `UNSPECIFIED` represents absence at a wire boundary and is never a business fallback — valid only for `content_language` and stage projections where language is inapplicable, invalid for post creation, generation and write snapshots; proto ↔ domain ↔ SQL mappers are the only conversion sites
- LANG-2 [o] three values are independent: the browser-owned UI locale (interface copy and formatting), a post's `target_language` (its next ordinary generation or write A/B) and a post's nullable `content_language` (the provenance of its current machine content) ← a locale switch must never rewrite a post
- LANG-3 [o] Postpilot neither detects nor translates authored or generated text; language fields are explicit product provenance; regional variants, account-synced locale, locale-prefixed URLs or redirects, and a multilingual sub-profile inside one voice are out of scope
- LANG-4 [o] the locale is resolved synchronously before React renders: an exact valid `localStorage['postpilot.locale']` → the first supported primary subtag in `navigator.languages` (case-insensitive, everything after the first `-` ignored, so `en-US` matches and `ja-JP` does not) → `ko`; a malformed stored value is ignored, not repaired; storage failures fall back to the browser preference without blocking the mount; the resolved value initializes i18next and sets `<html lang>`, the localized `<title>` and description, and the locale the formatters read, all before the first frame ← the first accessible tree must not claim Korean while rendering English
- LANG-5 [o] an explicit switch is one operation — change the i18next language, update document metadata and `lang`, persist the canonical tag, notify React — that changes no URL, session, query cache, post, voice or server preference; focus stays on the selector and a polite status announces the language
- LANG-6 [o] the locale control is an app-drawn `Menu` with a 44 px icon trigger and `menuitemradio` options labelled with the autonyms `한국어` and `English`, marking the active option with a check; below `lg` the authenticated shell's account panel draws the locale as a `SegmentedControl` in its rows layout, and the `Menu` stays everywhere else; it lives in `features/change-locale`, is composed by login, the authenticated shell and the public `/about` header through the shared `widgets/interface-preferences` (→THEME-6) and is never forked per shell; it is not a route, settings page, domain entity or navigation destination
- LANG-7 [o] resources are bundled TypeScript catalogs with no runtime fetch, detector plugin or HTTP backend — `i18next` and `react-i18next`, at the versions the lockfile resolves (→ARCH-33), are the only runtime packages ← a detector would duplicate the resolver and a backend would add a network failure mode
  - namespaces follow product surfaces (`common` `auth` `nav` `posts` `voices` `templates` `guidelines` `memories` `models` `errors` `plans` `marketing` `billing` `clips`)
  - only `common` `auth` `nav` `errors` `marketing` live under `app/providers/i18n/resources/{ko,en}`, and every other namespace is assembled from slice fragments (`<slice>/config/i18n.ts` →ARCH-16)
  - lower layers import `useTranslation` from the package, never from `app/providers`
  - keys express meaning (`posts.language.currentMismatch`), interpolation carries dynamic values, pluralization is i18next's, no sentence is built by concatenating fragments, and no translation opts into unescaped HTML
  - TypeScript augmentation derives valid keys from the resource shape and a topology test requires identical leaf keys and compatible placeholders in both catalogs
  - Korean is the runtime fallback for an unexpected missing key and a key name is never shown to a user
- LANG-8 [o] Korean is the static no-JavaScript document fallback in `index.html`, product-level rather than route-specific or localized ← it is the only metadata a client that refuses JavaScript ever sees (→MKT-10)
- LANG-9 [o] formatting helpers read the initialized locale through one adapter (never a file-scope Korean formatter): absolute dates use `Intl.DateTimeFormat`, relative times `Intl.RelativeTimeFormat` with thresholds that stay product behaviour, counts and costs `Intl.NumberFormat`; formatting never alters stored RFC3339 timestamps or their UTC semantics; English can be wider by word count but Korean remains the layout stress case for non-breaking labels, and neither locale may force a nested scroller or shrink a touch target at 360 px
- LANG-10 [o] the 목표 언어 picker lives behind the writing brief's trigger (→POST-51); a new post initializes its target from the resolved UI locale but the create request carries the concrete enum and the server substitutes no default; on update an absent target preserves and a present valid target replaces through the same newest-wins draft queue as title and memo, while the request still carries the complete title/memo snapshot; a target change preserves content, observations, revisions, machine baseline, status, finalization, voice and template assignment, and content language (→POST-19)
- LANG-11 [o] `content_language` changes only when canonical machine content changes: ordinary generation success and A/B winner application set it to the job's frozen target while preserving the current post target; AI revision preserves the frozen current content language; manual block edits, target selection, finalization, copy and export preserve it; an older frozen run may legitimately leave `target != content_language`, shown with an explanatory mismatch hint — the next full generation will switch it, and this is not a race
- LANG-12 [o] `SetGeneratedContent` and winner application receive content and language in one post-context operation ← there is no observable machine result without matching provenance; manual editing never claims to detect a translation, so provenance stays the last machine language until a future explicitly designed feature allows changing it
- LANG-13 [o] revision uses `content_language`, never `target_language`: it requires non-absent provenance, freezes content language with voice, template, instruction, content and attachments, projects the voice relative to it (→LANG-15), instructs the writer to preserve that language and make only the requested local edit, and persists the same value with the new baseline; an instruction asking for a translation conflicts with the preserve rule and the UI explains that language changes use target plus a full generation or A/B (→GEN-38)
- LANG-14 [o] a voice is Korean: creation carries no language and no screen offers one, and its 학습 글 are taken as Korean prose with no detector (→VOICE-10) ← v1 voices are Korean only, their counted items being Korean habits (→VOICE-57)
- LANG-15 [o] prompt projection is owned by voice, not generation or the frontend (→VOICE-46):
  - a Korean target receives the complete projection
  - an English target receives a portable projection tagged `target_language` and `portable=true` holding only the language-independent items: the sentence-final marks (②), emoji (③, not ㅎㅎ·ㅋㅋ·ㅠㅠ), sentences per paragraph and the line-break habit (④, not sentence length), and heading and list habits (⑧)
  - it excludes the endings, the opening and closing lines, adverbs and phrases, first person, sentence length, the AI part, every excerpt and its facts or phrasing, and any translated or generated substitute ← each is Korean text or a Korean measure
- LANG-16 [o] prompt assembly labels a portable section and states that the target language wins over a conflicting language instruction inside a template, a guideline or the profile; template and memo stay verbatim user inputs; the LLM port is language-blind and no provider-specific language option crosses it
- LANG-17 [o] observation is target-independent: target is absent from the observe prompt builder, the observation-only experiment hash, the candidate request and the persisted `Observation`; changing the target alone neither clears nor translates observations, otherwise-identical Korean- and English-target runs form the same observation requests, and `visible_text` is what the photo contains (→GEN-7)
- LANG-18 [o] StartGeneration freezes the target into the payload beside length, tag count and template and the handler uses only the payload target even if the post changes while queued
  - a queued payload without language decodes as Korean and an enqueue may not omit it
  - a write A/B snapshot freezes post, voice id or its absence, target, the full, portable or absent projection, template, target length, tag count, images and observations once, records target in its detail and hash, and applying a winner passes target with the content
  - the leaderboard is keyed by `(scope, stage, window)` and target does not partition it (→MODEL-38)
  - a Korean target receives the naturalness baseline and a non-Korean target omits the complete section (→GEN-17)
- LANG-20 [o] the analysis is Korean alone (→VOICE-24): no English analyzer, schema or word-count measurement exists; UI labels and unknown values are localized while the analysis's own text stays Korean
- LANG-21 [o] stable failures:
  - a synchronous Connect error attaches exactly one `AppErrorDetail { reason, params }` with an allowlisted `UPPER_SNAKE_CASE` reason from a backend registry and display-safe string params (`max`, `actual`, a stable model label — never SQL, stack traces, prompts, private text, cookies, provider keys or HTML; each reason documents its allowed set), while the handler still picks the semantically correct Connect code and the raw message stays a safe English operator fallback that is never primary UI copy
  - durable rows and projections expose `Failure { reason, params, technical_detail }`
  - the frontend's `shared/api` boundary parses details into `AppFailure { reason, params, technicalDetail? }` and presentation translates `errors.${reason}`
  - a missing, duplicate, unknown or malformed detail, missing or extra params, or a row carrying only a raw error becomes localized `UNKNOWN_FAILURE` regardless of the Connect code
  - code never recovers meaning by substring-matching the raw message
  - technical detail is escaped and shown, if at all, behind a labelled disclosure
- LANG-22 [o] the same parser serves mutation controls and route failures; the root route owns an eagerly available localized error component so even a lazy-route exception discards `error.message`, offers an explicit router-invalidation retry, and cannot fall through to TanStack Router's diagnostic default; device decoding and direct-upload network classification may stay local while Connect create and confirm failures keep their structured detail
- LANG-23 [o] the failure owner decides the reason:
  - `internal/llm` normalizes provider classes and job and experiment map them to product reasons
  - job owns interruption, panic and missing-handler
  - post, voice, template and guideline own validation and lifecycle
  - cross-context code never parses another context's prose and domain packages import no proto or connect types
  - stores encode params as a JSON object at the edge, reject malformed or non-object rows, project a raw error carrying no reason as `UNKNOWN_FAILURE` plus technical detail, and clear every failure field together on a retry or success
  - the language-boundary reasons are `POST_TARGET_LANGUAGE_REQUIRED` `POST_TARGET_LANGUAGE_UNSUPPORTED` `CONTENT_LANGUAGE_REQUIRED`
- LANG-24 [o] every registered backend reason maps to both catalogs (asserted by test); a reason without a catalog entry renders as the generic failure
- LANG-25 [o] exports derive language metadata from content provenance, never from a newer target (→EXPORT-2): the Naver and Tistory markers switch label language by provenance, the site HTML sets `<html lang>`, and Markdown adds `language: ko|en`; content bytes are never translated
- LANG-26 [o] language provenance is checked in the schema (`posts.target_language NOT NULL`, nullable `posts.content_language`, nullable `model_experiments.target_language`, each `CHECK … IN ('ko','en')`) beside structured durable failures; a contentless draft carries no content provenance
- LANG-27 [o] the supported set, the fallback, the storage key `postpilot.locale`, translation keys, prompt text, the proto and DB schema and the portable field set are code and product contracts — no environment value, network service, language-only job kind, detector or translation provider exists
- LANG-28 [x] more languages or regional translations, locale-prefixed routes or query parameters or redirects, account-synced locale, machine translation of any authored or generated text, language detection, translating model names or provider diagnostics, revision as a translation operation, target-dependent observation, SSR or backend-rendered copy — out of scope

## flow
- locale: storage → `navigator.languages` → `ko` → init i18next + `<html lang>` + metadata + Intl before paint → menu(한국어 | English) → persist, no navigation
- post language: create(target = UI locale, sent explicitly) → generation freezes target → success writes `content_language = target` → revision preserves `content_language` → a later target change → mismatch hint until the next full generation
- failure: domain sentinel → rpc edge(Connect code + one AppErrorDetail) → `shared/api` parse → `errors.<reason>` in the active locale | `UNKNOWN_FAILURE`

## constraints
- placement FE: `app/providers/i18n` (index, locale, metadata, resources) · `features/change-locale` · `features/select-post-language` · `widgets/interface-preferences` · `shared/api/app-failure.ts` (the one reason allowlist and parser) · `shared/lib/datetime.ts` and the formatter adapters · the root route's localized error component
- placement BE: `proto/postpilot/v1/language.proto` and `error.proto`; the reason registry beside each owning context's rpc edge
- tests that pin it: locale precedence including malformed and denied storage · primary-subtag matching and URL/session stability · pre-paint `lang` and metadata · catalog key and placeholder parity · enum ↔ tag ↔ SQL round trips rejecting unknown values · target changes preserving content byte-for-byte · observation request equality across targets · exact Korean and portable projection snapshots · every reason mapping to both catalogs · unknown or reason-less failures never rendering raw detail as the sole message · UI locale choosing defaults only for a new post
