# LANG languages, locale, stable failures
> r1 | Exactly Korean and English. Four independent language values — the browser UI locale, a post's target language, a post's content-language provenance, a voice's immutable source language — with no detection and no translation, plus the stable localized failure contract every surface renders from. Migrated from legacy policy/languages.md, tech/ui-localization-and-error-contract.md, tech/content-language-and-voice-projection.md, plan/13.

## decisions
- LANG-1 [o] the product supports exactly `ko` and `en`; the proto enum is `UNSPECIFIED = 0`, `KOREAN = 1`, `ENGLISH = 2`; owning contexts persist only checked `ko|en` tags; `UNSPECIFIED` represents absence at a wire boundary and is never a business fallback — valid only for `content_language` and stage projections where language is inapplicable, invalid for post creation, voice creation, generation and write snapshots, and language-sensitive profile work; proto ↔ domain ↔ SQL mappers are the only conversion sites
- LANG-2 [o] four values are independent: the browser-owned UI locale (interface copy and formatting), a post's `target_language` (its next ordinary generation or write A/B), a post's nullable `content_language` (the provenance of its current machine content), and a voice's immutable `source_language` (the language of its evidence and profile) ← a locale switch must never rewrite a post and an English post must never contaminate a Korean voice
- LANG-3 [o] Postpilot neither detects nor translates authored or generated text; language fields are explicit product provenance; regional variants, account-synced locale, locale-prefixed URLs or redirects, and a multilingual sub-profile inside one voice are out of scope
- LANG-4 [o] the locale is resolved synchronously before React renders: an exact valid `localStorage['postpilot.locale']` → the first supported primary subtag in `navigator.languages` (case-insensitive, everything after the first `-` ignored, so `en-US` matches and `ja-JP` does not) → `ko`; a malformed stored value is ignored, not repaired; storage failures fall back to the browser preference without blocking the mount; the resolved value initializes i18next and sets `<html lang>`, the localized `<title>` and description, and the locale the formatters read, all before the first frame ← the first accessible tree must not claim Korean while rendering English
- LANG-5 [o] an explicit switch is one operation — change the i18next language, update document metadata and `lang`, persist the canonical tag, notify React — that changes no URL, session, query cache, post, voice or server preference; focus stays on the selector and a polite status announces the language
- LANG-6 [o] the locale control is an app-drawn `Menu` with a 44 px icon trigger and `menuitemradio` options labelled with the autonyms `한국어` and `English`, marking the active option with a check; it lives in `features/change-locale`, is composed by login, the authenticated shell and the public `/about` header through the shared `widgets/interface-preferences` (→THEME-6) and is never forked per shell; it is not a route, settings page, domain entity or navigation destination
- LANG-7 [o] resources are bundled TypeScript catalogs under `app/providers/i18n/resources/{ko,en}` with no runtime fetch, detector plugin or HTTP backend — `i18next` 26.4.0 and `react-i18next` 17.0.12 are the only runtime packages ← a detector would duplicate the resolver and a backend would add a network failure mode; namespaces follow product surfaces (`common` `auth` `nav` `posts` `voices` `templates` `guidelines` `models` `publishing` `errors` `plans` `marketing`) and lower layers import `useTranslation` from the package, never from `app/providers`; keys express meaning (`posts.language.currentMismatch`), interpolation carries dynamic values, pluralization is i18next's, no sentence is built by concatenating fragments, and no translation opts into unescaped HTML; TypeScript augmentation derives valid keys from the resource shape and a topology test requires identical leaf keys and compatible placeholders in both catalogs; Korean is the runtime fallback for an unexpected missing key and a key name is never shown to a user
- LANG-8 [o] Korean is the static no-JavaScript document fallback in `index.html`, product-level rather than route-specific or localized ← it is the only metadata a client that refuses JavaScript ever sees (→MARKETING-10)
- LANG-9 [o] formatting helpers read the initialized locale through one adapter (never a file-scope Korean formatter): absolute dates use `Intl.DateTimeFormat`, relative times `Intl.RelativeTimeFormat` with thresholds that stay product behaviour, counts and costs `Intl.NumberFormat`; stored RFC3339 timestamps and UTC semantics are unchanged; English can be wider by word count but Korean remains the layout stress case for non-breaking labels, and neither locale may force a nested scroller or shrink a touch target at 360 px
- LANG-10 [o] the 목표 언어 picker lives behind the writing brief's trigger (→POST-51); a new post initializes its target from the resolved UI locale but the create request carries the concrete enum and the server substitutes no default; on update an absent target preserves and a present valid target replaces through the same newest-wins draft queue as title and memo, while the request still carries the complete title/memo snapshot; a target change preserves content, observations, revisions, machine baseline, status, finalization, voice and template assignment, and content language (→POST-19)
- LANG-11 [o] `content_language` changes only when canonical machine content changes: ordinary generation success and A/B winner application set it to the job's frozen target while preserving the current post target; AI revision preserves the frozen current content language; manual block edits, target selection, finalization, copy, export and publishing preserve it; an older frozen run may legitimately leave `target != content_language`, shown with an explanatory mismatch hint — the next full generation will switch it, and this is not a race
- LANG-12 [o] `SetGeneratedContent` and winner application receive content and language in one post-context operation ← there is no observable machine result without matching provenance; manual editing never claims to detect a translation, so provenance stays the last machine language until a future explicitly designed feature allows changing it
- LANG-13 [o] revision uses `content_language`, never `target_language`: it requires non-absent provenance, freezes content language with voice, template, instruction, content and attachments, projects the profile relative to it, instructs the writer to preserve that language and make only the requested local edit, and persists the same value with the new baseline; an instruction asking for a translation conflicts with the preserve rule and the UI explains that language changes use target plus a full generation or A/B (→GEN-38)
- LANG-14 [o] voice `source_language` is required at creation (the wire field is optional only so absence can be distinguished from enum zero; the service rejects both) and immutable; existing voices and the bootstrap default are Korean; the new-voice UI defaults the field from the UI locale but sends an explicit value; rename, default, delete and restore preserve it; a different source is a new isolated voice (→VOICE-10); pasted samples are user-declared evidence in that source language and no detector runs
- LANG-15 [o] prompt projection is owned by voice, not generation or the frontend (→VOICE-46): equal source and target receive the complete profile — structured lexical, endings and register, syntax, structure and axes, active contrast rules, manual rules, ranked imported and finalized excerpts, and the ending-consecutive constraint; cross-language projection is tagged with `source_language`, `target_language` and `portable=true` and includes only the intro and closing pattern, the paragraph sentence-count range, heading, list and emoji habits, and the six axes (involvement, narrativity, persuasion overtness, abstractness, addressee focus, humor) as numbers; it excludes preferred and banned words and patterns, base register, ending distribution, signatures, bans and constraints, sentence-length, connective, nominalization and passive fields, free-form guidance and unclassified rules, lexical, endings and syntax contrast rules, every excerpt and its facts or phrasing, and any translated or generated substitute; structure-layer rules are not automatically portable ← existing statements are authored in one language
- LANG-16 [o] prompt assembly labels a portable section and states that the target language wins over a conflicting language instruction inside a template, a guideline or the profile; template and memo stay verbatim user inputs; the LLM port is language-blind and no provider-specific language option crosses it
- LANG-17 [o] observation is target-independent: target is absent from the observe prompt builder, the observation-only experiment hash, the candidate request and the persisted `Observation`; changing the target alone neither clears nor translates observations, otherwise-identical Korean- and English-target runs form the same observation requests, and `visible_text` is what the photo contains (→GEN-7)
- LANG-18 [o] StartGeneration freezes the target into the payload beside length and template and the handler uses only the payload target even if the post changes while queued; legacy queued payloads without language decode as Korean and new payloads may not omit it; a write A/B snapshot freezes post, voice id and source, target, the full or portable projection, template, target length, images and observations once, records target in its detail and hash, and applying a winner passes target with the content; the leaderboard stays `(account, stage)` and target does not partition it (→MODEL-38); a Korean target receives the naturalness baseline and a non-Korean target omits the complete section (→GEN-17)
- LANG-19 [o] the learning gate: every post-backed voice mutation — finalize-and-learn and its retry, sentence feedback, revision `save_as_rule`, post-backed rule comparison and profile validation — requires content provenance, an active assigned voice, a matching machine-baseline voice and `content_language == frozen source language == active voice source language`, checked before any event, rule, evidence row, job or provider call; a mismatch is a normal `FailedPrecondition` with reason `VOICE_CONTENT_LANGUAGE_MISMATCH` that creates nothing; finalization, manual editing, copy, export and explicit publishing stay available; learning events freeze their languages with their revisions and a retry cannot become eligible because target, assignment or locale later changed (→VOICE-34)
- LANG-20 [o] language-aware analysis: Korean keeps deterministic segmentation, average character length, paragraph range and the `다 / 해요 / 습니다 / 기타` ending distribution with the ending-first prompt; English reuses punctuation and newline segmentation, adds a deterministic average word count and terminal cadence without pretending Korean endings apply, and its structured analyzer covers register and contractions, preferred and avoided vocabulary and connectives, sentence length in words, passive and nominal tendency, statement/question/exclamation/fragment cadence, intro, closing, paragraph, heading, list and emoji habits, and the six axes; `VoiceSyntax` carries an optional average-word measurement beside the character one; UI labels and unknown values are localized while analyzed profile values stay in the source language; comparison, validation, rule extraction and semantic prompts select their template from the frozen source (→VOICE-23)
- LANG-21 [o] stable failures: a synchronous Connect error attaches exactly one `AppErrorDetail { reason, params }` with an allowlisted `UPPER_SNAKE_CASE` reason from a backend registry and display-safe string params (`max`, `actual`, a stable model label — never SQL, stack traces, prompts, private text, cookies, provider keys or HTML; each reason documents its allowed set), while the handler still picks the semantically correct Connect code and the raw message stays a safe English operator fallback that is never primary UI copy; durable rows and projections expose `Failure { reason, params, technical_detail }`; the frontend's `shared/api` boundary parses details into `AppFailure { reason, params, technicalDetail? }` and presentation translates `errors.${reason}`; a missing, duplicate, unknown or malformed detail, missing or extra params, or a legacy row becomes localized `UNKNOWN_FAILURE` regardless of the Connect code; code never recovers meaning by substring-matching the raw message; technical detail is escaped and shown, if at all, behind a labelled disclosure
- LANG-22 [o] the same parser serves mutation controls and route failures; the root route owns an eagerly available localized error component so even a lazy-route exception discards `error.message`, offers an explicit router-invalidation retry, and cannot fall through to TanStack Router's diagnostic default; device decoding and direct-upload network classification may stay local while Connect create and confirm failures keep their structured detail
- LANG-23 [o] the failure owner decides the reason: `internal/llm` normalizes provider classes and job and experiment map them to product reasons; job owns interruption, panic and missing-handler; post, voice, template and guideline own validation and lifecycle; publishing owns agent, lease and ambiguous-commit reasons; cross-context code never parses another context's prose and domain packages import no proto or connect types; stores encode params as a JSON object at the edge, reject malformed or non-object rows, project legacy raw errors as `UNKNOWN_FAILURE` plus technical detail, and clear every failure field together on a retry or success; the language-boundary reasons are `POST_TARGET_LANGUAGE_REQUIRED` `POST_TARGET_LANGUAGE_UNSUPPORTED` `VOICE_SOURCE_LANGUAGE_REQUIRED` `VOICE_SOURCE_LANGUAGE_UNSUPPORTED` `CONTENT_LANGUAGE_REQUIRED` `VOICE_CONTENT_LANGUAGE_MISMATCH`
- LANG-24 [o] every registered backend reason maps to both catalogs (asserted by test); a reason without a catalog entry renders as the generic failure — the known gap is `MODEL_PURPOSE_NOT_REGISTERED` and `MODEL_PURPOSE_INELIGIBLE` (MODEL)
- LANG-25 [o] exports derive language metadata from content provenance, never from a newer target (→EXPORT-2): the Naver and Tistory markers switch label language by provenance, the site HTML sets `<html lang>`, and Markdown adds `language: ko|en`; content bytes are never translated
- LANG-26 [o] migration 0012 added checked language provenance (`voices.source_language NOT NULL`, `posts.target_language NOT NULL`, nullable `posts.content_language`, nullable `model_experiments.target_language`, each `CHECK … IN ('ko','en')`) and structured durable failures, deterministically backfilling existing voices, targets and machine content as Korean while leaving contentless drafts without provenance; frozen queued payloads without language are read as Korean so deployment changed no prompt
- LANG-27 [o] the supported set, the fallback, the storage key `postpilot.locale`, translation keys, prompt text, the proto and DB schema and the portable field set are code and product contracts — no environment value, network service, language-only job kind, detector or translation provider exists
- LANG-28 [x] more languages or regional translations, locale-prefixed routes or query parameters or redirects, account-synced locale, machine translation of any authored or generated text, language detection, translating model names or provider and Mac diagnostics, changing a voice's source language, revision as a translation operation, target-dependent observation, SSR or backend-rendered copy — out of scope

## flow
- locale: storage → `navigator.languages` → `ko` → init i18next + `<html lang>` + metadata + Intl before paint → menu(한국어 | English) → persist, no navigation
- post language: create(target = UI locale, sent explicitly) → generation freezes target → success writes `content_language = target` → revision preserves `content_language` → a later target change → mismatch hint until the next full generation
- failure: domain sentinel → rpc edge(Connect code + one AppErrorDetail) → `shared/api` parse → `errors.<reason>` in the active locale | `UNKNOWN_FAILURE`

## constraints
- placement FE: `app/providers/i18n` (index, locale, metadata, resources) · `features/change-locale` · `features/select-post-language` · `widgets/interface-preferences` · `shared/api/app-failure.ts` (the one reason allowlist and parser) · `shared/lib/datetime.ts` and the formatter adapters · the root route's localized error component
- placement BE: `proto/postpilot/v1/language.proto` and `error.proto`; the reason registry beside each owning context's rpc edge; `internal/voice`'s language-specific prompts and schemas
- tests that pin it: locale precedence including malformed and denied storage · primary-subtag matching and URL/session stability · pre-paint `lang` and metadata · catalog key and placeholder parity · enum ↔ tag ↔ SQL round trips rejecting unknown values · target changes preserving content byte-for-byte · observation request equality across targets · exact same-language and portable projection snapshots · a learning mismatch creating zero events, jobs or provider calls · every reason mapping to both catalogs · unknown or legacy failures never rendering raw detail as the sole message · UI locale choosing defaults only for a new post
