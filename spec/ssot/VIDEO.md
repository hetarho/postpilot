# VIDEO video attachments (영상)
> r1 | A post may carry a few short video clips beside its photos: uploaded as-is from the browser to private storage, observed by a video-capable model as material for the writer, placed in the post as a VIDEO block, rendered and exported as a marker the author attaches by hand on the platform; never transcoded, never published by the agent until that is decided.

## decisions
- VIDEO-1 [o] a video is a second attachment kind of the post aggregate, beside photos: owned by the post, addressed by filename like a photo, deleted with the post, and material for observation and writing ← the owner asked for the model to read what a photo cannot show (motion, sequence, sound) and for the clip to stand in the post where it belongs
- VIDEO-2 [o] a video belongs to the post body as well: `VIDEO` is a block type of `PostContent` with the IMAGE block's fields (`file`, `alt`, `caption`) and none of its own, editable, exportable and revisable like an IMAGE ← the owner chose placement over material-only (interview 260906); a video that is only material would leave the reader a post that never shows what the author filmed (→GEN-1 →POST-14)
- VIDEO-3 [o] the ceilings: at most `UPLOAD_MAX_VIDEOS_PER_POST` (3) videos per post, each at most `VIDEO_MAX_SECONDS` (60) long and `UPLOAD_MAX_VIDEO_MB` (200) large; the browser refuses over any ceiling before reading the file and lists the reason under 건너뜀, the server refuses on confirm ← 3 × 1 minute keeps one post's worst-case observation inside the credit hold's 30 000-token prompt assumption (QUOTA-14: Gemini-class video tokenization runs ≈ 300 tokens per second, so one clip is ≈ 18 000 tokens per call); raising any of the three is a QUOTA change first
- VIDEO-4 [o] accepted containers are `mp4` `mov` `m4v` `webm` (case-insensitive extension) and the file is uploaded exactly as picked: no transcode, no downscale, no trimming, no thumbnail rendering anywhere — the browser reads only the container metadata (duration, width, height) through a `<video>` element and sends the bytes straight to storage ← there is no browser-side transcoder worth shipping to two users and the models accept phone containers as they are; the API never reads the bytes (POST-34 stands)
- VIDEO-5 [o] the handshake is the photo's: `CreateUpload` → presigned PUT with the container's `Content-Type` in the signature → browser PUT → `ConfirmUpload` carrying duration and dimensions → the server HEADs the object and records the video; a filename is one namespace per post across photos and videos (a video named like a confirmed photo is `AlreadyExists`) ← the model and the exporters address every attachment by filename alone; the filename is the original name with its extension, de-duplicated with ` (2)` against the post and the same pick; server refusals: size 1 byte … `MAX_VIDEO_BYTES` (200 MiB, a rejected object deleted at once), duration 1 … `VIDEO_MAX_SECONDS` s, a `Content-Type` outside the four containers; duration and dimensions are client-reported like a photo's dimensions ← the server never opens a container; a forged confirm can only spend the forger's own credits, and an overrun drains that account's lots and stops (QUOTA-15)
- VIDEO-6 [o] storage: key `posts/{slug}/{video_id}.{ext}` with a random 16-byte id in the same private bucket; view URLs are presigned GETs minted on every GetPost; delete removes the object before the row; the orphan sweep, the post delete cascade and the pending-upload replacement rule apply unchanged (→POST-28 →POST-39 →POST-40)
- VIDEO-7 [o] the upload surface is the photo surface: one 사진·영상 추가 control and one drop zone accept both kinds, the gate sorts by extension, a video converts nothing and starts its PUT at once, and its card shows the PUT's progress as a percentage ← a 200 MB PUT over mobile takes a minute and a card that only says 올리는 중 reads as stuck; photos keep their existing conversion path (POST-31 … POST-33 untouched)
- VIDEO-8 [o] the observe stage sees videos: after the photo batches, each video is observed in its own call (never batched, never mixed with photos) on the run's observe model, and the observation is written into the same per-filename snapshot, with provenance, reuse, freezing and the picker exactly as for photos (→GEN-7 →GEN-8 →GEN-9 →GEN-10 →GEN-11) ← one clip is a photo batch's worth of tokens by itself
- VIDEO-9 [o] a video observation entry carries the photo fields (`scene` `mood` `visible_text` `objects` `people`) plus `events` — what happens, in order, as short factual lines — and `speech` — what is said or heard, summarized, empty when the model heard nothing or the model takes no audio; the writer receives them under 영상 관찰 beside 사진 관찰 and the grounding rule covers them (GEN-16); the contact sheet card for a video shows `events` under the shared fields and plays the clip inline from its presigned URL (→GEN-24)
- VIDEO-10 [o] the video is delivered to the model by reference — a short-lived signed URL minted for that call — never through the API process ← the largest thing an RPC or the API ever carries stays a memo (POST-34) and a 200 MB body cannot ride a request to a provider from this process; the URL lives `PRESIGN_GET_TTL` and the call is bounded by `LLM_STAGE_TIMEOUT`, so a stale URL fails the call, never leaks a standing link
- VIDEO-11 [o] capability: the catalog records `video_input` from `"video" ∈ input_modalities` (→MODEL-18); a video part on a model without it is `ErrUnsupported` before any network call (→MODEL-5); StartGeneration and StartWriteExperiment with at least one attached video require the observe model to carry `video_input`, refused before enqueue with reason `MODEL_VIDEO_UNSUPPORTED` naming the model, and the editor's 생성 / A/B 비교 say so under the button in the same place a missing observe model is said (→GEN-23 →GEN-25); the `photo-analysis` registration gate stays `vision` — video ability is a per-run check, shown as a 영상 badge on the observe selector and the admin tab, not a sixth purpose ← a separate purpose would force every user to curate two observe selections for one stage
- VIDEO-12 [o] the write prompt names the attached video filenames beside the photo filenames, asks for VIDEO blocks placed where the clip is most natural and at most where the observations support it, and the validator matches `VIDEO.file` exactly and case-sensitively against the attached video filenames and drops the rest (→GEN-2); revision filters VIDEO blocks with the same fresh attachment snapshot as IMAGE blocks (→GEN-41); a deleted video's observation is deleted with it and its blocks are dropped on the next save or revision, as an IMAGE's are (→POST-18)
- VIDEO-13 [o] one observe call per video is a planned call the enqueuing service states exactly (→GEN-29), priced by the hold at the observation completion budget of one full photo batch ← a video answer carries a timeline and is longer than one photo's; a reuse-everything run plans zero video calls
- VIDEO-14 [o] the reading view and the block editor render a VIDEO block as a native `<video controls preload="metadata">` from the presigned view URL, no autoplay, no poster generation, caption below it like an IMAGE; the block editor edits `alt` and `caption` and moves or deletes the block; the four exports carry a video as a marker or an empty-source element and never a URL or bytes (→EXPORT-3): Naver `[동영상 <file> — <caption>]` / `[동영상 <file>]` (en `[Video …]`) on its own line in marker order · Tistory `<video controls data-file="<file>"></video>` with the same replacement-instruction comment as an image · site `<video controls src="<relative file>">` with a caption `<figcaption>` · Markdown a link line `[동영상: <file>](<file>)` with the optional italic caption ← Markdown has no video syntax and a link is what every renderer keeps
- VIDEO-15 [o] the Naver export tab plays the video inline in marker order and offers NO copy control on it, saying instead to attach the original from the device in the platform's editor ← the clipboard cannot carry a video file from a page (EXPORT-13), and the file the author filmed is on the phone they are pasting from; the photo copy controls are unchanged
- VIDEO-16 [o] the Naver publisher does not carry videos yet: StartPublish refuses a post whose finalized content holds a VIDEO block with `FailedPrecondition` `VIDEO_NOT_PUBLISHABLE`, the 발행하기 surface says so before the button is pressed and names the export tab as the way, and nothing about a video is staged or frozen (→PUBLISH-9); a post with videos attached but no VIDEO block publishes normally
- VIDEO-17 [?] how the agent should publish a VIDEO block — SmartEditor's own video attach (upload, Naver-side encoding wait, a placeholder until encoded) means a new manifest asset kind (→PUBLISH-10), a new upload step and new fence evidence (→PUBLISH-21 →PUBLISH-22); owner's call by update-ssot PUBLISH after T008 closes ← a PUBLISH rev now would stale the publisher work in flight
- VIDEO-18 [o] a post is generated from "photos and videos" wherever the UI said photos: the zero-material case is no photos AND no videos (→GEN-13), the observe model requirement is "photos or videos attached" (→GEN-5 →GEN-23), the stage label stays 사진 관찰 중 while photos are observed and reads 영상 관찰 중 while a video is (→POST-46), and the reobservation picker lists videos after photos with a duration badge
- VIDEO-19 [x] transcoding, trimming, thumbnails or poster frames (server or browser); frame extraction into photos; video generation (the `video-generation` purpose is unrelated); a template `video` position (TEMPLATE-34 stands; a video is placed by the writer or by hand); videos in observe A/B experiments (the observe comparison stays photos-only, MODEL-30); a video copy control; publishing videos through the agent (→VIDEO-17); audio-only files; more than three or longer than a minute (→VIDEO-3); server-side duration verification — out of scope

## flow
- attach: pick(gate: extension · size · duration · count) → read metadata → CreateUpload(content type from the container) → PUT with progress → ConfirmUpload(duration, w, h) → cache patch → next GetPost supplies the presigned view URL
- generate: 생성(observe model has `video_input` | refused MODEL_VIDEO_UNSUPPORTED) → StartGeneration(freeze photo and video filenames + reusable snapshot → hold: photo batches + one call per video) → worker(photo batches → one call per video → merged snapshot) → write(사진 관찰 + 영상 관찰 + filenames) → validate(IMAGE and VIDEO files against attachments) → content with VIDEO blocks
- export: any tab → video as marker | empty-source element; Naver tab plays it inline, no copy; 발행하기 with a VIDEO block → refused VIDEO_NOT_PUBLISHABLE

## constraints
- config BE (`platform/config` env, boot-fatal when invalid): `UPLOAD_MAX_VIDEOS_PER_POST` 3 · `VIDEO_MAX_SECONDS` 60 · `MAX_VIDEO_BYTES` 200 MiB (typed constant beside `MAX_IMAGE_BYTES`); FE `shared/config`: `UPLOAD_MAX_VIDEOS_PER_POST` 3 · `UPLOAD_MAX_VIDEO_MB` 200 · `VIDEO_MAX_SECONDS` 60 · `UPLOAD_VIDEO_EXTENSIONS` mp4 mov m4v webm (mirrors via `VITE_*`); the container → `Content-Type` map, the observation schema, the prompt text and the marker forms are code
- credit hold: unchanged (QUOTA r2) — the three ceilings are what keep one call under `holdInputTokens` 30 000; changing any of them reopens QUOTA-14
- schema: `videos(id PK, post_slug FK cascade, filename, r2_key, content_type, bytes, duration_ms, width, height, created_at, UNIQUE(post_slug, filename))`; pending video uploads share the `uploads` table with a kind column; filename uniqueness across `images` and `videos` is enforced in the post service's confirm and create transactions; `catalog_models.video_input`; `observations` entries gain optional `events` `speech` `duration_ms`
- proto: `Block.type` gains `VIDEO`; `Post` gains `videos` beside `images` (id, filename, view_url, duration_ms, width, height, bytes); `ConfirmUpload` gains `duration_ms`; `CatalogModel` gains `video_input`; new refusal reasons `MODEL_VIDEO_UNSUPPORTED` `VIDEO_NOT_PUBLISHABLE` need entries in the frontend reason catalog (LANG owns it)
- provider wire: the adapter's video content part and URL delivery must be confirmed against the provider's current docs before implementation (ARCH-33); if the gateway accepts no URL delivery for a model, that model is treated as lacking `video_input` rather than streaming bytes through the API
- placement BE: `backend/internal/post` (video type, upload kind, confirm rules, cascade) · `backend/internal/generation` (video observe call, schema, prompt material, validator) · `backend/internal/llm` (video part, capability check) · `backend/internal/modelcatalog` (`video_input` mapping) · `backend/internal/publishing` (start refusal only)
- placement FE: `entities/video` (`@x/post`) · `features/upload-photos` (gate and PUT progress for both kinds) · `entities/post` `BlockList` and `features/edit-post-content` (VIDEO block) · `widgets/contact-sheet` · the four `features/export-*` converters · `widgets/export-panel` · `features/generate-post` (the video-capability blocker)
- tests that pin it: gate refusals per ceiling · confirm refusals (size, duration, content type, cross-kind filename) · one observe call per video after `ceil(photos/4)` batches with a stubbed provider · validator drops a VIDEO file not attached · the four converters' video mapping goldens · StartPublish refusal on a VIDEO block · `video_input` mapping from the catalog fixture
