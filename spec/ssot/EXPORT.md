# EXPORT platform export
> r1 | Four copy-ready formats derived in the browser from the canonical block array — Naver plain text with photo markers (and per-photo image copy), a Tistory HTML fragment, a standalone fixed-template HTML page, Markdown with front matter — never stored, never served, never publishing. Migrated from legacy policy/export.md and plan/08.

## decisions
- EXPORT-1 [o] Naver, Tistory, standalone site HTML and Markdown are pure synchronous conversions `(PostContent, images) → string` of the same block array (I2), computed in the browser; switching formats makes no request; no derived format is stored or served by the API; the export surface never publishes and the copy-ready path stays the universal fallback (I1) ← SmartEditor ONE has no HTML input and discards pasted markup, so the Naver output must be plain text the user drags photos into
- EXPORT-2 [o] converters require the post's concrete `content_language` and the panel fails closed when provenance is absent; they never substitute a newer target, inspect prose or translate content (LANG)
- EXPORT-3 [o] every image reference comes from `Block.file`; attachment `view_url`s, API origins, storage hosts and image bytes are never emitted ← presigned URLs expire and would rot in a pasted page; site and Markdown encode the filename as one relative URL path segment so accepted punctuation cannot become a query, fragment or malformed destination; HTML text and attributes are escaped, Markdown image labels escape label delimiters, YAML strings use JSON-compatible double-quoted escaping
- EXPORT-4 [o] an unfilled template slot renders in all four formats as a bracketed placeholder — the author's label, falling back to the slot's kind — in marker order, never as its copy token, distinguishable from the Naver photo markers by the filename those carry; the panel states how many positions remain and says to fill them in the platform's editor after pasting; nothing about a slot blocks a copy or a finalization (→TEMPLATE-23); the four outputs are byte-identical for a post with no slots
- EXPORT-5 [o] Naver output is plain text without the title, blocks separated by one blank line, image markers `[사진 <file> — <caption>]` / `[사진 <file>]` for Korean content and `[Photo …]` for English; the title has its own copy field ← the marker format is a contract the guidance and users rely on
- EXPORT-6 [o] Tistory output is an HTML fragment without document wrappers: it begins with the summary, leaves every image `src` empty, stores the exact filename in `data-file`, and places a Korean or English replacement-instruction comment right after the image per content provenance; comment-closing sequences in unusual accepted filenames are neutralized inside the comment
- EXPORT-7 [o] site output is one standalone document whose `<html lang>` comes from content provenance, with a fixed, content-independent inline stylesheet (two different posts produce byte-identical `<style>`), including title, summary, creation date, tags and article blocks with URL-safe relative filenames ← the design is a fixed template; the model never writes CSS
- EXPORT-8 [o] Markdown begins with YAML front matter containing title, creation date (`YYYY-MM-DD`), summary, tags and canonical `language: ko|en`; body headings, quotes, lists, images and optional italic captions follow the fixed mapping (Hugo / Jekyll / Obsidian compatible)
- EXPORT-9 [o] the export panel (`widgets/export-panel`) exists for canonical content in both `review` and `finalized`, is absent while a post has no generated content, and shows localized format-specific guidance; Tistory, site and Markdown show the exact string passed to the clipboard in a read-only field; the Naver tab shows the rendered post instead — the block array through `entities/post`'s `BlockList`, body only, photos inline in marker order — and the `[사진 …]` markers exist only in the copied text, which stays byte-identical ← the owner's verdict on a marker-text strip was that it did not read as the post
- EXPORT-10 [o] a successful clipboard write shows 복사됨 for `COPY_FEEDBACK_MS` (1500); when the API is absent or rejects, the relevant field is focused and fully selected with the manual-copy hint; on the Naver tab the raw text field is first revealed for that fallback, and a later copy, tab switch or content change returns the tab to the rendered preview (focus is handed back to the copy button when the dismissal unmounts the focused field) ← the fallback is revealed, not resident
- EXPORT-11 [o] copy operations are serialized; a tab or content change or a newer copy invalidates stale feedback and fallback selection; feedback carries the value and content identity it described, so a delayed browser permission result or a re-materialized output string cannot act on or label a different preview
- EXPORT-12 [o] the Naver format also copies photos, one at a time: each inline photo IS its own copy control — the photo is the button, named by its marker filename, in marker order, derived from the same block array — with the `<img>` inside the `<button>` so the browser's own image-copy command stays available on it ← a 44 px corner control over a column-wide photo was a quarter of the reach it needed and sat where the thumb rests; a marker whose photo is missing holds its inline position as a filename placeholder so later photos cannot shift against their markers; the other three formats render no photo copies
- EXPORT-13 [o] the clipboard payload for a photo is exactly one `ClipboardItem` carrying `image/png` and nothing else — measured (owner, 2026-08-31, SmartEditor ONE on macOS Chrome), not chosen: a `text/html` flavor beside it makes the editor render a broken image, a second item is silently ignored, and a page cannot write files to the system clipboard; there is no text fallback for a photo copy ← the text output beside it is the fallback already promised
- EXPORT-14 [o] the PNG is handed to the `ClipboardItem` as a promise and the write is issued before the bytes arrive ← awaiting the encode first spends the user activation WebKit requires and would make every iOS copy fail
- EXPORT-15 [o] a photo is copied from the pixels already on screen, never re-requested: `copyImage` takes the `<img>` (`createImageBitmap(element)` → `encodePng`, which reuses the upload pipeline's canvas machinery without resizing or flattening) so after a photo has painted the copy depends on no URL, network or clock ← a presigned view URL lives 10 minutes and the panel outlives one; nothing encoded here is uploaded, published or persisted
- EXPORT-16 [o] reading those pixels requires the photo to be CORS-loaded, so the preview's photos are `crossOrigin="anonymous"` and not lazy ← a photo has to have painted to be copyable and deferring the load defers it past the URL's lifetime; this is the one surface where the bucket's browser-`GET` allow decides whether a photo DISPLAYS, and every other screen's plain `<img>` is unaffected
- EXPORT-17 [o] a photo failure is stated on that photo and told apart by kind: no image clipboard in the browser · the write was refused · the pixels were blocked (this origin may not read them — the fallback is the text output, reloading changes nothing) · the photo was unreadable (it never painted; reloading the post remints its URL) · no photo matches the marker; a photo that cannot be read, or one still carrying its local upload preview, offers no copy control at all rather than one that would write an empty image
- EXPORT-18 [o] blocked and unreadable are separated by the URL, not by the response ← R2 answers an expired read with a 403 carrying no CORS headers, which the browser withholds exactly as it does when the bucket allows this origin no `GET`; `shared/lib/presign`'s `presignExpired` reads the lifetime SigV4 states in the URL's own query (`X-Amz-Date` + `X-Amz-Expires`) to decide which a photo that never painted was, while on the copy itself the browser's `SecurityError` says so; the bucket rule is a repo artifact (`deploy/r2-cors.json`, applied per DEPLOY.md §5) asserted at deploy time by a `GET` preflight from `WEB_ORIGIN` against the host the URLs are signed for
- EXPORT-19 [o] a photo that fails to LOAD asks for a fresh set of view URLs once (`useRefreshPostImages` invalidates the post query, at most once per photo per mount) ← nothing else refetches the post while the editor sits open, so a panel opened past the presigned lifetime is one refetch from fixed; it is bounded because every refresh mints a new URL, and it is not a poll ← a painted photo is never re-requested; the presign TTL is unchanged ← a leaked URL is a leaked object
- EXPORT-20 [o] the generated tags get a read-only field with its own copy button on every format tab, above the output and below the title: `#tag1 #tag2 #tag3`, each tag prefixed exactly once (a tag the model already wrote with `#` is not double-prefixed), single-space separated, no trailing separator (`toHashtags` in `widgets/export-panel/lib`); a post whose tag list is empty renders no field and no label; the copy follows the title's discipline (same confirmation, dwell, manual fallback, staleness rule) and a tags fallback does not reveal the Naver raw field; the four outputs are unchanged ← Naver and Tistory omit tags because those platforms have their own tag box, and the site HTML and Markdown embed theirs as markup, so the panel showed them nowhere usable
- EXPORT-21 [o] export reads the latest canonical edited `PostContent` before or after finalization; rendering, opening a tab, copying through either clipboard path and feedback timers never freeze a learning snapshot, enqueue work, update a profile or call a provider; the publishing panel is composed after export in 글 완성 and a copy action never becomes a publication request (PUBLISH)
- EXPORT-22 [x] publishing, browser automation or platform credentials inside the export surface; server-side conversion or storage; theming or per-post styling of the site format; embedding image bytes or long-lived URLs; bulk photo download (the owner chose per-photo copy; only Finder can put files on the clipboard); editing the derived text in place; refetching to remint a URL on the copy path — out of scope

## flow
- open panel(content exists) → tab(naver rendered | tistory · site · markdown raw) → copy(text | photo) → 복사됨 1500 ms | fallback(select field, hint) — no request, no state change
- photo copy: painted CORS `<img>` → bitmap → PNG promise → one `ClipboardItem` → ok | failure named on the photo(unsupported · refused · blocked · unreadable · missing)

## constraints
- config: `COPY_FEEDBACK_MS` 1500 (FE `shared/config`, shared by text and photo copies) · the site CSS and document shell are a code constant in `features/export-site/config` · format guidance lives in the i18n `posts` catalog; no env, no backend impact
- placement FE: `features/export-naver` `export-tistory` `export-site` `export-markdown` (one pure converter each with snapshot tests over a fixture covering every BlockType, an image without caption, a level-3 heading and Korean text needing escaping) · `widgets/export-panel` (tabs, copy discipline, `lib/hashtags.ts`) · `entities/post` (`BlockList` seams `label`, `className`, `renderMissingImage`; `useRefreshPostImages`) · `shared/lib/clipboard` (`copyImage`) · `shared/lib/image` (`encodePng`) · `shared/lib/presign`
- ops: the production bucket's CORS rule must allow browser `GET` (and PUT/HEAD for uploads) from the FE origin; the deploy asserts the preflight (DEPLOY.md §5)
