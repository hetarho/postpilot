# THEME theme preference and design language
> r42 | Shared accessible visual contracts for tab-navigated creation, guided authoring, comparisons and semantic-origin review.

## decisions
- THEME-1 [o] three browser-owned preferences: `system` (the default, follows `prefers-color-scheme`), `light` → the `day` semantic map, `dark` → the `night` map; the effective theme is always exactly `day|night`; components consume semantic or functional tokens and never branch on a preference, an effective theme or a palette step
- THEME-2 [o] the storage key `localStorage['postpilot.theme']` holds only the explicit values `light|dark` and choosing System removes it; a missing, malformed, unknown, unreadable or throwing value resolves to System; storage read, write and removal failures never prevent rendering and a failed write leaves the tab's in-memory selection active for the session
- THEME-3 [o] theme is not account or session state: it survives navigation, logout, later login and reload on the same browser and has no RPC, row, cross-device sync, provider call, job, analytics event or env value; the same single preference serves the public `/about` page (→MKT-7), so a visitor's choice there is what the app starts from after login
- THEME-4 [o] one synchronous bootstrap snapshot is resolved and applied before React creates its root — the source entry is render-blocking in `<head>` and the Vite HTML transform preserves that on the hashed production entry — and the mounted provider starts from that snapshot instead of rereading storage ← the first frame and runtime state cannot disagree; while System is active the provider listens to `matchMedia('(prefers-color-scheme: dark)')` and an explicit Light or Dark detaches that listener; a same-origin `storage` event for the key updates the open tab without writing back, a removed or invalid value meaning System; listeners are cleaned and reattached safely under Strict Mode
- THEME-5 [o] every effective-theme transition atomically synchronizes `<html data-theme="day|night">`, the document element's native `color-scheme`, `<meta name="color-scheme">` and `<meta name="theme-color">`
  - the day and night chrome colours are owned by `frontend/index.html`'s theme-colour element as `data-day` and `data-night` and TypeScript selects one rather than duplicating literals ← Chrome for Android tints its address bar from that tag alone
  - the static no-JavaScript fallback is Night
  - changes are immediate with no full-page transition
  - the app icon is fixed art on its own tile that does not follow the theme (`public/favicon.svg` is the source; `favicon.ico` and `apple-touch-icon.png` are rasterised from it and regenerated when it changes)
- THEME-6 [o] the translated `widgets/interface-preferences` is the single composition of the locale and theme controls, mounted by login, the authenticated shell (its header, account panel and 나's 화면 group, →THEME-38) and `/about`: a labelled group of two icon-triggered app-drawn `Menu`s (WAI-APG menu button, `menuitemradio` options, roving focus, Escape and outside-press close with focus return)
  - the theme trigger wears the stored preference's icon (monitor = System, sun = Light, moon = Dark) and carries a translated accessible name so the closed header reports the preference
  - below `lg` the authenticated shell keeps the pair in the account panel instead of its header (→AUTH-29), drawn there in its rows layout as two labelled `compact` `SegmentedControl`s stating their choices in place — the locale's showing both autonyms (→LANG-6) —, 나's 화면 group draws the same rows layout at every width, and the `Menu`s stay everywhere else ← a signed-in person has one place for everything about their session, the header keeps two fewer controls at 320 px, and a menu cannot open inside that height-capped, scrolling panel
  - theme and locale are independent and changing either changes neither the other nor the URL, session, query or server state
  - the pair never overflows at 320 px
- THEME-7 [o] both themes keep primary, secondary and tertiary content on every surface and every functional foreground on its background at WCAG AA (4.5:1 body, 3:1 large text — for Korean "large" is the CJK equivalent of 18 pt, so 19 px Hangul earns no exemption); every mapped pair is re-checked with a contrast tool when a foundation moves
- THEME-8 [o] the product is a purposeful creation tool: a spacious, memorable launch canvas precedes focused writing or clip creation; quiet chrome stays at the edges and setup lives in settings. Planes, semantic colour, accessibility and shared primitives bind every surface; the launch canvas uses large typography and three equally weighted channel choices under THEME-47.
- THEME-9 [o] the device contract every surface is designed and reviewed against: design width 360 CSS px (390 and 430 also checked); conformance floor 320 px with no horizontal page scroll (WCAG 1.4.10); a one-handed grip where the top ~40 % of a 430 × 932 phone is out of thumb reach; a software keyboard covering the bottom ~40 % whenever a field has focus; Korean script, ~1.8× wider per character than Latin and breaking between syllables unless told not to; a cellular network where every RPC can be slow or fail; a change looked at only in a desktop browser is not reviewed
- THEME-10 [o] hard rule, only design-system UI: every generic control the product renders lives in `frontend/src/shared/ui/<name>/` and is used from there; slices never hand-roll a control (a bare `<button className>` is a design-system bug); the inventory is demand-driven — use the existing primitive, otherwise add the smallest domain-agnostic one the current screen needs, and never prebuild unused controls, variants or states; a primitive has no product noun in its name (`Button`, `TextField`, `Menu`; not `PhotoStrip`); two slices reaching for the same shape means a missing primitive and the second copy is the bug report
- THEME-11 [o] hard rule, only Tailwind-registered tokens: a class must resolve to a token registered in `@theme` — the colour foundations and functional roles, the radius, duration, ease, shadow and font scales, the safe-area spacing tokens, and Tailwind's stock spacing and type scales — using the narrowest role that describes the element
  - forbidden with no exception in `frontend/src`: Tailwind's stock colour palette (unset in `index.css`, so such a class emits no CSS at all), arbitrary colour values and raw literals in TS, TSX or CSS, and arbitrary sizes off the scale (change the scale in `index.css`, never the call site: the Guide's type steps — 13, 15, 17, 18, 21, 28/32, 30/36, 34/42 and 44/60 px — are registered `--text-*` tokens (→THEME-19); no recipe is below 12 px)
  - `pnpm lint:style` fails on colour escapes, arbitrary text sizes and weights in slice `.tsx`, and the banned `bg` · `surface` · `text` · `primary` · bare status · `border` · `overlay` · `depth` utility families, and `pnpm lint:style:probe` proves the scanner catches them without rejecting the live names
  - a line that is genuinely not UI colour carries `// style-escape: <why>`
- THEME-12 [o] hard rule, borders are the last resort: depth and grouping come from the surface steps and from spacing; a `border-*` class is allowed only for the outlined button variant, a `divide-divider` hairline between rows with no background of their own, a table rule, a spinner's ring and the options a promotional surface lists (→THEME-37); besides the focus ring the only rings are the inset `checkbox-edge` of an unticked checkbox or choice mark and the accent ring of a chosen choice card (→THEME-52); never around a card, a panel, an input at rest, a header or a section — step one of them to a different surface or add space
- THEME-13 [o] the card is the one lifted plane content sits on — `card-bg`, `rounded-xl`, `shadow-md` and its own padding through `cardStyles` — holding a list item, a settings group, a choice or destination tile, a summary list or a guided step's grouped content ← one task per screen sits on one plane the eye lands on while the page ground recedes
  - not a card: the whole page, a page heading, a chip row, a docked bar, or a single line of text with nothing else; never nest a card in a card
  - an interactive card is ONE target — its link stretched over the whole card when the card carries links of its own, those staying separate targets above it — that tints and lifts on hover and sinks on press
  - a secondary button standing on a card takes the card's inner well (`card-well`) as its plane, so it still reads as a button
- THEME-14 [o] author a finished 320–430 px phone layout first; breakpoints respond to content needs. `sm` changes density, `md` permits side-by-side composition and `lg` widens desktop workspaces and shell chrome. Desktop surfaces deliberately redistribute guidance, controls and previews instead of scaling or centering the phone column, except the post editor's one-question column (→THEME-26); mounted form/job state survives breakpoint changes.
- THEME-15 [o] colour is authored once in `frontend/src/app/styles/index.css` in three layers with a one-way dependency palette → foundation → function → component:
  - OKLCH palette ramps (`mauve`, `violet`, `red`, `green`, `gold`, `blue`, white, black), the only raw literals in the frontend and deliberately not Tailwind variables
  - semantic foundations (`--surface-*` `--content-*` `--stroke-*` `--intent-*` `--interaction-*` `--physical-*`) mapped per theme to palette steps, never literals
  - functional roles referencing foundations, grouped by what the product renders:
  | group | roles |
  |---|---|
  | buttons | `button-cta-*` `button-secondary-*` `button-ghost-*` `button-danger-quiet-*` |
  | cards | `card-bg` `card-bg-hover` `card-bg-active` `card-well` (a quiet well inside a card) |
  | fields | `field-bg` `field-bg-hover` `field-bg-focus` `field-fg` `field-label` `field-placeholder` `field-error` `checkbox-edge` |
  | navigation and lists | `link-*` `link-fg-current` `row-bg-*` `divider` `tab-bar-*` `chip-*` (the current chip inverted) |
  | labels and feedback | `badge-{neutral,accent}-*` `notice-{danger,success,warning,info}-*` |
  | guided progress | `progress-step-done` `progress-step-todo` |
  | system and media | `focus-ring` `selection-*` `media-scrim-*` `shadow-color` |
  | brand | `brand-wordmark` `brand-mark` |
  | promotional | `stroke-promo-{from,via,to}` (the stroke and halo stops) `promo-aurora-{1,2,3}` (the backdrop's three blobs) `promo-spot` (the pointer spotlight) `promo-text-{from,to}` (gradient text) — the only roles allowed to reach for a hue outside the accent family, and only under →THEME-37 |
  - `@theme inline` exposes the roles plus the surface and content foundations
  - state names are explicit (`bg`, `bg-hover`, `bg-active`, `fg`) so a primitive never invents a hover by opacity
  - direct `intent-*` utilities are deliberately not registered
  - a role is added only when a current need cannot be expressed
- THEME-16 [o] the neutral is mauve: the greys carry the primary hue (298°) at a whisper-level chroma (~0.01) so the interface reads as one material rather than a grey box with a purple button; never a true grey or a different-hue neutral
- THEME-17 [o] the surfaces are an ordered depth scale walked one step at a time:
  | surface | holds |
  |---|---|
  | `surface-lowest` | deep wells and the primary navigation plane |
  | `surface-recessed` | inputs and regions pressed into the plane |
  | `surface-base` | the page canvas |
  | `surface-raised` | rows on interaction, compact controls, cards, resting floating content |
  | `surface-highest` | menus, sheets, dialogs, popovers, a docked action bar |
  - plus `surface-overlay`, outside the scale, for a panel that opens OVER one of the others (a portalled listbox): a step down plus its own `shadow-lg` ← up is unavailable in both themes
  - `content-primary` → `secondary` → `tertiary` carry copy hierarchy and `content-disabled` is never used for readable metadata
  - `stroke-subtle` and `strong` are rare structural hairlines, never a substitute for a surface step
  - `intent-*` is meaning before a component
  - `interaction-focus` is the one keyboard-focus colour
  - `physical-*` is light and occlusion, not product meaning
- THEME-18 [o] applying colour:
  - surfaces move one physical step (a field is recessed on base, a card is raised, a modal is highest — depth is the step plus rarely a shadow, not a border; `surface-lowest` is not a generic dark fill and `surface-highest` is not emphasis)
  - one CTA per view uses `button-cta-*` and every other button is ghost, secondary or rarely outlined ← two filled CTAs means one is lying about its importance
  - accent is for action and identity — a control, a selected state, a focus ring, a single word — never area outside a promotional surface (→THEME-37) and ONE hero card per screen tinted accent-subtle (`badge-accent-bg`) — the latest in-progress work (→!THEME-73), the credit balance (→QUOTA-75), waiting guideline candidates (→GUIDE-22), a running writing card (→POST-125) — so the screen's first answer is told at a glance; the screen still has at most one filled CTA and a hero card's own action is never a second one
  - status colour never travels alone
  - inline notices use the notice contract with explanatory text and no border
  - primitives use functions, not foundations
- THEME-19 [o] typography: one family, the product's own Wanted Sans Variable — named first in `--font-sans`, ahead of the platform stack (Apple SD Gothic Neo, Noto Sans KR) that shapes the beat before it lands — self-hosted as the very file the clip renderer pins (→CDS-17), no second family ← the app and the clips it makes read as one product, and `font-display: swap` keeps the phone's first paint off the download
  - weight carries emphasis, colour importance, size hierarchy, never all three for one thing
  - the roles are code in `shared/ui/typography` — `<Typography variant>` and `typographyStyles({ variant })` for an element that keeps its own component; sizes read phone → `sm:`:
  | role | element | recipe | use |
  |---|---|---|---|
  | `launch` | `h1` | `text-4xl sm:text-6xl font-semibold tracking-tight leading-tight` | the creation launch heading under →THEME-47 |
  | `hero` | `p`/`span` | `text-xl sm:text-4xl font-bold tracking-tight` | the one figure a promotional surface leads with — a plan's price — and nothing else; it outranks `display` only because on a surface whose job is to be chosen from the thing being compared outranks the page's own name, and it is the one role that may be painted as gradient text through `PromoText`, →THEME-37 |
  | `largeTitle` | `h1`/`p` | 34 → 42 px, extrabold, tight tracking, 1.15 leading | a hub page's and 만들기's large title (→THEME-38 →THEME-68) |
  | `display` | `h1` | 30 → 36 px, bold, tight tracking and leading | the screen's one top title |
  | `stepTitle` | `h2` | 28 → 32 px, bold, tight tracking and leading | the current guided task: a guided screen's one question |
  | `title` | `h2` | 21 → 24 px, bold, tight tracking, snug leading | every section heading and dialog title, `as` for deeper levels |
  | `fieldTitle` | `h3`/`label` | 18 px, bold, tight tracking, snug leading | a field's own name beside a step's action; a choice card's name |
  | `body` | `p` | 17 px, relaxed leading | primary reading and supporting explanations |
  | `input` | - | 17 → 16 px | field primitives only |
  | `label` | `span` | 15 px, semibold, `text-content-secondary` | concise labels and secondary annotations |
  | `meta` | `span` | 13 px, `text-content-tertiary` | metadata and tab labels; `mono` for verbatim ids |
  | `groupLabel` | `h2` | 13 px, semibold, wide tracking, uppercase, `text-content-tertiary` | the name over a settings group |
  | `figure` | `p` | 44 → 60 px, extrabold, tight tracking, leading none, tabular numerals | the one number a hero card is about — the credit balance — named by the card's label, never a heading |
  | `eyebrow` | `span` | 12 px, semibold, wide tracking, uppercase | - |
  - a slice never composes a raw type utility (`text-<size>` `font-<weight>` `font-mono` `tracking-*` `leading-*`) and `pnpm lint:style` fails on one in a non-test slice `.tsx` outside `shared/ui` unless it carries a reasoned `// style-escape:` pragma (the sanctioned case is a nav control's active-state `font-medium`)
  - a caller's colour wins over the recipe's while the size stays the role's
  - prose is capped at `max-w-measure` (40rem)
  - field labels and placeholders use `text-field-label` and `text-field-placeholder` owned by the primitive
  - an eyebrow is not a heading
  - 12 px is the floor and an eyebrow's alone; metadata is 13 px, and copy the user acts on — a tab label included — is never below 13 px
- THEME-20 [o] the 16 px input floor: every control the user types into computes to at least 16 px on a phone (the `input` role, 17 px on a phone and 16 px from `sm:`) ← iOS Safari zooms the whole layout when a focused field is smaller and never zooms back out on blur; the fix is the font size and nothing else — `user-scalable=no` and `maximum-scale=1` are forbidden (WCAG 1.4.4, and iOS ignores them anyway)
- THEME-21 [o] Korean line breaking: `body` sets `word-break: keep-all` and `overflow-wrap: anywhere` together, once ← `keep-all` alone lets an unbreakable Latin token (a model id, a slug, a provider URL) push the page into horizontal scroll; `break-all` is never used since it excludes CJK; any container rendering a server- or model-supplied string additionally carries `break-words` at the call site — the global rule protects the layout, the local class protects the box
- THEME-22 [o] space and hierarchy: one 4 px scale — inside a control 2–3, inside a group 3–4, between groups 6–8, between page sections 10–16; hierarchy is built position → size → weight → colour → surface → border, each used only when the one before is not enough; a group of actions reads left to right by rising emphasis, the way out first and the committing action last and the only filled one; pages are full-bleed on `surface-base` with `px-4` (phone) → `px-6` (from `sm:`) gutters and no visible container
- THEME-23 [o] target size follows the POINTER, not the device class:
  - under a coarse pointer (`pointer-coarse:`, a thumb) every pressed control keeps the 44 × 44 CSS px floor counting both dimensions (a bare text link like `말투` is ~28 px wide and fails, so text-sized controls get horizontal padding)
  - under a fine pointer the resting height is 40 px (`min-h-10` / `size-10`) for buttons, fields, listbox triggers and tabs, 36 px (`min-h-9`) for menu rows and listbox options, and 32 px (`min-h-8`) for `compact` — every one above WCAG 2.5.8's 24 px minimum ← 44 px controls under a mouse read as a touch layout blown up, and the web norm is 32–40 (WCAG 2.5.8 sets 24, 2.5.5 and Apple's HIG set 44 for touch, Material draws a 40 dp button on a 48 dp touch target)
  - the committing action is larger at every pointer: a `cta` 48 px, a `hero` action (a step bar's big action, a list's creation button) 56 px; fields and listbox triggers are 48 px under a coarse pointer
  - the primitive carries both values itself (`min-h-10 pointer-coarse:min-h-11`) so a slice never sizes a control, and a bare text link with no plane of its own keeps a 44 px box at every pointer since nothing visible is oversized
  - controls inside the shared bottom action dock use a48px height floor and proportional horizontal padding at every pointer; icon controls stay square; on a phone the step bar's buttons take narrower sides (16 px, 20 px for its big action) so no label wraps at 360 px (→THEME-71)
  - 24 × 24 is the absolute floor
  - ≥ 8 px between adjacent targets
  - when the visible box must stay small the primitive grows the hit area itself
  - a settings/list row has one primary target; operational history may expose a separate named recovery/export action without nesting interactive targets
  - padding is a ratio, not a leftover — the height floor is a floor, not padding, and a control's horizontal padding is roughly twice its effective vertical: fields and selects `px-4`, buttons `px-5` (`px-6` a CTA, `px-7` a `hero` action), icon buttons square at the pointer floor, list rows `px-4 py-3`, a row holding a control `px-4 py-2 min-h-16`, badges `px-2 py-0.5`, section chips `px-4`, inline notices `px-4 py-3`, cards `p-5` (`p-6` from `sm:`, `p-4` compact, up to `p-8` a hero card), sheets `p-5`
  - a row is never inset less than the gutter it sits in
  - a control and its panel never share a padding step or a radius
  - a list's row-height floor is set once by the tallest thing any row can hold
- THEME-24 [o] reach and placement:
  - the committing action of a view lives in the lower band, never a top corner: a stepped screen's in its step bar on the bottom edge (→!THEME-71), any other view's floating above the edge or the tab bar (`새 글`, `저장`, `복사`)
  - navigation is reachable from anywhere in the scroll
  - a control and the thing it commits stay on one screen — after the field, or docked
  - a dock for a list's add action stays docked at every width above the tab bar and carries NO plane of its own — no surface, no padding and no shadow behind the control — its control spanning the width on a phone and taking only the width it needs, right-aligned, from `sm:`, floating over the rows on its own shadow ← a long list pushes the one action the screen exists for below the fold, a phone's full width is the thumb's target, and a plane behind one button would be a card holding one control (→THEME-13)
  - outside a step bar (→THEME-71), a multi-action dock wraps only its controls at their useful width, centered within its parent and capped by available space; an input/composer dock uses a bounded readable width rather than spanning the desktop workspace
  - multi-action and composer docks use a compact translucent semantic surface with backdrop blur; unsupported blur falls back to a readable solid surface; the bar is one element at every width
  - one docked bar per scroller ← two sticky bars pin to the same offset
  - a dock may carry more than one row and an unused row collapses
  - feedback renders where the user is looking, in a live region mounted before its text changes
  - a dock holds controls and refusals while what is merely TRUE goes to ONE page-top status region outside the focused-job exception in THEME-40 and the post's writing card and requirements tracker (→POST-45 →POST-124) — a `ProgressBar` pinned to the top edge (`sticky`, in normal flow, no layout height, pinned below every sticky chrome row through the one `top-chrome` token, →THEME-38) plus one `meta` line carrying at most one thing in a stated precedence where a state the user must act on outranks one they only need to know, numbers belong to the bar and not the prose, and a standing state never gets an event's presentation (the editor is the reference, →POST-45)
- THEME-25 [o] one scroller per screen: the document is the only vertical scroll container — no `max-h-* overflow-y-auto` content panel and no fixed-`rows` textarea holding more than it shows (a textarea grows with `autoGrow`); four deliberate exceptions: a horizontal strip (a photo strip, a tab row, the contact-sheet carousel whose cards are narrower than the strip so a sliver of the next one shows, with a 현재/전체 indicator), a sheet's own body, a form field capped at `max-h-field` and a copy-only document (→THEME-43) ← an uncapped generated value would put the committing control thousands of pixels from the caret, and reach wins; the editor's title and memo are not capped; all four set `overscroll-behavior: contain`
- THEME-26 [o] every authenticated screen shows its current location, and every screen outside a focused flow shows the primary destinations (→!THEME-38) at every width; the shell has no hamburger-only navigation or centered modal for primary navigation.
  - a focused flow (→THEME-38) hides the destinations and keeps its own location and one way back ← one task per screen, with nothing competing with its one action
  - the clip workspace uses the wide shared frame aligned with shell content, bounding readable prose inside it; the post editor is one centred readable column at every width, its guided screens asking one question each (→POST-122)
  - each channel's work list is compact operational information inside 내 글 (→THEME-69); home offers the channels under THEME-47
- THEME-27 [o] elevation and shape:
  - three shadow steps mixed from `shadow-color` at each theme's `--shadow-strength` (night 55 %, day 14 %; `shadow-lg` at 1.4×) — `shadow-sm` resting, `shadow-md` a card or a floating panel, `shadow-lg` a modal, a docked bar or a lifted card — encoding distance from the page, never importance; the page ground casts none
  - radii `rounded-sm` (10 px) badges, checkboxes and small marks · `rounded-md` (14) fields · `rounded-lg` (20) panels and choice cards · `rounded-xl` (24) cards, sheets, dialogs and a docked bar · `rounded-2xl` (28) the tab bar's and the step bar's free edge · `rounded-full` buttons, chips, tabs, segmented controls, avatars and pills
  - an inner control is one step smaller than its panel
  - an edge-attached surface rounds the free side only (`rounded-t-2xl`)
  - no gradients on surfaces; glassmorphism is limited to the header, the tab bar, the step bar and the compact action dock under THEME-24 and promotional surfaces under THEME-37, with readable text and focus in both themes
- THEME-28 [o] motion:
  - `duration-fast` (120 ms) hover and press · `duration-base` (200 ms) reveal and dismiss · `duration-slow` (320 ms) a sheet or page transition
  - `ease-standard` for everything and `ease-emphasized` only for something arriving
  - a guided screen arrives once with a slide-and-fade at `duration-slow` — forward from the right, a step back from the left — on `transform` and `opacity` only
  - animate `opacity` and `transform` only, never layout properties
  - every control has an `active:` press state and a variant needing a resting plane on touch uses `pointer-coarse:` ← `hover:` compiles to `@media (hover: hover)` and a touchscreen never matches it
  - a pending action shows its state in place at a fixed size — a spinner covers a label hidden with `opacity-0`, never `visibility: hidden`, `display: none` or unmounting, which would drop the accessible name — and the button sets `aria-busy`
  - feedback is paced to the wait (under 1 s nothing, 2–9 s indeterminate, 10 s or more determinate plus a way out)
  - `prefers-reduced-motion` is honoured globally
- THEME-29 [o] the primitives:
  - `Button` (`cta`, `secondary`, `ghost`, quiet `danger` with a pressed plane on touch, and `scrim` for a control standing on footage — a media preview's glyph buttons — taking the `media-scrim-*` plane at rest so the glyph reads over any frame; `default` and `icon` sizes at the pointer floor — 40 px under a fine pointer, 44 under a coarse one, a `cta` 48 at every pointer (→THEME-23) — padded to the ratio; `hero` 56 px at every pointer for a step bar's big action and a list's creation button; every button a full pill that sinks by scale when pressed; `compact` 32 / 36 px only for a low-emphasis way out sharing a dock with the content it would otherwise cover, never a committing action; no vertical padding and `leading-snug`; `pending` swaps the label for a `Spinner` while holding the box; `buttonStyles` for router links and the file-input label; a committing action is `w-full sm:w-auto` on a phone, a list's add action included (→THEME-24))
  - fields (`TextField`, `Textarea`, `FieldLabel`, `FieldMessage` with `well` and editor-only `bare` appearances: a recessed `field-bg` well with no border at rest, `field-bg-hover` / `field-bg-focus` plus the global ring, validation as a `field-error` message under the field plus `aria-invalid` — the field never turns red or grows a border, labels always visible, `autoGrow`; every field states `type`, `inputMode`, `autoComplete`, `autoCapitalize`, `autoCorrect`, `enterKeyHint`; the post's 가제 and memo are wells with visible labels, →POST-50)
  - no native `<select>` anywhere — `pnpm lint:style` fails on the literal — and in its place, per surface, `Listbox`, `SegmentedControl` and `Menu`
  - `Listbox` (the labelled form field: a `field-bg` trigger at the pointer floor, `role="combobox"` + `aria-haspopup="listbox"`, named `"<label> <current value>"`, an app-drawn `surface-overlay` panel of `role="option"` rows with a check, the trigger the only tab stop, arrow/Home/End, Enter/Space, Escape and outside press; generic over the option value; its panel a bounded scroller measured to the room actually beneath its trigger, flipping above only when that room cannot hold the list and the room above is larger (→THEME-30), capped at `LISTBOX_MAX_VIEWPORT_RATIO` and floored at `LISTBOX_MIN_PANEL_PX`; an option's text is the choice and a reason goes in the message slot)
