# PUB automatic publishing retirement
> r6 | Retire automatic Naver publication in stages while preserving authored content and manual export; withdrawn publisher decisions remain as history.

## decisions
- PUB-1 [x] publishing is explicit and local-capability-bound (I1): the copy-ready export stays the universal fallback (EXPORT); Naver has no public blog-writing API, so the browser that publishes lives on the owner's Mac with its Naver login, and the VPS holds only postpilot agent credentials and a user-requested immutable publish manifest ← an overseas server would carry the login session, make the identity less familiar to Naver and harder for the owner to recover interactively
- PUB-2 [x] the whole human publishing surface is master-only: all nine PublishingService procedures sit in the interceptor's master set (→AUTH-18, →QUOTA-25); the frontend hides the nav entry, the publish panel and `/publishing-agents` from other tiers while the server stays authoritative; the PublishingAgentService bearer path is bypassed by the cookie interceptor before the master check is reached
- PUB-3 [x] publishing is separate from finalization, learning, autosave, generation, export, reconnect and polling; rendering 발행하기 issues reads only; StartPublish is called only after the user presses `네이버에 발행` and confirms that the Mac will activate Naver's final publish control without another prompt; before opening that confirmation the editor flushes any pending content save and refuses when the saved revision is no longer the finalized one
- PUB-4 [x] only the exact currently finalized `content_revision` may start; a stale tab, unfinalized post, foreign, revoked or unready agent, missing category, second live job, ambiguous outcome or already-published post is refused; the 발행하기 section appears only in 글 완성, immediately after the unchanged export panel, and no other lifecycle step renders it; there is no scheduling and no notification surface — the in-app panel is the only status channel
- PUB-5 [x] two credentials, two trust domains: human procedures use the HttpOnly session and agent procedures a separate random bearer token, and neither authenticates the other's procedures (→AUTH-21); a pairing code carries 48 random bits in three readable groups, is short-lived (`PUBLISH_PAIRING_TTL` 10m), hashed at rest, globally capped (`PUBLISH_MAX_PENDING_PAIRINGS` 8) by one atomic conditional insert, and consumed once; the raw agent token is returned once, stored only in macOS Keychain, hashed on the server, account-scoped, and invalid immediately after revocation; neither raw token nor pairing code is ever logged
- PUB-6 [x] Naver credentials, cookies, browser profile paths and CDP URLs never enter the VPS, frontend state, the RPC contract or logs; two Postpilot accounts on one Mac use separate Keychain entries, browser directories, queues and job directories; agent profile sync carries only safe driver/browser labels, the driver version, an opaque compatibility-signature id and readiness — never locators, JavaScript, coordinates, action sequences, profile paths or other executable driver configuration
- PUB-7 [x] the Mac exposes no public listener: setup is loopback-only — each run uses a cryptographic URL/form nonce, accepts only its exact loopback Host and same-origin POST, and bounds form size and actions; public HTTP API URLs are refused and HTTP is allowed only for loopback development — and work arrives through outbound authenticated polling; the agent's Connect client rejects redirects and injects the bearer only when the request origin exactly matches the configured API origin
- PUB-8 [x] setup lets the deterministic driver follow only the signed-in Naver UI to the account's own blog and open its writer without typing, uploading or publishing; it reads the logged-in blog identity, editor readiness and non-conflicting categories directly through the single local CDP page — user input, page prose and claimed identifiers are never identity evidence — accepts only the versioned editor root and the blog identity Naver selected, rechecks that the same page is still the sole CDP target, takes the first observed category as the initial default, and only then persists an unarmed recoverable local connection and lets `SyncAgentProfile` mark the server record ready; a lost sync response is retried with the same Keychain credential instead of a new pairing code
- PUB-9 [x] StartPublish reads an ownership-checked, side-effect-free snapshot from the post context (→POST-21) and freezes canonical protojson, tags, the selected category id and name, visibility, the expected Naver blog identity and the image order from IMAGE blocks; a category rename during the atomic start gate rejects the request rather than changing the frozen label; the job records the post's immutable creation timestamp with its slug snapshot so a deleted-and-recreated slug starts a new publication identity; the hand-off revalidates the complete content even for rows finalized before the current validator, and empty or canonically duplicate tags (whitespace collapsed, leading hashes removed) fail before any staging copy, a check the local publisher repeats before the fence and before readback
- PUB-10 [x] every image is the already-converted JPEG, copied server-side inside object storage to `publishing/{job_id}/{ordinal}.jpg` with its stored size verified and never read or decoded by the API (→POST-42); each IMAGE occurrence gets a unique ordinal filename plus its canonical source filename so one attached JPEG may appear at several positions without rewriting content; a cryptographically random job id is durably reserved before the first copy and never reused after a job has existed; a random-source failure or a reservation collision stops before any storage mutation; an unused reservation is released only after every staged object was removed
- PUB-11 [x] after staging, Start reserves the serialized writer, re-reads the exact post snapshot through post behavior and the current connection through publishing behavior, and inserts the job and its assets in that transaction ← concurrent post edits, photo changes, profile sync or revocation either happen before the guard and reject Start or after the frozen job exists; publishing persistence never queries the post table
- PUB-12 [x] a claim mints short-lived GET URLs (`PUBLISH_ASSET_URL_TTL` 10m) for the active lease and every claim points to the same immutable bytes and manifest; the manifest is detached from later post edits and retained only while the job can still run or receive an explicit safe retry; the Mac strips the signed GET capabilities from `manifest.json` after verified download, before the publisher may read it; publication history is not foreign-keyed to the source post, so deletion detaches rather than erases it
- PUB-13 [x] legal progress is `queued → claimed → preparing → opening_editor → filling_content → uploading_photos → filling_settings → committing → verifying → published`, with terminal `failed`, `needs_attention`, `outcome_unknown` and `canceled`; sequence numbers strictly increase and a current, unexpired lease token (`PUBLISH_LEASE_TTL` 45s) is required; progress writes compare the persisted stage and sequence atomically and failure classification reads the durable commit timestamp and stage in the same SQL mutation ← a delayed pre-commit failure cannot overwrite a concurrent commit fence; cancellation is allowed only before `committing`
- PUB-14 [x] a lease lost before `committing` requeues safely; the agent must receive a synchronous server acknowledgement that `committing` is durable before it may activate Naver's final control; a transient renewal failure cancels the local run and sends no competing terminal failure report — the server-owned lease expiry later performs the same safe pre-commit requeue or post-commit ambiguous classification; every lease renewal, progress, completion and failure boundary and its SQL mutation also rechecks that the owning agent is ready, not revoked and carries a validated deterministic executor version ← revocation or executor retirement fences an already-authenticated in-flight request atomically, not only its next claim
- PUB-15 [x] any failure, timeout, browser loss or lease expiry at or after `committing` becomes `outcome_unknown` and is never automatically retried, canceled or treated as failed ← browser publication cannot offer transactional exactly-once semantics, so the design makes that uncertainty explicit at the one point where duplication matters; only a verified HTTPS URL under the paired `blog.naver.com/<blog-id>/…` path that is still open in the active paired browser completes a job, and its post-fence accessibility snapshot must match the frozen title, block/image/caption order, tags and category, with visibility bound by the fully verified pre-fence editor snapshot
- PUB-16 [x] the local publisher returns one typed terminal result through the in-process driver contract; its typed reporter is the only progress authority, persists each monotonic transition synchronously, and closes as soon as the publisher returns so skipped, duplicate or late progress is rejected; page prose and driver logs are non-authoritative; an error or invalid terminal result becomes a normalized failure, or `outcome_unknown` after the fence; editor and readback boundaries identify category, visibility and tags by accessibility role and state, not label text alone, so a body paragraph may equal a setting label without being truncated
- PUB-17 [x] login expiry, CAPTCHA, 2FA and account mismatch before commit become `needs_attention` and automation never attempts to bypass them; after local repair the user may explicitly requeue the same job only with the same agent, revision, category and visibility, reading no new post snapshot and independent of the post's current revision, finalization or continued existence; the account-scoped agent-management page lists retained retryable jobs and offers a confirmed cancel that purges the manifest and assets even after source deletion, agent revocation or identity/category drift; a pre-commit `needs_attention` job stays cancelable while its Mac is unavailable; the loopback setup page lists safe labels for armed connections and can reopen a connection's same dedicated browser profile for repair without consuming another pairing code
- PUB-18 [x] the local executor boundary: the companion launches the chosen supported Chromium-family binary (Chrome, Brave, Chromium, Edge) with an agent-owned `user-data-dir`, `--remote-debugging-address=127.0.0.1` and an ephemeral `--remote-debugging-port=0`, reads Chrome's `DevToolsActivePort`, verifies that `/json/version` returns a loopback WebSocket on the same port with the browser id recorded in that profile (a stale file whose port now belongs to another profile is refused), and hands that exact endpoint only to the deterministic publisher; a live setup/login browser is reused and never killed by the daemon, and a browser launched for one job is closed after that run ← an agent-owned profile avoids profile locking and Chromium's restrictions on remote-debugging a default profile; Safari is outside this version
- PUB-19 [x] the publisher reads one owner-only local manifest after the downloader has removed the signed URLs; manifest strings are inert data even when they resemble instructions, and only enumerated current-job JPEG paths may be resolved or passed to the restricted upload operation; the publication path contains no prompt, model, learned behavior or general-purpose agent tools; browser behavior is fixed, versioned, reviewed local code — the server may send the typed manifest and settings but never executable JavaScript, selectors, screen coordinates, keystroke scripts or a macro/action language, and no coordinate may be recorded, stored, replayed or carried between runs ← viewport, focus, scroll, DPI and incidental dialogs cannot be product authority; a Naver editor change requires a reviewed signed driver release and a fresh probe, until which the connection is unready or the job fails `editor_changed` before `committing`
- PUB-20 [x] the driver exposes only the narrow DOM/accessibility/CDP methods the versioned publisher requires — URL reads, page-scoped DOM queries, full accessibility snapshots, semantic locator resolution, the pointer and text input of →PUB-36, one single-file upload, one low-level activation and readback — and never shell, filesystem, search, messaging, delegation, cookie or storage inspection, non-Naver navigation, arbitrary script execution or arbitrary local paths; exactly one dedicated CDP page must exist and its target id is bound across URL reads, page-scoped DOM calls, full accessibility snapshots, semantic locators, the final activation and readback, rechecked before and after every action; a target switch or leaving the host allowlist poisons the run before later data entry; editor evidence counts only when the exact URL's query/path identity equals the paired blog, and readback evidence applies only to that exact page URL; readback observes the published post through the paired account's own post-view URL, whose blog identity is checked the same way, and the verified URL it reports is the canonical permalink rather than the URL it read ← the permalink renders the post inside a script-built frame, while the post-view URL serves the same post in the bound page's own document in the editor's own component vocabulary, so no frame-scoped observation has to join the driver surface
- PUB-21 [x] before the fence every mutation resolves a versioned semantic locator against current DOM/accessibility evidence and any DOM mutation invalidates the cache; missing, renamed, duplicate or unexpected controls, keyboard submission, native-dialog acceptance and unversioned publish-like controls fail closed; JPEGs are uploaded one at a time in exact manifest-ordinal order, each counted only after a successful one-file upload followed by a fresh full accessibility snapshot showing exactly one additional editor image (resolving a path or an upload API acknowledgement alone is not evidence); TEXT, HEADING, QUOTE, LIST and ordered IMAGE + caption blocks map exactly as the Naver export does (EXPORT)
- PUB-22 [x] the fence requires a current full snapshot matching the title, the exact semantic body sequence with no inserted text or image, block/image/caption order, the exact ordered tag collection with no extra or duplicate tag, the frozen category name and id, and visibility, with category and visibility exposing selected or checked state; any subsequent pre-fence interaction invalidates that verification; from photo verification onward every activation is blocked until the synchronous server commit-fence call succeeds; the fence accepts exactly one button whose accessible name is in the versioned final-control allowlist (scheduled, generic, renamed or duplicate publish-like controls cannot arm it); after acknowledgement, authorization is consumed before exactly one low-level activation is sent with automatic retry disabled and every other or repeated mutation blocked; missing evidence, action-order errors or a rejected durable progress call fail closed
- PUB-23 [x] one owner-only OS file lock permits only one companion daemon on a Mac (a manual `run` and the LaunchAgent never operate together) and a process-local permit additionally serializes every paired account's claim and publisher execution; startup removes abandoned job directories only after acquiring the lock; the daemon reloads the owner-only config every two seconds and starts newly armed connections without restart; each job downloads its signed JPEGs to a random owner-only per-job directory without forwarding auth, rejecting redirects or hosts outside the signed storage target and verifying filenames, byte counts and count, and deletes local job data on every terminal or abort path
- PUB-24 [x] setup and diagnostics run a versioned non-publishing compatibility probe against the exact dedicated profile — the required Chromium/CDP/accessibility capabilities, the sole-target rule, the Naver-selected account identity, category discovery, the editor root and signature, semantic locators and the readback surface — and refuse to arm a connection on any mismatch; recorded driver, browser and editor versions are diagnostics, never a substitute for capability evidence; compatibility data selects only code already present in the installed reviewed agent; the driver is versioned together with its editor signature, locator set, supported CDP capabilities and manifest schema
- PUB-25 [x] retention and recovery: published, failed, canceled and ambiguous jobs purge manifest content and staged objects while retaining metadata, structured failure, settings, timestamps and the verified URL; `needs_attention` retains its exact frozen manifest and assets only for explicit safe retry; recovery checks leases at half the configured TTL, marks expired post-commit work ambiguous and requeues only pre-commit work; lease recovery is a database-only startup requirement while terminal object cleanup is retryable sweeper work — the independent publishing orphan sweep (`PUBLISH_ORPHAN_SWEEP_INTERVAL` 24h, `PUBLISH_ORPHAN_MIN_AGE` 1h) removes old unreferenced `publishing/` objects and protects every key a live or retryable job references ← an object-store outage must neither take down login or unrelated reads nor make a durable terminal transition look ambiguous to the Mac or the human client; terminal cleanup attempts all assets and all terminal jobs before returning an aggregated error, and only fully cleaned jobs lose their asset rows
- PUB-26 [x] raw browser or driver failure detail never enters an agent RPC: the Mac records only a redacted diagnostic marker and the VPS derives `PUBLISH_AGENT_UNAVAILABLE`, `PUBLISH_NEEDS_ATTENTION` or `PUBLISH_OUTCOME_UNKNOWN` plus optional technical detail solely from the constrained failure kind, localized by the frontend (LANG); transient agent-auth storage failures stay retryable and only a revoked token permanently stops a connection; a revoked Mac encountered by a human session is `FailedPrecondition`, never `Unauthenticated` ← it must never log the human user out
- PUB-27 [x] a non-terminal publish job (`queued`, `running`, `needs_attention`) blocks deletion of its source post with `POST_PUBLISHING` (→POST-29) through the published query `HasLiveJobForPost`, keyed on user, slug and `post_created_at`, consumed by the post context through a port wired in the composition root — it takes no lease and mutates nothing; terminal publication history deliberately outlives its post: there is no foreign key to `posts`, `publish_jobs.post_created_at` beside the slug keeps a deleted post's history distinct from a later post reusing the slug, `publish_jobs_deleted_post_history_idx` indexes that lookup and `LatestJobForDeletedPost` reads it so a retained `needs_attention` job stays retryable after its post is gone; the block is a read, not a lock — a publication started between the delete's check and its row delete completes correctly against its frozen manifest and job-owned `publish_assets.staged_key` objects
- PUB-28 [x] `last_seen_at` is a display hint and never an authorization input; the server refreshes it at most once per `PUBLISH_AGENT_HEARTBEAT_INTERVAL` (15s) per agent, on the first poll after the interval ← the Mac polls far faster than the freshness window and the single writer must stay free for real work; the interval plus the agent's poll (5s) must stay below the frontend's `PUBLISH_AGENT_STALE_MS` (30000) or a live agent renders offline, and lowering the poll multiplies requests without multiplying writes; a failed refresh is logged and the call proceeds, except a revocation the write itself discovers
- PUB-29 [x] the Mac companion (`agent/`, →ARCH-12) uses typed defaults of 5 s polling with jitter and backoff (`Supervisor.Run`'s fallback), 10 s lease heartbeats strictly below the server lease TTL, a 15-minute job timeout that yields unknown rather than retry after commit, HTTPS except loopback development, an OS-selected loopback setup port and owner-only app and work directories; it validates the enrollment lease and every claim's advertised lease TTL against its heartbeat cadence before running work, and a renewal failure cancels the active driver at once; it is installed as a user LaunchAgent with a reproducible build, install, uninstall and diagnostics flow, and uninstall never deletes a browser profile or Keychain credential without a separate explicit confirmation
- PUB-30 [x] frontend: `widgets/publish-panel` is composed directly after the unchanged export panel only in 글 완성 in `pages/editor`, never importing one widget from the other, with no-agent, unavailable-but-queueable, ready, running/history, published-link, failed, `needs_attention` and `outcome_unknown` states and the explicit `네이버에 발행` confirmation; `entities/publishing-agent` and `entities/publish-job` carry account-scoped query keys, proto mappers, category/default/last-seen projections, job polling (`PUBLISH_JOB_POLL_MS` 2000 while a nonterminal job is visible) and explicit terminal/error models; `features/publish-post` handles category and visibility selection, stale-revision-aware confirmation, start and cancel, and invalidation; mounting a query or rendering a control never calls StartPublish; the `/publishing-agents` page creates and displays a short-lived single-use device code, shows only safe server metadata (connection, blog and browser labels, defaults, categories, health and last seen), explains that Naver login stays on the Mac, and never renders or stores an agent bearer token, Naver credential, cookie, CDP endpoint or local path in browser state, query cache, analytics or logs
- PUB-36 [x] pointer and text input belong to the narrow driver surface: the driver may focus or activate a control by dispatching a pointer event at the live geometry of the single element its versioned semantic locator just resolved, and may insert manifest text at the resulting caret; the same locator-derived caret is what positions an inserted image, which Naver places immediately after the block holding it, so a position is never a coordinate and never a pre-allocated slot; the geometry is read at action time and every such action stays bracketed by the full observations of →PUB-21 and →PUB-22 ← SmartEditor renders its document outside contenteditable and offers no semantic caret placement, so the observation and not the coordinate has to carry the authority
- PUB-37 [x] tags, category and visibility are reachable only inside a settings layer the publisher opens, and that layer covers the editor: the title, every body block and every photo are complete and observed before it opens, no body mutation follows it, and the fence's full snapshot (→PUB-22) is taken with it open, which is the one place all three settings and the final control are observable at once; opening it is a versioned step that fails closed like any other, and reaching a setting may require opening one control inside the layer before the setting itself resolves ← an occluded editor turns a body mutation resolved from its own geometry into a click on whatever the layer put over it
- PUB-31 [x] Instagram Reels, Naver Clip or any other platform; video generation or short-form metadata; Web Push, email, Telegram or any completion notification; scheduled publication; publishing as a side effect of finalize, finalize-and-learn, autosave, generation, opening the panel or reconnecting; Safari, iOS browser control, a menu-bar app, App Store packaging, automatic Mac wake, simultaneous browser runs, a general remote-control channel; screen-coordinate recording or a server-supplied macro language; bypassing CAPTCHA, 2FA, suspicious-login or bot checks; automatic reconciliation after an ambiguous final click; reformatting the canonical content into a new rich-text model — out of scope
- PUB-32 [x] the Mac owns a durable local connection draft id generated independently of every server-issued device code: starting a new connection creates one draft and one isolated Chromium profile, and reopening that draft, closing and relaunching its browser, restarting the setup companion, replacing an expired device code and retrying pre-enrollment setup all resolve to the same profile path without clearing or copying browser storage ← the pre-enrollment path derived the local id from the single-use device code, so a replaced code opened a new empty cookie jar that looked like a private window to the user
- PUB-33 [x] device-code replacement changes only the one-time authorization presented to Postpilot; successful enrollment binds the server agent identity and Keychain token to the existing local draft and does not rename, relocate, recreate or reset the profile; all later repair and publishing runs for that armed connection use the bound paths; stopping and restarting the setup companion before enrollment presents the unfinished draft as resumable with the same paths, and no server token is required merely to preserve or reopen that browser state
- PUB-34 [x] creating a genuinely new connection is explicit and creates a new draft with a different cookie jar; the companion never guesses an association from a label, browser choice, directory age, current Naver login or device code, and an absent, malformed, duplicated or conflicting draft identity fails closed with an actionable local error; every setup, repair and publishing launch uses the connection-owned persistent `user-data-dir`, never incognito, guest or a temporary profile, and does not clear cookies or storage on normal launch or exit; two accounts on one Mac remain isolated and reopening either never opens the other's jar
- PUB-35 [x] upgrade behaviour: existing armed connections retain their configured profile paths; legacy unowned code-derived directories are left untouched and never automatically attached, merged, copied or deleted; there is no automatic migration between Chrome, Brave, Chromium and Edge; profile deletion requires a separate explicit local destructive confirmation and is never a side effect of revocation, repair, upgrade or uninstall; the contract preserves browser storage and promises nothing about Naver keeping its own session valid — logout, expiry, CAPTCHA, 2FA, suspicious-login checks and blog-identity mismatch still stop locally for repair or become `needs_attention`, and no authentication material or profile detail reaches the VPS; no new env, shared-config or platform-config value, dependency, server contract or migration
- PUB-38 [o] automatic Naver publication is retired for every tier, including master; the product has no paired publishing companion, automatic editor filling, scheduled publication or automatic final click after retirement completes
- PUB-39 [o] retirement starts by refusing every new pairing, enrollment, start, retry, readiness activation, claim, lease renewal and commit authorization; old clients and already-paired devices cannot restore execution, and no configuration switch re-enables it
- PUB-40 [o] at cutover, queued, attention-required and running pre-commit jobs become canceled; any unfinished job with a durable commit timestamp or a committing/verifying/published stage becomes outcome_unknown; already terminal outcomes and known published URLs remain unchanged until exported for retirement
- PUB-41 [o] retirement never retries or automatically reconciles an uncertain publication, claims that a final action already authorized was undone, or edits/deletes a post on Naver; stopping every installed companion precedes destructive data cleanup
- PUB-42 [o] retirement preserves canonical posts, revisions, finalization, voice learning, photo/video originals, clip outputs and every EXPORT copy format; publishing-owned copies and execution records have no ownership over these source assets
- PUB-43 [o] the publishing navigation, final-step panel, pairing and agent-management surfaces, progress polling, plan benefits and marketing claims are removed; old /publishing-agents links redirect to /posts without a publishing request or replacement publishing screen
- PUB-44 [o] local retirement stops the installed daemon and removes its LaunchAgent, binary, job files, Postpilot device credentials, config and logs without opening Naver; browser login profiles are preserved by default and can be erased only by a separate explicit local destructive choice identifying the profile paths, never by server revocation
- PUB-45 [o] before deleting publishing records, produce an owner-only retirement report with job/account identity, terminal status, commit/publication timestamps, safe failure reason and known published URL, plus the companion inventory needed to verify shutdown; omit contents, manifests, media, credentials, token hashes, signed URLs and browser paths; the report is an operator-held file, not a new retained product history service
- PUB-46 [o] after execution is stopped and the report is verified, delete all publishing-owned staged copies and execution/connection records; cleanup is repeatable and must retain enough bookkeeping to retry every failed object deletion; any incomplete shutdown, report or cleanup blocks final removal without modifying unrelated data
- PUB-47 [o] the final product has no publishing runtime, API, device authentication, queue, sweeper, settings, stored records/tables, companion source, generated client, installer, dedicated CI job or executable live-survey harness; historical migrations, withdrawn spec decisions and completed-task/review evidence remain as migration/history artifacts
- PUB-48 [o] cutover and final removal are separate rollout checkpoints; returning to a pre-retirement build must not re-enable publishing, and final removal proceeds only after companion shutdown and data cleanup are evidenced for each deployed environment
- PUB-49 [o] retirement is validated with deterministic local fixtures and upgrade/fresh-install checks; no real Naver publication is part of its acceptance, and deferred photo-row/video automation is removed from the product roadmap

## flow
- retire: refuse new execution and revoke device capabilities → classify outstanding jobs → remove product surfaces → stop installed companions → verify private retirement report → purge publishing copies and records → remove runtime/schema/contracts/tooling → verify absence and preserved export
- unresolved external result: durable commit crossed → outcome_unknown in retirement report → owner checks Naver manually; never automatic retry or deletion

## constraints
- retirement applies to every account and environment; server-side denial precedes client removal and credentials never enter the report
- browser profiles and existing Naver posts are user data, not automatically deleted publishing infrastructure
- transient compatibility/cleanup tools are removed after their rollout checkpoint; historical migration files remain executable for fresh and upgraded databases
