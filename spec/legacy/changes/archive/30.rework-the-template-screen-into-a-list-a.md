# 30. Change: Rework the template screen into a list and a dedicated block editor

> A **change proposal** (a WHAT delta) that modifies the already-shipped behavior of [plan/11.post-templates](../../plan/11.post-templates.md).
> Filled by /create-change through a user interview — a reviewable doc, not a one-line prompt.
> The STEPS live in the job that /create-change-job creates. Write it in English.

## As-is

Change 25 (job 53) replaced the prose 용도 with a **템플릿** whose body is a small tag grammar
([tech/post-template-grammar](../../tech/post-template-grammar.md)). The grammar is the right contract — the server
expands `<repeat>` against the real attachments and freezes the result at enqueue — but `/templates` presents it as
if the *user* were its audience, and the screen is unlike every other authoring surface in the product.

Five specific failures, all on the frontend:

1. **The empty state teaches a notation — and not even the real one.** `page.exampleBody` renders a worked template
   body as copy: a literal separator line, indentation, and `{작성}` / `{자리}` / `{반복}` / `{사진}` markers. That
   brace notation is a **third** spelling of the grammar, and it exists nowhere else in the product — the stored
   body is XML tags (`<write>`, `<slot kind="place"/>`, `<repeat each="photo">`) and the builder labels the same
   blocks 작성 · 자리 · 반복 · 사진 with no braces at all. So the first thing a new user reads is a syntax they can
   neither type anywhere nor find again.

   The deeper problem is that it should not be there at all. The grammar exists so the *write prompt* can carry a
   shape a model reads reliably; it is an internal encoding between the builder and the prompt, and the user's
   half of the contract is the blocks, not their spelling.

2. **The body editor exposes its own storage format.** `TemplateBodyEditor` is a `SegmentedControl` over two modes —
   **구성** and **원문** — of one string. The 원문 tab is a monospace textarea holding raw
   `<write>…</write>` / `<repeat each="photo">`. It exists today for two reasons the user does not share: a body
   that fails to parse can only be repaired there, and a hand-written body that parses gets its spacing normalized
   by the structure view.

3. **The structure is not legible.** Every block renders as a kind eyebrow, a `FieldLabel`, and a full-width input,
   stacked vertically. A six-block template is six label/input pairs roughly 120px tall each; the *shape of the
   post* — intro, then a map slot, then one description per photo, then a closing — is not visible anywhere without
   reading each field. The thing the screen exists to author is the thing it does not show.

4. **Creation sits outside the list, unlike every sibling.** `/templates` renders the saved list and then, below it,
   a permanently expanded `CreateTemplateForm` with its own name/description/body-editor triple. `/voices` is a list
   plus one docked action that adds to it; `/posts` is a list plus 새 글. Templates is the only authoring surface
   where an empty second copy of the whole editor is always on screen, which also means the block palette and the
   mode switch appear twice.

5. **There is nowhere to edit a template.** A template has no screen of its own. Each row carries three read-first
   fields that save independently the moment each is confirmed, so the row grows to hold a full body editor inline
   and the list stops being a list. A voice, by contrast, has `/voices/$voiceId`.

Nothing about the grammar, the parser, the server-side expansion, the RPC surface or the storage is at fault, and
none of it is what this change touches.

## To-be

`/templates` becomes a **list**, and a template becomes a **screen**, exactly as a voice already is.

### The list

- `/templates` renders the account's templates as rows and nothing else. A row shows the name, the description and
  the post count, and the whole row is the way into that template. The delete stays on the row, above the link
  layer, as it is on `/voices`.
- One docked action at the bottom: **`+ 새 템플릿`**. It is the only thing on this screen that adds.
- The empty state says what a template is for **in plain language** and shows no grammar, no marker syntax and no
  worked body. It seeds nothing — there are still no shipped presets.

### The screen

- **`/templates/$templateId`** edits one template. **`/templates/new`** is the same screen with nothing in it, and
  `+ 새 템플릿` goes straight there — no naming sheet in between. A `new` screen that is left without saving creates
  nothing at all.
- The screen holds a single **draft**: name, description and composition together. Nothing is written until the one
  **저장** at the bottom, which is the screen's only committing action. It is disabled while the draft equals what
  is stored, and leaving with unsaved changes is warned about.
- Layout, top to bottom: a back link to the list · the name and description fields · a **추가 툴바 that stays put
  while the composition scrolls** · a **bounded composition area** · 저장.

### The composition area

- **One line is one block.** A collapsed row shows the block's kind as a badge and its content as one truncated
  line, so the list of rows reads as the outline of the post. A `repeat`'s children are indented rows under it.
- **Clicking a row expands that row alone**, revealing its fields inline; clicking again collapses it. At most one
  row is expanded at a time, so the outline stays readable while one block is edited.
- **Reordering and editing happen only inside this area.** Pointer drag and the move buttons both stay — the base
  device is a 360px phone and HTML5 drag events do not fire on touch.
- **The toolbar inserts at the current position.** The current position is after the row last touched — expanded,
  dragged or added — and *inside* a `repeat` when that is where the position is. The area **shows** where the next
  block will land; a toolbar that inserts somewhere the user cannot see would be worse than the two entry points it
  replaces. With no current position, the toolbar appends to the end.
- The palette offers the same seven commands it does today, and `repeat` is still refused inside a `repeat`.

### The source view is gone

- There is no 원문 mode and no mode switch. The grammar string never appears in the interface.
- A stored body the parser cannot read is not silently dropped and not silently repaired: the screen says **the
  composition cannot be read** and offers exactly one action — **clear the composition and build it again**. The
  name and description are untouched and still editable, and nothing is written until 저장.
- This is deliberately destructive-on-request rather than lossy-on-load: a body only ever authored by the builder
  cannot reach this state, so the case is a row from before the builder existed, and the honest thing is to say so
  rather than to guess at a structure the author did not write.

## Scope / Non-goals (regression boundary)

**In scope**

- `/templates` as a list plus one docked `+ 새 템플릿`, matching `/voices`.
- `/templates/$templateId` and `/templates/new` — one screen, one draft, one 저장, an unsaved-changes warning.
- The composition area: collapsed one-line rows, one row expanded at a time, indented `repeat` children, drag and
  move-button reordering bounded to the area.
- The always-visible add toolbar, its current-position insertion, and the visible indication of where that is.
- Removal of the 원문 mode, the mode switch, and every rendering of grammar syntax to the user — including the empty
  state's worked example.
- The unreadable-composition state and its single 비우고 다시 만들기 action.
- Whatever `entities/template/ui/TemplateBodyEditor.tsx` has to become, and the relocation of `create-template`'s
  form into the shared screen.

**Non-goals — these must NOT change**

- **The grammar itself.** The five constructs, the tag syntax, the parse rules, the canonical serialization and
  `tech/post-template-grammar.md`'s contract are untouched. This change moves who sees it, not what it is.
- **The backend, entirely.** No proto field, no RPC, no migration, no store query, no service rule. `templates.body`
  keeps holding exactly the same strings; a template saved before this change and one saved after are
  byte-identical for the same composition.
- **Server-side expansion, freezing and prompt injection.** `<repeat each="photo">` still expands against the post's
  attachments at enqueue, the expansion bound still refuses an over-long render, and the frozen brief still reaches
  the write and revise prompts unchanged ([policy/templates](../../policy/templates.md) *Rendering, freezing*).
- **Slots in the canonical post** ([I2]): `<slot>` still resolves to the same blocks in the same positions.
- **The field rules and the caps** — name/description/body limits, the per-account cap, the name-taken refusal,
  and `TEMPLATE_MAX_REPEAT_EXPANSION` — all unchanged, and the client still predicts none of the server's refusals.
- **Assignment and the picker.** The `템플릿` select on the editor and `/posts/new`, its 없음 default, the
  presence-aware patch, the running-job behavior and the post list's name projection are untouched.
- **Deletion semantics.** A delete still detaches rather than cascades and still confirms against the post count.
- **No model and no job** ([I5]). Nothing on either screen calls a provider or enqueues work; a template is
  authored text and every write here is plain CRUD.
- No template versioning, history, duplication, import/export, preview-against-a-real-post, or seeded presets.
- No change to `/voices`, `/guidelines` or any other screen; this change only makes templates match them.

## Acceptance Criteria

1. `/templates` shows only the list and one docked `+ 새 템플릿`; no create form, no block palette and no mode
   switch appears on it. The empty state contains no grammar syntax and no worked body, and creates no row.
2. `+ 새 템플릿` opens `/templates/new` with an empty draft. Leaving it without saving creates no template, and the
   list is unchanged.
3. A row on `/templates` opens `/templates/$templateId` with that template's name, description and composition
   loaded into one draft.
4. 저장 is disabled while the draft equals what is stored, enabled once any of the three differs, and writes all
   three in one action. Leaving with unsaved changes warns first.
5. The composition area renders one row per block, collapsed, showing the kind and a one-line summary; a `repeat`'s
   children render as indented rows beneath it. The whole composition is readable without expanding anything.
6. Clicking a row expands that row alone and collapses any other; its fields edit in place.
7. A block added from the toolbar lands at the current position — inside a `repeat` when that is where the position
   is, and at the end when there is none — and the area showed where that was before the click.
8. Both pointer drag and the move buttons reorder within the composition area, and neither can move a block out of
   it. `repeat` is still refused inside a `repeat`.
9. No screen renders `<write>`, `<repeat>`, `<slot>`, `<note>` or any other grammar syntax to the user, and there is
   no 원문 mode or mode switch anywhere.
10. A template whose stored body does not parse opens with its name and description editable, says the composition
    cannot be read, and offers only 비우고 다시 만들기 — which empties the composition in the draft and writes
    nothing until 저장.
11. For an unchanged composition, the body the screen saves is byte-identical to what was stored before this change,
    and a generation started from that template produces the same frozen brief.
12. Nothing on either screen calls a provider or enqueues a job, and no template write happens except through 저장
    and the row's delete.

  with the object's own screen behind the row. `design-language` §1.5 (the 360px base), §4.1 (44px targets),

  the composition area must not become a second one).
- Affected policy / tech: [policy/templates](../../policy/templates.md) — its whole *Frontend* section is rewritten
  (the two modes, the forced source view, the worked example, the create form's position). **The
  *Editing* section changes too**: field-at-a-time saving becomes one screen-level save.

  framing gains that the grammar is never shown to the user.
  [policy/posts](../../policy/posts.md) is untouched (the picker is a non-goal).
- Affected config: **none.** No new value, and no existing one changes owner. The template limits stay where they
  are (`TEMPLATE_NAME_MAX_CHARS` / `TEMPLATE_DESCRIPTION_MAX_CHARS` / `VITE_*` mirrors in `shared/config`;
  `TEMPLATE_MAX_PER_ACCOUNT` / `TEMPLATE_MAX_REPEAT_EXPANSION` backend-only). The collapse/expand rule, the block
  palette's contents and the current-position rule are **code, not configuration** (ARCHITECTURE §4).
