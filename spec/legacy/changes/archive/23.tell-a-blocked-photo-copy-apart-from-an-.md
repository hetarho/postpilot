# 23. Change: Tell a blocked photo copy apart from an expired view URL

> A **change proposal** (a WHAT delta) that modifies the already-shipped behavior of [plan/08.platform-export](../../plan/08.platform-export.md).
> Filled by /create-change through a user interview — a reviewable doc, not a one-line prompt.
> The STEPS live in the job that /create-change-job creates. Write it in English.

## As-is

A per-photo copy on the Naver export tab names its failure by kind on the photo that failed: `unsupported` (no
image clipboard), `refused` (the write was rejected), `unreadable` (the bytes never became an image), and a
separate "no matching photo" placeholder (plan 08 *As-built extension — job 44 / change 17*,
[policy/export.md](../../policy/export.md) *Photo copy*).

`unreadable` collapses two unrelated situations, because `loadPng` reaches the same `catch` for both: a `fetch`
that **rejects** (the browser blocked the request — no CORS allow from the bucket, a network fault, mixed
content) and a `fetch` that **resolves with a non-2xx response** (the presigned view URL expired; view URLs are
minted per `GetPost` with a 10-minute TTL and `usePost` refetches only on mount). Both surface the one message
"사진을 읽지 못했어요. 글을 다시 불러오면 사진 주소가 새로 발급돼요." / "Could not read the photo. Reload the
post to mint a fresh photo URL."

That message is **correct advice for exactly one of the two**. When the bucket does not allow a browser `GET`,
reloading remints a URL that is blocked just the same, and the user is sent around a loop that cannot end. The
failure is also invisible from the panel's own evidence: `<img>` needs no CORS, so the photo renders while its
URL is unfetchable, and the existing guard (`failedUrl` from `onError`, which disables the control) never fires.

The bucket side is a hand-typed step. [DEPLOY.md](../../../DEPLOY.md) §5 prints a CORS JSON body for the operator to
paste into the Cloudflare dashboard. Its `AllowedMethods` lists `PUT`, `GET`, `HEAD`, but nothing in the repo or
the deploy verifies that what the bucket actually holds matches: an operator who pastes a `PUT`-only rule gets
working uploads and photos that display, and the copy control is the only thing that breaks. Cloudflare requires
a bucket CORS policy for presigned URLs consumed by a browser, and applies it to the S3 API endpoint the app
signs against. The deploy already ends with a CORS preflight gate for the API origin
(`.github/workflows/deploy-backend.yml` *Verify CORS preflight for the browser origin*); the bucket has no
equivalent.

## To-be

**One. The two read failures are separate kinds with separate messages.**

`copyImage` distinguishes them by *how* the fetch ended, which is already available at the point of failure:

- a rejected `fetch` on a URL whose SigV4 lifetime had **not** run out → a new kind, **`blocked`**: the bytes were
  not served to this origin. The photo says the copy cannot be used right now and points at the text output beside
  it — it does **not** tell the user to reload, because reloading cannot fix a rule on the bucket.
- a rejected `fetch` on a URL that **had** already expired, a resolved response that is not `ok`, and a decode or
  encode failure → **`unreadable`** keeps its present meaning and its present message: reloading the post remints
  the URL, which genuinely fixes it.

  **The response cannot make this distinction, so the URL does.** R2 answers an expired read with a 403 that
  carries no CORS headers, so the browser withholds it and `fetch` rejects exactly as it does for a missing `GET`
  allow (Cloudflare, *R2 → CORS → Use CORS with a presigned URL*). Classifying by the response would therefore
  have relabelled every expired URL as `blocked` — trading the old dead end for a new one. SigV4 states the
  lifetime in the URL's own query (`X-Amz-Date` + `X-Amz-Expires`), so the answer needs no request. A wrong client
  clock costs a less useful message and nothing else.

The panel renders the new kind on the photo that failed, on the same per-photo status line, with the same
`copyGeneration` / `copyQueue` discipline and the same live region as every other kind. No console diagnostics
are added.

**Two. The bucket CORS rule is a repo-tracked file, applied by a command and verified by the deploy.**

- The rule lives in the repo as `deploy/r2-cors.json` — one artifact, reviewable in a diff.
- DEPLOY.md §5 replaces its paste-this-JSON prose with the Wrangler command that applies that file
  (`npx wrangler r2 bucket cors set <bucket> --file deploy/r2-cors.json`), so the allowed methods can no longer
  drift from what the app needs by a transcription slip.
- The backend deploy gains a step, beside the existing API CORS gate, that fails the deploy when the bucket does
  not allow a browser `GET` from the web origin: a CORS **preflight** (`OPTIONS` with
  `Access-Control-Request-Method: GET`) against the bucket endpoint, asserting the response allows that origin
  and that method. A preflight needs no signature, so the check needs no presigned URL and no session.
- The check reads `R2_ENDPOINT` and `R2_BUCKET` from the stack `.env` through the `compose config --environment`
  helper the rollout step already uses, and the browser origin from the existing `WEB_ORIGIN` repo variable. It
  therefore introduces **no new GitHub secret or variable** — deliberately, because the project's GitHub account
  cannot create repo secrets.
- Like the API CORS gate, it runs **separate from the rollout and does not roll the image back**: a bucket rule
  is not a bad image, so it must fail loudly rather than trigger a rollback that cannot fix it.

## Scope / Non-goals (regression boundary)

**In scope**

- `shared/lib/clipboard/copyImage`: the new `blocked` kind and the rejected-vs-not-ok discrimination.
- `widgets/export-panel`: rendering the new kind per photo; the new i18n message in the `posts` catalog (ko + en).
- `deploy/r2-cors.json` (new), DEPLOY.md §5, and the bucket CORS verification step in
  `.github/workflows/deploy-backend.yml`.
- Reflecting both into the SSOT: plan 08's as-built photo-copy failure kinds, and [policy/export.md](../../policy/export.md)
  *Photo copy*.

**Must NOT change (regression boundary)**

- **The clipboard payload.** Exactly one `ClipboardItem`, `image/png` only, and the write still issued **before**
  the bytes arrive — the WebKit user-activation reason for that ordering is untouched, and no text flavor or text
  fallback is added for a photo ([I1]).
- **`toNaver` and the other three formats.** The copied string stays byte-identical; format snapshots are untouched.
- **The existing kinds.** `unsupported`, `refused`, the no-matching-photo placeholder, and `unreadable`'s message
  and meaning all stay as they are; only the population that reaches `unreadable` narrows.
- **The disabled-control rules.** A `blob:` preview photo and a photo whose `<img>` failed still offer no copy
  control; a marker with no photo keeps its inline position.
- **URL minting.** The 10-minute presign TTL, `usePost`'s `refetchOnMount: 'always'`, and the per-`GetPost` mint
  stay exactly as they are. A leaked URL is a leaked object, so the TTL is not widened to paper over this.
- **The rollout and health gate.** The new deploy step neither gates the image swap nor rolls it back.

**Non-goals**

- **Automatically refetching `GetPost` and retrying the copy when a URL has expired.** Explicitly deferred by the
  owner: it would thread a `refetch` from `DraftEditor` into `ExportPanel` and re-open the user-activation
  question, for a case the (now accurate) message already resolves with a reload.
- Console or telemetry diagnostics for the blocked case.
- Bulk photo download — still the unfilled PRD gap plan 08 records.
- Applying the rule to any bucket; the change ships the file, the command and the gate, not a credentialed write.

## Acceptance Criteria

<!-- The testable criteria that mark this change done. Copied into the job's Acceptance Criteria section. -->

1. `copyImage` returns `blocked` when the photo `fetch` rejects on a URL whose presigned lifetime has not run out,
   and `unreadable` when it rejects on an already-expired URL, when the fetch resolves with a non-2xx response, or
   when the decode/encode of a readable response fails.
2. A blocked photo copy shows, on that photo, a message that points at the text output beside it and does **not**
   tell the user to reload the post; an expired-URL copy still shows the existing remint-by-reloading message.
3. The clipboard payload is unchanged for a successful copy — one `ClipboardItem`, `image/png` only, the write
   issued before the bytes arrive — and no text flavor or text fallback is introduced for a photo.
4. Both messages exist in the Korean and English `posts` catalogs, and the panel renders them per photo through
   the same status line, feedback dwell and live region as the existing kinds.
5. `deploy/r2-cors.json` exists in the repo and allows `GET` (alongside `PUT` and `HEAD`) for the web origin, and
   DEPLOY.md §5 applies it with the Wrangler `r2 bucket cors set --file` command instead of prose JSON.
6. The backend deploy fails when a CORS preflight for `GET` from `WEB_ORIGIN` against the configured bucket
   endpoint is not allowed, reading the endpoint and bucket from the stack `.env` and adding no new GitHub secret
   or variable; the step does not roll the image back.
7. No regression: `toNaver` output and the other three formats are byte-identical, the existing failure kinds and
   the disabled-control rules behave as before, and the presign TTL and `usePost` refetch policy are unchanged.
