# 01. Change: Migrate Current UI to the Design System

> A **change proposal** (a WHAT delta) that modifies the already-shipped behavior of [plan/02.post-drafting-and-list](../../plan/02.post-drafting-and-list.md).
> Plan 02 is the primary target because it owns most of the currently shipped product UI. The
> migration also covers the login and authenticated shell from
> [plan 01](../../plan/01.accounts-and-login.md) and the model selector from
> [plan 04](../../plan/04.model-provider-registry.md).

## As-is

Plans 01, 02, and 04 have shipped the current frontend surface: the login screen, authenticated
shell, post list, draft editor, autosave status, browser photo workflow, and per-stage model
selector. Their product behavior is covered by feature tests and their respective plan contracts.

The design foundation now defines a three-layer colour system in
`frontend/src/app/styles/index.css`:

- a private OKLCH palette;
- semantic foundations for the five physical planes (`surface-lowest` → `surface-highest`),
  content hierarchy, intent, interaction, and physical light; and
- functional roles for buttons, fields, navigation/rows, badges, notices, focus/selection, and
  media overlays.

However, the shipped UI predates that contract. Generic controls are still styled directly inside
`app`, `pages`, and `features`: bare buttons, inputs, a textarea, a select, a label-backed file
trigger, button-like router links, and locally styled status/error treatments. There is no
`frontend/src/shared/ui` primitive inventory yet, so equivalent states do not inherit one API,
size, interaction, accessibility, or colour contract.

The old `bg` / `surface` / `text` / `primary` / bare status / `border` colour vocabulary remains
exported as a temporary compatibility bridge. Current call sites still consume those aliases, so
the functional token groups are not yet the real UI contract and the style linter cannot reject
regressions to the old vocabulary.

## To-be

Every UI surface that exists after plan 04/job 06 is composed according to
[`spec/tech/design-language.md`](../../tech/design-language.md):

- Page composition uses the five-level surface hierarchy and content hierarchy. Controls use the
  narrow functional colour group that names their purpose (`button-cta-*`, `field-*`,
  `notice-*`, `badge-*`, `row-*`, and so on), including explicit hover, active, focus, disabled,
  pending, error, and selected states where the control supports them.
- Generic interactive UI is owned by `frontend/src/shared/ui`. The migration creates only the
  primitives and variants required by the current screens. A slice reuses an adequate primitive;
  when none exists, the smallest domain-agnostic primitive required by that screen is added first.
  No unused primitive, speculative variant, or complete component kit is built in advance.
- Every element presented as a button, including button-like router links, icon-only actions, and
  the file-picker trigger, shares the Button visual/interaction contract without losing its native
  navigation, label, or submit semantics. Text inputs, textarea, editor-bare fields, select, and
  badges likewise share their respective primitive contracts.
- Product-named UI such as `PhotoStrip`, `SaveStatus`, `UploadProgress`, and
  `StageModelSelect` remains in its FSD slice and composes primitives where it contains generic UI;
  the migration does not flatten domain UI into `shared`.
- Login, shell, list, editor, photo, and model-selection screens may change layout, spacing, and
  visual hierarchy to satisfy the binding design language. Their routes, user-visible operations,
  data flow, asynchronous state transitions, and error meanings remain unchanged.
- The temporary legacy colour aliases are deleted once no call site needs them. `pnpm lint:style`
  rejects the retired utility vocabulary as well as the existing stock palettes, raw colours, and
  arbitrary escapes.
- Both `night` and `day` render from the same functional roles. The existing absence of a theme
  switcher remains unchanged; theme validation is performed by setting `data-theme` during review.

## Scope / Non-goals (regression boundary)

**In scope**

- Authenticated shell navigation, identity/logout affordance, and logout error feedback (plan 01).
- Login form, pending/error states, and mobile layout (plan 01).
- Post list header/CTA, rows, badges, loading/empty/error states, and retry affordance (plan 02).
- New/existing draft editor chrome, title/memo fields, load failures, autosave status, and editor
  layout (plan 02).
- Photo picker, conversion/upload progress, thumbnail overlays, delete/retry/dismiss actions, and
  skipped-file feedback (plan 02).
- `StageModelSelect`, including loading, unavailable/disabled model, selection, save-pending, and
  error states (plan 04), even though later plans mount it on its final screens.
- The smallest `shared/ui` primitive set evidenced by those surfaces, its public exports, tests,
  and the design-token/style-lint cleanup required to make it the enforced contract.
- Responsive mobile-first spacing, both themes, keyboard/focus behavior, live regions, labels,
  touch targets, and contrast across every touched surface.

**Non-goals / must not change**

- No backend, Connect RPC/proto, SQLite/migration, provider registry, upload pipeline, image
  processing, authentication/session, autosave queue, or query-cache behavior changes.
- No route additions or removals and no changes to login redirect, logout ordering, post minting,
  caret restoration, post ordering, direct-to-R2 uploads, deletion, retry, or model-selection
  persistence semantics.
- No theme switcher, third theme, user-configurable brand/theme settings, new product capability,
  or new design-system/component-library dependency.
- No primitives or variants for future dialogs, sheets, toasts, tooltips, switches, checkboxes,
  skeletons, or other controls unless a currently in-scope screen actually renders them.
- No redesign of planned-but-unbuilt voice, generation, revision, or export screens. Those future
  jobs inherit the design language directly and must create primitives only when their real UI
  requires them.
- No change to constitution invariants [I1]–[I7].

## Acceptance Criteria

1. The login, authenticated shell, post list, draft editor, photo workflow, and
   `StageModelSelect` all render and retain the plan 01/02/04 behavior described above; their
   existing feature tests pass without weakening assertions around routing, mutation ordering,
   autosave, upload, deletion, retry, or selection persistence.
2. No generic button, button-like link/file trigger, text input, textarea, or select is visually
   hand-rolled in `app`, `pages`, `widgets`, `features`, or `entities`; it uses or composes the
   current-need primitive in `shared/ui`, while domain-named UI remains in its owning slice.
3. The resulting `shared/ui` inventory contains no primitive, variant, or state that has no
   production call site in the in-scope UI. Each primitive has focused tests for the semantics and
   interaction states it actually exposes.
4. Every in-scope colour utility uses the new surface/content foundation or the narrow functional
   role appropriate to the element. There are no call sites using the retired `bg`, `surface`,
   `text`, `primary`, bare status, `border`, `overlay`, or `depth` vocabulary.
5. The temporary migration-alias block is absent from `frontend/src/app/styles/index.css`, and
   `pnpm lint:style` fails on a probe containing any retired colour utility while passing the
   migrated frontend.
6. Each in-scope view has at most one CTA treatment. Every other existing action uses the quietest
   current-needed functional button treatment, including hover and active feedback; outlined is
   used only when an actual secondary action needs a visible rim, and a solid danger treatment
   appears only in a confirmation context.
7. Generic controls that a user presses have a minimum 44 px touch target in their normal mobile
   presentation; icon-only actions have accessible names; every control is keyboard reachable and
   has a visible `focus-visible` indicator.
8. Labels remain visible or programmatically associated, field errors use `aria-invalid` plus an
   explanatory message, and logout/save/upload/model-selection asynchronous feedback retains the
   appropriate `role="status"` or `role="alert"` behavior.
9. The UI is reviewed with both `data-theme="night"` and `data-theme="day"`; primary, secondary,
   and tertiary content meet WCAG AA on every surface used, functional foreground/background pairs
   meet AA, and information is never communicated by colour alone.
10. Cards, borders, surface jumps, type roles, spacing, radius, shadow, and motion across all
    in-scope screens satisfy the design-language review checklist; no card is nested and every
    remaining border matches an allowed exception.
11. `pnpm build:web`, frontend lint, FSD lint, frontend tests, `pnpm lint:style`, and
    `pnpm lint:spec` pass after the migration.
12. No backend/proto/schema/config value or product policy changes as a result of this refactor,
    and invariants [I1]–[I7] remain true.
