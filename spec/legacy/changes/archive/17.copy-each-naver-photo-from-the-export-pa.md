# 17. Change: Copy Each Naver Photo From The Export Panel

> A **change proposal** (a WHAT delta) that modifies the already-shipped behavior of [plan/08.platform-export](../../plan/08.platform-export.md).
> Filled by /create-change through a user interview — a reviewable doc, not a one-line prompt.
> The STEPS live in the job that /create-change-job creates. Write it in English.

## As-is

The Naver export derives plain text from the canonical block array ([I2]) and marks each photo's position inline as
`[사진 <filename>]`, or `[사진 <filename>: <caption>]` where the block has one. The panel's single 복사 puts that
whole text on the clipboard, and its guidance line reads
붙여넣고 표시된 자리에 사진을 드래그하세요. The export deliberately uses only canonical block filenames — the
`PostImage` array reaches `toNaver` and is explicitly discarded, because the view URLs it carries expire.

So the panel hands over the text and then stops. The photos it just named are on screen nowhere in that step: the
user is told to drag files into the marked positions, and has to go find them. The last mile of the flow the whole
product exists to shorten is still manual file wrangling.

What the clipboard can and cannot do here was **measured** against Naver SmartEditor ONE (blog.naver.com 글쓰기) on
2026-08-31, not assumed. That table is settled and must not be re-derived:

| Clipboard payload | Result |
| --- | --- |
| `text/html` with an `<img>` on an external origin | image component created, then rejected as 존재하지 않는 이미지 |
| `text/html` with a `data:` image src | the `<img>` is stripped at parse time; no image slot at all |
| either of those wrapped in real `se-component` markup with the editor's own buffer marker | identical failures |
| a `copy` event adding `File` objects to `clipboardData` | files never reach the system clipboard; only the text falls through |
| `navigator.clipboard.write` with several `ClipboardItem`s | no effect — multiple items are not supported |
| `dragstart` adding `File` objects to `dataTransfer` | the editor does not recognize the drop |
| one `ClipboardItem` carrying **both** `image/png` and `text/html` | the editor prefers the HTML flavor → broken image |
| one `ClipboardItem` carrying **only** `image/png` | **works** — the photo uploads, one per paste |

Two consequences follow, and they are what this change is built on: the editor normalizes any pasted HTML into its
own component model and only trusts image sources on its own domains; and an image `ClipboardItem` must carry no
`text/html` flavor or the HTML wins. Copying several photos at once from a web page is not merely unsupported by
Naver — a page may read `clipboardData.files` but may never write files to the system clipboard, which is a browser
security boundary. Finder can, which is why bulk photo download remains the only "all at once" path and remains an
unfilled PRD gap.

## To-be

The Naver format's output panel gains a **photo strip** beneath the copied text: one entry per `IMAGE` block, in the
same order as the `[사진 …]` markers in that text, each showing the photo itself with a copy control laid over it.
The strip states each photo's marker filename, so a photo on screen and a marker in the pasted text are matched by
eye rather than by counting.

Pressing a photo's copy control puts **exactly one** `ClipboardItem` on the clipboard, carrying **only** `image/png`
and no `text/html` flavor. Pasting it into SmartEditor ONE at the marker's position uploads that photo. One photo per
copy and per paste, which is what the editor accepts.

The stored photo is a JPEG — every upload is decoded, downscaled to a 1024px long edge and JPEG-encoded in the
browser before it ever leaves the device ([I6]) — so the page converts it to PNG at copy time, from the pixels it
already displays. The conversion happens on demand, for the one photo pressed, and nothing converted here is ever
uploaded: [I6] governs the upload pipeline and is untouched.

The text copy is unchanged. It remains the full plain text with its `[사진 …]` markers and remains the universal
copy-ready fallback ([I1]); the strip is an addition beside it, never a replacement. The guidance line is rewritten
to describe the flow that now exists: paste the text, then copy each photo and paste it at its marker.

Failures are stated per photo, on the photo:

- A photo whose presigned view URL has expired or failed to load says so and offers no copy that would put nothing on
  the clipboard. Reloading the post remints the URL, which is the existing recovery.
- A browser that refuses the image clipboard write, or that lacks it, says so on that photo. It does not fall back to
  a text flavor — a `ClipboardItem` carrying HTML alongside the image is measured to produce a broken image, which is
  worse than no copy at all. The text output beside it is still the fallback the plan promises.
- A photo whose bytes cannot be read for conversion says so rather than copying a blank image.

## Scope / Non-goals (regression boundary)

**In scope**

- `widgets/export-panel` — the photo strip for the Naver format, its ordering against the markers, its per-photo copy
  control, its per-photo failure states, and the rewritten Naver guidance line.
- The browser-side JPEG→PNG conversion and the single-flavor image clipboard write, placed per
  [ARCHITECTURE](../../ARCHITECTURE.md) §3 (the clipboard/image mechanics belong in `shared/lib` beside the existing
  `copyText`; the Naver-specific composition belongs to the export surface).
- [policy/export.md](../../policy/export.md) and [plan/08](../../plan/08.platform-export.md) — the Naver export's contract
  gains per-photo clipboard copy beside the text.

**Non-goals — these must NOT change**

- The derived Naver **text**: its plain-text shape, its `[사진 <filename>]` / `[사진 <filename>: <caption>]` markers,
  its blank-line collapsing, and the fact that the export names only canonical block filenames and never a URL.
- The block array as the canonical post ([I2]). The strip is derived from the `IMAGE` blocks; nothing is written back
  into the content.
- The other three formats — Tistory, site, Markdown — their outputs, their guidance, and their copy behavior.
- The existing text copy path, its clipboard fallback to manual selection, its live-region announcements, and the
  separate 네이버 제목 copy ([I1]'s copy-ready fallback).
- The upload pipeline ([I6]): HEIC decode, 1024px downscale, JPEG encode, and the rule that originals never reach the
  API. The PNG made here exists only for the clipboard.
- Publishing ([I1]): nothing here starts, implies, schedules or retries a publish, and no platform credential or
  browser profile comes near the frontend. The paired Mac agent's flow (plan 12) is untouched.
- Presigned-URL handling: view URLs stay short-lived, minted per `GetPost`, and never persisted
  ([policy/uploads.md](../../policy/uploads.md)).
- **Bulk photo download is not built here.** The user chose per-photo copy only; multi-photo paste via Finder remains
  the unfilled PRD gap plan 08 already records.
- The clipboard measurements above are settled. The job must not re-run the experiment or try a rejected payload
  shape — in particular, no `text/html` flavor alongside the image, and no multi-item write.

## Acceptance Criteria

1. With the Naver format selected on 글 완성, the panel renders one entry per `IMAGE` block, in the same order as the
   `[사진 …]` markers in the copied text, each showing the photo and naming its marker filename.
2. A post with no photos renders no strip and the text output is unchanged.
3. Pressing a photo's copy control results in a single `ClipboardItem` whose only flavor is `image/png`; no
   `text/html` flavor is written alongside it, and no second item is written.
4. The copied PNG's pixels are the photo's, at the stored photo's dimensions.
5. The 복사 for the text still copies the full plain text with its `[사진 …]` markers, and the 네이버 제목 copy still
   copies the title; both keep their existing confirmation and manual-selection fallback.
6. Selecting Tistory, 자체 사이트 or 마크다운 renders no photo strip, and each format's output text is byte-identical
   to today's.
7. A photo whose view URL fails to load states so in its entry and offers no copy control that would write an empty
   or partial image.
8. In a browser without image clipboard support, or when the write is refused, the photo's entry says so and no text
   flavor is substituted.
9. The Naver guidance line describes copying the text and then pasting each photo at its marker.
10. No regression in plan 08: all four formats remain synchronous browser-only derivations of the canonical block
    array, and nothing is uploaded, published, or persisted by this panel.
