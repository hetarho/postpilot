# 20. Change: Purpose-scoped model enablement with admin purpose tabs

> A **change proposal** (a WHAT delta) that modifies the already-shipped behavior of [plan/18.openrouter-model-catalog-and-admin-model](../../plan/18.openrouter-model-catalog-and-admin-model.md).
> Filled by /create-change through a user interview — a reviewable doc, not a one-line prompt.
> The STEPS live in the job that /create-change-job creates. Write it in English.

## As-is

- Enabling a model is **purpose-agnostic**: `catalog_models.enabled` is one global flag, and an enabled model is
  served to every user-facing surface at once. `ListModels` returns one stage-agnostic list with capability flags;
  the FE `StageModelSelect` narrows the observe dropdown to vision models, and the BE refuses a non-vision model
  for observe (`StageSuitable`, `backend/internal/provider/types.go`) at `SaveSelection`/`Complete` time.
- The 모델 관리 tab of `/admin` renders **one** catalog list with **one** enable checkbox per row. There is no
  purpose dimension anywhere: the operator decision is "usable at all", never "usable for what".
- The app knows exactly three usage purposes, expressed as the `Stage` enum: `observe` (photo interpretation),
  `write` (post writing), `analyze` (voice/style analysis). Image generation and video generation do not exist as
  concepts in the schema, the proto, or any UI.
- The OpenRouter field mapping reads `architecture.input_modalities` (→ `vision`) and ignores
  `output_modalities` entirely ([tech/openrouter-catalog](../../tech/openrouter-catalog.md) — "output modalities are
  ignored; we only consume text").
- `ApplyRecommendationSet` validates its nine refs at apply time against the **global** enabled set plus the stage
  suitability check (observe needs vision).

## To-be

- The app gains a first-class **purpose** dimension with five values (English slugs; ko labels in parentheses):
  `photo-analysis` (사진 해석) · `style-analysis` (문체 분석) · `writing` (글 작성) · `image-generation`
  (이미지 생성) · `video-generation` (비디오 생성). The first three map 1:1 onto the existing stages
  `observe` / `analyze` / `write`; the last two are **settings-only** — registered in admin, consumed by nothing yet
  (future plans add the features).
- **Curation is per purpose.** A catalog model is *registered to* zero or more purposes; the single global
  `enabled` flag stops being the user-visibility gate. One model may be registered to several purposes at once.
  Per-model metadata — label, capability flags, pricing snapshot, `reasoning_effort` override, `listed`
  bookkeeping — stays one row shared across purposes.
- The 모델 관리 tab of `/admin` splits into **five purpose tabs** (one per purpose, in the order above). Each tab
  keeps the shipped catalog UX — featured-provider ordering, search, provider/capability filters, virtualized
  window list, 새로고침 status line — but its checkbox now registers the model **for that tab's purpose only**.
- **Capability-forced candidate filtering per tab** (the tab does not even list what cannot serve the purpose):
  - `photo-analysis`: only models with `"image" ∈ input_modalities` (vision). This restates the existing [I3]
    observe gate — the stage already required vision; now the tab shows nothing else.
  - `image-generation`: only models with `"image" ∈ output_modalities`.
  - `video-generation`: only models with `"video" ∈ output_modalities`. OpenRouter currently lists few or none:
    the tab renders an explanatory empty state rather than an error.
  - `style-analysis` and `writing`: unrestricted (any text model).
  The catalog field mapping therefore grows two flags derived from `architecture.output_modalities`:
  `image_output` and `video_output`.
- **User-facing pickers serve only the matching purpose's registrations.** The observe / write / analyze model
  inputs (`StageModelSelect`, everywhere it is mounted — generation options, A/B slots, model lab, voice
  analysis) list exactly the models registered to `photo-analysis` / `writing` / `style-analysis` respectively,
  and `SaveSelection` / `Registry.Complete` refuse a model not registered to the stage's purpose server-side.
  The contract must carry purpose membership to the client (shape is the job's call — a purposes list per model
  or a per-stage query — but the FE must not re-derive it from capability flags).
- **Migration starts every purpose empty** (interview decision). Existing `catalog_models` rows keep their
  metadata and reasoning overrides, but no purpose registration is seeded. Immediately after cutover every stage
  dropdown is empty and every previously saved selection is unavailable — handled by the **existing**
  unavailable-selection machinery (greyed with reason, cleared per current policy), with no bespoke clearing
  logic and no auto-selection ([I3]). The operator re-curates each purpose from the admin tabs.
- `ApplyRecommendationSet` validates each ref against **its purpose's registration** (observe ref must be
  registered to `photo-analysis`, and so on), still collecting all offenders into one `SetRefusal` grouped by
  cause.

## Scope / Non-goals (regression boundary)

**In scope**

- Purpose model (five values), per-purpose registration storage + migration, and the purpose-aware curation RPCs
  in `ModelCatalogService`.
- `/admin` 모델 관리: five purpose tabs with per-tab capability-forced candidate filtering and empty states.
- `output_modalities` → `image_output`/`video_output` mapping in the OpenRouter client and catalog rows.
- Purpose-filtered user-facing catalog: `ListModels`/`SaveSelection`/`Registry.Complete` and every mounted stage
  picker; apply-time recommendation-set validation against purpose registrations.
- ko/en i18n for all new copy (plan 13); config values in their owners (purpose order/labels keys in FE
  `shared/config` + i18n resources; any BE constants in `platform/config`).

**Non-goals (must NOT change)**

- **No image/video generation feature**: no jobs, no generation paths, no user-facing UI consume the
  `image-generation`/`video-generation` registrations — they persist and round-trip in admin only.
- The `internal/llm` boundary, the single OpenRouter provider entry, `providers.yaml`'s shape, and the
  server-side catalog client/TTL cache are untouched; boot still never contacts OpenRouter, and an empty
  registration set still boots fine.
- Selection-memory semantics, A/B slots, the model lab flow, credits/ledger (plan 17), pricing display rules
  (plan 09), and the 제공 종료 (`listed = false`) machinery all keep their current behavior; delisting stays
  per model, affecting all its purposes at once.
- Enabling (now: registering) never selects ([I3]); nothing is auto-registered or auto-deregistered.
- The shipped catalog UX mechanics stay: virtualized window list (design-language §4.4), featured-provider
  ordering, client-side search/filters, no native selects.
- Master-only access to `ModelCatalogService` and the `/admin` route guard are unchanged.

## Acceptance Criteria

1. The 모델 관리 tab of `/admin` presents five purpose tabs — 사진 해석 · 문체 분석 · 글 작성 · 이미지 생성 ·
   비디오 생성 — and registering a model in one tab does not register it in any other; one model can be
   registered to several purposes simultaneously.
2. Per-tab candidate filtering is capability-forced: 사진 해석 lists only vision-input models, 이미지 생성 only
   image-output models, 비디오 생성 only video-output models (an empty result renders an explanatory empty
   state, not an error), and 문체 분석 · 글 작성 list the full catalog. A model failing a tab's capability gate
   cannot be registered to that purpose, client- and server-side.
3. Each user-facing stage picker (observe / write / analyze, wherever mounted: generation options, A/B candidate
   slots, model lab, voice analysis) lists exactly the models registered to its purpose (`photo-analysis` /
   `writing` / `style-analysis`); `SaveSelection` and `Registry.Complete` refuse any other model server-side.
4. `image-generation` and `video-generation` registrations persist, survive reload, and are editable in admin,
   while no generation path, job type, or user-facing surface reads them.
5. The migration seeds no purpose registrations: after cutover all five tabs are empty, stage dropdowns are
   empty, and previously saved selections flow into the existing unavailable-selection machinery (greyed with a
   reason, cleared per current policy) with no crash and no auto-selection.
6. `ApplyRecommendationSet` validates every ref against its purpose's registration at apply time and refuses
   with all offending refs named, grouped by cause, in one answer.
7. Per-model reasoning override, pricing/metadata snapshots, refresh bookkeeping, and 제공 종료 badging behave
   exactly as before, shared across the model's purposes.
8. All new copy ships in ko and en resources; no native `<select>` appears; the catalog list stays virtualized
   with the page as the only scroller.
