# 08. Change: Stop Dropping Blocks Over a Schema-Mandated Level Field

> A **change proposal** (a WHAT delta) that modifies the already-shipped behavior of [plan/06.two-stage-generation-and-contact-sheet](../../plan/06.two-stage-generation-and-contact-sheet.md).
> Filled by /create-change through a user interview — a reviewable doc, not a one-line prompt.
> The STEPS live in the job that /create-change-job creates. Write it in English.

## As-is

Plan 06's validation table is deliberately strict: *any populated field outside the type's set drops the block and
logs the offending field*. `invalidField` implements this, and `level` is outside the set for every type except
`HEADING` — a `TEXT` or `IMAGE` block arriving with `level: 2` is discarded whole.

The structured-output schema that the app itself sends contradicts that rule. `post_content.schema.json` declares
one uniform block object with `additionalProperties: false` and

```json
"required": ["type", "content", "level", "file", "alt", "caption", "items"]
```

so **every** block must carry `level`, whatever its type. A model that obeys the schema and writes `level: 1` or
`level: 2` on a body paragraph has its paragraph deleted by the validator — for complying with the instruction the
app gave it.

This is not theoretical. Production API logs for the successful write candidate at `2026-08-30T05:17:03Z` contain
16 consecutive `dropping invalid generated block` lines, every one of them `field=level`, on `type=TEXT` and
`type=IMAGE`. The user dismissed that comparison. The same field is the only reason given in every drop line the
deployment has logged.

The rule is right for a field that signals genuine confusion — a `TEXT` block carrying `items`, or an `IMAGE`
block carrying `content`, means the model mixed up two block types, and dropping it is correct. `level` is not
that: it carries no meaning at all outside `HEADING`, and the app's own schema forces it to be present.

## To-be

`level` stops being a drop reason for the types that have no use for it. A `TEXT`, `IMAGE`, `QUOTE`, or `LIST`
block whose only defect is a non-zero `level` is **kept**, with `level` normalized to `0` — the same shape it would
have had if the model had written `0`. `HEADING` keeps its existing rule unchanged, including the clamp of an
out-of-range level to `2`.

Every other field combination keeps today's behavior exactly: `TEXT` with `items`, `IMAGE` with `content`, a
missing `file` on `IMAGE`, an unknown type — all still drop, still log.

Because a normalized `level` is no longer an anomaly, it stops producing a warning line. The log keeps naming real
drops, so the signal that made this bug findable is not lost to noise.

## Scope / Non-goals (regression boundary)

**In scope**

- `backend/internal/generation/blocks.go`: `level` is normalized rather than fatal for non-`HEADING` types, and no
  longer logged when it is the only defect.
- Plan 06's validation table, updated to state the `level` rule per type.
- Unit coverage for the exact production case: a schema-shaped payload where every block carries a non-zero
  `level`.

**Non-goals**

- No change to `post_content.schema.json`. The uniform required-field list is what makes structured output work
  across providers; the validator is the right place to absorb a meaningless value.
- No change to the `Block` proto contract, to `BlockType`, or to how content is persisted or rendered ([I2]).
- No relaxation of any other field-combination rule — cross-type confusion still drops the block, and validation
  still never repairs across blocks.
- No change to the attachment filter, observation matching, contact sheet, prompt assembly, or the two-stage
  pipeline ([I3]).
- No frontend change: `level` on a non-heading block is already ignored by the renderer.

## Acceptance Criteria

1. A `PostContent` payload whose `TEXT`, `IMAGE`, `QUOTE`, and `LIST` blocks all carry a non-zero `level` survives
   validation with every block kept, each with `level == 0`.
2. `HEADING` behavior is unchanged: `level` 2 and 3 pass through, any other value clamps to 2, empty `content`
   still drops.
3. Every other drop rule still drops and still logs with the offending field named — `TEXT` with `items`, `IMAGE`
   with `content`, `IMAGE` without `file`, `LIST` with an empty item, unknown type (plan 06 acceptance criterion 5
   continues to hold).
4. A block kept only because its `level` was normalized produces no warning line; a genuinely dropped block still
   produces exactly one.
5. Replaying the production payload shape that logged 16 `field=level` drops keeps all 16 blocks.
6. No regression: generation, revision, A/B write candidates, persisted content, and platform export are unchanged
   for payloads that were already valid.
