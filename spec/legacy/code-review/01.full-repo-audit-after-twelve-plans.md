## Architecture Baseline

The rules this report judges against, as the SSOT states them:

- **[I1] Publishing is explicit and local-capability-bound.** The VPS owns a durable job; credentials and the browser
  stay on the paired Mac; an ambiguous external commit is never auto-retried.
- **[I5] Long work is a server-side job record**, consumed by an in-process worker, polled by the client, swept to
  `failed` on restart.
- **[I6] Image work happens in the browser** — that is a *placement* rule, not an optimization.
- **[I7] Migrations are embedded and run at boot**; a failure kills the process so the `/health` gate rolls back.
- **ARCHITECTURE §2.4** — one serialized writer connection (`SetMaxOpenConns(1)`), WAL, reads on the pool, and never
  hold the write transaction across a provider call.
- **ARCHITECTURE §2.1/§2.2** — `internal/llm` is a hard boundary; dependencies point inward only; two
  anti-corruption mappers (`proto↔domain`, `row↔domain`).
- **ARCHITECTURE §3** — FSD layering `app → pages → widgets → features → entities → shared`, one `index.ts` per
  slice, `shared/api/gen/**` reached only through `shared/api`.
- **ARCHITECTURE §4** — *"No setting is a literal buried in a component or a handler."* FE settings flow through
  `frontend/src/shared/config`; BE settings through `backend/internal/platform/config`.

**The codebase honours these to an unusually high degree.** FSD passes `steiger` with zero problems; the composition
root is the only place that imports an LLM adapter; every store splits `write`/`read` pools correctly; the publishing
guard reserves the writer with a deliberate no-op UPDATE before re-reading other aggregates. The findings below are
about the *edges* of that discipline, not its centre.

### R002 Every agent poll writes to the single SQLite writer, six times more often than the value it maintains is read

- Priority: **P2**
- Area: backend / SQLite single-writer discipline (ARCHITECTURE §2.4)
- Evidence:
  - `agent/internal/config/config.go:16` — `PollInterval = 5 * time.Second`.
  - `agent/internal/publishing/supervisor.go:31-53` — `Run` calls `s.Client.Claim(ctx)` every interval, and on
    `CodeNotFound` (nothing to do) resets the backoff to the same interval and loops.
  - `backend/internal/publishing/rpc/agent_interceptor.go:48-67` — every agent procedure except `Enroll` goes through
    `i.auth.AuthenticateAgent(ctx, token)`; `ClaimPublishJob` is in `isAgentProcedure`'s list (`:70-81`).
  - `backend/internal/publishing/service.go:104` — `AuthenticateAgent` unconditionally calls
    `s.store.TouchAgent(ctx, agent.UserID, agent.ID, now)`.
  - `backend/internal/publishing/store/store.go:81` — `TouchAgent` runs on `s.write`, i.e. the writer pool, and
    `backend/internal/publishing/store/sqlc/publishing.sql.go:1009-1012` shows it is a real
    `UPDATE publishing_agents SET last_seen_at=?,updated_at=?`.
  - The value it maintains is consumed only as a staleness hint: `frontend/src/shared/config/index.ts` —
    `export const PUBLISH_AGENT_STALE_MS = 30_000`.
- Why it matters: `backend/internal/platform/db/db.go:45` caps the writer at exactly one connection *by design*, and
  `WorkerConcurrency = 1` (`backend/internal/platform/config/config.go:54`) shares it with generation jobs while every
  editor keystroke's autosave queues behind it too. One paired Mac therefore issues **17,280 writes a day whose only
  purpose is a 30-second freshness indicator** — a 6× overshoot — and each one takes the writer for the duration.
  There is a second consequence at `agent_interceptor.go:60-66`: because the touch is inside authentication, a write
  failure (a full disk, a locked file) is reported as `CodeUnavailable` for *authentication*, so a storage problem
  presents as the Mac being unable to log in.
- Recommendation: make the touch cheap and rate-limited rather than removing it — skip the UPDATE when the stored
  `last_seen_at` is younger than a threshold derived from the display window (an in-memory per-agent last-touch map,
  or a `WHERE last_seen_at < ?` predicate so SQLite decides). Separately, move the touch off the authentication path
  so a failed write degrades the freshness display instead of the agent's ability to authenticate. Consider whether
  `PollInterval` belongs in the agent's config seam as an env-tunable value rather than a package constant that is
  also re-defaulted at `supervisor.go:34`.
- Suggested job split: one backend job (throttle + decouple from auth), optionally carrying the agent-side
  `PollInterval` config move.

### R003 The probes that prove the custom guards still bite are not in CI

- Priority: **P2**
- Area: CI parity / enforcement vs documentation
- Evidence:
  - `package.json:14-17` defines four scripts: `lint:style`, `lint:style:probe`, `lint:spec`, `lint:spec:probe`.
  - `.github/workflows/ci.yml:27-28` runs `pnpm lint:style` and `pnpm lint:spec` — **neither probe**.
  - The probes are not decoration: `scripts/check-spec-hygiene.mjs:185-210` states the reason outright — *"a guard is
    only worth having once someone has watched it bite"* — and asserts both that the check catches two corruption
    shapes and that it does **not** reject the real template. `scripts/lint-style-escapes.mjs` carries an equivalent
    16-case scanner self-test.
- Why it matters: both guards are regex scanners over source text. A regex that stops matching — a renamed token
  prefix, an escaped bracket, a refactor of `scaffoldKeys`' brace walker — makes the guard pass *everything*, and the
  green check reads identically to a real pass. The probe is the only thing that can tell those apart, and it runs
  only when a human remembers to type it. This is the textbook "documented-but-unenforced" shape, one level up: the
  enforcement exists and is itself unenforced.
- Recommendation: add `pnpm lint:style:probe` and `pnpm lint:spec:probe` to the `frontend` job in `ci.yml`,
  immediately before their non-probe counterparts. Both are sub-second and need no extra setup.
- Suggested job split: fold into the R001 job (both touch the same gate), or ship as a one-line CI change.

### R004 `SentenceFeedback` keeps the sentence it was mounted with, so feedback on an edited block is rejected by the server

- Priority: **P2**
- Area: frontend / lifecycle (stale derived state)
- Evidence:
  - `frontend/src/features/give-voice-feedback/ui/SentenceFeedback.tsx:15-20` — `sentences` is recomputed from the
    `text` prop on every render, but the selection is `useState(sentences[0] ?? '')`, which is an **initializer**: it
    is read once, on mount, and never again.
  - `frontend/src/features/edit-post-content/ui/BlockEditor.tsx:130-131` — the component is rendered as
    `renderSentenceAction?.(block.content, autosave.flush)`, i.e. its `text` prop *is* the live, editable block
    content. No `key` forces a remount when that content changes.
  - `frontend/src/features/give-voice-feedback/ui/SentenceFeedback.tsx:27` — submit sends
    `{ sentenceRef: sentence, authoredText: sentence }`, the stale state, not anything derived from the current
    `sentences`.
  - The server refuses it: `backend/internal/voice/feedback.go:60-62` —
    `if !strings.Contains(finalBody, strings.TrimSpace(authoredText))` → `"sentence feedback must reference the owned
    finalized text"`.
  - `frontend/src/shared/ui/select/Select.tsx` is a native `<select>`, so a controlled `value` absent from the option
    list leaves the control showing something other than what will be submitted.
- Why it matters: concrete failure — a user edits a text block, opens 문장 의견, sees a sentence list built from the
  *new* text, submits without touching the dropdown, and the request carries a sentence from the *old* text. The
  server rejects it with a message about ownership that describes nothing the user did. The saving grace is that
  `feedback.go:60` prevents the bad evidence from entering voice learning ([I4] holds), so this is a UX and
  correctness-of-intent defect rather than data corruption — but the guard is the *server's*, and the client is
  sending something it should never have been able to construct.
- Recommendation: derive the selection instead of storing it — keep the state but reconcile it against `sentences`
  during render (`const selected = sentences.includes(sentence) ? sentence : (sentences[0] ?? '')`) and submit
  `selected`, or reset the state when `text` changes. Do not reach for a `key` on the call site: that would also
  discard the reason and the open dialog on every keystroke.
- Suggested job split: group with R006 and R011 as one frontend-hygiene job.

### R010 Query keys carry the transport object, which hashes to `{}` and distinguishes nothing

- Priority: **P3**
- Area: frontend / seam without effect
- Evidence:

  arrays.
- Recommendation: drop the segment, or replace it with a stable string the app controls. Verify the invalidation call
  sites still match afterwards — they use the same key builders, so this should be mechanical.

### R013 The long-press timer in `SentenceFeedback` outlives the component

- Priority: **P3**
- Area: frontend / lifecycle
- Evidence: `frontend/src/features/give-voice-feedback/ui/SentenceFeedback.tsx:22` declares
  `const timer = useRef<number | undefined>(undefined)`; `:37` sets it on `onPointerDown`; `:39-40` clear it on
  `onPointerUp`/`onPointerCancel`. There is no `useEffect` cleanup, so a component unmounted between pointer-down and
  pointer-up (a block removed or reordered mid-press) leaves the timeout scheduled.
- Why it matters: React 18+ silently ignores the resulting `setOpen` on an unmounted component, so there is no
  visible symptom — which is exactly why it will not be found later. It is one `useEffect(() => () =>
  window.clearTimeout(timer.current), [])` away from correct, and the same file is already being touched by R004 and
  R006.
- Recommendation: add the cleanup effect while fixing R004.
- Suggested job split: with R004/R006.

## Cross-Cutting Themes

1. **The guards are good; the guards' own coverage is the gap.** R001, R003 and R007's second half are one root cause
   seen three times: a custom check exists, is well-reasoned, is documented as authoritative — and either audits a
   narrower path than its name implies (`lint:spec` reads `.claude/skills`, not `spec/`), or has a self-test that no
   automated run executes, or reasons from a sibling gate (`format:check`) that was never created. All three produce
   the most expensive kind of green: one indistinguishable from a real pass. Note the asymmetry with the *language*
   gates, which are exemplary — `steiger`, `go vet`, generated-freshness diffs and the 394-test frontend suite all
   run in CI on every push. It is specifically the **repo-authored** guards whose own coverage was never audited,
   which is exactly what a first review is for.

2. **Structural moves do not carry their references.** R001's 158 broken links and R007's citations of
   code-review 03/11 are both artifacts of things moving (jobs into `archive/`) or arriving (a scaffold from
   elsewhere) without a step that reconciles what pointed at them. The workflow has a rule for *where* a document
   lives and none for *what pointed at it*.

3. **The config seam is 95% complete, and the exceptions cluster where a value looked "obviously" local.** R006's
   `600` long-press and `60_000` staleTime, R005's dead `Analyze` field, and the duplicated `5 * time.Second` in the
   agent (`config.go:16` and `supervisor.go:34`) are all values that felt too small or too default to route through
   the seam. The result is not chaos — it is a small number of settings that cannot be found from the place a reader
   would look.

4. **A per-request write was chosen where a per-window write was meant (R002).** The `last_seen_at` touch is the one
   place the otherwise-careful SQLite writer discipline was not applied, and it is easy to see why: it is invisible
   at the call site, sitting inside an interceptor. It is worth checking future interceptors for the same shape.

## Questions / Tradeoffs

- **`ReasoningUnspecified` vs `ReasoningUnset` for analyze (R005).** Deleting the field is the clean fix, but if the
  intent was to reserve a slot for a future analyze policy, the honest version is to wire it through to
  `internal/voice`'s call sites now and let `ReasoningUnspecified` mean "no stage decision". Which one is right is a
  product call about whether analyze will ever get a reasoning policy.
- **How much of `PollInterval` should be config (R002).** The agent's 5 s poll is a device-side behaviour, not a
  server setting. Throttling the *write* fixes the cost without touching the poll; making the poll configurable is a
  separate, optional question.
- **Whether the transport query-key segment (R010) is worth removing at all.** It is inert, not wrong. Removing it
  touches three entity slices and their invalidation sites; leaving it costs a paragraph of explanation to every
  future reader. Recorded so the decision is deliberate either way.
- **Comment style: acceptance-criteria back-references.** Backend tests carry ~30 comments of the form
  `// TestSaveDraftCreatesThenUpdates is job 03 A9: …`. This is *not* filed as a finding — it is consistent,
  deliberate, and genuinely useful traceability — but it does couple test names to documents that R001 shows are
  already hard to follow, and the jobs referenced now live in `archive/`. Worth an explicit decision to keep.
