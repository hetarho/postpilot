# 02. Post Drafting and List

> Create a post, autosave title + memo, upload phone photos through the browser-side pipeline straight to R2, and find
> the post again in the list | Scope: FS | Status: done — backend (job 03) · list, editor and autosave (job 04) ·
> browser photo pipeline (job 05)

## Template

The whole product promise is "photos + a rough memo in, a draft out" (PRD §1). This plan is the **input side** of
that promise plus the way back to unfinished work:

- The memo must survive a phone that kills the tab (PRD F-2: 폰에서 앱을 닫아도 안 날아간다) — autosave, not a save
  button.
- Eight iPhone HEIC photos must go up cheaply on cellular. The browser converts them to ≤1024px JPEG before upload
  and PUTs directly to R2, so a 25 MB original becomes ~200 KB and the API never relays bytes ([I6], PRD §6.2). This
  is where S1's "체감" is decided.
- A post is something you come back to (PRD F-8): the list shows your posts, and opening one restores memo, photos,
  and draft.

## Scope / Non-goals

**In scope**

- `posts` and `images` tables; a `uploads` table for in-flight presigned uploads (an addition to PRD §5, see Design).
- `SavePostDraft` (create-or-update with 1 s debounce), `GetPost`, `ListPosts`.
- `CreateUpload` → presigned PUT, direct browser PUT to R2, `ConfirmUpload`, `DeleteImage` (row + R2 object).
- `DeletePost` — the owner's hard delete of one post, from that post's editor. Refused while a generation job is
  active (`POST_BUSY`) or a publication is non-terminal (`POST_PUBLISHING`), and nothing is destroyed on a refusal.
  Rules in [policy/posts](../policy/posts.md#deletion).
- Browser image pipeline: accepted extensions, 25 MB pre-conversion cap, HEIC/HEIF decode via libheif WASM, long-edge
  1024 px downscale, JPEG q0.85, per-file skip list with reasons, per-photo retry.
- R2 wrapper (`internal/storage`) behind a consumer-owned port: presign PUT/GET, HEAD, DELETE, LIST.
- Orphan cleanup of unconfirmed uploads.
- Presigned GET URLs for viewing photos (consumed by the contact sheet in plan 06).
- Slug minting and the "same title same day" collision rule (PRD §7).
- FE: post list page, editor page skeleton (title, memo, photo strip), routes `/posts`, `/posts/new` and
  `/posts/:slug`, with `/` redirecting to the list.

**Non-goals**

- Generation, block content, observations — plan [06](06.two-stage-generation-and-contact-sheet.md). The editor's
  in-flight "generating" indicator also arrives with 06.
- Deleting a whole post. The PRD defines photo deletion (F-2) but no post deletion; flagged as a PRD gap.
- Face blurring / image correction / image generation (PRD §8). If face blurring is ever added, its place is inside
  the browser conversion step — the pipeline is shaped to leave that seam.
- Keeping originals or larger resolutions (PRD §6.2: 원본은 서버에 남지 않는다).
- Offline queueing of autosaves beyond the debounce + retry; version history (PRD §8).
- Server-side image decoding of any kind (would break the CGO-free image — [I6]).

## Design

### Contract — `proto/postpilot/v1/post.proto` (this plan's part)

```
service PostService {
  rpc SavePostDraft (SavePostDraftRequest) returns (SavePostDraftResponse); // slug empty → create + mint slug
  rpc GetPost       (GetPostRequest)       returns (GetPostResponse);
  rpc ListPosts     (ListPostsRequest)     returns (ListPostsResponse);
  rpc CreateUpload  (CreateUploadRequest)  returns (CreateUploadResponse);  // presigned PUT
  rpc ConfirmUpload (ConfirmUploadRequest) returns (ConfirmUploadResponse); // verifies object, creates Image
  rpc DeleteImage   (DeleteImageRequest)   returns (DeleteImageResponse);   // row + R2 object
  rpc DeletePost    (DeletePostRequest)    returns (DeletePostResponse);    // hard delete: row + photos + R2 objects
}
message SavePostDraftRequest  { string slug = 1; string title = 2; string memo = 3; }
message Post { string slug = 1; string title = 2; string memo = 3; string status = 4;   // draft | review
               repeated Image images = 5; string created_at = 6; string updated_at = 7;
               /* content / observations / active_job are added by plans 05–06 */ }
message Image { string id = 1; string filename = 2; int32 width = 3; int32 height = 4; int64 bytes = 5;
                string view_url = 6; /* presigned GET, short-lived, minted per GetPost */ }
message PostSummary { string slug = 1; string title = 2; string status = 3; string updated_at = 4; }
message CreateUploadRequest   { string post_slug = 1; string filename = 2; }
message CreateUploadResponse  { string upload_id = 1; string put_url = 2; string content_type = 3;
                                string expires_at = 4; }
message ConfirmUploadRequest  { string upload_id = 1; int32 width = 2; int32 height = 3; }
```

Width/height come from the client because the server never decodes images ([I6]); `bytes` comes from the R2 HEAD
at confirm time. `content_type` is returned because it is **part of the presigned signature** — a PUT with any other
value is rejected as a signature mismatch, so the client must send back exactly what it was given. `Post` and `Image` are the proto messages plans 05–08 extend; the block `content` field is defined
in plan 06.

### Data model (PRD §5 + one addition)

```sql
posts    (slug TEXT PRIMARY KEY, user_id TEXT NOT NULL REFERENCES users(id),
          title TEXT NOT NULL DEFAULT '', memo TEXT NOT NULL DEFAULT '',
          observations TEXT, content TEXT,                 -- filled by plan 06
          status TEXT NOT NULL DEFAULT 'draft',            -- draft | review | finalized (job 17)
          created_at TEXT NOT NULL, updated_at TEXT NOT NULL)
images   (id TEXT PRIMARY KEY, post_slug TEXT NOT NULL REFERENCES posts(slug) ON DELETE CASCADE,
          filename TEXT NOT NULL, r2_key TEXT NOT NULL,
          width INTEGER NOT NULL, height INTEGER NOT NULL, bytes INTEGER NOT NULL,
          created_at TEXT NOT NULL, UNIQUE(post_slug, filename))
uploads  (id TEXT PRIMARY KEY,                             -- becomes images.id on confirm
          post_slug TEXT NOT NULL REFERENCES posts(slug) ON DELETE CASCADE,
          filename TEXT NOT NULL, r2_key TEXT NOT NULL,
          expires_at TEXT NOT NULL, created_at TEXT NOT NULL,
          UNIQUE(post_slug, filename))                     -- mirrors images; closes the concurrent-CreateUpload race
```

- `uploads` is **not in PRD §5**. It exists because the PRD's `ConfirmUpload(upload_id)` needs the server to remember
  what an `upload_id` referred to (post, filename, key) across a 10-minute window and a possible restart. Rows are
  deleted on confirm or by the orphan sweep.
- `filename` is the name the model and the exporters refer to (PRD §5). It is unique per post, in **both** tables:
  `CreateUpload` rejects a name a *confirmed* photo holds, and the FE de-duplicates before asking
  (`IMG_1.jpg` → `IMG_1 (2).jpg`). A name held by a *pending* upload is the retry case, so that upload is replaced
  rather than refused. The database constraints, not the service's precheck, are what close the race between two
  concurrent calls.
- R2 key: `posts/{slug}/{image_id}.jpg` (PRD §5). Image bytes never enter SQLite.
- `status`: `draft` while the post is input-only; plan 06 moves it to `review` when a generation completes.

### Slug

Minted once, on the first `SavePostDraft` with an empty slug, and never changed afterwards (it is the PK and appears
in R2 keys):

```
<YYYYMMDD>-<title sanitized: trimmed, whitespace→'-', path/URL-unsafe chars removed; Korean kept>
empty title → <YYYYMMDD>-untitled
collision   → append -2, -3, … (PRD §7: 같은 날 같은 제목 → 일련번호)
```

Retitling a post later does not change its slug.

### Autosave

Debounced 1 s after the last keystroke on title or memo, then `SavePostDraft`. The first save creates the post;
later ones are idempotent updates. Photos attach to an existing post, so the editor creates the post on the first
photo selection if no save has happened yet: the save queue exposes `mint()` — send what is queued now (the empty
draft, if nothing was typed) and resolve with the slug once the create lands, retrying like any other save. A pick
made only of skipped files does not create a post.

A save's answer carries the whole post, photos included. The editor takes the **text** from it and keeps the
**photo list** the cache already holds: a save that left before a confirm or a delete would otherwise land after
it and undo the patch, and the fresh presigned URLs in every answer would change each thumbnail's `src` once a
second while someone types.

The save state is **not** owned by the editor component. One queue per post lives in `features/save-draft`, outside
React, and holds the debounce, the retry backoff, the in-flight gate and the reported state. Its guarantee is that
for a given post there is at most one save in flight and what it sends is always the newest text queued — which is
what makes the three awkward cases behave: a save still failing when the user navigates away keeps retrying, the
route swap the mint causes does not split one draft across two chains of saves, and an undo made while a request is
out is sent rather than mistaken for "already saved". The reasoning and the full rule list are in
[spec/tech/draft-autosave.md](../tech/draft-autosave.md).

Every way out of the editor flushes: the debounce, `visibilitychange`(hidden), `pagehide`, and unmount. All are
best-effort — a browser may cut short a request begun as it discards the document — so the bound on what can be lost
is the debounce window, which is why it is one second.

A queue is dropped when its **session** ends (logout, or a session that died mid-use). A retry firing after someone
else signs in on the same device would send the previous account's text under the new account's cookie.

### Screens and routes (FE)

| Route | Screen | Notes |
|---|---|---|
| `/` | — | redirects to `/posts`; the post list is the app's home |
| `/posts` | `pages/posts` | title (or "제목 없음"), status badge, relative `updated_at`, "새 글" |
| `/posts/new` | `pages/editor` | a draft with no slug yet |
| `/posts/$slug` | `pages/editor` | 403 / 404 / unavailable views for a slug that is not the caller's; carries the delete control |

All four sit under the authenticated layout route, so the session guard covers them structurally. Login's default
destination is `/posts`.

The first save of a new draft mints the slug and the editor navigates to `/posts/<slug>` with `replace` — the back
button then goes to the list, not to a second empty draft. Because those are two different routes, that navigation
unmounts one editor and mounts another: the text rides the save queue across it, and the caret rides a one-shot
handoff (`pages/editor/model/editor-handoff.ts`) so the next keystroke still lands where the user was typing.

`/posts/$slug` carries its **delete control in the editor's top row**, at the right end beside the status line: a
danger-toned `글 삭제하기` button (`Button variant="danger"`). It says so in words rather than wearing an icon — a bare
`X` there read as "close the editor" rather than "destroy this post" (owner decision, 2026-09-02), and this is the one
control in the product whose misread cannot be undone. The visible label is also its accessible name, so no
`aria-label` restates it (WCAG 2.5.3). Pressing it opens the shared `Dialog`, which names the post and states that the
post, its photos, and its generation and revision history are removed permanently. A refusal closes the dialog and
takes its own full line under the row, which is why that row wraps. `/posts/new` renders no control at all — a draft
with no slug has nothing to delete — and the post list is untouched: its rows stay whole-row links, with no row menu,
swipe, or per-row button. A successful delete ends that slug's autosave queues, then navigates to `/posts`.

The shipped screens compose the demand-driven primitives in `shared/ui`: the list's sole CTA shares the `Button`
contract through `buttonStyles`, status uses `Badge`, and retry actions use `Button`; the editor uses the bare
`TextField` / `Textarea` appearances so the page remains the writing surface. Photo actions retain their domain
composition under `features/upload-photos` while reusing the shared button contract, including a keyboard-visible
label trigger for the native file input and named 44 px icon actions. Page structure and typography use the
five-level surface/content foundations, while controls and feedback use their functional colour groups.

### Upload path (PRD F-2, §6.2)

```
browser
 1. filter:   ext ∈ {jpg, jpeg, png, webp, heic, heif}, size ≤ 25 MB (at selection, pre-conversion)
              anything else → skipped list with a reason, never uploaded
 2. decode:   HEIC/HEIF → libheif WASM (libheif-js, in a Web Worker, loaded on first use) → RGBA;
              others via the browser's native decoder (createImageBitmap, EXIF orientation applied)
 3. resize:   canvas, long edge ≤ 1024 px (never upscaled), white behind transparency, metadata dropped by re-encode
 4. encode:   JPEG quality 0.85
 5. CreateUpload(post_slug, filename)  → upload_id + presigned PUT (10 min)
 6. PUT to R2 directly (Content-Type image/jpeg)      ← the API never sees the bytes
 7. ConfirmUpload(upload_id, width, height) → server HEADs the object, creates the Image row, deletes the uploads row
```

- The decoder is **`libheif-js`** (Emscripten libheif; the WASM binary embedded in its ESM bundle). It is imported
  only by the worker module, which the bundler emits as its own chunk, so nothing about it is fetched until the
  first HEIC is selected. The worker decodes one file at a time (one `HeifDecoder`; a second `decode` would free the
  first file's context) and is torn down after `HEIF_DECODER_IDLE_MS` — its heap does not shrink after a 12 MP
  decode. At most `UPLOAD_CONVERT_CONCURRENCY` files are decoding/resizing at once.
- The uploaded copy is filed as `<stem>.jpg`; a name the post already holds — or an earlier file in the same pick —
  gets `(2)`, `(3)`, … before `CreateUpload` is asked.
- A device that cannot decode a given HEIC puts that file on the skipped list with the reason (PRD §7); the rest
  proceed. A HEIC that fails to decode is "unreadable" (the file's fault); a decoder that fails to come up is
  "HEIC unsupported on this device".
- A failed PUT or an expired URL shows a per-photo retry that restarts from step 5 with a fresh `upload_id`. The
  server supports this by **replacing** a pending upload that holds the same filename. A confirm whose *answer* was
  lost is retried as the same `ConfirmUpload(upload_id)` — it is idempotent, and starting over would be refused as a
  duplicate filename because the confirm may well have landed. `FailedPrecondition` (no object) goes back to step 5.
- Conversion progress ("변환 중 3/8", then "올리는 중 5/8") is shown; on older phones 8 files take seconds (PRD §6.2).
- The confirm answer carries no `view_url` (the client holds the bytes it just sent). A confirmed photo enters the
  cached post with the local object URL of the converted copy as its `view_url`, until the next `GetPost` replaces
  it. The upload batch forgets the photo at that point — from then on it is the post's photo like any other.
- Per-post upload state lives outside React (`features/upload-photos/model/upload-batch.ts`), like the save queue,
  so the first photo of a new draft survives the route swap the mint causes and a batch keeps going when the editor
  is left. It never survives the session: logout and a session that dies mid-use both call the app's `endSession()`,
  which discards draft queues and upload batches together.
- Step 7 is **one transaction** (write the image row, drop the uploads row) and is **idempotent**: a client that
  never saw the response retries and gets the photo back. Both matter for the same reason — an uploads row that
  outlives its move still names the live photo's object, and the sweep would delete it.
- The server refuses an object it cannot believe is one of our photos: non-positive or absurd dimensions, and a size
  outside 1 byte…10 MiB. The browser's 25 MB cap is advice; a presigned PUT is a URL an authenticated client can use
  however it likes.
- `DeleteImage` deletes the R2 object first, then the row; a missing object is not an error (S3 deletes are
  idempotent).

### R2 wrapper

`internal/storage` implements the port the post context declares (ARCHITECTURE §2.1 "supporting wrapper behind
consumer-owned ports"):

```go
type ObjectStore interface {
    PresignPut(ctx, key, contentType string, ttl time.Duration) (url string, err error)
    PresignGet(ctx, key string, ttl time.Duration) (url string, err error)
    Head(ctx, key string) (size int64, err error)        // ErrNotFound when absent
    Delete(ctx, key string) error
    List(ctx, prefix string) ([]Object, error)           // for the orphan sweep
}
```

The bucket is **private**. Nothing is readable without a presigned URL, and the API issues one only after checking
that the acting user owns the post (PRD F-5, §7). Presigned GET URLs are minted fresh on every `GetPost` with a
short TTL; the FE never persists them.

The adapter holds **two S3 clients**: one for the calls the API makes itself (HEAD, DELETE, LIST) and one that only
signs URLs. A SigV4 signature covers the Host header, so a URL signed for the endpoint the API dials is rejected when
the browser sends it somewhere else. In production both are the same R2 endpoint (`R2_PUBLIC_ENDPOINT` is left
unset); in local dev the API reaches MinIO by its compose service name while the browser reaches the published port.

Two SDK defaults are turned off deliberately: `RequestChecksumCalculation` and `ResponseChecksumValidation`. Left on,
the SDK adds a CRC32 header to every PUT and bakes `x-amz-checksum-mode=ENABLED` into presigned GETs — R2 does not
implement the full-object CRC32 form, and a signed query parameter cannot be stripped by the client.

**Local development runs MinIO** (`docker-compose.yml`), not R2. It speaks the same S3 API and reads the same four
`R2_*` variables, so no Go code knows the difference; path-style addressing is used because MinIO requires it and R2
accepts it.

**Operational prerequisite:** the R2 bucket needs a CORS rule allowing `PUT` (and `GET` for thumbnails) from the FE
origin. Without it, steps 1–5 succeed and step 6 fails silently (PRD F-2). This is recorded in `DEPLOY.md` by the
job.

### Orphan cleanup

A ticker in the post context runs every `ORPHAN_SWEEP_INTERVAL`: deletes `uploads` rows past `expires_at` +
`ORPHAN_MIN_AGE` together with their R2 objects, and deletes any object under `posts/` that has neither an `images`
nor an `uploads` row and is older than `ORPHAN_MIN_AGE`. The PRD leaves the cadence undecided (§9.5); daily is the
provisional default.

Three rules keep it from destroying a live photo, which would be silent and permanent:

- It never deletes an object an `images` row references, even when an expired `uploads` row also names it (that row
  is a confirm whose cleanup was lost; only the row is dropped).
- The referenced-key set is read as **one transaction**. Read as two queries, a confirm landing in between could
  leave a live key in neither result.
- A failed listing or a failed key read deletes **nothing**. A short read looks exactly like "these objects are gone".

It does not run at boot: a restart loop would turn every crash into a full bucket listing, and nothing it collects is
urgent.

### Ownership

Every query is scoped by the interceptor's user id. A slug that exists but belongs to another user → `PermissionDenied`
(HTTP 403, PRD §7). A slug that does not exist → `NotFound`.

### List and resume (PRD F-8)

`ListPosts` returns the acting user's posts newest-first with title, `updated_at`, and `status`. The list screen
renders the "제목 없음" placeholder for a post nobody has titled yet, labels the status (`draft` → 초안,
`review` → 검토, anything a later plan adds passes through as itself), and shows `updated_at` as a relative time up to
a week old and as a date beyond that.

Opening a row navigates to `/posts/:slug`; `GetPost` restores title, memo, images (with fresh view URLs) and — once
plans 06–08 land — content, observations, and the active job. A slug belonging to another user renders a "다른 사람의
글이에요" view (403) and an unknown one "없는 글이에요" (404); only a failure that is *not* an answer offers a retry.

#### As-built extension — job 20 / change 05

The editor renders the post's lifecycle as three steps derived from `post.status` (글 생성 · 글 다듬기 · 글 완성),
each owning one panel, with the step bar at the top of the screen built from `SegmentedControl` and the read-first
block surface from `Editable` + `BlockList`. The memo renders inside 글 생성, the step that works from it; the
title, the step state and the autosave/mint/caret plumbing sit outside the panels, so the editor stays one mounted
component per slug and no step change can strand a queued save. The dock appears only when it has an action, a job,
or a save to report. The rules now in force are in [policy/posts.md](../policy/posts.md)
§"Editor presentation".

## Acceptance Criteria

1. Typing a memo, force-killing the browser within a few seconds, and reopening the post shows the typed text
   (autosave fires ≤ ~2 s after the last keystroke).
2. Selecting an executable (or any non-listed extension) stores nothing and lists the file under "건너뜀" with a
   reason.
3. Eight iPhone HEIC photos all upload; each arrives in R2 as a JPEG with long edge ≤ 1024 px and appears in the
   editor's photo strip.
4. A file over 25 MB at selection is skipped with a reason; a 20 MB HEIC is accepted and uploads as a ~200 KB JPEG.
5. The API process never receives image bytes: uploads go browser → R2 (verifiable in the network tab: the PUT
   targets the R2 host, not `api.postpilot.*`).
6. Deleting a photo removes the `images` row and the R2 object (a subsequent HEAD returns not-found).
7. An `uploads` row whose `ConfirmUpload` never arrives is removed, with its object, by the sweep after expiry.
8. A photo's URL is a presigned GET; the same object requested without a signature is denied (bucket private).
9. `ListPosts` shows only the acting user's posts; `GetPost` on another user's slug → 403; unknown slug → 404.
10. Two posts created the same day with the same title get slugs `…-title` and `…-title-2`; retitling does not change
    the slug.
11. Opening a post from the list restores title, memo, and photos.

## Policy / Config Impact

**The rules live in [`spec/policy/posts.md`](../policy/posts.md) and
[`spec/policy/uploads.md`](../policy/uploads.md)** (backend by job 03, autosave by job 04, the browser side of the
pipeline by job 05). In summary:

- Accepted upload extensions are exactly `jpg jpeg png webp heic heif`; everything else is skipped and reported.
- Photos reach R2 only after browser-side conversion to JPEG q0.85 with long edge ≤ 1024 px; originals never leave
  the device. Server code never decodes images.
- The R2 bucket is private; read access is via presigned GET issued only to the owner; write access via presigned PUT
  bound to a `uploads` row.
- R2 keys follow `posts/{slug}/{image_id}.jpg`; `filename` is unique within a post and is the name the model and
  exporters use.
- Slugs are minted once (`YYYYMMDD-title[-N]`) and immutable.
- Cross-user access to a post or image is 403.
- Confirming an upload is atomic and idempotent; the orphan sweep never deletes an object a photo still references.
- Autosave fires 1 s after the last keystroke and on every way out of the editor; a failed save retries with a capped
  backoff and survives leaving the editor, but never survives the session.

## As-built extension — job 17 / change 03

## As-built extension — job 42 / change 15

Everything the editor has to **say** about its own state is one region at the top of the page, and the docked bar
below it holds only controls and the reason a control is refused
([policy/posts.md](../policy/posts.md) *Editor presentation*).

- **One status region, at the page top** (`pages/editor/ui/EditorStatus.tsx`). It is two mounts of one module,
  because the two halves need different boxes:
  - a **2px progress bar** pinned along the top edge while a job runs (`shared/ui/progress-bar`, a new primitive:
    `role="progressbar"`, determinate from `progressRatio(job)` and indeterminate — no `aria-valuenow` at all —
    where the stage reports no ratio). It is `sticky` with two offsets, because the shell's header has two shapes:
    `top-0` on a phone, where the header is not sticky and scrolls away, and `sm:top-16` from `sm:` up, where it is
    `sticky` at `min-h-16`. It adds **no layout height** in either — the primitive's root is zero-height and the
    track is painted out of flow — so it cannot move the draft when it appears or leave a gap when it goes. Mounted
    as the first child of the editor's `main`, since a sticky box can only be pinned by the box it sits in.
  - one **`meta` line** on the row that already holds 목록 and 삭제, carrying at most one thing in this precedence:
    a failing save, then the running job's stage, then the save state, then `postStatusLabel(post.status)`. It
    **replaced the status badge** that stood there — the row may not carry two state indicators. A failing autosave
    outranks the job because a generation runs for minutes and this screen has no save button at all (PRD F-2).
    It is mounted for `/posts/new` as well, which has no status but does have an autosave that can fail.
- **The job's label lost its counts.** `progressLabel(job)` names the stage only (사진 관찰 중 · 작성 중 ·
  문체 분석 중 and their A/B forms); the numbers are the bar's value, through the new `progressRatio(job)`. The
  `default:` branch returns the generic 생성 중 instead of the literal sentence 작업 준비 중, which also fixes the
  voice screen: a `seed` run hits the same branch and used to announce that nothing had happened for its whole life.
  `ProgressLine` is **kept** — it is the learning-run and voice-run surface — and now renders the count-free label.
- **The save state settles.** A completed save shows 저장됨 for `SAVE_STATUS_SETTLED_MS` and the line then goes
  quiet. The autosave **queue is unchanged**: the settle is presentation, in `features/save-draft/model/useSaveStatus`
  ([tech/draft-autosave.md](../tech/draft-autosave.md)). `SaveStatus.tsx` is gone — with one status line there is no
  second place for it to be mounted.
- **The dock holds controls and refusals.** No save line, no progress notice, no status badge; its existence test is
  now just "does it hold a control or a refusal". `FailureNotice` **stays**, with its retry and with the rule about
  which step offers it: a failure the user can act on is a control, not a status. The voice warnings, the
  deleted-voice warning and the refine step's language-mismatch notice also stay where they are, for the same reason.
- **A refusal is said once.** 먼저 대기 중인 A/B 결과를 확인해 주세요 is gone — a pending comparison still disables both
  buttons and the A/B 결과 확인 link is the single statement of what to do. The purely temporal reasons
  (`jobChecking` · `selectionSaving` · `selectionChecking`) are gone from under the buttons, because the status line
  already says a job or a save is in flight. What survives is a **setup** refusal that names something the user must
  choose, suppressed while the model catalog is still answering, and collapsed to ONE bare line when both actions are
  refused for the same reason. **No precondition changed**: `ordinaryGenerationPreconditions`,
  `comparisonGenerationPreconditions`, `isSetupBlocker` and every `disabled` expression keep their truth values.
- **A standing state is not announced as an event.** The 이 revision을 확정했어요 notice is gone from 글 완성; the

  taken on that screen.
- **글 다듬기's revision row commits with the space it has.** 수정 요청을 입력하세요 takes the new `fieldTitle` type
  role — smaller than the step title it used to borrow, heavier than a caption — and 확정하기 (and 글 완성으로 가기 on
  an already-finalized post) fills the whole remaining width of that heading row.
- **The editor watches its job once.** The `useJob` poll moved up from the step panels to the page
  (`pages/editor/model/useEditorJob.ts`), so the status region and the panels read one 2s poll rather than two ([I5]).
- **Three shared primitives were fixed underneath it** — see
  [tech/design-language.md](../tech/design-language.md) §2.1, §3, §4.3, §7 and §9:
  - `Listbox` **portals its open panel** to the document body and positions it `fixed` from the trigger's measured
    rect, so no scrolling ancestor can clip it — it was clipped worst inside `Sheet`, whose body is the sheet's one

  - The panel wears the new **sixth surface**, `surface-overlay`, plus its own `shadow-lg`, and stacks above every

    wears.
  - `Sheet`'s scrolling body **reserves the focus ring's 4px** on both axes (`p-focus-gutter -m-focus-gutter`, so
    nothing moves): a scroll container resolves both axes away from `visible`, which cut the left and right edges of
    a `w-full` field's ring. `Popover`'s own panel scroller was audited and needs nothing — its `p-4` already
    exceeds the gutter on every side.
