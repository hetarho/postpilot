## Acceptance Criteria (from changes/03.separate-generation-experiments-and-fina)

<!-- The source spec's acceptance criteria. After building, verify each is true in the running code. -->

- [x] A1 The editor renders separate `생성` and `A/B 비교 생성` actions. Starting one never starts the other, and each action exposes its own accurate disabled reason and pending state without allowing concurrent work for the post.
- [x] A2 `생성` resolves and sends the user's active observe/write refs, needs no write comparison pair, observes once only when photos exist, calls one writer, creates no `model_experiment`, applies validated canonical blocks, and leaves the post in `review`.
- [x] A3 `A/B 비교 생성` requires two distinct eligible write candidates, freezes one shared input, observes at most once, calls both writers, creates a resumable blind experiment, and does not mutate canonical content until a user applies a result.
- [x] A4 Neither generation mode silently supplies, changes, recommends, or falls back to a model. Missing active refs block ordinary generation; a missing/invalid pair blocks only A/B generation; no-photo generation still performs zero observation provider calls.
- [x] A5 Target length is collapsed behind an accessible keyboard-operable options popover. A new post and a cleared option round-trip as absent, show no always-visible length field, and cause generation/revision prompts and snapshots to contain no numeric length target or hidden 1,200-character constraint.
- [x] A6 Enabling target length validates the existing allowed range, persists the value per post, and freezes the exact value for ordinary generation, both candidates of an A/B generation, and later AI revision. Existing stored positive values survive migration as enabled options and can be explicitly cleared.
- [x] A7 A ready paired write comparison with a selected blind candidate offers `결과 적용` and `결과 적용하고 활성 모델로 변경`. Both record one verdict, apply the selected output once, reveal the models, update the leaderboard once, and leave the post in `review`; neither finalizes or starts voice learning.
- [x] A8 `결과 적용` leaves every active model unchanged. `결과 적용하고 활성 모델로 변경` changes only the active write selection to the winner. Retries are idempotent, and a post-application/adoption partial failure is reported truthfully and can recover without duplicate content application or ranking.
- [x] A9 The post contract, persistence layer, list, and editor support `draft`, `review`, and `finalized`, with Korean labels `초안`, `검토`, and `확정`. Existing `draft`/`review` rows migrate without changing meaning.
- [x] A10 `확정` flushes pending content edits, records the exact finalized content revision, transitions an eligible post to `finalized`, and succeeds without an analyze-model selection, learning event, durable job, or provider call.
- [x] A11 `확정하고 말투 학습` establishes the same finalized revision and explicitly enqueues the existing idempotent learning flow. A learning setup/enqueue/worker/provider failure leaves the post `finalized`, shows the learning outcome separately, and permits retrying only learning.
- [x] A12 A finalized revision may be learned later by an explicit action, while repeating the same baseline/final revision reuses the learning event and never increments profile evidence twice. Finalize-only never changes the voice profile.
- [x] A13 The first successful changed-content save after finalization returns the post to `review`; unchanged saves do not. Ordinary generation, AI revision, and A/B winner application always produce reviewable content. Export is available from both `review` and `finalized` content and never publishes it.
- [x] A14 Reloading or navigating away and back preserves optional generation settings, active jobs/experiments, finalized state, and learning retry state without starting any write or provider call on mount.
- [x] A15 Focused domain, RPC, store/migration, prompt/snapshot, frontend interaction, cache, and accessibility tests cover every branch above, and the repository's backend tests/vet/build, generated-contract check, frontend tests, lint/FSD/style checks, production build, and spec lint all pass without weakening existing assertions.
