**The clipboard payload is settled — do not re-derive it.** The change doc carries the measured

cannot write files to the system clipboard at all. Do not try a rejected shape "just to check".

### A. Shared clipboard + image mechanics

## Build notes — decisions and deviations

- **T004 — the copy control sits BESIDE the photo, not laid over it.** The change described it as overlaid; at the
  44px touch floor the control's own plane covers roughly a quarter of a 128px tile, which hides the thing the user
  is matching against the pasted markers. It takes the FULL 44px size, not `compact`: design-language §7 reserves
  that one sub-floor step for a low-emphasis way out sharing a dock with the reading area, and this is the feature's
  own repeated primary action. Both review passes flagged the `compact` size; the overlay deviation is deliberate
  and this is where it is recorded.
- **T002 — the PNG reaches `ClipboardItem` as a PROMISE, and `write` is issued before the bytes exist.** The first
  implementation awaited the fetch, the decode and the encode and then wrote; that spends the user activation WebKit
  requires, so on iOS every copy would have failed as `refused` — a retry that could never work. The PAYLOAD is
  unchanged (one item, `image/png`, nothing else); only when the bytes are supplied changed. A load failure now
  surfaces through the write's rejection and is told apart from a policy refusal by a flag set in the load's own
  catch. **This is the one part of the measured path that changed shape, so T009's real-editor check should confirm
  it on Chrome as well as on iOS.**
- **T003 — an `IMAGE` block with an EMPTY file keeps its entry.** The first version filtered it out, on the
  assumption that it produced no marker; `toNaver` in fact writes `[사진 ]` for it, so dropping it would shift every
  later photo against its own marker — precisely what pairing the strip to the marker order exists to prevent. Both
  review passes confirmed the drift by running it. The strip renders such an entry as a marker with no photo behind
  it, and the test now asserts the entry count against `toNaver`'s own marker count rather than against itself.
- **T004 — the entry is a `div`, not a `figure`.** `Thumbnail` brings its own `<figure>`, and a `<figcaption>` has to
  be its figure's first or last child; nesting one mid-list left the marker filename — the caption's whole purpose —
  unreliably associated. The filename is a `Typography as="p"` instead.
- **T005 — the disabled copy control points at its reason** (`aria-describedby`), because a disabled button is
  skipped by the keyboard and would otherwise carry no explanation of why.
- **T004 — a dead view URL is detected, not just a missing one.** A presigned URL expires, and the first version only
  refused to copy when the URL was absent or a `blob:` preview. `Thumbnail` gained an optional `onError`, and the
  entry keys its failure BY URL so a reload that remints it clears the state with no reset plumbing.
- **T006 — two guidance strings, not one.** `export.guidance.naverPhotos` describes the photo flow and
  `export.guidance.naver` stays the plain paste line, because a post with no photos would otherwise be told to copy
  each photo from a strip that is not rendered.
- **`shared/lib/image`'s private `toBlob` was generalized over the mime type** rather than copied, so the
  `OffscreenCanvas` → `HTMLCanvasElement` fallback exists once. `encodePng` does not resize (the stored photo is
  already inside `IMAGE_MAX_LONG_EDGE_PX`, [I6]) and does not flatten onto white (PNG keeps its alpha).
- **Rejected review finding:** `copyPhoto`'s stale guard checks the generation counter and the mount, but not that
  the entry's URL is still the one the press started with. A post refresh mid-copy would report that photo's result
  on that photo's tile, which is the photo the user pressed — the message is about the press, not the URL. The
  format switch and any newer press already invalidate through the shared counter.
- **T009 — NOT performed.** The `/run` pass at 360px and desktop, and the only check that actually proves the
  feature — pasting a copied photo into blog.naver.com 글쓰기 at its marker — need a browser and a real Naver
  session, and this session has neither. What was verified instead: the payload SHAPE (exactly one `ClipboardItem`,
  exactly one `image/png` key, no text flavor) against a stub that awaits the item's promises the way the real API
  does; every failure kind; the strip's marker order asserted against `toNaver`'s own markers; the absence of a
  strip for the other three formats and for a post with no photos; and `toNaver`'s snapshot unmodified. A3–A4 and
  A7–A9 are ticked on that automated evidence; the real-editor paste is left for the owner and is the one thing that
  can still invalidate the promise-valued `ClipboardItem` change above.
