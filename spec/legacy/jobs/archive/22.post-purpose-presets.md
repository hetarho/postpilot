## Acceptance Criteria (from plan/11.post-templates)

<!-- The source spec's acceptance criteria. After building, verify each is true in the running code. -->

- [x] A1 An authenticated user can create, list, update, and delete purposes. `name` is trimmed, non-empty, bounded, and unique within the account (a duplicate is `AlreadyExists` with a Korean message); `instructions` is trimmed, non-empty, and bounded; `description` may be empty. No RPC accepts a user id; a foreign purpose id is indistinguishable from an unknown one.
- [x] A2 `UpdatePurpose` changes only the fields present in the request; an update carrying only `instructions` leaves a concurrently saved `name` intact (store test).
- [x] A3 A post can be saved with a purpose, with the purpose cleared, or with the field omitted; omitted preserves the current assignment under autosave. An unknown or foreign `purpose_id` is rejected and nothing else in the request is applied. Assignment is allowed in every status and changes no content, revision, baseline, or finalization field.
- [x] A4 Generating a post **without** a purpose produces a write prompt byte-identical to the current one (snapshot test unchanged). Generating **with** a purpose appends exactly one `[글의 용도: …]` section after the `[종결어미 제약]` section and before `[이번 글]`, containing the description line only when non-empty, the instructions verbatim, and the fixed precedence sentence (prompt snapshot).
- [x] A5 The voice profile portion of the prompt is byte-identical with and without a purpose for the same voice and post (test compares the prefix up to the purpose section).
- [x] A6 Revision of a post with a purpose injects the same section at the same relative position in the revise prompt; revision of a post without one is unchanged (snapshots).
- [x] A7 The purpose is frozen at enqueue: editing or deleting the purpose after `StartGeneration` / `StartRevision` returns does not change the prompt the worker builds, including after a restart-resume or explicit retry (test edits the row between enqueue and drain).
- [x] A8 An A/B write experiment started on a post with a purpose gives both candidates byte-identical system prompts that include the brief; the experiment detail shows the purpose name; changing the purpose changes the input hash.
- [x] A9 Deleting a purpose referenced by N posts returns `detached_posts = N`, sets those posts' `purpose_id` to NULL in the same transaction, deletes no post or content, and leaves frozen payloads/snapshots intact. Deleting an unreferenced purpose returns 0.
- [x] A10 The migration adds `purposes` and nullable `posts.purpose_id` with the composite account FK; existing posts have no purpose and every existing prompt/job/experiment output is unchanged.
- [x] A11 `/purposes` supports create, read-first per-field edit, and delete with the post-count confirmation, using design-system primitives and semantic tokens; the empty state shows the example as copy only and creates no row.
- [x] A12 The editor's 글 생성 step and `/posts/new` show a `용도` select defaulting to 없음 with the purposes as options and a link to `/purposes`; changing it saves through the draft queue and survives a delayed title save; the list shows a purpose badge for assigned posts. During an active job the select remains usable and explains that the running job keeps its original purpose.
- [x] A13 Purpose list/detail, selection, page mount, polling, copy, and export make no provider call and enqueue no job.
- [x] A14 Domain/store/RPC/prompt/payload tests cover validation limits, uniqueness, presence semantics, foreign-id rejection, freeze-after-edit, detach counting, and snapshot equality; proto/sql generation checks, backend vet/build/tests, frontend tests/lint/FSD/style/build, and spec lint pass without weakening existing assertions.

## Review

### Review log — 2026-08-31

`/code-review high` ran over the whole uncommitted tree (this job plus job 25's, which shares it). Six findings landed
in this job's scope; all six are fixed, each with a regression test where one was possible.

1. **`cmd/api/main.go` dropped `PurposeID`** when projecting a post into `generation.PostInput`, so `freezePurpose`
   always short-circuited and the feature was a **no-op in the real binary**. Both contexts' tests injected the id into
   a fake, so nothing caught it. Fixed, and `cmd/api/bootstrap_test.go` now walks the real adapters end to end
   (purpose → post → generation → prompt); removing the line again makes that test fail.
2. **A rename left stale names on every post** — `useUpdatePurpose` invalidated only the directory, though the name is
   projected onto each post and rendered on the list. Now invalidates the post keys too, exactly as `useRenameVoice`
   does for the identical projection.
3. **The delete confirmation could state a stale `post_count`** — the count is a projection over *posts*, so no purpose
   mutation can invalidate it. The directory query now re-reads on every mount; it is the number a destructive detach
   is confirmed against.
4. **A failed `ListPurposes` rendered as "you have no 용도"** in the editor's select, leaving clearing as the only
   action. Now disabled, said out loud, with a retry.
5. **Field optionality was inferred by comparing numeric limits** (`limit !== PURPOSE_LIMITS.description`), so two
   equal env overrides would make a required field accept an empty save. Now an explicit `optional` prop.
6. **Dead code removed**: `purposeListQueryKey`, `loadPurposes`, `purpose.Service.Exists`.

Rejected / out of scope: the review's other findings (global pairing cap, executor requeue loop, cleanup-after-commit
error, `outcome_unknown` message, missing `publish_jobs` index, `usePublishJob` returning `undefined`, the `CopySource`
escaping) all belong to job 25's publishing surface, not this job — relayed to that job rather than changed here.
