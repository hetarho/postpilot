# Job 27: Throttle the publishing agent heartbeat write (refactor)

> Implementation work doc. Source spec: [code-review/01.full-repo-audit-after-twelve-plans](../../code-review/01.full-repo-audit-after-twelve-plans.md).
> /implement-job 27 builds it via the two checklists below. When done, reflect the result into the
> SSOT (plan/policy/tech) and set status: done. Write it in English.

Finding covered: **R002** — every paired Mac's 5-second poll takes the single SQLite writer to refresh a value read
only as a 30-second freshness hint, and a failure of that write is reported as an authentication failure.

## Acceptance Criteria (from code-review/01)

- [x] A1 A sequence of agent-authenticated calls arriving faster than the heartbeat interval produces **one**
      `TouchAgent` write, not one per call. Proven with a fake clock and a counting store, not by inspection.
- [x] A2 A call arriving after the interval has elapsed does write, so `last_seen_at` never falls further behind
      than the interval.
- [x] A3 The heartbeat interval flows through `backend/internal/platform/config` — it is not a literal in the
      publishing service (ARCHITECTURE §4) — and its documented relationship to the frontend's
      `PUBLISH_AGENT_STALE_MS` (30 s) is stated where a reader will find it: the interval must stay **shorter** than
      the staleness window, or an online agent renders as offline.
- [x] A4 A failed `TouchAgent` no longer fails authentication. The call proceeds, and the failure is logged. Proven
      by a test whose store returns an error from `TouchAgent` and whose `AuthenticateAgent` still returns the agent.
- [x] A5 A revoked agent is still refused before any touch is attempted, and an unknown or empty token still returns
      `ErrAgentRevoked` — the existing refusal order is unchanged.
- [x] A6 No behavior change visible to the Mac agent or the user: claim, lease renewal, progress, complete, fail and
      cancel all behave exactly as before; `ListAgents` still reports a `last_seen_at` that moves.
- [x] A7 The existing publishing test suite passes unchanged except where a test asserted the per-call write it is
      this job's purpose to remove.

## Implementation Checklist

- [x] T001 `backend/internal/platform/config/config.go` — add the heartbeat interval beside the other publishing
      values (`PublishPairingTTL`, `PublishLeaseTTL`, `PublishAssetURLTTL`, …). Use the existing
      `positiveDuration("PUBLISH_AGENT_HEARTBEAT_INTERVAL", "15s")` helper so a non-positive or malformed value
      stops boot like its neighbours. **15 s is chosen, not arbitrary:** the frontend renders an agent stale after
      `PUBLISH_AGENT_STALE_MS = 30_000`, so a heartbeat at half that window keeps a live agent always inside it
      while cutting the writes from the agent's 5 s poll by two thirds. Comment that constraint at the field — the
      two values live in different config seams and nothing else will connect them.
- [x] T002 `.env.example` and `.env.production.example` — add `PUBLISH_AGENT_HEARTBEAT_INTERVAL=15s` next to the
      other `PUBLISH_*` entries (ARCHITECTURE §4: a new env var is added to both in the same job).
- [x] T003 `backend/internal/publishing/service.go` — add the interval to `Config` and carry it into `NewService`.
      Add a small last-touch registry to `Service`: a `map[string]time.Time` keyed by agent id, guarded by a
      `sync.Mutex`, because `WrapUnary` runs concurrently. Keep it unexported and internal to the service — it is a
      write-suppression cache, not state anyone else may read.
- [x] T004 `service.go:104` — replace the unconditional `s.store.TouchAgent(...)` with: read the agent's last
      recorded touch; if `now.Sub(last) < s.config.AgentHeartbeatInterval`, skip the write; otherwise write and
      record `now`. Record the timestamp **only after** a successful write, so a failed write is retried on the next
      call instead of being suppressed for a full interval.
- [x] T005 Same site — stop returning the touch error (A4). A storage failure must not present as the Mac being
      unable to authenticate: the token was valid and the agent is legitimate. Log it (`slog.Warn`, with the agent
      id) and continue. Then revisit `rpc/agent_interceptor.go:60-66`: its comment explains mapping non-revocation
      errors to `CodeUnavailable` so the supervisor backs off rather than stopping — that mapping stays correct for
      `AgentByTokenHash` failures, but the comment should no longer imply the touch is among them.
- [x] T006 Keep `agent.LastSeenAt = &now` on the returned value even when the write was skipped. The agent *was*
      just seen; the returned struct is per-request context, and `ListAgents` reads the database independently
      (`rpc/mapping.go:18`), so the displayed value stays honest either way.
- [x] T007 (**decided: no eviction.** Entries are bounded by the agents enrolled in one deployment, a revoked agent
      is refused before the touch so its entry only goes cold, and an agent id is generated fresh per enrollment so a
      cold entry can never suppress a re-enrolled agent. The reason is recorded at the field in `service.go`.)
      Consider whether the process-lifetime map needs eviction. Entries are bounded by the number of enrolled
      agents per deployment (a handful — `PUBLISH_MAX_PENDING_PAIRINGS` defaults to 8), and a revoked agent never
      reaches the touch, so its entry simply goes cold. Decide explicitly and write the reason down; do not add a
      sweeper without one.
- [x] T008 `backend/internal/publishing/service_test.go` — tests: (a) three authenticated calls one second apart
      with a fake clock produce exactly one `TouchAgent` (A1); (b) a call past the interval writes again (A2);
      (c) a store whose `TouchAgent` returns an error still yields a successful `AuthenticateAgent` (A4);
      (d) a revoked agent and an unknown token are still refused, with no touch attempted (A5). The suite already
      swaps `service.clock = fakeClock{...}` (see `service_test.go:228`), so the clock seam is in place.
- [x] T009 `backend/internal/platform/config/config_test.go` — assert the new value's default and that a
      non-positive or malformed override refuses boot, matching how the sibling `PUBLISH_*` values are tested.
- [x] T010 Re-read `agent/internal/config/config.go:16` (`PollInterval = 5 * time.Second`) and

- [x] T011 Verify the full backend gate and confirm the agent is unaffected:

## Review

- [x] `/code-review` applied (rejections noted with reason) · for non-trivial logic, `/codex:review --background`

**Applied.** (1) `agent/internal/config/config.go` — the new comment broke the const block's gofmt alignment;
realigned, and `gofmt -l` is clean for the whole `agent` module. (2) `service.go` — `touchAgent` swallowed the
`ErrAgentRevoked` that `store.TouchAgent` returns when its `WHERE ... revoked_at IS NULL` update matches no row, so a
revocation landing between the token lookup and the write would have been logged as a transient freshness failure and
the call served as authenticated. That error is now propagated and refuses, with
`TestAuthenticateAgentRefusesARevocationSeenOnlyByTheWrite` locking it in; every other `TouchAgent` failure stays
non-fatal, which is what A4 asks for.

**codex (`gpt-5.5`, read-only) — merged.** Four findings; two were real and are fixed.
*Applied.* (1) *The throttle was not race-safe.* The first version read the registry, dropped the lock, then wrote —
so N calls arriving together at an interval boundary would all read the stale stamp and all reach the writer, which is
exactly the cost the job exists to remove. `touchAgent` now **claims the interval under the lock** before releasing it
and hands the claim back if the write fails; the lock is still not held across the database call.
`TestConcurrentAuthenticationStillWritesLastSeenOnce` fires 16 simultaneous authentications at one instant and asserts
a single write, and the package passes under `-race`. (2) *The map had no lifecycle.* `RevokeAgent` now drops the
agent's entry, so the bound the field comment claims — the agents currently enrolled — is real rather than asserted.
`TestRevokingAnAgentDropsItsHeartbeatEntry` covers it.

*Accepted without change: "revocation can be missed during the throttle window."* The premise does not hold. Revocation
is enforced by the **token lookup**, not by the touch: `GetAgentByTokenHash`
(`store/sqlc/publishing.sql.go:377`) is `WHERE token_hash = ? AND revoked_at IS NULL`, so a revoked agent returns
`ErrNotFound` → `ErrAgentRevoked` on *every* call, and the lookup is never throttled. What the throttle can skip is the
redundant second check inside the write, which only ever narrowed a same-request race that the original code had too.
Every durable mutation is independently fenced on `revoked_at IS NULL` (`publishing.sql.go:41, 106, 334, 759, 832,
909, 942, 970, 1037, 1080`), so **[I1]** is intact.

**Post-merge review pass — one correction applied.** A later `/code-review` over the same diff caught that the
documented freshness budget was **too loose**: a refresh lands on the first poll *after* the interval elapses, so the
worst staleness a viewer sees is the interval **plus the agent's 5 s poll**, not the interval alone. At the `15s`
default that is `20s` against a `30s` window (10 s of margin, not 15 s), and `PUBLISH_AGENT_HEARTBEAT_INTERVAL=25s`
would have passed both the old comment and the old assertion while rendering a live Mac offline. The field comment,
both env examples, `config_test.go`, `policy/publishing`, `plan/12` and `tech/paired-local-publishing-agent` now state
and assert the **sum**.

*Accepted without change: "the throttle disengages when the write keeps failing."* Rolling the claim back on failure
is what T004 specifies, and the degenerate case is exactly the pre-refactor behavior — one write attempt per call —
so the change is never worse than what it replaced, and is far better whenever the failures are intermittent.
Suppressing for a full interval after a failure would instead trade a recoverable stale display for a guaranteed one.

**Rejected.** *Enforce `PUBLISH_AGENT_HEARTBEAT_INTERVAL < 30s` in `Load()` so a misconfigured interval cannot boot.*
The 30 s ceiling is the frontend's `PUBLISH_AGENT_STALE_MS`, which the backend cannot read; enforcing it would hardcode
a frontend constant into backend boot validation and create exactly the cross-seam coupling the documented note exists
to carry. A3 asks for the relationship to be *stated where a reader will find it*, and it now is: the config field
comment, both env examples, `policy/publishing`, `plan/12` and `tech/paired-local-publishing-agent`. The default is
asserted against the window in `config_test.go`, and a raised interval is an operator choice whose only consequence is
a coarser liveness display, visible immediately and reversible by an env change. Making the staleness window
server-owned and serving it to the frontend is the real fix and belongs to its own change, not to this refactor.
Both reviewers raised this independently, so it is recorded as a named follow-up rather than a silent omission. Raised a **third** time during job 30, then with the claim that a stale agent *blocks
publishing*. That premise was checked and is false: `offline` (`PublishPostForm.tsx:61-63`) is consumed only at
`:97`, where it renders an informational notice that the request is stored server-side and starts when the agent
comes up; the publish button's `disabled` at `:175` never reads it. The consequence is cosmetic, which is why the
rejection stands.
