# Postpilot 이야기

> as of ARCH@1 AUTH@1 QUOTA@2 POST@1 VOICE@1 GEN@1 MODEL@2 TEMPLATE@1 GUIDE@1 EXPORT@1 PUBLISH@2 LANG@1 THEME@1 MARKETING@1 | 260905 | 독자: 신규 합류 팀 동료

이 문서를 읽으면 Postpilot이 왜 존재하는지, 어떤 원칙으로 동작하는지, 지금 무엇이 완성됐고 무엇이 남았는지 이해할 수 있습니다. 상세한 제품 결정은 `spec/ssot/`, 진행 상태는 `spec/STATE.md`가 기준입니다. 이 글과 기준 문서가 다르면 기준 문서를 따릅니다.

## 사진과 메모를 내 글로 바꾸는 도구

Postpilot은 두 사람이 쓰는 개인용 글쓰기 도구입니다. 사용자가 사진과 짧은 메모를 넣고 말투, 템플릿, 작문 지침, 목표 언어와 모델을 고르면 블로그 초안을 만듭니다. 결과는 네이버용 일반 텍스트, 티스토리용 HTML 조각, 독립 사이트용 HTML, Markdown으로 복사할 수 있습니다. 운영자 등급 사용자는 명시적으로 요청해 페어링된 Mac으로 네이버 블로그 발행을 맡길 수도 있습니다.

핵심은 “AI가 알아서 전부 한다”가 아닙니다. 사용자가 모델과 실행 시점을 고릅니다. 사진 관찰과 글쓰기를 나눕니다. AI 결과는 언제나 검토하고 직접 고칠 수 있습니다. 페이지를 열거나 목록을 읽는 행위만으로 모델을 호출하지 않습니다.

## 글 한 편이 만들어지는 흐름

새 글은 사용자의 기본 말투와 현재 화면 언어를 초기값으로 삼지만, 서버에는 말투와 목표 언어를 명시해서 보냅니다. 사용자가 가제와 메모를 입력하면 브라우저가 1초 뒤 자동 저장합니다. 첫 저장에서 날짜와 제목을 바탕으로 영구 슬러그를 만들며, 이후 제목이 바뀌어도 슬러그는 바뀌지 않습니다.

사진은 서버가 아니라 브라우저에서 처리합니다. JPEG·PNG·WebP는 브라우저 디코더를 쓰고, HEIC·HEIF는 Web Worker의 `libheif-js`로 풉니다. 긴 변을 최대 1,024px로 줄이고 JPEG 품질 0.85로 다시 인코딩합니다. 이 과정에서 휴대전화가 넣은 위치·기기·촬영 시각 메타데이터도 빠집니다. 한 글에는 사진을 최대 30장 붙일 수 있습니다.

글 생성은 다음 순서를 지킵니다.

1. 사진이 있으면 관찰 모델이 사진을 최대 4장씩 봅니다. 이미 쓸 수 있는 관찰 결과는 사용자가 다시 볼 사진만 고르도록 해 재사용합니다.
2. 글쓰기 모델은 메모와 관찰 결과, 선택한 말투, 템플릿, 작문 지침, 목표 언어와 분량을 한 번에 받습니다.
3. 서버는 모델 출력을 HTML이 아닌 블록 배열로 검증합니다. 텍스트, 제목, 인용, 목록, 이미지 다섯 종류만 허용합니다.
4. 사용자는 생성된 글을 직접 고치거나 AI 수정 요청을 보냅니다. 수정 작업도 전체 블록 배열을 되돌려주지만, 요청하지 않은 문장은 그대로 두라는 계약을 따릅니다.
5. 사용자가 확정하면 그 시점의 정확한 콘텐츠 리비전을 기록합니다. 말투 학습은 확정과 별도의 명시적 선택입니다.

자동 저장과 모델 작업은 서로 다른 대기열을 씁니다. 같은 글에서 요청이 겹쳐도 최신 편집을 잃지 않으며, 모델 호출처럼 오래 걸리는 일은 서버의 영속 작업 레코드로 남습니다. 서버가 재시작되면 실행 중이던 작업을 성공으로 가장하지 않고 실패로 돌려 사용자가 다시 판단하게 합니다.

## 말투, 템플릿, 지침은 서로 다른 책임을 맡습니다

말투는 문장이 어떻게 들리는지를 정합니다. 한 계정은 여러 말투를 가질 수 있고, 각 말투는 다른 말투의 자료를 물려받지 않습니다. 가져온 글, 직접 쓴 설명, 명시적으로 확정하고 학습시킨 글, 수동 수정과 규칙은 해당 말투에만 속합니다. 말투를 삭제해도 과거 글과 학습 기록은 남지만 새 학습에는 쓰지 못합니다. 현재 `규칙으로 저장`을 작문 지침으로 통합할지는 아직 정하지 않았습니다.

템플릿은 글의 모양을 정합니다. 이름, 설명, 본문을 가지며, 본문은 반복 사진과 작성 위치, 비워 둘 슬롯을 나타내는 작은 태그 문법으로 저장됩니다. 사용자는 문법 원문을 편집하지 않고 블록 편집기를 씁니다. 파서는 저장 전 오류를 막고, Go와 TypeScript 구현은 같은 테스트 자료로 판정을 맞춥니다. 템플릿을 삭제하면 글과 지침의 연결만 끊기며, 이미 시작한 작업은 동결된 사본을 계속 씁니다.

작문 지침은 피하거나 주의해야 할 내용을 정합니다. 모든 글에 적용하거나 특정 템플릿에만 묶을 수 있습니다. AI 수정이 성공하면 사용자가 입력한 수정 요청을 후보로 쌓지만, 자동 승인하거나 모델로 요약하지 않습니다. 사용자가 범위를 정해 승인한 지침만 이후 프롬프트에 들어갑니다.

세 층이 충돌하면 책임 경계를 따릅니다. 말투는 어조를, 템플릿은 구조를, 지침은 내용상의 금지와 주의를 맡습니다. 목표 언어는 세 층 안에 적힌 상충하는 언어 지시보다 우선합니다.

## 모델을 고르고 비용을 통제하는 방법

모든 모델 호출은 `internal/llm` 경계를 통과합니다. 현재 OpenRouter 연결 하나를 쓰지만, 도메인 코드는 어느 공급자가 답했는지 알지 못합니다. 운영자가 모델을 사진 분석, 문체 분석, 글쓰기, 이미지 생성, 비디오 생성 목적에 등록해야 해당 화면에 나타납니다. 새 계정에는 숨은 기본 모델이 없습니다.

사용자는 관찰, 분석, 글쓰기 모델을 따로 고릅니다. 일반 생성은 관찰을 최대 한 번 하고 글쓰기 모델 하나만 호출합니다. A/B 비교를 명시적으로 시작한 때에만 두 후보를 같은 입력으로 실행합니다. 판정 전에는 모델 이름을 브라우저에도 보내지 않아 실제로 블라인드 비교가 됩니다. 판정 결과는 계정과 단계별 Elo와 원시 승패 수치에 반영합니다.

모든 계정은 `free`, `basic`, `pro`, `max`, `master` 중 한 등급을 가집니다. 월 지급량은 각각 50, 200, 500, 1,000 크레딧이며 `master`는 무제한입니다. 무료 계정은 만료되지 않는 가입 보너스 50 크레딧도 받습니다. 1크레딧은 상품상 0.01달러의 고정 단위이고, 실제 공급자 비용은 별도 원장에 마이크로달러로 남습니다. 결제와 구독은 아직 없습니다.

모델 작업을 시작할 때 최악의 비용을 먼저 보류하고, 끝나면 실제 사용량과 정산해 남은 크레딧을 원래 묶음에 돌려줍니다. 잔액이 부족하면 작업 레코드를 만들기 전에 거절합니다. 현재 남은 T001은 각 호출이 실제로 사용할 완료 토큰 예산으로 이 보류액을 계산하도록 고칩니다. 그 다음 T002는 네이티브 추론 모델의 글쓰기 예산에 여유를 주고, 추론을 끄는 올바른 요청 형식을 지원합니다.

## 언어와 오류는 추측하지 않습니다

지원 언어는 한국어와 영어 두 가지입니다. 화면 언어, 다음 생성의 목표 언어, 현재 콘텐츠를 만든 언어, 말투 자료의 원본 언어는 서로 독립적입니다. Postpilot은 글의 언어를 감지하거나 번역하지 않습니다. 다른 언어로 쓰려면 목표 언어를 바꾸고 전체 생성을 다시 실행합니다. AI 수정은 현재 콘텐츠 언어를 보존합니다.

오류 화면도 서버 문장을 그대로 보여주지 않습니다. 백엔드는 안정된 오류 이유와 허용된 매개변수만 보내고, 프런트엔드는 현재 화면 언어의 문구로 바꿉니다. 알 수 없거나 낡은 오류는 일반 실패로 처리합니다. SQL, 스택 추적, 프롬프트, 비공개 글, 쿠키와 공급자 키는 사용자용 오류 매개변수가 될 수 없습니다.

## 복사와 네이버 발행은 분리돼 있습니다

네 가지 내보내기 형식은 브라우저가 같은 블록 배열에서 즉시 만듭니다. 서버에 저장하지 않고 전환할 때 요청도 보내지 않습니다. 네이버용 출력은 제목을 따로 복사하고 본문에 사진 파일명 표식을 넣습니다. 화면에 그려진 사진은 한 장씩 PNG로 복사할 수 있습니다. 티스토리는 HTML 조각, 독립 사이트는 고정 스타일의 완전한 HTML 문서, Markdown은 YAML 앞부분이 있는 문서를 만듭니다. 채우지 않은 템플릿 슬롯은 네 형식 모두에서 눈에 띄는 자리표시자로 남습니다.

자동 네이버 발행은 이 복사 기능의 대체가 아니라 별도 경로입니다. 사용자가 확정한 글에서 `네이버에 발행`을 누르고 최종 확인해야 서버가 수정 불가능한 발행 작업을 만듭니다. VPS는 네이버 쿠키나 비밀번호를 받지 않습니다. 페어링된 Mac이 전용 Chromium 프로필과 macOS Keychain의 기기 토큰으로 작업을 가져옵니다.

마지막 발행 클릭에는 트랜잭션으로 보장할 수 없는 경계가 있습니다. Mac은 제목, 블록, 사진과 캡션 순서, 태그, 카테고리, 공개 범위를 먼저 검증합니다. 서버가 `committing` 상태를 영구 저장했다고 확인한 뒤 정확히 한 번만 최종 컨트롤을 누릅니다. 이 뒤 결과를 확인하지 못하면 자동 재시도하지 않고 `outcome_unknown`으로 남깁니다. 중복 발행을 숨기지 않기 위한 선택입니다.

서버와 프런트엔드, 발행 대기열, Mac 동반 앱의 기반은 완성됐습니다. 그러나 네이버 편집기를 다루는 결정적 드라이버, 호환성 탐침, 전체 동반 앱 테스트와 실제 네이버 발행 검증은 아직 완성되지 않았습니다. T003부터 T008이 이 흐름을 순서대로 마칩니다. 마지막 실제 발행은 사용자가 테스트 블로그를 지정하고 그 한 번을 명시적으로 승인해야 실행합니다.

## 작고 조용한 화면을 만드는 원칙

화면은 360px 휴대전화를 먼저 설계하고 320px에서도 가로 스크롤이 생기지 않아야 합니다. 누르는 대상은 원칙적으로 44×44px 이상입니다. 휴대전화 입력 글자는 최소 16px라서 iOS가 화면을 갑자기 확대하지 않습니다. 한 화면에는 세로 스크롤러를 하나만 두고, 중요한 실행 버튼은 엄지손가락이 닿는 아래쪽에 놓습니다.

색은 장식보다 역할을 나타냅니다. 표면의 높낮이와 간격으로 묶음을 드러내고 테두리와 카드는 드물게 씁니다. 공용 컨트롤은 모두 `shared/ui`에서 가져오며, 프런트엔드는 등록된 디자인 토큰만 사용합니다. 시스템·라이트·다크 테마는 브라우저에만 저장되고 첫 React 화면 전에 적용됩니다. 한국어와 영어 선택도 같은 환경설정 묶음으로 로그인, 앱, 공개 소개 화면에서 공유합니다.

## 코드를 지키는 구조

백엔드는 Go의 도메인 문맥별 패키지로 나뉩니다. 순수 도메인은 Proto, SQL 행, 데이터베이스나 전송 계층을 알지 못합니다. RPC와 저장소 어댑터가 경계에서 변환하며, 각 문맥은 자기 테이블만 소유합니다. 조립은 `cmd/api`에만 둡니다.

프런트엔드는 Feature-Sliced Design을 따릅니다. 의존성은 `app → pages → widgets → features → entities → shared` 방향으로만 흐릅니다. 파일은 도메인 명사, 사용자 행동, 큰 화면 블록, 전체 페이지, 공용 코드라는 역할에 따라 놓습니다. Proto 생성물은 `shared/api` 경계 밖에서 직접 가져오지 않습니다.

계약이나 스키마가 바뀌면 생성 코드를 다시 만들고 차이가 남지 않는지 확인합니다. 프런트엔드는 테스트, 린트, FSD 검사, 스타일 검사와 빌드를 통과해야 합니다. 백엔드와 Mac 동반 앱은 포맷, vet, 빌드와 테스트를 통과해야 합니다. 새 의존성을 다룰 때는 현재 공식 문서를 먼저 읽고 패키지 관리자가 결정한 최신 버전과 잠금 파일을 확인합니다.

## 지금 어디까지 왔나

기존 `plan/changes/jobs` 체계의 현재 진실은 14개 도메인 SSOT로 옮겼습니다. 옛 문서는 `spec/legacy/`에 읽기 전용 기록으로 남겼습니다. 진행을 관리하는 문서는 `spec/STATE.md` 하나이며, 프로젝트에는 `create-architecture`, `create-ssot`, `update-ssot`, `create-task`, `implement-task`, `create-narrative` 여섯 스킬만 남았습니다.

현재 구현 대기 작업은 두 갈래입니다.
