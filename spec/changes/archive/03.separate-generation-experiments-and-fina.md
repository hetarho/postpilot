# 03. Change: Separate Generation Experiments and Finalization Controls

> A **change proposal** (a WHAT delta) that modifies the already-shipped behavior of [plan/09.stage-model-experiments-and-leaderboards](../../plan/09.stage-model-experiments-and-leaderboards.md).
> Filled by /create-change through a user interview — a reviewable doc, not a one-line prompt.
> The STEPS live in the job that /create-change-job creates. Write it in English.

## As-is

Plan 09 replaced plan 06's single-writer generation with a write experiment. The editor's only generation action
requires an observe selection and two configured write candidates. One durable job observes once, fans the immutable
snapshot out to both writers, and waits for a blind verdict. The active write-model selection is not used by this
normal editor action, so choosing an active write model has no effect on the ordinary path.

A completed write comparison currently separates one user decision across three actions: choose a blind candidate,
apply its output to the post, and optionally adopt its model as the active model. Applying the winner replaces the
canonical block content and moves the post to `review`; choosing a model-experiment winner does not finalize the
post. The model-lab comparisons for observe and analyze stages use the same experiment aggregate but do not produce
canonical post content.

The editor always shows a required positive target-length field above `생성`. New and migrated posts carry a
1,200-character default. That number is persisted with the post, frozen into every write snapshot, included in the
prompt, and also reused by AI revision. There is no representation for "no length constraint", even when the user
wants the model to choose a natural length.

Posts have only `draft` and `review` states. Generation or applying a write winner moves a post to `review`, while
manual content saves preserve the current state. The `확정하고 말투 학습` action flushes pending edits, freezes a
learning input, and enqueues a voice-analysis job, but it does not change the post status. It also requires an active
analyze model, leaving no way to mark a post complete without spending another provider call or adding more voice
evidence. Consequently, a successfully learned post still appears as `초안` or `검토` rather than as explicitly
finalized.

## To-be

### Explicit single generation and A/B generation

The editor exposes two distinct, user-initiated generation modes:

- **`생성`** is the primary ordinary path. It uses the account's explicitly selected active observe model when
  photos exist and its explicitly selected active write model. One durable job observes at most once, calls exactly
  one writer, validates the result through the existing canonical block path, applies it directly to the post, and
  sets the post to `review`. It creates no model experiment and requires no configured write A/B pair.
- **`A/B 비교 생성`** is a separate secondary action. It requires the configured write candidate pair, observes at
  most once, and runs both writers over the same frozen input exactly as plan 09 does today. Candidate completion
  does not change canonical post content. The result remains resumable and blind until the user selects one.

Both actions retain ownership, active-job, pending-experiment, capability, and photo preconditions. They send
explicit model refs resolved from the user's saved selections; neither the server nor the page silently chooses a
model, applies a recommendation, starts both modes, or falls back from one mode to the other. With no photos,
observation remains a zero-call stage. Every provider call remains inside a user-started durable job [I3, I5].

### Optional generation options

The default editor surface shows the two generation actions and a compact options affordance, not an always-visible
number field. Opening its popover lets the user enable, edit, or clear an optional target character count. A new post
starts with no target length. When the option is absent, generation and revision carry an explicit absence through
their contracts and snapshots and the writing prompt contains no numeric length target; the model chooses a natural
length. The implementation must not translate absence back to a hidden 1,200-character default.

When enabled, the existing minimum/maximum validation remains, the positive value is persisted per post, and the
exact value is frozen into ordinary and A/B generation snapshots. Both A/B writers receive the same option. Existing
stored positive target lengths remain configured during migration so the change does not silently discard a user's
setting, and the user can clear them from the popover. The current mandatory default is removed; no new runtime
configuration value is introduced.

### One-step write-result decisions

After selecting the preferred blind write candidate, the result surface offers exactly two positive completion
choices:

- **`결과 적용`** records the A/B verdict and applies that candidate to the current post only.
- **`결과 적용하고 활성 모델로 변경`** records the same verdict, applies the candidate to the current post, and
  explicitly changes the active write model to the winner's model.

Both choices reveal and rank the same valid pairwise verdict, apply the chosen content once, and leave the post in
`review`. Neither choice finalizes the post, starts voice learning, or changes observe/analyze selections. The first
choice never changes an active model. The second is the only write-result action that does so, and a retry after a
partial failure must not apply content twice or count a second leaderboard verdict. If content application succeeds
but active-model adoption fails, the UI reports those two outcomes separately and offers an adoption retry instead
of pretending that the post application failed.

The existing failed-candidate retry, use-single-result, dismiss, blind assignment, retention, cost accounting, and
leaderboard rules remain. Observe/analyze model-lab comparisons retain their stage-specific application semantics;
this streamlined two-choice contract is for a successful paired write comparison attached to a post.

### Finalization independent of voice learning

Posts gain a third durable state, `finalized`, rendered as `확정`. Finalization means only that the current saved
canonical blocks are the version the user intends to copy or export; it never publishes the post [I1]. The editor's
final section exposes two explicit actions for an eligible `review` post:

- **`확정`** first flushes the current editor save, records that exact content revision as finalized, and changes the
  post status to `finalized`. It requires no analyze model and makes no provider call, learning event, or job.
- **`확정하고 말투 학습`** performs the same finalization and then explicitly creates or reuses the idempotent
  baseline/final-revision learning event and enqueues its durable analyze job.

Finalization and learning have independent outcomes. If saving or finalization fails, neither action claims success.
Once finalization succeeds, a missing analyze selection, enqueue error, worker failure, or provider failure does not
roll the post back from `finalized`; the UI reports the learning failure and lets the user retry learning alone. A
finalized revision that was not learned remains eligible for a later explicit learning action, while repeating the
same baseline/final revision cannot add duplicate evidence.

Editing canonical content after finalization returns the post to `review` on the first successful changed-content
save. Applying a new generation, AI revision, or A/B write winner likewise establishes reviewable content and leaves
or returns the post to `review`. Repeated unchanged saves do not demote a finalized post. Export remains available
for both `review` and `finalized` content, and the list/editor badges expose the new state consistently.

## Scope / Non-goals (regression boundary)

**In scope**

- Separate ordinary single-model generation and explicit write A/B generation actions in the post editor.
- Active observe/write selection semantics for ordinary generation and A/B-pair semantics for comparison
  generation, including independent preconditions and durable job payloads.
- A collapsed generation-options popover and an optional, nullable target-length contract across post persistence,
  generation, revision, experiment snapshots, prompts, and editor cache/autosave behavior.
- Two combined write-verdict/application choices, with optional explicit adoption of only the winning write model
  and idempotent partial-failure recovery.
- A persisted `finalized` post status, an explicit content-revision finalization boundary, and separate finalize-only
  and finalize-plus-learning actions.
- Correct status transitions and eligibility across manual editing, ordinary generation, AI revision, A/B result
  application, export, post lists, reloads, and failed/retried learning.
- Contract, migration, policy, and focused backend/frontend test updates required by those behaviors.

**Non-goals / must not change**

- No automatic or scheduled generation, A/B comparison, finalization, voice learning, validation, retry, model
  adoption, or provider call. Opening a page and the passage of time remain read-only.
- No automatic publishing, platform credentials, browser automation, or change to block-array canonical content
  and browser-derived export [I1, I2]. `finalized` is not a published state.
- No automatic active-model choice, recommended-set application, leaderboard-driven routing, fallback model, or
  server inference of a missing model ref [I3].
- No change to blind randomization, fair shared snapshots, two-candidate maximum, Elo rules, private account scope,
  retention, usage/cost accounting, or observe/analyze model-lab experiment semantics.
- No voice-profile reset and no requirement to learn again after every finalized post. Finalize-only is a complete
  successful outcome, including after the user's voice profile is already satisfactory.
- No requirement for previous posts or imported samples, no background learning, and no weakening of the
  idempotent evidence rules in change 02.
- No new queue implementation, provider SDK, frontend library, or runtime configuration value.

## Acceptance Criteria

1. The editor renders separate `생성` and `A/B 비교 생성` actions. Starting one never starts the other, and each
   action exposes its own accurate disabled reason and pending state without allowing concurrent work for the post.
2. `생성` resolves and sends the user's active observe/write refs, needs no write comparison pair, observes once only
   when photos exist, calls one writer, creates no `model_experiment`, applies validated canonical blocks, and leaves
   the post in `review`.
3. `A/B 비교 생성` requires two distinct eligible write candidates, freezes one shared input, observes at most once,
   calls both writers, creates a resumable blind experiment, and does not mutate canonical content until a user
   applies a result.
4. Neither generation mode silently supplies, changes, recommends, or falls back to a model. Missing active refs
   block ordinary generation; a missing/invalid pair blocks only A/B generation; no-photo generation still performs
   zero observation provider calls.
5. Target length is collapsed behind an accessible keyboard-operable options popover. A new post and a cleared
   option round-trip as absent, show no always-visible length field, and cause generation/revision prompts and
   snapshots to contain no numeric length target or hidden 1,200-character constraint.
6. Enabling target length validates the existing allowed range, persists the value per post, and freezes the exact
   value for ordinary generation, both candidates of an A/B generation, and later AI revision. Existing stored
   positive values survive migration as enabled options and can be explicitly cleared.
7. A ready paired write comparison with a selected blind candidate offers `결과 적용` and
   `결과 적용하고 활성 모델로 변경`. Both record one verdict, apply the selected output once, reveal the models,
   update the leaderboard once, and leave the post in `review`; neither finalizes or starts voice learning.
8. `결과 적용` leaves every active model unchanged. `결과 적용하고 활성 모델로 변경` changes only the active
   write selection to the winner. Retries are idempotent, and a post-application/adoption partial failure is reported
   truthfully and can recover without duplicate content application or ranking.
9. The post contract, persistence layer, list, and editor support `draft`, `review`, and `finalized`, with Korean
   labels `초안`, `검토`, and `확정`. Existing `draft`/`review` rows migrate without changing meaning.
10. `확정` flushes pending content edits, records the exact finalized content revision, transitions an eligible post
    to `finalized`, and succeeds without an analyze-model selection, learning event, durable job, or provider call.
11. `확정하고 말투 학습` establishes the same finalized revision and explicitly enqueues the existing idempotent
    learning flow. A learning setup/enqueue/worker/provider failure leaves the post `finalized`, shows the learning
    outcome separately, and permits retrying only learning.
12. A finalized revision may be learned later by an explicit action, while repeating the same baseline/final
    revision reuses the learning event and never increments profile evidence twice. Finalize-only never changes the
    voice profile.
13. The first successful changed-content save after finalization returns the post to `review`; unchanged saves do
    not. Ordinary generation, AI revision, and A/B winner application always produce reviewable content. Export is
    available from both `review` and `finalized` content and never publishes it.
14. Reloading or navigating away and back preserves optional generation settings, active jobs/experiments,
    finalized state, and learning retry state without starting any write or provider call on mount.
15. Focused domain, RPC, store/migration, prompt/snapshot, frontend interaction, cache, and accessibility tests cover
    every branch above, and the repository's backend tests/vet/build, generated-contract check, frontend tests,
    lint/FSD/style checks, production build, and spec lint all pass without weakening existing assertions.
