# 07. Change: Bound Reasoning Tokens and Surface Candidate Failure Causes

> A **change proposal** (a WHAT delta) that modifies the already-shipped behavior of [plan/04.model-provider-registry](../../plan/04.model-provider-registry.md).
> Filled by /create-change through a user interview — a reviewable doc, not a one-line prompt.
> The STEPS live in the job that /create-change-job creates. Write it in English.

## As-is

`llm.Request` carries no notion of reasoning, and `openaicompat.buildRequest` sends exactly
`model · messages · max_tokens · stream · stream_options · response_format`. The word `reasoning` does not appear
anywhere under `backend/internal/llm`. A registered model that reasons by default therefore reasons unbounded, and
the app has no way to say otherwise.

Reasoning tokens are billed against the *same* completion budget as visible output. `LLM_MAX_TOKENS_DEFAULT` is the
typed constant `4096`, filled in by `Registry.Complete` whenever a caller sets none, and every generation caller sets
none. So a reasoning model can spend the entire completion budget thinking and emit no text at all.

When that happens the provider ends the stream with `finish_reason: length` and zero content. `Client.Complete`
sees an empty completion and returns `ErrBadOutput` with a bare `llm.Response{}` — discarding the usage it had
already collected from the stream. Nothing distinguishes this from a model that answered with garbage.

Above the port, `experiment.userFacingError` collapses every non-deadline error into the single string
`모델 호출에 실패했어요. 다시 시도해 주세요.`, and `experiment.runCandidate` logs nothing at all. The job layer already
does the right thing here — `job.failureMessage` unwraps `llm.ProviderError` and surfaces the provider's own message —
but the experiment candidate path does not reuse that rule. A failed candidate therefore leaves no line in the API
log and no cause in the database.

**Measured on 2026-08-30** against production experiment `53f3039f…` (write stage, prompt rebuilt from its stored
`input_snapshot` through `BuildWritePrompt`, 3,571 prompt tokens, `z-ai/glm-5.3` over OpenRouter):

| `max_tokens` | `reasoning` sent | reasoning tokens | `finish_reason` | visible content | cost |
|---|---|---|---|---|---|
| 4,096 | — | 3,609 | `length` | **0 chars** | $0.018 |
| 16,384 | — | 13,932 | `length` | 487 chars | $0.073 |
| 16,384 | `{effort: low}` | **26** | `stop` | 4,205 chars | $0.015 |

Both candidates of that experiment failed this way (`z-ai/glm-5.3` and `deepseek/deepseek-v4-pro-0813`, both with
NULL usage, both with the generic error string), while `z-ai/glm-5.3-flash` — which does not reason by default —
succeeded in the same pair. **Raising the budget alone does not fix this**: the model simply reasons longer and costs
four times as much.

## To-be

**1. The port carries reasoning intent.** `llm.Request` gains a reasoning effort field. The `openai_compatible`
adapter sends a `reasoning: {effort: …}` object **only** when one is resolved; with none resolved the outgoing body
is unchanged from today.

**2. Effort is resolved per stage, overridable per model.** A code-owned stage policy supplies the default —
`write` and `observe` ask for low effort (neither task benefits from extended reasoning; the table above shows low
effort producing *better* output faster and cheaper), `analyze` sends nothing. A model entry in
`config/providers.yaml` may carry `reasoning_effort` to override that default, including the sentinel that means
"send no reasoning key at all" so a model whose provider default is already right is left untouched. The shipped
file uses that sentinel for `anthropic/claude-sonnet-5`, the current active write model, whose adaptive thinking
works today and must not be changed by this change.

**3. The completion budget goes up.** `LLM_MAX_TOKENS_DEFAULT` becomes `8192` — roughly three times the 2,386-token
completion measured with reasoning bounded, so a long draft plus modest reasoning fits, while a model that has run
away still hits a ceiling worth asking about.

**4. Budget exhaustion is its own failure, named as such.** A response that ends with `finish_reason: length` and no
usable content produces a distinct normalized error, separate from `ErrBadOutput`. Its user-facing message says the
model spent its budget without producing text and points at the remedy (a shorter target length, or a different
model) instead of the generic "모델 호출에 실패했어요".

**5. Usage survives a failed call.** When the adapter fails *after* the provider reported usage, that usage reaches
the caller so a failed candidate can still record its tokens, cost, and latency. A failure that costs money must be
visible as having cost money.

**6. A failed experiment candidate is observable.** Each one is logged exactly once at ERROR with the experiment id,
candidate id, model ref, and the underlying error, and the error persisted on the candidate row carries the
provider's own message — the same rule `job.failureMessage` already applies, reused rather than re-derived.

## Scope / Non-goals (regression boundary)

**In scope**

- `backend/internal/llm`: the `Request` reasoning field, the new truncation error in the normalized set, usage
  travelling with a failed call, and the registry resolving stage default + per-model override.
- `backend/internal/llm/openaicompat`: emitting the `reasoning` object, and classifying a `length` finish with no
  content.
- `backend/config/providers.yaml`: the optional per-model `reasoning_effort` field, validated strictly at boot, and
  the `anthropic/claude-sonnet-5` override.
- `backend/internal/platform/config`: `LLM_MAX_TOKENS_DEFAULT` 4096 → 8192, and the stage effort policy as a typed
  code-owned value.
- `backend/internal/experiment`: candidate failure logging, and persisting the provider message plus reported usage
  on a failed candidate.
- [`spec/policy/providers.md`](../../policy/providers.md): the reasoning rule and the new failure mode.

**Non-goals**

- **No `reasoning.exclude`.** It only hides reasoning from the response; the tokens are still generated and still
  billed. It solves nothing here and must not be used as if it did.
- No in-app routing, fallback, or automatic retry to a different model on truncation — plan 04 already rules that
  out; the user retries explicitly through the existing `RetryCandidate` action.
- No change to which models or providers are registered beyond the one `reasoning_effort` override, to selection
  memory, to the dropdowns, or to any proto contract.
- No change to A/B blindness, snapshot immutability, ranking, retry, winner application, or adoption.
- No change to the `anthropic` adapter (still unbuilt) and no new dependency.
- No streaming of tokens to the client — the stream stays inside the process (PRD §6.6).
- No change to block validation or the post-content JSON schema; the `level`-field contradiction found alongside
  this failure is a separate change against plan 06.
- No frontend change: the experiment UI already renders `candidate.error` and the usage fields verbatim.

## Acceptance Criteria

1. A model that resolves to no effort (no stage default and no `reasoning_effort`) produces a chat-completions
   request body with **no** `reasoning` key — byte-identical to today's shape for that model.
2. A write candidate on `z-ai/glm-5.3` over a production-shaped snapshot finishes with `finish_reason: stop` and
   non-empty content, with reasoning tokens a small fraction of the completion rather than all of it.
3. `LLM_MAX_TOKENS_DEFAULT` is `8192`, owned by `backend/internal/platform/config`; neither `4096` nor `8192` appears
   as a completion-budget literal anywhere else.
4. A `reasoning_effort` declared on a model in `config/providers.yaml` wins over the stage default; an unrecognized
   value stops the api at boot with a clear error, matching plan 04's loud-config posture. `anthropic/claude-sonnet-5`
   sends no `reasoning` key.
5. A provider response ending `finish_reason: length` with no usable content surfaces as the new truncation error,
   whose user-facing message names budget exhaustion and its remedy — distinct from the generic provider-failure
   message and from `ErrBadOutput`.
6. A candidate that failed after the provider reported usage stores that provider message and non-null
   prompt/completion tokens and cost, instead of the generic sentence and NULL usage.
7. A failed experiment candidate emits exactly one ERROR log line carrying experiment id, candidate id, model ref,
   and the cause — reproducing today's silent failure leaves a diagnosable trace.
8. No regression: ordinary observe/write/analyze generation, revision, A/B blindness, `RetryCandidate`, winner
   application, adoption, and the leaderboard behave exactly as before; the boundary test still passes (no adapter
   or SDK type escapes `internal/llm`).

## Grounding

- Target plan: [plan/04.model-provider-registry](../../plan/04.model-provider-registry.md) — the port, the registry,
  `providers.yaml`, and `LLM_MAX_TOKENS_DEFAULT` are all its as-built surface.
- Constitution ([I1]–[I7]): [00.overview](../../plan/00.overview.md) §3 — none is touched. **[I3]** is reinforced: the
  app still chooses no model and applies no pairing; reasoning effort is a call parameter, not a model choice.
  **[I5]** is unaffected: failures still land on the job/candidate record, not in a blocking RPC.
- Also reflected into: [plan/09](../../plan/09.stage-model-experiments-and-leaderboards.md) (candidate failure now
  carries the provider message and usage) — the change is owned by plan 04.
- Affected policy / tech / config: [`spec/policy/providers.md`](../../policy/providers.md) gains the reasoning rule
  (effort resolution order, `exclude` is forbidden, truncation is a named failure). Config: `LLM_MAX_TOKENS_DEFAULT`
  → `8192` and the new stage effort policy both belong to `backend/internal/platform/config`; the per-model
  `reasoning_effort` belongs to `backend/config/providers.yaml`. No new env var, no new FE config value.
