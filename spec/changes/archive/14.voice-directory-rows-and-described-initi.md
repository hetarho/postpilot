# 14. Change: Voice Directory Rows and Described Initial Voice

> A **change proposal** (a WHAT delta) that modifies the already-shipped behavior of [plan/10.independent-voice-profiles-and-post-assi](../../plan/10.independent-voice-profiles-and-post-assi.md).
> Filled by /create-change through a user interview — a reviewable doc, not a one-line prompt.
> The STEPS live in the job that /create-change-job creates. Write it in English.

## As-is

### The directory is three stacked forms, not a list

`/voices` renders the account's voices as one section among three. Below the active list sits an always-expanded
`CreateVoiceForm` — a labelled name field, a character counter, a hint, a source-language `Listbox`, a second hint,
and a submit button — and below that, whenever tombstones exist, a fully expanded deleted section with its own
heading and help paragraph. The list a returning user came for is the shortest part of the screen, and on a phone the
creation form pushes the tombstones a full viewport below the fold.

### A row is four targets in two lines

An active row is a `RenameVoiceField` (the shared `Editable`) wrapping a flex line. Inside that line, the voice name
is an **underlined `Link`** into `/voices/$voiceId`, followed by the default and language badges; `Editable` adds its
own pencil trigger, which swaps the whole line for an in-place rename form. When the voice is not the default, a
second line underneath carries `SetDefaultVoiceButton` and `DeleteVoiceButton`.

So one conceptual row is a link, a pencil, and two buttons spread over two lines, and the row's large remaining area
does nothing. §4.1 of the [design language](../../tech/design-language.md) says the opposite: "A row in a list is one
target, not a row with a small button inside it."

### The detail screen cannot rename

`/voices/$voiceId` (`VoiceLayout`) shows the voice's name as a static `h1` with its badges, an optional restore
notice, and the five tabs (말투 · 버전 기록 · 기존 글 가져오기 · 대조 규칙 · 프로필 검증). Renaming exists only on
the directory, so the name is edited on the screen that shows the least about the voice.

### A new voice has no way to be described

`CreateVoice` trims the name, requires an explicit immutable `source_language`, refuses an active-name collision, and
creates an **empty isolated profile**. It never copies the default profile — deliberately, and that stays true.

The consequence is that a freshly created voice is genuinely blank and the product offers only two ways to fill it,
both of which require text the user has already written:

1. paste a historical text of at least `VOICE_SAMPLE_MIN_CHARS` (200) characters on the 기존 글 가져오기 tab, which
   writes a `voice_samples` row and enqueues an `analyze_voice` job; or
2. finalize a post under that voice, which enqueues a `learn_voice` event.

A user who knows exactly the register they want but has no corpus for it ("단순하고 차분하지 않은, 농담조의 요리
말투") has nowhere to say so. Until they produce 200 characters of matching prose, every generation under the new
voice runs against an empty profile.

## To-be

### 1. The directory is a list with one docked action

`/voices` shows the active voices and nothing else above the fold. Creating a voice is a single docked
`새 말투 만들기` action at the bottom of the screen that opens an overlay; the inline creation form is gone from the
page. Tombstones become a **collapsed disclosure** that is rendered only when at least one deleted voice exists and
names its count in the summary; expanding it reveals the same rows with their restore action.

### 2. A row is one target, and it goes to the voice

The whole active row is the navigation target for `/voices/$voiceId`. The name is no longer underlined, because the
row — not the text inside it — is the link. The row's own lifecycle controls, `기본으로 설정` and `삭제`, sit **on
that same row** beside the name and badges rather than on a second line, and a press on either one acts without
navigating. As today, they appear only for a non-default active voice: the default voice can be neither re-defaulted
nor deleted, and the row for it therefore carries no controls at all. A deleted row keeps `복원` on the same footing
inside the disclosure.

The row remains one accessible link whose name is the voice's name, with the badges as supporting text, and the
controls stay separate focusable buttons in the tab order. Nothing is nested inside an anchor.

### 3. Renaming moves to the detail screen

`RenameVoiceField` leaves the directory and wraps the voice's name in `VoiceLayout`, keeping its existing read-first
`Editable` shape, its 50-character rule, its collision error, and its ability to rename a tombstone so a restore
conflict can be resolved. The directory has no rename affordance at all; the row is a way in, and the name is edited
where the voice is.

### 4. Creation is a sheet that can also describe the voice

The docked action opens the shared `Sheet` — a bottom sheet on a phone, a centred panel from `md:` up — carrying
three fields:

- **이름** (required) — unchanged: 1–`VoiceNameMaxChars` (50) Unicode scalar values, unique among active voices.
- **원문 언어** / `source_language` (required) — unchanged: an app-drawn `Listbox`, immutable after creation.
- **말투 설명** (optional) — new: free text of at most `VoiceDescriptionMaxChars` Unicode scalar values.

Submitting with an empty description behaves exactly as creation does today. Submitting **with** a description
creates the voice and, in the same request, enqueues exactly one durable seeding job; the sheet closes and the user
lands on the new voice's detail screen, where the existing job progress line and `FailureNotice` report the run.

### 5. A described initial voice, written by the analyze-stage model

`CreateVoice` gains an optional `description` and an explicit `ModelRef`. When a description is present the server:

1. creates the voice exactly as today (an empty isolated profile, no copy of the default); then
2. enqueues one voice-owned durable job of a new kind, `seed_voice`, frozen to that voice, that user, the
   description, the voice's `source_language`, and the caller-supplied model ([I5] — the RPC never blocks on the
   provider, and the response carries a `job_id` the client polls with the existing `GetGeneration` machinery).

The handler makes **one** completion call against the account's saved **analyze-stage** selection — the same stage
that already writes every voice profile in the product (sample analysis, finalized-post learning, profile
validation), so one voice's profile is never written by two different models ([I3]: the choice is explicit and
user-owned; the client sends the concrete ref, the server never guesses one). It asks for a styleguide in the voice's
declared source language, in the shape the existing analysis prompts already require, and publishes it as the voice's
**first profile version** with origin `seed`.

Three rules bound what a seed may claim:

- **A description is an instruction, not evidence.** It is never written as a `voice_samples` row, never counted in
  `source_count` or `finalized_source_count`, never entered into the few-shot bank, never embedded, and never bumps
  `corpus_version`. Validation eligibility (`can_validate`) is unchanged by seeding.
- **A seed carries no measurements.** Descriptors it produces are `ANALYZED`; the measured quantities that only a
  real corpus can supply (average sentence length, ending distribution, the six axes) stay unknown rather than being
  measured from the description's own prose.
- **A seed never overwrites real work.** The publish is conditional on the profile still being empty and unversioned.
  A seed job that finishes after a sample analysis or a finalization has already published a version is a no-op that
  completes without failing, and the same guard makes the first genuine analysis authoritative over the seed.

The result lands directly on the profile, with no separate preview-and-apply step: the version history and the
existing read-first profile editors are already the way a user overrules a machine-written profile.

### 6. Creating a voice never fails because of a model

Voice creation and seeding are separable outcomes. A provider error, a truncated response, a missing analyze-stage
selection, or a disabled model can fail the seed; none of them may fail or roll back `CreateVoice`. A voice whose
seed failed is a normal empty voice, and the failure is legible on its detail screen through the existing failure
surface rather than as a lost creation.

Where the account has no usable analyze-stage selection, the sheet says so in the description field's message slot
and creation still proceeds without a seed. A description submitted without a resolvable model is refused with
`InvalidArgument` before the voice is inserted, so the user never gets a silently unseeded voice.

## Scope / Non-goals (regression boundary)

### In scope

- The `/voices` directory: list-first layout, the docked creation action, the collapsed tombstone disclosure, and the
  removal of the inline creation form.
- Full-row navigation on an active and a deleted row, the removal of the name's underline, and `기본으로 설정` /
  `삭제` / `복원` moving onto the row they belong to without becoming nested interactive elements.
- Moving `RenameVoiceField` from the directory row to the voice name in `VoiceLayout`.
- A creation `Sheet` carrying name, source language, and the optional description, with the existing counters,
  hints, and error messages preserved and translated.
- The `CreateVoice` contract gaining optional `description` + `ModelRef` and returning an optional `job_id`.
- A new voice-owned durable job kind `seed_voice`, its handler, its single analyze-stage completion, its
  source-language-aware prompt, and its empty-profile-guarded first-version publish.
- The new description ceiling as a config value owned by both sides, plus the new `voices` i18n strings.
- Automated coverage for row navigation vs. row controls, the sheet's create/seed paths, the seed's guard against
  overwriting real evidence, and the create-succeeds/seed-fails split.

### Non-goals

- No change to the server rules of `SetDefaultVoice`, `DeleteVoice`, or `RestoreVoice`. The default voice still
  cannot be deleted or re-defaulted, the last active voice still cannot be deleted, a delete is still refused while a
  voice-owned job, an undecided comparison/validation, or a publishable analyze experiment is outstanding, and
  restore still fails on an active-name collision.
- The description is **not** evidence and does not become one later. No sample row, no source count, no few-shot
  entry, no embedding, no corpus version bump, no effect on `can_validate`.
- No re-seed, re-describe, or "regenerate from description" RPC after creation. Seeding happens once, at creation,
  because the user submitted the sheet. Later work uses the existing 기존 글 가져오기 and finalization paths.
- No scheduled, background, or automatic AI ([I5], plan 03). Mounting `/voices`, opening the sheet, listing, and
  polling still make no provider call.
- No copying, inheritance, merging, or fallback between voices ([I4]). A seeded voice is seeded from its own
  description, not from another voice.
- No change to the observe or write stages, to generation, revision, post assignment, the five detail tabs, the
  profile editors, version restore, rules, or validation.
- No change to `source_language` immutability, and no new language.
- No native `<select>` anywhere; the language control stays the app-drawn `Listbox` ([design language](../../tech/design-language.md) §7).
- No hard delete, no voice-count cap, no new provider, no new migration to the `voices` table itself beyond what the
  job kind requires.

## Acceptance Criteria

1. `/voices` renders the active voices and one docked `새 말투 만들기` action, with no creation form on the page. At
   360 CSS px the first active row is visible without scrolling, and the page has exactly one scroller.
2. Tombstones appear only when at least one deleted voice exists, inside a collapsed disclosure that names the count
   and is closed on load; expanding it lists the deleted rows with `복원` on each row.
3. Pressing anywhere on an active row that is not one of its controls navigates to `/voices/$voiceId` for that voice.
   The name renders without an underline, the row exposes one link whose accessible name is the voice's name, and no
   interactive element is nested inside that link.
4. `기본으로 설정` and `삭제` render on the same row as the name and badges for a non-default active voice, and
   pressing either one performs its action and does **not** navigate. The default voice's row carries neither.
5. The voice name in `/voices/$voiceId` is renameable in place with the existing rules (1–50 scalar values,
   `AlreadyExists` on an active-name collision, a tombstone renameable so a restore conflict can be resolved), and
   the directory offers no rename affordance.
6. The docked action opens a sheet that, below `md:`, is a bottom sheet: full-bleed to the bottom edge, safe-area
   padded, scrim-dismissed, focus-trapped, `Escape`-closing, with the body as its only scroller. Its commit action
   sits **in flow directly after the last field**, not in the sheet's pinned footer: the panel is anchored to the
   layout viewport, which the software keyboard does not resize, so a pinned footer would sit behind the keyboard
   exactly while these fields are being typed into ([design language](../../tech/design-language.md) §8.3). Submitting
   name + language with an empty description creates the voice exactly as before and enqueues no job.
7. Submitting name + language + a description creates the voice, returns a `job_id`, closes the sheet, and lands on
   the new voice's detail screen with the run's progress visible. Exactly one durable `seed_voice` job exists for
   that voice, and exactly one provider completion is made, against the account's saved analyze-stage selection.
8. When the seed job succeeds, the voice's profile shows a first version with origin `seed`, a styleguide in the
   voice's declared `source_language`, and `ANALYZED` descriptors; its measured quantities and the six axes remain
   unknown rather than being measured from the description.
9. Seeding creates no `voice_samples` row, leaves `source_count`, `finalized_source_count`, `corpus_version`, the
   few-shot bank, and `can_validate` exactly as an unseeded new voice leaves them, and 기존 글 가져오기 lists no
   sample for the description.
10. A `seed_voice` job that resolves after a sample analysis or a finalization has already published a version for
    that voice completes without publishing and without failing; the real version stays head.
11. A provider failure, a truncated response, or a disabled model fails only the job: the voice exists, is selectable
    for a post, has an empty profile, and its 말투 tab shows the failure through the existing `FailureNotice`. No
    partial profile is written. There is no re-seed control, because re-seeding is a non-goal; the recovery path is
    the existing 기존 글 가져오기, and the failure notice is what says the described profile is not coming.
12. A description submitted with no resolvable analyze-stage model is refused with `InvalidArgument` and creates no
    voice; where the account has no usable analyze-stage selection, the sheet says so in the description field's
    message slot and creating without a description still succeeds.
13. A description longer than `VoiceDescriptionMaxChars` Unicode scalar values is refused by the server and reported
    in the sheet by the same counter/message shape the name field already uses; the ceiling is read from the owning
    config on each side and is not written inline.
14. A `seed_voice` job is voice-owned: it serializes against that voice's other personalization work, is refused for
    a deleted voice, blocks that voice's deletion while queued or running, and is swept at boot like every other
    durable job.
15. Every string introduced by this change is translated in both interface locales, and no user-facing copy contains
    an em dash.
16. Existing behavior is unregressed: creating without a description, renaming, setting a default, deleting,
    restoring, sample analysis, finalization learning, validation, generation, and post assignment all behave as
    before, and `pnpm lint`, `pnpm build`, the frontend tests, `go vet`, and the backend tests pass.
