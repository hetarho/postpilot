# 02. Change: Progressive Voice Personalization from Finalized Edits

> A **change proposal** (a WHAT delta) that modifies the already-shipped behavior of
> [plan/03.voice-profile-learning](../plan/03.voice-profile-learning.md). Plan 03 is the primary target because it
> owns the account-scoped voice profile and its prompt contract. The delta also changes the post editing,
> generation, revision, export, durable-job, and experiment surfaces shipped by plans 02, 05, 06, 07, 08, and 09.

## As-is

One account owns one voice profile with two free-form text fields: a machine-generated, user-editable `styleguide`
and user-owned `rules`. A user may paste a Korean sample of at least 200 characters and explicitly start an
`analyze_voice` job. Every sample change re-analyzes the account's full accumulated corpus and replaces the
styleguide with nine ordered prose sections, with Korean sentence endings first. The profile can be empty; an empty
profile warns but never blocks generation.

Generation receives the styleguide, up to three most-recent sample excerpts, and the free-form rules in that order.
The excerpts are selected by recency, not by similarity to the new post. Rules are exact lines: they have no layer,
evidence, contradiction, status, aging, or version history. An AI revision can optionally append its instruction as
a rule, but the system does not learn from what the user actually changed in the resulting prose.

The canonical post is a validated `PostContent` block array. The editor renders generated content read-only and can
replace it only through another AI generation, a model-experiment winner, or a whole-content AI revision. There is
no manual block editor, immutable machine-draft baseline, finalization record, sentence-level diff, content-versus-
style classification, or post/profile version history.

Export derives four formats in the browser and copies one to the clipboard. The user edits and publishes outside
postpilot, in the destination platform. Because that final text never returns to the app, postpilot cannot compare
the machine draft with the user's final prose. It never publishes, in accordance with [I1].

Plan 09 compares model choices for one pipeline stage at a time. Those experiments vary a `ModelRef`; they do not
validate one uncertain writing rule while holding every other input constant. There is no recurring or on-demand
profile validation workflow and no profile-version quality trend.

## To-be

### Zero-history bootstrap

Having no previous post is the primary supported starting state, not an error or an incomplete onboarding state.
The product must never require 30, 10, 3, or even 1 previous post before the user can generate their first draft.
No metric or preference is fabricated for an empty profile.

The first useful learning loop is:

```
empty profile -> generate -> edit the canonical blocks -> explicitly finalize and learn
              -> compare machine baseline with final text -> save the first authored example and evidence
```

Pasting an older post remains an optional shortcut for a user who already has one; its existing 200-character
validation remains scoped to that optional import action. There is no corpus-size prerequisite for analysis. The
numbers 30–50 are not an onboarding target or validation gate.

### Structured, versioned voice profile

The canonical profile becomes a typed, account-owned document rather than two opaque prose fields. Its externally
observable shape contains:

- `meta`: monotonically increasing profile version, update time, and the number of source posts analyzed;
- `lexical`: preferred words with alternatives and weight, banned words with reasons, and banned patterns;
- `endings`: base register, measured ending distribution, banned/signature endings, and constraints;
- `syntax`: sentence-length statistics, connective style and preferences, nominalization, and passive tendency;
- `structure`: intro/closing patterns, paragraph range, heading/list habits, and emoji use;
- `axes`: integer scores from -3 through +3 for involvement, narrativity, persuasion overtness, abstractness,
  addressee focus, and humor;
- `contrast_rules`: rule id, `LLM ... but I ...` statement, affected layer, evidence count, lifecycle status,
  evidence origin, and creation/last-evidence timestamps;
- `few_shot_bank`: finalized post id, title, tags, an authored excerpt capped at 800 characters (targeting 500–800
  only when the source is long enough), and an optional embedding reference; and
- `feedback_log`: source post, feedback kind (`diff`, `thumbs`, or `ab_test`), private payload reference, and
  processing state.

The four descriptive layers and axes are editable in human-readable controls. Manual changes create a new profile
version and are recorded as manual evidence; they never rewrite an older snapshot. Every effective profile change
stores an immutable whole-profile snapshot. Restoring an older snapshot creates a new head version, preserving the
history it restores from.

At zero evidence there is no persisted pretend-neutral profile: the API returns an explicit empty/unknown state.
Once evidence exists, weakly supported fields remain unknown instead of being guessed. Existing free-form
styleguide and rule text must migrate losslessly as manual guidance and continue to affect prompts until the user
explicitly edits, converts, or removes it; migration must not silently reinterpret prose as measured facts.

Every explicit import or finalization learning job rebuilds the evidence-derived portion from all currently eligible
authored sources, even when there is only one. The qualitative analyzer returns the typed profile shape, excludes
topic-specific domain vocabulary, and reports unknown rather than inventing weak traits. Deterministic sentence
segmentation and Korean morphological measurements supply ending distributions and sentence-length statistics;
those measured values override an LLM estimate. A successful result creates a new profile version. Explicit manual
field overrides stay effective until the user clears them and are never silently replaced by later analysis.

### Explicit finalization and edit-derived learning

The editor gains block-native manual editing while keeping `PostContent` as the only canonical content shape [I2].
The user can edit text-bearing fields and blocks and arrange valid blocks, but cannot create an image reference that
is not attached to the post. Manual edits autosave without destroying the immutable latest machine-produced
baseline used for learning.

Learning starts only when the user explicitly invokes **Finalize and learn**. Copying, opening an export tab,
loading a page, or the passage of time never starts model work. Finalization stores the current canonical content as
the final snapshot, ties it to the latest machine baseline, and enqueues durable learning work. Repeating the same
finalization is idempotent and cannot count the same edits twice. A later machine result establishes a new baseline;
later final prose can therefore produce a separate learning event.

Finalization means "this is the version I intend to copy". It does not publish, hold platform credentials, call a
platform API, or drive a browser [I1]. Existing browser-only format conversion remains derived from the finalized
block array.

The learning job aligns baseline and final text at sentence level and asks the analysis model to:

1. separate content changes from style changes and completely discard content changes;
2. emit at most three style rules;
3. require at least two same-kind edits in that one diff before emitting a rule;
4. phrase every emitted rule as `LLM does X, but I do Y`; and
5. return no rules when the evidence does not support one.

One qualifying finalization is one evidence event for a rule, even when the extractor cites multiple edits from
that diff. A new extracted rule begins as `candidate` with `evidence_count = 1`. A semantically matching rule found
in a later independent event increments the count and refreshes `last_evidence_at`; reaching 3 promotes it to
`active`. Only active rules participate in generation. A semantically contradictory observation never overwrites
an active rule: it creates an account-scoped confirmation item that shows the old and new behavior and waits for an
explicit user decision.

An active rule with no evidence for 180 days becomes `retired` and is excluded from prompts but retained in history.
Age is evaluated only as part of an explicit generation, finalization, rule-management, or validation action; there
is no timer, cron process, scheduled task, page-load mutation, or background model call. A user may inspect and
explicitly change rule status.

A finalization with no textual edits may offer a simple satisfaction control as auxiliary feedback. Satisfaction
alone cannot create or activate a contrast rule. Sentence-level negative feedback is available after the diff loop:
the user chooses `vocabulary`, `ending`, `length`, or `structure`, and the event is routed to that layer. A whole-post
rating is never the only feedback mechanism.

### Evidence-aware generation

Every explicit generation or revision renders the structured profile and legacy manual guidance, then injects:

1. the profile's descriptive layers and axes;
2. active contrast rules ordered by descending evidence, plus banned words, patterns, and endings; and
3. up to three topically similar authored excerpts from the few-shot bank.

The system uses every available excerpt when fewer than two exist, including zero for the first post. It never
blocks generation or duplicates an excerpt to pretend that 2–3 examples exist. Tag matching is sufficient while
the bank is small; embedding retrieval may replace it only after the configured corpus threshold and only within a
user-initiated operation. Example content and distinctive phrases must not be copied into the new post.

The writing prompt treats Korean endings as a first-class constraint, follows the measured ending distribution,
and prohibits the same ending three times consecutively. The user supplies a visible per-post `target_length` for
generation; the exact selected value is carried into the frozen input and writing prompt. Profile material remains
before per-post observations/topic, preserving the stable-prefix and observe-before-write contracts [I3].

### User-initiated rule comparison and profile validation

The "weekly A/B" idea from the source request becomes an **on-demand candidate-rule comparison**, with no calendar
cadence. When a candidate has one or two evidence events, its detail screen may offer **Compare this rule**. Nothing
runs until the user opens that action, chooses/confirms the source and model, and starts it.

The comparison produces two blind versions from one frozen input. Every byte of model, topic, profile, examples,
and prompt is identical except for the one candidate rule being tested. The UI places the versions vertically,
highlights only their differences, and asks one question: which version sounds more like the user? The verdict
updates or rejects that candidate only; it does not affect the model leaderboard because model identity was not the
variable.

The "monthly validation" idea likewise becomes an **on-demand profile validation**. It is unavailable until three
finalized authored posts exist. After an explicit start, it randomly selects three eligible posts, creates neutral 1–2
sentence topic summaries that contain no author wording or style description, regenerates from those summaries,
and presents original and regenerated versions side by side. The user may also explicitly enable an LLM judge that
scores ending forms, sentence-length rhythm, opening/closing structure, vocabulary habits, and addressee behavior as
Y/N while ignoring topic similarity. The Y ratio is stored against the profile version for a trend view.

Neither comparison nor validation is scheduled, pre-fetched, triggered by age/page load, or automatically charged.
All provider calls use an explicitly confirmed enabled model and all long work uses durable jobs [I3, I5].

### Staged and modular delivery

The full MVP, v2, and v3 behavior is in scope, but it is not one coupled release unit:

- **MVP foundation:** zero-history structured profile, profile versions, block editing/finalization, authored
  few-shot examples, evidence-aware generation, and profile editing;
- **v2 learning loop:** sentence diff, content/style separation, rule merging/lifecycle, confirmation queue, and
  sentence-level tagged feedback; and
- **v3 explicit validation:** on-demand single-rule comparison, on-demand neutral-summary validation, optional
  judge scoring, and profile-version trends.

The implementation job must preserve these boundaries in separate typed backend responsibilities, durable handlers,
API contracts, frontend feature slices, and focused tests. No single catch-all handler, component, or unvalidated
JSON mutation path may own the whole workflow. A later stage stays unavailable until its required earlier data and
contracts are valid; a failure in diff mining or validation cannot corrupt the last effective profile or finalized
post.

## Scope / Non-goals (regression boundary)

**In scope**

- Zero-previous-post onboarding and progressive learning from the user's own finalized posts.
- A structured five-layer profile, editable descriptors, evidence-aware contrast rules, full profile snapshots,
  and lossless migration of existing free-form guidance.
- Optional import of existing writing, without any minimum number of imported posts.
- A block-native manual editor, durable autosave of canonical content, immutable machine baselines, explicit and
  idempotent finalization, and private baseline/final snapshots for learning.
- Sentence alignment, content/style classification, rule extraction/semantic merge, lifecycle transitions,
  contradiction confirmation, and tagged sentence feedback.
- Similar authored-example retrieval, profile/rule/example prompt composition, and zero-example fallback.
- A visible per-post target-length input that is frozen with an explicitly started generation.
- User-initiated candidate-rule comparison and user-initiated three-post profile validation, including optional
  judge scoring and version trends.
- Account isolation, deletion/retention rules for private samples and learning payloads, restart-safe jobs, explicit
  model confirmation, failure recovery, and staged delivery gates.

**Non-goals / must not change**

- No automatic publishing, platform credentials, browser automation, or server-side platform conversion [I1].
- No requirement or recommendation to supply 30–50 historical posts. A user with zero previous posts is complete
  enough to begin.
- No scheduled weekly/monthly task, cron loop, timer-driven provider call, automatic page-load experiment, or other
  background AI execution. "Weekly" and "monthly" are removed as execution semantics.
- No shared, copied, or merged profile between accounts [I4].
- No HTML canonical content and no free-form editor that bypasses `PostContent` validation [I2].
- No topic/content edits used as style evidence, no source phrase copying, and no style-contaminated validation
  summaries.
- No multi-variable rule comparison and no rule-comparison outcome added to the model Elo leaderboard.
- No automatic reversal of an active rule after contradictory evidence and no deletion of retired rules or profile
  history.
- No provider-specific behavior above the `internal/llm` boundary, implicit model selection, blocking long RPC, or
  provider call inside a database write transaction [I3, I5].
- No weakening of image browser preprocessing [I6], embedded boot migrations [I7], current model experiments,
  AI revision, export formats, clipboard fallback, or existing account/post ownership rules.
- No dependency or NLP-library choice in this WHAT proposal. The implementation job must use the library-setup gate
  and current official documentation before adding a sentence splitter, morphological analyzer, or embedding SDK.

## Acceptance Criteria

1. An account with zero samples and zero finalized posts can generate a first post. The API/UI represents its profile
   as empty/unknown, makes no style claim, and neither requests nor recommends a historical-post minimum.
2. A user can edit the generated `PostContent` in the app, including its text-bearing blocks, while the canonical
   value remains a validated block array and no unattached image filename can be introduced.
3. Manual content edits autosave while the latest machine-produced baseline remains immutable. Explicit **Finalize
   and learn** stores a final snapshot and returns a durable learning job; opening/copying an export or loading the
   page does not start that job.
4. Retrying the same finalization or its job is idempotent: it creates no duplicate finalization, sample, feedback
   event, profile version, or rule evidence. A later machine baseline can be finalized as a distinct event.
5. The first finalized post becomes the first authored source and eligible few-shot excerpt. The next generation
   uses that one excerpt; generation with zero, one, two, or three available excerpts succeeds without duplication.
6. A non-empty canonical profile exposes the five required layers, six bounded axes, meta/version data,
   contrast-rule lifecycle metadata, few-shot entries, and feedback references. Endings are analyzed and rendered as
   a distinct primary layer rather than folded into vocabulary.
7. A one-source explicit learning run produces the typed profile without topic-specific preferred words; measured
   ending distribution and sentence-length values override conflicting model estimates, while unsupported traits
   remain unknown and existing manual overrides remain effective.
8. Editing a profile descriptor, resolving a contradiction, changing a rule state, applying new evidence, or
   restoring a snapshot creates a new immutable whole-profile version. Reload and rollback preserve every older
   snapshot and identify the current head.
9. Existing styleguide and rule content survives migration byte-for-byte as manual guidance, remains account-scoped,
   and continues to reach generation/revision until that account explicitly changes it.
10. A crafted finalization diff containing factual changes and repeated ending changes ignores all factual changes
   and emits at most three rules only for style patterns with at least two cited edits. A diff without such a pattern
   returns no rules.
11. A rule extracted from one qualifying finalization is `candidate/1`; two later independent matching evidence
    events produce `candidate/2` then `active/3`. Only the active rule appears in generation, ordered consistently
    with other active rules by evidence count.
12. Evidence that semantically contradicts an active rule leaves the active rule and current profile unchanged and
    creates a visible confirmation item. Only the owning user's explicit resolution creates the replacement profile
    version.
13. A rule whose last evidence is older than 180 days is excluded and retained as `retired` when the next explicit
    eligible request evaluates the profile. Advancing time alone runs no process and makes no provider call.
14. Sentence feedback requires one of vocabulary, ending, length, or structure and is logged against that layer. A
    no-edit satisfaction response is auxiliary and cannot independently create or activate a rule.
15. A generation prompt contains structured descriptors, bans, active evidence-ranked contrast rules, and up to
    three similar authored excerpts before per-post material; it contains no candidate/retired rule, carries the
    user's selected target length, and enforces the ending-distribution and no-three-identical-endings constraints.
16. Candidate-rule comparison starts only after a user action and explicit model confirmation. Its candidates share
    one frozen input and differ in exactly the selected rule; the blind verdict affects that rule only and creates no
    model-leaderboard match.
17. Profile validation is unavailable with fewer than three finalized posts. An explicit run uses three neutral
    summaries that reuse no author wording, presents original/regenerated pairs, and—only when explicitly enabled—
    stores the five-dimension judge Y ratio against the evaluated profile version.
18. No timer, scheduler, page load, copy action, profile age, or application boot starts rule comparison, profile
    validation, profile extraction, embedding, or judge work. Provider calls occur only within a user-initiated
    operation whose model is explicit, and long operations remain restart-safe server-side jobs.
19. Two accounts cannot read or influence each other's profiles, versions, samples, baselines, finalized snapshots,
    diffs, feedback, confirmation items, few-shot examples, comparisons, or validation scores.
20. Existing observe-before-write generation, AI revision, model-stage experiments, block validation, browser image
    preprocessing, platform converters, and clipboard fallback retain their current behavior; postpilot still never
    publishes.
21. MVP, v2, and v3 can be verified independently at their declared gates, and a failed later-stage job leaves the
    last valid canonical post and effective profile version unchanged.
