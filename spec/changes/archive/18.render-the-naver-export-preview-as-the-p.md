# 18. Change: Render the Naver export preview as the post with inline photo copy

> A **change proposal** (a WHAT delta) that modifies the already-shipped behavior of [plan/08.platform-export](../../plan/08.platform-export.md).
> Filled by /create-change through a user interview — a reviewable doc, not a one-line prompt.
> The STEPS live in the job that /create-change-job creates. Write it in English.

## As-is

The Naver tab of the export panel (job 44 / change 17) shows the copyable value itself: a read-only
auto-growing `Textarea` holding `toNaver`'s raw plain text, `[사진 <file>]` markers included, and —
below it, only when the post has photos — a separate horizontal **photo strip**: one 128px
`Thumbnail` tile per `[사진 …]` marker in marker order (`naverPhotoOrder`), each with the marker
filename and its own full-width `사진 복사` button beside the tile.

The owner's verdict after using it: this is not how the post reads. The human sees marker
placeholders where photos belong and has to match strip tiles against marker text by filename,
while the rest of the app (the reading view, 글 다듬기) already renders the same block array as a
natural post with photos inline between the paragraphs.

Mechanics that already exist and work: the body 복사 button copies `toNaver`'s exact string via
`copyText`, whose refusal fallback focuses and fully selects the mounted `Textarea`; each photo
copies through `shared/lib/clipboard/copyImage` (exactly ONE `ClipboardItem`, `image/png` only,
PNG handed over as a promise so the write spends the user activation before the fetch — the
measured SmartEditor/iOS contract); per-photo failures are named per kind (unsupported · refused ·
unreadable · missing), a `blob:` preview or missing photo offers no copy; all copies share one
generation counter, one queue, `COPY_FEEDBACK_MS`, and always-mounted live regions.

`entities/post`'s `BlockList` is the app's read-only rendering of the canonical block array
(text/headings/quotes/lists as styled text, images inline at their positions with captions), and it
already exposes `renderBlock` / `renderHeader` render-prop seams so a consumer can wrap a block
with its own affordance without the entity gaining one.

## To-be

The Naver tab's preview **is the post, not the wire text**. What the human sees is a natural
rendering; the `[사진 …]` markers exist only in what the copy button puts on the clipboard.

- **Rendered preview.** The Naver tab replaces the raw `Textarea` with the block array rendered
  the way the reading view renders it — paragraphs, headings, quotes, lists, and photos inline at
  their marker positions, captions shown. Only the **body** is rendered (no title/summary/tags
  header): the preview shows exactly what the body copy pastes, and the title has its own field.
  No `[사진 …]` marker text is visible in this default view.
- **Inline photo copy.** Each inline photo carries its own copy control **overlaid at the photo's
  top-right** — an icon-sized button on its own legible plane (job 44 measured that a 44px control
  covers a quarter of a 128px strip tile; an inline photo fills the column, so the same control
  covers a small corner and the objection no longer applies). Pressing it runs the existing
  `copyImage` contract unchanged (one item, `image/png` only, promise-passed bytes). The control's
  accessible name carries the marker filename, and per-photo copied/failure status renders at that
  photo with the existing kinds. A photo that cannot be copied (missing file, `blob:` preview,
  unreachable URL) renders a placeholder/disabled control with its reason instead of silently
  dropping the marker position.
- **Copied text unchanged.** The body 복사 button still copies `toNaver`'s output **byte-identical**
  — markers included. `toNaver` and its snapshot tests do not change.
- **Manual fallback still visible.** When the body copy is refused and falls back, the Naver tab
  reveals the raw marker text (the same read-only field as today), focused and fully selected, with
  the existing manual-copy hint — the fallback is never a silent no-op ([policy/export.md]).
  Copying again, switching tabs, or content changing dismisses it back to the rendered preview.
- **The photo strip is gone.** The separate strip section (heading, help line, carousel) is removed
  from the Naver tab; photo copying lives on the photos themselves.
- **Guidance matches the new flow.** The Naver guidance says: paste the body, then copy each photo
  from the preview and paste it at its `[사진 …]` marker — photo wording only when the post has
  photos, as today.
- **The other three formats are untouched.** Tistory / site / markdown outputs are markup meant to
  be read as source; they keep the raw `Textarea` and render no photos.

## Scope / Non-goals (regression boundary)

**In scope**

- `widgets/export-panel`: Naver-tab presentation (rendered preview via `entities/post` `BlockList`
  with `renderBlock` overlay, photo-copy controls, fallback reveal, strip removal, guidance copy).
- `spec/policy/export.md` *Clipboard and UI*: the strip rule is replaced by the inline-control rule.
- i18n strings for the changed guidance/labels (ko + en).

**Must NOT change (regression boundary)**

- `toNaver` / `naverPhotoOrder` output and tests — the copied string stays byte-identical.
- The image clipboard payload contract: one `ClipboardItem`, `image/png` only, bytes as a promise,
  no text flavor ([I1] text output stays the fallback). `copyImage` itself does not change.
- Copy-state discipline: one generation counter, one serialized queue, `COPY_FEEDBACK_MS` dwell,
  always-mounted live regions, per-target feedback.
- Title field + title copy; the other three formats' output, presentation, and guidance.
- Export stays read-only and browser-only: no lifecycle mutation, no network work in converters,
  no presigned URL in any copied text.
- Bulk photo download stays out (unchanged PRD gap).

## Acceptance Criteria

1. The Naver tab's default view renders the block array as a natural post — text, headings, quotes,
   lists, captions, and photos inline in marker order — and contains no visible `[사진 …]` marker
   text and no raw-text `Textarea`.
2. Each copyable inline photo shows a copy control overlaid at its top-right; pressing it places
   exactly one `ClipboardItem` carrying `image/png` only (payload contract unchanged), and the
   confirmation/failure renders at that photo with the existing kinds.
3. The body 복사 button copies `toNaver`'s exact output, markers included — byte-identical to
   before this change (converter snapshots unchanged).
4. When the body copy falls back to manual, the raw marker text appears focused and fully selected
   with the manual-copy hint; a subsequent copy, tab switch, or content change returns the tab to
   the rendered preview.
5. A photo that cannot be copied (missing image, `blob:` preview, failed load) holds its inline
   position with a disabled/absent control and a stated reason — later photos do not shift against
   their markers.
6. The photo strip section no longer renders anywhere; Tistory, site, and markdown tabs keep their
   read-only `Textarea` presentation and identical output.
7. The Naver guidance line describes the inline flow, with photo wording only when the post has
   photos.
8. Copy operations keep the shared generation/queue discipline: a stale async result cannot label
   the wrong target, and two presses do not race the clipboard.
