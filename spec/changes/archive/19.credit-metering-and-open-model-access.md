# 19. Change: Credit Metering and Open Model Access

> A **change proposal** (a WHAT delta) that modifies the already-shipped behavior of [plan/17.plan-based-authorization-and-usage-quota](../../plan/17.plan-based-authorization-and-usage-quota.md).
> Filled by /create-change through a user interview — a reviewable doc, not a one-line prompt.
> The STEPS live in the job that /create-change-job creates. Write it in English.

## As-is

Plan 17 (job 37) bounds every account along **three independent numeric axes** plus a **model floor**, all
denominated in raw provider cost. An account carries one of four plans (`free < basic < max < master`); the limits
table in `backend/internal/plan` gives each tier a daily job-start count, a daily budget and a monthly budget in
micro-USD, and `master` carries zeros meaning unlimited. Windows are the calendar day and calendar month in a
fixed `Asia/Seoul` zone.

Admission is a single `BEGIN IMMEDIATE` transaction at the shared enqueue seam. It asks, in order: may this tier
run these models, then the daily start count, then today's spend, then the month's. The count axis reads
`usage_admissions`; both budget axes are `SUM(cost_microusd)` over `usage_events`, the append-only ledger written
at the llm boundary for every server-side call. A refusal writes nothing and creates no job row.

**Model access is a second, parallel authorization mechanism.** Each registry model declares `min_plan:
free|basic|max` in `config/providers.yaml` as a required field validated at boot, and the server enforces that
floor on every ref-accepting RPC — starting a job (including a write comparison's observe model and the stored refs
a retry re-runs), saving a selection, saving a comparison pair, applying a recommendation set. `ListModels.locked`
lets pickers disable a model, a refusal is `permission_denied` with reason `MODEL_LOCKED` carrying the required
tier, and a saved selection that a downgrade locked is reported missing while its row is preserved so an upgrade
restores it. This floor machinery currently spans roughly 52 sites across the backend and the frontend.

Enforcement is admission-only and **bounded overshoot is accepted**: a window may exceed its budget by the cost of
the jobs already in flight when it filled, and nothing is killed mid-flight ([I5]). That bound is unbounded in one
direction the plan did not model — **there is no cap on how many photos a post may hold.** Observation batches
four photos per call, so a single generate job issues `ceil(photos / 4)` observation calls before its write call.
At Claude Opus 5 pricing a forty-photo post costs about $2.72 in one admission, and a profile validation (three
samples × three calls plus summaries) about $2.94. An account with one micro-USD of headroom can therefore start
work that overshoots by nearly three dollars.

`GetMyPlan` publishes the tier, all three limits, live usage and both reset instants; the app shell shows a plan
badge whose panel renders three meters. There is no upgrade, purchase or checkout affordance anywhere — the plan
ladder is shaped like a subscription but no money moves, and accounts remain operator-provisioned with no signup
surface (plan 01).

## To-be

Usage is metered in **credits**, and a credit is the only axis. One credit is a product-fixed $0.01 of *list*
value; it is a billing unit, not a cost measurement, and the ledger keeps recording true provider cost in
micro-USD underneath it unchanged.

### The ladder

Five rungs, `free < basic < pro < max < master`. A tier now decides exactly two things: **how many credits are
granted each month**, and — for `master` alone — access to the master-only publishing and admin procedures. It
decides nothing else.

| Plan     | Monthly credits | Intended monthly price | Master surfaces |
| -------- | --------------- | ---------------------- | --------------- |
| `free`   | 50              | —                      | —               |
| `basic`  | 200             | $2                     | —               |
| `pro`    | 500             | $5                     | —               |
| `max`    | 1000            | $10                    | —               |
| `master` | unlimited       | —                      | ✅              |

The prices are recorded here as the product intent the credit grants are sized against; **this change moves no
money and builds no checkout.** `master` is metered but never refused: its calls are held, recorded and settled
exactly like everyone else's, and only the balance check is skipped, so the operator's spend stays readable.

### What a request costs

One formula, applied per job, code-owned in `backend/internal/plan` beside the grant table:

```
credits = BASE + ceil(actual_cost_usd × 100 × MULTIPLIER)      BASE = 2, MULTIPLIER = 3
```

`BASE` recovers the per-request infrastructure cost a pure cost multiple cannot see (storage, database, worker) and
keeps a near-free model from being effectively unmetered. `MULTIPLIER` covers the OpenRouter top-up fee, card PG
fees, VAT and gross margin; at these values the margin holds between roughly 61% and 68% across every tier and
model, assuming full credit consumption. Both are single named constants, not env config, so two deploys can never
disagree about what a request costs.

The resulting economics, for a post of eight photos (two observation calls plus one write call):

| Model pair                          | Provider cost | Credits | free 50 | basic 200 | pro 500 | max 1000 |
| ----------------------------------- | ------------- | ------- | ------- | --------- | ------- | -------- |
| GLM 5.3 Flash + DeepSeek V4 Flash   | $0.0023       | 3       | 16      | 66        | 166     | 333      |
| Gemini 3.7 Flash + GPT-5.6 Luna     | $0.026        | 10      | 5       | 20        | 50      | 100      |
| Gemini 3.7 Flash + Claude Sonnet 5  | $0.069        | 23      | 2       | 8         | 21      | 43       |
| Claude Opus 5 for both stages       | $0.256        | 79      | —       | 2         | 6       | 12       |

### Credit lots

Balances are **lots**, not counters: one row per grant, carrying what was granted, what remains, and when it
expires.

```
credit_lots(id, user_id, kind, granted, remaining, expires_at, created_at)
  monthly → kind='monthly', expires_at = the next renewal instant
  bonus   → kind='bonus',   expires_at = an explicit instant, or NULL for no expiry
```

Consumption walks lots by **`expires_at` ascending, NULLs last**, then by `created_at`. Because a monthly lot
always expires before a non-expiring bonus, "spend the monthly grant first, then the bonus" falls out of that one
ordering rule rather than existing as a second rule — and a promotional grant with its own deadline needs no new
mechanism. A lot whose `expires_at` has passed contributes nothing to the balance; expiry is a read-time
predicate, so no scheduled job has to run for a balance to be correct.

Monthly renewal is **computed on access, not on a timer**. When a request finds the account's renewal instant in
the past, it closes the stale monthly lot and opens a fresh one inside the same write transaction. A server that
was down at midnight, and accounts whose renewal days differ, both stay correct without a sweeper.

### Holds and settlement

Admission changes from "check a window, then record" to a **two-phase hold**.

1. **Hold.** At the enqueue seam the gate computes the job's worst case — for every call the work will make, the
   estimated input tokens at the model's input price plus `LLMMaxTokensDefault` at its output price — runs it
   through the same `BASE + ceil(cost × 100 × MULTIPLIER)` formula, and deducts that many credits from the lots in
   consumption order, inside the existing `BEGIN IMMEDIATE` transaction. An insufficient balance is refused with
   no job row, exactly as a quota refusal is today.
2. **Settle.** When the job reaches a terminal state the hold is reconciled against what the ledger actually
   recorded for it, and the difference is returned to the lots it came from. A job that fails after spending
   tokens settles at what it spent. A job whose row failed to insert releases the whole hold, on a context that
   outlives the caller's cancellation, exactly as an admission is released today.

Settlement is what makes the worst-case hold acceptable: an eight-photo Opus post holds far more than it will use,
but gets the remainder back within the minute, and the worker is single-consumer so holds cannot pile up.

**A balance can never go negative.** This is the property the change exists to guarantee, and it replaces bounded
overshoot as the accepted posture for the credit axis. The ledger's own bounded overshoot in micro-USD is
unaffected — provider cost is still only knowable after a call returns — but it is now absorbed by the hold rather
than by the account.

### Balance-based model access, and the end of model floors

`min_plan` is **removed** from the registry, from `config/providers.yaml`, and from every RPC that enforces it.
Every account may select every model. The floor was always a second answer to a question the budget already
answered, and with credits proportional to true cost it answers it exactly: a `free` account cannot run Opus
because 79 credits do not fit in 50, not because a table says so.

What replaces it is the hold itself. A model whose hold exceeds the current balance is refused, and `ListModels`
reports — per model, for the caller — the hold that model would require and whether the balance covers it, so a
picker can disable it and say why. The distinction that matters: a floor refusal was **permanent until upgrade**,
so a downgrade-locked selection had to be preserved rather than deleted; a balance refusal is **temporary until
renewal**, so a saved selection is never invalidated by it and needs no preservation rule at all.

Refusals become `resource_exhausted` with reason `INSUFFICIENT_CREDITS`, carrying `required`, `balance` and
`renews_at`. `MODEL_LOCKED` and `required_plan` are retired with the floors.

### What the user sees

- The plan badge's three meters become **one balance**: credits remaining, the renewal instant, and the lots
  behind it when opened (the monthly grant and each bonus with its own expiry).
- The model picker shows, per selectable pair, **"about N posts with your remaining credits"** — the balance
  divided by that pair's estimated per-post credits. The estimate uses the account's own recent history from
  `usage_events` (its median photo count and token volume per stage) and falls back to a product default when the
  account has no history yet. It is labelled an estimate.
- An exhausted balance **blocks every LLM-consuming action** and sends the user to a **plan comparison screen**
  listing the four tiers, their credit grants and their intended prices. Each tier's action is the place a
  checkout will later attach; until payments exist it states that plans are operator-assigned and does not pretend
  to sell anything. Everything that does not consume LLM work — writing, editing, exporting, reading posts —
  keeps working with a zero balance.

### Provisioning

`api adduser <id> [--plan=<tier>]` opens the account's first monthly lot **and**, for a `free` account, a 50-credit
signup bonus lot, in the same transaction that creates the user. A new `api grantcredits <id> <amount>
[--expires=<RFC3339>]` opens a bonus lot on an existing account. `api setplan` and the master-only `SetUserPlan`
keep changing tiers; a tier change re-sizes the **next** monthly lot and never retroactively edits the current one.

### Photo ceiling

A post accepts at most **30 photos**, enforced server-side at upload and surfaced in the browser's selection gate
so the user learns of it before converting files. This caps a generate job at eight observation calls and makes
the worst-case hold a computable number instead of an open one.

## Scope / Non-goals (regression boundary)

**In scope**

- The `pro` rung, and the redefinition of a tier as a monthly credit grant plus (for `master`) the admin surfaces.
- `credit_lots` and its consumption ordering, expiry-as-predicate, and access-time monthly renewal.
- The `BASE + ceil(cost × 100 × MULTIPLIER)` charge formula as code-owned product constants.
- Two-phase hold and settlement at the existing enqueue seam and terminal-state transitions, including release of
  a hold whose job row failed to insert.
- Removal of the three numeric axes (daily starts, daily budget, monthly budget) and of the `Limits` table they
  were read from.
- Removal of `min_plan` from the registry, `providers.yaml`, boot validation, every ref-accepting RPC, and
  `ListModels.locked`; removal of the downgrade-preserved-selection rule.
- `INSUFFICIENT_CREDITS` as a typed refusal carrying `required`, `balance`, `renews_at`; retirement of
  `MODEL_LOCKED`.
- `GetMyPlan` returning balance, lots and renewal instant; `ListModels` returning per-model required credits and
  affordability for the caller.
- The plan badge's balance panel, the per-pair "about N posts" estimate, the blocked-state plan comparison screen.
- The 30-photo ceiling, server-side and in the browser selection gate.
- `adduser` opening the first monthly lot and the free signup bonus; `grantcredits`; `setplan` re-sizing the next
  monthly lot.
- A migration that creates `credit_lots`, adds `pro` to the plan `CHECK`, and opens an initial monthly lot for
  every existing account ([I7]).

**Non-goals**

- **No payments.** No PG integration, no checkout, no subscription lifecycle, no invoices, no proration, no
  refunds. The plan comparison screen ends at the point a checkout would begin.
- **No signup.** Accounts stay operator-provisioned (plan 01); the free bonus rides `adduser` precisely because
  there is no registration surface to hang it on. No multi-account abuse defense is designed here, because there
  is no self-service account creation to abuse.
- No change to `usage_events`: the same row per LLM call, the same recording point at the llm boundary, the same
  `reported → estimated → unavailable` cost resolution, the same append-only posture, the same micro-USD storage.
  Credits are computed *from* the ledger; they do not replace it.
- No change to the master-only procedure set, the auth interceptor's closed-by-default pattern, the last-master
  guard, or the agent bearer path ([I1]).
- No mid-flight cancellation. A held job runs to completion ([I5]); the hold, not a kill switch, is what bounds
  the account's exposure.
- No model substitution or automatic downgrade. A refusal names what the choice would cost and stops; it never
  quietly runs a cheaper model ([I3]).
- No change to observe/write separation, the block canon ([I2]), voice isolation ([I4]), or the browser image
  pipeline ([I6]) beyond the count ceiling.
- No metering of non-LLM resources (storage, uploads, publish jobs). The paired agent's local publisher performs
  no inference and stays unmetered.
- No retroactive credit reconstruction for work done before this change; lots start at the migration.
- No per-model or per-stage multipliers. One `BASE` and one `MULTIPLIER` for every model, so margin variation
  across models is accepted rather than tuned away.

## Acceptance Criteria

1. An account's balance is the sum of `remaining` over its unexpired lots, and consumption draws from lots ordered
   by `expires_at` ascending with NULLs last; a monthly lot is therefore exhausted before a non-expiring bonus.
2. A request arriving after the renewal instant closes the stale monthly lot and opens the tier's new one in the
   same write transaction, with no scheduled job involved, and the caller sees the renewed balance on that request.
3. Starting an LLM-consuming job deducts a hold computed as `BASE + ceil(worst_case_cost × 100 × MULTIPLIER)`,
   where the worst case prices every call the work will make at its estimated input tokens plus the configured
   completion cap; the deduction and the job row are one `BEGIN IMMEDIATE` transaction.
4. Reaching a terminal state settles the hold against the ledger's recorded cost for that job and returns the
   difference to the lots it was taken from; a job that fails after spending tokens settles at what it spent, and a
   job whose row failed to insert releases the whole hold on a context that outlives the caller's cancellation.
5. **No sequence of operations leaves a balance below zero**, including two concurrent starts that each read the
   same balance, and including a job whose actual cost exceeds its own hold.
6. A start whose hold exceeds the balance is refused `resource_exhausted` / `INSUFFICIENT_CREDITS` carrying
   `required`, `balance` and `renews_at`, writes nothing, and creates no job row.
7. `min_plan` no longer exists in `providers.yaml`, the registry, boot validation, or any RPC; a `free` account may
   select and save any model, and is refused only when its balance cannot cover the hold. `MODEL_LOCKED`,
   `required_plan` and `ListModels.locked` are gone, and no saved selection is invalidated by a tier change.
8. The daily start count, the daily budget and the monthly budget are gone: no code path reads them, and an
   account may spend its whole monthly grant within one day.
9. `master` is held, recorded and settled like every other tier but is never refused for balance, and its usage
   remains readable through the same surfaces.
10. `GetMyPlan` returns the balance, the individual lots with their expiries, and the renewal instant; the plan
    badge renders them, and the frontend hardcodes no credit figure.
11. `ListModels` reports, per model and for the calling account, the credits a job with that model would require
    and whether the balance covers it; the picker disables what is unaffordable and states the required credits.
12. The model picker shows an "about N posts" estimate per selectable pair, derived from the account's own recent
    `usage_events` history where it exists and a product default otherwise, and labelled as an estimate.
13. A zero balance blocks every LLM-consuming action and routes to a plan comparison screen listing all four tiers
    with their credit grants and intended prices; writing, editing, exporting and reading posts remain fully
    usable at a zero balance.
14. A post cannot exceed 30 photos: the server refuses the upload that would cross it, and the browser's selection
    gate reports the excess as skipped before any file is converted or sent.
15. `adduser` opens the first monthly lot for the tier and, for `free`, an additional 50-credit signup bonus lot,
    in the account-creating transaction; `grantcredits <id> <amount> [--expires]` opens a bonus lot on an existing
    account; `setplan` re-sizes the next monthly lot without editing the current one.
16. The migration creates `credit_lots`, admits `pro` into the plan `CHECK`, and opens an initial monthly lot for
    every pre-existing account; it runs embedded at boot and a failure kills the process ([I7]).
17. No regression: the master-only procedure set and its refusals, the last-master guard, the agent bearer path,
    `usage_events` recording at the llm boundary with its existing cost resolution, and the job-queue contract
    ([I5]) all behave exactly as before.
