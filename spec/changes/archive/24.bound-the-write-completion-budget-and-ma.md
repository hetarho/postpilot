# 24. Change: Resolve reasoning per purpose and bound the completion budget per stage

> A **change proposal** (a WHAT delta) that modifies the already-shipped behavior of [plan/04.model-provider-registry](../../plan/04.model-provider-registry.md).
> Filled by /create-change through a user interview — a reviewable doc, not a one-line prompt.
> The STEPS live in the job that /create-change-job creates. Write it in English.

## As-is

Change 07 → job 23 gave the port a reasoning intent, resolved per stage and overridable per model, and raised the
shared completion cap to 8,192. Its measurement still holds: on 2026-08-30, sending `{effort: low}` collapsed one
write call's reasoning from 13,932 tokens to 26 and produced *better* output (4,205 characters against 487) for a
fifth of the cost. Raising the budget alone made things worse, not better.

What that change could not settle is that the seam is **stage-aware in the code-owned half and stage-blind in the
operator-owned half**, and that the budget they share is a single constant.

### The override is per model, the policy is per stage

`LLMReasoningPolicy` is per stage — observation asks `low`, writing and revision ask `low`, analysis deliberately
supplies nothing so the request body carries no `reasoning` key at all. The operator's override is not: change 20
made *registration* per purpose (`catalog_model_purposes`), but `reasoning_effort` stayed a column on
`catalog_models`, one value for the whole model. The admin row says so in its own words — the checkbox "acts on the
active tab's purpose only", while the reasoning control beside it is "the **shared** per-model reasoning override".

So a model registered to both 사진 해석 and 글 작성 has exactly one effort for both, and the five purpose tabs each
present that one value as though it belonged to the tab. **On 2026-09-03 an operator lowered the effort on the 글
작성 tab and silently changed photo observation**, which is a different task with a different model policy. The
resolution order the plan documents — model override → stage value → nothing sent — means the model-wide override
also erases the per-stage distinction the code policy exists to express.

### An effort a model does not understand is worse than no effort

That same edit set `minimal` on all eight curated models. `z-ai/glm-5.3-flash`, whose observation calls had been
producing 647–733 completion tokens under the stage default `low`, then produced **8,192 — the cap** — on an
identical 4,304-token prompt, and the job failed as truncated at the observation stage. Because an A/B run observes
once and compares writers over that snapshot, both candidates surfaced the single failure as their own error.

The behavior matches the "no effort sent" rows of change 07's table (3,609 and 13,932 reasoning tokens, `length`,
unusable) rather than a weaker `low`. `minimal` is an OpenAI-dialect value; a family that accepts only
`low`/`medium`/`high` does not clamp an unknown effort to the nearest one, it drops the constraint — and an
unconstrained reasoning model runs to the cap. The catalog cannot prevent this by validation: OpenRouter's
`supported_parameters` (already read for `structured_outputs`) says whether a model accepts `reasoning_effort`, never
which **values** it honors. Only measurement can tell, and today nothing measures it.

### Nothing records where a completion budget went

`llm.Usage` carries prompt tokens, completion tokens and cost; the adapter parses exactly those three. OpenRouter
reports reasoning tokens separately and the adapter drops the field, so `usage_events` cannot distinguish "wrote
8,192 tokens of post" from "spent 8,192 tokens thinking and wrote nothing". Both 09-03 investigations had to infer
that split from an empty body. A model disregarding its effort is therefore invisible until it fails a user's work.

### The budget is one constant shared by every call

`llmMaxTokensDefault` is the typed constant `8192`. No caller anywhere sets `Request.MaxTokens` — the only assignment
is the registry's fallback — so every observation, writing and revision call runs under the same cap, and reasoning
and visible output share it. The cap is also unrelated to how long a post was asked to be: `TargetLength` reaches the
prompt and nothing else, so a 1,500-character target and a 5,000-character target get the identical budget. **A
failed write costs more than a successful one**, because it bills the full cap: the two 09-03 write failures spent
44,917 of the 52,473 microusd wasted that day and produced nothing.

### The rate-limit framing is stale

Plan 04's acceptance criterion 8 explains `ErrRateLimited` as "PRD §7: 무료 모델 한도 초과", `llm/errors.go` comments
the sentinel as "the free-tier daily limit case", and PRD §6.5 and §7 are written for a product where the user picked
free models from a dropdown. Plan 18 moved the usable list into curated `catalog_models` rows and change 19 made
credits the only gate. The 09-03 rate limit arrived as **HTTP 200 with an upstream `code: 429`** on
`google/gemini-3.7-flash`, a row priced at $0.75/$3.75 per million — nothing free anywhere in the path. The
user-facing copy is already neutral and correct; it is the comment and the doc prose that assert a cause that is no
longer true.

**Already correct, and named here so the change does not "fix" it:** a non-empty body cut off mid-JSON is *already*
a named truncation. `responseParseError` turns any parse failure with `finish_reason == "length"` into
`ErrOutputTruncated`, and both the write and observation paths route through it. Plan 04's acceptance criterion 12 is
met.

## To-be

**Reasoning effort is resolved per purpose.** The operator's override moves to where registration already lives —
one effort per (model, purpose) — so the same model can observe photos at one strength and write at another. Each
purpose tab in 모델 관리 shows and edits **its own** value, and editing one purpose changes nothing about any other.
The resolution order is unchanged in shape and gains the missing dimension: the override for *this purpose* → the
stage value → nothing sent.

**Analysis keeps sending nothing by default, and may be bound.** 문체 분석's default stays "no `reasoning` key",
which is not "reasoning off" but "the model's own adaptive behavior", the most permissive setting available — the
09-03 measurements show unconstrained reasoning producing the *most* tokens, and analysis calls have been small and
successful throughout. The per-purpose override may still set an effort there, so an analysis model that one day runs
away can be bounded without a deploy. The default is not changed by this change.

**Existing model-wide overrides are cleared at deploy.** The migration does not copy the current values forward:
every override becomes empty and every model returns to the code-owned stage policy (observation `low`, writing and
revision `low`, analysis nothing). That is the configuration measured working before 09-03, and carrying today's
blanket `minimal` into five purposes each would propagate a setting already known to break observation.

**The completion budget is derived per stage, not shared.** A stage asks for the budget its work needs. The writing
stage's budget accounts for the post's requested length when it has one, so asking for a longer post raises the
ceiling instead of meeting the same wall; observation, whose per-photo output is small and bounded, does not need the
writer's headroom. The registry's fallback remains for a caller that expresses no need, and the cap stops being a
bare constant: it becomes a value its owner (`backend/internal/platform/config`) resolves, so an installation that
has measured its own models can change it without a code edit.

**Reasoning spend is recorded and surfaced.** The port's usage carries the provider-reported reasoning token count,
the adapter parses it alongside the tokens it already reads, and the ledger stores it. A provider that reports
nothing yields zero, which keeps meaning "not reported". The curation surface shows, per model and per purpose, that
a model is spending its budget on reasoning while its resolved effort says otherwise — so the 09-03 failure mode is
visible to an operator before it fails a user's generation, which is the only reliable check available given that
`supported_parameters` cannot enumerate accepted values.

**Budget exhaustion says which half consumed the budget.** When a call fails as truncated and the provider reported
reasoning tokens, the technical detail names the split, so the remedy — lower this purpose's effort, or pick another
model — follows from the message rather than from a database query.

**The free-tier framing is retired** wherever it asserts a cause. `ErrRateLimited` means the provider refused for
rate reasons, whether that is the user's quota, the account's, or the gateway's upstream pool. No user-facing string
changes.

**Reasoning effort stays operator-owned.** Per-purpose curation in 모델 관리 remains the only place effort is
decided. A per-user control was considered and rejected: the 08-30 and 09-03 measurements together show the right
effort is a property of the *model and the task* (`low` restrained one model to 26 tokens, left another at the cap,
and `minimal` broke a third), not a user preference, and a user has no way to observe the difference — the A/B
surface varies models, not effort.

## Scope / Non-goals (regression boundary)

**In scope**

- Moving the reasoning override from `catalog_models` to a per-(model, purpose) value, with the migration clearing
  existing values rather than copying them.
- The resolution order gaining the purpose dimension: this purpose's override → stage value → nothing sent.
- Every execution boundary resolving the override for the purpose it is running (observe → `photo-analysis`,
  write/revise → `writing`, analyze → `style-analysis`), including the A/B candidate path.
- 모델 관리: each purpose tab showing and editing its own effort, with the control scoped to that tab.
- A per-stage completion budget, the writing stage's derived from the post's requested target length when set, with
  the registry fallback retained; the cap moved to a config-owned, deployment-resolvable value.
- `llm.Usage` gaining a provider-reported reasoning token count, the adapter parsing it, and the ledger persisting
  it.
- Surfacing reasoning spend per model and purpose where models are curated.
- Naming the reasoning/visible split in the truncation failure's technical detail when the provider reported it.
- Retiring the free-tier explanation of `ErrRateLimited` in `llm/errors.go`, plan 04's acceptance criterion 8, and
  the PRD §7 row.
- Automated coverage for every item above, plus the regressions named below.

**Non-goals — these must NOT change**

- **Per-user reasoning selection.** Effort stays operator-curated, for the reasons stated above.
- **The stage reasoning policy's values.** Observation and writing/revision keep asking `low`; analysis keeps
  supplying nothing. Retuning a stage default is a measurement, not this change.
- **Validation of effort values against a model.** `supported_parameters` cannot enumerate accepted values, so the
  change adds measurement, not a whitelist, and never silently substitutes an effort the operator did not choose.
- **The non-empty truncation path.** `responseParseError` already satisfies plan 04's acceptance criterion 12.
- The `unset` sentinel, the `reasoning_format` provider opt-in, and the standing ban on `reasoning.exclude`.
- Purpose registration itself: which purposes exist, the capability gates, and `SetModelPurpose`'s meaning.
- The normalized error set and every user-facing error string, `MODEL_RATE_LIMITED`'s copy included.
- Cost and credit arithmetic: reasoning tokens are recorded for diagnosis, not re-priced.
- Invariants [I1]–[I7] hold; in particular [I3] — every model choice stays explicit, and nothing here substitutes a
  model or an effort on the operator's behalf.

## Acceptance Criteria

1. The same model registered to both 사진 해석 and 글 작성 holds two independent efforts, and each purpose's
   execution boundary sends its own — a post generation observes at the photo-analysis effort and writes at the
   writing effort in one run.
2. Editing the effort on one purpose tab leaves every other purpose's effort for that model unchanged (the 2026-09-03
   regression, asserted directly).
3. Resolution per purpose is override → stage value → nothing sent: an empty override falls through to the stage
   policy, and `unset` still emits no wire key.
4. The migration clears every existing override; after it, all curated models resolve to the code-owned stage policy
   and no row carries the pre-migration blanket value.
5. 문체 분석 sends no `reasoning` key by default after the migration, and an operator setting an effort there causes
   it to be sent.
6. The writing stage's completion budget is derived from the post's requested target length when one is set, and a
   longer requested draft is sent a larger budget (unit test over the derivation, not a provider call).
7. A caller that sets no budget still receives the registry's configured fallback, and the observation stage's budget
   is independent of the writer's.
8. The completion cap is resolved by `backend/internal/platform/config` as a deployment-settable value with `8192` as
   its default, and an invalid value is refused the way the other LLM config values are.
9. `llm.Usage` carries a reasoning token count; the adapter populates it from a provider that reports one and leaves
   it zero for a provider that does not, with no other usage field affected.
10. A generation call's `usage_events` row records the reasoning token count alongside the tokens and cost it already
    records.
11. A model spending most of a completion budget on reasoning is identifiable by an operator from the curation
    surface, per purpose, without reading the database and without waiting for a user's job to fail.
12. A truncation failure whose provider reported reasoning tokens names the reasoning/visible split in its technical
    detail; one whose provider reported none keeps today's message.
13. `llm/errors.go`, plan 04's acceptance criterion 8, and the PRD §7 rate-limit row no longer attribute
    `ErrRateLimited` to a free tier, and no user-facing string changed.
14. Regression: a non-empty body cut off mid-JSON is still `ErrOutputTruncated` through `responseParseError`, for
    both the write and observation paths.
15. Regression: `reasoning.exclude` is still never sent, `reasoning_format` still gates the nested object, and
    purpose registration and its capability gates are unchanged.
