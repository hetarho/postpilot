# 27. Change: Persist catalog reasoning capabilities and constrain the effort override

> A **change proposal** (a WHAT delta) that modifies the already-shipped behavior of [plan/18.openrouter-model-catalog-and-admin-model](../../plan/18.openrouter-model-catalog-and-admin-model.md).
> Filled by /create-change through a user interview — a reviewable doc, not a one-line prompt.
> The STEPS live in the job that /create-change-job creates. Write it in English.

## As-is

The catalog reads one entry out of OpenRouter's `supported_parameters` array — `structured_outputs` — and
[tech/openrouter-catalog](../../tech/openrouter-catalog.md) declares every other field ignored. The reasoning override
the operator sets beside it is therefore chosen with **no knowledge of what the model accepts**.

Change 24 wrote the reason down: "`supported_parameters` says a model accepts `reasoning_effort` but never which
values it honors." That was true of the field it was looking at. The same response also carries a **top-level
`reasoning` object** that names them exactly, and the field table in the tech doc never listed it.

### What the source actually publishes

Measured against the live endpoint on 2026-09-05 (427 models for the three requested modalities):

| Field | Present on | Meaning (OpenRouter's own words) |
|---|---|---|
| `reasoning` (the object) | 300 models | the model reasons at all |
| `mandatory` | 300 (97 `true`) | "When `true`, hide disable controls and do not send `effort: \"none\"`" |
| `supported_efforts` | 154 | "Filter effort selectors to these values, returned in descending effort order" |
| `default_effort` | 154 | pre-selected effort when reasoning is enabled |
| `default_enabled` | 134 | "Default on/off state when the user has not set `reasoning.enabled`" |
| `supports_max_tokens` | 10 | "When present and `true`, show a token budget control" — never published as `false` |

`supported_parameters` additionally distinguishes a model that takes `reasoning_effort` **natively** (157 models)
from one whose effort OpenRouter converts into a token percentage. Nothing in the product records that difference,
and [change 29](../29.give-the-write-budget-reasoning-headroom.md) cannot size a budget safely without it.

### What the unconstrained control already permits

[types.ts:76](../../../frontend/src/entities/model-catalog/model/types.ts#L76) offers the same eight values for every
model, [service.go:340](../../../backend/internal/modelcatalog/service.go#L340) validates only that the value is in
that enum, and [client.go:206](../../../backend/internal/llm/openaicompat/client.go#L206) sends it verbatim. Against
the models registered in production on 2026-09-05:

- `deepseek/deepseek-v4-pro-0813` accepts `max·high·low` and **not `medium`** — an operator can pick `medium` today.
- The same model is `mandatory: false` yet lists no `none`, so the app's only "turn it off" control is a value that
  model does not take. `anthropic/claude-sonnet-5` is the same shape.
- `google/gemini-3.8-flash` and `z-ai/glm-5.3-flash` are `mandatory: true` — `none` must never be sent to them.

None of the five overrides stored in production is invalid right now, so nothing has broken yet. This change closes
the hole before it does, and gives change 29 the signal it depends on.

### `unset` reads as the wrong thing

With `default_effort` unrecorded, the admin's `unset` looks like "this model will not reason". It means the model's
own default: `high` on `deepseek/deepseek-v4-pro-0813`, `medium` on `google/gemini-3.8-flash`. Every model
registered in production reasons by default.

## To-be

### The catalog records what the source says about reasoning

The same successful fetch that already writes `vision`, `structured_output`, `image_output`, `video_output` and the
pricing snapshot also writes, per model:

| Our field | Source | Rule |
|---|---|---|
| `reasons` | the `reasoning` object is present | the model reasons at all |
| `reasoning_efforts` | `reasoning.supported_efforts` | verbatim, in the source's descending order; empty when absent |
| `reasoning_default_effort` | `reasoning.default_effort` | empty when absent |
| `reasoning_mandatory` | `reasoning.mandatory` | false when the object is absent |
| `reasoning_native_effort` | `"reasoning_effort" ∈ supported_parameters` | whether the provider receives the effort string itself rather than a budget OpenRouter derived |
| `reasoning_max_tokens` | `reasoning.supports_max_tokens` present and `true` | recorded and displayed; nothing consumes it yet |

Absence stays absence, exactly as the pricing rules already treat an unpublished price: a model with no
`supported_efforts` is "unknown", never "supports nothing".

### The override control is constrained by them

- The effort options offered for a model are its `reasoning_efforts` when that list is non-empty, and the existing
  eight-value list when it is empty. Partial coverage is the source's intended contract, not a gap to paper over.
- `none` is withheld when `reasoning_mandatory`, and when the list is non-empty and does not contain `none`.
- `unset` is labelled with the model's `reasoning_default_effort`, so the operator can see that leaving it alone
  means `high` rather than "off".
- A model that does not reason at all offers no effort control.
- `SetModelReasoning` applies the same rule server-side and refuses with `ErrInvalidReasoning`; the FE constraint is
  an affordance, the server one is the contract.

### Drift is a flag, not an action

If a stored override later leaves the model's `supported_efforts` — a revised model, a replaced slug — **the value
is kept and still sent**, and the admin row shows a warning naming the mismatch. This is plan 18's own `listed = 0`
precedent: the source's list changing is not a mandate to rewrite an operator's decision.

## Scope / Non-goals (regression boundary)

**In scope**

- The catalog mapping and its tech doc, the `catalog_models` migration for the six fields, and the RPC/proto
  surface that carries them to `/admin`.
- The 모델 관리 effort control: option filtering, `none` withholding, the `unset` label, the drift warning.
- Server-side validation of an override against the model's list.

**Non-goals — these must NOT change**

- What goes on the wire. The request body `openaicompat` builds is untouched here; the `reasoning: {enabled: false}`
  transport belongs to [change 29](../29.give-the-write-budget-reasoning-headroom.md).
- Any completion budget, and any generation behavior. This change is curation only.
- A token-budget control for `reasoning_max_tokens` models — recorded, displayed, not surfaced as an input.
- Auto-correcting, clearing or migrating a drifted override, and any automatic deregistration.
- The fetch itself: the endpoint, its `output_modalities` query, the TTL cache, and the admin-only trigger are
  unchanged; no new request is made.
- Availability bookkeeping (`listed` / `last_seen_at`) and the pricing rules, including change 20's per-modality
  price selection.
- The per-purpose registration model (change 20) and the per-purpose override column (change 24). This change
  constrains the value, it does not move it.

## Acceptance Criteria

1. A catalog refresh persists `reasons`, `reasoning_efforts`, `reasoning_default_effort`, `reasoning_mandatory`,
   `reasoning_native_effort` and `reasoning_max_tokens` for every model in the response, and a model whose entry
   carries no `reasoning` object is recorded as not reasoning rather than skipped or failed.
2. For `deepseek/deepseek-v4-pro-0813` the stored list is exactly `max·high·low`, the default effort is `high`,
   mandatory is false, and native effort is true.
3. The 글 작성 tab's effort control for that model offers `max·high·low` and `unset`, and does **not** offer
   `medium`, `xhigh`, `minimal` or `none`.
4. The control for `google/gemini-3.8-flash` (mandatory) offers no `none`; the control for a model with no stored
   list still offers all eight values.
5. `unset` is labelled with the model's default effort where one is known.
6. `SetModelReasoning` refuses `medium` for `deepseek/deepseek-v4-pro-0813` with `ErrInvalidReasoning`, and accepts
   any value for a model whose list is empty.
7. An override that is no longer in its model's list survives a refresh unchanged, is still sent on a call, and is
   shown with a warning in the admin row.
8. A model that does not reason shows no effort control at all.
9. No generation path changes: an unchanged registration produces a byte-identical provider request body before and
   after this change.
