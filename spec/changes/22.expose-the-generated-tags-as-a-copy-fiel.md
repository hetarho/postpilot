# 22. Change: Expose the generated tags as a copy field in the export panel

> A **change proposal** (a WHAT delta) that modifies the already-shipped behavior of [plan/08.platform-export](../plan/08.platform-export.md).
> Filled by /create-change through a user interview — a reviewable doc, not a one-line prompt.
> The STEPS live in the job that /create-change-job creates. Write it in English.

## As-is

Generation produces `PostContent { title, summary, tags, blocks }`, and the writing prompt asks for three to six
tags. The export panel on 글 완성 receives that whole content object and derives four platform formats from it.

Plan 08 decides per format where the header fields go, and for tags it decided *omission* on the two platforms that
have their own tag input: the Naver body omits summary and tags, and the Tistory body omits tags because Tistory has
a tag field. Only the site HTML (a tags list) and the Markdown front matter (a `tags` key) carry them.

That decision was right about the body and incomplete about the screen. The panel gives the title exactly the
treatment tags need and never gave tags the same: on the Naver tab there is a read-only title field with its own copy
button, because Naver has its own title box. The rendered Naver preview is the post body with the
title/summary/tags header explicitly suppressed, since the body copy does not paste it.

So the generated tags are, at the moment the user is filling in Naver's tag box:

- **Invisible on the Naver tab.** Suppressed from the preview header, omitted from the body copy, and given no field
  of their own.
- **Invisible on the Tistory tab.** Omitted from the output, and the tab shows only that output.
- **Present but unusable on the site and Markdown tabs.** They sit inside the raw output blob as an HTML list or a
  YAML sequence, so reading them means picking them out of markup, and pasting them into a tag box means retyping
  them by hand.

The tags render properly in exactly one place — `BlockList`'s header in the 글 다듬기 reading view — which is the
step the user has already left by the time they are pasting into a platform. The result is that a user on 글 완성
cannot see, let alone paste, the tags the model wrote.

## To-be

The export panel gains a **tag copy field**, built the same way the Naver title field already is: a read-only field
holding a ready-to-paste string, with its own copy button beside it and its own copy confirmation below it.

**It is shown on all four format tabs.** The site and Markdown outputs keep their embedded tags, and the field is
still offered there: what is embedded is an HTML list or a YAML sequence, and what the field carries is a
ready-to-paste string. Those are different artifacts, and the tags are equally worth seeing on every tab.

**The copied string is hashtag-formatted** — `#tag1 #tag2 #tag3`, single-space separated, each tag prefixed with `#`
exactly once. A tag the model already emitted with a leading `#` is not double-prefixed.

**A post with no tags shows no field.** An empty tag list is not an empty control; the field and its label are absent
rather than present and blank.

**The copy behaves like the title's copy.** Same confirmation message pattern, same feedback duration, same manual
selection fallback when the clipboard write is refused, and the same staleness rule — a confirmation that no longer
matches the content on screen does not survive a content change.

Nothing about the four derived outputs changes. The Naver body still omits summary and tags, the Tistory body still
omits tags, and the site and Markdown outputs still carry theirs exactly as plan 08 specifies. This change adds a
surface, not a format.

## Scope / Non-goals (regression boundary)

**In scope**

- The tag field in `widgets/export-panel`: read-only field, copy button, copy confirmation, manual-selection
  fallback, and the staleness rule — mirroring the existing Naver title field.
- The hashtag string derivation (`#`-prefixed, single-space separated, no double prefix).
- Presence on all four format tabs, and absence when the post has no tags.
- Korean and English copy for the label, the button, and the confirmation, through the existing localization
  contract.
- Automated coverage: the field renders on each of the four tabs, the copied string's exact shape, the no-tags case
  renders no field, the already-`#`-prefixed case, and the copy confirmation and fallback paths.

**Non-goals — these must NOT change**

- **The four derived outputs.** Naver body omits summary and tags; Tistory body omits tags; site HTML keeps its tags
  list; Markdown keeps its front-matter `tags`. No format gains or loses a tag.
- The Naver photo-copy flow, the `[사진 …]` markers and their positions, the preview's suppressed header, and the
  title field.
- The tag rendering in `BlockList`'s header and the 글 다듬기 reading view.
- Tag editing, reordering, adding, or removing — the tags are what generation wrote, and this is a read-only surface.
  Revision is plan 07's business.
- The generation prompt's tag instruction and the 3–6 tag count.
- No new config value: copy feedback timing stays owned by `COPY_FEEDBACK_MS` in `frontend/src/shared/config`.
- Invariants [I1]–[I7] hold; this is a browser-only derivation of content the client already has, and it makes no
  request.

## Acceptance Criteria

1. On a post whose content has tags, the export panel shows a labelled read-only tag field with a copy button on
   **each** of the four format tabs (naver, tistory, site, markdown).
2. Copying it puts `#tag1 #tag2 #tag3` on the clipboard for tags `[tag1, tag2, tag3]` — each tag prefixed with a
   single `#`, separated by single spaces, with no trailing separator.
3. A tag that already begins with `#` is copied with exactly one `#`, not two.
4. A post whose content has an empty tag list renders no tag field and no tag label — not an empty field.
5. The copy confirmation appears on success, and a clipboard refusal falls back to manual selection beside the tag
   field, in both cases behaving as the title field's copy does today.
6. A confirmation shown for one tag list does not survive a content change to a different tag list.
7. Regression: all four outputs are byte-identical to their current values for the same content — in particular the
   Naver body still omits tags, the Tistory body still omits tags, the site HTML still renders its tags list, and the
   Markdown front matter still carries `tags`.
8. Regression: the Naver tab still shows the title copy field and the body preview with its header suppressed, and
   per-photo copy still works at every marker position.
