# 21. Change: Reuse finished observations and pick which photos to re-observe

> A **change proposal** (a WHAT delta) that modifies the already-shipped behavior of [plan/06.two-stage-generation-and-contact-sheet](../plan/06.two-stage-generation-and-contact-sheet.md).
> Filled by /create-change through a user interview — a reviewable doc, not a one-line prompt.
> The STEPS live in the job that /create-change-job creates. Write it in English.

## As-is

Plan 06 runs generation as two stages, observation then writing, and persists the observation snapshot
incrementally so the contact sheet can fill in while the job runs. That incremental persist exists for the *screen*,
not for recovery: nothing ever reads it back.

The generate handler re-observes unconditionally. When the post has attached images it calls the observation stage
with no reference to what is already known, and the observation loop walks every attached photo from the first index,
re-reads each JPEG from R2, and re-calls the vision model in batches of `OBSERVE_BATCH_SIZE`. The generation context
*cannot* consult the existing snapshot even in principle: the input struct the handler receives carries no
observations field, so the persisted contact sheet is write-only from this context's point of view. Each batch then
calls the post context's `SetObservations`, whose contract is a full replacement of the snapshot.

A failed job is terminal. There is no automatic retry, and the boot sweep marks interrupted rows failed rather than
requeueing them. "Retrying" is therefore always a fresh `StartGeneration` that inherits nothing from the run before
it — not the stage that succeeded, not the photos already understood.

Three consequences are already visible in production:

- **A write-stage failure re-pays for the whole observation stage.** On 2026-09-03 job `921834e3` repeated the exact
  four observation calls that `aef21a6a` had completed minutes earlier — same photos, same model, same prompts — for
  3,764 microusd and roughly seventy seconds of wall clock, and produced no information that was not already stored.
- **The contact sheet regresses during a retry.** Because the first batch of the new run replaces the whole snapshot,
  a sheet showing fifteen observations drops to four and refills from there.
- **The wait is paid twice.** Observation is the slow half for a photo-heavy post; a user whose writing stage failed
  waits through it again before the stage that actually failed is even attempted.

The A/B write-comparison path shares this shape: it observes first, then compares write candidates, so it repeats the
same work for the same reason.

Preconditions today require `observe_model` to be set, enabled and vision-capable whenever the post has images, and
generation options (language, target length, purpose, guidelines) are frozen into the durable job payload at enqueue
precisely so a later edit cannot retarget queued work.

## To-be

A post that has both attached photos and a stored observation snapshot no longer re-observes silently. Starting
generation on such a post always goes through a **re-observation picker** first, and the run observes only the photos
that picker names.

**The picker.** One surface in two presentations — a dialog on the desktop and a bottom sheet on the phone. It lists
every attached photo in the post's own order, each with its thumbnail, the observation currently stored for it, and a
checkbox that means *observe this photo again*. It states which model produced the stored observations, and it offers
a way to select or clear every photo at once.

**Defaults favour reuse.** Every checkbox starts clear. Confirming the picker without touching anything reuses every
stored observation and skips the observation stage outright, so the common case — the writing stage failed and the
photos did not change — costs one confirmation and no vision calls.

**A photo with nothing to reuse is not optional.** A photo attached since the last observation, or one whose stored
entry is empty, is checked and cannot be cleared: the run must not write from a photo it has never looked at.

**A changed observe model warns, it does not compel.** If the selected observation model differs from the one that
produced the stored snapshot, the picker says so plainly and names both models, and the defaults stay clear. Mixing
one model's observations with another's is the user's call, not the system's.

**The selection is frozen at enqueue**, in the durable job payload, as the explicit set of filenames to observe
together with the observations being carried over. Editing photos or switching models after the enqueue must not
change what a queued run observes — the same discipline the payload already applies to language, target length,
purpose and guidelines.

**The handler observes only the frozen set**, in the same batch size and with the same prompt, schema, filename
matching and attachment filter as today. It seeds its merged snapshot with the carried-over observations before the
first batch, so every persist is a complete snapshot and the contact sheet only ever grows or stays put — it never
shrinks mid-run.

**Progress counts only real work.** The observation stage's total is the number of photos actually being observed; a
run that reuses everything reports observation complete at once and moves to writing. A run with no photos behaves
exactly as it does today.

**A/B comparison shares the picker** and the same reuse contract, for the same reason.

**Preconditions are unchanged.** A post with photos still requires an enabled, vision-capable observation model even
when nothing is being re-observed. Relaxing that is a separate decision and is deliberately not taken here.

## Scope / Non-goals (regression boundary)

**In scope**

- The re-observation picker as one composed surface in two presentations (desktop dialog, phone bottom sheet), built
  on the existing `shared/ui` dialog and sheet primitives, including per-photo thumbnail, stored observation,
  checkbox, select-all/clear-all, the changed-model notice, and the forced state for photos with nothing to reuse.
- The start contract: the set of filenames to observe travels from the picker through `StartGeneration` and the A/B
  start into the durable job payload, and is frozen there.
- Carrying the reused observations into the run so the handler can seed a complete snapshot without reading another
  context's tables.
- Partial observation in the handler: observe only the named filenames, in the existing batches; persist a complete
  merged snapshot after each batch; skip the stage entirely when the named set is empty.
- Observation progress accounting over the named set, and the immediate-completion case.
- A/B write-comparison parity.
- Korean and English copy for every new string, through the existing localization contract.
- Automated coverage: reuse-everything, reuse-some, forced photos, changed-model notice, snapshot never shrinking,
  payload freeze against post edits after enqueue, batch count over a partial set, and the zero-photo path.

**Non-goals — these must NOT change**

- **The write stage's completion budget.** The larger production cost was the writing stage exhausting its 8,192-token
  completion budget on reasoning and returning an empty body — 44,917 of the 52,473 microusd spent on the three
  failed runs. This change does not touch `MaxTokens`, the reasoning policy, or the truncation verdict; that is its
  own change against plan 04, and doing it here would hide it behind a UI feature.
- **Failure handling.** A failed job stays terminal. No automatic retry, no resume of a failed job, no requeue in the
  boot sweep. A retry remains an explicit user action that creates a new job.
- The observation prompt, the observation schema, `OBSERVE_BATCH_SIZE` as the owner of batching, filename matching
  (extras dropped, missing ones empty), the validation function, and the attachment filter.
- The contact sheet widget's own purpose and layout, and the reading view.
- The observation-model precondition for a post with photos.
- Hand-editing observation text, or reusing observations across posts.
- The zero-photo path: no picker, no observation call, unchanged behavior.
- Invariants [I1]–[I7] hold. In particular the generation context still never writes another context's tables: the
  seeded snapshot is persisted through the post context's published behavior, and no write transaction spans a
  provider call.

## Acceptance Criteria

1. Starting generation on a post that has photos and a stored observation snapshot opens the picker; the desktop
   presentation is a dialog and the narrow-viewport presentation is a bottom sheet. A post with no photos, or with no
   stored snapshot, starts generation directly as it does today.
2. Every checkbox is clear when the picker opens. Confirming without changing anything enqueues a run that makes
   **zero** observation calls, reports the observation stage complete immediately, proceeds to the writing stage, and
   leaves the stored snapshot byte-identical.
3. Checking a subset enqueues a run that observes exactly those photos: with `OBSERVE_BATCH_SIZE = 4` and five photos
   selected out of fifteen, the handler makes two observation calls and the persisted snapshot afterwards still holds
   one entry per attached photo — the ten unselected entries unchanged, the five selected ones replaced.
4. The snapshot never shrinks during a run: after the first batch of a partial re-observation, the persisted snapshot
   already contains an entry for every attached photo (carried-over plus newly observed).
5. A photo attached after the last observation, or one whose stored entry is empty, renders checked and cannot be
   cleared; a picker in which those are the only photos with nothing to reuse still allows confirming.
6. When the selected observation model differs from the model that produced the stored snapshot, the picker shows a
   notice naming both models, and the checkboxes still default to clear.
7. The selection is frozen at enqueue: attaching a photo, deleting a photo, or switching the observation model after
   `StartGeneration` returns and before the job is dequeued does not change which photos that run observes.
8. The A/B write comparison goes through the same picker and honors the same reuse, including the zero-observation
   case.
9. Observation progress reports the count of photos actually being observed as its total, not the number attached.
10. Regression: a first generation on a post with photos and no stored snapshot observes every photo in
    `ceil(N / OBSERVE_BATCH_SIZE)` calls, and the zero-photo path still makes no observation call and clears the
    snapshot — both exactly as plan 06 specifies today.
