# 05. Change: Present the Post Editor as Lifecycle Steps

> A **change proposal** (a WHAT delta) that modifies the already-shipped behavior of [plan/02.post-drafting-and-list](../plan/02.post-drafting-and-list.md).
> Filled by /create-change through a user interview — a reviewable doc, not a one-line prompt.
> The STEPS live in the job that /create-change-job creates. Write it in English.

## As-is

**One column holds the whole lifecycle at once.** `/posts/$slug` renders `DraftEditor` as a single `<main>`: back
link and status badge, title, memo, photos, the empty-profile warning, then `GenerationSection` — which renders the
글 생성 heading with two stage-model selects and an A/B link, the pending-experiment link, the contact sheet, and,
only once content exists, the block editor, the revision form, the finalize control, and the export panel — closed
by the docked action bar. Writing the memo, choosing models, editing paragraphs, and exporting are all the same
screen, in the same scroll, in every state the post can be in.

**The generation controls never leave.** `GenerationSection` renders its two model selects and the A/B link
whenever a post exists, before the first generation and forever after. On a post that already has a draft they sit
permanently between the memo and the text the user came to read, and the generation CTA occupies the dock — the one
place §4.3 reserves for the committing action — no matter how far past generating the post is.

**The post already knows which phase it is in, and the screen ignores it.** `draft`, `review`, and `finalized` are
in the contract with the Korean labels 초안, 검토, 확정, and the list screen tells them apart. The editor renders
one `Badge` next to the back link and is otherwise byte-identical in all three states.

**There is no reading view of the draft.** Every block is a form card: a type `Select`, three icon buttons, and a
`Textarea`, per block, stacked. A twelve-block post is twelve stacks of controls with no way to just read the
result. This was not the original design — plan 06 shipped "the rendered draft (block reading view)" and listed
"a manual block editor" under **Non-goals**. That reading view still exists as
`entities/post/ui/BlockList.tsx` ("The canonical block array rendered as a read-only draft"), is exported from the
entity's barrel, and **has no importer anywhere in the app**: direct block editing replaced it and orphaned it.

## To-be

### Three steps, derived from the post's own status

The editor presents the post's lifecycle as three steps, and the current step is **derived from `post.status`** —
not from a new field and not from local component state. Reload, navigation, and the list screen's badge therefore
cannot disagree with the editor, and nothing new has to be persisted.

| Step | Status | Holds |
|---|---|---|
| ① 글 생성 | `draft` | title, memo, photos, empty-profile warning, stage-model selects, the A/B link, the generation actions, the contact sheet |
| ② 글 다듬기 | `review` | generated title/summary/tags, the block editor, AI revision, sentence feedback |
| ③ 글 완성 | `finalized` | finalize, finalize-and-learn, export |

Each step renders only its own panel. The generation controls exist on step ① and nowhere else, which is the whole
point: once a draft exists the user is refining it, and re-generating is a deliberate trip back to step ①.

**The steps are freely navigable.** The step bar can move to any step at any time — to export from step ③ while the
post is still in `review`, or back to step ① to add a photo before regenerating. A step with nothing in it yet says
so rather than being locked, so the shape of the whole flow is visible from the first screen. Moving between steps
does not change `post.status`; only the real actions (generate, finalize) do.

`/posts/new` has no post and therefore no lifecycle: it shows step ① alone, with no step bar.

The docked action bar keeps its contract — save state plus the one committing action — but the action it docks is
the current step's: generate on ①, and finalize on ③. Step ② commits continuously through content autosave, so it
docks the save state and the revision control.

### Read the draft; edit a block on request

Step ② opens as **prose**, not as a form. The generated title, summary, tags, and every block render as the
rendered draft — reusing `BlockList`, the reading view plan 06 specified and the app orphaned, rather than building
a second one.

Each block carries one edit control. Pressing it turns that block — and only that block — into the editing UI it
has today: the type select, the move/delete actions, and the content field. Saving or cancelling returns it to
prose. Cancel discards the block's draft and restores the saved value.

This is the same read-first shape as change 04's voice fields, so it is built on the **same `shared/ui` primitive**
that change 04 introduces, not a second copy of it (design-language §1.1: "if two slices reach for the same shape,
that shape is a missing primitive, and the second slice's copy is the bug report").

## Scope / Non-goals (regression boundary)

**In scope**

- The editor screen's composition: the step bar, step-derived panels, and per-step dock contents.
- Step ②'s read-first block presentation, reusing `BlockList` and change 04's `Editable` primitive.
- Retiring the permanently-mounted 글 생성 section from post-generation states.

**Must NOT change**

- **The autosave contract.** The per-post save queue in `features/save-draft`, the flush on debounce /
  `visibilitychange` / `pagehide` / unmount, the slug mint + `replace` navigation, and the caret handoff through
  `pages/editor/model/editor-handoff.ts` all keep working exactly as they do. The editor stays **one mounted
  component per slug** — steps are panels, not routes — so no step change may remount it or strand a queued save.
- **Content autosave and its revision check.** Block edits keep saving through `useContentAutosave` with the same
  revision guard and the same conflict reporting.
- **Generation semantics, which job 17 owns.** Separate 생성 / A/B 비교 생성 actions, the target-length option,
  explicit model refs with no fallback ([I3]), finalize vs finalize-and-learn, and every status transition behave
  exactly as job 17 leaves them. This change only decides *which step* renders them.
- **[I2]** the canonical post stays a block array; **[I1]** export still derives copy-ready output and never
  publishes.
- **One scroller per screen** (§4.4) and the docked-action contract (§4.3). Steps must not introduce a nested
  vertical scroller.
- The post list, the voice screens, generation/revision backends, and every RPC. **No contract change, no
  migration, no new RPC** — this change is frontend-only.

## Acceptance Criteria

1. The editor renders a three-step bar labelled 글 생성 · 글 다듬기 · 글 완성, and the step marked current is the one
   matching `post.status` (`draft` → ①, `review` → ②, `finalized` → ③). Reloading the page keeps that step.
2. Step ① renders the stage-model selects, the A/B link, and the generation actions. Steps ② and ③ render none of
   them.
3. Step ② renders the block editing surface and AI revision; step ③ renders finalize, finalize-and-learn, and
   export. Neither renders the other's panel.
4. Any step can be opened at any time regardless of status, including a step whose work has not happened yet, which
   states that it is empty rather than being disabled. Opening a step never changes `post.status` and never starts a
   job or a provider call.
5. `/posts/new` renders step ①'s content with no step bar, and the first autosave still mints the slug and replaces
   the URL with the caret preserved.
6. Switching steps does not remount the editor: a pending title/memo save started before a step change still
   completes, and the content autosave's revision guard is unaffected.
7. Step ② opens with the draft rendered as prose — title, summary, tags, and every block — with no form control
   visible until a block's edit control is pressed. `entities/post`'s `BlockList` is the component that renders it.
8. Pressing a block's edit control puts that block, and only that block, into its existing editing UI. Cancel
   restores the saved value and discards the block's draft; saving returns it to prose with the new value shown.
9. The block editing UI reached this way keeps every capability it has today: type change, move up/down, delete,
   add paragraph, per-block validation messages, and sentence feedback on text and quote blocks.
10. The read-first behavior is provided by the shared `Editable` primitive from change 04, not by a second
    implementation inside the editor slice.
11. The docked bar shows the save state on every step, the generation action only on ①, and the finalize action only
    on ③, and never grows a second committing action.
12. At a 360px viewport the step bar meets the 44px target minimum, does not wrap or clip, and the page does not
    scroll horizontally or acquire a nested vertical scroller.
13. No regression: autosave (debounce, visibility, pagehide, unmount), slug mint and caret handoff, content-autosave
    conflict reporting, contact-sheet fill-in during observation, generation/revision/finalize/learning behavior,
    export output, and the empty-profile warning all behave exactly as before.
