# 09. Change: Persist Dedicated Browser Sessions Across Pairing Retries

> A **change proposal** (a WHAT delta) that modifies the already-shipped behavior of [plan/12.automated-naver-publishing-through-a-pai](../plan/12.automated-naver-publishing-through-a-pai.md).
> Filled by /create-change through a user interview — a reviewable doc, not a one-line prompt.
> The STEPS live in the job that /create-change-job creates. Write it in English.

## As-is

Plan 12 gives each paired Postpilot connection an agent-owned Chromium `user-data-dir`, asks the user to sign into
Naver once, and reopens the stored directory when an armed connection needs login repair. A saved connection
therefore has the right long-term shape: its config contains the exact browser profile path, and neither browser
launch nor repair is intended to use incognito mode or a temporary directory.

The pre-enrollment setup path does not yet have a durable local connection identity. It derives a twelve-character
local ID directly from the current single-use device code and immediately uses that ID for both the browser directory
and the Hermes profile. Device codes are deliberately short-lived and replaceable server credentials, not Mac
profile identities. When a code expires, is replaced, or must be regenerated after a failed setup attempt, the same
intended connection opens a new empty cookie jar. The previous cookies still exist on disk, but the newly launched
browser looks indistinguishable from a private window to the user because it is a different profile.

The pending connection record is written only after server enrollment has returned an agent identity and token. An
unfinished login/setup attempt therefore cannot be resumed safely across a fresh code or companion restart. Picking
an old directory by label or recency would be unsafe: one Mac may intentionally host two Postpilot connections backed
by different Naver accounts.

## To-be

The Mac owns a durable **local connection draft ID** that is generated independently of every server-issued device
code. Starting a new connection creates one draft and one isolated Chromium/Hermes profile pair. Reopening that
draft, closing and relaunching its browser, restarting the setup companion, replacing an expired device code, and
retrying pre-enrollment setup all resolve to those same profile paths without clearing or copying browser storage.

Device-code replacement changes only the one-time authorization presented to Postpilot. Successful enrollment binds
the server agent identity and Keychain token to the existing local draft; it does not rename, relocate, recreate, or
reset the profile. All later repair and publishing runs for that armed connection keep using the bound paths.

Creating a genuinely new Postpilot connection remains explicit and creates a new local draft with a different
browser cookie jar and Hermes profile. The companion never guesses an association from a label, browser choice,
directory age, current Naver login, or device code. An absent, malformed, or conflicting draft identity fails closed
rather than opening another connection's profile.

This contract preserves browser storage; it does not promise that Naver will keep its own session valid forever.
Naver logout, expiry, CAPTCHA, 2FA, suspicious-login checks, or account mismatch continue through the existing local
repair and `needs_attention` behavior.

## Scope / Non-goals (regression boundary)

**In scope**

- The loopback setup lifecycle for creating, persisting, listing, resuming, enrolling, and activating a local
  connection draft.
- Stable ownership of the dedicated Chromium directory and Hermes profile before and after enrollment, including
  setup-companion and visible-browser restarts.
- An explicit distinction between resuming an unfinished connection and starting a second isolated connection.
- Safe upgrade behavior: existing armed connections keep their configured paths; unowned legacy profile directories
  are neither deleted nor silently attached to a connection.
- Automated coverage for stable path selection, code rotation, restart/resume, activation, isolation, and fail-closed
  handling, plus one local smoke test that closes and reopens a signed-in dedicated browser.

**Non-goals**

- No cookie, password, browser storage, profile path, CDP endpoint, or Hermes credential leaves the Mac ([I1]).
- No sharing with or takeover of a normal personal Chrome profile, and no cross-connection cookie/profile sharing.
- No attempt to extend, refresh, synthesize, or bypass Naver authentication and security challenges.
- No automatic association of the already-created unowned code-derived directories. They may be left untouched for
  explicit manual cleanup; the change does not inspect their cookie contents.
- No automatic migration of one connection between Chrome, Brave, Chromium, and Edge. A browser change must not
  silently reuse, overwrite, or erase an existing profile.
- No change to server pairing TTLs, agent bearer-token rules, publishing jobs, immutable manifests, commit fencing,
  the Hermes publishing surface, frontend publishing UI, or mobile notifications.
- Revocation, repair, upgrade, or uninstall must not erase a dedicated profile without a separate explicit local
  destructive confirmation.

## Acceptance Criteria

1. Starting a local connection once, signing into Naver, closing its visible Chromium window, and reopening the same
   draft uses the byte-identical `user-data-dir`; absent Naver-side expiry, the generic Naver writer resolves as the
   same signed-in blog without asking for credentials again.
2. Replacing or regenerating the device code for an unfinished connection changes neither its local draft ID,
   Chromium profile path, nor Hermes profile name and creates no additional profile pair.
3. Stopping and restarting the setup companion before enrollment presents the unfinished draft as resumable and
   opens the same paths. No server token is required merely to preserve or reopen that local browser state.
4. Successful enrollment and activation bind the returned server identity and Keychain reference to the existing
   draft. Login repair and a later publishing run both use the same browser/Hermes paths that were used before
   enrollment.
5. Explicitly starting a second connection creates a distinct local draft, `user-data-dir`, and Hermes profile. Two
   Postpilot/Naver accounts on one Mac remain isolated, and reopening either connection never opens the other's jar.
6. A missing, invalid, duplicated, or conflicting draft reference fails closed with an actionable local error; the
   companion never chooses a profile by label, device-code hash, browser type, directory age, or currently logged-in
   Naver account.
7. Every setup, repair, and publishing launch uses the connection-owned persistent `user-data-dir`, never
   incognito/guest mode or a temporary profile, and does not clear cookies or other browser storage as part of normal
   launch/exit.
8. Existing armed connections retain their configured profile paths after upgrade. Legacy unowned directories are
   left untouched and are not automatically attached, merged, copied, or deleted.
9. Natural Naver logout/expiry, CAPTCHA, 2FA, suspicious-login checks, and blog-identity mismatch still stop locally
   for repair or become `needs_attention`; no authentication material or browser/profile detail reaches the VPS.
10. Revoking or repairing one connection leaves its on-disk profile and every other connection usable. Profile
    deletion requires a separate explicit local confirmation and is not a side effect of this change.
