# 13. Change: Expose Post Deletion In The Editor

> A **change proposal** (a WHAT delta) that modifies the already-shipped behavior of [plan/02.post-drafting-and-list](../plan/02.post-drafting-and-list.md).
> Filled by /create-change through a user interview — a reviewable doc, not a one-line prompt.
> The STEPS live in the job that /create-change-job creates. Write it in English.

## As-is

**A user cannot delete a post, but the server can.** `DeletePost` is a fully implemented, tested, ownership-checked
RPC that no client has ever called.

`proto/postpilot/v1/post.proto` declares `rpc DeletePost(DeletePostRequest) returns (DeletePostResponse)` with
`DeletePostRequest { string slug = 1; }`. `post/rpc/handler.go` resolves the acting user and delegates.
`post.Service.DeletePost` resolves the owned post, lists its images, refuses with `ErrPostBusy` when the job context
reports an active generation job, calls the required `ExperimentContentPurger.PurgePost` hook, deletes every image
object from R2, then deletes the row. Deletion is **hard**: there is no `deleted_at` column on `posts` and no
`RestorePost`. Cascade is carried by the schema — `images`, `uploads`, `generation_jobs`, and every
`voice_*`/post-scoped learning table declare `ON DELETE CASCADE`, while `model_experiments.post_slug` declares
`ON DELETE SET NULL` so durable experiment metadata survives with its content already purged.

This RPC arrived as a side effect of plan 09 (commit `03ea9b5`), which needed a deletion path to prove the experiment
content purge. It was never surfaced, never documented, and never given a product rule.

Three consequences follow, and all three are defects rather than deliberate design:

- **No frontend surface at all.** The only occurrence of `deletePost` under `frontend/src` is the generated type in
  `shared/api/gen/postpilot/v1/post_pb.ts`. There is no `entities/post` mutation hook, no feature slice, no button,
  and no test. Every other deletable entity in the product has a complete path from RPC to UI: photos
  (`DeleteImage` → `EditorPhotos`), voices (`DeleteVoice`/`RestoreVoice` → `DeleteVoiceButton`), voice samples
  (`DeleteVoiceSample` → `SampleList`), purposes (`DeletePurpose` → `DeletePurposeButton`), guidelines
  (`DeleteGuideline` → `DeleteGuidelineButton`), publishing agents (`RevokePublishingAgent`), and publish jobs
  (`CancelPublish`). The post is the single entity where the wiring stops at the transport layer.
- **The policy document contradicts the shipped code.** [spec/policy/posts.md](../policy/posts.md) states verbatim:
  "**There is no post deletion.** The PRD defines photo deletion but not post deletion; flagged as a PRD gap, not an
  oversight." A reader of the SSOT is told the opposite of what the binary does.
- **The delete guard ignores publishing.** `DeletePost` consults only `ActiveJobFinder.ActiveForPost`, which covers
  the generation queue. It does not ask the publishing context anything. A post with a `queued`, `running`, or
  `needs_attention` publish job can be deleted right now while a paired local agent is driving a browser against the
  frozen manifest.

The publishing schema, by contrast, was already written to survive post deletion. `publish_jobs.post_slug` carries no
foreign key, and the migration's own comment reads "Publication history deliberately outlives the source post.
StartPublish is the application-level integrity boundary: after it freezes the manifest, deleting the post must
neither delete nor block its publication record." The table stores `post_created_at` alongside the slug so a
publication belonging to a deleted post stays distinguishable from one belonging to a later post that reuses the
slug, `publish_jobs_deleted_post_history_idx` indexes exactly that lookup, and `Store.LatestJobForDeletedPost`
already reads it. Publish assets are staged under their own `publish_assets.staged_key`, separate from the `posts/`
prefix the post context and the orphan sweep own, so removing a post's photos cannot starve an in-flight publish.

Autosave is the remaining hazard. Per [spec/tech/draft-autosave.md](../tech/draft-autosave.md), a draft queue
"outlives its editor, never its session": a failed save keeps retrying with a capped backoff after the user leaves
the editor, and the content queue behaves the same way. The only discard primitives are the session-wide
`discardDraftQueues()` and `discardContentQueues()`, called from `app/model/end-session.ts`. There is no way to
discard the queues for one slug.

## To-be

**A user can delete one of their own posts from that post's editor, and the deletion is honest about what it
destroys and about when it is refused.**

**Placement.** The control lives on the post editor screen (`/posts/$slug`) only, in a clearly separated destructive
region below the editor's working content. The post list stays exactly as it is: every row remains one whole `Link`,
and no row-level menu, swipe gesture, or per-row button is introduced. Deleting a post therefore always happens on
the screen that shows the post's own title, memo, photos, and content, so the user confirms against the thing itself
rather than against a truncated row label. `/posts/new` shows no delete control, because a draft with no slug has
nothing to delete.

**Confirmation.** Activating the control opens the shared `Dialog` confirmation, following the established
`DeleteVoiceButton` pattern: a danger-toned trigger, a dialog naming the post being deleted and stating that the
post, its photos, and its generation and revision history are removed permanently and cannot be restored, and a
`FieldMessage` beside the trigger for a refusal. The dialog closes on failure too, so the message is never left
behind the scrim.

**Deletion remains hard and immediate.** No `deleted_at` column, no trash state, no `RestorePost`, no retention
window. The confirmation dialog is the whole protection, and it must say so in plain words. This keeps the change a
thin exposure of shipped server behavior rather than a new lifecycle.

**A live publication blocks deletion.** `DeletePost` gains a second precondition beside the generation-job check: if
the acting user has a **non-terminal** publish job for this post — `queued`, `running`, or `needs_attention`, the
three states `publishing.Job.Terminal()` excludes — the RPC refuses with `FailedPrecondition` and a new stable
reason `POST_PUBLISHING`, distinct from `POST_BUSY` so the client can explain the right remedy. The editor's message
tells the user to cancel or finish the publication first and points at the publishing surface, which already exposes
`CancelPublish`. The block is temporary by construction: a job past the commit fence cannot be canceled, but the
agent's outcome report or the lease-expiry sweep drives it to a terminal state on its own.

Terminal publication history never blocks and is never deleted. A post with a `published`, `failed`,
`outcome_unknown`, or `canceled` job deletes normally, and its `publish_jobs` and `publish_assets` rows survive
untouched, exactly as the schema comment and `LatestJobForDeletedPost` already intend. This is what keeps the change
inside **[I1]**: an external commit that already happened stays recorded, and deleting the local draft neither
retracts it nor implies a new publish.

**The post context still owns no knowledge of publishing.** The check is a consumer-declared port in
`post/ports.go`, in the same shape as the existing `ActiveJobFinder`, `ExperimentContentPurger`, `VoiceDirectory`,
and `PurposeDirectory`. The adapter that satisfies it is wired in the composition root (`cmd/api/main.go`) and
delegates to a query the publishing context publishes; `internal/post` never imports `internal/publishing`, and the
post store never reads `publish_jobs`.

**Deleting a post silences that post's autosave.** A successful delete discards the draft queue and the content
queue for that slug before navigating away, so no retry fires against a slug that no longer exists and the user
never sees a save error for a post they intentionally destroyed. The session-wide discards keep their current
behavior; the new primitives are per-slug and additive.

**After a successful delete** the editor navigates to `/posts`, and the post list and the post's own query are
invalidated so the deleted row is gone on arrival rather than after a manual refresh.

**The SSOT tells the truth.** `spec/policy/posts.md` replaces its "There is no post deletion" paragraph with the
deletion rule this change makes true: who may delete, what is destroyed, what survives, and the two refusal
conditions. Plan 02's contract section gains `DeletePost` beside the `DeleteImage` line it already documents.

## Scope / Non-goals (regression boundary)

**In scope**

- One frontend mutation hook in `entities/post` for `DeletePost`, and one feature slice carrying the trigger, the
  confirmation dialog, and the failure message.
- The destructive region on the `/posts/$slug` editor screen that hosts it, and its Korean and English strings.
- Post-delete navigation to `/posts` plus invalidation of the post list and the deleted post's query.
- Per-slug discard primitives for the draft queue and the content queue, called on a successful delete.
- A new consumer-declared port on the post context for "does this post have a non-terminal publish job", the
  publishing-side query that satisfies it, and the composition-root adapter that connects them.
- `post.ErrPostPublishing` and its `POST_PUBLISHING` / `FailedPrecondition` mapping in `post/rpc/handler.go`.
- Backend tests for the new refusal and for the terminal-history case that must still delete; frontend tests for the
  confirmation flow, the two refusal messages, the queue discard, and the navigation.
- Correcting `spec/policy/posts.md` and reflecting `DeletePost` in plan 02's contract section.

**Non-goals — these must not change**

- **The post list screen.** Rows stay whole-row `Link`s. No row menu, no swipe-to-delete, no bulk selection, no
  per-row button, and no change to row content, ordering, status chips, or the docked CTA.
- **Hard-delete semantics.** No `deleted_at` column, no soft delete, no trash, no restore, no retention window, and
  no migration to the `posts` table.
- **The existing `DeletePost` body beyond the one added precondition.** Ownership resolution, the experiment purge
  call and its ordering, R2 object deletion, the row delete, and the `ErrPostBusy` generation-job refusal all keep
  their current behavior and their current order.
- **Publication history.** No `publish_jobs`, `publish_job_ids`, or `publish_assets` row is deleted, rewritten, or
  detached by a post deletion, and no foreign key is added between them and `posts`. `LatestJobForDeletedPost` keeps
  working for a deleted post's slug.
- **[I1].** Deleting a post never starts, retries, resumes, or retracts a publication, and never touches an agent,
  a pairing, a lease, or a frozen manifest.
- **The other invariants.** No change to canonical block content [I2], the observe/write split [I3], voice isolation
  [I4], the durable job queue [I5], browser-side image processing [I6], or embedded migrations [I7] — this change
  adds no migration at all.
- **Session-wide autosave behavior.** `discardDraftQueues()` and `discardContentQueues()` keep their current
  signatures and their logout and dead-session call sites; the queue-outlives-its-editor rule is unchanged for every
  path except an intentional delete.
- **Account deletion and generation-job cancellation.** The audit that produced this change found that a user has no
  way to delete their account (no RPC exists at all; `plan.proto` offers only `ListUsers` and `SetUserPlan`) and no
  way to cancel an in-flight generation job. Both are real gaps and both are deliberately excluded here: account
  deletion needs a cascade policy spanning sessions, voices, posts, and publication history, and job cancellation
  changes plan 05's queue contract. Each deserves its own change.
- **Every other delete surface.** Photos, voices, voice samples, purposes, guidelines, publishing agents, publish
  cancellation, and experiment dismissal were all verified complete from RPC to UI and are untouched.

## Acceptance Criteria

1. On `/posts/$slug`, a signed-in owner sees a danger-toned delete control in a visually separated destructive
   region of the editor. `/posts/new` shows no such control.
2. Activating the control opens a confirmation dialog that names the post and states that the post, its photos, and
   its generation and revision history are permanently removed and cannot be restored. Dismissing the dialog deletes
   nothing and leaves the editor untouched.
3. Confirming deletes the post: `GetPost` for that slug then returns `NotFound`, the slug is absent from
   `ListPosts`, its `images`/`uploads` rows and their R2 objects are gone, and its experiment content is purged while
   the `model_experiments` row survives with a null `post_slug`.
4. After a successful delete the app is on `/posts`, the deleted post is absent from the rendered list without a
   manual refresh, and the post's own query no longer serves the stale post.
5. A successful delete discards that slug's draft queue and content queue. No autosave request is sent for the
   deleted slug afterwards, and no save-failure notice appears.
6. `DeletePost` on a post with a non-terminal publish job (`queued`, `running`, or `needs_attention`) fails with
   `FailedPrecondition` and reason `POST_PUBLISHING`, deletes nothing — no R2 object, no experiment content, no row —
   and the editor shows a message telling the user to cancel or finish the publication first.
7. `DeletePost` on a post whose only publish jobs are terminal (`published`, `failed`, `outcome_unknown`,
   `canceled`) succeeds, and every `publish_jobs` and `publish_assets` row for that post survives unchanged.
   `LatestJobForDeletedPost` still returns that history for the deleted slug.
8. `DeletePost` while a generation job is active still fails with `FailedPrecondition` and reason `POST_BUSY`, and
   the editor distinguishes that message from the `POST_PUBLISHING` one.
9. Deleting another user's slug is `PermissionDenied` (`POST_FORBIDDEN`) and an unknown slug is `NotFound`
   (`POST_NOT_FOUND`), matching the existing ownership rules; neither destroys anything.
10. `internal/post` contains no import of `internal/publishing`, the post store issues no query against
    `publish_jobs`, and the new port is declared in `post/ports.go` and satisfied by an adapter in `cmd/api/main.go`.
11. `spec/policy/posts.md` no longer claims that post deletion does not exist and instead documents the shipped
    rule, including both refusal conditions and what survives a deletion. Plan 02's contract section lists
    `DeletePost`.
12. The post list screen renders identically to before the change, and `pnpm build`, `pnpm lint`, `pnpm test`, and
    `go vet ./...` pass with no regression in the existing post, publishing, and autosave suites.
