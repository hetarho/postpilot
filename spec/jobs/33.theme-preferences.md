## Acceptance Criteria (from plan/14.theme-preferences)

<!-- The source spec's acceptance criteria. After building, verify each is true in the running code. -->

- [ ] A1 With no valid stored override, the first rendered application frame matches the current OS colour scheme and the selector reports System.
- [ ] A2 Selecting Light or Dark applies `day` or `night` immediately and survives navigation, reload, logout, and later login on that browser.
- [ ] A3 Selecting System removes the explicit override and immediately follows the current OS setting.
- [ ] A4 An OS colour-scheme change updates an open System-mode tab but does not alter an explicit Light or Dark tab.
- [ ] A5 A preference change in another same-origin tab updates the current tab through the storage event.
- [ ] A6 Disabled, unavailable, malformed, or throwing storage never prevents the application from rendering; it falls back to System for that session.
- [ ] A7 `<html data-theme>`, CSS/native `color-scheme`, and browser `theme-color` always describe the same effective theme.
- [ ] A8 Theme bootstrap completes before the React app renders; automated bootstrap tests detect no initial wrong-theme frame.
- [ ] A9 `/login` and every authenticated route can reach the selector through their shared shells; the public contract is reused by `/about` when plan 15 lands rather than creating a second theme state.
- [ ] A10 Korean and English labels come from plan 13's typed resources, and changing theme never changes locale or URL.
- [ ] A11 Locale/theme/session-control composition has no horizontal overflow at 320 px, preserves 44 px targets, and is fully usable by keyboard and screen reader.
- [ ] A12 Existing screens use only semantic/functional tokens and meet WCAG AA in both themes.
- [ ] A13 Rendering or changing theme performs no RPC, provider call, job enqueue, or account mutation.
- [ ] A14 Theme resolver, bootstrap, media/storage listeners, selector behavior, metadata synchronization, both-theme visual states, frontend tests, lint, FSD/style checks, and build pass.

## Implementation Checklist

<!-- How to build it, top to bottom. [P] = parallel (different files, no dependency). Flag (gen)/(migrate).
     Config values are never magic literals — FE via shared/config, BE via internal/platform/config. -->

- [ ] T001 Preflight: do not claim this job until [job 32](32.multilingual-interface-and-target-langua.md) is done
      and its locale runtime, typed `common` catalogs, and `change-locale` control are available. Read plan 14,
      `ARCHITECTURE.md` FE §3, `tech/design-language.md` §2.5, and job 32's as-built language policy; invoke
      `/fe-architecture` before adding the provider, feature, or widget. Confirm the current `night` and `day`
      semantic maps render unchanged. This is a browser-only feature: install no dependency and add no API,
      backend, proto, migration, environment variable, or account state.
- [ ] T002 Put the two fixed values in their owner, `frontend/src/shared/config/index.ts`:
      `THEME_PREFERENCE_STORAGE_KEY = 'postpilot.theme'` and `DEFAULT_THEME_PREFERENCE = 'system'`, as typed
      constants. Choosing System removes this key; no component, provider, head script, or test invents another key
      or fallback literal.
- [ ] T003 Build the domain-agnostic theme contract under `frontend/src/shared/lib/theme`: the
      `ThemePreference = 'system' | 'light' | 'dark'` and `EffectiveTheme = 'day' | 'night'` types, strict stored-value
      parsing, the preference + `prefersDark` resolver, and safe local-storage/browser adapter functions shared by
      bootstrap and runtime. Keep resolution pure and inject browser ports for tests. Cover the complete mapping,
      missing/malformed/unknown values, unavailable or throwing storage, explicit write/remove behavior, and SSR-like
      missing browser globals without causing a render failure.
- [ ] T004 [P] Create `frontend/src/features/change-theme/{model,ui}` and its public `index.ts`. The model exposes a
      narrow controller context (`preference`, `effectiveTheme`, `setPreference`) that the app provider can inject
      without the feature importing `app`; `ThemeSelector` consumes it and the existing `shared/ui` native select or
      equivalent primitive. Extend job 32's Korean/English `common` catalogs with `Theme / 테마` and
      `System|Light|Dark / 시스템|밝게|어둡게`. The label and selected preference are exposed to assistive
      technology, selection is not conveyed by colour alone, every target is at least 44 px, and selection triggers
      no navigation, locale change, RPC, or provider call. Add keyboard, screen-reader-name, translation, and
      mutation tests.
- [ ] T005 [P] Implement the one pre-paint path in `frontend/src/app/providers/theme`: safely resolve the stored
      preference and OS media query, then atomically synchronize `<html data-theme="day|night">`, native/CSS
      `color-scheme`, `<meta name="color-scheme">`, and `<meta name="theme-color">` to the effective theme. Wire it
      from the earliest executable head/main entry so it completes before `createRoot(...).render`; bootstrap and
      mounted runtime must call the same resolver/document synchronizer rather than carry two mappings. Preserve the
      existing raised-header-plane chrome colours as a design code contract, not deployment config. Add bootstrap
      tests for stored Light/Dark, System in both OS modes, malformed/throwing storage, metadata parity, and an
      assertion that React rendering is not reached before bootstrap finishes.
- [ ] T006 Add `app/providers/theme/ThemeProvider.tsx` and wrap the app once in `App.tsx`. Initialize from the
      bootstrap snapshot; apply Light/Dark immediately and safely persist it, remove the override for System, listen
      to `matchMedia('(prefers-color-scheme: dark)')` only while System is active, and consume same-origin `storage`
      events for `postpilot.theme`. Every transition reuses the document synchronizer. Treat null/invalid cross-tab
      values as System, keep an in-memory selection when persistence throws, and clean media/storage listeners under
      React Strict Mode. Logout and route changes must not reset the provider. Unit-test listener attachment,
      detachment, mode switching, cross-tab updates, same-tab immediate updates, and non-fatal browser failures.
- [ ] T007 Compose job 32's `LocaleSelect` and this job's `ThemeSelector` in the new
      `frontend/src/widgets/interface-preferences` slice, exporting `InterfacePreferences` as the only reusable
      public-surface control for plan 15. A widget may import both features; neither feature imports the other.
      Provide one compact, keyboard-operable popover/control at narrow widths so locale, theme, and session actions
      do not overflow at 320 px, with translated trigger/dialog names, visible current values, Escape/focus return,
      and 44 px targets. Add widget tests for both locales, all theme choices, focus behavior, and its stable public
      API.
- [ ] T008 Mount `InterfacePreferences` on `pages/login/ui/LoginPage.tsx` without displacing the phone keyboard-safe
      login path, and in `app/routes/AuthenticatedLayout.tsx` so every signed-in route can reach it alongside the
      existing logo, account hint, and Logout action. Preserve the one shared navigation list and all existing
      session semantics. Verify the header/control composition manually at 320 px, 360 px, and desktop widths in
      Korean and English, in both effective themes, with no clipping or horizontal page scroll.
- [ ] T009 Update the real-app test harness and route tests to install the theme provider and deterministic
      `matchMedia`/storage ports. Add integration coverage that `/login` and a representative authenticated route can
      select all three preferences; reload/navigation/logout/login preserve an explicit choice; System responds to
      an OS event; a storage event simulates another tab; theme changes leave locale and pathname/search/hash
      untouched; and the fake backend call log records no call caused by render or selection.
- [ ] T010 Update `frontend/src/app/styles/index.css` and `frontend/index.html` comments/metadata from “night only”
      to the shipped two-map preference contract. Keep components on semantic/functional tokens, add no full-page
      colour transition, and do not alter the fixed app-icon artwork. Audit all mapped foreground/background pairs
      at WCAG AA in both `day` and `night`, and exercise both DOM states so CSS `color-scheme`, the effective
      `data-theme`, and browser chrome metadata cannot drift.
- [ ] T011 Verify the complete FE surface: targeted theme/bootstrap/provider/selector/widget/router tests, then
      `pnpm --filter ./frontend test`, `pnpm build:web`, `pnpm lint`, `pnpm --filter ./frontend lint:fsd`,
      `pnpm lint:style`, and `pnpm lint:spec`. Walk A1–A14 in a running browser, including an actual reload with each
      stored mode and a second same-origin tab. Confirm the production build has no initial wrong-theme application
      frame and run `/code-review`.
- [ ] T012 Reflect only the now-shipped behavior into the SSOT: create `spec/policy/themes.md`; replace the “no
