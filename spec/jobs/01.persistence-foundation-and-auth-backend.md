## Acceptance Criteria (from plan/01.accounts-and-login)

<!-- Plan 01 criteria owned by this job (plan AC numbers in parentheses). AC 9 and the devtools half of AC 4 belong to job 02. -->

- [ ] A1 (plan AC1) Any RPC other than `Login`/health called without a session returns `Unauthenticated` (HTTP 401); the same call with a valid cookie succeeds.
- [ ] A2 (plan AC2) Altering a single character of the `pp_session` value yields 401 (the hashed lookup misses).
- [ ] A3 (plan AC3) Login failure for an unknown id and for a known id with the wrong password return byte-identical error messages and codes, and the unknown-id path performs a real argon2id verification (asserted by a unit test on the dummy path).
- [ ] A4 (plan AC4, server half) No response body, log line, or URL ever contains the session token; it travels only in the `Set-Cookie` / `Cookie` headers.
- [ ] A5 (plan AC5) There is no signup RPC or screen; an account created with `adduser` can log in; a duplicate id is refused with a clear message.
- [ ] A6 (plan AC6) After `Logout`, replaying the previous cookie yields 401 (server-side revocation, not just cookie clearing).
- [ ] A7 (plan AC7) A session expires 30 days after login on both ends: cookie `Max-Age=2592000` and `sessions.expires_at`.
- [ ] A8 (plan AC8) A deliberately failing migration makes the api process exit non-zero before it serves; `/health` never turns green ([I7]).
- [ ] A9 (plan AC10) The Set-Cookie header carries exactly `HttpOnly; Secure; SameSite=Lax; Path=/` and `Max-Age=2592000`, and no `Domain`.
- [ ] A10 (derived) `docker compose run --rm api adduser <id>` works against the production image unchanged (`ENTRYPOINT ["/api"]` dispatches the `adduser` subcommand); `go run ./cmd/adduser <id>` does the same on a host.
- [ ] A11 (derived) The api opens SQLite in WAL mode with exactly one write connection; `go test ./...` runs in CI.
