## Acceptance Criteria (from plan/12.automated-naver-publishing-through-a-pai)

<!-- The source spec's acceptance criteria. After building, verify each is true in the running code. -->

- [ ] A1 A user can pair two different postpilot accounts on one Mac; each stores a distinct token in Keychain, owns a distinct browser profile and job directory, sees only its account's jobs, and publishes through the Naver identity verified for that connection. Revoking one leaves the other usable and the revoked token immediately fails.
- [ ] A2 The Mac exposes no public listener: its setup UI binds loopback only and work arrives through outbound authenticated polling. Turning the Mac off leaves a confirmed job durably queued; starting its LaunchAgent later claims it and proceeds without another phone action.
- [x] A3 In 글 완성, `내보내기` is unchanged and a separate `발행하기` section follows it. No other lifecycle step renders the panel. Opening/rendering it performs no publication; only the explicitly confirmed `네이버에 발행` action does.
- [x] A4 `StartPublish` rejects an unfinalized post, stale `expected_content_revision`, foreign/revoked agent, stale/foreign category, second nonterminal job, and a post already successfully published to Naver. Finalization and voice learning behavior are unchanged.
- [x] A5 A successful request freezes the exact finalized protojson, category, visibility, tags and ordered image set. A later post edit/delete cannot alter the job, and every staged object is the existing converted JPEG copied inside R2 without entering or being decoded by the API process.
- [ ] A6 Given a finalized fixture containing every block type and eight photos, the paired Mac publishes one Naver post whose title, plain-text block order, eight JPEG positions, captions, tags, category and visibility match the frozen manifest, then stores and renders the verified Naver URL.
- [x] A7 Agent/job progress survives phone reloads and Mac/VPS reconnects. A lease lost before `committing` safely requeues; stale lease/progress tokens cannot update a newer attempt or regress its stage.
- [ ] A8 Immediately before the deterministic publisher activates the final Naver publish control, the server has durably recorded `committing`. Any crash/timeout/disconnect from that point until verified URL capture becomes `outcome_unknown` and is never automatically retried. Reproducing this fault never creates a second post through the system.
- [ ] A9 Expired Naver login, CAPTCHA, 2FA or account mismatch becomes `needs_attention`; the agent neither bypasses the challenge nor sends Naver credentials/cookies/CDP/profile data to the VPS. After local repair, an explicit safe retry before commit can finish the same job.
- [ ] A10 The deterministic publisher reads only the validated local manifest and current staged assets, treats every manifest string as inert data, and is blocked from navigating outside the allowed Naver editor/login hosts. The server cannot supply selectors, JavaScript, coordinates, keystroke scripts, or action sequences. Missing or ambiguous controls/assets, a target or identity mismatch, or an unknown editor signature fails closed before commit.
- [x] A11 On terminal completion/cancel, staged R2 objects and sensitive manifest content are purged while job metadata, normalized error, selected settings and published URL remain. The orphan sweep removes partial copies left by a killed staging operation and never deletes a live job asset.
- [x] A12 The first version has no schedule control and sends no Web Push/email/chat notification. The in-app panel alone shows live status and actionable failure text.
- [x] A13 Existing Naver/Tistory/site/Markdown conversion snapshots and clipboard behavior remain unchanged; disabling or never pairing the Mac agent leaves postpilot fully usable as the copy-only product it is today.
- [ ] A14 Setup installs or verifies a signed, versioned Postpilot Naver driver and supported Chromium/CDP surface, runs the non-publishing compatibility probe against the exact dedicated profile, and refuses to arm the connection unless target binding, account/category discovery, editor signature, semantic locators and readback capabilities match.
