# Job 07: Generation Job Queue (new)

> Implementation work doc. Source spec: [plan/05.generation-job-queue](../plan/05.generation-job-queue.md).
> /implement-job 07 builds it via the two checklists below. When done, reflect the result into the
> SSOT (plan/policy/tech) and set status: done. Write it in English.
>
> Whole of plan 05 in one full-stack job: the `generation_jobs` record, the in-process worker, the boot sweep,
> `GetGeneration`, `Post.active_job`, and the frontend polling hook + progress UI. No job *kind* ships here — the
> handlers arrive with jobs 08 (`analyze_voice`), 10 (`generate`) and 12 (`revise`); this job verifies the queue with a
> fake handler. Requires jobs 01–03 (users, posts).

## Acceptance Criteria (from plan/05.generation-job-queue)

<!-- Criteria whose wording depends on job kinds that land later are refined to what is checkable here; the original check is re-run by the kind's job. -->

- [x] A1 (refined from plan AC1) `Enqueue` returns a job id without running the handler synchronously — a fake handler that blocks proves the caller returns first. (`StartGeneration` latency is re-verified in job 10.)
- [x] A2 (refined from plan AC2) `GetGeneration` reflects `stage`, `progress_done`, `progress_total` exactly as written through the handler's `progress()` callback, and `status` transitions `queued → running → done | failed` (fake handler test). The `observe`/`write` stage names arrive with job 10.
- [x] A3 (refined from plan AC3) Reopening a post with a non-terminal job shows `Post.active_job`; the editor resumes polling from it; when the job reaches `done` the post query is invalidated (fake handler with a delay).
- [x] A4 Killing the API process while a job is `running` and restarting it leaves the job `failed` with the restart reason; the UI shows the reason and a retry affordance (`onRetry` callback, wired by the kinds' jobs).
- [x] A5 The client polls at 2 s intervals while the job is non-terminal and issues no further `GetGeneration` calls after `done`/`failed` (network-tab evidence + fake-timer test).
- [x] A6 `GetGeneration` for another user's job → 403; unknown id → 404.
- [x] A7 Starting a second job for a post that already has a non-terminal job is refused with `FailedPrecondition` carrying the active job id (`Enqueue` guard; same for a second `analyze_voice` per user).
- [x] A8 A handler error becomes `failed` with a non-empty user-facing `error`; a provider quota error preserves the provider's message (a handler returning `llm.ProviderError` from a stubbed 429 yields a job error containing that message).
- [x] A9 Progress writes never occur inside a transaction that spans a provider call (asserted by the handler test harness: a concurrent write succeeds while a handler is mid-flight).
- [x] A10 `ListPosts` marks posts with an active job as generating (badge), derived from the job context's published behavior (`ActiveFor`), not from a cross-context table read.
- [x] A11 (derived) A handler panic is recovered into `failed` with a generic reason and the worker keeps running.
