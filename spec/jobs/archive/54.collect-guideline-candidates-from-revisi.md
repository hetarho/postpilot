## Acceptance Criteria (from changes/26.collect-guideline-candidates-from-revisi)

<!-- The source spec's acceptance criteria. After building, verify each is true in the running code. -->

- [x] A1 Running a revision to completion records one pending candidate holding the instruction **verbatim**, with the source post and the timestamp. A failed or cancelled revision records none.
- [x] A2 Running a revision with the identical instruction again creates no second row: the existing candidate's occurrence count becomes 2 and its last-seen advances. The 후보 section shows the count.
- [x] A3 An instruction that already exists as a saved guideline, or as an `approved` or `dismissed` candidate, records nothing and revives nothing.
- [x] A4 No candidate — pending, approved or dismissed — appears in any write or revise prompt, and a pending candidate changes no generated output. An account with candidates but no new guidelines produces prompts byte-identical to the same account before this change.
- [x] A5 Approving a candidate opens the scope control with 전역 preselected, and saving creates a guideline through the standard RPC with exactly the chosen scope. The candidate becomes `approved` and leaves the 후보 section.
- [x] A6 무시 marks the candidate `dismissed` and removes it from the section; the same instruction from a later revision does not reappear.
- [x] A7 A candidate longer than the guideline text bound opens for editing with the live remaining count, and approving it unedited is refused by the server's existing bound contract — never silently truncated. Recording it was not refused.
- [x] A8 Approving past the account guideline cap is refused with the existing `FailedPrecondition` naming the cap; the candidate stays pending.
- [x] A9 With `GUIDELINE_CANDIDATE_MAX_PENDING` pending candidates, a completed revision still completes normally, records nothing, and the section states that the queue is full. Approving or dismissing one resumes recording.
- [x] A10 `지침으로 저장` after a completed revision behaves exactly as before, and the saved instruction never afterwards appears as a pending candidate.
- [x] A11 Deleting the source post leaves the candidate listed with its text and no link; deleting a saved guideline neither revives nor resets its approved candidate.
- [x] A12 No revision, candidate list, approval or dismissal makes a provider call or enqueues a job, and no candidate text is read or written by a model anywhere in the flow.
- [x] A13 After migration `0023`, an existing account's 후보 section is empty, no past revision is reconstructed, and every existing guideline, scope and prompt is unchanged.

### Phase 1 — config, contract, schema

- [x] T001 `backend/internal/platform/config`: add `GUIDELINE_CANDIDATE_MAX_PENDING` (default `50`) as a typed env
      value beside the two guideline ceilings, non-positive/malformed = boot-fatal, and extend

      **backend-only** — the frontend never predicts the cap, it relays the refusal (as it already does for
      `GUIDELINE_MAX_PER_ACCOUNT`).
- [x] T002 (gen) `proto/postpilot/v1/guideline.proto`:
      - `GuidelineCandidate {id, text, post_slug, occurrences, first_seen_at, last_seen_at}` — no scope field, by
        design: a candidate carries none, and the scope is chosen at approval.
      - `ListGuidelineCandidates` returns the **pending** ones in review order (occurrences desc, then last_seen
        desc) plus `queue_full`, so the screen can say why nothing new is arriving without the client owning the cap.
      - `DismissGuidelineCandidate {id}`.
      - `CreateGuidelineRequest` gains `optional string from_candidate_id`. See T005 for why the create — not a
        separate Approve RPC — is the approval path.
      Then `pnpm gen:proto`.
- [x] T003 (migrate) `backend/internal/platform/db/migrations/0023_guideline_candidates.sql` — **confirm 0023 is
      still free first** (0022 is job 53's). One new table, so goose's own transaction is enough; no table is
      rebuilt and no composite FK is added to an existing parent, unlike 0009/0011/0022.
      ```
      CREATE TABLE guideline_candidates (
          id         TEXT PRIMARY KEY,
          user_id    TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
          text       TEXT NOT NULL,
          post_slug  TEXT,                    -- nullable: the source post may be deleted
          status     TEXT NOT NULL CHECK (status IN ('pending','approved','dismissed')),
          occurrences   INTEGER NOT NULL DEFAULT 1,
          first_seen_at TEXT NOT NULL,
          last_seen_at  TEXT NOT NULL,
          UNIQUE (user_id, text)
      );
      CREATE INDEX idx_guideline_candidates_review ON guideline_candidates(user_id, status, occurrences DESC, last_seen_at DESC);
      ```
      `UNIQUE (user_id, text)` is what makes deduplication a constraint rather than a service check two concurrent
      recordings could both pass — the same reasoning `guidelines(user_id, text)` already carries. `post_slug` is a
      plain nullable column with **no** foreign key: deleting the post must leave the candidate's text intact
      (change 26's lifecycle), and an FK with `SET NULL` would be the only way to keep that, which is more machinery
      than a column the reader treats as optional. It seeds nothing and backfills nothing — no revision history
      exists to reconstruct. Write the down.

### Phase 2 — the candidate aggregate (BE, inside the guideline context)

- [x] T004 `backend/internal/guideline/candidate.go` (+ `types.go`): the `Candidate` aggregate, its `Status`, and
      the sentinels. It belongs to the **guideline context**, not a new one: a candidate has no lifecycle of its own
      apart from becoming a guideline, and `/guidelines` is the only screen that reads it (ARCHITECTURE §2.3 — an
      entity with its own lifecycle is its own aggregate; this one's lifecycle is the guideline's).
      The recording rule lives here as a pure decision: **record**, **count** (an existing candidate in any state),
      or **skip** (the text is already a guideline, or the pending queue is full).
- [x] T005 `backend/internal/guideline/service.go`:
      - `RecordCandidate(ctx, userID, postSlug, instruction)` — trims, refuses blank, and stores **verbatim** at the
        REVISION bound (500), not the guideline bound (300). Change 26's reasoning: refusing a long instruction at
        recording time would lose exactly the most specific corrections; the 300 bound is enforced at approval,
        where the user can shorten it with a live counter.
      - `ListCandidates` / `DismissCandidate`.
      - `Create` gains the approval side effect: in the SAME transaction as the insert it marks approved (a) the
        candidate named by `from_candidate_id` when present, and (b) any candidate whose trimmed text equals the
        saved text. (b) is what makes `지침으로 저장` mark the candidate the just-completed revision recorded
        without the client having to learn its id; (a) is for approving a candidate the user EDITED first, whose
        text no longer matches. A separate Approve RPC was considered and rejected: it would duplicate every field
        rule and every refusal the create already owns.
- [x] T006 `backend/internal/guideline/store/queries/guidelines.sql` + `store/store.go` (+ `sqlc generate`).
      **ASCII only in the query file** — the header says why: sqlc slices statements by byte offset and counts in
      runes, so one multi-byte character rotates every query after it.
      - `InsertCandidate` / `BumpCandidate` (occurrences + 1, last_seen) / `CountPendingCandidates` /
        `CandidateByText` / `ListPendingCandidates` / `SetCandidateStatus` / `DropCandidatePostSlug`.
      - Recording is ONE transaction: read by text → bump or (count pending → insert). The cap and the dedupe are
        both inside it, so two concurrent recordings cannot both pass either.
      - `ApproveCandidateByID` and `ApproveCandidateByText` join the existing `Insert` transaction.
- [x] T007 `backend/internal/guideline/rpc/handler.go`: the two new procedures, `from_candidate_id` on the create,

## Review

- [x] `/code-review` applied (rejections noted with reason) · for non-trivial logic, `/codex:review --background`

Both reviews ran (`/code-review` at `high`, and Codex `gpt-5.5` on the same diff) and converged on
the same defects. All findings were applied; none was rejected.

| Finding | Fix |
|---|---|
| Post deletion detached the candidate link BEFORE the blob and row deletes, so a delete that failed afterwards left a candidate saying its post was gone while the post survived — and nothing ever re-links it. | Moved the detach after `store.DeletePost` succeeds, and made its failure log-and-continue: a dead link is not worth failing the delete the user asked for. `TestDeletePostSucceedsWhenTheDetachFails`. |
| `SetCandidateStatus` had no `status = 'pending'` guard on the by-id path (the by-text sibling had one), so a stale tab could approve one candidate twice or dismiss one already approved. | Guard in the query. A terminal candidate now reads as not-found, which rolls the create back. `TestARuledOnCandidateCannotBeMovedAgain`. |
| `Update` did not reconcile a candidate with the same text, unlike `Create`: renaming a guideline onto a pending candidate's text left that candidate permanently un-approvable (its create would be a duplicate) with a rising count. | A guideline text edit now runs the same approval inside its own transaction. `TestUpdateGuidelineTextApprovesASameTextCandidate`. |
| Approving into an already-saved text closed the dialog silently and left the row pending with a stale cache. | The dialog stays open with `candidate.approveDuplicate` and re-reads the candidate list — the usual cause is another tab having saved it, which also approved this row. |
| `ErrCandidateTextInvalid` -> `GUIDELINE_TEXT_REQUIRED` was a dead mapping: recording has no RPC entry point. | Mapping and its test row removed. |

Codex additionally flagged that an EDITED `지침으로 저장` (the pre-existing revision dialog) does
not approve the candidate the same revision recorded, because it sends no `from_candidate_id`.
**Not a defect of this change, and deliberately unfixed:** change 26 scopes that dialog as
*unchanged*, and its A10 asks only that the SAVED instruction never appear as a candidate, which
the by-text approval satisfies. An edited save is a different rule from the one recorded, so the
original correction is still a real pending candidate — which is the accrual this change exists
to produce.
