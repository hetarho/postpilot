## Implementation Checklist

- [x] T001 (**decided: 24.18.0, not the recommended 22.** The deciding fact is A4: Node 22 is not installed on this
      machine and `fnm list` shows only `v24.18.0 lts-latest, default`, so pinning 22 would have meant pinning a
      version this job could not run the gate against — which is the very "environments that never agree" the
      finding is about. 24.18.0 is fnm's `lts-latest`, is what the developer actually runs, and the full gate was
      executed on it. The exact patch is pinned rather than the major, matching how `packageManager` pins pnpm
      exactly; `actions/setup-node@v4` accepts an exact semver in `node-version-file`. **This does move CI from 22
      to 24** — that realignment is the point of R008, not a side effect.) Choose the pinned version, and say why in one line. The facts: `package.json:40` declares
      `"engines": { "node": ">=20" }`; CI runs Node 22 (`ci.yml:18`); the machine this review ran on had Node
      24.18.0. Three environments, no agreement. **Node 22 is the conservative choice** — it is what CI has been
      validating all along, so pinning it changes nothing about what has been proven. Pinning 24 is defensible too,
      but then A4 is doing real work rather than confirming the status quo, so run the full gate before committing
      to it.
- [x] T002 Add the pin file. `.node-version` is the widest-supported form (fnm, nvm ≥0.39 via `--use-node-version`,
      Volta-adjacent tooling, and `actions/setup-node`'s `node-version-file`); `mise.toml` is the alternative if
      the project wants pnpm pinned in the same file. Pick one and do not add both — two pins that can disagree is
      the problem this finding is about, not the solution.
- [x] T003 `package.json` — raise `engines.node` to the pinned major (`>=22`, or `>=24` per T001). `>=20` accepts
      three majors with different loader, fetch and test-runner behaviour, which for Vite 8 / rolldown and vitest 4
      is the kind of difference that shows up as a build or test difference rather than a warning. Leave

- [x] T004 `.github/workflows/ci.yml:16-19` — replace `node-version: 22` with `node-version-file: .node-version`

## Review

- [x] `/code-review` applied (rejections noted with reason) · for non-trivial logic, `/codex:review --background`

**A pre-existing flaky test, surfaced by A4 and fixed here.** `PostsPage > lists the posts the server returned, in
that order` failed on roughly half of full-suite runs (`Unable to find role="link"`, at ~1.5 s) while passing 5/5 in
isolation. It is **not** caused by this work: a worktree at `335363a` — before job 27 — failed it in 2 of 3 full-suite
runs. Cause: testing-library's default `asyncUtilTimeout` is 1 s, and a page-level `findBy*` can exceed that from
scheduling pressure alone when 72 files run in parallel. Fix: `configure({ asyncUtilTimeout: 5_000 })` in the shared
`src/test/setup.ts`. Only the deadline moves — every assertion stays as strict, and a genuinely broken query still
fails, just later. Four consecutive full-suite runs then passed 398/398. This is recorded rather than folded in
silently because review 01's gate table reports the suite as `PASSED`, which was a lucky run: **the suite was never
reliably green.**

**`/code-review` — one finding applied, one rejected.** *Applied:* `.node-version` was untracked, so committing
`ci.yml` without it would make `actions/setup-node@v4` fail on a clean checkout; it is staged with this change.
*Rejected (and the premise corrected):* the reviewer re-raised the `PUBLISH_AGENT_HEARTBEAT_INTERVAL` ceiling from
job 27, this time claiming a stale agent **blocks publishing**. It does not. `offline`
(`PublishPostForm.tsx:61-63`) is consumed at exactly one place, `:97`, where it renders an informational `Notice`
saying the request is stored server-side and starts when the agent comes up; the publish button's `disabled` at
`:175` depends on `finalized`, `effectiveCategoryId` and `preparing` only. The consequence of a misconfigured
interval is a reassuring notice shown when it need not be — cosmetic, and *less* severe than job 27's rejection
already assumed. That rejection stands.

**codex (`gpt-5.5`, read-only) — no findings.** It confirmed against GitHub's documentation that
`actions/setup-node@v4` accepts `.node-version` with an exact semver patch, that the lockfile already contains
packages declaring `>=24` engine ranges, and that the reworded CI header is now true. It flagged one real
consequence, not a defect: `engines.node: >=24` will refuse `pnpm install` for a contributor still on 22 or 23 —
which is the intended meaning of a floor, and the reason the pin file ships beside it.
