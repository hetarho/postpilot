## Acceptance Criteria (from plan/02.post-drafting-and-list)

<!-- Plan 02 criteria owned by this job (plan AC numbers in parentheses). AC 1, 2, 4, 11 and the browser halves of 3, 5, 6 belong to jobs 04/05. -->

- [x] A1 (plan AC3, server half) `ConfirmUpload` creates the `images` row only after a HEAD finds the object; the row records `filename`, `r2_key = posts/{slug}/{image_id}.jpg`, client-supplied `width`/`height` and the HEAD `bytes`.
- [x] A2 (plan AC5, server half) No RPC accepts image bytes; `CreateUpload` returns a presigned PUT URL on the R2 host, so the API never relays a photo.
- [x] A3 (plan AC6) Deleting a photo removes the `images` row and the R2 object (a subsequent HEAD returns not-found).
- [x] A4 (plan AC7) An `uploads` row whose `ConfirmUpload` never arrives is removed, with its object, by the sweep after expiry.
- [x] A5 (plan AC8) A photo's URL is a presigned GET minted per `GetPost`; the same object requested without a signature is denied (bucket private).
- [x] A6 (plan AC9) `ListPosts` shows only the acting user's posts; `GetPost` on another user's slug → 403 (`PermissionDenied`); unknown slug → 404 (`NotFound`).
- [x] A7 (plan AC10) Two posts created the same day with the same title get slugs `…-title` and `…-title-2`; retitling does not change the slug.
- [x] A8 (derived) `CreateUpload` refuses a filename already attached to the post (`AlreadyExists`); filenames are unique per post.
- [x] A9 (derived) `SavePostDraft` with an empty slug creates the post and returns the minted slug; repeated saves with the slug are idempotent updates of `title`/`memo` and bump `updated_at`.
- [x] A10 (derived) The api refuses to boot when any `R2_*` variable is missing, with a message naming it.

## Deviations from the checklist (as built)

Each is reflected in [plan/02](../plan/02.post-drafting-and-list.md) and the two policy docs.

| Task | Wording | As built | Why |
|---|---|---|---|
| T002 | four `R2_*` vars | plus `R2_PUBLIC_ENDPOINT` (defaults to `R2_ENDPOINT`) and `MaxImageBytes` (10 MiB) | a SigV4 signature covers the Host header, so a URL signed for the endpoint the API dials is rejected when the browser sends it elsewhere — production leaves it unset. The size cap exists because a presigned PUT is a URL an authenticated client can use however it likes |
| T002 | `Load` errors when an `R2_*` is missing | `Config.RequireObjectStorage()`, called by the server before the listener | `api adduser` must work on a fresh box before a bucket exists. A10 still holds: the check runs before `/health` can answer |
| T003 | R2 for local dev | **MinIO in `docker-compose.yml`** | decided with the user. Same S3 API and the same four variables, so no Go code knows the difference; it made A2/A3/A4/A5 verifiable for real without a Cloudflare account |
| T004 | plan 02 schema | plus `UNIQUE(post_slug, filename)` on `uploads` | the service's precheck is a TOCTOU; the constraint is what actually stops two concurrent `CreateUpload` calls |
| T005 | one sqlc entry per context | plus `omit_unused_structs: true` on both | without it every generated package gets a struct for every table, so adding a table to one context rewrites another's generated code |
| T006 | `CreateUploadResponse{upload_id, put_url, expires_at}` | plus `content_type` | the content type is part of the signature, so the client has to be told exactly what to send |
| T009 | `CreateUpload` duplicate filename → `AlreadyExists` | only for a **confirmed** photo; a pending upload is **replaced** | a pending duplicate is the retry the plan asks for. Refusing would strand the user until the sweep ran, up to an hour |
| T009 | `ConfirmUpload` inserts the image, then deletes the upload row | **one transaction**, and idempotent on retry | see the review below — separable writes were a data-loss bug |
| T011 | sweep deletes expired uploads with their objects | never deletes an object an `images` row references | same bug |

## Review

Two reviews, merged: **8 findings applied, 1 rejected.** Each fix has a regression test.

- [x] `/code-review` (high) — 5 findings, all applied. The first three share one root cause: `ConfirmUpload` was not
      atomic, so an upload row could outlive its move.
  1. **Data loss.** The sweep deleted a *confirmed photo's* object whenever a stale uploads row still named it (a
     cancelled request context is enough). The photo row survived, so `GetPost` returned a URL that 404s — silent and
     permanent. Fixed at both ends: confirm is one transaction, and the sweep refuses to delete a key `images` uses.
  2. A confirm retry hit the images primary key and surfaced as a permanent `Internal` for a photo that uploaded
     fine. Confirm is now idempotent.
  3. `AllReferencedKeys` read the two tables separately, in the one order that can miss a key mid-handoff — the
     sweep would then delete a live photo. Now one read transaction.
  4. `FilenameTaken` was a TOCTOU and `uploads` had no uniqueness constraint.
  5. No server-side object-size limit; the 25 MB cap was browser-only.
- [x] Codex (`gpt-5.5`, xhigh) — 6 findings + 2 test issues. Three duplicated the above; **3 new, applied**:
  6. Slug minting was check-then-insert with no retry, so two concurrent first saves of the same title made one fail
     instead of taking the next serial.
  7. `ConfirmUpload` accepted any dimensions, including zero and negative.
  8. Two tests asserted the wrong thing: the duplicate-filename test never covered concurrency, and
     `TestImagesCascadeWithTheirPost` never deleted a post. Both rewritten (the second renamed to what it checks —
     nothing deletes a post, so the cascade half has no exercise yet).
- [x] **Rejected (1):** codex claimed the PUT URL is *not* bound to `image/jpeg`, on the theory that the SDK strips
      `Content-Type` from a nil-body presigned request. Disproved twice: the signed URL carries
      `X-Amz-SignedHeaders=content-type;host`, and a live PUT with `Content-Type: text/plain` to a URL signed for
      `image/jpeg` returns **403** against real MinIO.
- [x] Comment pass — the comments arguing for the reverted behaviors (best-effort upload-row delete, pending-upload
      duplicates) were rewritten to argue for what the code now does.
