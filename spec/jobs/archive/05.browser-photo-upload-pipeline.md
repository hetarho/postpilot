## Acceptance Criteria (from plan/02.post-drafting-and-list)

<!-- Plan 02 criteria owned by this job (plan AC numbers in parentheses). -->

- [x] A1 (plan AC2) Selecting an executable (or any non-listed extension) stores nothing and lists the file under "건너뜀" with a reason. — `filter.test.ts`, `upload-batch.test.ts` ("without touching the pipeline"), `EditorPage.test.tsx` ("lists a pick made only of skipped files without creating a post").
- [x] A2 (plan AC3, browser half) Eight iPhone HEIC photos all upload; each arrives in R2 as a JPEG with long edge ≤ 1024 px and appears in the editor's photo strip. — pipeline: `decodeImage` → `resizeToJpeg(…, 1024, 0.85)` → handshake; `resize.test.ts` (4032 → 1024), `upload-batch.test.ts`, `EditorPage.test.tsx` end-to-end with a stubbed decoder. **Not run against real iPhone HEICs on this box** (no sample files) — see Risk notes.
- [x] A3 (plan AC4) A file over 25 MB at selection is skipped with a reason; a 20 MB HEIC is accepted and uploads as a ~200 KB JPEG. — `filter.test.ts`; size of the output is the encoder's (q0.85 at 1024 px lands around 150–300 KB for a photo).
- [x] A4 (plan AC5, browser half) The PUT targets the R2 host, not `api.postpilot.*` (network tab); the API only sees `CreateUpload` / `ConfirmUpload`. — `put` is a plain `fetch(put_url)`; `EditorPage.test.tsx` asserts the PUT went to the storage origin and the API saw exactly `SavePostDraft, CreateUpload, ConfirmUpload`.
- [x] A5 (plan AC6, browser half) Deleting a photo from the strip calls `DeleteImage` and the photo disappears from the strip and from `GetPost`. — `EditorPage.test.tsx` ("deletes a photo from the strip through DeleteImage"); the cache patch mirrors the server (`usePostImagesCache.remove`).
- [x] A6 (plan AC11, photos half) Opening a post from the list restores its photos in the strip via `view_url`. — `EditorPage.test.tsx` ("restores its photos in the strip from their view URLs").
- [x] A7 (derived) Conversion progress is visible ("변환 중 n/m") and the UI stays responsive while eight files convert. — `UploadProgress`; HEIC decode runs in a Web Worker, conversions are capped at `UPLOAD_CONVERT_CONCURRENCY` (2).
- [x] A8 (derived) A failed PUT or an expired presigned URL leaves that photo in a `failed` state with a retry that restarts from `CreateUpload` with a fresh `upload_id`; other photos are unaffected. — `upload-batch.test.ts` ("retries from CreateUpload"). Refinement from review: a *lost confirm* retries `ConfirmUpload` with the same id (idempotent) instead, because starting over would be refused as a duplicate filename; `FailedPrecondition` (object missing) goes back to `CreateUpload`.
- [x] A9 (derived) A HEIC the device cannot decode lands on the skipped list with the reason; the rest proceed. — `upload-batch.test.ts` ("skips a file the decoder cannot read … carries on"); `heif-unsupported` (worker failed to come up) vs `unreadable` (the file) are distinguished.
- [x] A10 (derived) The WASM decoder is loaded lazily — the main bundle does not include it, and no WASM request happens unless a HEIC/HEIF file is selected. — `vite build`: libheif is only in `dist/assets/heif-worker-*.js` (1.46 MB), fetched when the worker is first constructed; main bundle 441 kB → 457 kB (+16 kB, the pipeline code itself). `decode.test.ts` proves only HEIC reaches the lazy module.
