## Acceptance Criteria (from plan/13.multilingual-interface-and-target-langua)

<!-- The source spec's acceptance criteria. After building, verify each is true in the running code. -->

- [ ] A1 With no stored override, `navigator.languages=['en-US','ko-KR']` yields English; `['ja-JP']` yields Korean. Selecting Korean/English persists `postpilot.locale`, survives reload, and changes no URL, session, or domain row.
- [ ] A2 Locale resolves before React paint; `<html lang>`, document title/description, dates, relative times, numbers, visible labels, and accessibility names all match it.
- [ ] A3 Every current route is operable in Korean and English at 360px and desktop widths. Catalog topology tests catch missing keys; app-owned prose does not remain scattered through components or backend messages.
- [ ] A4 An English UI opens `/posts/new` with target English; Korean opens it with Korean. The first create request always carries a concrete non-`UNSPECIFIED` value, and missing/unsupported values are rejected without server fallback.
- [ ] A5 Changing a post target from Korean to English preserves content bytes, observations, revisions, baseline, status, and finalization. Reload shows English target, Korean content provenance, and the explanatory mismatch hint.
- [ ] A6 Ordinary generation freezes the stored target. Changing target after enqueue cannot alter that job; success writes content and content-language provenance in the frozen language.
- [ ] A7 Otherwise-equal Korean- and English-target jobs build byte-identical observation requests with no target-language instruction, and changing only the stored target does not translate, clear, or invalidate existing observations.
- [ ] A8 Write A/B gives both candidates the same frozen target and appropriate voice projection, includes target in the input hash/detail, and applying a winner atomically establishes matching content-language provenance.
- [ ] A9 Revision after changing target preserves the existing content language through five revisions; its prompt never reads the newer target as output language.
- [ ] A10 Existing voices/posts migrate as Korean without changing current Korean content/profile/history. Contentless drafts have no content provenance; existing machine content has Korean provenance.
- [ ] A11 Creating an English-source voice requires explicit English; source language appears after reload and cannot be changed through any RPC. It receives only its own English evidence.
- [ ] A12 Same-language generation receives the complete voice projection. Cross-language prompt snapshots prove that only structure/axes remain and there are no excerpts, lexical/endings/syntax rules, or free-form guidance.
- [ ] A13 A finalized English-content post assigned to a Korean-source voice can be finalized, edited, exported, copied, and published, but learn/save-as-rule/feedback is rejected before event/job/provider creation with a localized explanation. The inverse behaves identically.
- [ ] A14 Korean analysis retains deterministic ending behavior. English analysis uses its language-specific prompt and word-length/register/contraction/cadence measurements; neither corpus includes a different-language post.
- [ ] A15 Connect validation/conflict failures and durable job/experiment failures render from stable reason+params in both locales. Unknown reasons show a localized generic fallback; arbitrary raw backend text is never the sole message.
- [ ] A16 Locale selection, language-option saves, voice/list/profile reads, page mount, copy, export, and finalization make no provider call and enqueue no language-related job.
- [ ] A17 Proto/sql generation, migration integrity/backfill tests, prompt/payload/snapshot tests, backend vet/build/tests, frontend tests/lint/FSD/style/build, and spec lint pass without weakening existing Korean assertions.
