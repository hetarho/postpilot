## Acceptance Criteria (from code-review/01)

- [ ] A1 An executable Node pin exists at the repo root and names one version. A contributor whose tool reads it
      (`nvm`, `fnm`, `mise`, `asdf`, Volta — pick per what the file supports) lands on that version without being
      told.
- [ ] A2 `.github/workflows/ci.yml` derives its Node version from that pin rather than hardcoding
      `node-version: 22`, the way the Go jobs already derive theirs from `go-version-file: backend/go.mod`.
- [ ] A3 `engines.node` in the root `package.json` states the same major as the pin, not a floor three majors below
      it.
- [ ] A4 The full gate passes on the pinned version — lint, FSD lint, style, spec, tests, and `pnpm build:web`.
      If the pinned version differs from what the tree was last built on, that is exactly what this criterion is
      for.
- [ ] A5 `ci.yml`'s header describes the triggers the file actually declares. No present-tense claim about a
      `develop` branch that neither exists nor appears in `on:`.
- [ ] A6 Running the agent's Python test suite leaves `git status` clean.
- [ ] A7 No behavior change to any application code.

## Implementation Checklist

- [ ] T001 Choose the pinned version, and say why in one line. The facts: `package.json:40` declares
      `"engines": { "node": ">=20" }`; CI runs Node 22 (`ci.yml:18`); the machine this review ran on had Node
      24.18.0. Three environments, no agreement. **Node 22 is the conservative choice** — it is what CI has been
      validating all along, so pinning it changes nothing about what has been proven. Pinning 24 is defensible too,
      but then A4 is doing real work rather than confirming the status quo, so run the full gate before committing
      to it.
- [ ] T002 Add the pin file. `.node-version` is the widest-supported form (fnm, nvm ≥0.39 via `--use-node-version`,
      Volta-adjacent tooling, and `actions/setup-node`'s `node-version-file`); `mise.toml` is the alternative if
      the project wants pnpm pinned in the same file. Pick one and do not add both — two pins that can disagree is
      the problem this finding is about, not the solution.
- [ ] T003 `package.json` — raise `engines.node` to the pinned major (`>=22`, or `>=24` per T001). `>=20` accepts
      three majors with different loader, fetch and test-runner behaviour, which for Vite 8 / rolldown and vitest 4
      is the kind of difference that shows up as a build or test difference rather than a warning. Leave
      `packageManager: pnpm@10.30.3` as it is — pnpm is already pinned exactly and CI reads it via
      `pnpm/action-setup`.
- [ ] T004 `.github/workflows/ci.yml:16-19` — replace `node-version: 22` with `node-version-file: .node-version`
      (or the `mise` equivalent). This is the same pattern the two Go jobs already use with `go-version-file`, so
      the workflow ends up consistent with itself.
- [ ] T005 Run the whole gate on the pinned version (A4): `pnpm install --frozen-lockfile`, `pnpm lint`,
      `pnpm --filter ./frontend lint:fsd`, `pnpm lint:style`, `pnpm lint:spec`, `pnpm --filter ./frontend test`,
      `pnpm build:web`. Report what passed. If a version change breaks something, that break belongs to this job —
      do not pin around it.
- [ ] T006 `.github/workflows/ci.yml:1-3` — rewrite the header (A5). It currently reads *"Runs on PRs (merge gate)
      AND on direct pushes to develop/main"*, but `on:` declares `pull_request: branches: [main]` and
      `push: branches: [main]`, and `git branch -a` shows only `main`. Match [DEPLOY.md](../../DEPLOY.md) line 29,
      which frames the same fact correctly for the deploy workflow: main only today, `develop` a one-line addition
      when the branch exists. Do **not** add a `develop` trigger — the dormancy is deliberate and documented.
- [ ] T007 `.gitignore` — add `__pycache__/` and `*.pyc`. Evidence: running `python3 -m unittest
      hermes/postpilot-publisher/test_plugin.py` from `agent/` — the exact command `ci.yml:52` runs — leaves
      `?? agent/hermes/postpilot-publisher/__pycache__/` in `git status`. The file already covers `node_modules/`,
      `dist/`, `.env`, `*.log`, `backend/bin|tmp|data/` and `*.exe`; Python is the one runtime with no entry.
- [ ] T008 Verify A6 directly: run the Python suite, then `git status --porcelain`, and confirm nothing is listed.
- [ ] T009 Confirm A7 — `git diff --stat` shows changes only to `package.json`, `.node-version` (new),
      `.gitignore` and `.github/workflows/ci.yml`. No file under `backend/`, `frontend/src/`, `agent/` or `proto/`.
