## Acceptance Criteria (from plan/09.stage-model-experiments-and-leaderboards)

<!-- The source spec's acceptance criteria. After building, verify each is true in the running code. -->

- [x] A1 A fresh account has no active or A/B selections and generation is blocked; nothing applies the recommendation automatically. Pressing `추천 조합 적용` stores the complete versioned set atomically, and reload shows it.
- [x] A2 The shipped set contains the six pinned model ids in the table above. Apply is rejected without partial writes when any ref is missing, disabled, duplicated in a pair, or unsuitable for its stage.
- [x] A3 Starting normal generation returns `job_id` and `experiment_id` before any provider call. With photos, exactly one observe pipeline runs and both write calls receive byte-identical prompt/schema snapshots except for model ref.
- [x] A4 While the job is active the post list shows `AI 생성 중`; after two candidates finish it shows `AI 결과 확인`. Closing/reopening the browser at either point resumes polling/review from server state.
- [x] A5 Before a verdict, `GetExperiment` contains opaque candidate ids/sides and outputs but no model refs or labels. Left/right assignment is server-randomized, stable across reloads, and revealed only after decision/dismissal.
- [x] A6 Choosing a write candidate records one verdict, applies exactly that validated `PostContent`, moves the post to `review`, and removes the pending-result badge. Repeating the apply RPC is idempotent.
- [x] A7 A write candidate is never persisted as canonical merely because the job finished. If winner application fails, the verdict remains with a visible retry and the previous post content/status is preserved.
- [x] A8 An observe experiment sends the same ordered photo snapshot to two vision models, writes neither result during the run, and renders aligned per-photo fields. Its winner may be explicitly applied to the source post and/or adopted as active observe model.
- [x] A9 An analyze experiment sends the same complete corpus snapshot to both models and changes neither profile nor rules during the run. Applying its winner requires confirmation, replaces `styleguide`, and never changes `rules`.
- [x] A10 If one candidate fails, the successful result remains, the list/review shows a partial state, and retry invokes only the failed model with the original snapshot. `Use single` may apply the survivor but creates no win/loss.
- [x] A11 Starting another write experiment for a post with an active or undecided experiment is refused with the existing id. A changed/deleted snapshot that cannot be fairly retried produces the fixed "새 비교" reason.
- [x] A12 Choosing "둘 다 사용하지 않기" dismisses the experiment and does not change either model's match count/rating.
- [x] A13 Leaderboards are isolated by account and stage. A decided winner changes exactly two entries; ratings replay in decision order from 1500/K=32, and entries under three matches are marked provisional.
- [x] A14 Candidate usage stores prompt/completion tokens, latency and reported `usage.cost` when present. When absent, a catalog-price estimate is marked with `≈`; unavailable data is not silently treated as zero.
- [x] A15 A removed model remains legible in history/leaderboard from its snapshotted label but cannot start/retry/apply as an active selection. Provider capability checks still happen before network calls.
- [x] A16 Another user cannot read, decide, retry, apply or list an experiment; raw model identities are not discoverable in a pre-verdict network response.
- [x] A17 On desktop candidates render side by side; on phone the A/B switch preserves each candidate's scroll position and the choice controls remain at least 44px. All three stage output shapes are readable without horizontal prose.
- [x] A18 Thirty days after a terminal verdict/dismissal the payload/output is purged while leaderboard counts, usage and model labels remain. Post deletion purges related payload immediately; account deletion removes everything.
